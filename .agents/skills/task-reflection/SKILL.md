# 任务反思回写

把一次任务里得到的可复用知识整理成回写建议，经开发者批准后写回它所属的真相源，让下一个 Agent 不再踩同一个坑。建议随主任务交付一起展示，不阻塞主任务；没有值得写的内容时不硬凑。

## 触发与类别

- **踩坑**：意外失败、绕路或误判，实际行为与规范、文档或原先的预期不一致，并且查明了原因。
- **用户纠正**：用户指出已有规范未被遵守（例如某组件的滚动条没按 UI 规范实现），或纠正 Agent 的做法。
- **新规范**：用户提出新的规范、偏好或取舍。
- **规范缺陷**：发现规范缺失、过时或互相矛盾。
- **工作流损耗**：某一步费时、费 token、返工、反复重试或等待，或者手工重复了可以自动化、缓存、并行、换便宜模型的事。

## 工作流损耗：先量，再提

损耗建议要带数字，没有数字的只算猜测。数字取自 Task 记录、命令的实际耗时、子代理与外部审查的用时和条数、重跑次数。每条写清：现象与数字、原因、建议（改规则、加工具、换做法、换模型）、预计节省、代价。例：“omp 审查三次因额度退出，前后多花约 1.5 小时；改为额度不足时直接用 openai-codex 续跑、它也限额再用 `@default`。”

用户要求复盘时，按以上类别整理本次任务。只对当前任务有效的一次性指令（“这次先别跑测试”）不回写。

## 判断是否值得提出

- 只提廉价环境查询得不到的知识：约定、决策原因、易错点、判据与边界。
- **通用**：条目要能拦截“同类但不同具体位置或属性”的下一次问题，而不是只把主语从具体组件换成泛称、内容仍是当次改动的具体类名、变量组合或修补步骤。从本次事件抽象出背后的通用原则或自检判据（例如从“某卡片与下拉框激活边框不一致”抽象为“同类交互状态复用同一状态基座或 token，不各自手写近似样式”）；组件名、类名、像素值和当次参数只在说明判据必需时作例子。只对某个组件或当次具体实现成立的内容写进它的同名 `.md`，不进全局规范。
- **先查重**：拟写入前在目标文件和相近规范里搜同义规则。已有规则覆盖时不提；只是不够清楚时改写原条目，不另开小节。
- 用户纠正时先修正实现；修正实现属于当前任务，不需要等批准。规范已写清楚而只是没被遵守的，不追加条目。
- 新规范与已有条目冲突时，建议替换旧条目，不并列保留两个版本。
- 推断标为推断；未验证的现象不能写成判据。

## 写法

每条一到两句，写成“在什么情况下，做什么（为什么）”，能准确表达即可。不写修饰和比喻，不用强调词代替判据。

- 不写：“Slider 轨道用 `flex-1 min-w-[140px]`，档位标签 `w-[64px] shrink-0`，确保滑轨纹丝不动。”
- 写：“与弹性元素同行、内容会变化的文字给固定宽度且不收缩，避免内容变化推动相邻元素。”并先确认它是否已被现有的零布局位移条目覆盖。

## 目标位置

| 类别 | 通常写到 |
|---|---|
| 踩坑 | 对应规范、Skill 或模块文档；UI 类按 [UI 开发](../ui-development/SKILL.md#反思回写) 的分工 |
| 用户纠正 | 先修正当前产出；规范写得不清楚时才改规范 |
| 新规范 | 它所属的规范、Skill；只对 Claude Code 有效的写用户级 `~/.claude/CLAUDE.md`，各工具通用的写 `~/.agent/AGENTS.md` |
| 规范缺陷 | 原规范所在位置，改写或删除旧条目 |
| 工作流损耗 | 小改动直接建议改规则或工具；要开发的建成 planned Task（经 `nbdev task new`），或写进对应 Work 的后续清单（例如 nbdev 的 w00022 `followups.md`） |

- 领域 Skill 或作用域 `AGENTS.md` 指定的回写位置优先，例如 [UI 开发](../ui-development/SKILL.md#反思回写)。
- 没有指定时，选该知识的现有真相源（见根 [`AGENTS.md`](../../../AGENTS.md) 的“文档真相源”与文件路由表），不新建平行文档。
- 优先改写或合并已有条目，再考虑追加；本次发现的过时或矛盾内容一并建议删除。
- 按 Work/Task 规则更新执行快照与证据不属于回写，不需要走本流程。

## 展示与批准

在主任务交付说明末尾用一张表列出建议，按类别排序：

| 编号 | 类别 | 依据 | 建议修改 | 目标位置 |
|---|---|---|---|---|
| 1 | 用户纠正 | <现象或用户原话> | 改写：<拟写入的原文> | <文件路径> 的 <小节名> |

- 依据写到开发者不回看过程也能判断的程度。
- 建议修改写明新增、改写或删除，并给出拟写入的原文。
- 子 Agent 不直接向开发者请求批准，把建议表随结果交给主 Agent 汇总展示。

开发者可以全部批准、按编号批准、修改后批准或拒绝。只写入明确批准的条目，写入内容与批准时展示的一致，含义有变化时重新展示；未获批准的建议不落盘，被拒绝的条目在同一会话中不再提出。开发者直接要求“把这条写进规范”时视为已批准，写入后说明写到了哪里。

## 完成条件

没有值得回写的内容时不列表，也不凑一段“反思”。批准的条目写入后，按 [验证门禁](../../../docs/testing/README.md#验证门禁) 检查链接与结构，并说明实际写入了哪些编号、写在哪里。进了 planned Task 或后续清单的条目，做完时改状态并链接改动。
