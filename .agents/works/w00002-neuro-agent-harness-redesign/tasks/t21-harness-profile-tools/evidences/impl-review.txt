### 1. 工具结果序列化在受控写队列之外抛错，运行假成功并永久丢失配对结果

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-harness/src/harness.ts:191-212`（尤其 198 行）；`node_modules/@oh-my-pi/pi-agent-core/src/agent.ts:1868-1883`。
- **现象**：工具返回合法 `AgentToolResult`，但 `details` 含循环引用或 BigInt 时，`toJson(message)` 在调用 `enqueue` 之前同步抛错。OMP 的事件派发捕获并记录订阅异常，harness 的 `localError` 没有被设置。收尾工具已经 terminal abort，最终返回 `{stopReason:"stop", finish:null, error:null}`，日志只有 user、assistant 调用和 usage，没有对应 toolResult；关闭也不补结果。
- **为什么是问题**：工具结构化 details 是公开扩展面；Spec 输出 8、10、16 和计划第 15 行要求不能序列化时以 `local` 失败，不能静默丢。这里把已停止且丢失提交的运行报成成功；恢复后工具调用不成对。base 没有原样消息与 finished 合同，本项是新落盘路径的问题，不重复 base 的文字日志问题。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-impl/lab/runtime.ts`，`nonserializable-finish` 经公开 `createHarness → turn → 真实 OMP Agent`，收尾工具 `details.self = details`；实测模型请求 **1 次**，返回 `stop`、无 error，日志 **4 条**（snapshot、user、assistant、usage），工具结果 **0 条**。对照 `finish-write-failure`：append 真正 reject 会正确返回 `error/local`，说明缺口在入队前的序列化而非磁盘错误处理。
- **建议改法**：把事件消息的 JSON 校验和序列化纳入写入的同一受控失败路径，失败时设置本次 `localError` 并停止继续请求；不要只在 enqueue Promise 上 catch。工具 details 在边界约束为可 JSON 往返的数据，不把 stringify 成功等同于所有扩展字段都保真。覆盖收尾与普通工具的不可序列化 details、日志配对和恢复拒绝；不能通过事件层吞异常把它变成成功。

### 2. 工具撤回后关闭会话拿不到旧实现，releaseSession 永远不会执行

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/nb-harness/src/harness.ts:322`；`packages/nb-harness/src/tools/registry.ts:76-86`；`packages/nb-harness/src/tools/builtin.ts:24-35`。
- **现象**：close 只通过 `tool.handle.resolve()?.releaseSession` 释放资源；revoke 已把该句柄的 impl 置空并删除登记，因此先使用工具、再撤回、最后 close 时跳过释放。内置工具按 sessionId 保留的 EditStore，以及插件以同一合同保存的会话数据不会回收。
- **为什么是问题**：计划审查第 6 条要求按会话释放；修订计划第 30、38 行承诺关闭及创建失败都释放。执行权限的撤回与已分配资源的释放是两个寿命，不能让失效的执行句柄成为唯一清理入口。每撤回后关闭 **N 个**有工具状态的会话，留下 **N 份**该状态。base 没有 registry 可撤回句柄或 releaseSession；这不是要求本轮修复 base 的 Store 回收问题。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-impl/lab/runtime.ts`，`release-after-revoke` 通过真实 Agent 执行工具，在公开执行上下文里以 sessionId 保存一份状态，随后 `plugin.unregister(); await harness.close()`；实测 `releases:0`，状态集合仍保留 **1 个 sessionId**。
- **建议改法**：为会话资源设置独立于执行句柄的清理所有权，例如会话绑定时登记 disposer、或 bridge 记录实际获得过的实现并在收口后释放。撤回只禁止后续执行，不切断 cleanup；close 的清理使用 finally，某个 release 抛错也要释放其它工具、撤回订阅并终结状态。覆盖“使用后撤回再 close”和创建失败的清理路径。

### 3. 旧插件的 unregister 按 id 撤回新登记，跨版本破坏在途会话

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/nb-harness/src/tools/registry.ts:117-127`。
- **现象**：`registerPlugin()` 的返回句柄仅保存 id，`unregister()` 每次都对当前登记表执行 `revoke(id)`。旧插件卸载后，同 id 重新登记新版本，再次调用旧句柄的 unregister，会把新版本也撤回；从已验证的 onRevoke 调用链推断，新版本在途调用也会同时被中止。
- **为什么是问题**：撤回必须属于某次登记的寿命。registry.get 取得的旧 ToolHandle 正确保持 null，不会复活，但插件注销句柄没有同样的代际边界。重复清理或旧异步卸载回调会越权注销后来启用的插件；这破坏设计审查第 4 条提出且已接受的重启/重新启用隔离。base 的 PluginHost 只有显式按 name 的宿主删除，没有这次新增的登记返回句柄。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-impl/lab/runtime.ts`，`old-unregister-after-reregister` 经公开 registry/registerPlugin：登记 v1 → 旧句柄 unregister → 登记 v2 → 再次旧句柄 unregister，实测 v2 从 `before:"2"` 变为 `after:null`；旧 ToolHandle 仍为 null。本实验直接使用该公开 registry 合同，不伪造 OMP 时序。
- **建议改法**：把注销绑定到登记实例/代次，比较当前 entry 是否仍属该次登记后才 revoke；至少保证返回的 unregister 幂等。部分登记失败时要回滚本次已登记项，避免没有返回清理句柄却留下半个插件。补同 id 重登记后旧注销不影响新工具及其在途调用的行为测试。

### 4. complete 把 Profile 静态消息混进请求，input 不是唯一用户消息

### 6. 一个 releaseSession 抛错会令 close 永久卡在关闭中，并泄漏全部后续清理

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/nb-harness/src/harness.ts:314-327`。
- **现象**：释放工具会话资源的 for 循环没有 finally。第一项 `releaseSession` 抛错后，后续工具不释放、`bridged.dispose()` 和 `unsubscribeAgent()` 不执行、listeners 不清、state 不到 closed；缓存的 closing Promise 永远 reject，重试 close 只拿回同一个失败 Promise。
- **为什么是问题**：close 是宿主的生命周期收口入口，插件 cleanup 的一个异常不能保留其它插件、Agent 订阅和 registry 的 onRevoke 闭包。Spec“状态与转换”要求关闭完成解除订阅；现有代码没有失败后的补偿或可重试通道。releaseSession 和这条清理链都是本轮新增。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-impl/lab/lifecycle.ts`，`release-throws` 用公开插件合同登记 **2 个**工具，第一个 release 抛错；实测 close reject `Error: release failure`，第二个 `released:0`，registry 仍保留 **1 个**桥接撤回订阅，重复 close 仍同一个失败 Promise。
- **建议改法**：关闭过程用 try/finally 保证每个资源独立释放与状态终结；逐项收集 cleanup 错误，所有必需收口完成后再按明确的 close 失败语义报告。不能在首个插件异常处中断整条生命周期。为异常 cleanup 补行为测试，验证其余释放、退订和重复 close。

### 8. 无 HTTP 状态被直接当成 network，明确的内容阻止与模型终态错误被误分类

### 10. 结算阶段的取消被提前选定的 stop 覆盖，用量也仍标完整

### 11. complete 没有捕获 provider 流的抛错或 reject，运行期错误直接逃逸

- **严重程度**：重要；**类别**：正确性。

### 12. run_end 写入失败被静默忽略，调用方收到错误的故障来源

### 13. 工具同步抛错发生在 try/finally 之前，已结束调用仍留在在途表与 signal 上

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/nb-harness/src/tools/bridge.ts:48-72`（64 行）。
- **现象**：bridge 已建立 signal 转发监听、把 settle 放入 inflight 后，直接调用 `impl.execute`，直到 67 行才进入 try。实现同步 throw 时，OMP 正确把它变成工具错误，但 bridge 跳过 finally，pending 与外部 signal 的 forward 监听都不移除；稍后撤回会对已经失败结束的调用再发送 abort。
- **为什么是问题**：返回 Promise 的 TypeScript 方法允许在返回前同步抛错，故障工具不能假定永远使用 async 关键字。调用已经在日志里结算，却仍保有未释放的 controller/settle/监听；同一会话发生 **N 次**此类同步失败就留下 **N 组**调用状态，直到撤回或会话整体回收。违背 bridge 的“每次调用收口”所有权；base 没有这层桥接状态。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-impl/lab/sync-throw.ts`，通过真实 Agent 执行一个在 Promise 返回前 throw 的合法 ToolImpl 方法；Agent 已得到 **1 条**错误工具结果、运行以 stop 完成。此后 `registry.revoke` 仍令该已结束工具的 signal 收到 abort，实测 `abortedAfterFinishedCall:1`。
- **建议改法**：从建立监听/加入在途表开始就进入 try/finally，把 impl.execute 的调用本身放进去；无需给工具再造重试或改写错误。正常完成后删除空 pending 集合，dispose 时清空残余注册。补同步 throw 与异步 reject 两条收口用例。
