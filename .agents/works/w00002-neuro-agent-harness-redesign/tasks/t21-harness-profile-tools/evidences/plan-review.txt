### 1. `syncContextBeforeModelCall` 不是 `Agent` 的公开配置，按计划装配不会执行上下文覆盖

- **严重程度**：阻断；**类别**：正确性。
- **位置**：计划“harness.ts”（35 行）、“不做与风险”（106 行）；`node_modules/@oh-my-pi/pi-agent-core/src/agent.ts:104-120,1583-1590`；`src/types.ts:334-338`。
- **现象**：计划要求配置 OMP `Agent` 的 `syncContextBeforeModelCall`，但它只属于底层 `AgentLoopConfig`；`AgentOptions` 没有这个字段，构造函数也不读取它。`Agent` 为自己的循环硬编码此钩子，仅运行注册的 before-model hooks，再同步内部的 systemPrompt 与 tools，不同步 messages。用户传入同名属性在运行时被忽略，直接传对象字面量还会触发 TypeScript excess-property 检查。
- **为什么是问题**：实现无法通过该装配达到 Spec 输出 7、8；关闭重开后依然可能发 Agent 内存历史而不是日志渲染历史。计划引用的旧 `context-probe.ts:14-20` 实际测的是 `transformContext`，没有测 `syncContextBeforeModelCall`，不能作为这项机制的证据。直接改为裸 `agentLoop` 又会丢失计划所依赖的 Agent 生命周期接口，不是无成本换名字。
- **如何核实**：运行 `bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-plan/lab/runtime.ts`，真实 `Agent.prompt()` 收到同名配置后 `syncCalls: 0`，模型收到 `receivedSystem:["old-system"]`，而非钩子内的 `rendered`。源码同时确认低层钩子存在、上层入口不转发。未调用真实模型。
- **建议改法**：保留 `Agent`，明确使用它确实提供的 `transformContext` / `transformProviderContext`；在实际 provider-context 变换中等待已排队的写入、渲染并替换本次请求，不替换工具调度历史。若用 `addBeforeModelCallHook`，说明它只给 signal，系统提示词要经 `setSystemPrompt` 同步、messages 仍须走变换接口；不要把它写成可直接修改 AgentContext 的同名钩子。新增测试断言模型收到的系统提示词和消息确实来自渲染，不能只断言日志已 flush。

### 2. `afterToolCall` 早于结果事件，当前收尾步骤没有实现合同要求的落盘线性化

- **严重程度**：阻断；**类别**：不变量。
- **位置**：计划“finish.ts”（45 行）、“harness.ts”（36 行）；`node_modules/@oh-my-pi/pi-agent-core/src/agent-loop.ts:2986-3024,3194-3250`。
- **现象**：计划在 `afterToolCall` 里记 finish 并 terminal abort，却又把成功时刻定义为工具结果 `agent_message` 写入完成。真实顺序是 `execute` 完成 → `afterToolCall` → `tool_execution_end` → 工具结果 `message_end` → harness 的异步写入。钩子执行时，当前工具结果还没有事件，更没有进入写队列；在这里 `await` 当前写队列只能等到此前的条目。
- **为什么是问题**：立即认定 finish 会把“钩子之后、落盘之前”的外部取消误判成 `finished`；terminal abort 先占据 AbortSignal.reason，之后外部 abort 也不会改变它。反过来，在钩子里等待由后续 `message_end` 驱动的落盘完成会形成环等：OMP 等钩子返回才发送该事件。日志写失败则也不能靠钩子内等待已有队列发现。计划虽写出正确合同，却没有可实现的结算步骤；S5 按当前步骤编码会返工。
- **如何核实**：同一 `runtime.ts` 真实 `Agent.prompt()` 探针输出顺序为 `message_end:user → persist:user → message_end:assistant → persist:assistant → afterToolCall:written-toolResults=0 → tool_execution_end → message_end:toolResult → persist:toolResult`；在钩子里等待现有 writes 后，结果仍然只在钩子返回后写入。事件先后另由上述源码确认。
- **建议改法**：钩子只记录候选 finish 并禁止下一次模型调用，不在此确认 `finished`、不等未来结果事件。统一从工具结果的 `message_end` 入队，写入成功后原子结算候选；另存外部取消是否早于提交的标记，不从已被 terminal reason 占用的 signal 推断取消先后。明确写入失败优先归为 `local`。用真实写入屏障覆盖“候选已产生但写入未完成时取消”“写入完成后取消”“写入 reject”，并确认没有环等。

### 3. `onResponse` 不覆盖传输重试，`complete` 会把已发生重试的运行标成完整

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划“usage.ts”（40 行）、“验收映射”（90 行）；`node_modules/@oh-my-pi/pi-ai/src/providers/openai-completions.ts:807-828`；`src/utils/openai-http.ts:92-118`。
- **现象**：计数只在 `postOpenAIStream` 成功返回之后触发。该函数内部的 `fetchWithRetry` 已经重试过 408、429、5xx 与网络故障；非成功最终响应和 fetch 抛错也没有 `onResponse`。因此它不是“一次 provider 尝试一次回调”。计划只测空回复重试，恰好绕过这一层盲区。
- **为什么是问题**：真实 `503 → 200`、`fetch failed → 200` 都发了 2 次请求，却只有 1 次回调、1 条助手消息；计划公式返回 `complete:true`。Spec 输出 11 的“发生过重试而计量不足时应视为下界”不能靠这个回调全面判断。这里不是上一轮“可见消息不等于账单”的产品口径争议，而是选定实现把实际存在的 retry 错当成没有 retry。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-plan/lab/provider.ts`，真实 `Agent → streamOpenAICompletions → HTTP transport`，仅用公开 fetch 接缝返回协议响应。`transport-503` 与 `socket-before-response` 均为 `requests:2,responses:1,assistants:1,plannedComplete:true`；对照空回复为 `2,2,1,false`；401 为 `1,0,1`。没有调用内部 retry 函数或真实端点。
- **建议改法**：把 `onResponse` 降为能够发现一部分重试的证据，不宣称逐 attempt 计数。对本次支持的 HTTP provider 在公开 fetch 接缝按运行观察实际传输尝试，或者对没有充分观测的路径保守返回不完整；不另造重试层。补传输 503、响应前网络断开，以及已提交部分输出后流断开的用例，区分“已知零”与“不可确认完整”。保持 Spec 已定的可见消息求和口径。

### 4. 只从 `message_end` 落盘再渲染，首个请求会缺本轮用户输入

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划“harness.ts”（34-36 行）；`node_modules/@oh-my-pi/pi-agent-core/src/agent-loop.ts:1253-1287,1337-1340`；现有 `packages/nb-harness/src/harness.ts:174-185`。
- **现象**：新计划只规定 `message_end` 驱动原样消息落盘，没有保留或替换当前“先写用户输入，再 prompt”的入口步骤。OMP 会先完成上下文准备，再发本轮输入的 `message_start/message_end`。即使修正发现 1，渲染钩子等待写队列时，本轮用户消息也尚未入队。
- **为什么是问题**：新建会话第一次请求的日志渲染结果没有用户问题；恢复会话的新问题同样晚一轮。若在钩子里等用户的后续事件，会死锁；若照旧手工 append 并同时订阅所有 `message_end`，则会把同一输入写 2 次，破坏输出 7、8、9。旧探针之所以成功，是它在调用 Agent 前就手工写了 user，不是订阅屏障自动包含了新输入。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t21-plan/lab/lifecycle.ts`，真实 `Agent.prompt → transformProviderContext`，事件通过真实 nb-session JSONL 排队写入。渲染时 `providerRoles:[user], logEntries:0`；用日志替换后实际 streamFn 收到 `receivedRoles:[]`；运行结束日志才有 user 与 assistant 共 2 条。没有内部函数调用或假造事件时序。
- **建议改法**：在 `turn` 获得运行所有权后显式构造并持久化本轮 UserMessage，再把同一个消息交给 `agent.prompt(message)`；规定如何跳过对应输入事件，确保恰写一次，并保留相同 timestamp 等字段。写入失败返回 `local` 且不发请求；预先取消的输入处理按既有状态合同收口。验收应断言第一次、第二次和恢复后的第一次请求都恰好含 1 条本轮输入，而不只是“写队列已完成”。

### 5. `close()` 只等待 Agent idle，不能等待尚在准备或正在结算的 harness 运行

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划“harness.ts”（37-38 行）；`node_modules/@oh-my-pi/pi-agent-core/src/agent.ts:1238-1243`；Spec“状态与转换”158-161 行。
- **现象**：运行锁在 `turn` 第一步占用，但真正 `agent.prompt` 之前仍有异步日志、密钥和上下文准备。计划的 close 只做 `agent.abort → waitForIdle → 写队列 → 解除订阅`，没有等待所属的完整 `turn` Promise。尚未 prompt 时 Agent 没有 abort controller，`abort()` 无效、`waitForIdle()` 立即完成；Agent idle 之后也仍可能有 harness 的结果、run_end 写入步骤。
- **为什么是问题**：close 可以在 `running` 仍为 true 时返回，之后那次 turn 继续启动模型请求或产生未被订阅的事件；与“拒绝新调用、中止并等在途运行及全部条目结束”冲突。S4 只测“已经挂在模型请求里再 close”抓不到这个窗口。
- **如何核实**：同一 `lifecycle.ts` 用真实 Agent 和真实 JSONL 搭建计划所写的锁/close 协议，用 Promise 屏障代表 prompt 前的异步准备；结果 `closeReturnedWhileRunning:true, requestsAfterClose:1`。这是对计划协议的运行时实验，不是声称尚未实现的新 harness 已有该实现；Agent 的两个方法确实只操作其当前 runningPrompt，源码如上。
- **建议改法**：保存完整运行任务及其独立取消状态，close 首先关闭接纳、取消该任务，等待它（包含准备、Agent 循环和日志结算）完成，再释放订阅与会话资源；所有 await 后进入模型之前检查本次取消/关闭状态。重复 close 共用同一个关闭任务。覆盖准备阶段关闭、模型阶段关闭、最终日志写入阶段关闭及重复 close。

### 6. 会话级 `EditStore` 的取得接口与关闭释放都没有落点

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划“tools/”（27-30 行）、“harness.ts”（37 行）；`packages/nb-harness/src/tools/read.ts:14-15`；`src/tools/edit.ts:22-23,54,117-139`；`node_modules/@oh-my-pi/pi-natives/native/index.d.ts:124-157`。
- **现象**：计划说“句柄 resolve 时按会话取”共享 EditStore，但同一 registry 的 `resolve(): ToolImpl | null` 没有 sessionId 参数；执行上下文到之后的 execute 才提供。close 步骤也没有清空 Store 或移除其会话映射，验收只有通用 initial 隔离，没有 read/edit 的真实状态隔离与释放。
- **为什么是问题**：若通过注册时闭包或某个“当前会话”变量让无参 resolve 找 Store，两个共享登记表的会话就会共用或串用已读行、快照和寄存器；若改用 `Map<sessionId, EditStore>` 却不回收，关闭 N 个会话仍保留 N 份 native Store 及读过的文件内容。这里的资源不是调用内 `EditSession`，它已有 finally.close；Store 的公开释放操作是 `clear()`，不是一个并不存在的 `close()`。
- **如何核实**：对照计划中无参句柄与只在 execute 出现的会话上下文；当前 read 将展示行写入外部 Store，edit 用同一个 Store 维持跨调用状态，上述公开声明提供 clear。此项为接口与生命周期的静态缺口，不声称已有新实现发生泄漏。
- **建议改法**：让无参 resolve 仅取得无会话状态的实现，在 execute 收到 sessionId 后从明确的会话资源所有者取 Store；或者把每会话绑定明确放在桥接阶段，不引入共享“当前会话”。指定 harness close 等运行与写入结束后 clear 并删除映射，创建失败也释放已建资源。增加两个会话对同一文件的 seen-lines/寄存器隔离，以及关闭后资源映射不再保留该会话的验收。

## 未发现问题的方面

- **混批预拦截可行，已实测。** `beforeToolCall` 按调用顺序准备整批，然后才进入调度执行；返回 block 的 finish 不执行，但仍有 tool_execution_end 与 toolResult 消息，普通兄弟工具正常执行。`runtime.ts` 的 finish+lookup 场景是 0 次 finish 执行、2 条配对结果（finish 为 error、lookup 成功）、2 次模型请求；不需要为了配对再手工伪造一条结果。
- **撤回后由桥接 Promise 单独结算可行，已实测该机制。** OMP 等待的是 bridge.execute 返回的 Promise，不要求继续等待底层原 Promise。真实 Agent 接入 race 包装后，中断先赢、原 Promise 后来成功，合计仍只有 1 次 tool_execution_end、1 条中断结果；原 Promise 的完成由包装层已安装的处理器消费，不会自动产生第二个 OMP 事件。未来 bridge 必须保留迟到 reject 的消费与自身监听器释放；本实验不是对尚未实现的 registry.revoke 通知的完整验收。
- **模型请求和调度历史可以分离，源码已确认。** `agent-loop.ts:1717-1745` 的 transformContext 只替换局部 messages，transformProviderContext 只替换 provider-bound Context；它们不会自动重写 Agent 内部 messages。按这两个真实入口实现时，可保留调度器、afterToolCall 和 terminal reason 所需的原始工具历史；发现 1 指出的是计划选错了入口，不是否定日志渲染方案。
- **当前轮之前的已入队写入可以等；未来事件不可以等。** 原探针证明的是已排队写入的屏障；本次真实 JSONL 探针明确区分了尚未发出的本轮 user 事件，真实收尾探针明确区分了尚未发出的 toolResult 事件。没有发现“等待已有、独立可完成写入”本身必然死锁的问题；环等发生在把这些未来事件的写入也放进钩子等待时。
- **无认证 OpenAI 端点已经有确定做法，已实测。** 公开子路径 `@oh-my-pi/pi-ai/providers/openai-shared` 提供 `NO_AUTH_SENTINEL = "N/A"`；返回此非空值不会触发 key 回退，也不会生成 Authorization。真实 openai-completions fetch 接缝收到 1 次请求、认证头缺席；普通任意占位字符串会生成 Bearer 头。因此“绝不返回 undefined”和 `apiKey:"none"` 能同时做到，无需绕过 provider 或自行删头。
- **TypeBox 1.3.6 常见 schema 可直接用，已实测。** 通过真实 Agent 的 union/literal/array/integer/optional/object 校验，合法输入执行 1 次且成功；不合法输入执行 0 次、得到 1 条工具错误；没有发现必须先造 schema 转换层的证据，不声称已覆盖 TypeBox 的每一种扩展。
- **错误标记的公开路径存在，已核实解析与导出值。** `@oh-my-pi/pi-ai/error`、`@oh-my-pi/pi-ai/error/flags` 及 `@oh-my-pi/pi-catalog/build` 都能从主工作区 package exports 解析；Flag.AuthFailed 值为 0x01000000。无需使用风险段设想的降级路径，也无需深导入私有文件。
- **正常的多响应并非已发现的误报。** OpenAI 空回复重试、输出前断流重试均为 2 次 onResponse 对 1 条助手消息，标不完整符合已定口径；普通成功是 1 对 1。已提交输出后断流是 1 次请求、1 次回调、1 条 error 助手消息；输出前取消为 1/0/1，输出后取消为 1/1/1，因此取消的独立 false 标记不可省。未把这些样本推广为所有 provider 的恰好一次保证；发现 3 是确定的漏报。
- **旧装配测试和包入口门禁已经列入迁移。** 计划 64、78 行明确更新 AGENTS.md 并改写 harness.e2e.test.ts，没有漏掉这两个文件；发现 8 只指出迁移和消费者验证的切片边界不自洽，不要求保留旧装配路径。
- **不重开已定产品取舍。** Profile 封闭工具集、快照恢复、收尾混批全部退回、可见用量下界、新旧日志边界、无工具 complete、删除 harness 的 DeepSeek 特例，以及已批准的切片/工作方式，均作为约束使用；没有重报上一轮 13 条设计问题。
