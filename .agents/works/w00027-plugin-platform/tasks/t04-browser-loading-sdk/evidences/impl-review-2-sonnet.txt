# t04 第二轮实现审查：浏览器装载器、构建预设与 SDK、插件页（Sonnet）

范围：`c9ca9f6d2..a41cdb0ad`，浏览器与作者工具一半。按影响排序。没有阻断与重要级发现；以下都是建议级，其中 1、2、3 是已用实验确认的真实缺陷。

## 1. 建议 / 不变量：已中止的信号进入 `activateOf` 时，宿主模块表失败会变成未处理的 reject，还会白插一次脚本

- 位置：`packages/neuro-book/src/web/host/plugin-code.ts:230-236`、`255-258`（`activateOf`、`untilAborted`）。
- 现象：`signal` 在进入 `activateOf` 时已经中止，`untilAborted` 走 `if (signal.aborted) return Promise.reject(...)` 的快速路径，没有给 `modules` 这个 promise 挂任何 handler。`modules` 之后若 reject（升级后动态 chunk 404，正是代码里注释写的典型原因），没人接，成为未处理的 reject。同一路径里 `factoryFor` 照样 `startLoading`：插入 `<script>` 触发一次请求，随后因 `users` 归零立刻 `remove()`；浏览器不会因元素被移除而撤回已经开始的取回。
- 为什么是问题：装载器的合同是“停止信号中止时不留残余”，这条路径留下一个浏览器级的 unhandledrejection 和一次没人要的请求。内核在入口刚被停止、`load` 刚被调用的竞态里完全可能传进已中止的信号。
- 如何核实（已在真实模块上复现）：
  - 用 `/tmp/review-t04-impl2/x/e1.test.ts`（已不保留）：`modules` 20 毫秒后 reject、`signal` 预先 `abort(new Error("stopped"))`，`bun test` 报 `error: chunk 404` 且用例失败（Bun 把未处理的 reject 记为错误）。
  - 另一个用例：`modules` 正常、信号预先中止，`document.head.append` 被调用 1 次、`script.remove()` 被调用 1 次（“inserted 1 removed 1”）。
- 建议改法：`activateOf` 开头先 `if (signal.aborted) throw signal.reason`，在 `hostModules()` 与 `factoryFor` 之前；并在 `plugin-code.test.ts` 补“预先中止：不插脚本、模块表晚到的失败不产生未处理的 reject”一例。另外 `untilAborted` 的快速路径也应当给 `promise` 挂一个空 catch，避免别的调用点再踩。

## 2. 建议 / 正确性与文档：浏览器入口里写顶层 await，构建以一条裸 Rolldown 错误失败，文档没有说

- 位置：`scripts/plugin-sdk/build-plugin.ts:301-319`（浏览器产物固定 `formats: ["cjs"]`）；`docs/specs/runtime/plugin-code-loading.md` 与 `examples/README.md` 都没有提到。

- 为什么是问题：作者从没选过 “cjs”，看不出该怎么改；两端行为不对称，应当在作者合同里写明。
- 如何核实：在 `/tmp/review-t04-impl2/x/a3` 写一个浏览器入口 `const data = await fetch("/x")...`，用 `buildPlugin({root, outDir, ...IN_REPO_BUILD})` 构建，得到上述错误（已复现，实验目录结束时删除）。
- 建议改法：把逐入口构建里 Rolldown 的错误包成 `PluginBuildError`（路径写入口 id，去掉 ANSI），对 `UNSUPPORTED_FEATURE` 加一句“浏览器入口的代码要同步求值，顶层 await 放进 activate”；作者合同（构建预设文件头注释与 Spec 的“SDK”一节）写一条。

## 8. 建议 / 不变量：中间产物目录改放输出目录旁边，带来两个新边界

- 位置：`scripts/plugin-sdk/build-plugin.ts:454-457`（`mkdtemp(join(dirname(outDir), ".nbook-plugin-build-"))`）、`498-503`（`rename`）。
- 现象：
  1. 构建被中断（Ctrl-C、被杀）时 `finally` 不会跑，`.nbook-plugin-build-XXXX` 留在 `dirname(outDir)`；常见写法 `outDir: "dist"` 时它落在作者项目根目录里，不在 `.gitignore` 里。原来在系统临时目录，由系统回收。
  2. `outDir` 本身是挂载点（容器里 `-v $PWD/out:/out`，`buildPlugin({outDir: "/out"})`）时，`dirname(outDir)` 是 `/`：要在根目录建目录（常常没有权限），就算能建，`rename` 到挂载点也是 EXDEV，这正是原来改位置想避免的错误，只是换了一种触发条件。同理输出目录的父目录不可写、而输出目录本身可写时也失败。
- 如何核实：从代码推断；第 1 点按 SIGINT 模拟，第 2 点需要真实挂载点，未验证。
- 建议改法：`rename` 失败为 EXDEV 时退回 `copyFile` 再删；或者把中间产物放进 `outDir` 内部的点目录，最后移动文件、删掉点目录（同一文件系统必然成立，也不依赖父目录可写）；`.gitignore` 里补 `.nbook-plugin-build-*` 的提示写进作者文档。

## 10. 建议 / 合同：SDK 的 `./build` 声明用了 `ErrorOptions`，并带着无用的 `typebox` 导入；测试只用 `lib: ESNext` 所以没发现

- 位置：生成的 `build.d.ts`（源 `scripts/plugin-sdk/build-plugin.ts:94` 的 `ErrorOptions`，`build-sdk.ts:105-114` 的声明生成）；`scripts/plugin-sdk/build-sdk.test.ts` 的 tsconfig。

## 12. 建议 / 注释与归属：装载器超时的注释与实现不一致；共享取回的失败只带第一个激活的插件与入口

- 位置：`src/web/host/plugin-code.ts:21`、`167-168`、`201`。
- 现象：
  1. 注释写“脚本执行后多久还没登记算失败”，计时器实际从插入脚本（开始下载）起算，覆盖下载时间。产物压缩后仍是几十 KB 到几百 KB（内联资源时更大），在回环上无关紧要，页面经局域网或慢链路访问时 30 秒是整段下载加执行。
  2. `startLoading` 的 `fail` 闭包捕获发起这次取回的激活的 `plugin`、`entry`、`url`。同一个文件的几个激活共用这次取回时（清单不禁止两个入口的 `main` 相同），失败原因对所有等待者都写第一个入口的 id，别的入口的诊断里看到的是错的入口名。
- 建议改法：注释改成“从插入脚本起算”；失败对象在每个等待者处按自己的 `plugin`、`entry` 重新生成（共享的只是 `code`、`detail`）。

## 仔细检查后没有发现问题的方面

- 装载器的等待表寿命：`finish` 是唯一的收口，结算、超时、停止、脚本出错都经它撤回登记对象上的等待者、全局 error 监听、计时器与脚本元素；`waiting` 里空集合会删键。一个停止、一个成功、一个超时的组合：`users` 计数与 `cancel()` 的幂等（已结算后什么也不做）正确，成功时 `factories` 缓存先于 `resolveFactory`。宿主模块表失败不缓存、并发共享同一次失败、下次重取，已核对。
- 构建产物：对一个手写的作者项目构建，核对压缩后的浏览器产物：共享模块的动态导入成了 `Promise.resolve().then(()=>p(r("vue"),1))`（同步 `require` 经宿主表）；插件自己的动态导入内联成惰性初始化，每次工厂调用重新求值；`import.meta.url` 全部换成块作用域里的脚本地址，压缩后变量改名一致；`"use strict"` 位于工厂函数体首；资源（图片、`new URL(..., import.meta.url)` 的文件）在库模式下全部内联，没有被静默丢弃。
