# 插件平台的分层重设计

本文是 t13 的架构设计：讲现状的耦合在哪里、目标分层是什么、每层的边界怎么守，以及哪些事要开发者决定。实施顺序与验证见 [plan.md](plan.md)。

第一轮设计审查（Sonnet，19 条，报告存为 [evidences/design-review-1-sonnet.txt](evidences/design-review-1-sonnet.txt)）推翻了初稿里“SDK 拆成独立工作区包”的做法：仓库的治理检查明文禁止任何包依赖主应用，绕开它的代价又很高（第 3.7 节）。本稿改为把作者材料收进应用包里一个独立的目录，并列为待决 D0：这条改变了开发者 2026-10-24 同意的做法，要开发者重新确认。

## 1. 背景与已定的方向

w00027 的 t03 到 t05 做完了第三方插件的整条路：清单校验、安装、服务端与浏览器的代码装载、SDK 与作者命令、作者文档与示例。2026-10-24 的两次复查（[t12](../t12-plugin-dx-review/README.md)）发现，功能是通的，但分层没守住：

- 可维护性审查（Sonnet，20 条）：同一条规则在内核、安装、构建、浏览器宿主里各写一份，有一份已经分叉；装载主线上同一个词有几种意思；SDK 子路径的名单写在 10 处。
- 作者体验（Sonnet 以作者身份从零写插件，20 条）：走得通，但出错时作者看不到原因，最常见的笔误逃过类型检查，声明样板偏重，示例不随包分发。

开发者在讨论中定了三件事（2026-10-24）：

1. 内核里写死的 NeuroBook 常量改由宿主在装配时传入。
2. 内置插件的合同留在应用，公开 API 只有一个入口；作者相关的工具、模板、文档、示例和应用代码分开。第三方插件的通用部分在应用里单独成一个目录、有自己的入口、不引用 NeuroBook 的合同；出现第二个使用插件模式的应用时再抽成通用包。
3. 文档写清内核的定位。

开发者还用一个假想实验检验耦合：如果另一个应用也要做 NeuroBook 这样的插件模式，nb-runtime 能不能支持。本设计以它为判据：做完之后，另一个应用应当能直接用内核；把应用里的通用插件管理目录整个搬走，就能用第三方插件，不用改写。

## 2. 现状

### 2.1 现在的分层

| 层 | 职责 | 在哪里 |
|---|---|---|
| 内核 | 插件定义、服务与依赖、激活、贡献点、远程服务、生命周期、诊断、清单格式 | `packages/nb-runtime` |
| 第三方插件管理 | 安装、登记表、版本租约、启动时盘点、服务端与浏览器装载、插件文件端点、构建预设 | 散在应用的 `src/backend/plugins/`、`src/manifest.ts`、`src/web/host/`、`src/server/`、`src/shared/`、`scripts/plugin-sdk/` |
| 宿主 | 进程、窗口、项目子进程、宿主能力、装配 | 应用的 `src/server/`、`src/project/`、`src/web/host/` |
| 内置插件与公开合同 | 工作台、设置、存储、命令、编辑器……；SDK 再导出其中的合同 | 应用的 `src/plugins/`、`src/shared/`、`src/ui/settings/`；公开入口 `src/sdk/` |
| 作者材料 | 作者命令、模板、作者文档、SDK 打包、示例 | 应用的 `scripts/plugin-sdk/`、`examples/` |

### 2.2 耦合与问题

**内核写死了 NeuroBook。** 非测试源码里有 17 行，分在 3 个文件：

- 清单格式的引擎键叫 `engines.neurobook`；
- 保留的发布者是常量 `BUILTIN_PUBLISHER = "nbook"`；
- 合同、插件版本约束、发布者按 `nbook.` 前缀判断“内置”；
- 内核自带的诊断插件 id 是 `nbook.diagnostics`。

另一个应用拿内核就会被保留 `nbook`，清单里必须写 `engines.neurobook`。

**第三方插件管理没有自己的边界。**

- 代码约 3000 行，分在 7 个目录。其中安装与启动代码 1640 行，反过来引用内置插件 `nbook.plugins` 的合同类型（列表、预览、失败码）：通用代码依赖了专有代码。
- 通用代码里还夹着 NeuroBook 的字面量：
  - 登记表文件的模式标记 `nbook.plugins/v1`，已经写进用户的状态根；
  - 宿主能力的服务键 `nbook/plugin-inventory`；
  - 用户可见文案里的“NeuroBook”；
  - 作者 `package.json` 里的 `nbook.definitions` 字段；
  - 样式标记名、临时目录名。
- 三处宿主（服务端、项目实例、窗口）各写一份“按清单登记第三方定义、失败时降级、记诊断”的流程（审查 F9）。
- 插件 id 规则在内核、登记表、盘点、作者命令里各写一份，登记表那份仍允许数字开头，已经和内核分叉（F2）。
- 装载主线上 `installed`、`thirdParty`、`manifestOf` 各有几种意思（F3）。
- 构建预设和装载器之间的约定（宿主共享模块表、浏览器产物登记用的全局对象名、产物目录结构）是一对协议，但一个在 `scripts/`、一个在 `src/`，靠相对路径深引用对上。
- 插件文件端点直接引用内置插件 `nbook.http` 的实现模块。

**SDK 的公开面不由一处决定。**

- 作者看到约 40 个名字，编译它们要用到应用里 36 个文件、4282 行。其中约 40% 是有意公开的功能：设置的定义、插件状态 store、设置页组件。真正被汇总导出顺带拖进来的内部文件约 6 个、600 行：工作台的首页、菜单、浮层，命令的快捷键与菜单。
- `/components` 是 `export *`，私有包 nb-ui 入口里的全部导出（含工作台内部用的分栏工具）都成了对外承诺，也没有导出名单快照（F18）。
- SDK 子路径的名单写在 10 处：两份 tsconfig、Vite 别名、构建脚本两处、共享模块表、三处装载器、架构测试，其中 6 处之间没有核对（F1）。

**作者材料埋在应用的 `scripts/` 和 `examples/` 里。** 示例不随 SDK 包分发，外部作者拿不到（作者体验 F14）。打包脚本一半在生成文档，用正则读 nb-ui 的源码文本（F4）。

## 3. 目标架构

### 3.1 分层与依赖方向

```text
          第三方插件（作者的目录）
                     │ 只依赖 SDK 包（tarball）
                     ▼
packages/neuro-book（应用 = NeuroBook 宿主）
  ├─ plugin-sdk/             作者包的源：作者命令、模板、作者文档、示例插件与场景测试、打包脚本 → 产出 SDK tarball
  │                           只经 src/sdk/ 与 src/plugin-platform/build/ 用应用
  ├─ src/sdk/                公开 API 的唯一入口（再导出内置插件合同与内核）
  ├─ src/plugin-platform/    通用的第三方插件管理：shared/ backend/ web/ build/
  │                           只依赖内核与列名的通用件；由 NeuroBook 的平台档案配置
  ├─ src/plugins/            内置插件（nbook.plugins 建在 plugin-platform 之上）
  └─ src/server、project、web/host   宿主：装配、能力、进程与窗口
                     │
                     ▼
packages/nb-runtime（内核，与应用无关）
```

依赖只朝下，几条边界由测试守住：

- `src/plugin-platform/` 不引用 `src/plugins/` 和 NeuroBook 的合同，内置插件 `nbook.plugins` 反过来建在它上面；
- `plugin-sdk/` 是应用包里的一个顶层目录，和 `src/`、`e2e/` 并列，产品代码不引用它；
- 示例插件只用 SDK 的名字。

### 3.2 各层的边界

| 层 | 可以依赖 | 不可以依赖 | 由什么机检 |
|---|---|---|---|
| nb-runtime | TypeBox | 任何应用名；文件系统与打包器 | 内核测试用另一份平台档案（`acme`）跑清单与装配；非测试源码（含注释）扫描不出现 `nbook`、`neurobook`；测试里的示例 id 一并改为 `acme.*` |
| `src/plugin-platform/` | nb-runtime、`typebox`、`semver`、`proper-lockfile`、Node 与 Bun 内置模块、应用的通用件 `src/backend/locked-replace.ts`；`build/` 另可用 Vite、Rolldown、`@vitejs/plugin-vue`、`@iconify/utils` | `src/plugins/`、`src/shared/` 里的 NeuroBook 合同、`src/sdk/` | 架构测试按子目录列出允许的导入；非测试源码不出现 `nbook`、`neurobook`、`NeuroBook` 字面量；子目录沿用 `shared`、`backend`、`web` 的路径段，现有前后端规则自动适用 |
| `src/sdk/` | 内核、内置插件的公开合同模块 | 内部实现 | 导出名单快照（三个子路径）；公开面闭包快照 |
| 应用其余部分 | 以上全部 | `plugin-sdk/` | 架构测试 |
| `plugin-sdk/` | `src/sdk/`（经 SDK 包名）、`src/plugin-platform/build/`、内核、nb-ui 的公开子路径；场景测试与场地另可引用内置插件的实现（它们是应用的集成测试设施，现有规则也这样放行） | 应用其余源码 | 架构测试 |
| 示例插件 | SDK 包名、`vue`、`@vue/reactivity`、`typebox` | 应用的任何东西 | 架构测试（现有规则，随目录迁移） |

### 3.3 内核：平台档案

内核新增一个由宿主给出的平台档案，凡是“哪个应用”的事实都从这里来：

```ts
interface PluginPlatform {
    /** 清单 `engines` 里的键，例如 "neurobook"。 */
    readonly engine: string;
    /** 保留给本应用内置插件的发布者，例如 ["nbook"]。内核自己的命名空间 `runtime` 总是保留。 */
    readonly reservedPublishers: ReadonlyArray<string>;
}
```

- **清单格式是一个对象。** 内核导出 `createManifestFormat(platform, versions)`，返回 `read`、`build`、`definitionOf`、`isPluginId`、`isBuiltinId`。
  - 应用在平台档案模块里建一次，服务端盘点、窗口、构建预设、作者命令都从那里取。
  - 这样 id 规则只有一份（F2）。
  - `build` 生成之后立刻按 `read` 校验，调用方不会忘了第二步，`description`、`license` 也归内核生成（F5）。
  - `plugin-manifest.ts` 一个文件 663 行做三件事，借这次改动拆成“读与校验”“由定义生成”“还原定义”三个文件，合同 schema 的遍历只写一份（F11）。
- **内核装配也收平台档案。** 应用清单（`ApplicationManifest`）加可选字段 `platform`，传到插件宿主，和现有的 `satisfies` 走同一条路。
  - 不给时只保留内核自己的 `runtime`，贡献前缀按严格的“插件 id 加点”执行。这样 47 个调用 `createApplication` 的测试与夹具不用改。
- **贡献 id 前缀统一由内核执行（D2）。** `idPrefix: "plugin"` 对保留发布者放宽：这类插件的贡献 id 也可以只以发布者加 `.` 开头。
  - 内置贡献点的 8 个校验器里各自手写的前缀计算删掉，改写 `idPrefix: "plugin"`。
  - 命令的域规则（`nbook.<域>.<动作>`）不是前缀规则，留在命令插件。
  - 应用里其余 5 处 `startsWith("nbook.")` 改用档案的 `isBuiltinId`。
  - 这条把“内置与第三方的区别”正式写进内核规则，ADR 0027 决策 1 要补一句。
- **合同按内容核对（D3）。** 内核现在要求激活产出的合同与声明的是同一个对象。第三方代码产出的是自己打包的那一份，所以应用写了约 45 行规范化比较来迁就（F10）。
  - 改为对所有入口：产出的合同与登记的同 id 合同是同一个对象，或规范化内容相同，就以登记的那份为准；都不是才 `remote-contract-mismatch`。
  - 不区分入口来源。规范化比较挪进内核的远程合同模块，应用的补丁删掉。
- **激活产出的形状由内核核对。** 入口的 `activate` 没有返回对象时，内核以 `activation-threw` 结束这一代，诊断写明“产出不是对象”。
  - 第三方入口在应用里已有同样的检查，挪进内核后两类入口一致。
  - 这就是 t11 的内容，t11 并入本 Task。
- **内核自己的命名空间是 `runtime`（D1）。** 内核自带的诊断插件改名为 `runtime.diagnostics`，服务键改为 `runtime.diagnostics/diagnostics`。
  - 这一条有破坏性：服务键已经写进构建出的第三方清单（`requires`），依赖诊断服务的外置插件要重新构建。
  - SDK 还没发布，影响限于本机已装的示例。

### 3.4 应用里的通用插件管理：`src/plugin-platform/`

这个目录就是将来要抽出去的通用包。现在先在目录、入口和机检上独立出来，子目录沿用应用已有的三分法，外加构建：

```text
src/plugin-platform/
├── shared/
│   ├── profile.ts     平台档案的形状：内核的 PluginPlatform 加下文的字段，纯数据
│   ├── protocol.ts    构建与装载共用的约定：共享模块名单、登记全局名、产物目录结构、插件文件 URL 的拼与解
│   ├── types.ts       列表、预览、未装载原因、失败码的 TypeBox 模式；nbook.plugins 的合同引用这里
│   ├── definitions.ts 三处宿主共用的第三方定义登记 registerThirdParty
│   └── versions.ts    版本比较与范围（从 src/shared/versions.ts 迁来）
├── backend/           登记表、复制、版本目录读取、租约、升级预览、安装与启停卸载、启动盘点、服务端装载、插件文件的请求处理
├── web/               浏览器装载：脚本、样式、宿主模块表的取用
└── build/             构建预设：打包、纯度检查、生成清单
```

没有汇总入口，每个宿主直接引用自己那一侧的子目录，免得浏览器构建经汇总入口卷进 Node 模块。

**平台档案分两层：**

- **纯数据的档案** `PlatformProfile`，构建预设、作者命令和三处宿主都能导入，不连带加载 SDK 的实现。字段：
  - 内核的 `engine`、`reservedPublishers`；
  - `productName`（文案里的“NeuroBook”）、`productVersion`；
  - `registrySchema`（登记表的模式标记，NeuroBook 取原值 `nbook.plugins/v1`，已有文件照常读）；
  - `capabilityPrefix`（宿主能力服务键的前缀）；
  - `authorField`（作者 `package.json` 里的字段名，NeuroBook 取原值 `nbook`）；
  - 浏览器登记全局名、样式标记名、临时目录前缀；
  - 插件文件端点的挂载前缀；
  - 两张共享模块表的模块名。
- **惰性的模块提供函数** `hostModules(location): Promise<Record<string, object>>`，只有装载器调用。没有第三方入口的窗口与项目进程不为它付出加载成本，这是现有的行为。

NeuroBook 专有的部分留在原处，只做三件事：

- 应用给出自己的档案 `src/plugin-platform-profile.ts`：上面的取值，加上提供模块的函数。
- 内置插件 `nbook.plugins` 的界面与远程合同建在 `plugin-platform` 的类型与服务上。
- 一个约 20 行的适配器，把 `backend/` 的插件文件请求处理挂到 `nbook.http` 的路由上。平台侧只给 `handlePluginFile(request, …) → Response`，错误响应自己写，不再引用 `nbook.http` 的实现。

借这次归拢，审查里的几条结构问题一起解决：

- 三处宿主共用 `registerThirdParty`，降级与诊断规则只写一份；项目实例不再把清单读两遍（F9）。
- 主线数据统一命名（F3）：
  - 已安装插件的数组在各处都叫 `installed`；
  - 描述数组叫 `descriptors`，在接收方现算，不再和 `installed` 并排传两份；
  - 启动准备的结果改名为 `PluginsPreparation`，并有一个“没有已装插件”的常量。
- 版本目录的读取从“启动”模块搬到 `backend/version-dir.ts`，升级预览搬到 `backend/preview.ts`，安装不再从启动模块借函数（F19）。
- 失败码按方法收窄，安装与启动对同一件事用同一个码（D4、F13）。
- 一组小问题（F20）：
  - 目录包含判断只留一份，并修掉把名为 `..foo` 的子目录判成“在外面”的错误（已复现）；
  - “宿主没有共享这个模块”的说法和错误类型各只有一份；
  - 装载错误的说明写成完整的一句；
  - 插件文件 URL 的拼与解放在一起。
- 构建预设的小问题：
  - 入口外壳不再重复查找定义（F6）；
  - 删掉只给一条测试用的命令行入口（F7）；
  - 输出目录的清理规则、读 `package.json` 各收成一个函数（F8）。

构建预设从 `scripts/` 挪进 `src/plugin-platform/build/`，理由是它和装载器之间是一对协议，格式要一起改。随之要做三件事：

- 架构测试原有“应用源码只有开发监督进程能用 Vite”的规则，加一个例外：`build/` 也可以，且产品代码不引用它；
- Tailwind 的源码扫描排除 `build/`；
- 两份 tsconfig 的 include 按 `shared`、`backend`、`web` 各认各的。

### 3.5 公开 API 的入口：`src/sdk/`

公开 API 仍由应用拥有：内置插件的合同是应用的一部分，合同变就是 API 变。

- **一张入口表。** `src/sdk/entries.ts` 列出子路径与文件。共享模块表、构建预设的外部名单、打包出的 SDK 包的 `exports` 都由它生成。
  - tsconfig 的路径别名写不成计算的，加一条测试把两份 tsconfig 和 Vite 别名与入口表对照（F1）。
  - 新增子路径要改的地方从 10 处变成一张表加两份 tsconfig，漏改会被测试拦住。
- **`/components` 改为逐个列名。** 只列组件和它们的属性类型，与作者文档的组件清单是同一份；导出名单快照覆盖三个子路径（F18）。工作台的分栏工具等内部件不再对外。
- **根入口的名字不删。** `defineStore`、`definePublicState`、宿主能力的键、诊断服务的键都是 [plugin-api](../../../../../docs/specs/runtime/plugin-api.md) 写明的公开 API，示例也在用。作者体验 F17 觉得它们多余，是因为作者文档没讲它们。处理办法是补文档（第 4 节 A9），不收名字。
- **公开面闭包：可见，适度缩小。**
  - 测试从三个入口出发，算出可达的应用文件清单并与快照比较，`.vue` 文件用 `@vue/compiler-sfc` 取出脚本块再解析。以后有新文件进入闭包，评审时看一眼是不是有意公开的。
  - 缩小只做确定能缩的三处：工作台与设置的两个贡献助手改为引用叶子模块，命令合同去掉末尾对快捷键与菜单的再导出。目标是闭包不超过 30 个文件，其余的有意公开功能不动。
- **typebox 进宿主模块表**（待确认清单改判第 15 行）。共享的说明符是宿主自己用到的 `typebox`、`typebox/value`、`typebox/compile`，浏览器与服务端两张表都加。

  - 所以宿主的 TypeBox 版本范围要写进兼容说明，与 Vue 同等对待。

作者看到的激活上下文类型，要随 `defineEntry` 一起收窄才有效：作者写 `activate: (context) => …` 时，类型是从 `defineEntry` 推出来的。所以放进第 4 节的 A2，和 `defineEntry` 的改动一起做，不在这里先做一遍。

### 3.7 为什么是这样分

| 分法 | 问题 |
|---|---|
| 把 SDK 和插件管理放进 nb-runtime | 内核要依赖应用的合同和打包器，成环；内核也就不再与应用无关 |
| 把内置插件的合同整个搬进 SDK 包（做法 A） | 要搬 36 个文件、改 751 处导入；内置插件被拆成两半；搬进去的内部实现看起来都像 API |
| 每个内置插件一个包（做法 B） | 包数量与装配复杂度大增，眼下没有对应的收益 |
| SDK 作为独立工作区包，经应用的包导出引用应用（初稿的做法，记为 C1） | 见下文 |
| 现在就抽通用插件管理包 | 只有一个使用者，接口只会照着 NeuroBook 设计；先按目录独立、边界机检，抽包时只是搬家 |

**C1 的问题（第一轮审查 R1、R2、R6、R7、R11）：**

- **违反治理规则。** 仓库规定“领域包不得依赖应用”，并由治理检查机检，要开例外。不声明依赖的话，按依赖选测试的工具在应用改动时又选不到 SDK 包。
- **类型声明拿不到。** 作者拿到的类型声明要从应用源码打平，跨包时路径映射必须深入应用源码，应用内部的 `nbook/*` 别名会外泄到 SDK 包的配置里。
- **测试设施重复一份。** 场景测试要装配真实的内置插件，应用得公开一个测试入口，而它会随需要越长越大；Vitest、Bun、tsconfig 的测试设施也要在 SDK 包里复制一份。
- **应用自己的测试受损。** 应用的装载 e2e 与插件页 e2e 现在靠示例插件撑着，搬走就要另写一套测试插件，覆盖会缩水。
- **新包要登记。** 根 workspaces、CI 的选包名单、工作流都要加。

换来的只是“在 `packages/` 下多一个包”。而这个 SDK 本来就是 NeuroBook 专有的：版本等于产品版本，随应用发布。放在应用包里的一个顶层目录，边界一样能用测试守住，依赖方向不用开例外。将来真要独立发布、独立版本，再搬出去，那时作者包只经 `src/sdk/` 与 `src/plugin-platform/build/` 用应用，搬家是可行的。

**和 VS Code 的对照只对一半成立。** 相同的部分：VS Code 的扩展 API 定义在应用仓库里。不同的部分：作者拿到的 `@types/vscode` 只有类型，脚手架与打包工具在别的仓库，不碰应用源码。我们的 SDK 带着应用实现的构建期拷贝：作者构建时要执行入口定义来生成清单，作者的测试也要执行它，所以离不开应用源码。改成“只有类型”的 SDK 是更大的方向变化，本设计不做。

## 4. 作者 API 的形状（第二阶段）

分层改完之后，再改作者直接写的 API。这些改动都在公开面上，SDK 还没发布，现在改成本最低。确认后单独成一个 Task（待决 D5），不和分层改动混在一起。

A2、A3、A4 是一个整体：需要一个拿得到插件 id 的对象，例如 `const plugin = definePlugin(descriptor)`，再用 `plugin.view({name, …})`、`plugin.command({name, …})`、`plugin.setting(…)`。

| 编号 | 改什么 | 依据 |
|---|---|---|
| A1 | 远程方法的结果助手 `ok(value)`、`fail(code, detail)`：类型由合同推出，不用再写 `as const`，`detail` 按错误码的 schema 检查 | 作者体验 F03 |
| A2 | 命令、状态栏条目也有和视图一样的助手，一次给出声明与实现；`defineEntry` 直接收助手的返回值，作者不再手写 `[贡献点]: {[id]: 实现}`，实现的 id 写错就不可能发生。`defineEntry` 的激活上下文对作者收窄（作用域只留 `register`）。缺实现时编译错误的第一行就写明缺哪一项 | F05、F09、F10、F04、F17 |
| A3 | 助手只收短名，贡献 id 由 SDK 拼成“插件 id 加点加短名”，作者不会写错前缀 | F11 |
| A4 | 缺省值：文字可以只写一个字符串；状态栏的对齐、顺序、优先级，视图的位置与版式给缺省；没有参数的命令可以不写 `args`；设置项经 `plugin.setting` 定义，不再逐项写 `plugin`（现有的 `defineSettings` 已经是这个形状） | F16 |
| A5 | 记录与远程方法输入的 schema 由 SDK 补 `additionalProperties: false`；记录的 `locality` 改为必填，不再缺省为服务端用不了的 `local` | F02、F06 |
| A6 | `provide` 改名为 `provideService` | 待确认清单改判第 16 行 |
| A7 | 出错时作者看得到原因：插件页逐个入口显示是否激活与失败原因，列出被拒的贡献与原因，显示插件的显示名与描述；提供方入口激活失败时，远程调用的 `unavailable` 带上原因；构建时入口模块里找不到导出的定义直接报错，并核对插件描述的运行位置 | F06、F11、F13、F20 |
| A8 | 命令面板执行命令遇到参数不合规时给出提示；作者文档写明“要给人用的命令，参数要全部可选” | F12 |
| A9 | 作者文档补：前置条件（怎样拿到能装插件的 NeuroBook、怎样重启）、订阅随入口停止自动释放、插件状态与公开状态、一段远程服务加订阅的完整代码；`create` 合并 `package.json` 时去掉 `npm init` 留下的占位字段 | F04、F08、F14、F17、F19 |

暂不改的：

- “插件描述由 `package.json` 生成，作者只写一份 id”（作者体验 F15）。仓库里按源码装配的内置插件也要用描述，改了要连带改宿主装配。A1 到 A9 做完后，id 重复写的问题会少很多，那时再看。
- `NumberInput` 的 `v-model` 是字符串（作者体验 F18）。这是 nb-ui 的事，记进 nb-ui 的后续事项，不在本 Work 做。
