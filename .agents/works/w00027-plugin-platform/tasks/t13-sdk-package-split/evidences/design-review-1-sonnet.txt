R2  [重要 / 打包与迁移 / 机制]  “SDK 包的 src/ 再导出应用的 ./sdk*”之后，现在 build:sdk 的做法不成立，设计没有写替代做法
位置：design 3.6（src/ 与 scripts/pack.ts）；scripts/plugin-sdk/build-sdk.ts:5-9、:36-47、:216-258；plan 8 风险二

  依赖范围（可放进 NeuroBook 档案或导出 ./package.json）、plugin-platform 的档案（见 R3）、vite 配置（给 vitest 用，见 R8）。

建议改法：颜色名直接导入 `@notnotype/nb-ui/colorway`；设计变量文档用 nb-ui 的 `./tokens.css`、`./theme.css` 子路径（package.json exports 加两行，文件内容就是真相源），
  脚本用 import.meta.resolve 取路径读文件，不再用相对路径下钻源码；分组表（COLOR_GROUPS、DESIGN_GROUPS）仍留在 SDK 包的文档生成里，这是文档的编排，不是 nb-ui 的数据。

R17 [建议 / 对照参照]  “和 VS Code 的分法相同”只对一半成立，SDK 包带的是应用实现的拷贝，不是纯类型
位置：design 3.7 末句；3.6（index.js 由应用源码打包）；build-sdk.ts 头注释第 1 点
现象：VS Code 的做法：API 以 vscode.d.ts 形式定义在应用仓库，作者拿的 @types/vscode 只有类型，没有 JS；运行时 `require("vscode")` 由宿主注入；vsce、yo code 在别的仓库、
  不 import 应用源码；测试 (@vscode/test-electron) 下载已发布的二进制，不依赖应用源码。这里的 SDK 包是应用实现的另一份拷贝：index.js、browser.js 带着
  defineStore、defineSetting、4 个 Settings* Vue 组件的构建期实现（要在作者机器上执行入口定义以生成清单，也要在作者的测试里跑），
  所以才有“宿主表里一份、作者机器上一份”和 R1/R2 的耦合。与 VS Code 对应的做法是：SDK 包只有 d.ts 加极薄的、不依赖宿主内部的实现，
  需要执行宿主实现的场合（生成清单、作者测试）交给宿主提供的工具（如一个 `nbook-plugin` 子命令去连宿主的构建模块）。这是设计方向的重大改动，我不建议在这一轮改，
  只提醒“同一分法”的说法不准确，别拿它当作依赖方向没问题的依据。
建议改法：3.7 的措辞改为“API 定义归应用、脚手架与打包工具在应用之外”，并写明 SDK 包与 @types/vscode 的差别（带实现拷贝）和由此带来的 R1/R2 成本。
