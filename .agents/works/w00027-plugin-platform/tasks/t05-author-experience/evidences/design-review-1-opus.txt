## 发现

### O1 重要 / 接口与合同：`--dev` 用预发布后缀，装上后版本“更旧”，且任何依赖它的插件都会 `version-mismatch`

- 位置：plan.md:69；Spec `runtime/plugin-api.md:133`（已写进 Spec）；代码 `packages/neuro-book/src/shared/versions.ts:35-45`、`src/backend/plugins/inventory.ts:225`、`scripts/plugin-sdk/build-plugin.ts:435`（HEAD）。
- 现象：`<version>-dev.<时间戳>` 是 semver 预发布版本。实测（`bun /tmp/review-t05-opus/semver.ts`，调用应用自己的 `compareVersions`、`pluginVersionSatisfies`、`isCanonicalVersion`）：
  - `compareVersions("0.1.0-dev.20261023120000", "0.1.0") = -1`：已装正式 0.1.0 时装 dev 构建，`inventory.ts:225` 判为 `downgrade`，确认界面按 plugin-install 输出 8.1 每次都提示“降级可能遇到新版本已迁移过的数据”；SDK 给的“上一次成功激活的版本”也会出现比当前版本新的值，插件的迁移逻辑若按 semver 比较会以为在降级。
  - `pluginVersionSatisfies(dev, "^0.1.0")`、`">=0.0.0"`、`"*"` 全为 `false`：别的插件在 `pluginVersions` 里对它写任何范围，重启后都以 `version-mismatch` 受阻，升级预览也会把它们列为“将受阻”。作者在调试两个互相依赖的插件时，`--dev` 循环直接打断依赖方。
  - 时间戳写法没定：ISO 写法 `2026-10-23T12:00:00.000Z` 不是合法 semver（`isCanonicalVersion` 为 false，清单校验失败）；纯数字段带前导零也非法。
  - 构建预设现在要求 `descriptor.version === package.json version`（`build-plugin.ts:435`），清单版本又取自 `descriptor.version`（`plugin-manifest.ts:636`）；计划没写 `--dev` 改的是哪一份、核对放在改之前还是之后，照字面实现要么报“不一致”，要么只改了 package.json 一侧。
- 为什么是问题：Spec 与计划都承诺“在插件页安装按升级处理”，实际是按降级处理；依赖关系里的范围判断与安装比较两套语义都被预发布规则改变，Spec 没写这层后果。
- 如何核实：上面的脚本；`semver` 的缺省规则（`includePrerelease` 为 false）在 `versions.ts:33` 的注释里也写明了。
- 建议改法：改用构建元数据 `<version>+dev.<YYYYMMDDHHmmssSSS>`。同一脚本实测：`isCanonicalVersion` 为 true（`versions.ts` 特意保留构建元数据）、`compareVersions(b1, "0.1.0") = 1`、两次 dev 构建之间 `= 1`、`pluginVersionSatisfies(b1, "^0.1.0") = true`；版本只进安装目录名，文件地址用内容摘要（`src/shared/plugin-files.ts:12-18`），`+` 不进 URL。Spec 写明时间戳的格式（UTC、毫秒、纯数字）与“只改产物清单与传给 `manifestOf` 的描述版本，作者源码与 `package.json` 不变”；`template.test.ts` 断言 dev 版本对正式版是升级、对 `^x.y.z` 仍满足。

### O2 重要 / 遗漏：`create` 合并已有 `package.json` 的规则只到顶层，`npm init -y` 生成的那份会让模板构建不过或 `npm run build` 找不到脚本

- 位置：plan.md:67、77、80；Spec `runtime/plugin-api.md:132`；代码 `scripts/plugin-sdk/build-plugin.ts:140-147、428-436`（HEAD）。
- 现象：构建预设把 `package.json` 的 `name` 当插件 id 的 name 段、`version` 当插件版本，并要求 `plugin.ts` 的描述与它们一致（`build-plugin.ts:435`）。计划的占位符只有 publisher、name、显示名，模板描述的版本写死 `0.1.0`（plan.md:77）；合并规则是“保留已有字段，只补缺的”。本机 npm 12.1.0 在空目录 `npm init -y` 的结果（`/tmp/review-t05-opus/npminit/package.json`）：`name` 为目录名、`version: "1.0.0"`、`description: ""`、`scripts: {test: ...}`、`type: "commonjs"`。按计划字面合并：
  1. `version` 保留 `1.0.0`，模板 `plugin.ts` 写 `0.1.0`：第一次构建就报“插件描述与 package.json 不一致”。
  2. `name` 保留 npm 名：与 `--name` 或目录名转出的段谁优先没写；npm 名可以是 `@scope/x`、大写（老项目）或数字开头（目录名 `2048-timer`），都不是合法 id 段，计划只核对“`--name` 或目录名”。
  3. `scripts` 已存在：只补顶层缺字段时 `build`、`dev`、`typecheck` 不会加进去，README 的 `npm run build` 报 Missing script。计划对 devDependencies 写了按键补，对 `scripts` 没写。
  4. `description: ""` 会原样进清单（`build-plugin.ts:514`），清单 schema 不看它，无害；但同理 `license`、`engines` 若作者早写了不兼容的 `engines.neurobook`，保留后构建出的插件装不上（`incompatible-engine`），create 不提示。
- 另外，“先 `npm install -D <tarball>` 再 `create .`”这条主路径本身会把作者推向 `npm init`：npm 在没有 `package.json` 的目录里向上找最近的含 `package.json` 的目录作前缀。实测 `/tmp/review-t05-opus/parent/child` 里 `npm prefix` 输出 `/tmp/review-t05-opus/parent`：作者在任何已有项目的子目录里新建插件目录，`npm install -D` 会装进上级项目、改上级的 `package.json`，新目录还是空的。README 若因此教“先 `npm init -y`”，上面 1–3 就是主路径而不是边角。
- 为什么是问题：计划把合并作为 F15 的修法，但只说了“保留依赖、补缺字段”，没定冲突字段的胜负；Spec 第 132 行已照这句写成合同，S2 照字面实现会返工。`template.test.ts` 计划只测“合并已有 `package.json`”，没写用哪份输入，用只有 `devDependencies` 的那份就测不到这些。
- 如何核实：`cd /tmp/review-t05-opus/npminit && cat package.json`；`cd /tmp/review-t05-opus/parent/child && npm prefix`；对照 `build-plugin.ts:435` 的一致性核对。
- 建议改法：Spec 与计划写成明确的字段表：`publisher`、`name`、`version`、`displayName` 由 create 决定并覆写（`name` 按 `--name`、否则目录名；已有 `name` 与之不同时在输出里说明被替换，npm 名不作为插件名来源），`version` 已有且是合法 semver 时沿用并同时写进 `plugin.ts`（版本也做占位符，或者模板 `plugin.ts` 直接从 `package.json` 读 publisher、name、version，去掉两处重复）；`scripts`、`devDependencies` 按键合并、已有同名键保留；`type`、`main`、`keywords` 等不管。README 的第一步写 `npm init -y`（或 `echo {} > package.json`）再装 tarball，测试输入用 `npm init -y` 的真实产物。

### O3 重要 / 依赖的机制：服务端打开 user 记录要写 `locality: "shared"`，缺省的 `local` 在服务端得到 `no-client`

- 位置：plan.md:92；代码 `packages/neuro-book/src/shared/storage.ts:44、56`（`locality` 缺省 `local`），`src/plugins/storage/backend/owner.ts:48`、`src/plugins/storage/shared/facade.ts:64`；Spec `storage/persistence.md:89-95` 的“在哪里能打开什么”表（服务端实例打开 `local` 记录为 `no-client`）。
- 现象：计划写“用 `nbook.storage` 的私有记录（用户层一条记录）”，没写 locality。`defineRecord({key, scope: "user", version, schema})` 不写 locality 时是 `local`，服务端入口 `open` 直接失败 `no-client`；focus 的服务端入口激活就读不到记录。
- 为什么是问题：focus 是“私有存储”的教学示例，作者照抄最短写法会撞上这个失败；计划也没说 `open` 失败时入口怎么办（激活失败？只记诊断、远程方法返回业务失败？）。
- 如何核实：读 `owner.ts:48` 与 Spec 表格。
- 建议改法：计划写明 `scope: "user"`、`locality: "shared"`，讲解注释说明为什么（服务端没有客户端身份；“每台浏览器各记各的”与“这台机器上的用户只有一份今日统计”是两种产品语义，这里要后者）；写明 `open` 失败时入口的去向（建议激活失败并带原因，入口状态可查，场景 07 覆盖一次）。

### O4 重要 / 遗漏：focus 的“完成”只由服务端计时器触发，没有按 revision 条件写；多服务端、机器休眠、存储失败下会重复记完成或一直停在“进行中”

- 位置：plan.md:91-93、97；代码 `src/shared/storage.ts:154-163`（`save` 是按 `expect` 的条件写，`subscribe` 只推本进程的写入）、`packages/nb-runtime/src/lifecycle/clock.ts:11-17`（系统时钟的 `schedule` 是 `setTimeout`）；Spec `runtime/projects.md:111`（`projects.stats` 的条件保存做法）、`:175`（两个服务端“互相收不到对方写入的变更通知”）、`storage/persistence.md:121`。
- 现象：
  1. **多服务端**：plugin-install 与 projects 都支持同一状态根同时跑几个服务端，user 分区是同一个 `<状态根>/storage/user.sqlite`。第三方 `onStartup` 入口在每个服务端都激活，各自读到同一个进行中的会话、各自 `schedule` 到 `endsAt`。两边到点都“记为完成”：若实现是“读、加一、写”且冲突时重读重放（存储失败表里 `conflict` 的标准处理），第二个进程重读后照样加一，完成数记两次。反过来，会话在 A 上开始，B 激活得早、不知道（订阅只推本进程写入），A 在 `endsAt` 前退出后，B 上的 `today()` 一直返回 `running`，`endsAt - now` 变成负数，直到 B 重启。
  2. **休眠**：`setTimeout` 走单调时钟，Linux 上挂起期间不计时；笔记本合盖 30 分钟，完成就晚 30 分钟，期间 `today()` 返回已过期的 `running`。
  3. **存储失败**：计划没写 `conflict`、`unknown-outcome`、`busy`、`io-error`、`corrupt`、`unsupported-version` 各怎么办；`start()` 写失败时返回什么业务失败码、`changed` 发不发都没定。合同只有 `already-running`、`not-running` 两个失败码。
- 为什么是问题：计划宣称“窗口关闭、服务端重启，进行中的会话照常结束”，但正确性只靠“唯一的进程、计时器准时”，这两条在受支持的部署里都不成立；完整示例会被作者照抄成“读改写不带条件”的范式。场景 07 只测单服务端、注入时钟，测不出来。
- 如何核实：读上面的代码与 Spec；`storage.ts:162` 的注释“推送分区拥有者进程里的每次写入”。
- 建议改法：把“结算”写成一个函数，在激活、`today()`、`start()`、`cancel()` 与计时器回调里都先调用：读记录，若进行中且 `endsAt <= now` 就以读到的 revision 条件保存“完成数加一、清掉进行中”；`conflict` 与 `unknown-outcome` 时重读，进行中的会话已不是这一个（以 `startedAt` 作会话身份）就放弃。计时器只负责“到点推一次 `changed`”，不承担正确性。合同加一个存储失败的业务码（例如 `storage-failed`，带原因），计划写出各失败码的处理（照 `projects.stats` 的做法）。场景 07 加：两个服务端实例共用状态根、各自到点只记一次完成；注入时钟越过 `endsAt` 但不触发计时器时 `today()` 已结算。

### O5 重要 / 接口与合同、验收映射：空目录里 `create` 仍把 SDK 写成 `^<产品版本>`，而自动测试与 e2e 都走这条路并手工链接依赖，测不到断点

- 位置：plan.md:67（“没有时 SDK 依赖写 `^<产品版本>`”）、84、110；Spec `runtime/plugin-api.md:132`（允许目录不存在或为空）；代码 `scripts/plugin-sdk/build-sdk.test.ts:85-102`（HEAD，作者项目的依赖是从仓库 `node_modules` 软链来的）。
- 现象：Spec 允许在空目录或不存在的目录里 `create`（例如 `npx <tarball> create my-plugin`、`node <sdk>/cli.js create my-plugin`），这时生成的 `package.json` 写 `"@notnotype/nb-plugin-sdk": "^0.1.0"`。本轮不发布，`npm install` 去 registry 找它是 E404（omp 第 3 条已实测）。计划对 omp 3、F15 的修法只覆盖了“先装 tarball 再 `create .`”这一条路。`template.test.ts`（plan.md:84）与 `plugin-authoring.e2e.ts`（plan.md:110）都是“在临时目录 `create`，依赖从仓库链接”，正好走的是这条装不上的路，而且绕过了生成的依赖声明。
- 为什么是问题：Spec 写进了一条作者照做必然失败的路径；自动验收对“生成的 `package.json` 能装上依赖”这件事没有任何覆盖，只有手动 smoke 一次。
- 如何核实：对照 plan.md:67 与 plugin-api.md:132；`build-sdk.test.ts:85-102` 的软链做法。
- 建议改法：二选一写进 Spec。（a）`create` 在目标目录没有已安装的 SDK 依赖时加 `--sdk <npm 依赖写法>`，缺省时拒绝并提示先装 tarball 或给 `--sdk`；发布后再把缺省改成 registry 版本。（b）只允许“已装 SDK 后 `create .`”，空目录拒绝。测试加一条：生成的 `package.json` 里 SDK 的写法等于目标目录原有的那条（逐字），并断言不含 registry 版本号写法；e2e 的临时目录按 README 的第一步先写出带 `file:` 依赖的 `package.json` 再 `create .`，链接 `node_modules` 只替代“真实下载”这一步。

### O6 建议 / 遗漏：“Node 与 Bun 都能运行”没有自动覆盖，SDK 包也没声明 Node 下限

- 位置：plan.md:70、127、158；Spec `runtime/plugin-api.md:130`；`node_modules` 里 `vite` 8.1.4、`rolldown` 1.1.5、`@vitejs/plugin-vue` 6.0.7 的 `engines.node` 都是 `^20.19.0 || >=22.12.0`；`build-sdk.ts`（HEAD 120-131）写出的 SDK `package.json` 没有 `engines`。

### O7 重要 / 接口与合同：`example.focus/minutes` 缺省同时允许 user 与 project 层，服务端只看得到 user 层，窗口里改的作品层值不会生效

- 位置：plan.md:90-92；代码 `packages/neuro-book/src/shared/settings.ts:27-29、176`（`layers` 缺省 `["user", "project"]`）。
- 现象：时长由服务端入口在 `start()` 时读（会话的权威在服务端）。服务端实例没有绑定作品，读到的有效值只来自 user 层；设置窗口在绑定了作品的窗口里会让用户把它改在作品层。用户在作品层设 50 分钟、点开始，实际得到 25 分钟的会话，视图与状态栏都按服务端返回的 `endsAt` 显示，用户看不到原因。
- 为什么是问题：完整示例同时演示“设置项”与“服务端读设置”，这正是作者会照抄的组合；层与读取位置的匹配是 Spec 里的规则，计划没提。
- 如何核实：读 `settings.ts:176`；`docs/specs/settings/configuration.md` 的层与读取位置。
- 建议改法：`minutes` 声明 `layers: ["user"]`，讲解注释写明“在服务端读的设置只放 user 层，原因是服务端没有作品”；或者 `start(input: {minutes})` 由浏览器把它读到的有效值传过去、服务端按 schema 限 1–120（这样也更好测）。二者选一写进计划。

### O8 建议 / 遗漏：“今天”按哪个时区、跨零点怎么算没定；空闲时浏览器不排计时器，状态栏会一直显示昨天的数

- 位置：plan.md:92-93、97。
- 现象：（1）服务端按自己的本地日期清零，浏览器显示“今天”；服务端与浏览器不在同一时区（远程访问）时，“今天”按谁没写。（2）23:50 开始、00:15 结束的会话记到哪一天没写。（3）计划要求空闲时浏览器不排计时器，并在场景里断言“空闲推进一天后 `clock.pending()` 为 0”；于是零点过后没有任何事件触发重读，状态栏一直显示昨天的完成数，直到下一次 `changed` 或重连。这条断言恰好把“零点刷新”排除掉了。
- 为什么是问题：跨日清零是计划列出的行为，却没有可观察的定义；dom 测试与场景各自实现时会给出不同答案。
- 如何核实：读计划这几行；我用真实 `Stage`（`/tmp/review-t05-opus/pending.ts`）确认服务端加窗口、无插件时推进一天 `pending()` 为 0，所以场景里的断言只取决于 focus 自己排不排零点计时器。
- 建议改法：Spec 化一句：“今天”按服务端本地日期，会话按结束时刻计入；`today()` 返回 `date`，浏览器 store 空闲时排一个到下一个零点（按服务端 `now` 与偏差算）的单次计时器，到点重读；场景断言改成“零点后状态栏显示 0、入口停止后 `pending()` 为 0”。

### O9 建议 / 别扭之处：`create` 的“非空目录”白名单会拒绝 `.git`、`.npmrc`，`npm install` 后还有 `.package-lock.json` 之类之外的常见文件

- 位置：plan.md:67；Spec `runtime/plugin-api.md:132`。
- 现象：允许的只有“`package.json`、锁文件与 `node_modules`”。作者常见的第一步 `git init`、为了走代理或私有源放的 `.npmrc`、编辑器生成的 `.vscode/`，都会让 `create .` 拒绝；“锁文件”是哪几个（`package-lock.json`、`npm-shrinkwrap.json`、`yarn.lock`、`pnpm-lock.yaml`、`bun.lock`、`bun.lockb`）也没列，Yarn PnP 的 `.pnp.cjs`、`.yarn/` 不在内。
- 为什么是问题：规则的目的是“不覆盖作者的文件”，白名单做法既拒绝无害的文件，又要随包管理器的变化维护；create-vite、create-vue 的普遍做法是“目录为空或只有 `.git`”，或“只在模板要写的文件已存在时拒绝”。
