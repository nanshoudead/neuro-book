### F1 重要｜测试｜场景 07 测不到 focus 服务端的三条核心机制：条件保存、激活时结算、服务端到点计时器

- 位置：`packages/neuro-book/examples/scenarios/07-focus.test.ts:122-160`；`examples/plugins/focus/backend/plugin.ts:111-116,136,155-156`
- 现象：在副本里分别做三个变异，场景 07 都是 6 过 0 败：
  1. 去掉条件保存（保存前重读一次，用最新 revision 作 `expect`，等于盲写）；
  2. 删掉激活时的 `const first = await update(() => null)` 与随后的检查；
  3. 删掉 `arm` 里的 `clock.schedule(...)`（服务端完全不排计时器）。
  另在原实现上给冲突分支加日志，整个场景 07 只走到 1 次 `conflict`。
- 为什么是问题：计划 S3（plan.md 第 93、98 行）把“停掉服务端入口再启动后已过期的会话记为完成”“两个服务端到点只记一次”“核对记录、`changed`”列为场景 07 的判据，场景头注释也说“服务端到点结算并推送”。实际上：

  - 第 4 例两个服务端从同一份旧记录各自结算，`settle` 是幂等的，盲写也只得到 `completed: 1`（见 F2），条件保存有没有都一样；
  - 第 1 例状态栏变成“今天 1 个番茄”是窗口 store 走到零时自己 `refresh()` 拿到的，不是服务端计时器推来的 `changed`。

- 建议改法：
  - 激活时结算：重新激活后不调 `today`，改为先订阅 `changed`（或用存储探针直接读记录），断言首推/记录里已经是 `completed: 1`；
  - 服务端计时器：不挂窗口（只用远程探针订阅 `changed`），推进时钟过 `endsAt` 后等到推来 `running: null, completed: 1`；
  - 条件保存：见 F2，测它真正防的东西（丢更新），例如服务端 A 的结算与 B 上的新一次 `start` 交错后，新的一次没有被盖掉。

### F2 重要｜代码质量（教学注释讲错）｜focus 把“不重复记数”归功于条件保存，实际靠的是 `settle` 幂等；条件保存真正防的“丢更新”没讲也没测

- 位置：`examples/plugins/focus/backend/plugin.ts:9-10`（文件头第 3 条）、`:54-56`（`settle` 注释）；`examples/scenarios/07-focus.test.ts:7-8,144`；计划 plan.md 第 93 行
- 现象：文件头说“冲突了就重读：别的服务端已经结算过，重读之后没有要记的，这一次就不会被记两遍”。但两个服务端都从同一份旧记录（`running` 为那一次、`completed: 0`）结算时，各自算出的都是 `{running: null, completed: 1}`，盲写两次结果仍是 1；读到对方已写的记录时 `running` 已是 null，也不会再加。F1 的变异 1（去掉条件保存）下场景 07 第 4 例“只记一次”照过，就是这个原因。`settle` 的注释自己也写了“纯函数……几个服务端各自结算不会多记”，与文件头的说法互相矛盾。
- 条件保存实际防的是丢更新（从代码推断，未在真实运行时复现出交错）：服务端 A 的到点结算读到旧记录后、写入前，用户经服务端 B（或 A 上另一个并发调用）开始了新的一次；A 盲写 `{running: null, completed: 1}` 会把新的一次盖掉。条件保存让 A 冲突、重读，看到新的一次，不再写。`cancel` 与到点结算交错同理。
- 为什么是问题：`examples/` 是教学材料，读者会照着“条件保存 = 防重复记数”去理解，换成非幂等的改动（例如“每次结算 `completed += 1`”这类读改写）时仍以为有保护的是计数而不是整条记录；场景名“只记一次”也给了错误的证据。
- 如何核实：读 `settle` 与 F1 的变异 1 结果。我在副本里写了 A 计时器结算与 B 上 `start` 交错的实验（10 轮×两种交错），原实现与盲写都没有丢更新，说明时序难撞上，场景测试要构造确定的交错（例如在 A 读完、写之前插入 B 的 `start`）。
- 建议改法：文件头第 3 条改为“`settle` 幂等，所以几个服务端各自结算不会多记；条件保存防的是丢更新：结算读到旧记录后别处已经开始了新的一次，盲写会把它盖掉”；场景 07 第 4 例改测丢更新，或至少把名字与头注释改成与实际证据一致。

### F3 建议｜正确性（竞态）｜`changed` 订阅的首推可能是旧状态，且之后的推送已经错过

- 位置：`examples/plugins/focus/backend/plugin.ts:170-176`（`subscribe`）与 `:131-134`（没变就不写、不推）
- 现象（从代码推断）：订阅先 `await update(() => null)`，读完记录到把 `sink` 加进 `sinks` 之间隔着 `handle.read()` 这次 await。这期间同一服务端上另一个调用（例如另一个窗口的 `start`）完成写入并推送，新订阅还不在 `sinks` 里，收不到；而本次 `update` 读到的是写入前的记录，`settle` 后与读到的相同，走“没变”分支，返回旧的“今天”。于是新窗口的基线是“空闲”，又错过了“开始”的推送；store 只在有进行中的一次时走表，所以会一直显示空闲，直到用户再操作（`already-running` 后 `refresh`）或重连。
- 为什么是问题：文件头与合同注释都说“订阅建立时先推一次当前的，订阅方拿它当基线”，基线可能比随后（已错过的）推送更旧。窗口打开与另一窗口开始专注几乎同时时出现；概率低，但出现后不会自愈。
- 建议改法：先把 `sink` 加进 `sinks`（用一个本订阅的标记记住“已经推过更新的”），再读当前状态；首推前若这条订阅已经收到过写入推送就不再推旧的基线。或者给推送带上 revision，基线只在不旧于已推的 revision 时推。

### F4 建议｜正确性（失败方式）｜记录 `corrupt` 或 `unsupported-version` 时 focus 激活永久失败，示例没有用存储为此准备的 `reset`；诊断里丢了 `detail`

- 位置：`examples/plugins/focus/backend/plugin.ts:126`、`:155-156`
- 现象：`update` 遇到 `corrupt`、`unsupported-version` 返回 `storage-failed`；激活时这次结算失败就 `throw new Error(\`读不了专注记录：${first.detail.code}\`)`。persistence.md 读取分类第 3 条：“版本不同，高低都算”，所以插件把记录版本从 1 改到 2 后再降级、或 schema 改了没升版本，记录都会进入这两种状态；之后每次启动入口都激活失败，`today`/`start`/`cancel` 都不可用。宿主没有给用户清插件私有存储的入口，用户无法自救。抛出的错误只带 `code`（`corrupt`），丢掉了存储给的 `detail`（哪个字段不符），诊断里看不出原因。
- 为什么是问题：focus 的记录只是“今天的汇总 + 进行中的一次”，丢了代价很小；存储专门提供了 `reset`（先把原件存进原件区再写新值，persistence.md 第 105 行），正适合这里。“完整示例”教作者对坏记录直接让入口激活失败，作者照抄到自己的插件里会得到同样不可恢复的失败。
- 建议改法：激活时遇到 `corrupt`/`unsupported-version` 用 `handle.reset(空记录, {expect: snapshot.revision})` 重置（原件保留），写一条诊断带上 `detail`，并在注释里讲为什么这里选择重置而不是失败；若坚持失败，至少把 `detail` 带进错误消息，并在注释里写明用户如何恢复。

### F8 建议｜正确性（失败方式）｜组件清单与主题变量清单只在“一个都没读到”时报错，源码格式部分变化时静默漏项

### F9 建议｜正确性（失败方式）｜`create` 写到一半失败时留下半个目录，重跑被自己拒绝；文件系统错误以未捕获异常的栈退出

- 位置：`scripts/plugin-sdk/create-plugin.ts:84-97`（边读模板边写）；`cli.ts:87-104`（只认 `PluginBuildError`、`PluginCreateError`、用法错误，其余 `throw error`）
- 现象（实测，用 `/tmp/review-t05-impl/x/sdk` 的 `cli.js`）：

  - 只读目录、目标是文件（`create fileplug`）时，标准错误是 Node 的 `triggerUncaughtException` 栈与 `[Error: EACCES …]` 对象转储，不是一行说明。退出码 1 与 Spec 一致，但输出不是“逐行列出问题”的样子。

### F4 补充（升为重要）

### F11 建议｜代码质量｜几处小问题（各自影响小，合在一条）

1. `packages/nb-runtime/src/plugin-manifest/plugin-manifest.ts:607-621`：同一个贡献点在两份定义里是两个不同对象、带同样不可移植的 schema 时，同一条问题报两遍（实测 `[{"path":"contributionPoints.0.schema","message":"用了 Refine…"}, 同上]`）。建议对已有 `known` 的那份只做一致性比较、不再重复报可移植性问题，或对问题去重。
2. 同文件 `:618`：schema 一致性用 `JSON.stringify` 比较，对键顺序敏感。实测两份定义分别写 `Type.Object({a, b})` 与 `Type.Object({b, a})` 时报“两个运行位置的 schema 不同”。失败方向是安全的（构建报错而不是静默接受），作者按惯例从 `shared/` 引同一个常量也不会碰到；若想消除误报，可复用 `src/shared/storage.ts` 的 `canonical` 那种按键排序的规范化。记在这里，不必改。
3. `scripts/plugin-sdk/build-plugin.ts:81-82`：`version` 选项的注释仍写“给每次构建一个新的预发布版本”，实际是构建元数据（同文件 `devVersion` 的注释正是解释为什么不用预发布段），注释与实现相反。
4. `examples/plugins/focus/backend/plugin.ts:47-51`：`dayOf` 用服务端进程的本地时区，注释说“‘今天’是用户坐在机器前的今天”。服务端跑在别的机器或时区为 UTC 的容器里时（插件页的“服务端那台机器上的路径”说明这种部署存在），零点按服务端算，用户看到的“今天”在本地傍晚或早上清零。作为示例可以接受，建议注释写明这条假设与失效条件，而不是断言它成立。
5. `scripts/plugin-sdk/create-plugin.ts:91`：`sdkFromRegistry` 用 `/^[\^~]?\d/` 判断“registry 版本”，`latest`、`>=0.1.0`、`0.x` 这类同样装不上的写法不提示。影响只是少一条提示。

### F12 建议｜正确性（兼容声明）｜SDK 包的 `engines.node` 写 `^20.19.0`，但 SDK 根入口里有 Node 22 才有的 `Promise.withResolvers`
