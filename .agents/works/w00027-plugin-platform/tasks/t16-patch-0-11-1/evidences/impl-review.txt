### F1 重要 / 不变量（时序）：新建后的“封面失败”“作品目录没写进设置”通知随整页跳转丢失

- 位置：`packages/neuro-book/src/plugins/projects/web/components/BookshelfHost.vue:117-124`；`web/shelf-page.ts` 的 `setCover`（约 363 行）、`rememberLibrary`（约 374 行）；`docs/specs/workbench/bookshelf.md` 输出 11 与第 130 行失败表。
- 现象：`submitInfo` 先 `await setCover`、`await rememberLibrary`，这两步失败时只是 `notified("error", …)` / `warn(…)` 往通知队列推一条，随后同一个微任务链里 `props.page.open()` 走到 `location.assign`（`web/boot.ts:38`）。通知队列是工作台入口里的内存队列（`createNotifications`，入口停止时 `dispose`），整页跳转后新页面里没有它，用户一条也看不到。
- 为什么是问题：Spec 输出 11 同时写着“写失败发通知，作品照常建成”和“这两步结算之后打开新作品”，两句在新建路径上互相抵消。后果是用户选了新位置却没记住（下次新建又回到旧位置，不知道为什么），封面上传失败（作品封面是排版封面）也没有任何提示。只剩 `host.report` 写进诊断日志，用户看不到。`rememberLibrary` 返回 `void`，调用方连失败都判断不了，所以不能只靠“失败时不打开”。
- 如何核实：读代码即可（通知队列在 `plugins/workbench/web/plugin.ts:154` 随入口创建与销毁；`navigateDocument` 是 `location.assign`）。未跑浏览器复现：e2e 不在许可范围。判断来自代码推断。
- 建议改法：让 `rememberLibrary` 与 `setCover` 都返回成功与否；任一失败时不自动打开，留在书架上让通知可见（作品已建好、已被选中，用户点一下就能打开）。同步改 Spec 输出 11：“两步都成功才打开”。备选是等通知显示一小段时间再跳，但那是定时器补丁，不推荐。

### F3 建议 / 不变量：`open` 在新作品没进书架数据时静默什么也不做；对话框关闭后到跳转前的窗口期无提示、可被抢占

- 位置：`BookshelfHost.vue:117-124`；`shelf-page.ts:246-248`（`navigateTo` 里 `byId(id)` 为 `null` 就直接返回）、`fetchOnce`（刷新失败时 `items` 保持旧值）。
- 现象：
  - `create` 成功后 `await refresh(true)`，若这次刷新失败（`status` 已是 `ready`，只发一条常驻“刷新失败”通知），`items` 里没有新作品，`props.page.open(outcome.id)` 悄悄不跳；用户看到对话框关了、没选中、没打开，只有一条“刷新失败”的通知，与“新建成功”无关联。
  - `info.value = null` 在封面与 `loadLibrary` 之前就关了对话框，`infoBusy` 要到 `finally` 才复位；5 MB 封面上传加两次刷新期间，书架上没有任何忙碌提示，用户可以点别的卡片打开别的作品，随后新作品的 `open` 再把页面带到新作品（后发的 `location.assign` 覆盖先发的）。
  - `finally` 里 `infoBusy=false` 在 `open` 之后，但页面直到卸载前仍可交互，期间可再次点“新建”。
- 为什么是问题：边界上的用户体验问题，概率低；严重性取决于封面大小与网络。
- 如何核实：读 `shelf-page.ts` 刷新与 `navigateTo`；窗口期是代码推断，未复现。
- 建议改法：`open` 找不到条目时至少记一条诊断；对话框保持到全部步骤结束再关（或在 `create` 的结果里直接带出短名，不依赖 `items` 里能查到）。可与 F1 一起改。

### F6 建议 / 代码质量：撤回原因的白名单是 `Set<string>`，与 `RevokeReason` 没有类型关联；降级规则没有写进任何 Spec

- 测试：只覆盖 `--json` 下 SIGINT 退出 0 一种；退出码非 0 的分支（`NeuroBook 已停止（退出码 75，详情见 …）`）、文本模式、启动失败不写“已停止”都没断言（第 220 行的启动失败用例可顺手加 `not.toContain("已停止")`）。

- 如何核实：读代码；未实际起进程做启动中 Ctrl-C。
- 建议改法：把 `ran` 改成“没有以启动失败结束”的判断（`failed` 之外都算停止），或明确在 Spec 第 5 条写“启动中停止也不写”；给非 0 与启动失败各补一条断言。

### F9 建议 / 注释：PLUGIN_TIMINGS 的注释断言了一个没有验证的原因

- 位置：`packages/neuro-book/src/plugin-platform/build/build-plugin.ts:389-391`。
- 现象：注释写“说的是构建预设里 Vue 编译的耗时”。rolldown 的提示只说“在插件 `<名字>` 里花了较多时间”，具体是哪个插件看实际输出（冒烟记录里只有“JavaScript callbacks ran for 2.9s”，没有插件名）；“Vue 编译”是推断，不是证据。

## 未发现问题的方面

- 重点 1（降级是否藏住真问题）：从代码推断，三个原因出现的位置（`host.ts` 的 `#disconnectReceiver`、`#revokeTopLevel`、`activation-stopped` 各路径）都是作用域或接收方正常结束；接收方因故障关闭时，故障本身另有 `activate`/`close` 阶段的 error 或 info 记录，带错误的撤回仍记 warn，`activation-failed`、`delivery-failed`、`receiver-revoke-threw` 仍是 warn。内核里没有找到依赖“撤回是 warn”的代码（诊断消费方只有出口与查询，`git grep` 无按级别过滤 `plugins.diagnostic` 的逻辑；Spec 也没有这个级别规则，见 F6）。残留：debug 在浏览器控制台默认被隐藏，“这个接收方关闭时丢了哪些贡献”的细节不再显眼。
- 重点 2（`context.signal.aborted` 判断）：失败先于停止时，`pending` 的 reject 回调当时 `signal` 尚未 abort，仍记 error，所以“下载失败后恰好停止”不会被降级；反向（停止后才失败）才降级。被降级的是整个 `reportPart`（含文档根设置加载失败），粒度偏粗但页面此时正在离开。主要缺口是没有测试（F4）。更干净的根因修法是入口停止后不再去 `layout.acquire()`，这需要改加载函数的返回约定，不建议在补丁里做。
- 重点 5 的 `--json`：`context.output.hint` 恒写标准错误（`cli/output.ts` 的注释写明 `--json` 时也写），与 cli Spec 输出 1“提示照常写标准错误”一致。`process.stderr.write` 之后立即 `process.exit` 在 Bun 1.4.2 下对短句不丢（scratch 里试过 6 字节；200 KB 的大写入到慢读端会被截断，“已停止”一行不受影响）。
- 重点 6：scratch 里用 commander 14 复刻（`scratch/help-mut.ts`）：去掉 `displayWidth` 时测试那条正则能抓到错位（说明列起点 21 与 19 两个值），加上后统一为一个值；`Bun.stringWidth` 默认不计 ANSI 转义（与 commander 自带的 `stripColor` 等价）、emoji 与 ZWJ 序列按 2 格计。唯一的局限是测试与实现用同一个测量函数，终端把“ ”等模糊宽度字符画成两格时两者都测不到；`start --help` 之外的子命令（如 `plugin install --help`）没有对齐断言。
- 重点 5 的 `ran`：`ready.then` 先于 `await server.stopped` 注册，同一刻 settle 时 `ran` 先置位，顺序没问题；启动失败走 `onStartupFailed`，不写“已停止”。
- 版本号、npm 元数据、README 的 `~/NeuroBook`（`library.ts` 的 `documents ?? home` 与之相符）、`bun publish` 警告说明、nb-story 的 `GraphLayout` 拆分（类型从 `layout.ts` 导出，`.vue` 再导出同名类型）：未发现问题。
