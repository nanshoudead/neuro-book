### 重要｜失败路径与边界｜计划 3.3 第 49–59 行

- **现象**：`update` 只明确了 `missing`、正常值、`corrupt` 与 `unsupported-version`：前两者如何传给 `change`，后两者不调用并返回失败。但 `RecordSnapshot<T>` 还有 `status: "error"` 分支；计划没有说明它是否调用 `change`、如何把 `code/detail` 变成 `StorageFailed`。同样没有规定 `change` 抛异常/返回 rejected Promise 时的结果，也没有定义 `attempts` 是总保存次数还是冲突后的重试次数，以及 `0`、负数、非整数如何处理。
- **为什么是问题**：不同实现会产生不同且危险的行为：把 `error` 当缺失会在读取失败时写默认值，违反 Storage “读取失败不应写入默认值”的合同；把 `unknown-outcome` 或 `unavailable` 当普通 conflict 重试可能重复未知结果的写入；对异常不设语义会让 `update` 成为唯一可能拒绝的 Storage 方法，作者无法判断是否需要捕获。尝试次数边界也会改变是否发生写入，不能留给循环实现自行决定。
- **如何核实**：`packages/neuro-book/src/shared/storage.ts:160-168` 定义了 `error` 快照与 `StorageFailed`；`docs/specs/storage/persistence.md:103,128,156` 明确读取错误不当作缺失、经代理的未知写入不得自动重放；`packages/neuro-book/src/plugins/storage/shared/facade.ts:73-77` 当前只把 `read` 和 `write` 的已有结果原样转发，没有可借用的更新语义。
- **建议改法**：把 `update` 写成完整状态表：`missing` 传 `null`，`ok` 传值，`corrupt`/`unsupported-version` 返回对应错误，`error` 直接返回同码同详情且不调用回调；只对 `save` 返回的 `conflict` 重读并重算，`unknown-outcome`、`unavailable` 等立即返回。定义 `attempts` 的总次数/缺省/最小值与超限处理，并明确 `change` 抛异常是传播为代码异常还是转换成哪种结构化失败；为每个状态和重试边界补真实 Storage 测试。

### 重要｜类型合同｜计划 3.6 第 74–76 行

- **现象**：计划把调用方类型命名为 `RemoteResult<T, BusinessCode>`，同时要求失败分支按 `C` 取 `Static<errors[C]>`；但 `BusinessCode` 只携带字符串联合，没有合同的 `errors` 映射，无法从 `C` 反推出详情 schema。当前 `RemoteClient` 正是把 `BusinessCodes<Method>` 作为第二泛型参数传给 `RemoteResult`，所以按字面替换仍只能得到 `unknown`，或者会把所有业务码错误地赋成同一种详情类型。
- **为什么是问题**：B3 的验收目标是 `r.code === "too-many"` 后 `r.detail.max` 能直接通过类型检查。要做到这一点必须让结果类型携带“码到 schema”的映射或整个方法类型，并把运行时错误分支与业务分支做成可区分联合；仅改 `RemoteFailure` 的 `code` 展开不够。若实现者按计划只改 `RemoteResult<T, BusinessCode>`，会在 `RemoteClient`、`orThrow`、`RemoteCallError.failure` 和所有消费方之间反复返工。
- **如何核实**：`packages/nb-runtime/src/remote/protocol.ts:45-53` 的 `RemoteFailure` 只有 `detail?: unknown`；`packages/nb-runtime/src/remote/contract.ts:157-168` 的 `BusinessFailure` 才拥有 `Method["errors"][Code]` 映射；`contract.ts:241-246` 目前把 `BusinessCodes<Method>` 丢给 `RemoteResult`，没有传 `errors` 或 `Method`。仓库外写一个 `RemoteResult<{x: string}, "too-many" | "storage-failed">` 无法从第二个参数构造 `too-many` 的具体 detail。
- **建议改法**：把公共结果类型定义为按方法或错误映射参数化的类型，例如 `RemoteResultFor<Method>`，内部为运行时失败联合加 `BusinessFailure<Method>`；同步改 `RemoteClient`、`orThrow`、`RemoteCallError.failure` 的泛型与声明。补充含两个不同详情 schema、运行时失败码和业务码收窄的编译期反例，验收目标不能只测服务端返回值。

### 重要｜规范一致性｜计划 3.2 第 30–47 行、4 第 101–110 行

- **现象**：3.2 改 SDK 子路径与宿主模块表，4 的 Spec 清单却只把 `runtime/plugin-api.md` 列为子路径表的更新文件；`runtime/plugin-code-loading.md` 的宿主模块表仍明确列出旧的 `@notnotype/nb-plugin-sdk/browser`、`/components`，并要求 SDK 子路径名单与表一致。计划在 4 中只给该 Spec 安排“构建报错格式与 `--verbose`”。
- **为什么是问题**：这是作者装载合同，不是实现注释。只改 `entries.ts`、平台档案和宿主模块表而不改 `plugin-code-loading`，文档会同时承诺旧 `/browser` 和新的 `/settings/browser`、`/workbench`；作者据此判断服务端哪些入口可用、构建预设何时应留外部引用，会得到错误结论。也会漏掉该 Spec 的“共享入口即兼容承诺”与子路径表一致性验收。
- **如何核实**：`docs/specs/runtime/plugin-code-loading.md:23-30` 定义宿主模块表并在 `:27` 写死旧 SDK 子路径；`docs/specs/runtime/plugin-api.md:173-174` 也把宿主模块表与 SDK 子路径的关系作为兼容合同；计划 4 的表格第 105 行只列 `plugin-api.md` 子路径更新，第 109 行给 `plugin-code-loading.md` 的内容不是子路径。
- **建议改法**：把 `plugin-code-loading.md` 加入 3.2/Spec 改动清单，更新两端宿主模块表、每个子路径的服务端可用性和“名单与 SDK 子路径表一致”的验收；B5 的构建错误段另列，不要让同一文件的另一个改动遮住这项合同迁移。

### 重要｜工具机制｜计划 2 第 15–18 行、3.1 第 22–28 行

- **现象**：当前 `pack.ts` 的 `npmPack` 依赖 `npm pack --pack-destination <目录>`，取 stdout 最后一行作为 tarball 文件名；计划只写“换成 `bun pm pack`”，没有说明参数与输出解析。Bun 1.4.2 的默认输出把 tarball 路径放在中间，后面还有 `Total files`、校验和与大小；直接替换命令会把最后一行解析成统计文本而失败。Bun 也不接受 npm 的 `--pack-destination`，应使用 `--destination`，或 `--filename` 写绝对路径。
- **为什么是问题**：S1 的 SDK 打包会在发布前直接失败，且“产出同样的 tarball”并非字节等价：本实验同一包的 Bun tarball 把 `package.json` 重格式化为 114 字节，npm tarball 保留 88 字节的原始文本，压缩包哈希也不同。语义上的文件集合可以相同，但任何现有按包大小、校验值或打包输出解析的验收都不能沿用；计划没有把这个工具合同写清楚。
- **如何核实**：仓库外 `/tmp/review-t15-design-omp/pkg` 执行 `bun pm pack --filename /tmp/review-t15-design-omp/bun.tgz` 与 `npm pack --pack-destination /tmp/review-t15-design-omp`：Bun 默认输出最后一行是 `Total files: 2`，`bun pm pack --quiet --filename ...` 才只输出路径；两包解开后文件集合相同但 `package/package.json` 字节不同。当前实现位置为 `packages/neuro-book/plugin-sdk/pack.ts:364-372`。
- **建议改法**：在计划中规定 Bun 命令的精确参数（推荐 `bun pm pack --quiet --filename <绝对 tarball 路径>`）、输出/失败处理与 tarball 命名，再重写 `npmPack` 并用真实安装验证；把验收从“同样 tarball”改成“相同文件集合、权限、`package.json` 的 exports/bin/依赖语义与可安装性”，除非明确要保留原始 JSON 字节。

### 重要｜工具与失败路径｜计划 3.8 第 85–87 行、3.11 第 97–100 行

- **现象**：计划要求只有 `nbooke build --verbose` 才打印 Vite 的日志与堆栈，但 3.8 没有把 `--verbose` 加入作者命令的参数合同、`BuildPluginOptions` 或 CLI 传递链；3.11 只写了改名，没有列出新的开关。当前 `cli.ts` 的 `parseArgs` 只接受 `out`、`clean`、`dev`，未知 `--verbose` 会直接走退出码 2。
- **为什么是问题**：后续切片照计划实现“默认隐藏堆栈”时，作者没有任何可用的开关打开诊断；若只在构建预设内部加布尔字段，命令层仍会拒绝；若只放宽 CLI 又无法把选项传到 `loadModules`。这使 B5 的成功路径与失败路径合同不完整，作者遇到无法定位的顶层求值错误时不能获得计划承诺的详细信息。
- **如何核实**：`packages/neuro-book/plugin-sdk/cli.ts:48-56` 的 `parseArgs` 没有 `verbose`；`packages/neuro-book/src/plugin-platform/build/build-plugin.ts:80-96` 的 `BuildPluginOptions` 当前也没有该字段；`loadModules` 在 `:205-228` 无日志级别或 verbose 参数。仓库外执行当前命令 `bun .../plugin-sdk/cli.ts build --verbose`，实际输出 `Unknown option '--verbose'` 并退出码 2。
- **建议改法**：在计划 3.8 明确 `nbooke build --verbose` 的 CLI、`BuildPluginOptions.verbose` 与 `loadModules` 的传递和默认值；定义非作者错误的 Vite/打包异常在 verbose 下如何保留原始堆栈，默认模式只输出规范化的“作者文件:行:列 + 消息”；同时把该开关加入 Spec、usage、模板脚本（如需）和测试验收。

### 建议｜参照与 API 完整性｜计划 3.2 第 36–41 行、3.4 第 61–65 行

- **现象**：VS Code 扩展可经 `vscode.commands.executeCommand` 调用任意已登记命令，视图还有 `workbench.view.extension.*` 这类稳定的揭示命令；VS Code 的 `EventEmitter` 则把只读事件面、`fire` 和 `dispose` 分开。计划的 `/commands` 只列 `command`、`COMMANDS_POINT` 与命令类型，B1 只为状态栏提供 `openView(viewHelper)`，没有作者可调用的通用命令服务出口，也没有说明是否有意不支持其它命令的调用。
- **为什么是问题**：现有命令合同明确“任何插件都可以依赖” `nbook.commands` 的 `commandServiceKey`，但当前 SDK 根入口没有导出该键；作者只能手拼 raw service key 或无法调用内置/其它插件命令。这样状态栏、视图动作和 Agent 只能靠计划新增的特例助手，无法表达“执行已有命令并传参数”的普通扩展场景。若 `eventSource` 也要作为普遍事件助手使用，计划同样没有 EventEmitter 式的只读事件面、显式释放/销毁和 provider-side disposer 合同。
- **如何核实**：`docs/specs/workbench/commands.md:35-38,111-114` 定义命令服务的通用查询/执行能力；`packages/neuro-book/src/plugins/commands/shared/contracts.ts:126-139` 有 `CommandService` 与 `commandServiceKey`，而 `packages/neuro-book/src/sdk/index.ts:53-55` 未导出它；计划 3.2 的 `/commands` 内容也未列出。`eventSource` 计划 3.9 只有 `match`、`subscribe`、`emit`。
- **建议改法**：明确“只允许作者贡献命令、不允许作者执行命令”是本期非目标；若不是，按 `/commands` 公开 `commandServiceKey` 与其 `execute/get/isEnabled` 类型，给出调用失败和停止语义，并把 `openView` 定义为这个通用能力之上的便捷封装。对事件助手增加只读事件面、`dispose`/入口代次所有权和 provider-side 资源释放合同，或在 Spec 中明确它只覆盖最小远程推送集合而不是 EventEmitter 等价物。
