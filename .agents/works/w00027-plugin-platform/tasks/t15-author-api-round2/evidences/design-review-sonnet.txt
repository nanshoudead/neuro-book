[F01] 重要 / 遗漏 / 3.2 子路径表没有给 nbook.state 的导出找归属
位置：plan.md 3.2 表；src/sdk/index.ts 第 56-58 行（defineStore、definePublicState）
现象：现在根入口导出 defineStore、definePublicState（内置插件 nbook.state）。3.2 的表只有 storage / settings / commands / workbench 四个内置插件，根入口的描述也没提这两个，也没提 defineSetting、WORKBENCH_*_POINT、SETTINGS_*_POINT、COMMANDS_POINT、settingsChoicesEvent 这些原始贡献点常量和 defineRecord 之外的 storage 低层名字去哪。开发者的决定是“所有贡献助手都改成所属子路径的函数，子路径按内置插件分”，nbook.state 是同一类内置插件。
为什么是问题：S2 的实现者只能自己猜：放根入口就违反“根入口只留插件框架”，加 /state 就是表之外的新子路径（每个子路径都是 engines.neurobook 内的承诺，也要进宿主模块表、两份 tsconfig、pack）。counter 示例同时用 defineRecord、storageKey、defineStore、definePublicState（plugin-sdk/examples/plugins/counter/backend/plugin.ts:20、shared/contracts.ts:10），这是真实用例，不是边角。
如何核实：grep -n "defineStore\|definePublicState" packages/neuro-book/src/sdk/index.ts；对照 plan.md 3.2 表无一行含它们。
建议改法：表里补一行 `/state`（server 可用，defineStore、definePublicState 与类型）；另列一张“现有导出 -> 新子路径”的逐名对照（含上面那些点常量、defineSetting、StorageService/RecordHandle 等类型），S2 验收就是 sdk.test.ts 的导出面快照按这张表更新，不靠实现者判断。同时写明被移走的名字在根入口不留别名（SDK 未发布，开发者已定不保留旧名可沿用）。

[F02] 建议 / 作者体验 / 3.1 `bunx nbooke create .` 在没装 SDK 的目录里会去 npm 取同名包
位置：plan.md 3.1 第一条
现象：实测（bun 1.4.2）：在装了 SDK tarball 的目录里 `bunx nbook-plugin create . --publisher acme` 走本地 node_modules/.bin，正常；在空目录里 `bunx <不存在的包名> create .` 直接向 registry 取该名字的包（本例 404）。nbooke 是 bin 名，不是包名（包是 @notnotype/nb-plugin-sdk），`npm view nbooke` 现在 404，也就是谁先注册这个名字，谁就在“忘了先装 SDK”或装 SDK 失败的作者机器上拿到代码执行。`npm view nbook` 已经是别人的包（0.0.4），P5 第二期的 `bunx nbook` 同理。
为什么是问题：文档顺序是“先 bun add -d SDK，再 bunx nbooke create .”，顺序对时没事；但 bunx 对写错顺序没有任何保护，而且这是新手最常见的失误。
如何核实：/tmp/review-t15-design-sonnet/empty 下 `bunx nbook-plugin-nonexistent-xyz create .` 得到 `error: GET https://registry.npmjs.org/... - 404`；auth1 目录下 `bunx nbook-plugin create .` 成功。
建议改法：二选一或都做：(1) 发布前在 npm 上占位 nbooke（和第二期的 nbook 命名一并看）；(2) 文档里把第一步写成不依赖 bin 名的形式：`bunx --package @notnotype/nb-plugin-sdk nbooke create .`（发布后可直接用），tarball 阶段写 `bun add -d <tgz>` 之后 `bun run nbooke create .` 或 `./node_modules/.bin/nbooke create .`。

[F03] 建议 / 机制 / 3.1 / 2 “bun pm pack 产出同样的 tarball”：内容等价，但 pack.ts 解析输出的方式要改
位置：plan.md 第 2 节、3.1；plugin-sdk/pack.ts 的 npmPack（取 stdout 最后一行当文件名）
现象：实测：同一个 build:sdk 输出目录，npm pack 与 bun pm pack 打出的 tarball 解开后 `diff -rq` 无差异，cli.js 可执行位都保留（尺寸 571350 对 569441 字节，压缩层差异）。但 bun pm pack 默认 stdout 是逐文件列表，最后几行是 `Packed size: 0.57MB`，不是文件名；只有加 `--quiet` 才只打印 tarball 的绝对路径（已实测）。npmPack 现在的“最后一行必须以 .tgz 结尾，否则抛错”会直接抛。--pack-destination 在 bun 里叫 --destination，cwd 用 --cwd。
为什么是问题：计划只说“换成 bun pm pack”，S1 的实现者会遇到一次失败才发现；pack.test.ts 若有对 npm 输出形状的断言也要同步。
如何核实：/tmp/review-t15-design-sonnet/cmp（两份解包目录），`bun pm pack --quiet --cwd <dir> --destination <dir2>`。
建议改法：计划 3.1 写明 `bun pm pack --quiet --destination <目录旁>`，并保留“结果必须以 .tgz 结尾”的检查；pack.ts 顶部注释与 pack.test.ts 里提到 npm pack 的地方一并改。

[F04] 重要 / 机制 / 3.4 “显示区域”点名的 setPartHidden 管不了面板，布局里已有更合适的 applyView 的 reveal 选项
位置：plan.md 3.4 第一条；web/state/layout-store.ts:172（setPartHidden）、:217（applyView 的 options.reveal）；web/shell/sizes.ts:19-21
现象：计划写“选中容器、显示区域（布局已有 applyView({kind: "select-container"}) 与 setPartHidden）”。setPartHidden 的参数类型 ShellHideablePart 只有 titlebar / activitybar / sidebar / auxiliarybar，sizes.ts 的注释写明“面板走自己的 hidden”，面板要用 setPanelHidden（还要清收起、清拖到零、清最大化）。视图在面板里时照计划实现没有可调用的东西。而 applyView(intent, {reveal: part}) 正是为“选中容器并同一次写入显示该 Part”做的：它处理侧栏/右栏的隐藏位、拖到零、右栏“主动显示过”，也处理面板的 hidden 与 collapsed，并且“意图本身无变化（选中本来就选中的容器）时照样显示”（layout-store.test.ts:252 有这条用例）。
为什么是问题：(1) 按计划字面实现，面板里的视图（标题栏、Agent 要打开的常见落点）打不开；(2) 选中与显示分成两次 customizations.commit，既不是同一次写入，也可能被保存冲突重放拆开，Spec 外壳二输出 39 对“放进不显示的 Part”要求的就是同一次写入；(3) 再加展开多视图容器里收起的视图（intent set-view-collapsed，只在 mode=multiple 生效）就是三次写。
如何核实：sed -n 10,24p src/plugins/workbench/web/shell/sizes.ts；layout-store.ts 172 行 setPartHidden 的签名；layout-store.test.ts 252-257 行。
建议改法：3.4 改写为：由 placement.views.get(viewId) 得容器，由容器得 part；`applyView({kind:"select-container", part, containerId}, {reveal: part})`，再在容器 mode 为 multiple 且该视图 collapsed 时 `applyView({kind:"set-view-collapsed", viewId, collapsed:false})`（或让 applyView 一次接收这两个意图，避免两次提交）；删掉 setPartHidden 的说法。验收里写一条“视图在面板、面板收起 / 隐藏时打开后可见”。

[F05] 重要 / 合同 / 3.4 “人与 Agent 都能用，expose.agent: auto，只读”与布局命令的现行约定、与命令执行规则冲突
位置：plan.md 3.4 第一条；web/commands/{view,part,panel,theme}-commands.ts 的声明；docs/specs/workbench/commands.md 第 43、66、269 行
现象：(1) “只读”不对：打开视图会写布局记录（选中的容器、右栏 shownParts、面板 hidden/collapsed、视图 collapsed 都落进 customizations 的保存），现有布局命令（panel-commands 五条、part-commands、view-commands）全是 effect: "write"、expose.agent: "never"；唯一 agent: "auto" 的是主题命令，它同样是 effect: "write"。effect 是只读模式（discuss/plan）阻断 Agent 的唯一依据（commands.md 第 43 行），写成 read 会让 plan 模式下的 Agent 改用户的布局。(2) “人也能用”：命令面板用 {} 执行命令，viewId 若是必填，面板里这条命令会一直 invalid-args；SDK 的 plugin.command 对这种情况加载即抛错并要求 expose.human: false，内置命令没有这道检查（runsWithoutArgs 只在 SDK 助手里调用），所以不会有人提醒。现行做法是 viewId 可选，省略时走 quickPick 选（move-view、set-part-hidden、主题命令都这样）。(3) 计划没说 agent 的默认：commands.md 第 269 行“暴露默认关闭，逐条显式开放”，要开放就要写理由。
为什么是问题：effect 写错是安全语义错误，且 Spec 与测试会照“只读”写；required viewId 会让命令面板出现一条必败的命令。
如何核实：grep -n 'effect\|expose' src/plugins/workbench/web/commands/*-commands.ts；commands.md 第 43、269 行。
建议改法：声明 `effect: "write"`；`args: {viewId?: string}`，省略时 quickPick 列出所有已登记的视图（标题 + 所在区域），选中后同一路径执行（相当于 VS Code 的 “View: Open View…”）；agent 暴露 `auto` 还是 `never` 由开发者在计划里点名决定并写进 workbench-shell Spec 的命令表（Agent 能让用户的侧栏换页，我倾向 auto 但要显式写 effect: write，plan 模式下被挡）。

[F06] 重要 / 机制缺失 / 3.4 “焦点给视图”没有现成的实现，“返回 ok”的含义也没定
位置：plan.md 3.4 第一条；web/state/layout-store.ts:246（focusPart）；web/components/WorkbenchShellLayout.vue:160-168（focusTarget）；docs/specs/ui/workbench-shell.md 外壳一输出 10、外壳二输出 27
现象：布局里唯一叫“焦点”的动作 focusPart 只是把内存里的 focusedPart 改成某个值（Spec 输出 27：它记“最近获得焦点的 Part”，且只由外壳里的 focusin 改）；真正把 DOM 焦点移走的只有 WorkbenchShellLayout.focusTarget，它只会落到 data-shell-focus-target 的 "panel-toggle" / "panel-title" 两个固定元素，用于“焦点内容被隐藏”的兜底。没有任何代码能把 DOM 焦点送进某个视图（视图内容是插件自己的组件，不一定有可聚焦元素），Spec 也没规定落点（视图标题把手？内容根？内容里第一个可聚焦元素？）。Spec 输出 10 还要求“焦点在外壳之外（菜单、对话框）时不抢”，状态栏条目的点击发生在外壳内，菜单触发则在外壳外。另外 applyView 的提交是 void customizations.commit(...)，命令返回时视图还没渲染出来（也可能还在 load() 组件、入口还没激活：views.md 第 20 行写明 onView 按需激活不在第一版），所以“聚焦”要等渲染后再做，“ok”也只能是“已接受”，不是“已可见”。
为什么是问题：三个子需求（选中、显示、展开）在布局里都有现成动作，焦点这一项是新机制，计划把它和前三项并列写成“布局已有”，实现时才会发现要新写焦点落点、时序和 Spec；Agent 调用时 ok 不代表用户已看到。
如何核实：grep -rn "\.focus(" src/plugins/workbench/web 只有 teleport-memory、drag-session、focusTarget 等，没有视图聚焦；sed -n 160,168p WorkbenchShellLayout.vue。
建议改法：二选一并写进 Spec：(a) 第一期不聚焦，只保证可见（选中 + 显示 + 展开），命令参数留可选 `focus?: boolean` 供以后加；(b) 要聚焦就写明落点（建议：该视图 section 的标题把手或内容根设 tabindex=-1，nextTick 后 focus({preventScroll:true})，焦点原本在外壳之外时不抢，Agent 来源默认不抢），并加 `focus` 参数，对应 VS Code 的 view.show(preserveFocus) / <viewId>.focus 的区别。另在 Spec 写明 ok = 已接受并写入布局，入口未激活时视图显示等待状态。

[F07] 建议 / 一致性 / 3.4 失败码：“视图不在布局里返回 unavailable”与同族命令的映射不一致
位置：plan.md 3.4；web/commands/view-commands.ts:resultOf、web/commands/part-commands.ts:56
现象：现有布局命令：布局没打开（layout() 为 null）→ unavailable；意图被 applyIntent 拒绝：stale-source → stale-target，其它（unknown-view、unknown-container 等）→ invalid-args，并把 reason 原样带出。计划把“视图不在布局里、没有已接受的声明”归到 unavailable。
为什么是问题：同一组命令里，未知 viewId 在 move-view 是 invalid-args、在 open 是 unavailable；调用方（Agent、状态栏的 failure-notice）按码分流，会得到两套含义。
如何核实：view-commands.ts 的 resultOf；IntentRejection 的取值见 views/intents.ts。
建议改法：unknown-view → invalid-args（reason 写明视图 id 与可能原因：插件未启用 / 声明被拒）；unavailable 只留给布局没打开；若想区分“插件被停用所以视图暂时没有”，用 reason 文字区分，不新增码。

[F08] 重要 / 机制 / 3.4 openView(viewHelper) 在第一期没有任何作者能用的消费者
位置：plan.md 3.4 第二条；src/sdk/index.ts 的导出（只有 WORKBENCH_STATUSBAR_ITEMS_POINT，没有标题栏、活动栏、菜单项的点常量或助手）
现象：计划让 `openView(viewHelper)` 返回 `{id, args}`，“给标题栏、菜单这类收命令引用的地方用”。作者现在能用的助手里，只有 statusItem 收命令（而且 3.4 让它直接收视图助手，不需要 openView）。标题栏条目（WORKBENCH_TITLEBAR_ITEMS_POINT）、活动栏条目、菜单项（commands/shared/menus）在 SDK 里既没有助手也没有导出的点常量，作者只能手写 rawContributions 才用得上这些点，且常量拿不到。
为什么是问题：新增一个公开面的名字就是一条 engines.neurobook 内的兼容承诺（entries.ts 顶部注释、plugin-api.md “兼容”）；没有消费者的承诺既无法用真实运行时测试（验收映射不出来），又会在以后加标题栏助手时被迫改形状。
如何核实：grep -n "TITLEBAR\|ACTIVITYBAR\|MENU" packages/neuro-book/src/sdk/*.ts 无结果；SDK 里的 command 引用只有 statusItem 的 `command`。
建议改法：第一期删掉 openView，只做 statusItem 收视图助手；等标题栏或菜单助手进 SDK 时再加。如果要保留，把它挂在视图助手上（`panel.open`，返回命令引用），不要另起一个自由函数：命令引用跟着视图走，读者看 `panel.` 的补全就能发现，也对应 VS Code 每个视图自带 `<viewId>.focus` 命令的做法。

[F09] 建议 / 实现陷阱 / 3.4 statusItem 的 command 同时收命令助手与视图助手，现有的区分写法会把视图助手当成命令助手
位置：src/sdk/browser-plugin.ts statusItem 里的 `"contribution" in command ? {id: command.id} : command`
现象：命令助手和视图助手都有 `contribution` 字段（ContributionHelper 的公共形状）。现在的判别是“有 contribution 就取 id”，对视图助手会得到 `{id: "acme.x.panel"}`，也就是把视图 id 当命令 id 去执行；类型上两者都满足联合，编译不报错，点击时才得到 unknown-command。
为什么是问题：“点了即打开视图”恰好是 3.4 的核心路径，写错不会被类型或构建发现。

[F10] 建议 / 对照参照 / 缺“从代码里执行命令”，t14 F01 的后半没有被计划接住
位置：plan.md 3.4；author-acceptance-sonnet.txt F01（“也没有从代码里执行另一条命令的服务”）；src/plugins/commands/shared/contracts.ts:139（commandServiceKey）未导出到 SDK

[F11] 建议 / 作者体验 / 3.2 浏览器专用子路径被服务端入口导入时，报错只有“宿主没有共享的模块”，没有指向原因

[F12] 建议 / 一致性 / 3.2 浏览器专用部分的命名规则不统一：settings 有 /settings/browser，workbench 整个就是浏览器专用
位置：plan.md 3.2 表
现象：规则一：X 与 X/browser（settings）；规则二：整个 X 浏览器专用（workbench、components）。作者看到 /settings/browser 会推断 /workbench/browser、/commands/browser 也存在；而 /workbench 里放的又都是只在窗口里有意义的东西，视图/条目的声明类型 ViewDeclaration、ItemDeclaration 本是 Vue 无关的（shared/views.ts、shared/items.ts），现在连同挪进“服务端不可用”的子路径。
