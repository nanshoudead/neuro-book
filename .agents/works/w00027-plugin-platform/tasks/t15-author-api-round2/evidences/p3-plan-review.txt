# w00027 t15 第三期计划只读设计审查

审查基线：`0f627a12f`；计划：主工作区 `plan-phase3.md`（2026-10-27）。E1 到 E6 按已定决定处理，不重新讨论。以下按核实顺序追加发现；最终影响排序与数量在文末。

## 发现 F01：SDK 生成清单没有发布元数据与许可证，计划明确绕过这部分门禁

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划第 3.2 节、第 3.3 节；`packages/neuro-book/plugin-sdk/pack.ts:385-401`；`scripts/release/packages.ts:117-129`；`packages/neuro-book/plugin-sdk/pack.test.ts:155-170`。
- **现象**：计划让 `release:check` 对两个生成包只查版本，并声称生成物检查已由现有测试覆盖；SDK 的生成 `package.json` 实际没有 `license`、`files`、`repository`、`publishConfig`，打包过程也没有复制 `LICENSE`。应用打包器有这 5 项，SDK 没有。现有 SDK 测试只核对 peer、入口、文件与作者可用性，没有发布元数据或许可证断言。
- **为什么是问题**：新增公开分发的 SDK 直接绕过现有 npm 清单合同；SDK bundle 包含内核与 nb-ui 的实现，却不随包提供仓库的 AGPL 文本，npm 页面也没有许可证与源码归属信息。`bun publish --access public` 只能补访问级别，不能补这些内容。
- **如何核实**：逐行读取上述生成清单、`buildSdk` 全部文件复制步骤、SDK 打包测试与 `checkReleasePackages` 的实际检查；没有执行 registry 写入。
- **建议改法**：在 S2/S3 明确补齐 SDK 的 `LICENSE`、`license`、`files` 白名单、`repository` 与 `publishConfig.access`，在真实生成目录上复用适用于生成包的发布清单检查；不要把“只查版本”当成发布资格。为许可证和白名单补实际 tarball 验收。

## 发现 F02：Smoke 验证的 tarball 与实际发布输入不是同一份物件

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划第 3.2 节第 3 点与第 4 点、第 8 节风险。
- **现象**：计划发布前先生成 `dist/app-package` 与 `dist/plugin-sdk`，`--from pack` 为 smoke 再从生成目录打 tarball；实际发布仍对生成目录运行 `bun publish`，会重新打包，而不是发布 smoke 刚验过的 tarball。`publish.ts` 现有 9 个源码包也是直接在目录里 `bun publish`（`scripts/release/publish.ts:121-129`）；新增生成目录位于 Git 忽略的 `dist/`，现有 dirty gate 不覆盖它们（`publish.ts:74-80`）。
- **为什么是问题**：没有不可变的发布输入或摘要关联，Smoke 成功并不能证明最终上传的字节就是那份已验证包；重新打包时可能因目录内容变化、文件筛选、元数据或打包器行为不同而发布未验证物件。违反“发出去的就是 smoke 过的那份生成物”的发布不变量。
- **如何核实**：读取 `scripts/release/publish.ts:74-80,121-129`、`scripts/release/pack-smoke.ts:53-67` 与计划第 3.2 节；不需 registry 写入。
- **建议改法**：发布与 smoke 共用同一组 tarball 文件：build 一次，生成 tarball，Smoke 从这些文件安装并验收，发布也从这些文件发布；保存并核对每个 tarball 的 SHA-256，禁止 Smoke 后重新构建或重新打包。若 Bun publish 无法直接发布指定 tarball，改成发布 smoke 后冻结的目录快照并核对其 tarball 字节/哈希。

## 发现 F03：重建 workflow 后，社区校验仍会读取已删除的三个旧 YAML

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 3.4 节第 3 点、第 5 节 S4。
- **现象**：计划删除 `community-docs.yml`、`code-baseline.yml`、`workspace-packages.yml` 并加入 `ci.yml`，但仅列出删 `validateWorkflows` 与它专用的常量，没有列出更新 `validate-community-files.ts` 的 `yamlPaths`。当前 `yamlPaths` 在校验开头无条件解析上述三个旧文件（`scripts/ci/validate-community-files.ts:165-172,493-510`），删除后 `bun scripts/ci/validate-community-files.ts` 会因读取不存在文件直接失败。
- **为什么是问题**：计划自身的 CI S4 验证命令与社区文件门禁必然失败；若只删 workflow 语义校验而遗漏 YAML 列表，所有 CI 推送都会失败。
- **如何核实**：运行 `bun scripts/ci/validate-community-files.ts`；当前基线仍有旧 workflow，因此预期当前通过；在实现中删除旧 workflow 后会在 `validateYaml()` 处读到 ENOENT。静态依据如上行号。
- **建议改法**：把 `yamlPaths` 中旧 workflow 条目替换为 `ci.yml`，或明确把 workflow YAML 解析也全部移出该检查并由必跑的 actionlint/等价校验覆盖；加一条覆盖“新 workflow 能被解析、旧路径不再被读取”的检查。

## 发现 F04：`^0.11.0` 会拒绝当前所有 `0.1.0` 插件示例，计划把“版本更新”写成只改版本号

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 3.1 节第 2 点、第 6 节“版本一致”；`docs/specs/runtime/plugin-api.md:175`；`packages/neuro-book/src/plugin-platform/build/build-plugin.ts:554-556`；`packages/neuro-book/plugin-sdk/template/_package.json:4` 与 `template/shared/contracts.ts:12`。
- **现象**：新建插件缺省 engine 是 `^<产品版本>`，产品从 `0.1.0` 升至 `0.11.0` 后模板生成 `^0.11.0`。semver 的 caret 对 0.x 锁定 minor；现有示例声明 `engines.neurobook: ">=0.1.0"` 的可运行性要重新核验；未指定 engine 的旧插件默认 `^0.1.0` 不再兼容 `0.11.0`。计划说“示例插件自己的版本与产品无关，不动”，但 engine 约束并非插件自己的版本。另有 `pluginVersions` 依赖可能同样按 `^0.1.0` 与示例插件版本耦合。
- **为什么是问题**：SDK 兼容合同明说 NeuroBook 0.x 的 minor 号变化可能不兼容；同一 0.x minor 内的 `^` 不跨 minor。只改产品版本就会让新用户生成的插件不能安装到稍后发布的 0.12.x，且当前内置演示插件/插件互依赖可能因构建清单、插件兼容范围变化而失效。计划没有定义示例插件的最低兼容版本与对照验证。
- **如何核实**：读 `plugin-api` 的兼容条款、`build-plugin.ts` 默认 engine、模板 package 与 SDK tests；按 Node semver 规则判断 `^0.11.0` 不匹配 `0.12.0`，并需在实施时跑模板和示例闭环。
- **建议改法**：版本切片列出所有用户可安装示例中的 `engines.neurobook` 与 `pluginVersions`，将“示例插件自己的 version 不动”与“兼容范围要随产品改变”分开。更新适用范围并用真实构建的全部示例/插件组合验证当前版本可安装、依赖可满足；将预期兼容区间写到 SDK 文档/Spec，不只改测试。

## 发现 F05：`test:affected` 的 GitHub `--since` 缺少三种边界处理，强推边界没有被覆盖

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 3.4 节第 2 点、第 5 节 S4、第 6 节“CI”；`scripts/ci/change-scope.ts:78-89`。
- **现象**：计划给 `test:affected --since <基准>` 传 PR base SHA 或 push 的 `github.event.before`，只在 before 全零或“不在历史里”时传 `--all`。实际 `changedFiles()` 对 `--since` 无回退逻辑，直接 `git merge-base <since> HEAD`，不存在或非共同祖先时执行器抛错；PR 的 base SHA 在分支改写/浅历史缺失时同样失败。`github.event.before` 对删除分支、首次推送和非快进更新应明确分支条件，而不只是全零检测。
- **为什么是问题**：新工作流在合法 push 边界可直接红灯，而非运行全量验证。计划把“不在历史里”近似为可检查条件，但没有定义这是指对象不存在还是无 merge-base；强推的 before 常仍是可达对象，只是与 HEAD 无 merge-base，正好不会被“无效 SHA”判断捕获。
- **如何核实**：读 `scripts/ci/change-scope.ts:78-89` 并确认它无异常转换；在临时 Git 仓库造一个与当前 HEAD 不相交的 before，执行 `bun run governance:check --since <sha>` / `bun run test:affected --since <sha> --dry-run`，应在 merge-base 失败退出；不要改仓库。
- **建议改法**：先在 workflow 中对基准执行 `git merge-base`，退出非零（包括合法 SHA 但无共同祖先）时明确传 `--all`；覆盖 push 删除/新建分支、首次推送、强推、checkout fetch 完整性及正常 fast-forward 的工作流合同测试。PR base 缺失也按明确定义回退全量。

## 发现 F06：README 包列表的强制同步规则没有被新计划满足，`release:check` 也不检查根 README

- **严重程度**：重要；**类别**：文档。
- **位置**：计划第 3.5 节根 README/npm 包表、第 5 节 S5、第 6 节“README 包列表”；`scripts/release/packages.ts:14-25,110-147`；`README.md:184-203`；`README.en.md:169-167`。
- **现象**：发布清单源码注释要求“加包时同步 ADR 0029 与根 README 的列表”；本期会新增 `@notnotype/neuro-book` 与 `@notnotype/nb-plugin-sdk`，但计划只说“npm 包表加上应用与 SDK”，没有写进 ADR 0029 更新（该 ADR 标题/决定仍只覆盖 9 个源码包，决定 6 仍排除应用），也未列出让 `release:check` 核对根 README 的实现。现有 `release:check` 只读 `RELEASE_PACKAGES` 对应包，不读取 README。
- **为什么是问题**：发布成功时可能出现根 README、ADR 与实际新增包清单不一致；S5 写的 `release:check（README 的包列表）` 当前并不具备这个行为，验收是假门禁。该项目已有明确的发布清单维护约定，新增两个发布物正是它要求同步的情况。
- **如何核实**：读 `packages.ts:14-25,110-147`，调用路径为 `bun run release:check`；该脚本的默认参数加载 9 个目录，没有 README 校验。
- **建议改法**：计划明确 ADR 0029 的适用范围和“新应用/SDK”与 9 个源码包的关系：旧 ADR 保持历史决策时，新增补充 ADR/决定记录，不把历史 ADR 的范围悄悄扩写；根 README 两种语言的实际包名列表要和 `RELEASE_PACKAGES + BUILT_PACKAGES` 对齐。要把 README 写进 `release:check` 就在计划列出实现与可观察测试，否则删掉 S5 对它的验收声称，改用 `docs:check` 或专门文档合同验证。

## 发现 F07：`create-plugin.ts` 返回合同变化没有明确跟进类型与所有测试调用方

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 3.3 节第 1 点；`packages/neuro-book/plugin-sdk/create-plugin.ts:55-62,66-101`；`packages/neuro-book/plugin-sdk/cli.ts:41-50`；`packages/neuro-book/plugin-sdk/template.test.ts:137-146`。
- **现象**：计划指出删除“registry 版本装不上”的返回字段与提示，但 `CreatePluginResult.sdkFromRegistry` 不只用于 CLI 提示：`template.test.ts` 直接断言提示；`create-plugin.ts` 中 `sdkFromRegistry` 仍由 `isRegistrySpec` 判断并被 `createPlugin` 返回。计划没有要求删掉不再使用的 `isRegistrySpec`、`sdkSpecOf` 和创建结果字段的所有引用，也没有说明现有测试要改成何种新行为。
- **为什么是问题**：照文字只删 CLI 提示会留下失效的结果字段/计算；若直接删除字段但没更新模板测试和类型引用，测试失败或无意义的状态仍保留。并且模板允许保留已有 `@notnotype/nb-plugin-sdk` 范围：默认创建出来会改成 `^0.11.0`，但已有 `^0.1.0` 会原样保留；所谓“装得到”并不保证用户安装的是运行 `create` 的同一 SDK 版本。
- **如何核实**：检查 `createPlugin` 的 `sdkFromRegistry` 完整生产与消费调用点、`template.test.ts` 断言；读 `mergePackage`（`create-plugin.ts:175-205`）确认已有依赖优先保留。
- **建议改法**：把结果类型、内部检测函数、CLI 文案、所有调用方与测试作为一个接口切片一并删除，测试改测可观察行为（生成的依赖版本与后续安装结果）；计划第 3.3 节第 3 点显式处理 `create` 对已有 SDK 依赖的保留政策，保证其运行版本与文件写出的范围一致，或明确这是作者自选 pin 而不做隐式改写。

## 发现 F08：作者的“同版本 SDK”烟测没有建立目录隔离，命令会在存在的 package.json 上下文中解析 SDK

- **严重程度**：建议；**类别**：正确性。
- **位置**：计划第 3.2 节第 2 点与第 3.3 节第 3 点、第 6 节；`packages/neuro-book/plugin-sdk/create-plugin.ts:26-30,66-75`。
- **现象**：计划脚手架 smoke 把 `bunx -p <SDK> nbooke create hello` 与 `bun install` 放在“仓库外的临时目录”描述不清楚，也未说明 `bunx` 的执行工作目录与 SDK 安装缓存、作者项目根如何隔离。`create` 允许目标目录已有 `package.json`，并会按它已有 SDK 依赖保留；若目标是现存项目的子目录或将当前目录直接拿作 create 目标，生成 manifest 可能继续用旧的依赖范围，而 `bunx -p` 使用的 SDK 版本由 Bun 的 package 安装/缓存决定，不由该现存项目依赖决定。
- **为什么是问题**：烟测可能只证明临时空目录默认路径，不覆盖产品点名的“在已有 package.json 的上级目录里执行”。`bunx` 与 `bun install` 可能解析不同包版本；该组合是计划第 3.3 节要证明的关键前提。现有 `createPlugin` 对已有 `package.json` 的明确优先级证明了输入状态会影响输出范围。
- **如何核实**：`bunx --help` 显示 `-p` 直接安装到全局共享 cache；读 `create-plugin.ts:175-205` 可见已有依赖被 merge 保留。需要在 smoke 增加真实命令调用，分别在干净的临时作者根、以及已有 `package.json` 的父目录/项目中运行并读解析后的 SDK 版本；本次未联网操作，不声称已验证该特定 Bun 解析时序。
- **建议改法**：把 smoke 的作者项目、执行 cwd、BUN_INSTALL/cache、`--sdk`/已有 SDK 依赖版本与安装命令逐项写清。用隔离的临时 `BUN_INSTALL` 与临时作者项目实测版本号相等；另测已有项目的显式依赖策略，不依赖 `bunx` 缓存碰巧与项目 lockfile 相同。若要保证一致，CLI 应使用自身实际版本重写 SDK 依赖范围，或对冲突范围报错并要求显式选择。

## 发现 F09：CI 新 workflow 删除旧 workflow 后，计划仍保留旧 YAML 的无条件解析入口

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 3.4 节第 3 点；`scripts/ci/validate-community-files.ts:165-172,493-510`。
- **现象**：与 F03 同属一个已核实根因，补充具体调用链：`validate-community-files.ts` 的 `main()` 每次先 `validateYaml()`，旧 workflow 名在 `yamlPaths` 内；后面才执行 `validateWorkflows()`。计划说移除后者的“逐字核对 workflow 内容”，但没提前置 YAML 解析清单。
- **为什么是问题**：不管旧结构测试如何删，新的 `ci.yml` 只要没有同步替换旧的 YAML 路径，S4 指定的 `bun scripts/ci/validate-community-files.ts` 会在尝试读旧文件时先报 `ENOENT`，无法跑到 Issue Form、贡献指南检查。
- **如何核实**：实际代码 `validateYaml()` 遍历所有 `yamlPaths`，`readRepoFile` 用 `readFile` 无 `ENOENT` fallback；构建本地隔离副本删除旧 workflow 后执行即可复现。由于是同根因，最终计数与 F03 合并，不重复计条。
- **建议改法**：如 F03，将 `yamlPaths` 旧项替换成 `ci.yml` 或删除 workflow YAML 解析责任，并将新检查纳入 CI。

## 发现 F10：计划允许 CI 运行 affected 的新应用检查，但 `app-package` 提交产物未包含可见 UI/browser 验收

- **严重程度**：建议；**类别**：测试。
- **位置**：计划第 3.4 节第 2 点、第 5 节 S4、第 6 节 CI 映射。
- **现象**：CI 的 `app-package` job 会构建 Web 与两包并跑 `smoke:server`；`test:affected` 的 fast tier 包脚本是 Bun + Vitest，排除 `test:e2e`。虽然按 E4 不应在 GitHub Actions 跑 e2e，计划只把“干净机器构建成功”作为 CI 判据，没有把 browser runtime 检查放到本地 S4/S5 的正式 Smoke 验收之外。计划收口列了全量 e2e，因此属于边界说明不足而非遗漏全部测试。
- **为什么是问题**：`build:app-package` / `build:sdk` 只能证明能生成目录与 tarball，`smoke:server` 不会打开生成应用包的页面；若把 CI 作为唯一自动化回归证据，生成包的浏览器入口未被这个新 CI job 实际加载。此处不能通过 CI Chrome 解决，因为产品合同规定 browser e2e 在本地跑。
- **如何核实**：读 `packages/neuro-book/package.json:13-27` 与 `scripts/ci/workspace-package-matrix.ts:73-76`，观察 `test:affected --tier fast` 只调用 `test`，没有 `test:e2e`；`smoke-server.ts` 是服务器进程测试。
- **建议改法**：保留 E4，不给 CI 加 e2e；计划在 S4 的本机验证与收口中明确用真实生成的 `app-package` tarball 做已有 `e2e/app-package.e2e.ts` smoke（Chrome、Node，真实 `BUN_INSTALL`），并说明这条本地证据是 CI build job 的浏览器运行时补充，而不是构建成功的替代。

## 发现 F11：npm README 的绝对图片地址会在本地发布先于 GitHub push 时返回 404

- **严重程度**：重要；**类别**：文档。
- **位置**：计划第 3.5 节第 6–7 点与第 8 节；发布命令第 7 节第 2 点。
- **现象**：计划要把图片放进 `docs/images/readme/`，并在 npm 页面用 GitHub 上的绝对地址；发布流程是先合入本地 `master` 再 `release:check`/`release:smoke`/`release:publish`，没有先 push 此提交的步骤（远端 push 还要另授权）。GitHub 上的 raw/README 路径在新文件提交尚未 push 时不存在。

## 发现 F15：推 master 时“新的一轮取消旧的”与按 `github.event.before` 选包叠加，被取消那次推送的改动永远不会在 CI 上测

- **现象**：两条规则单看都常见，合在一起有洞。推送 P1（`A..B`，改了 `nb-ui`）触发运行 R1，基准 `A`；几分钟内推送 P2（`B..C`，只改文档）触发 R2，按计划的 concurrency 取消 R1；R2 的基准是 P2 的 `github.event.before`，即 `B`，`test:affected --since B` 只看到文档改动，不选 `nb-ui`。`B` 的改动从此没有任何一轮 CI 跑完过，而 R2 是绿的。本仓库的做法是本地连续合入、再推 master，几次推送挨得近是常态（计划第 1 节也说各包测试从 09-12 起就没在 CI 上跑过，说明没人盯着每次运行）。
- **为什么是问题**：CI 的意义是“合入的东西在干净机器上验证过”；按改动选包时，每轮只对自己那段提交负责，取消一轮就等于跳过一段提交，且结果显示为绿，没有任何信号。PR 上取消旧轮没问题（新一轮的基准是 PR base，覆盖全部提交），push 上不行。

- **建议改法**：二选一写进 `ci.yml` 的设计：（1）concurrency 只对 `pull_request` 取消旧轮，`push` 到 master 排队不取消（`cancel-in-progress: ${{ github.event_name == 'pull_request' }}`），代价是密集推送时多跑几轮；（2）push 时基准不用 `github.event.before`，而取 master 上一次 `check` 成功的提交（`gh run list --workflow ci.yml --branch master --status success --limit 1 --json headSha`，需要 `actions: read` 权限），取不到就 `--all`。（1）更简单，推荐。S4 的工作流验收补一条“连续两次推送、第一轮被取消时第二轮覆盖哪些包”的说明或测试。
