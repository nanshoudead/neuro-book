## R01 阻断｜正确性｜release-manifest.json 在冒烟之前就写下，冒烟失败后 publish 门禁照样放行

- **位置**：`scripts/release/pack-smoke.ts:369-375`（写清单）与 `:381-384`（之后才跑 `smokeStory`、`smokeVueHost`、`smokeAppAndPlugin`）；`scripts/release/publish.ts:105-118`（门禁只核对提交与 SHA-256）。
- **现象**：`--from pack` 时清单在“打包与入口检查”之后立刻写入 `dist/release/release-manifest.json`，三段用户与作者闭环在其后才跑。闭环任何一步失败（nbook 起不来、插件构建失败、Vite 宿主构建失败），脚本退出 1，但 `dist/release/` 里的 tarball 与清单都留着，提交也等于 HEAD。`publish.ts` 已经不再自己跑 `release:smoke`（旧门禁里有这一步，本次删了），只看清单的 `commit` 与摘要，于是 `release:publish --yes` 会把一份冒烟失败的 tarball 发出去。
- **为什么是问题**：违反计划 3.2 与 `repository-workflow.md` 第 5 步写的“发的就是第 4 步验过的 tarball”；模块头 `manifest.ts` 也说“smoke 把验过的 tarball 放进 `dist/release/`”。版本号一旦发出去不能再用（计划第 8 节的首要风险），这正是门禁要防的情形。
- **如何核实**：读 `pack-smoke.ts` 主流程顺序；或在 scratch 里把 `smokeAppAndPlugin` 换成直接 `fail()` 后跑 `--from pack`，`dist/release/release-manifest.json` 仍在，`publish.ts` 的 `releaseManifestProblems` 返回空。
- **建议改法**：打包后先把清单写到临时名（或内存），三段闭环全部通过后再原子地写出 `release-manifest.json`（写临时文件再 rename）；冒烟开始时先删掉旧清单（现在 `rm(RELEASE_DIRECTORY)` 已删目录，保留）。清单里可加 `smokedAt` 或 `verified: true` 字段，publish 门禁要求它存在。`publish.test.ts` 补一条“清单缺验证标记时拒绝”。

## R02 重要｜正确性｜“未提交的改动”门禁查在发布时，而字节是在冒烟时打的；冒烟时工作区脏不会被发现

- **位置**：`scripts/release/publish.ts:92-96`（`git status --porcelain` 只在 publish 时查）；`scripts/release/pack-smoke.ts:359-374`（生成、打包、记 `commit` 时不查工作区）。
- **现象**：改成“发 smoke 打的 tarball”以后，干净工作区的检查仍留在 publish 一侧。tarball 是 smoke 当时从工作区生成的，清单只记 `git rev-parse HEAD`。流程：主工作区里 `packages/neuro-book`（或 nb-ui、nb-runtime 等被打进应用 bundle 的 9 个源码包之一）有别的会话未提交的改动 → 跑 `release:smoke`，tarball 含这些改动、`commit` 记为 HEAD → 那个会话 `git restore`/`stash` 掉改动（HEAD 不变）→ `release:publish` 的干净检查、提交检查、摘要检查全部通过，发出去的是一份不对应任何提交的代码。
- **为什么是问题**：publish 模块头说只看会发布的目录“是因为主工作区常有别的会话的改动”，即作者知道这种情况常见；这条门禁的本意是“发的是提交过的代码”，现在它检查的对象（发布时的工作区）已经不是发出去的东西（冒烟时的工作区）。清单的 `commit` 字段因此可能是假的。
- **如何核实**：读两处代码；`pack-smoke.ts` 全文没有 `git status`。
- **建议改法**：把同一条 `git status --porcelain --untracked-files=all -- <会发布的目录>` 挪到（或复制到）smoke 生成之前，工作区脏就拒绝打包（或在清单里记 `dirty: true`，publish 拒绝）；两处共用 `publish.ts` 里的目录列表，抽成 `manifest.ts` 的一个函数。根目录的 `bun.lock`、`package.json` 也影响生成结果，可一并列入。

## R03 建议｜测试｜冒烟的“重启后插件已加载”不要求结果来自运行中的实例，去掉重启也照样通过

- **位置**：`scripts/release/pack-smoke.ts:329-335`；对照 `packages/neuro-book/src/cli/plugin.ts:38-46,74-77`。
- **现象**：`nbook plugin list` 在找不到运行中的实例（或实例没有报 `plugins`）时退回 `previewInstalledPlugins`，按登记表“预演”一次启动：已启用、清单与入口都对的插件同样得到 `notLoaded: null`、`pending: []`。冒烟只断言这两项，没有看输出里的 `running`。所以第二次 `withNbook` 即使没起来实例、或者实例没有把插件算进启动集合，这一步也是绿的；把 `withNbook(...)` 换成直接调用回调，断言照样成立。
- **为什么是问题**：计划 3.2 第 3 步与 `repository-workflow.md` 写的判据是“实例应答的启动集合里它是已加载”，现在测到的是“登记表上它是好的”。
- **如何核实**：读 `inventoryFor`：`instance === null` 时 `startup = await previewInstalledPlugins(...)`；`itemOf` 里 `running = atStartup`，对已启用插件产出 `pending: []`。
- **建议改法**：断言 `listed.running?.pid` 存在（最好等于这次 `nbook start` 结果里的 `pid`，`withNbook` 把结果对象传给 `use`）。同一处顺带：第一次 `withNbook` 的 `checkWorkbench` 只等 `data-workbench-root` 上线，没有看书架；文档写“打开书架”，要么加一条书架的选择器，要么把文档改成“连上服务端”。

## R04 建议｜正确性（与计划不符）｜实际发布顺序是“源码包、应用、SDK”，计划写的是“源码包、SDK、应用”

- **位置**：`scripts/release/packages.ts:31-34`（`BUILT_PACKAGES` 应用在前）；`scripts/release/pack-smoke.ts:362`（`publishOrder([...源码包, ...built])`，清单按这个顺序写）；`scripts/release/publish.ts:140-146`（按清单顺序发）。
- **现象**：两个生成包的清单都没有 `@notnotype/*` 依赖，`publishOrder` 对它们保持输入顺序，于是应用先于 SDK 发布。计划 3.2 写明“顺序：源码包、SDK、应用”。
- **为什么是问题**：应用包的 README（npm 页面）与 `nbook` 的引导都让作者 `bunx -p @notnotype/nb-plugin-sdk …`；SDK 一步失败（OTP 过期、网络断）而应用已经发出时，npm 上有一段时间是“应用说去装 SDK，SDK 404”。先发 SDK 则失败只会让应用晚一点出现。影响小，但这是计划里明说的约束，实现没有遵守，也没有测试或注释说明顺序。
- **如何核实**：在 worktree 里 `bun -e 'import {BUILT_PACKAGES} from "./scripts/release/packages.ts"; console.log(BUILT_PACKAGES.map(p=>p.name))'`，得到应用在前。
- **建议改法**：`BUILT_PACKAGES` 改成 SDK 在前（`smokeAppAndPlugin` 里用 `[0]`、`[1]` 取包名的地方改成按名字查），或在 `publishOrder` 之后显式排序；注释写明为什么 SDK 先发。`release:check` 没有像计划 3.2 写的那样检查生成包与“源码包版本等于 `PRODUCT_VERSION`”（改由 smoke 做），也属与计划不符、不在已知偏离里，建议在 Task 记录里写一句。

## R05 重要｜正确性｜推 master 共用一个 concurrency 组，`cancel-in-progress: false` 仍会取消排队中的旧轮，F15 要防的“某次推送没人测”照样发生

- **位置**：`.github/workflows/ci.yml:14-17`。
- **现象**：推 master 的组名是 `ci-refs/heads/master`，所有推送（以及在 master 上手动触发的 `workflow_dispatch`）共用。GitHub 的 concurrency 语义：同组最多一个运行中、一个等待中；新一轮进来时，已在等待的那一轮会被取消，`cancel-in-progress: false` 只保证不取消“正在运行”的。连续推三次 A、B、C（check 一轮按实测可达几十分钟，本地合入后连推很常见）：A 在跑，B 排队，C 到达时 B 被取消；C 按 `github.event.before = B` 只测 B..C，B 那次推送（A..B）的改动没有任何一轮测过，而 A、C 都是绿的。
- **为什么是问题**：注释与计划 3.4（审查 F15 的处理）都写明要避免的就是这件事，现在的写法没有做到。
- **如何核实**：GitHub 文档 “Control the concurrency of workflows and jobs”：“Any existing pending job or workflow in the same concurrency group … will be canceled and the new queued job or workflow will take its place.”（`cancel-in-progress` 只影响正在运行的）。
- **建议改法**：推送不进 concurrency 组，例如 `group: ci-${{ github.event_name == 'pull_request' && github.event.pull_request.number || github.run_id }}`（push 与手动各自独占一组，互不取消）；或者推 master 时基准不用 `event.before`，改用“上一次成功的 CI 运行的提交”（要额外权限与 API 调用，不如前者简单）。

## R11 重要｜正确性（隔离）｜`bunx -p <tarball>` 的安装缓存在 `$TMPDIR/bunx-<uid>-@<tarball 绝对路径>/`，不随 `HOME`、`BUN_INSTALL` 隔离；重跑冒烟时 `create` 用的是第一次那份 SDK

- **位置**：`scripts/release/pack-smoke.ts:308`（`env` 只换了 `BUN_INSTALL`、`HOME`、`XDG_*`、`PATH`）、`:320`（`bunx -p <sdkSpec> nbooke create …`）。
- **现象**：bunx 把 `-p` 的包装进系统临时目录下按包写法命名的目录，下次同样的写法直接复用，不看 tarball 内容。`--from pack` 时写法是 `dist/release/notnotype-nb-plugin-sdk-0.11.0.tgz` 的绝对路径，每次冒烟都一样（版本不变、文件名不变）；于是第二次及以后的冒烟里，`nbooke create` 跑的是第一次冒烟那份 SDK 的命令与模板。之后 `bun install` 用 `--sdk file:` 装的是新 tarball，所以 `build`、`typecheck` 用的是新的，但“生成插件”这一步（模板、`create` 的合并逻辑、写进 `package.json` 的依赖）验的是旧字节。这也与模块注释和计划 3.2（审查 F08）说的“临时 `BUN_INSTALL` 与 `HOME`，不碰开发者自己的全局包、缓存”不符：缓存写在共享的 `/tmp/bunx-<uid>-@/…` 下，冒烟结束也不删。
- **为什么是问题**：发布前通常要“改一处、重跑冒烟”好几轮（计划第 7 节的发布步骤本身就要在主工作区再跑一次）；模板或 `create` 的回归会被旧缓存遮住，而发布的正是新的那份 SDK。版本号发出去不能再用。
- **如何核实**（scratch 里做过，已清理 `/tmp` 下的探针目录）：做一个带 bin 的小包 `1.0.0`，`bun pm pack` 到固定路径；用新的 `HOME`、`BUN_INSTALL` 运行 `bunx -p <tarball> zzprobe` 打印 `A`；改成打印 `B` 后重新打包到同一路径，再换一组全新的 `HOME`、`BUN_INSTALL` 运行，仍打印 `A`。第三次只多设 `TMPDIR=<新目录>`，打印 `B`，缓存目录出现在新 `TMPDIR` 下（`bunx-1000-@`）。Bun 1.4.2。
- **建议改法**：`smokeAppAndPlugin` 的 `env` 加 `TMPDIR: join(root, "tmp")`（先建目录），让 bunx 的缓存落进本次冒烟的临时根、随它删除；registry 模式同样受益（不复用以前从 registry 装过的同名版本）。顺带把 `BUN_INSTALL_CACHE_DIR`、`XDG_CACHE_HOME` 也显式指进临时根，免得开发者环境里设了它们时漏出去。

## R12 建议｜正确性｜续发时“已发布，跳过”不比对字节：中途失败后改了代码再冒烟，已发的那几个包与这次验过的不是同一份，门禁不提示

- **位置**：`scripts/release/publish.ts:141-146`（`npm view <名>@<版本> version` 只看版本在不在）。
- **现象**：场景：发到第 5 个包失败，原因要改代码（不只是 OTP 或网络），于是提交修复、推送、重跑 `release:smoke`（新提交、新 tarball、新清单）、再 `release:publish`。前 4 个包版本号没变，被“已发布，跳过”；冒烟验的是新提交上这 4 个包的 tarball 与其余包的组合，用户装到的却是 registry 上旧提交的那 4 个。清单里明明有这 4 个包的新 SHA，门禁没有拿它与 registry 上的对比。
- **为什么是问题**：本期的目标是“发出去的就是验过的字节”，续发是 brief 点名的情形；跳过逻辑沿用 base（base 也只看版本），但现在清单里已有摘要，检测几乎零成本。
- **如何核实**：读 `main()` 的待发列表；`npm view <名>@<版本> dist.shasum dist.integrity --json` 可取 registry 上 tarball 的 SHA-1 与 SHA-512。
- **建议改法**：对“已发布”的包再取 `dist.integrity`（或 `dist.shasum`），与本地 tarball 的 SHA-512（或 SHA-1）比较；不同就停下并提示“这个包要先提高版本号”，而不是跳过。`publish.test.ts` 按现有 `publishedState` 的写法补一条纯函数用例。

## base 上就有的问题（另记，不计入本期条数）

- **CI 不钉 Bun 版本**：`ci.yml` 两个 job 的 `oven-sh/setup-bun@v2` 都不给 `bun-version`，仓库根也没有 `packageManager` 或 `.bun-version`，于是 CI 用的是当时最新的 Bun；本机与干净克隆验证用的是 1.4.2。Bun 的小版本改过锁文件与 `bun pm pack` 的行为，`--frozen-lockfile` 可能在某天无故失败，或者 CI 打出的包与本机不同。旧的三份 workflow 也一样没钉。建议加一个 `.bun-version`（或根 `package.json` 的 `packageManager`），两个 job 用 `bun-version-file`。
- **冒烟里读子进程输出只读第一行**：`withNbook`、`smokeServe` 读完结果行后不再读 `stdout`，`stderr` 只在失败时读；子进程写满管道（约 64 KB）会阻塞。`firstLine` 也没有超时，`nbook` 卡住不打印时冒烟无限等待、临时根不清。`smokeServe` 在 base 就是这样，`withNbook` 沿用了写法。
