## F1 [重要] 测试：打开视图命令的声明属性与整条接线没有任何测试
- 位置：packages/neuro-book/src/plugins/workbench/web/commands/view-commands.test.ts:179-227；declarations 在 view-commands.ts:33-43
- 现象：测试只直接调用 viewCommands(...)[OPEN_VIEW_COMMAND].run(...)。声明里的 expose.agent "never"、effect "write"、when 要 layoutReady 三项（计划第 6 节“Agent 调用：not-exposed”）没有一例断言；“经真实命令注册表登记”那一例只登记 MOVE_VIEW_COMMAND。
- 核实（副本里变异，重跑 view-commands.test.ts）：把打开视图的 expose.agent 改成 "auto"、effect 改成 "read"、when 去掉 layoutReady，三种变异都是 10 例全过（0 失败）。对照：去掉“展开收起的视图”、reveal 改成只显示侧栏、去掉 reveal、未知视图码改 unavailable，各有 1 例失败，说明行为本身测到了。
- 为什么是问题：“不对 Agent 开放”是安全属性，被改成 auto 后 Agent 可以直接改布局记录而无人发现；when 去掉后外壳没打开时命令面板仍会列出它（run 里虽然有 unavailable 兜底，但与 Spec 输出 14“when 要布局已就绪”不一致）。
- 建议：在测试里用真实注册表登记 OPEN_VIEW_COMMAND（同 MOVE 那一例），断言 Agent 调用得 not-exposed、布局没打开时 isEnabled 为 unavailable、打开后可用。

## F2 [重要] 作者 API：statusItem 的 command 收下任何助手，“写错类型编译不过”不成立
- 位置：packages/neuro-book/src/sdk/workbench-helpers.ts:70-79（ItemCommand 与 itemCommandOf）；测试 src/sdk/browser-helpers.dom.test.ts:44-47 与文件末尾 typeChecks
- 现象：ItemCommand = CommandHelper | ViewHelper | {id, args?}。任何助手都有 `id: string`，变量（非字面量）传进来不做多余属性检查，所以落进第三个成员。运行时 itemCommandOf 里 `"contribution" in command` 为真、贡献点不是视图，就当命令处理，产出 `{id: 助手的 id}`。
- 核实：在副本里写 scratch 文件，`statusItem(plugin, {name, title, command: settingsPage 助手})`、`command: 另一个 statusItem 助手`、`command: choices 助手` 三个都通过 vue-tsc（tsconfig.web.json）；运行时得到指向并不存在的命令的条目，点击没有任何反应（见 F3）。把 ItemCommand 的第三个成员改成 `NonNullable<ItemDeclaration["command"]> & {readonly contribution?: never}` 后这三个都按预期报错（同时需要在 itemCommandOf 里对 `command.contribution` 做 undefined 收窄）。
- 为什么是问题：计划 3.4 写明“命令助手与视图助手按各自的 kind 字段区分，不再用 `"contribution" in command`，写错类型编译不过”，且这是上一轮 Sonnet F09 的处理结论。实现仍用 `"contribution" in command`，也没有写进计划第 10 节的调整；测试只有正例，typeChecks 里没有一条 @ts-expect-error 反例，所以退化没有被发现。
- 建议：按上面的类型改法收紧（或按计划给助手加 kind 字段），在 typeChecks 里加三条反例（设置页助手、状态栏条目助手、选项来源助手）；若保留 capability 比较，把偏离写进计划第 10 节。

## F3 [建议] 前端行为：状态栏条目点击丢弃命令结果，视图打不开时没有任何反应
- 位置：packages/neuro-book/src/plugins/workbench/web/titlebar/titlebar-source.ts:183-186（runItem：`void commands.execute(...)`）；失败通知 commands/failure-notice.ts 只接命令面板与键位
- 现象：状态栏条目收视图助手后，点击执行 nbook.view.open {viewId}。视图所属入口激活失败、声明被拒或插件被禁用时，命令返回 invalid-args（“没有这个视图”），结果被丢弃，用户点了没有反应、也没有通知；按钮此刻是可点的（isEnabled 只看 layoutReady，不看目标视图是否存在）。同理，command 收一个有必填参数的命令助手（expose: {human: false}，类型允许）时点击得 invalid-args，同样静默。
- 为什么是问题：failure-notice.ts 开头的理由就是“点了没反应是作者与用户都看不出原因的失败”，作者文档“命令没反应”一条只讲命令面板与快捷键，状态栏条目是遗漏的第三个入口；本次新增的“条目点击打开视图”正好把唯一的失败路径（invalid-args）放在了这个入口上。Spec（workbench-shell 外壳四条目点击）只写了“命令不可用时禁用并以原因作提示”，没写失败反馈，所以是缺口而不是违约。
- 核实：从代码推断（runItem 与 failureNotice 的调用点）；未跑 e2e。
- 建议：runItem 的结果交给 failureNotice 同一条通知路径；或在 README 的“命令没反应”里补一句状态栏条目的失败不会弹通知。

## F7 [建议] 小项（可不改）
- Lab 场景注释错位：src/plugins/lab/web/fixtures/PluginsPageFixture.vue:93-94 两行 JSDoc 叠在一起，原来属于 `failing` 的注释（“write-failed”“version-in-use”“busy”场景的安装结果）现在悬在 `FailureOf` 类型上面，`failing` 自己没有注释。`FailureOf<"enable">` 同时给 disable、uninstall 用，当前三者失败类型相同所以没问题，哪天分开会静默变形。把 `FailureOf` 的注释放到类型上，`failing` 的注释放回去。
- 空操作也会写记录：对已选中且可见的视图再打开一次，applyView 因为传了 reveal 仍提交一次修改。记录已存在时 persisted 层判为 unchanged 不写盘（实测 queue 短暂为 1 后回 0，display 不变）；记录不存在时（用户从没改过布局）会因此创建布局记录（实测 base 从 missing 变 ok），右栏视图还会多写一个 shownParts。后果只是多一条记录，属于拖动预备区那条规则（layout-store.ts:213-216“意图无变化时照样显示”）的副作用，收益很小，可以不改。
- examples/plugins/focus/shared/contracts.ts:88-94 原来给 `focusCommand` 的说明（“用户自己的节奏，不交给 Agent……写在合同模块里，别的插件按 id 执行它们”）现在挂在 `focusCommandBase` 上，读起来像在说一个常量；三条命令的 `// 直接调用 command` 注释又在下面。可以把说明挪到三条命令前。
