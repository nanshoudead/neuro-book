现象：计划把 claimStateRoot 放在 runServerProcess 里（process.ts:62，prepareInstalledPlugins 之前）。但 src/server/testing/fixture-entry.ts 自己重复了启动序列：第 43 行 readServerConfig、第 60 行 startServer、第 67 行 prepareInstalledPlugins，完全不调用 runServerProcess。用 fixture-entry 起进程的有：

建议改法：把“取锁并在 server.stopped 之后放下”抽成一个 instance.ts 里的函数，让 runServerProcess 与 fixture-entry 都调用它（或让 fixture-entry 改走 runServerProcess，把测试插件作为选项传入）；S1 的进程测试同时覆盖 MAIN 与 FIXTURE 各一次，并在 smoke-server.ts 加一条打包产物的单实例场景（见下面 Spec 遗漏一条）。

### 重要 | 正确性 | 计划 3.1 第三条、第 8 节第一条风险 | 开发入口也受锁约束，但只给 nbook start 设计了等锁；nbdev/TaskStop 杀掉开发会话后马上重起会进入“后端启动失败、等改动”的死状态

现象：dev-panel 的 dev-ops.ts:22 写明 Claude Code 的 TaskStop 对整棵树发 SIGTERM，约 1.5 秒后整棵 SIGKILL；开发监督的第二个信号也是 supervisor.kill() 即 SIGKILL（dev/backend-process.ts kill()）。开发状态根缺省是每个 worktree 固定的 packages/neuro-book/.dev-state（dev/config.ts），重起时是同一个目录。
实测（真实 holdLock，Bun）：process.exit(0)、process.exit(1)、带 SIGTERM 处理的退出、无处理的 SIGTERM，锁目录都被 proper-lockfile 的退出钩子清掉；只有 SIGKILL 会留下锁目录。SIGKILL 之后新进程取锁：在约 10 秒内失败，实测 3312 ms 才返回 locked（holdLock 内置约 3.3 秒退避），约第 10 秒后才取得。
后果：后端首次用 SIGKILL 结束后 10 秒内再 nbdev dev start，新后端 runServerProcess 取不到锁、写 runtime.state-root.busy 并以 1 退出；监督进程（supervisor.ts）把它判为 backend-start-failed，进入 waiting，“下一次改动才重试，不循环重启”，页面服务活着、/api 一直 503。计划里的等锁重试只写在 `nbook start`，开发入口走 runServerProcess 的同一路径却没有。
如何核实：锁行为见 /tmp/review-t15-p2plan-tests/holder.ts、run.sh、probe.ts；监督行为读 supervisor.ts 的 launch()/exited 分支。SIGKILL 与 nbdev 的时间关系是从代码推断，未跑 nbdev。
建议改法：等锁过期的重试放进共用的取锁函数（runServerProcess 层），nbook start 与开发入口共用，busy 的诊断里写“上一个实例 N 秒内异常结束，等待锁过期”；或者开发入口的状态根锁用更短的 stale（开发进程仍须与产品进程一致，不可行时第一种）。dev.e2e 加一条“SIGKILL 后重起”用例（配合下条的拨回 mtime 技巧，不要真等 10 秒）。

### 重要 | 测试 | 计划 S1 自跑验证、第 8 节第一条风险 | “崩溃后 10 秒”无法按仓库规则写成测试，计划没写怎么测

现象：S1 要求“第一个被 SIGKILL 后重新启动成功”，第 8 节要求 nbook start “等锁过期再试一次（至多 15 秒）”。真实时间下：锁要约 10 秒才能被接管，bun test 缺省单测 5 秒超时；docs/testing/README.md 禁止固定等待（fixed-wait 机检）并给 200 ms 的快速层预算。busy 的返回本身也要 3.3 秒（holdLock 的 LOCK_RETRIES 约 12 次退避，locked-replace.ts 第 33 行），所以“第二个进程以 1 退出带地址”这条每次也固定多花 3.3 秒（实测 3312 ms）。
为什么是问题：写测试时只剩两个选择，真等（违反规则、慢、flaky），或在产品代码里给 stale 开一个测试专用的环境变量（AGENTS.md 禁止“在产品代码里加测试专用分支”）。
如何核实：/tmp/review-t15-p2plan-tests/probe.ts 的输出（live 持有者 3312 ms 失败；SIGKILL 后第一次探测失败，约 11 秒后成功）。
建议改法：沿用现成的做法：plugins.test.ts:521 用 utimes 把锁目录的 mtime 拨回，再启动第二个进程，立刻成功，无需等待。计划里写明这一点，并让 claimStateRoot 接受 retries/stale 选项（pins.ts 的租约测试已经传 stale），nbook start 的“等过期再试”用注入时钟做单测。再决定第二个进程对 busy 的退避：用于“是不是有实例”的判断不该白等 3.3 秒。

### 重要 | 测试（兼设计） | 计划 3.1 第二条、3.2 start 第 1 步 | 第二次启动落在“第一个实例已持锁、尚未写地址文件”的窗口里，行为没写、也没测；findRunning 的健康探测没有超时

现象：地址文件在“HTTP 与 RPC 都监听之后”才写，而取锁在 prepareInstalledPlugins 之前，中间还有插件装配与启动激活（几百毫秒到数秒，装了第三方插件更久）。这段窗口里：
1. 持锁、server.json 不存在：findRunning 得到 null（running: null）。nbook start 于是走第 2 步，进程内 runServerProcess 取不到锁，以 1 退出报 runtime.state-root.busy，诊断里没有地址。用户双击两次、或两个终端几乎同时 nbook，结果是第二个报错，而不是“打开已有实例”，这正是计划要对标的“第二次运行 code”场景。
2. server.json 已写、插件还在激活：GET <url>api/runtime/health 在就绪前会挂起等待（backend-process.ts 头注释、server-host Spec 启动序列第 5 步：“就绪前的请求会等待，启动失败时得到 503”）。计划没有给探测设超时，nbook start 与 nbook plugin list（也调 findRunning）会一直等第一个实例就绪，实例卡在启动里就永远等。
S1/S2 的自跑验证只测了“实例已就绪之后再启动第二个”，这两个窗口都没覆盖。
如何核实：读 plan 3.1/3.2；health 的挂起语义见 src/server/dev/backend-process.ts 头注释与 docs/specs/runtime/server-host.md 启动序列。窗口时长未实测。
建议改法：Spec 里先定第二次启动落在窗口里怎么办（建议：持锁但没有地址或没有就绪时，等到有地址再打开它，带上限；上限到了报 busy 并说明“正在启动”）；findRunning 的探测加短超时（例如 2 秒），把“超时”和“连不上”区分成不同结果；S1 加一条“两个进程几乎同时启动，恰好一个运行、另一个或者打开前者的地址或者带地址报 busy”（用两个真实进程，等 Listening 之前就放第二个）。

### 重要 | 测试 | 计划 5 节 S2 到 S4 的自跑验证 | S2 至 S4 的进程测试依赖完整的 dist/ 产物，仓库里没有任何快速层测试依赖构建产物

### 重要 | 测试 | 计划 5 节 S4、第 7 节端到端 | npm 包验收只到“health 与首页 200”，没有覆盖这条路径独有的三件事

这条发行路径与已有 e2e 的差别正是：webRoot 靠 bundle 相对位置、project.js 与 nbook.js 同目录、插件装进状态根后重启生效。pack-app.test.ts 列出的断言（--version、start --no-open 后 health 与首页 200、plugin install 示例插件）测不到：

### 重要 | 测试 | 计划 6 节“nbook start”一行、S2 | 打开浏览器、已有实例时打开它的页面、Ctrl-C、地址文件的生命周期都没有对应测试

### 建议 | 测试 | 计划 3.1“受影响的既有行为”、第 4 节 component-lab 行 | Lab 场景 22 的改写：放行没问题，但丢掉了“全新进程读到磁盘上的偏好”，而 Spec 原文是“先后”

- localhost 与 127.0.0.1 是两个不同的浏览器来源，localStorage 与客户端身份（web/host/client-identity.ts，存在各来源自己的 localStorage）都不同；

问题在覆盖：原用例（lab.e2e.ts:352 起）里第二个开发服务是全新的后端进程，从磁盘读 first 写下的 shared 偏好；改写后读的还是同一个后端进程的内存与同一个 SQLite 连接，“进程重启后偏好仍在”这半条不再被这条用例碰到。component-lab.md 验收 22 的原文是“同一状态根先后用两个端口启动开发服务”，“先后”本身与单实例相容：先停第一个、再起第二个。
注意：原用例里第二个页面用 browser.newPage()，本来就是新的浏览器上下文（新的客户端身份），所以改成别名之后，“换来源”这一半其实由 newPage 单独就保证了，别名没有增加覆盖。
建议改法：保持原场景与 Spec 原文（“先后”）：这条用例自己起一个专用的开发会话（独立的 tmp 状态根），写偏好后停掉它（SIGTERM，退出码 0），再在同一状态根起第二个，用 browser.newPage() 打开，断言偏好相同。代价是多一次开发服务的启动时间（未测）。如果坚持用别名，则 Spec 验收 22 的措辞要改成覆盖面更小的说法，并另说明“进程重启后偏好保留”由哪条用例承担。

### 建议 | 测试（兼设计） | 计划 3.2 main.ts / plugin.ts | 退出码 2 与 `list --json` 的输出形状要有测试，commander 的缺省行为与计划不同

- 计划写“退出码 0 成功，1 失败，2 用法错误”。实测 commander 14.0.3：未知选项、缺参数都以 1 退出（/tmp/review-t15-p2plan-tests/cmd.ts），要得到 2 必须 exitOverride 或自定义输出；不写测试的话最先实现出来的是 1。另外 isDefault 的 start 下，把子命令拼错（nbook plguin list）得到的是误导的“too many arguments for 'start'”并以 1 退出（cmd2.ts），用法错误的提示和退出码都值得一条用例。
- plugin list 有运行中实例时“首行写‘变化在 <url> 的服务端重启后生效’”：带 --json 时这行如果写到标准输出，JSON 就不可解析。S3 的“list --json”用例要在服务端正在运行时跑一次，断言标准输出整体是合法 JSON，提示走标准错误或进 JSON 字段。
- nbook plugin 子命令每次都调用 findRunning（含 HTTP 探测）；没有实例时不应有任何等待，S3 加一条“没有实例时 list 在亚秒内返回”。

### 建议 | 不变量 | 计划第 8 节第一条风险 | 主线程被同步任务卡住 5 到 10 秒就足以让持锁的活实例被判为残留，第二个 nbook 会再起一个

锁靠主线程的计时器每 5 秒刷新（proper-lockfile 的 update 取 stale/2），锁在 mtime 超过 10 秒时被判为残留。主线程同步阻塞（Storage 用 bun:sqlite 的同步接口（partition.ts:12）、大目录扫描、第三方插件的同步计算——stall-watchdog.md 的阈值也是 10 秒，说明这类阻塞是被预期的）从最近一次刷新之后超过 5 秒就可能让锁过期，而看门狗还没触发。此时：健康探测同样因主线程阻塞而失败，findRunning 判为无实例，第二个 nbook start 取到被判为残留的锁，在同一状态根起第二个实例，正是单实例要防的状态。计划对“暂停超过 10 秒”的处理是 stillHeld 发现后“记诊断，不自行退出”，等于允许两个活实例并存。
这条无法在测试里自然复现（需要阻塞主线程 5 到 10 秒），我没有实测；机制来自 locked-replace.ts 的 LOCK_STALE_MS 与 proper-lockfile 默认刷新间隔，加上实测的“SIGKILL 后约 10 秒可接管”。
建议改法：要么把状态根锁的 stale 设得比看门狗阈值与预期最长阻塞明显更长（例如 30 秒，代价是崩溃后重启要等得更久，nbook start 的等待上限同步调整），要么 findRunning 在“锁过期但 server.json 的 pid 仍存活”时不接管，而是报告“实例无响应”。选哪个要在 cli.md/server-host 里定下来。
