### 重要｜正确性｜未声明依赖的检查按服务值形状比较，不能按服务键识别

- **位置**：`packages/neuro-book/src/sdk/plugin.ts:80-82,98-101`（本报告源码路径均相对 worktree `/home/notnotype/CodeRepository/neuro-book/.worktree/w00027-t15-impl-review`）。
- **现象**：声明 `a = defineServiceKey<{now(): number}>("acme.test/a")` 后，未声明的同形状键 `b = defineServiceKey<{now(): number}>("acme.test/b")` 仍能直接传给 `context.services.require(b)` 与 `resolve(b)`，类型检查无诊断；声明 `ServiceKey<{}>` 时，连不同接口的键也能通过。
- **为什么是问题**：S5 与计划 3.7 承诺未声明键在编辑器就报错，但 `ServiceKey<T>.name` 是普通 `string`，`Declared` 只比较值类型的结构可赋值性。两个实际不同的服务恰好同接口时，检查完全失效；真实激活会因未解析的必需依赖抛 `TypeError`，入口失败。现有反例用 `now()` 与 `other()` 两种不同形状，漏掉了最基本的同形状不同 id。
- **如何核实**：仓库外 `/tmp/review-t15-impl-omp/types.ts`；执行 `node node_modules/typescript/bin/tsc -p /tmp/review-t15-impl-omp/tsconfig.json --pretty false`，TypeScript 5.9.3 退出 0，无诊断。执行 `bun /tmp/review-t15-impl-omp/dependency-runtime.ts`，真实 `createApplication` 启动返回激活失败，原文 `acme.test/b 不是入口 acme.test/server 已解析的必需依赖`，最后正常关闭。基线无此编译期检查；这是本次新增判据未实现，不是把原有运行时限制当回归。
- **建议改法**：服务键类型携带稳定 id 的字面量类型，依赖检查按 id 比较；同步迁移键的定义与声明生成。若暂时无法保留 id，明确撤回“未声明键必然编译不过”的承诺，不能以值接口的结构兼容性冒充键身份。增加同形状不同 id、可选键与必需键同形状的编译期反例。

### 重要｜正确性｜方法上下文的 fail 接受联合失败码时可漏掉必需详情

- **位置**：`packages/nb-runtime/src/remote/contract.ts:190-199`。
- **现象**：方法有 `missing: Type.Undefined()` 和 `bad: Type.Object({max: Type.Number()})` 两个业务码，输入 `code` 类型为 `"missing" | "bad"`。实现直接写 `get: ({code}, ctx) => ctx.fail(code)` 无需断言便编译通过；输入 `bad` 时实际上没有交出必需的 `{max}`。
- **为什么是问题**：`DetailArgs` 在整个 `Code` 联合上检查 `undefined extends Static<errors[Code]>`：只要任何一个码允许无详情，所有码的详情参数都变成可选。返回类型又声称是合法的 `BusinessFailure`，绕过外层结果校验。提供方按新推荐写法转交输入里的业务码，调用方却得到 `provider-error` 而不是声明的业务失败。改前根助手 `fail(code)` 的结果会在 `provideRemote` 处正确报缺详情，本次上下文助手反而抹掉了这个错误。
- **如何核实**：`/tmp/review-t15-impl-omp/union-types.ts` 同时包含新助手的错误实现（无错误抑制）与根助手反例（`@ts-expect-error`）；`node node_modules/typescript/bin/tsc -p /tmp/review-t15-impl-omp/tsconfig.json --pretty false` 退出 0。真实运行 `bun /tmp/review-t15-impl-omp/union-fail.ts`，`bad` 返回 `{"ok":false,"code":"provider-error","detail":"失败 bad 的详情不符合合同：/：must be object"}`，`missing` 返回 `{"ok":false,"code":"missing"}`；应用正常关闭。
- **建议改法**：将参数建模为按业务码分布的元组联合（`[code: "missing", detail?: undefined] | [code: "bad", detail: {max: number}]`），让码和详情保持相关；或拒绝未收窄的联合码，要求作者先按码分支。补“一个无详情码加一个有详情码，联合码不得无详情调用”的编译期反例。

### 建议｜正确性｜错误堆栈解析拒绝合法目录名，丢失作者模块定位

- **位置**：`packages/neuro-book/src/plugin-platform/build/build-plugin.ts:236-256`。
- **现象**：作者目录叫 `author (copy)` 时，共享模块 `shared/contracts.ts:2` 顶层抛错，构建问题却定位到导入它的 `backend/plugin.ts`，消息附的是 Vite 的 `module-runner.js:6:17`；没有真正的作者文件与行号。
