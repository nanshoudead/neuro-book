# w00027 t02 修订版与 t08：只读设计审查

审查日期：2026-10-20。计划与 Task 依据读取主工作区；源码依据读取 `.worktree/w00027-plugin-platform/`。以下是计划缺陷；尚未实现的行为不冒充产品故障复现。按影响排序逐条追加。

## 问题

### 1. 重置先移走提交文件，再生成主密钥，崩溃后会把未完成重置误判为空库

- **严重程度**：阻断；**类别**：不变量、崩溃恢复。
- **位置**：t08 `plan.md:47,53,58-59,71,121-122`，“存储的状态”“主密钥从哪来”“并发与崩溃”。
- **现象**：重置顺序为 `rename(secrets.json, secrets.json.reset-<时间>)` → 探测并保存新主密钥 → 写空的新文件。第 1 步之后任意一次崩溃、密钥库操作失败、写盘失败，都会留下不存在的 `secrets.json`；重启按状态表得到 `empty`，所有旧项报 `unset`，下一次普通写入又自动初始化。备份文件存在不等于提交状态可恢复。
- **为什么是问题**：原来的“整库不可读，必须显式重置”已经失去持久状态；一个失败/结果未知的重置能在下次启动变成成功重置。第 59 行只讨论首次初始化的孤儿主密钥，不能恢复重置事务。锁只解决并发，不解决先移走正式文件造成的崩溃窗口；现有 `replaceLocked` 也只原子替换一个文件。
- **如何核实**：按计划顺序在重置第一次改名后终止进程，再套用第 47 行的不存在规则，必然是 `empty`；现有 `src/backend/locked-replace.ts:143-187` 的提交点仅为最后一次 `rename(temporary, file)`。这是计划时序证明，未声称运行了尚不存在的 reset。
- **建议改法**：旧正式文件保持原位，先准备新主密钥与空库临时文件；在锁内保存旧文件的备份副本，核对 `stillHeld`，最后只用一次原子替换发布新库。失败时旧正式文件仍可读，未提交的新密钥按孤儿处理。备份名使用随机唯一后缀并排他创建，不仅依赖时间。验收分别在备份后、新主密钥保存后、替换前/后强杀并重启；区分“旧库仍在”与“新空库已提交”，不能出现第三种空文件缺失态。

### 2. 主密钥缓存没有绑定已提交的 `key` 描述，另一个服务端重置后仍可能使用旧主密钥

- **严重程度**：重要；**类别**：不变量、跨进程一致性。
- **位置**：t08 `plan.md:38,52,71-72`，“存储的状态”“并发与崩溃”。
- **现象**：“拿到后留在内存，直到服务端停止”与“持锁后重读文件”之间缺少缓存失效规则。A 缓存 K1，B 显式重置为 K2；A 下一次持锁已经看到新 locator/check，却没有规定必须丢弃 K1、获取 K2 并重新核对 check。只监视文件或重读 JSON 不会自动刷新主密钥。
- **为什么是问题**：按旧缓存加密的条目会被写进引用 K2 的文件，其他进程及 A 自己重启后都不能解密；若每次拿旧缓存对新 check 核对但不重取，又会把正常的外部重置误判为 `unrecoverable`。没有实时通知可以接受，持锁写入使用正确主密钥不能豁免。同样要写清已经成功缓存后系统密钥库锁住/条目被删的语义：继续使用已获得的能力，还是重新探测，不能同时承诺两者。
- **如何核实**：以 A 读旧库、B 重置、A 写新键三步推演第 52、71、72 行；当前计划的并发验收只覆盖首次初始化，不覆盖重置后的缓存。此为计划缺口，未运行不存在的存储实现。
- **建议改法**：缓存绑定完整的已提交 `key` 元数据（至少 store、locator、check），每次持锁重读后先比较，变化即失效并获取当前主密钥，确认 check 后才写；读值至少在下一次实际读取时核对当前库身份。无须增加主密钥代次字段。补两个真实服务端 A/B 的“缓存后重置再读写”，以及缓存成功后密钥库临时不可达的明确判据。

### 3. 普通层只过滤 `values`，新增的全文接口会重新把人工写入的密钥发给浏览器

- **严重程度**：重要；**类别**：安全、合同一致性。
- **位置**：t02 `plan.md:30,78,94,119-120,143`；t08 `plan.md:7,94,124`。
- **现象**：S1 只明确 `settings.json` 的密钥键不进层快照，`set`、`edit` 拒收；S5 又承诺 `readText` 返回文件全文，`writeText` 只明确解析与重复键校验。人工写进 user/project 文件的密钥仍留在原文中，因此全文响应直接绕过过滤；原文写入也没有明确禁止新增密钥键。
- **为什么是问题**：这是上一轮第 10 条已经点出的旁路，拆分后没有闭合。t08 的错误脱敏不能保护 t02 所拥有的原文接口；“普通层拒收”不是删除磁盘已有文本，也不自动约束原文读取。即使密钥服务完全正确，浏览器仍能收到被声明为 secret 的旧明文值。
- **如何核实**：对照 t02 第 30 行“不进 values”与第 78 行“文件全文”；现有 `backend/layer-text.ts:30-54` 的解析结果与原始文件文本是两份数据，`owner-link.ts:52-54` 只负责快照。尚无 readText 实现，本条为明确的计划合同冲突。
- **建议改法**：在 S1 就定义人工残留明文的处理，并让 S5 继承：含已声明 secret 键时，全文读取返回不含值的固定错误及键/位置，允许用户在本机移除；或定义不会把原值发出的脱敏编辑协议，但不能把脱敏文本当原文无条件回写。`writeText` 明确拒绝新增 secret 键；允许清除残留时按修订号条件写入。补 user/project 文件、readText/writeText、错误响应与诊断的唯一标记泄漏检查。

### 4. `holdLock` 后再用现有“加锁替换”会重入同一把锁，计划缺少可用的提交接口

- **严重程度**：重要；**类别**：依赖机制、实施可行性。
- **位置**：t08 `plan.md:13,71`；worktree `src/backend/locked-replace.ts:53-75,143-187`。
- **现象**：计划要求先 `holdLock`，在锁内异步获取/产生主密钥，之后“写文件用加锁替换”。现有导出的 `replaceLocked` 自己再调用 `holdLock`；真正接受持锁核对的 `replaceOnce` 是私有函数，`decide` 则只能是同步纯函数。当前接口没有“已经持锁后提交”的模式。
- **为什么是问题**：照字面组合会被自己的外层锁阻挡，约 3 秒后失败；若先释放外层锁再替换，又把第 2 条上一轮审查要求的初始化临界区拆开。把异步密钥副作用塞进 `decide` 也不成立：该回调会在冲突重试时重复执行。
- **如何核实**：实际运行 `bun /tmp/neuro-book/review-w00027-r2/lab/t08/runtime-smoke.ts`，工作目录为 worktree `packages/neuro-book`。真实 `holdLock` → 同路径 `replaceLocked` 返回 `{\"ok\":false,\"reason\":\"failed\",\"detail\":\"写入锁一直被别的进程占着\"}`，耗时 3320 ms，文件仍为 `old`。
- **建议改法**：在 S2 明列最小的共享帮助函数改造：拆出接受 `HeldLock`/`stillHeld` 的提交操作，由 `replaceLocked` 负责取得锁再复用它，密钥存储则在同一外层锁内调用；不复制一份临时文件、权限、sync、身份核对与清理逻辑。提交前重新核对锁与所读文件身份，失败时不发布主密钥引用。验收包含“已持锁提交成功”与锁被接管时拒绝提交。

### 5. 只绑定插件 id 不能约束 `ctx.activation.trigger` 的寿命，旧上下文能借新登记继续触发

- **严重程度**：重要；**类别**：生命周期、接口。
- **位置**：t02 `plan.md:51,55,95,136`；worktree `packages/nb-runtime/src/plugins/host.ts:498-533,1019-1036`。
- **现象**：关键设计只有“绑定 requester 后内部调 triggerActivationEvent”；后面的验证提到“入口停止后调用”，却没定义停止后的返回值、是否派发或怎样绑定入口代次。现有 host 方法只查当前前缀拥有者，不检查发起入口、代次或停止信号。
- **为什么是问题**：插件 id 仍存活时，一个入口停止不使插件级前缀失效；旧插件登记关闭后，同 id 重新登记也会让旧闭包再次通过拥有者核对。仅合并一个已 aborted 的等待信号仍不够：`#activateByEvent` 先逐项调用 `activate`，取消等待不等于不启动激活。测试不能在没有合同的情况下自行选择停止语义。
- **如何核实**：上述 runtime smoke 在 browser/server 各运行真实 host：旧拥有者激活上下文的 `signal.aborted === true`，关闭旧登记并重新登记同 id 后，用只绑定旧 `ctx.plugin` 的闭包调用 host，仍得到 `triggered` 并激活 `demo.late/late`。这是对计划所述转发方式的实验，不声称新 ctx API 已存在；两端输出一致。
- **建议改法**：在激活上下文构造处捕获本次 attempt；调用入口首先核对该 attempt 尚可接纳，停止后返回写定的结构化拒绝且不枚举/激活目标；等待再合并调用方 signal 与入口 stopSignal。前缀归属只复用输出 21 的现有核对，不另建权限表。补同插件两个入口、旧代次与同 id 新登记、停止前后竞态的两位置测试。留在 ctx 比放进仅浏览器的 `window.plugins` 更适合通用机制，缺的是寿命门禁，不是再增加宿主能力。

### 6. 打包 smoke 接受所有 `unavailable`，无法区分“没有密钥库”和“原生依赖根本没交付”

- **严重程度**：重要；**类别**：构建交付、验收。
- **位置**：t08 `plan.md:64,66-67,108,125,139`；worktree `scripts/check-dist.ts:37-55`、`scripts/smoke-server.ts:28-41,161-165`。
- **现象**：脚本加载失败、非零退出与平台密钥库不可用都被归为 `unavailable`，产物 probe 的合格结果又允许 `unavailable`。external 备选只说“从安装目录解析”，没有规定安装目录/原生平台包如何随产物交付。若 helper 捕获模块加载错误回 `unavailable`，缺 `.node` 的包也能 smoke 通过，并在所有机器上静默退到文件密钥。
- **为什么是问题**：失去系统密钥库保护是交付错误，不是使用者机器缺 Secret Service。`bun build` 不是把 `.node` 内联成 JS：Bun 官方把它当 file asset；该包的加载器还会尝试相对 `.node`、平台 optional 包与 package.json。只把 JS 文件移到仓库外、但仍能从祖先目录或 NODE_PATH 找到 node_modules，也不能证明独立产物可用。现有 check-dist 对 server 下全部文件按 UTF-8 扫描，不是原生资产完整性检查。
- **如何核实**：本轮 worktree/主工作区 node_modules 均未找到已安装 keyring，未安装、未构建。读取 [Bun loader 文档](https://bun.sh/docs/bundler/loaders#napi)（`.node` 为 file loader）和 [2.1.2 固定提交加载器](https://github.com/Brooooooklyn/keyring-node/blob/52184fbebffeef8a061234f60f313c479b954f9f/index.js)（Linux 分支先 relative `.node`，再 `@napi-rs/keyring-linux-x64-gnu` 等平台包，最终会抛加载异常）。这是源码/文档证据，不是打包实测结论。
- **建议改法**：协议先区分 `helper-ready`/`backend-unavailable` 与 `dependency-load-failed`/协议错误；正式产物 smoke 对后两种必须失败。S1 写定交付布局：复制 Bun 产生的原生 asset，或 external 包及其平台 optional 包一起发布；check-dist 针对该布局检查，不把二进制当 JS 标记扫描。隔离目录不应有仓库 node_modules 解析后路；在此目录运行真实 helper probe，证明加载成功但可允许 Secret Service 不存在。再补移走一个原生依赖时 smoke 必须非零的负向判据。

### 7. 只有单条 revision，没有整份快照的顺序与重连合同，清除和重置后会发生状态倒退

- **严重程度**：重要；**类别**：远程合同、一致性。
- **位置**：t08 `plan.md:40,79-91,123`；configuration.md“时序与寿命”；worktree `shared/instance.ts:125-130,157-180,246-260`。
- **现象**：快照只有 `{store, entries}`，revision 放在尚存在的每个 entry 内；clear 后该 entry 消失，reset 后全部消失。没有整个快照的启动标识/序号，没有声明订阅事件与首个基线、写成功是否附回快照、迟到响应如何过滤、连接失败/恢复如何变为 unknown 再同步。
- **为什么是问题**：旧的“写入成功、key 已设置”响应可能晚于 clear/reset 的新快照到达，重新把已清除项报成 set；每键 revision 无法比较“键已消失”的新旧，也不能排序整库 ready/unavailable 的变化。单个订阅按序不保证它与独立方法响应之间按序。上一轮第 11 条要求的响应式、就绪与断线恢复只剩一个 unknown 字面量，未变成行为合同。
- **如何核实**：现有配置实现专门用 `{boot, seq}` 与 `supersedes` 解决同一乱序，第 259 行把写响应快照也交给 apply；远程 Spec 输出 7 只保证同一订阅内顺序，重连不补事件。新计划没有相应字段和步骤；当前 t08 S3 也没有断线、乱序、重置期间订阅的验收。
- **建议改法**：复用配置已存在的快照排序约定，增加拥有者启动标识与单调快照序号（不是主密钥代次），事件先给当前基线；写/清除/reset 成功返回可排序快照，门面先应用再结算；明确断线 unknown、重连基线与释放后的行为。定义 store 不可读且 entries 不能解析时 `status(key)` 的优先级，不能因为键不在 entries 就报 unset。补写响应/推送乱序、clear/reset 后迟到旧响应、重连、释放与已接纳写入结算。

### 8. SIGKILL 只是发信号，子进程退出确认与服务停止的收口规则仍然丢了

- **严重程度**：重要；**类别**：资源寿命、并发。
- **位置**：t08 `plan.md:52,63-64,71,120,137-138`；上一轮第 6 条。
- **现象**：计划只规定 5 秒后 SIGKILL 和并发共享结果，没有规定 kill 后等实际退出、同时消费 stdout/stderr、关闭 stdin、解除计时器、服务停止时谁杀并等待子进程，以及共享等待者各自取消的语义。
- **为什么是问题**：若 timer 先结算 unavailable 并释放 single-flight 槽/初始化锁，而被杀进程还未退出，就不再满足“同一时刻至多一个子进程”，首次降级与后续操作也会和前一个请求重叠。主进程退出不会天然终止所有独立 Bun 子进程；未排空的 stderr/stdout 可以堵住 helper。5 秒单操作截止也不是整个 probe→set→提交流程的总截止，两个原生步骤已经可达 10 秒。
- **如何核实**：逐项核对 t08 的“密钥库子进程”与验收表，只有超时的返回码，没有退出确认、停止服务端、迟到结果丢弃判据；现有 configuration.md:174-177 已明确门面释放、接纳后写入、拥有者停止的时序，新合同没有继承声明。尚无 helper 实现，本条为上一轮资源寿命要求未完整转移。
- **建议改法**：让 keyring-client 的一次任务拥有 child、输入输出读取、deadline 与退出 Promise；超时/关闭时 kill，确认退出并收完管道后才释放执行槽与锁；输出严格限额、只接受一个有版本的结果帧，stderr 只作脱敏归类，不原样入日志。写明服务停止拒绝新任务、已接纳任务如何完成或中止，用户取消只退出自己的等待、不杀掉其他人共享的主密钥获取。补实际子进程退出、迟到结果、停止时清理和并发取消的可观察判据，不只断言返回 unavailable。

### 9. 密钥写入没有 schema 校验与完整失败合同，表单限制不能替代服务端约束

- **严重程度**：重要；**类别**：接口、异常输入。
- **位置**：t02 `plan.md:28-30`；t08 `plan.md:79-94,98,123`；configuration.md 输出 11、19。
- **现象**：secret 声明仍携带字符串 schema，但 t08 只规定未声明/非密钥项与声明者核对，没有规定 `write`、`editSecret` 对 minLength/maxLength/pattern 等约束的校验、空字符串与 clear 的区别、校验顺序。`SecretWriteResult` 没有定义；read 的失败集合也没有说明如何映射远程的 timeout/cancelled/target-gone/provider-error。
- **为什么是问题**：直接调用远程合同可绕过 SecretInput，把不符合声明的字符串写入密文库；只写 `value: string` 不能表达声明的约束。设置普通项原有的 invalid-value、无副作用写入失败与 unknown-outcome 不能因为拆服务而默默消失。之后 S3 若补校验与错误映射，S2/S3 的存储成功判据和界面回退都会返工。
- **如何核实**：新计划第 93 行只有两项校验，而现有普通写入口 `layer-owner.ts:137-159` 先 admission，配置 Spec 输出 11/19 明确值校验；直接按一个 `Type.String({minLength: 1, maxLength: 32})` 的 secret 声明代入新写路径，计划没有条款拒绝 `\"\"` 或 33 字符。
- **建议改法**：写定密钥声明允许的 schema 形态和后端按已接受声明校验；保持字节不被隐式 trim，空串是否有效由 schema 决定，clear 是独立动作。定义完整 SecretWriteResult、读失败/传输失败归类、授权优先级与 unknown-outcome（不自动重发），固定安全摘要而不暴露输入。补越界字符串、正则不匹配、非字符串远程输入、非声明者、用户编辑代理、无副作用失败的验收。

### 10. “结果为空”不是“本页入口没声明事件”，非目标监听者仍会留下无限等待

- **严重程度**：重要；**类别**：按需激活、失败闭合。
- **位置**：t02 `plan.md:52-55,122`；worktree `packages/nb-runtime/src/plugins/host.ts:520-533`。
- **现象**：新计划说按 page 所属 plugin/entry 取结果，但只把“没有任何入口声明这个事件（结果为空）”定义为 entry-not-activatable。本页所属入口漏写事件，另一个入口却声明相同事件时，整体 results 非空，本页匹配结果仍不存在；没有对应终态。若另一个监听者激活一直不 settle，host 的 Promise.all 还会让整体结果迟迟不回来。
- **为什么是问题**：事件参数是字符串，内核不把分区 id 自动约束为该分区入口；允许多个入口监听是既有合同，不是非法输入。上一轮第 9 条的“按所属入口关联结果”不能只筛选后就等句柄，缺失目标和其它入口的慢激活都不应让本页卡住。
- **如何核实**：runtime smoke 在 browser/server 都得到 `onDemo:page` 的非空 results，唯一结果是 `demo.other/not-the-page`；内核确实只根据入口 activationEvents 选择目标，并对所有目标 Promise.all。真实页面尚未改造，本条验证的是依赖机制与计划漏分支。
- **建议改法**：触发前按 page 归属检查该入口是否精确声明 `onSettingsPage:<id>`，缺失直接 entry-not-activatable；发布/失败状态只跟踪该入口，别等整个事件广播完成才处理本页。触发返回仍可用于整体诊断，非目标结果不得决定本页状态。补“只有非目标入口监听”“目标成功而另一监听者挂起”“关闭后再开”“受阻解除后重新触发”的真实窗口到内核路径。

### 11. 已批准“显式整库重置”，但仍保留了与它相反的逐键重新输入合同

- **严重程度**：重要；**类别**：合同迁移、Spec 边界。
- **位置**：t08 `plan.md:96-101`；t02 `plan.md:94-95,143,156`；`docs/specs/runtime/plugin-api.md:136,145,167`。
- **现象**：t08 只计划把 plugin-api 的“配置与密钥不在 ctx 上”改为链接密钥服务；没有计划修改第 145 行“重新输入的值覆盖原密文”与验收 11“重新写入后读取成功”。它们目前没有区分单条认证失败与整库主密钥丢失。t02 的旧处理摘要仍先说分代次保留旧密文，再在后文推翻。
- **为什么是问题**：新设计明确整库 check 不匹配/主密钥丢失时拒绝所有普通 write，只能显式 reset；按旧 Spec 写测试会要求 write 自行恢复，与开发者已经批准的取舍相反。拆新 Spec 可以让运行时只链接领域合同，但不能留下两个恢复真相源。不是要求重新讨论单主密钥决定，而是迁移与它冲突的承诺。
- **如何核实**：对照 plugin-api.md:145、167 的现有文字与 t08 状态表第 50 行、重置第 53 行；新计划 Spec 改动清单没有覆盖这两处。
- **建议改法**：S0 同步改 plugin-api 的恢复正文与验收：单条认证失败可以重新写这一条；主密钥丢失或整库损坏须用户显式整库重置。plugin-api 只保留“不泄漏、不静默删除”的运行时底线，格式、状态、恢复和失败码集中到 settings/secrets.md；configuration 只管 secret 声明与普通层拒收。旧处理摘要标成已被本次决定替代，不作为实施规则；避免再复制一套状态机。

### 12. “服务商对象数组 + 一个 API Key 密钥项”没有定义多服务商凭据的身份

- **严重程度**：重要；**类别**：领域模型、验收可实现性。
- **位置**：t02 `plan.md:88-90,110,125`；t08 `plan.md:7,93`；上一轮审查“旧应用参照”。
- **现象**：Lab 要支持服务商列表、详情编辑与默认模型，但 API Key 仍描述为一个静态 `secret: true` 字符串配置项。服务端只接受描述里已登记的键，运行时不能为对象数组中新加的 provider id 临时登记新的配置键。
- **为什么是问题**：两家服务商不能无歧义地共享一个密钥项；按数组下标映射会在删除/排序后串凭据，按 provider id 拼 key 又会得到 undeclared。把 map 序列化进一个字符串 secret 会破坏逐项状态、清除与并发写，并不是已经承诺的服务商详情语义。上一轮已指出这项缺口，新计划仍未选择映射。
- **如何核实**：旧 `server/models/provider-credential.ts:21-34` 用 provider id 与连接身份防错配；`server/config/config-service.ts:1327-1345,1372-1413` 保留现有密钥并拒绝悄悄改变其身份。新服务只接受静态声明，t02 S7 未给出两个 provider 各自保留/替换/清除的判据。这是模型不闭合，不要求迁入旧 provider 的连接检测或模型发现。
- **建议改法**：本轮 Lab 选择有限且固定 id 的服务商，每个 id 对应一个预声明 secret 定义，数组存选择与普通设置，不承诺任意动态 provider；或明确提出独立凭据集合模型并另经开发者决定，不能暗中扩大本轮静态 secret 合同。验收至少两家分别写密钥、切换/排序后仍对应、替换一家不影响另一家、清除一家保留另一家；已有值未编辑时不回写占位符。

### 13. `unknown` 已加到服务，却没有可传给表单的表示和不可用后的恢复触发

- **严重程度**：重要；**类别**：跨 Task 接口、状态转换。
- **位置**：t08 `plan.md:49,52,80-82`；t02 `plan.md:18-19,62,106`；`docs/specs/ui/forms.md:112,175`。
- **现象**：SecretsService.status 有 set/unset/unreadable/unknown 四态，t02 说直接经 meta 传给 SecretInput；后者合同只有 set/unset/unreadable 三态。密钥库 unavailable 后“下一次访问重新探测”，但窗口只读取同步响应式 status/store，计划没有明确哪个异步入口负责重新探测并更新快照。
- **为什么是问题**：把 unknown 强转 unset 会重新造成上一轮第 11 条指出的假状态；转 unreadable 又会误导用户整库重置。若每次 computed 读取都发 5 秒探测，失败发布会触发再读取，形成持续重试；若 getter 不发请求，单纯解锁密钥库并留在窗口的用户永远看不到恢复，窗口唯一已写明的动作只有重置。
- **如何核实**：对照上述三个可读取合同，四态到三态没有映射；`unavailable` 不缓存只解释下一次 I/O，不定义同步 getter 的异步副作用，S3 的验收也没有“首快照未到、断线、解锁后恢复”的路径。
- **建议改法**：unknown 在设置适配层单独显示等待/断线并停用编辑，不冒充 SecretInput 的任意三态；store/status 同为可跟踪的快照读取，不产生 I/O。给不可用提示提供一次显式“重试/重新检查”，或规定受限的恢复触发，触发异步刷新后发布新快照；同一个当前 key 描述的主密钥获取共享一次在途 Promise，所有等待者取同一结果，settle 后下一次新访问才重新探测。补并发等待失败只起 1 个 helper、之后一次访问可恢复、getter 无循环探测的判据。

### 14. 两条验收按字面不能成立，“对过协议”的替身也还缺行为对照判据

- **严重程度**：建议；**类别**：测试、验收映射。
- **位置**：t08 `plan.md:120-124,130`；`docs/testing/README.md:16,24,26`。
- **现象**：第 120 行要求 unavailable 时不产生新主密钥，第 121 行又允许 unavailable 下 reset 并生成新主密钥；第 124 行要求“所有响应”不含测试密钥，但合法 server/project read 响应必须包含它。替身只写“与真实脚本对过协议”，没有列哪些真实行为要对过。
- **为什么是问题**：不澄清例外，验收只能靠测试作者自己排除失败或收窄范围。“响应 JSON 形状相同”不能证明真实 helper 已成功加载原生模块、把缺项映射正确、退出/管道与取消行为一致。真实 Secret Service 测试允许未验证可以保留，但那不等于替身证明了它。
- **如何核实**：直接对照 t08 read 返回类型和 reset 状态表即可发现前两项冲突；[原生 result.rs](https://github.com/Brooooooklyn/keyring-node/blob/52184fbebffeef8a061234f60f313c479b954f9f/src/result.rs) 把 NoEntry 变成 Option 空值，不是一个能按文案捕获的错误，必须经真实 helper 证明 null→no-entry 的映射。测试规范要求真实行为对照，不只 shape 对照。
- **建议改法**：明确“普通读写失败不生成新主密钥，显式 reset 例外”；不泄漏范围改为浏览器响应/全部快照/错误/诊断/日志，合法 server/project read 单独断言精确回值。替身仅用于可控制的挂起、坏帧与大输出等故障注入，实际 helper 另验 stdin 关闭后处理一条请求、固定安全错误、加载成功标记、缺项映射与 set→get；有真实平台服务时做契约对照，做不到的项单独记未验证，不能拿 probe 或替身替代。

### 15. 生产路径的 `probe` 和永不使用的 `delete` 增加协议与失败分支，可以删掉

- **严重程度**：建议；**类别**：可维护性、可简化之处。
- **位置**：t08 `plan.md:24,53,58,63,138`。
- **现象**：主密钥初始化先 probe，成功后再 set；协议还列 delete，但计划明确旧密钥库条目不自动删除，也没有其它删除入口。probe 成功不能保证下一个进程 set 时仍可用或有写权限。
- **为什么是问题**：首次成功初始化至少要启动 probe 与 set 两个 Bun 进程，不是风险项所说一次几十毫秒；增加“probe 成功、set 失败”的分支，却不能增加实际写入的保证。delete 的完整输入/输出/截止/测试负担没有产品使用者。四个模块的职责划分本身不要求这些多余操作。
- **如何核实**：计划第 53 行不删旧条目、第 59 行不枚举孤儿，第 63 行仍有 delete；第 58 行先探测成功再存，与第 64 行每次操作独立进程相结合就是至少 2 次启动。此为计划静态计数，未测启动耗时。
- **建议改法**：生产首次初始化直接用随机账号执行一次 set，成功后再提交引用；在此之前失败按已定首次降级规则转文件，不发布失败 keyring 引用。probe 只留给产物“模块已加载/后端不可用”的 smoke，删除无调用方的 delete；不要把 probe 当持久化保证。`store.ts` 管格式/加解密/持锁提交，`master-key.ts` 管获取/选择与绑定元数据的缓存，`keyring-client.ts` 只管有界子进程协议，`service.ts` 管声明核对与快照/远程适配，避免每层再包装一次相同错误与状态。

## 未发现问题的方面

- **两个服务同属一个插件**：当前 `settings.properties` 已在每个位置登记，`acceptedSettings(context.declarations)` 从内核已接受声明直接建立登记表；密钥复用此来源不要求先取得 `SettingsService`，没有必须另建插件或引入双向服务依赖的依据。应让配置与密钥各消费判别后的声明视图，不让普通配置快照承载密钥状态；新的远程合同不要求 user/project 升版本。
- **ctx 与 window.plugins 的取舍**：`host.ts:1019-1036` 在每次激活构造统一上下文，具有 plugin、entry、generation 与 signal，足以两端绑定触发身份与寿命；window.plugins 是浏览器专属的状态/重试能力，把通用触发只放在那里会需要第二个服务端出口。输出 21 的前缀拥有者核对是同一项授权，复用而非叠加另一份核对。
- **read 原调用方可核实**：`host.ts:555,573-617` 以签发身份创建委托访问，`router.ts:109-110` 按登记实例覆盖 location/client；不是相信业务参数。实际 `delegation.test.ts` 5 条通过，包含原身份、伪造拒绝与门面释放。注意 browser→project 的远程来访身份不能在 project 再任意代理到 server：Spec 输出 10 第 3 点只允许本实例签发的身份；这条负向用例可以在内核先得到 denied，但不能用它证明 secrets 提供方真正收到了 browser 身份。提供方方法级 location 拒绝还须分别用 browser 直调与 browser 本地签发的代理路径验证。
- **密码学与定位**：随机 32 字节主密钥、12 字节 IV、16 字节 tag、版本及键作为 AAD、随机账号随文件保存，没有发现与单主密钥决定冲突的理由；主密钥 check 对不上时整库拒写、单条认证失败只覆盖本条，是不同故障，不应合并成“空库”。

- **表单未知态的代码依据**：本轮另外读到 `packages/nb-form/src/validate.ts:35-36` 的 FormMeta.secret 确实只有 set/unset/unreadable，与 Spec 一致；本轮问题 13 不是仅凭旧文档推断。
