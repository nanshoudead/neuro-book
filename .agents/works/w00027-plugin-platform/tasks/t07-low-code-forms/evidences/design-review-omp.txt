# w00027 t07 只读设计审查

审查范围：主工作区 t07 `plan.md` 的核心、描述格式与下游接口；依据 worktree 当前实现和 t02 计划。仅写本报告及指定 `/tmp/neuro-book/review-w00027-t07-design/lab/` 实验文件，不修改源码。

### 1. 密钥状态不能作为字符串字段值传入，现有接口缺少状态与操作通道

- **严重程度**：重要；**类别**：接口。
- **位置**：计划“描述格式”第 56、74 行、“Vue 渲染层”第 104–108 行、“nb-ui 的控件合同”第 119–126 行；t02 计划“密钥”第 66–74 行。
- **现象**：`writeOnly: true` 的 `Type.String` 自动选择不显示值的 `SecretInput`，但公开字段入口只有普通 `v-model`，没有 `set / unset / unreadable` 状态输入及替换、清除、撤销的操作合同。t02 明确浏览器 `get / inspect` 不给密钥，另经 `secretStatus` 返回三个状态，并由 t02 登记密钥控件。
- **为什么是问题**：`undefined` 无法区分“已有密钥但不可读”和“没有密钥”；状态字符串不能冒充通过 schema 校验的密钥值。每次普通值更新也不能区分未编辑与明确清除。t07 的内建 `secret` 和 t02 的登记控件还存在职责重叠。把旧值或占位符塞进 model 会破坏密钥不回传及校验合同。
- **如何核实**：逐项对照两份计划；t02 第 70 行规定三态，第 72 行规定值只朝服务端走一次，第 74 行规定不可解密提示；t07 的公开入口无对应输入或事件。此为设计接口缺口，未声称运行了尚不存在的组件。
- **建议改法**：区分 schema 的 `writeOnly` 注解与宿主拥有的密钥存储协议。定义 `SecretInput` 的显式状态和操作（保留、替换、清除），由设置适配器读取状态并执行写入；不要把状态当业务值，不把密钥存入普通受控值树。明确 t07 提供基础控件、t02 提供宿主适配器。增加已有密钥无明文、不可解密、取消替换、清除、失败保留状态的接口验收。

### 2. Agent 策略只限字段和深度，不能阻止同步校验冻结线程或抛异常

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划“核心”第 93–95 行、“给 nbdev 与 Agent 的映射”第 143 行、“验收映射”第 173 行。
- **现象**：允许 Agent 提供 JSON Schema 和条件 schema，然后同步交给 `Value.Check / Value.Errors`；策略只列禁止密钥、自定义控件、嵌套深度与字段数，没有约束 `pattern / patternProperties`、联合分支数、描述字符串总量、`$ref` 或异常出口。
- **为什么是问题**：不执行表达式字符串不等于安全求值。TypeBox 的 `CheckPattern` 每次直接构造 JavaScript `RegExp` 并执行 `.test`。一个字段、深度 1 的 `^(a+)+$` 即可指数回溯；无效正则 `[` 直接抛 `SyntaxError`，不返回 `DescriptionProblem[] / FormIssue[]`。条件里的 schema 也是同一入口，不能漏查。
- **如何核实**：在 `packages/neuro-book` 执行 `bun /tmp/neuro-book/review-w00027-t07-design/lab/typebox-smoke.ts`，真实 TypeBox 的输入为 16、20、24 个 `a` 加 `!`，耗时分别 0.41、6.4、101.54 ms（单次观测，不是性能基准）；`invalid-pattern` 抛 `SyntaxError: Invalid regular expression: missing terminating ] for character class`。源码：`node_modules/typebox/build/schema/engine/pattern.mjs:14–16`。没有运行更长的阻塞输入。
- **建议改法**：把 Agent 描述规定成可枚举的安全子集；最简单是 Agent 禁止自由正则及未支持的引用，只允许宿主登记的格式。为所有 schema 子树（包括条件）和布局定义节点数、联合宽度、字符串与总字节上限；若开放自由正则，需可中止的隔离求值，不能只用字符串长度限制。明确坏 schema 的结构化失败，不让异常穿透渲染。验收增加坏正则、深度小但联合极宽、引用循环、条件内危险 schema。

### 3. TypeBox 的错误不能只按 instancePath 换成字段问题，当前格式会误定位或丢失必填信息

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划“技术选型”第 19 行、“核心”第 91–99 行、“验收映射”第 171 行。
- **现象**：计划只说错误换成 `{path, code, message, severity}`，未规定路径编码、`required` 展开、联合分支筛选与同字段错误归并。真实 TypeBox 的必填错误位于父对象，缺两个属性只产生 1 条错误，缺失键放在 `params.requiredProperties`；联合失败产生分支错误加总错误；属性名中的 `/`、`~` 在 `instancePath` 中没有转义。
- **为什么是问题**：若直拷路径，缺必填的子控件不会收到错误；若把路径按 JSON Pointer 切开，键 `"a/b"` 与对象 `a.b` 同为 `/a/b`，会给错误字段标红。单字段可能有多条互相矛盾的分支错误，`code=keyword` 后又丢失分支和参数，宿主无法稳定合并跨字段错误或本地化消息。返回数组并不自动解决定位与优先级。
- **如何核实**：同一 `typebox-smoke.ts` 实测：`required-two` 为 1 条根路径错误，参数 `["x","y"]`；`union` 为 `/x` 上 3 条（`type`、`type`、`anyOf`）；`multi` 为 2 条（`minLength`、`pattern`）；数组错误路径分别 `/items/0/a/b~c`、`/items/1/a/b~c`；`path-collision` 的两个不同字段均输出 `/a/b`。可选缺省与显式 `undefined` 均通过、0 条错误。
- **建议改法**：内部使用无歧义的路径片段数组，对外规定统一编码；结合 schema 遍历恢复 TypeBox 路径，或明确拒绝不能区分的属性名，不能假设它已是转义后的标准 Pointer。展开必填错误到子字段；保留关键字、参数及错误来源，规定联合错误压缩、同字段多条呈现和 `extra` 的合并顺序。增加上述真实 TypeBox 用例，以及根错误与调用方 warning/error 共存的验收。

### 4. 条件隐藏与数据校验没有共同规则，隐藏的必填字段会令表单永远无效

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划“描述格式”第 68 行、“核心”第 93–99 行、“Vue 渲染层”第 105 行。
- **现象**：`visibleWhen` 只控制可见性，`validateForm` 仍按原 schema 校验；没有声明隐藏后保留还是清除值、是否继续校验，也没有规定相对路径基准、缺值行为和循环依赖。单值 `NbField` 只拿到本字段值，缺少判断兄弟字段所需的根数据。
- **为什么是问题**：`proxy` 在 schema 中必填、只在 `kind === "openai"` 时显示；`kind="other"` 且未填 proxy 时，用户没有可用控件修复错误。清掉隐藏值会与受控表单和全 schema 校验冲突，跳过校验又可能让命令或服务端拒绝提交。数组项内 `"kind"` 究竟指本项兄弟还是根字段没有定义，排序后的作用域也不确定。若隐藏触发清值，循环依赖还会产生反复更新；若只读数据、保留值，则无需为显示递归求依赖，应该直接写明。
- **如何核实**：`typebox-smoke.ts` 的 `visible-hidden-required` 用真实 `Type.Object` 得到缺失 `proxy` 的必填错误。`Value.Check({}, undefined)` 为 true，`{not:{const:"x"}}` 对 undefined 也为 true；不能假定引用字段未填时一律隐藏。计划接口里没有 `rootValue / basePath` 或隐藏值处理策略。
- **建议改法**：建议默认“隐藏只影响呈现，值保留、完整 schema 仍校验”，并要求条件必填用数据 schema 的分支约束表达，或描述检查拒绝不可能完成的组合；不要静默跳过服务端合同。明确根路径、当前对象相对路径、数组索引和 undefined 规则；给 `NbField` 提供可选根上下文或禁止脱离整表使用跨字段条件。测试隐藏必填、来回切换保值、数组两行不同条件、排序、缺引用和循环条件。

### 5. 只有 v-model，不能同时兑现设置提交时机与“无效草稿及错误位置”的下游合同

- **严重程度**：重要；**类别**：接口。
- **位置**：计划“Vue 渲染层”第 104–105 行、“第一批使用方”第 131 行；t02“前置：低代码”第 19 行。
- **现象**：公开入口只有 `v-model` 和输入的 `issues`，没有定义草稿更新、提交、校验结果输出、提交失败后的复位，以及 JSON 解析失败的通道。删除的 `SettingsControl` 目前承担数字与文本的本地草稿、失焦或回车提交；t02 又要求控件交出当前草稿是否合 schema 和错误位置。
- **为什么是问题**：输入 JSON 的 `{`、数字的 `-` 时尚没有对应业务值，只靠 `unknown` model 无法无损表达解析状态。若每次 model 更新直接写设置，改变已有失焦提交合同；若只输出合法值，调用方不知道当前无效草稿，保存可能提交上一个合法值。对象数组新增必填项且不填默认值时也必然经历无效中间态，不能让即时保存的拒绝回滚不断删掉新项。
- **如何核实**：`SettingsControl.vue:43–71` 明确保存字符串草稿并仅在提交时转换；`SettingsListSection.vue:57–64` 把 `update:modelValue` 直接接到写入；`settings-window.md` 输出 14 要求失焦或回车写入、失败回到实际值。计划没有说明迁移后这些语义由谁负责；t02 第 19 行的输出在 t07 组件签名中缺席。
- **建议改法**：保持业务值受控，另定义可观察的草稿/解析/校验状态和提交事件，或明确由调用方持有草稿并提供对应适配器；不要把无效 JSON 当普通字符串值。规定即时选择类、文本类和结构编辑的提交边界，失败或外部值更新时如何复位。验收覆盖无效 JSON、数字中间态、增加必填对象项后逐字段填写、写入失败恢复，以及外部更新与未提交草稿冲突。

### 6. nbdev 四种题的映射会放宽既有答案合同，并丢失逐题说明

- **严重程度**：重要；**类别**：接口。
- **位置**：计划“描述格式”第 70 行、“给 nbdev 与 Agent 的映射”第 137–143 行、“验收映射”第 170 行。
- **现象**：多选只写 `uniqueItems`，没有至少选 1 项；文字只写字符串与 multiline，没有非空白、10000 字上限及控制字符约束；没有说明逐题 `comment` 如何进入表单与答复封装。`recommend` 被扩成任意值数组，却没约束必须来自选项，也没说明多选推荐和未答状态。
- **为什么是问题**：按映射照做，`[]`、全空白文字或过长文字能在新表单通过、再被 nbdev 提交拒绝。确认题的 `false` 是合法否决，不能与未答混同；逐题说明不能塞进选项或推荐值，否则改变 `values` 合同。计划声称用四题样例测试钉住映射，但只测四种控件不足以证明无损。
- **如何核实**：`questions.ts:83–97` 明确 multi 非空且唯一，text 去空白后非空、最长 10000 并经 `controlCharProblem`，confirm 接受两个布尔值；第 76–77 行限制推荐只能来自选择题的选项。`artifact-ops.ts:562–570,618–620,627–639` 单独校验并保存 `comments`，不是答案值的一部分。
- **建议改法**：给出完整的 `QuestionDefinition → schema + hints` 与 `form value → values/comments` 适配合同。多选加 `minItems: 1`，文字保留原校验（不能表达的规则经 `extra`），未答用缺失值而不是 false，说明用独立可选字段并在提交适配时拆出；推荐只作标记、不自动作答，校验其取值。以真实 `validateAnswerValue` 对照测试合法与非法边界，并覆盖带说明答复和 optional 未答。

### 7. 动态选项只有数组，无法承载 t02 的提供者不可用与过期值语义

- **严重程度**：重要；**类别**：接口。
- **位置**：计划第 66–67、108、131 行；t02“声明 API”第 29–32 行、“动态选项”第 78 行。
- **现象**：t07 的 `x-form.options` 是源名，Vue `options` 仅接 `Record<源名, Readonly<Ref<选项[]>>>`；t02 的 `choices: {from}` 是贡献提供者 id，提供者交 `{value,title}`，要求不存在/未激活时停用并说明原因，当前值消失时仍显示并标“已不存在”。t07 未定义这两套名字和 `label/title` 的适配、源缺失状态，且 `NbField` 签名没有 `disabled` 输入。
- **为什么是问题**：空数组无法区分“成功返回 0 项”和“源不可用”；如果未找到源退回普通字符串输入，用户能绕过必须停用的设置合同。只显示数组中的值还会把旧值显示成空选项或误清除。现有设置的层无效或继承状态同样必须停用，不等于 `readonly`。
- **如何核实**：对照两份计划的上述类型；现有 `SettingsListSection.vue:60–64` 明确传 `disabled`，`SettingsRow.vue:53–59,108–109,125–126` 按层状态及沿用计算停用。旧 `LowCodeFieldOption`（`profile-sdk/contracts.ts:511`）还支持选项级 `disabled`，新 `choices` 定义未保留也未说明舍弃。
- **建议改法**：明确宿主适配 `choices.from → x-form.options`、`title → label`，不把提供者注册表放入通用核心。给选项源增加可用/加载/失败状态及原因，或提供等价的字段状态输入；`NbForm/NbField` 应有递归传递的 disabled。规定未知当前值保留呈现、源变化不改业务值、选项级 disabled 是否保留。补源缺失、源恢复、空结果、当前值被移除与层停用的合同测试。README 决定第 6 条写“提供函数”，若采用 Ref 快照适配，应同步写明这只是调用方负责取数后的输入，不是把函数藏入描述。

### 8. 没有定义支持的 schema 方言，“未知用 JSON”与“画不了则拒绝”互相冲突

- **严重程度**：重要；**类别**：接口。
- **位置**：计划“描述格式”第 54–56 行、“核心”第 91–99 行、“描述检查”第 95 行。
- **现象**：输入被等同于标准 JSON Schema，字段种类却仅列有限几种；`resolveForm` 对未知类型兜底 JSON，`checkDescription` 又要报告画不了的类型。没有区分结构化编辑、JSON 编辑和拒绝的集合，也没有规定开放对象、`patternProperties`、nullable 联合、非对象数组、引用及递归的处理。
- **为什么是问题**：`Type.Record(Type.String(), …)` 只有 `patternProperties`；`Type.Object({})` 是允许任意键的对象，不是一个无需编辑的空表单。若仅按 `type:"object"` 递归 properties，这两种值都没有可编辑入口。nullable 联合、整数数组明明可由 JSON 编辑表达，但描述检查是否拒绝未定。递归 schema 的展开深度与实际值深度不是一回事，合法递归描述不能直接无限展开字段树。Agent 会生成原始 `enum`，TypeBox 字面量联合则是 `anyOf + const`，二者需要明确统一。
- **如何核实**：真实 TypeBox 实验输出：Union 两个 Literal 为 `anyOf` 两个带 `const` 的节点；Optional 体现在父对象不列 required；Integer 为 `type:"integer"`；Record 为 `type:"object",patternProperties:{"^.*$":…}`。另以 `bun -e` 验证 `Type.Object({})` 生成 `properties:{}`，nullable 是 string/null 的 anyOf，整数数组是 array/integer；带 `$defs` 的有限递归值在 `Value.Check` 中可通过。不能按“TypeBox 都有相同 type 结构”实现推断器。
- **建议改法**：在 S0 写出关键字/结构支持矩阵，覆盖原始 JSON 与 TypeBox 生成形状；明确 Record、开放对象、复杂联合、其余数组走 JSON，或明确拒绝但不要消失。区分“合法可编辑（含 JSON）”与“坏描述/策略不允许”；为引用、递归、maxDepth 定义有限遍历规则。用真实生成 schema 的表驱动测试覆盖以上形状，不只手写理想化 enum。

### 9. 可选值只有初始 undefined，没有“设值后恢复缺失”的更新合同

- **严重程度**：重要；**类别**：遗漏。
- **位置**：计划“核心”第 99 行、“Vue 渲染层”第 104–111 行、“nb-ui 的控件合同”第 119–123 行。
- **现象**：计划说可选属性值为 undefined、表单不填默认值，但没有规定删除属性、取消选择、清除数字/对象，以及数组项与属性的 undefined 如何区别处理。`readOnly` 只是列作 schema 关键字，没有定义父级只读、字段只读与指定 widget 的优先级。
- **为什么是问题**：可选布尔具有缺失/false/true 三种语义，开关只能表达后两种；可选数字清空不能擅自写 0、NaN 或 null；可选字符串清空为 `""` 也不等于缺失。命令参数允许缺失，但不会转换或补默认值。把“只读”交给 `Value.Check` 也无效，它只是注解；父对象被 JSON 编辑或数组结构操作改写时仍需保护只读成员，不能只给叶控件加 readonly。
- **如何核实**：`typebox-smoke.ts` 验证 Optional 缺省与显式 undefined 都通过；`readOnly` 字符串改值仍通过，required 上的 default 不会补值。另用严格对象 schema 验证 `{id:"x"}` 与 `{id:"x",enabled:false}` 均合法且语义不同，多余键被拒。`commands/shared/contracts.ts:54–55` 明确参数不转换、不补默认值。此项指出设计缺失，不声称未实现控件已经出错。
- **建议改法**：规定属性更新为设值/移除两种操作（或保证 undefined 对属性意味着移除），不允许用数组 undefined 冒充删除；给 optional 字段统一的取消/恢复未设置入口。明确 readonly 取父级与节点标记的最强限制，且覆盖结构操作及 JSON 兜底。补缺失→false→缺失、数字清空、空字符串与缺失区分、对象删除、只读对象/数组不发修改的验收。

### 10. 声称保留旧 validate 钩子，但同步返回类型无法承接旧异步校验

- **严重程度**：重要；**类别**：接口。
- **位置**：计划“旧应用的低代码”第 36–37 行、“核心”第 93 行、“Vue 渲染层”第 104–105 行。
- **现象**：旧 `validate` 支持返回 Promise；计划写“保留，由调用方提供”，公开函数却是同步 `validateForm(…, {extra?}): FormIssue[]`，`extra` 是函数还是已算好的问题列表都没定义。组件还另收 `issues`，没有说明是否重复自动校验、何时运行 extra、无效类型时能否运行。
- **为什么是问题**：照“跨字段校验钩子保留”迁移异步服务端规则时会遇到类型或生命周期返工。核心 schema 校验失败时若仍把值按 `Static<T>` 交给 extra，校验器也可能因字段缺失直接抛错；若异步结果与当前草稿不一致却照常显示，会把旧错误标到新值上。
- **如何核实**：旧 `profile-sdk/contracts.ts:542` 明确 `validate` 为同步或 Promise；`server/low-code-form/index.ts:114–132` 先返回 schema 错误，只有类型通过才 `await form.validate(value, ctx)`。新签名和旧能力不等价，计划没有列出有意取消异步校验的决定。
- **建议改法**：最简单是核心只同步转换 TypeBox 错误并合并调用方已完成的 `FormIssue[]`；异步校验由宿主管，按值版本丢弃过期结果，组件只呈现。若坚持 extra 是钩子，就明确输入是 unknown 还是已校验值、调用顺序、Promise 与异常合同。测试 schema 不合法时不误调用强类型 extra、根/字段 warning 与 error 合并，以及宿主异步结果过期。

### 11. 核心引用的 LocalizedText 目前由应用拥有，独立包与错误国际化没有落地接口

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划“包”第 46–50 行、“描述格式”第 61 行、“核心”第 93 行、“Vue 渲染层”第 104–112 行。
- **现象**：计划规定核心只依赖 TypeBox、nbdev 与应用都可消费，却把 `Text` 定义为 `string | LocalizedText`，未说明该类型和语言解析的所有权。当前 `LocalizedText`、`DisplayLocale`、`textOf/localize` 都在应用的 `src/shared/localized-text.ts`；`FormIssue` 只保留 message，Vue 的 locale 不能使已生成的 TypeBox 英文错误自动切换语言。
- **为什么是问题**：直接从 `nbook/shared/localized-text` 引用会形成共享包反向依赖应用，nbdev 无法独立使用；复制一份却不规定值形状与回退规则，会在原始 JSON、单语 Agent 描述和宿主双语声明之间产生不一致。切换语言时，只传 `locale` 也无法重新解释已经丢弃参数的英文字符串。
- **如何核实**：`packages/neuro-book/src/shared/localized-text.ts:9–29` 定义固定中英对象、locale 和解析；`packages/AGENTS.md:10` 与 `docs/modules/monorepo-boundaries.md:19,24,76` 禁止领域包反向依赖应用、要求 nbdev 不依赖应用。实测 TypeBox 错误是 `must be …` 英文。计划未列文本协议的迁移或宿主适配。
- **建议改法**：在 nb-form 核心公开完整、自足、结构兼容的文本值协议，并让宿主在边界适配；不导入应用类型或当前语言设置，不把文本提前折成字符串。也可选择已有无框架公共合同入口承载它，但需明确依赖变更。问题保留稳定 code 与 params，渲染时按 locale 翻译；规定语言缺失回退、单语标题、选项与内建操作文字。以无应用依赖的核心导入 smoke 和运行时切换语言的验收守住包边界。

### 12. 旧应用的 searchable combobox 没有对应处理，九种字段并未逐项闭合

- **严重程度**：建议；**类别**：遗漏。
- **位置**：计划“旧应用的低代码”第 30–40 行、“描述格式”第 65 行、“nb-ui 的控件合同”第 125 行。
- **现象**：计划说参照九种字段，但只为 `resource-preset` 明确延期；`widget` 枚举没有 `combobox` 或搜索提示，虽列出要改造 nb-ui `Combobox`，没有说明 schema 如何选中它。旧 combobox 不只是普通下拉。
- **为什么是问题**：表单使用方无法只凭描述要求在长选项列表里搜索；若当作自定义控件才能取回这项能力，又会被 Agent 禁止自定义控件的策略排除。这是未登记的能力差异，不是要求恢复已经决定延期的 resource-preset。
- **如何核实**：`profile-sdk/contracts.ts:541` 明列九种 component；`LowCodeComboboxField.vue:49–57` 提供搜索输入，`useLowCodeComboboxDropdown.ts:40–50` 按选项 label、value、description 过滤。该组件只搜索并选择已有选项，不代表允许任意新值；不能用 tags 替代其语义。
- **建议改法**：在旧能力对照里补明处理：映射到可搜索的内建 select/combobox，或明确本轮不保留搜索。如果保留，写明选择规则或提示与 TUI 退回为普通选择，增加描述选控件的核心用例；无需为它另建一套字段系统。
