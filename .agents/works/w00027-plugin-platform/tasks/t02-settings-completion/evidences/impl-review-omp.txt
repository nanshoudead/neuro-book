### 1. 设置文件的远程 text 订阅结束后不会重建
- **严重程度**：重要；**类别**：不变量
- **位置**：`packages/neuro-book/src/plugins/settings/shared/remote-link.ts:81-95`
- **现象**：`remoteLayerFile.watch` 调用 `events.text.subscribe` 时没有传 `onEnd`，订阅失败只直接返回，成功后的句柄也只在本地保存一个 `release`。与同文件的 `remoteLayerLink`（24-32 行）不同，它没有把临时断线标为可重订阅，也没有在连接恢复后重新建立订阅。
- **为什么是问题**：设置文件视图打开后依赖 `text` 事件发现外部修改。远程连接或拥有者重启会结束这条事件订阅；窗口仍保留旧文本和旧修订号，之后文件再变化不会提示或自动重读，保存只能迟到地收到 conflict。若建立订阅时已经失败，视图也没有任何状态变化或后续重试。该行为破坏配置层已有的“订阅结束后按连接恢复重订”的合同，并使 `read` 的一次成功不能保证视图持续同步。
- **如何核实**：对照 `remoteLayerLink` 的 `events.layer.subscribe(..., {onEnd})` 与 `remoteLayerFile` 的无选项调用；在真实远程场景中打开“设置文件”，断开浏览器到服务端的连接，恢复后由另一实例改写文件，观察 `SettingsFileView` 不触发 `changedElsewhere`，直到再次手动读取或保存冲突。
- **建议改法**：为全文订阅增加与层订阅相同的生命周期封装：传入 `onEnd`，区分终态与可重试终态，重连后先释放旧句柄再重新订阅并推送当前修订号；手动取消、调用方释放和拥有者终止时只释放一次。建立失败也要记录当前订阅不可用并按连接恢复策略重试，不能静默丢掉。
### 2. readFile 的 UTF-8 替换字符使 revision 不是原始字节摘要
- **严重程度**：重要；**类别**：正确性
- **位置**：`packages/neuro-book/src/plugins/settings/backend/layer-owner.ts:47-49,147-149,216-219,229-231`；`packages/neuro-book/src/plugins/settings/backend/layer-file.ts:45-50,87-91`
- **现象**：`textRevision` 对字符串重新以 UTF-8 编码后取 SHA-256；而文件先由 `readFile(path, "utf8")` 解码。`writeLayerFile` 持锁阶段又把原始字节 `Buffer` 解码成字符串后交给 transform。非法 UTF-8 字节会被 Node 替换成 `U+FFFD`，摘要因此是“替换后的文本”而不是文件原始字节。
- **为什么是问题**：配置合同明确要求 `revision` 是原始 UTF-8 字节的 SHA-256。当前返回的 revision 与合同不符，外部或 TUI 以原始字节计算的摘要无法写入；更严重的是不同的非法字节序列可能在解码后归一成同一文本，冲突检测失去文件身份区分。写入路径还可能把原始非法字节当成替换字符文本重新落盘，破坏用户文件。
- **如何核实**：在 `/tmp/review-t02-impl/bad-utf8-settings.json` 写入字节 `c3 28`，用当前算法得到 `2d4bf56bf338c578dae8b2b20d4d8b28801557d4c38e1d7c6699abddf69fee8d`，直接对文件字节取 SHA-256 得到 `eddf68639913a3cb8331cdfe7f87559e0beccf2c289c0d90ac4d89b3204004f8`，两者不同（命令：`node -e '...'`，输出 `equal:false`）。
- **建议改法**：文件层同时保留原始 `Uint8Array` 与严格 UTF-8 解码结果；revision 直接对原始字节摘要。整份读写遇到不能严格解码的内容应按 `read-failed` 或明确的文本读取失败处理，不能用替换字符继续做冲突检查与写回。
### 3. 只有空白的搜索词会绕过未保存保护并丢页面草稿
- **严重程度**：重要；**类别**：正确性
- **位置**：`packages/neuro-book/src/plugins/settings/web/settings-window.ts:393-395,706-710`
- **现象**：`words` 会过滤空白并因此把查询视为“没有搜索”，但 `search()` 用原始 `query.value` 判断是否已经从空查询进入搜索。用户在脏 page 页面先输入一个空格时，`next.trim() === ""`，代码不走 `requestLeave`，却把 `query` 设为非空空白；随后再输入任意字母时，`query.value !== ""`，直接改查询，不再走 `requestLeave`。此时 `words` 从空变为非空，当前页面卸载，未保存改动无确认即丢失。
- **为什么是问题**：Spec 要求“在搜索框输入第一个字”触发未保存保护。空格是输入事件的一部分，不能成为绕过保护的中间状态；当前实现只要用户先按空格，就能在第二个字符时无确认地离开脏页面。与此同时查询显示仍保留空格，`Esc` 还会因 `query !== ""` 只清空而不关闭窗口，说明 `words` 与 `query` 的状态语义已经分裂。
- **如何核实**：在真实设置窗口的 page 页面令 `context.dirty(true)`，依次调用搜索输入事件 `" "`、`" x"`：第一次后 `window.leaving` 仍为 `null`，第二次后 `window.current.kind` 变为 `search` 且 `window.leaving` 仍为 `null`；页面已卸载。现有搜索测试只覆盖非空首词，没有覆盖首个字符为空白。
- **建议改法**：把“有搜索词”的判定统一为 `words.length > 0`。从无词到有词（包括由空白前缀组成的查询）一律调用 `requestLeave`；只有空白的输入规范化成空串，或至少按空查询处理清空、Esc 与页面生命周期，避免 `query` 原文状态参与离开保护判定。
### 4. 加载中的 page 关闭后会保留旧 context，下一次显示复用它
- **严重程度**：重要；**类别**：不变量
- **位置**：`packages/neuro-book/src/plugins/settings/web/settings-window.ts:484-497,556-565,617-630`；`packages/neuro-book/src/plugins/settings/web/components/SettingsWindow.vue:56-57,214-216`
- **现象**：`SettingsWindow.vue` 在 page 还处于 `waiting/loading`、组件尚未交付时就调用 `model.page(id)`，`contextOf` 因而把 context 放入 `visits`。但 `visits` 的结束 watch 只观察“窗口开着、当前 page 可用且 instance.status === ready”；关闭窗口或取消加载时 `performClose` 把 instance 从 `loading` 设为 `waiting`，这次显示从未有 `previous === ready`，所以 `endVisit` 不会执行。再次打开并加载同一 page 时会从 `visits` 取回同一个 context。
- **为什么是问题**：合同要求每次页面挂载/显示给新的上下文，旧上下文在关闭、重新加载时作废。当前旧 context 可跨关闭窗口和一次新的加载继续存在；以后页面在加载前后调用 `dirty`、或依赖 context 身份区分草稿代次时，会把两次显示混成一代。现有测试只覆盖已 ready 页面离开，没有覆盖加载中关闭。
- **如何核实**：让 page 的 `load()` 挂起，打开该分区直到 `page().status === "loading"`，读取 `window.page(id).context`，立即关闭再打开并允许 `load()` 完成；按当前代码两次 `window.page(id).context` 相同，且第一次显示没有经过 `endVisit`。这条路径只使用真实的页面加载与窗口关闭时序，不调用内部私有函数。
- **建议改法**：只在 page 已 ready、确实要挂载组件时创建 visit/context；或者关闭、撤回、重新加载时显式结束该 id 的所有 visit（包括尚未 ready 的预创建项），并为每次新的加载代次重新建 context。`page()` 不应为了渲染状态占位而提前创建一次显示的上下文。
### 5. 设置文件视图在初次读取期间会丢弃 text 事件
- **严重程度**：重要；**类别**：正确性
- **位置**：`packages/neuro-book/src/plugins/settings/web/components/SettingsFileView.vue:252-257`
- **现象**：`follow()` 先建立 `watch`，随后 `load()` 把状态置为 `loading` 并等待 `file.read()`。订阅回调看到 `state.value.kind === "loading"` 时直接 `return`，不记录事件。若文件在这次异步读取期间变化，事件先到、读取又返回旧文本，加载结束后组件会把旧文本与旧 revision 设为新的基线，之后不会再有事件触发重读。
- **为什么是问题**：设置文件视图打开后可能长期显示已经过时的全文，用户随后编辑并保存时才被动得到 conflict；在事件与读取结果跨远程帧乱序时，这不是理论上的固定顺序问题。Spec 要求没有草稿时收到 `text` 事件自动重读，`loading` 不是可以丢弃通知的终态。
- **如何核实**：用真实的远程文件视图打开时让 `readText` 挂起；在它完成前由另一实例写入只改注释的文本，确认 `text` 事件已到达；再让 `readText` 返回旧文本。当前回调因 loading 直接返回，加载完成后的 textarea 仍是旧文本，且没有后续 `changedElsewhere` 或自动重读。
- **建议改法**：加载期间不要丢事件：记录待核对的最新 revision，读取完成后若 revision 与返回值不同立即再读；或让事件回调排一个带 token 的重读，确保最后一次 read 与订阅看到的 revision 一致。换层、卸载时仍用现有 token 丢弃过期结果。
### 6. 动态选项的 notActivatable 诊断会污染入口换代
- **严重程度**：重要；**类别**：正确性
- **位置**：`packages/neuro-book/src/plugins/settings/web/choices.ts:87-92,145-149,178-199`
- **现象**：第一次读取已登记、未激活的提供者且入口没有 `onSettingsChoices:<id>` 时，`#activate` 把原因永久写入 `#notActivatable`。这个 Map 只增不删；`receiver().published`、`revoke`、插件状态变化和新入口代次都没有清理或换代标识。后续即使入口因别的途径交付后又撤回、同插件重新登记并声明了事件，`#state` 仍在 registered 状态命中旧原因，`#activate` 直接返回，不再触发新代次。
- **为什么是问题**：提供者目录与句柄是按入口代次变化的；一次“当前代次没有这个事件”的结论不能跨停止、撤回和重新登记复用。用户会看到永久 unavailable，必须刷新整个浏览器页面才能恢复，违反计划中“换代时丢掉旧缓存、按当前入口状态重新判断”的不变量。
- **如何核实**：真实运行时先登记没有按需事件的提供者并读取一次使其进入 `#notActivatable`，随后停止/撤回该入口，以新代次登记同一提供者并声明 `onSettingsChoices:<id>`，触发入口恢复；当前 `#notActivatable.has(id)` 仍为真，选项源不会发起激活。现有测试只验证“之后直接 activate 后句柄可用”，没有覆盖撤回/重新登记后的读取。
- **建议改法**：把不可激活状态绑定到入口代次或当前入口引用，而不是只按 provider id 记忆；入口代次改变、句柄发布/撤回或状态恢复时清除旧结论并重新核对事件。诊断去重键也应包含代次，避免新代次沿用旧代次的失败。

#### 第 4 条最终结论：关闭后重新打开同一 ready 页面，当前页面的 dirty 永久失效

- **严重程度**：重要；**类别**：不变量。
