### 1. 卸载后重装、撤销待升级与覆盖待升级的状态合同不闭合

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/runtime/plugin-install.md:40,57,64-84,102,109`。
- **现象**：第 40 行及 `already-installed` 明确拒绝当前版本或待切换版本，第 76 行却要求“卸载中的插件可以重新安装同一或另一版本”。当前为 A、待升级 B 时，重新安装 A 同样被拒，且没有撤销升级的操作。覆盖 B 为 C 时只要求删除 B，没有规定删除必须发生在 C 的登记提交之后。
- **为什么是问题**：`卸载 A → 重装 A` 同时被要求成功和失败；`A → 待升级 B → 撤销` 没有合法转换。若按准备步骤先删 B，再写 C，写入失败或进程中断后登记表仍指 B，但 B 已不存在，违反第 109 行“回到操作前”与提交点表。单次安装/升级的提交点不足以覆盖“已有 pending 的升级”。
- **如何核实**：逐行枚举上述三个操作序列，对照输入限制、状态覆盖规则、失败恢复与提交点表；现有场景 12、13 只覆盖一次升级和启停反转，没有覆盖这些组合。
- **建议改法**：明确卸载中重装是同版本拒绝规则的例外，或删除这条承诺；提供取消待切换的明确操作（不必复制当前 A）；将替换 pending 的提交点写清：C 完成并提交后才能回收 B，提交前失败保留 A/B，提交后失败由残留清理收口。补组合状态与各中断点的合同测试。

### 2. 获批决定没有落进可执行计划，卸载仍被安排为立即删文件

- **严重程度**：重要；**类别**：文档。
- **位置**：`.agents/works/w00027-plugin-platform/tasks/t03-manifest-and-install/plan.md:27,36-38,43,63-64,77-82`；`tasks/t01-requirements/plan.md:17,29,32,36-43,52-53,74`。
- **现象**：t03 S1b 仍要求 `uninstall`“删目录与登记项”，没有卸载中标记与启动恢复；验收映射引用已删除的输出 5，并明确“本轮不实现升级”，与同一计划第 36 行和 t01 已确认的重启升级相反。映射没有输出 8、9、场景 12–14，以及多次操作和提交点恢复。总计划还要求声明式贡献即时生效，S2/S3 用即时启停验收，却把即时启停留在 S5。总计划要求 S1 实现 `version-mismatch`，t03 明确推迟。插件页又在描述顶层贡献 `settings.sections`，违反该贡献点必须写在浏览器入口下的合同；页面上下文也不含计划依赖的“窗口连接”。
- **为什么是问题**：这不是“原型尚未追平”，而是交给实现者的下一步指令本身冲突。照 S1b 实施会在本次运行仍使用旧插件时删除其文件；照验收表可以漏掉已明确批准的升级与待生效状态而仍宣称完成。顶层分区会被真实设置贡献点以 `implementation-required` 拒绝。
- **如何核实**：对照 `plugin-install` 输出 3、8、9 与场景 12–14，`settings/settings-window.md:39,58-62,67`，以及 t01 文末已确认项；逐条核对 t03 验收映射，没有相应覆盖。
- **建议改法**：以已确认决定重写冲突的计划行：卸载仅提交意图，启动后清理；升级、取消/覆盖待切换、重启恢复、待生效 UI 都有明确验收；S1–S4 全部用重启后行为验收。将设置分区放浏览器入口，远程客户端由该入口获取并闭包传给页面，不扩张既有页面上下文。明确版本推导属于哪一片，并同步总计划。

### 3. 两个等待就绪超时的根因是必需插件集合换了来源，故障入口根本没有激活

- **严重程度**：重要；**类别**：测试。
- **位置**：`packages/neuro-book/src/server/start.ts:337`；`src/server/testing/test-plugins.ts:222-253`；`src/server/server.test.ts:180-195,320-342,481-509`。
- **现象**：原型把 `requiredPlugins` 从实际装配的 `plugins` 改为内置描述表。测试注入的 `test.fail-activate`、`test.fail-close` 不在描述表，也没有 `onStartup`，因此不再激活。HTTP/RPC 等待用例中的 `hold` 不再阻止启动，服务器直接 ready，`admission.active` 不会停在 1；失败测试实际上取得 200/101，而不是等待之后的 503。
- **为什么是问题**：新规则“第三方不是启动必需”正确，但测试注入 API 已无法表达“额外的必需插件”，原来覆盖启动失败和关闭失败的 4 个用例失去前提。增加等待时间解决不了。另 5 个失败只是发布/关闭插件 id 列表漏了新增的 `nbook.plugins`，不是关闭顺序回归。
- **如何核实**：在 `packages/neuro-book` 执行 `bun test src/server/server.test.ts`：23 个用例，14 pass、9 fail，32.66s。聚焦真实宿主实验 `bun --tsconfig-override /home/notnotype/CodeRepository/neuro-book/.worktree/w00027-t03-manifest-and-install/packages/neuro-book/tsconfig.json /tmp/neuro-book/review-w00027-t03-design/lab/startup.ts`：尚未 resolve hold 就 ready；故障入口为 `registered`、`generation: null`；health=200；停止 exitCode=0。由此确认不是 admission 计数或 I/O 卡住。
- **建议改法**：保留第三方非必需规则，让 `StartServerOptions` 能显式指定额外启动必需项，fixture 与这 4 条测试明确传入；不要仅加 `onStartup`，非必需入口的激活失败按合同不会拖垮应用。发布/关闭测试改为检查依赖先后与失败隔离，不枚举无关插件全集。

### 4. 删除代理允许清单后，普通服务的提供者可以跨合同读写消费者的 Storage，剩下两项核对不能保住命名空间隔离

- **严重程度**：重要；**类别**：不变量。
- **位置**：`docs/adr/0027-builtin-and-third-party-plugins-are-equal.md:28,40-42`；`docs/adr/0024-multi-instance-runtime-topology.md:45`；`docs/specs/storage/persistence.md:107`；`packages/nb-runtime/src/plugins/host.ts:575-618`、`src/services/composition.ts:343-353,585-636`；`packages/neuro-book/src/plugins/storage/backend/owner.ts:28-29,39-49`。
- **现象**：恶意插件只需提供一个被其它插件依赖的普通按调用方服务，就会收到那个消费者的真实身份对象；它自己声明 `remoteDelegates: [userStorageContract]` 后，可以用同一个身份对象代理 Storage。`issuedTo` 只核对身份是签发给这个提供入口的，不核对消费者究竟委托了哪项合同。Storage 按 `consumer.plugin` 分区，不检查 `via`。
- **为什么是问题**：伪造一个新对象确实会被拒，但把“调用格式化服务”转换成“读取调用者私有记录”完全通过两项核对。不是任意选一个从未依赖它的插件就能冒名，而是所有曾取得它的按调用方门面的消费者都暴露。ADR 0027 只声明部分取代 ADR 0022，仍声称是防伪造；ADR 0024 的受控代理与 Storage“插件之间同名记录互不可见、无法指定别人命名空间”的无条件合同却没有同步收窄。
- **如何核实**：运行 `bun --tsconfig-override /home/notnotype/CodeRepository/neuro-book/.worktree/w00027-t03-manifest-and-install/packages/neuro-book/tsconfig.json /tmp/neuro-book/review-w00027-t03-design/lab/delegation.ts`。实验经真实应用实例、服务门面签发、路由和 SQLite Storage；用现有宿主装配参数只给 `evil.proxy` 开放新决定将开放的代理能力，没有改内核或伪造签发。`example.victim` 保存 `victim-private-data` 后，evil 直接读取为 `missing`，复制身份对象得到 `denied`，使用收到的原身份代理读取却返回 victim 的正文。两实例均正常关闭。
- **建议改法**：不要求恢复已决定删除的权限系统。若保持完全信任，ADR 0027 必须明确接受“服务提供者可把消费者身份用于任意自声明远程合同”，并显式收窄 ADR 0024、Storage/配置中隔离的承诺；把剩余核对描述为对象来源与寿命检查，而不是通用防冒名保证。若仍要保住按合同隔离，则必须另行决定由消费者授予合同范围；仅让代理自己声明 `remoteDelegates` 无法做到。

### 5. 安装器只检查末级文件，`files` 可以穿过符号链接目录复制源目录外的文件

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/backend/plugins/registry.ts:167-189,215-235,277-284`；`docs/specs/runtime/plugin-install.md:39,103`。
- **现象**：源目录的 `linked` 是指向目录外的符号链接，`files: ["linked/payload.txt"]` 安装成功，并复制了目录外的 `payload.txt`。`lstat(source/linked/payload.txt)` 只检查 payload，本身是普通文件；中间组件 `linked` 已被操作系统跟随。清单 `main` 的存在性检查同样用会跟随链接的 `stat`。另一个边界只 realpath 源目录、没有 realpath 安装根，安装根经 symlink 别名进入时不能可靠识别“源位于 plugins 内”。
- **为什么是问题**：违反已定“复制范围出现符号链接就拒绝”和源目录边界，不是权限沙箱问题。安装器不能保证产物来自用户确认的源目录。静态拒绝末级链接的测试不能覆盖这种路径。
- **如何核实**：运行 `bun --tsconfig-override /home/notnotype/CodeRepository/neuro-book/.worktree/w00027-t03-manifest-and-install/packages/neuro-book/tsconfig.json /tmp/neuro-book/review-w00027-t03-design/lab/install-runtime.ts`。经真实 WebSocket、内核远程服务 `nbook.plugins/registry.install`，`symlink-parent-install` 为成功，安装目录读回 `outside-boundary`。不是直接调用私有复制函数；实验服务和项目子进程均正常关闭。
- **建议改法**：规范化安装根；对 `files` 命中的每个相对路径逐段 `lstat`，任何祖先或末级是 symlink 都拒绝，并在复制时维持最终目标位于源根的约束；对源内目录链接、末级链接、安装根别名与 glob 命中链接分别补行为用例。失败码统一用新合同的 `path-rejected`。

### 6. 声明式插件没有进入项目子进程，项目层配置从本 Task 起就不可用

- **严重程度**：重要；**类别**：正确性。
- **位置**：`.agents/works/w00027-plugin-platform/tasks/t03-manifest-and-install/plan.md:51-59,76-82`；`packages/neuro-book/src/project/start.ts:115-118`、`src/project/plugins.ts:49-53`；`docs/specs/runtime/plugin-manifest.md:93`。
- **现象**：计划与原型只把第三方清单送进服务端与窗口。项目子进程始终从编译进去的 `productPlugins` 装配，没有接收服务端已冻结的第三方集合。一个没有任何代码入口、合法声明 user/project 配置项的插件，在 user 层能写，在 project 层得到 `undeclared`。
- **为什么是问题**：顶层声明必须在每个实例登记，是 `plugin-manifest` 输出 11 的既有合同，也是第三方设置支持“用户 | 本作品”的必要条件，不依赖 t04 的项目代码装载。若项目进程以后自行扫描实时登记表，也会让同一次服务端运行中后来打开的作品提前看到尚待重启的启停/安装，破坏“本次运行集合不变”。
- **如何核实**：同第 5 条的 `install-runtime.ts`，经真实管理远程服务安装 `example.good`，停止并重新启动服务端，创建作品，由客户端握手启动真实项目子进程。服务端贡献状态 accepted，客户端同身份写 user 设置成功，写 project 设置得到 `settings-failed / undeclared`。最后服务端和项目子进程 exitCode=0。
- **建议改法**：S1d 同时覆盖项目宿主，把服务端本次启动确定的有效集合快照通过项目启动合同送进每个子进程，声明式贡献无需项目入口即可登记；不要让项目按打开时的实时登记表重新决定集合。加“安装→重启→打开作品→项目层写入”和“禁用待重启→再开另一作品仍保持本次集合”的真实子进程验收。

### 7. “所有内置定义往返，除 activate 外相等”按现有清单模型无法验收

- **严重程度**：重要；**类别**：不变量。
- **位置**：`docs/specs/runtime/plugin-manifest.md:21,41,52-59,68,121`；`.agents/works/w00027-plugin-platform/tasks/t03-manifest-and-install/plan.md:20-25`；`packages/nb-runtime/src/plugin-manifest/plugin-manifest.ts:41-44,49-54,273-302`。
- **现象**：内置定义已包含清单没有的语义：① `files/backend/plugin.ts:150`、`settings/web/plugin.ts:184` 等有 `{required:false}` 可选依赖，清单却明确“不提供可选依赖”，`requires: string[]` 映射回来全部是必需依赖；② `settings/shared/point.ts:17-30`、`commands/shared/plugin.ts:177` 等贡献点带 `validate` 函数，清单只收 `{id,implementation}`，甚至没有 Spec 承诺的声明 schema，转回必然丢校验；③ 内核要求激活产出的远程合同与声明为同一对象，但 JSON 只有 id，`definitionOf` 要额外提供 `contractOf`，计划没有定义其来源与寿命；④ `receives` 是现有激活输出必须严格匹配的字段，原型有它，Spec 输入表没有。
- **为什么是问题**：把这些信息删掉才能通过往返，不是“等价”；可选依赖变必需会使入口无端受阻，丢失 validate 会放行原来被拒的贡献。若为了按合同 id 找对象而提前 import 第三方入口，则违反“登记不执行插件代码”，也使 t04 的按需装载前提失效。服务键按 id 映射本身没有这个问题；`settings/backend` 用函数生成两个入口也能在取得定义后逐入口展开，不是障碍。
- **如何核实**：对照上述实际定义与解析器字段/映射；`PluginEntryDefinition.receives`、`ContributionPointDefinition.validate` 见 `packages/nb-runtime/src/plugins/contracts.ts:43-54,118-129`；合同对象一致性见 `docs/specs/runtime/plugins.md:77`。现有 `bun test src/plugin-manifest` 的 9 个通过用例没有任何内置定义往返，不能证明这项判据成立。
- **建议改法**：先定义可序列化元数据与仅运行期钩子的边界，往返测试只排除明确列出的函数钩子而不是只排除 activate；决定如何保留现有可选依赖，不能静默改为必需。贡献点清单携带可判定 schema，额外语义校验另有不需激活的明确入口；`receives` 补进公开格式。合同对象/元数据如何从 SDK 合同模块进入登记、如何保证激活产物使用同一对象，在 t04 开工前确定。宿主 capabilities 不冒充普通插件提供项，diagnostics/http 的工厂参数继续按 ADR 0026 留在宿主。

### 8. “一个状态根只由一个服务端拥有”没有实现，两个成功安装会互相覆盖登记

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/neuro-book/src/backend/plugins/registry.ts:98-103,127-131,296-325`；`.agents/works/w00027-plugin-platform/tasks/t03-manifest-and-install/plan.md:33-39`；`docs/specs/runtime/plugin-install.md:75-84`。
- **现象**：原型用 registry 对象内的 Promise 队列排他，注释据此假设跨进程不需要锁；服务端并没有 State Root 独占机制。两个进程使用同一状态根、各自监听随机端口，都能启动并成功处理安装。它们各自读旧 JSON、各自整表 rename，最后一次写覆盖另一次。
- **为什么是问题**：原子替换只防止半份 JSON，不防止丢更新。即使用户同时安装的是两个不同插件也会丢一个；未来按“未登记目录都是残留”恢复时，还会删除那个已经向用户报告安装成功的插件目录。仅按插件 id 加锁仍然不够，整表读改写必须有共同提交锁。
- **如何核实**：运行 `bun --tsconfig-override /home/notnotype/CodeRepository/neuro-book/.worktree/w00027-t03-manifest-and-install/packages/neuro-book/tsconfig.json /tmp/neuro-book/review-w00027-t03-design/lab/concurrency.ts`。实验启动两个真实服务端子进程，监听 `36987`、`43777`，经各自真实 WebSocket 管理接口同时安装 alpha/beta；2 次都返回成功，磁盘有 2 个目录，但登记表只剩 `example.alpha`。两个子进程最后都 exitCode=0。
- **建议改法**：最简单是宿主在任何状态根读写之前取得进程级独占锁，第二个进程明确拒绝启动，锁随异常退出释放；若产品允许共用状态根，则为登记表整次读改写及目录回收定义跨进程事务锁，不能只串行同一 id。计划和 Spec 写明可依赖的 owner 保证，并用两个真实进程验收。

### 9. 复制抛异常时没有回滚，重启也不清残留；“临时文件后 rename”不足以兑现恢复合同

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/backend/plugins/registry.ts:127-132,307-328,367-430`；`.agents/works/w00027-plugin-platform/tasks/t03-manifest-and-install/plan.md:34-37`；`docs/specs/runtime/plugin-install.md:81-84,105,109-110`。
- **现象**：只有 `copyRange` 返回失败或入口缺失的分支删 target；`copyFile`、`writeRecord` 直接抛异常时落入 catch，返回失败但不删已复制的目录。`writeRecord` 自身也没有 finally 清临时文件。启动发现只遍历登记项，未登记的版本目录永不扫描或回收。
- **为什么是问题**：普通权限错误就能留下半份安装，不必等到崩溃。新规范承诺 copy-failed 时已删部分文件、登记写入失败时恢复原状、重启后删除未登记残留；现有控制流三项都做不到。未来加入 pending 升级后，不能把这个 catch 直接复用成事务恢复。
- **如何核实**：运行 `bun --tsconfig-override /home/notnotype/CodeRepository/neuro-book/.worktree/w00027-t03-manifest-and-install/packages/neuro-book/tsconfig.json /tmp/neuro-book/review-w00027-t03-design/lab/install-failure.ts`。源 `z.txt` 无读取权限，经真实管理 RPC 返回 EACCES；列表为空，但 `example.unreadable/1.0.0/` 已留下 package.json。停止并重启真实服务端后，该残留仍存在，两次停止均 exitCode=0。
- **建议改法**：以已提交标志区分回滚与残留回收；提交前所有异常都清准备目录，临时登记文件在 finally 收口。启动恢复先读取并保留 current/pending 引用，再回收无引用版本；删除失败保留可重试证据与诊断。把复制抛错、登记 rename 失败、提交前后中断分开验收，不能只测显式返回失败的分支。

### 10. 引导协议把“构建里没有这个内置 id”也当成第三方，破坏原有构建核对

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/web/host/window.ts:313-330`；`.agents/works/w00027-plugin-platform/tasks/t03-manifest-and-install/plan.md:56-58`；`docs/specs/runtime/browser-host.md:47,49`。
- **现象**：新代码只在 `builtinLocal !== undefined` 时检查版本；找不到 id 时一律用引导描述合成插件，包含保留的 `nbook.*`。本地还有定义时，连内置描述缺失都照常 ready；真的是旧构建、没有定义时，有 browser 入口的内置插件变成 `startup-failed`，只有声明的内置插件则被静默注入，均不再按既有合同判 `incompatible` 提示刷新。
- **为什么是问题**：计划明确要求内置 id 与版本核对“不变”，实际只保留了已找到 id 的版本检查。“不在 builtin 表”不等于“第三方”；保留的 nbook 命名空间已经能明确区分这两种情况。协议 v3 没有明确来源字段，更不能据本地是否存在反推来源。
- **如何核实**：运行 `bun --tsconfig-override /home/notnotype/CodeRepository/neuro-book/.worktree/w00027-t03-manifest-and-install/packages/neuro-book/tsconfig.json /tmp/neuro-book/review-w00027-t03-design/lab/browser-selection.ts`。经真实服务端、引导、WebSocket 与窗口运行实例，从本地 builtin 描述表移除 `nbook.plugins`，保留定义表以单独观察 id 核对，结果 `missing-builtin-descriptor-state: ready`，不是原合同的 incompatible。完整缺少定义时的分类差异是上述分支直接推导，未另起浏览器验证。
- **建议改法**：在合成第三方描述前，保留对 `nbook.*` 的缺失 id 拒绝；或者引导显式携带可信来源并按来源分别处理。规范把第三方描述装载作为已实现“只给 id/version、必须在本地构建内”规则的明确例外，验收同时覆盖“新增内置 id + 旧外壳”“内置版本不同”“真正第三方声明式插件”。

### 11. 移入热插拔的升级流程会激活已禁用插件，和安装规范的用户状态保持规则冲突

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/runtime/plugin-hot-plug.md:73-81`；`docs/specs/runtime/plugin-install.md:57-58,72`。
- **现象**：安装规范允许对已禁用插件升级，要求保持已禁用，只切换文件与登记、不激活。热升级输出 10 第 2 步则统一要求旧版本“按禁用”停止、登记新版本、重新激活依赖者；第 4 步把新版本全部 `onStartup` 服务端入口激活成功作为成功条件，没有按用户状态区分。
- **为什么是问题**：对禁用的 B 安装新版本，照热升级文字实现就会把 B 的 onStartup 入口实际运行起来，或者因不激活而永远无法判定升级成功；“按禁用”若复用输出 2 的完整流程，还会把原本已启用插件的用户状态写成已禁用。新 Spec 没有说明这里仅复用停止机制、不能改用户状态。t03 的重启升级可以保持正确，但未来 t04/S5 按现有合同实现将返工。
- **如何核实**：按 `已禁用 A → 安装 B（B 有 onStartup）` 和 `已启用 A → 热升级 B` 两条时序，分别展开 plugin-hot-plug 输出 2 与输出 10，再对照 plugin-install 输出 8。该能力尚无实现，本项是合同推导，不宣称已运行复现。
- **建议改法**：显式区分用户禁用与升级内部停止；内部停止不写用户状态。热升级保持原用户状态，禁用插件只验证并提交新版本，不激活任何入口，也不恢复其依赖者；成功判定对禁用分支单列。补这两条状态组合与失败回滚的验收。

### 12. 规范收口仍保留相反的公开限制与实现历程，不能作为唯一作者合同

- **严重程度**：建议；**类别**：文档。
- **位置**：`docs/specs/workspace/markdown-syntaxes.md:84,112`；`docs/specs/runtime/browser-host.md:47,49,112`；`docs/specs/runtime/plugin-api.md:20,46,73`；`docs/specs/README.md:204`；`docs/specs/runtime/plugin-manifest.md:22,63,134`；`docs/specs/runtime/plugin-install.md:77,143`。
- **现象**：Markdown 输出 12 已允许任何来源，边界却仍写“第一版只给内置插件”；browser-host 的已实现引导仍只给 id/version、遇到本地没有的插件就提示刷新，与本轮第三方描述例外冲突；Spec 注册表仍把 plugin-install 描述成“热升级与回滚”。plugin-api 总述仍要求所有内置服务遵守形态约束，选用表同时保留第三方本地服务的异步数据面要求，而 ADR 0027 决策 3 已改成只有远程合同必须如此。ADR 0027 的“部分取代”摘要只提旧 ADR 后果，实际还改变 ADR 0022 决策 3 的公开 API 承诺。
- **为什么是问题**：作者照字面会得出不同的可用 API 与兼容边界。另有明确写法违例：清单 Spec 的“现状”列内部 `PluginDefinition`、源码位置与迁移历程；安装 Spec 指定临时文件替换算法，并在证据里保留“值尚无实现验证、可按实测修订”的行为门槛。前者换实现行为不变也要改，后者不是确定的目标合同，分别不满足 Spec README 的两条判据。
- **如何核实**：在 docs 与指定源码/示例范围查找 `只限内置|只给内置|不对第三方|允许清单`。除计划第 70 行已点名的实现合同外，遗漏还包括 `packages/neuro-book/src/plugins/commands/shared/contracts.ts:108-109`、`state/shared/contracts.ts:39-40`、`examples/plugins/notes/web/plugin.ts:7-9`、`examples/README.md:115,129`、`examples/scenarios/04-remote-service.test.ts:178`、`examples/testing/stage.ts:85-89`。这些旧限制应随切换一起清理，不把权限新决定只落实在若干 Spec 中。
- **建议改法**：同步修改当前边界与注册表；在新 ADR 中准确列出覆盖的旧决定范围，不改写旧 ADR 的冻结正文。实现策略与历程移进 plan/代码注释，Spec 只保留原子性、失败恢复、公开格式与寿命保证；固定决定不要再留“可按实测修订”的授权句。代理删除的三处条目已正确加 planned 标记，落地并取证后再去掉，不应直接把尚未切换的实现合同伪装成当前事实。

### 13. 声明式验收样例安装成功却永远不会出现设置项，现有目录测试也没有测到声称的边界

- **严重程度**：重要；**类别**：测试。
- **位置**：`packages/neuro-book/examples/external/declarative/package.json:14-23`；`src/shared/settings.ts:166-180`；`src/backend/plugins/registry.test.ts:89-100`；`.agents/works/w00027-plugin-platform/tasks/t03-manifest-and-install/plan.md:76-82,88`。
- **现象**：固定样例的设置声明缺少 `layers` 和 `applies`，真实贡献点要求这两个字段；安装器只校验清单外壳，所以安装成功、重启后贡献被拒。目录测试里的 symlink 是 `source/link.js`，但样例明确 `files:["dist"]`，链接根本不在复制范围内；另一测试断言整个 id 父目录消失，而不是失败版本没有残留文件，混淆空父目录和半份安装。
- **为什么是问题**：本 Task 的核心验收载体本身不可工作，现有测试却没有把它送入真实设置贡献点；错误的 symlink 用例也不能证明第 5 条边界成立。当前“字段合法/非法各一条”不能代替跨层组合验收。`files` 被称为 npm 语义，但 S0 尚未收口目录匹配规则，只有 `["dist"]` 的测试会掩盖 glob 与目录递归差异。
- **如何核实**：`install-runtime.ts` 经真实安装、重启后查询 `example.hello/greeting`，得到 `invalid-declaration`，详情为“layers 必须是 user、project 的非空子集”；同脚本补齐字段的 `example.good/greeting` 为 accepted。`bun test src/backend/plugins src/plugins/plugins` 实际只发现 registry 的 1 个测试文件，6 pass、2 fail；`src/plugins/plugins` 下没有服务合同测试。`install-failure.ts` 还证明 `files:["dist/*"]` 没有把匹配到的 nested 目录展开，实际存在的 browser 入口被报缺失；这是已测行为，是否采纳须在 S0 明确，而非声称已对齐 npm。
- **建议改法**：先修正固定样例并把它通过真实应用登记，断言设置声明 accepted、重启前后出现/消失；将链接放进实际复制范围，并增加“范围外链接不影响安装”的反例。失败回滚断言版本目录/登记/文件，不绑定空父目录实现；明确 files 支持的精确语法与目录递归规则，真实文件树覆盖普通目录、目录 glob、排除项、空匹配与缺失入口。再建立经内核管理合同与设置页的验收，不用 parser/磁盘成功替代产品贡献生效。
