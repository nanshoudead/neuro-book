二、码的来源（读代码后的结论）
- STORAGE_FAILURES（shared/storage.ts，14 个）：open、读取、保存、重试的失败码，经 shared/store/persisted.ts 的 failure 与 save.code 进入布局状态。
- corrupt、unsupported-version：不是 STORAGE_FAILURES。它们是 RecordSnapshot 的 status（shared/storage.ts），plugins/workbench/web/state/layout-store.ts 第 106 行把它们报成 kind 为 unread 的问题。
- provider-stopped：不是 STORAGE_FAILURES。它是订阅结束的原因，由 plugins/storage/backend/owner.ts 第 135 行调用 onEnd("provider-stopped") 产生，经 persisted.ts 的 #fail("ended", reason) 进入 failure，最后 unread。
- change-threw：不是 STORAGE_FAILURES，漏掉的一个。persisted.ts 第 382、394 行在修改函数抛错时把 save.code 设为 change-threw，状态栏据此显示 unsaved。brief 没提到它，我按它的实际来源补上了。

三、做了什么
1. 码表类型：type ReasonCode = StorageFailure | "corrupt" | "unsupported-version" | "change-threw" | "provider-stopped"；REASONS 声明为 Readonly<Record<ReasonCode, LocalizedText>>。缺一个码，或多写一个不存在的码，都过不了类型检查。StorageFailure 从 nbook/shared/storage 以 type 导入。
2. 新增 10 个 STORAGE_FAILURES 码的中英原因：invalid-value、too-large、protected、originals-full、definition-conflict、no-client、no-project、invalid-resource、denied、busy。另补 change-threw。原有 7 个文案保持原样（unavailable、conflict、unknown-outcome、io-error、corrupt、unsupported-version、provider-stopped）。文案按 Storage 规范 persistence.md“失败与恢复”表的含义、以及 explorer/web/feedback-text.ts 的既有写法（例如 busy 的“另一个…正在…，请稍后重试”）撰写。
3. 兜底：不认识的码仍原样显示（保持现状）。查表改用 Object.hasOwn（isReasonCode 类型守卫），不再用 REASONS[code] === undefined。
   原因：原来的写法会命中 Object.prototype 上的名字。实测 code 为 "constructor" 时，原来显示的是“布局未读取，正在用默认布局（undefined）”，这是个真实的 bug，已由新测试覆盖。
4. 注释：REASONS 上方写了码的来源、类型穷举的理由，以及订阅结束原因是无类型字符串这一限制。
