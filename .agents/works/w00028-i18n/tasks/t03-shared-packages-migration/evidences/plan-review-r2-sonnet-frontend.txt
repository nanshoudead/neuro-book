## 新发现

### 1. 第 4 片没写消费方怎么接 `Text`：纯 TS 函数没有端口，搜索会静默把 `kind`、`key` 当别的语言文字
- 严重程度：重要
- 类别：切片依赖 / 每片能否通过 typecheck / 验证是否真能发现错误
- 位置：plan.md 第 4 片（“浏览器渲染处显式取端口的 `t`”一句）与“边界”；`src/plugins/settings/web/settings-window.ts:409,434-450,461-466,614-635`；`src/plugins/workbench/web/commands/command-query.ts:134-173`；`src/plugins/workbench/web/components/WorkbenchCommandPalette.vue:97,106`；`src/ui/settings/setting-text.ts`；`src/plugins/commands/shared/menus.ts:218`
- 现象：第 4 片把声明字段的类型从 `LocalizedText` 换成 `Text`（string、TextRef、LocaleMap 三态）。声明字段流进的消费方里，不少是没有组件上下文的纯 TS，签名是 `locale: DisplayLocale` 或 `options.locale: Ref`：`createSettingsWindow` 里对声明字段调 `localize(...)`/`textOf(...)` 有 11 处（上列行号）；`searchCommands(commands, query, recent, locale)` 对 `command.title` 调 `localize`，并用 `otherTexts(text, locale)` 取其它语言写法，实现是 `Object.entries(text)`（command-query.ts:173）；`menus.ts:218` 是 `localize(declaration.label ?? command.title, facts.locale)`。我按“实参是声明字段（title、description、category、label、tooltip 等）”粗 grep `localize(`/`textOf(`，非测试代码有 34 处、18 个文件，实际更多（经局部变量传入的没算进去）。计划第 3 片给了端口和 `variants`，第 4 片只说“显式取端口的 `t`”，没说这些纯 TS 函数的签名怎么改。
- 为什么是问题：
  - 类型层面：`localize(text: LocalizedText, …)` 收到 `Text` 就编译不过，第 4 片“typecheck 通过”必须把这 18 个以上的文件都改完，而计划没有列、没有判一种统一的接法（把 `TextPort` 作参数传入，还是传 `resolve(text)` 与 `variants(text)` 两个函数）。第一轮第 2 条要求的正是这一句，处理记录只回应了“分出纯数据层”。
  - 运行层面更隐蔽：`otherTexts` 对 string 返回 `[]`，对 `TextRef` 对象则走 `Object.entries`，类型上完全合法，会把 `"text"`（kind）与键名当成“别的语言写法”参与命令面板匹配；`WorkbenchCommandPalette.vue:97` 对快速选择项的 `label`、`detail` 同样。第 4 片放宽后第三方立刻能写 TextRef，这条在测试里没有任何入口会红（第 4 片验收只写“全部内置插件装载、标题照常显示”，内置全是 LocaleMap）。
- 如何核实：在 W 里把 `SettingsWindowOptions.locale` 的消费处看一遍（`rg "options.locale.value" src/plugins/settings/web/settings-window.ts` 得 11 行）；`rg "otherTexts" src` 看到只有 command-query 与命令面板两处调用，实现为 `Object.entries`。
- 建议改法：第 4 片加一小节“文字解析的接法”：纯 TS 的工厂与查询函数把 `locale` 换成 `TextPort`（或 `{t, variants}` 两个函数），列出要改的文件（至少 settings-window、command-query、WorkbenchCommandPalette、ui/settings 下的 setting-text/SettingsRow/SettingsPageList/SettingsSaveBar、menus）；`otherTexts` 改为 `port.variants` 的包装；验收加两条：一个声明用纯字符串标题、一个用 `{kind:"text", ns, key}` 引用（用测试里临时登记的目录），命令面板与设置搜索都能按当前语言和其它语言命中，且不会出现 `kind`、`key` 被匹配上的结果。若文件太多，把第 4 片拆成“4a 类型与校验、4b 消费方接端口”，4a 不提交成独立可用的片（类型换了消费方必红）。

### 2. 第 4 片换 schema 时，两条跨位置出口没有转换规则：远程命令列表的 `title`，以及服务端也求值的公开状态 `reason`
- 严重程度：重要
- 类别：原子性 / 每片能否通过 typecheck
- 位置：plan.md 第 4 片“不含 `RemoteCommandSchema.title` … 本片对远程出口仍只送 `LocaleMap`”；`src/plugins/commands/shared/plugin.ts:123-135`（`title: command.title`）、`:66`（`localize(declaration.reason, locale())`）；`src/plugins/commands/shared/contracts.ts:145`；`src/plugins/state/shared/plugin.ts:46`、`src/plugins/state/shared/contracts.ts:21`；`packages/nb-runtime/src/remote/node.ts:857-862`
- 现象：
  - 命令的 `CommandDeclaration.title` 在第 4 片改为 `Text`，而 `RemoteCommandSchema.title` 保持 `LocalizedTextSchema`。`remoteCommands()` 直接写 `title: command.title`，类型是 `Text` 赋给“两个必填键的对象”，编译不过。计划只说“远程出口仍只送 LocaleMap”，没说一个 string 或 TextRef 标题怎么变成 LocaleMap：TextRef 要靠目录翻译，而 `TextPort.t` 只出当前语言一份；服务端不翻译。
  - 运行层面：浏览器是提供方，nb-runtime 在提供方侧按输出 schema 校验，不合格整个调用判 `provider-error`（node.ts:857-862）。第 4 片之后第三方一个字符串标题的命令就会让 `list` 对所有命令都失败，到第 6 片升版本才恢复。
  - 公开状态 `reason`：`state/shared/contracts.ts:21` 的 `reason?: LocalizedText` 在第 4 片换成 `Text` 后，`commands/shared/plugin.ts:66` 的 `localize(declaration.reason, locale())` 编译不过。这个文件在服务端与浏览器都激活（`commandsEntry(location)`），属于“边界”一节说的“服务端也加载的模块只依赖纯数据层”，而 TextRef 在服务端没有目录可翻。`menus.ts:218` 在 `shared/` 里，同类。
- 为什么是问题：计划的“边界”一节说服务端路径继续只产出 LocaleMap 或字符串，但没说这些路径的**输入**一旦是 TextRef 怎么办。照字面实现，实现者要么给服务端路径写“TextRef 取键名”的临时分支，要么在第 4 片里悄悄把 reason、title 排除出去，后者才是对的但计划里没有。
- 如何核实：看 `remoteCommands()` 的 `list`（plugin.ts:123-135）与 `RemoteCommandSchema`；`rg "reason" src/plugins/state/shared` 确认 reason 是 `LocalizedTextSchema`。
- 建议改法：把“命令声明的 `title`、公开状态的 `reason`”这两个 schema 的放宽放进第 6 片，与远程 `list` 升版本 2 一起原子提交；第 4 片对这两处保留 `LocalizedTextSchema`，其余 7 处照换。或者在第 4 片写明 TextRef 在服务端求值路径上的结果（例如服务端求值只接受 LocaleMap 与 string，TextRef 登记时拒绝并给诊断），并加一条测试。

### 6. 共享包交付的两处缺口：JSON 包装模块不减少消费者要求，交付验收没有消费者类型检查；nb-agent-ui 三个独立根的无注入验收没写
- 严重程度：建议
- 类别：兼容 / 验证（第一轮第 9 条的剩余部分）
- 位置：plan.md“技术选型”末行、“共享包几片”nb-agent-ui 一行、交付片“验收”；`packages/nb-ui/package.json`（`files` 含 `src`，`exports` 全是 `.ts`）
- 现象：
  - 共享包发布的是 `.ts` 源码（nb-ui 的 `exports` 指向 `./src/*.ts`）。计划选的做法是“目录写成 JSON，另有一个 `.ts` 模块包一层 `import … with {type:"json"}`”。包装模块自己仍在 import JSON，消费者的 TypeScript 编译这份源码时照样要 `resolveJsonModule`（以及 TS 5.3 以上才支持的 import attributes），包装并不减少要求，只是给目录一个统一出口。README 写明要求是对的，但提案原话“或者把目录包成 `.ts` 模块再导出”指的是把数据写成 `.ts` 对象字面量；计划“否决”了那条（翻译平台读不了），所以实际只剩 README 一条路，计划里的“包一层”的好处没说清。
  - 交付片的验收有 SDK 的“仓库外类型检查”，没有共享包的：用不开 `resolveJsonModule` 与开了两种 tsconfig 的最小消费工程各装一次 tarball 跑类型检查，才能证明 README 的说法属实、报错就是 TS2732。
  - nb-agent-ui 有三个可独立挂载的根（`AgentConversationView`、`AgentSessionList`、`AgentModelCatalog`，nb-story 都单独用）。计划只写“`locale` 属性只在没有注入时起作用”，没写三个根各自在无注入时提供端口；nb-story 查看器靠它保持单语中文。
- 为什么是问题：已发布包的消费者是这个 Task 里唯一不能回退的部分。
- 如何核实：`jq .exports packages/nb-ui/package.json`；`rg "AgentSessionList|AgentModelCatalog" packages/nb-story/src --files-with-matches`。
- 建议改法：交付片验收加“消费工程类型检查（开/不开 `resolveJsonModule`，各用 bundler 与 node16）”；nb-agent-ui 一行加“三个根在无注入时各自可挂载且显示中文”的组件测试；技术选型一行把“包一层”的目的写清（统一出口，不是降低要求）。

### 7. 第 3 片的语言来源机制只写了结果，没写谁调用、何时同步；六处“各自派生 locale”是保留还是改，没有说
- 严重程度：建议
- 类别：遗漏的假设
- 位置：plan.md“边界”第三条、第 3 片；`src/plugins/{commands/shared,editor/web,explorer/web,plugins/web,projects/web,workbench/web,settings/web}/plugin.ts`（各自 `computed(() => displayLocale(settings))`，共 7 处，`rg "displayLocale\(" src` 可数）
- 现象：“过渡期还在往下传 `locale` 属性的地方，由宿主从同一个来源传，不另读设置”这句有两种读法：保留各插件现有的 `computed(() => displayLocale(settings))`（它们本来就读同一份设置快照），或者把这 7 处改成读端口的 `locale`。计划没有选，第 3 片的代码清单也没列这 7 个文件。另外引擎的 `changeLanguage` 由谁在什么时机调用（设置插件的浏览器入口激活时？窗口根里的 `watch`？）以及刷新时机（`flush: "sync"` 还是默认）没写。
- 为什么是问题：若引擎靠默认 `flush: "pre"` 的 watch 同步，切换语言的那一拍里，读 `locale` 属性的组件已经换成新语言，用 `t()` 的组件还停在旧语言，同一屏中英混杂一拍，可能让 dom 测试出偶发红；若实现者选“改这 7 处”，第 3 片的范围就比计划写的大。
- 如何核实：看这 7 处与 `src/web/host/window.ts`（宿主已引用 workbench 合同，所以宿主层引设置服务键不违反分层）。
- 建议改法：写明保留现有 7 处不动，端口的 `locale` 由窗口根在设置服务就绪时用同步 watch 驱动；第 3 片的“切换语言不重新挂载”用例加一条：切换后同一个 tick 内，读 `locale` 属性与读 `t()` 的两个组件显示同一种语言。

### 8. 第 7 片起与后几节的相对顺序、数字口径没有写；`src/ui` 在第 4 片已被迫要改，却排在最后
