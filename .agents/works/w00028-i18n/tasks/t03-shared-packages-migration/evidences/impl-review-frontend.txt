### 1. 重要 / 正确性 / `packages/neuro-book/src/web/host/text-engine.ts:98-105`（translateRef）：插值参数名与 i18next 保留选项重名时行为错乱
- 现象：`lookup = {ns: ns ?? "", ...params}` 把调用方的参数整个摊进 i18next 的 `t` 选项。参数名恰好是 i18next 的选项名时，参数不再是“插值值”而是控制项。实测（实现 worktree，`bun run /tmp/w00028-t03/review-impl/exp/a.ts`、`b.ts`）：
  - 参数 `context`：目录 `ctx: "x {{context}}"`、`ctx_foo: "FOO"`，传 `{context:"foo"}`，宿主得 `FOO`，最小实现得 `x foo`。
  - 参数 `ns`：`{ns:"other"}` 把查找换到别的命名空间，宿主得到键名 `nsp`（严格模式抛缺键），最小实现得 `other`。
  - 参数 `lng`：`{{lng}}` 被链上的语言覆盖（得 `zh-CN`）；`defaultValue`、`replace`、`ordinal`、`interpolation` 同理被 i18next 吃掉或改变行为；`lngs: "en"` 直接抛 `codes.forEach is not a function`（渲染期异常）。
- 为什么是问题：`context`、`ns` 在“写作 + Agent”产品里是很自然的占位名（上下文、命名空间）；第三方插件作者看不到这条隐性约束，目录检查脚本（`scripts/ci/message-catalogs.ts` 的 PLACEHOLDER）和 Spec 输出 3/6 都没提。违反输出 9“两个翻译器相同”的精神：同一组目录同一组参数，两个实现结果不同，且宿主这边是静默错字。当前仓库内目录没有用到这些名字（grep 无命中），所以是潜在问题，不是现状故障。
- 如何核实：见上，`bun run /tmp/w00028-t03/review-impl/exp/b.ts`（在 `.worktree/w00028-i18n/packages/neuro-book` 下运行）。
- 建议改法：插值值放进 i18next 的 `replace` 选项（`i18n.t(key, {lng, ns, count, replace: params})`；`count` 仍须在顶层）；或在 `sanitizeParams`/目录检查里拒绝保留名。前者无代价，一并给输出 9 补一例“参数名叫 context/ns”。

### 2. 建议 / 正确性 / `packages/nb-ui/src/text/minimal.ts:62-64` 对 `packages/neuro-book/src/web/host/text-engine.ts`：`{{n, number}}` 收到数字字符串时两个翻译器不一致

### 5. 重要 / 不变量 / `packages/{nb-agent-ui/src/vue/text.ts:62-70, nb-form/src/vue/text.ts:81-86, nb-markdown/src/host/text.ts:60-66}`（`provideXxxText`）：共享包的缺省端口遮住兄弟包目录，应在 nb-ui 底层解决，而不是在使用方各合并一个端口
- 现象（从代码推断；仓库里唯一的复现是 nb-story 为它写了补丁）：三个包的根组件在“没有注入端口”时各建一个只含 `nb-ui + 本包` 目录的端口并 `provide`。凡是把两个共享包嵌在一起、又没有宿主的使用方（对话视图 `AgentConversationView` 里放 `nb-markdown` 的 `MarkdownDisplay`/`PromptEditor` 是它的设计用法；设置页 `SchemaForm` 里放 `nb-markdown` 的编辑器同理），内层的 `provideMarkdownText` 看到外层已经注入的“包内缺省端口”，`injected !== null` 就直接用它，于是 `nb-markdown` 的键显示成键名。`nb-story/src/web/qa/text-port.ts` 的头注释自己写明了这一点，只对 QaPage 做了合并端口 `storyTextPort()`（手写列三个包的目录，再 `provide`）。
- 为什么是问题：
  1. 这是回归：改前每个包的组件按各自 `locale` 属性独立工作，组合没有问题。改后，已发布的 nb-agent-ui/nb-markdown/nb-form（0.1.0，npm 上有人用）的第三方使用方在不接宿主引擎时，必须自己知道“要手写合并端口”，而版本表和 Spec 输出 8 只说“共享包的缺省端口只含自己的目录”，没有给使用方出路。
  2. 每新增一个共享包或一次新的嵌套组合，就要再改一处合并端口；nb-story 的合并端口已经和 `createHostTextEngine` 的登记列表是同一份清单的两份手抄。
  3. 缺省端口里 `injected !== null` 无法区分“宿主的完整端口”和“别的包的残缺缺省端口”，运行期没有任何诊断：只看到键名（宿主测试环境的严格模式会抛，缺省端口不抛）。
- 如何核实：读 `provideMarkdownText`（`nb-markdown/src/host/text.ts:62-70`）与 `AgentConversationView.vue:54`；`nb-story/src/web/qa/text-port.ts` 头注释。
- 建议改法（底层）：把“登记过的目录”放进 nb-ui 的缺省端口，而不是每个包私有：
  - nb-ui 新增 `registerDefaultCatalog(ns, catalogs, source?)`（进一个模块级 `createMinimalTranslator` 共用的可变表）和 `provideDefaultText(locale: () => string | undefined): TextPort`（有注入就用，没有就建一个按 `locale` 的端口并 `provide`）；`defaultTextPort()` 与 `provideDefaultText` 都用这张表。
  - 每个共享包的 `locales/index.ts` 在导入时登记自己的目录（需要在 package.json 写 `"sideEffects": ["./src/locales/index.ts"]` 或类似；目前四个包的 package.json 都没有 `sideEffects`）。
  - 三个包的 `text.ts` 各自约 40 行重复（`packageTranslator`、`packagePort`、`defaultPort`、`provideXxxText`）收缩成对 nb-ui 的薄包装；`storyTextPort()` 与 QaPage 的 `provide` 删除。
  - 代价：模块级可变状态（SSR/多实例要小心；用 `Symbol.for` 键挂 `globalThis` 保证两份 nb-ui 也共用一张表，与 `TEXT_PORT_KEY` 同样处理）；“导入即登记”要求目录模块不能被摇掉。收益：消除上面三点，Spec 输出 8 可以改成“缺省端口含所有已导入共享包的目录”。
- 若开发者不想引入模块级登记，次选：`provideXxxText` 发现注入的端口带 `fallback: true` 标记时，用“合并两个包的目录”重建；代码更多，不建议。

### 10. 建议 / 不变量 / `scripts/ci/message-catalogs.ts:63` 与 `docs/specs/ui/i18n.md` 输出 9：“最小实现与宿主引擎一致”只对目录用了子集成立，检查脚本却不把目录限制在这个子集内
- 现象：输出 9 的前提是“目录只用插值（含 `number` 格式）与 `_one`、`_other`”。实测（`bun run /tmp/w00028-t03/review-impl/exp/c.ts`，实现 worktree）以下写法都通过目录检查（PLACEHOLDER 是 `[^{}\s]+`），但两个翻译器输出不同：

  - `{{- v}}`（i18next 的不转义写法）：宿主得 `U<b>`，最小实现留原文。

- 为什么是问题：共享包（nb-ui/nb-form/nb-agent-ui/nb-markdown）的目录在没有宿主时走最小实现，在宿主里走 i18next；其中任何一个目录里写了上面之一，同一键在两个环境显示不同，没有任何机检拦截。第三方插件只走宿主引擎，所以它们不受限，但它们的目录若被共享包式的缺省端口（例如 nb-story）加载就会不一致。目前仓库里没有这样的写法（grep 无命中），所以只是缺机检。

### 12. 建议 / 代码质量（API 形状，站在使用方） / 共享包与插件取文字的入口：同一件事有五种形状，Task 目标里“合并 say/formatText/locale 类型”只做了一半
- 现象（接入草稿的所见）：
  - 取文字的写法按位置各不相同：nb-ui `useUiText()` 返回函数 `(key, params) => string`；`useText()` 返回端口 `{t(Text), variants, locale}`；nb-agent-ui `useAgentText()` 返回 `{locale, t(key), text(Text)}`；nb-form `useFormText()` 返回 `{locale, t(key), text(FormText|undefined)}`；nb-markdown `useMarkdownText()` 返回 `{locale, port, t(key), text(Text, params)}`；应用/插件 `usePluginText(ns)` 返回函数。`t` 一会儿收键，一会儿收 `Text`；`text` 在 nb-form 收 `undefined`，在 nb-markdown 多收一个参数。记忆负担：使用方每个包要重新查一次返回值形状。
  - 同样的“绑定命名空间 + 按源语言目录核对键”在五处各写一遍（第 6 条）。如果按第 5 条改成 nb-ui 里统一的 `useNamespaceText<typeof zhCN>(ns)`，各包的 `useXxxText` 只是它的一行别名，形状自然统一。
  - Task 的目标写“合并各自的 `say`、`formatText`、locale 类型（四份副本）”。实际仍留：`nb-agent-ui/src/text.ts` 的 `fill`/`formatText`、`nb-markdown/src/locale.ts` 的 `fillBraces`/`say`、`nb-form/src/text.ts` 的 `resolveText`，加应用里的 `localized-text.ts`；语言类型别名仍有 `PromptLocale`、`AgentLocale`、`MarkdownLocale`、`DisplayLocale` 四个（全是 `string`）。`fill` 与 `fillBraces` 是逐字相同的函数。
  - `MarkdownText` 同一个属性两套占位语法：`TextRef` 走 `{{name}}`（端口代入），字符串与语言映射走 `{name}`（`fillBraces`，`host/text.ts:67-71`）。作者在同一个 `imageMissing` 属性上换一种写法就要换一种花括号。
  - 宿主侧（接入一个 Vue 根）要知道：`TEXT_PORT_KEY`、`TextPort` 三个成员的语义（`variants` 是什么、`locale` 必须是响应式 ref）、每个共享包的 `./locales` 要自己登记（漏了只显示键名，无诊断）、`mount.ts` 要在三个根上各 `provide` 一次。没有 `createTextPlugin(port)` 之类的一步安装。
- 为什么是问题：概念数量对使用方偏多；“遮住兄弟包目录”（第 5 条）与“漏登记显示键名”都是这些样板的直接后果。
- 如何核实：`grep -rn "function fill\b\|function fillBraces" packages --include='*.ts' --exclude-dir=node_modules`；读五个 `text.ts`。
- 建议改法：
  1. nb-ui 提供一个入口 `useNamespaceText<Source>(ns)` 与 `defineNamespaceText<Source>(ns)`，返回函数形（与 `usePluginText`、`useUiText` 一致）；各包只导出一行别名，需要 `locale` 时单独 `useText().locale`。
  2. `fill`/`fillBraces`/`say` 合并到 nb-ui `text/` 一份；单花括号占位给旧的 `LocalizedText` 用，注明只为兼容。
  3. nb-ui 导出 `installTextPort(app, port)`（等价于 `app.provide(TEXT_PORT_KEY, port)`），并在 `createHostTextEngine` 里登记共享包目录时用“已导入包的登记表”（第 5 条）代替手抄列表。

### 15. 建议 / 正确性 / `packages/nb-ui/src/text/minimal.ts:49,59`：缺省端口的语言是任意字符串后，非法标签会在渲染期抛 `RangeError`，大小写不同则静默显示键名

- 建议改法：缺省端口在 `packagePort`/`defaultTextPort` 里把 `locale` 规范化一次（`Intl.getCanonicalLocales` 成功用规范形，失败回退 `zh-CN`），最小实现内的 `Intl.*` 调用也包 `try`，失败当 `other` 类别/原样数字；顺手在 Spec 输出 8 写明“非法标签按 `zh-CN`”。
