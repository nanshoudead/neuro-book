### 1. 第 3 片“不改变行为、测试不改”不成立：TextSchema 放宽了校验，现有测试断言的正是被放宽的拒绝
- 严重程度：重要（验证与范围）
- 位置：plan.md:36-38；`packages/neuro-book/src/shared/settings.test.ts:106-117`、`:187-190`；`docs/specs/settings/configuration.md` 输出 1、21；`docs/specs/workbench/commands.md:60`
- 现象：计划称第 3 片只是把 `LocalizedTextSchema` 换成 `TextSchema`，“现有双语字面量作为 LocaleMap 照常显示，测试不改”，且该片没有列任何 Spec。但 `TextSchema = string | TextRef | LocaleMap` 之后，下面这些现有断言会反过来：`declaration({title: {"zh-CN": "主题"}})` 期望被拒（只有一种语言，LocaleMap 允许）；`declaration({description: "主题"})` 期望被拒（纯字符串现在合法）；`ui: {placeholder: "只有一种语言"}` 期望被拒。Spec 里“title 缺语言”“选项的 title、description 缺语言”“文字缺语言”各使声明 `invalid-declaration` 被拒（configuration.md 输出 1、21），commands.md:60 写“中英两份文本”。这些是产品合同，不是实现细节。

- 建议改法：第 3 片明确“放宽哪些校验”（单语言 LocaleMap、纯字符串是否合法，须与提案“LocaleMap 取不到当前语言取 en-US 再取第一项”一致），列出要改的 Spec（configuration.md 输出 1、21，commands.md、menus.md、views.md、editor.md 等凡写“中英两份”的输出）和要改的测试（把“缺语言被拒”改成新语义下的拒绝场景，例如空字符串、非法语言标签、`kind` 错误）。

### 2. 第 3 片的体量被低估，且“渲染处改用端口”在没有端口的地方做不到
- 严重程度：重要（切片依赖、范围）
- 位置：plan.md:37-38
- 现象：计划写“10 处 `LocalizedTextSchema`”，实际是 9 个文件、22 处引用（menus 1、commands/contracts 3、sections 4、state/plugin 1、home 1、items 2、views 2、settings.ts 6、editor/contracts 2；`rg LocalizedTextSchema` 逐行数得）。更大的是下游：`Static<typeof TextSchema>` 变成 `Text` 后，所有 `localize(text, locale)`、`textOf(text, locale)`、`title["zh-CN"]` 的类型都会报错——`rg '\b(localize|textOf|formatText)\('` 在 `src`、`plugin-sdk` 里 170 处调用、72 个文件；`DisplayLocale` 205 处引用；另有直接取 `["zh-CN"]` 的（`view-commands.ts:88-89`、`ShellViewsScene.vue`、`WorkbenchViewContainerHostFixture.vue` 等）。其中大量是纯 TS 函数（`settings-window.ts`、`command-query.ts`、`shelf-format.ts`、`status-items.ts`），它们拿 `locale: Ref<DisplayLocale>` 作参数，没有 Vue 组件上下文，无法 `useText()`。

- 如何核实：上面两条 `rg`；读 `settings-window.ts:409-466`、`command-query.ts:134-173`。
- 建议改法：第 3 片拆成“类型与校验（TextSchema、Spec）”和“消费方改用端口”，后者先写清纯 TS 函数的接法（端口作参数 / `localize` 接受 `TextPort`），再列影响的文件数；`otherTexts`、`variants` 一并处理。

### 3. `TextSchema` 与 `Text` 放在哪没有写；`localized-text.ts` 被 Bun 服务端加载，“改为调端口”会把 Vue 注入带进服务端
- 严重程度：重要（切片依赖、包边界）
- 位置：plan.md:26、:37-38；`packages/neuro-book/src/server/plugins.ts:16,24`；`src/plugins/commands/shared/plugin.ts:19,41,66`；`src/plugins/settings/shared/contracts.ts:176`；`packages/nb-ui/package.json`
- 现象：
  - 第 1 片列了 `Text`、`TextRef`、`LocaleMap`、判别函数，没有列 `TextSchema`（TypeBox 值）；第 3 片却直接用 `TextSchema` 替换。提案把类型放 nb-ui，nb-ui 的 `package.json` 没有 `typebox` 依赖，`exports` 里没有纯 TS 子路径（根入口 `src/index.ts` 会拉进 `.vue` 组件）。
  - `src/server/plugins.ts` 直接 import `commands/shared/plugin`、`state/shared/plugin`，它们又 import `nbook/shared/localized-text`；`commands/shared/plugin.ts:41,66` 与 `settings/shared/contracts.ts:176` 在服务端/项目子进程里就地 `localize(formatText(…), displayLocale(settings))` 得到字符串（命令的失败 `reason`）。主 tsconfig 的 `include` 含这些 `shared` 目录，`lib` 只有 ESNext、无 DOM，`exclude` 掉了 `web`。
- 为什么是问题：计划第 3 片说“`localized-text.ts` 的函数改为调端口”，端口是 provide/inject 的 Vue 机制，服务端没有。若 `TextSchema` 放进 nb-ui 的子路径，该子路径必须不 import `vue`（`TextPort` 里的 `Ref` 只能是 `import type`）、nb-ui 要加 `typebox` 依赖（它是随 Nuxt 模块发布、被旧应用使用的包，加依赖是公开接口变化）；若放应用，则 nb-form/nb-agent-ui 核心层拿不到同一份判别函数。这几件事决定第 1 片的文件清单和 `exports`，却没有写。
- 如何核实：`rg -n "localized-text" packages/neuro-book/src/server packages/neuro-book/src/plugins/*/shared`；`grep typebox packages/nb-ui/package.json`（无输出）。
- 建议改法：第 1 片写明：`Text`/`TextRef`/`LocaleMap`/判别函数/`TextSchema` 在 nb-ui 的一个纯 TS 子路径（如 `./i18n/text`），端口与 `useText()` 在另一个（Vue）子路径；加 `typebox` 依赖或把 `TextSchema` 留在应用的 `shared/`（只引类型）。第 3 片写明服务端侧的字符串解析用 `(text, locale) => string` 的纯函数，不经端口。

### 4. 宿主引擎如何拿到语言没有写：语言是 `nbook.settings` 插件的服务，引擎在插件之前就要存在；过渡期有两份 locale 来源
- 严重程度：重要（切片依赖、遗漏的假设）
- 位置：plan.md:29-35、:37-38；`packages/neuro-book/src/plugins/settings/shared/contracts.ts:72`；`workbench/web/plugin.ts:148`、`explorer/web/plugin.ts:109`、`editor/web/plugin.ts:104`、`commands/shared/plugin.ts:160` 各自 `computed(() => displayLocale(settings))`；`src/web/mount.ts:31-54`；`docs/specs/settings/configuration.md` 输出 16
- 现象：当前语言只存在于设置服务（`settingsKey`），各插件各自派生一个 `locale` computed，再作为属性/host 参数传给组件（38 个测试文件、62 个 `.dom.test.ts` 里有 27 个在驱动 `locale`）。第 2 片的 `web/host/i18n.ts` 创建引擎并读写本地记录，但没有写：谁在设置快照到达时调用 `changeLanguage`（宿主不依赖 `nbook.settings`，ADR/Spec 写明依赖方向是单向的“其它插件依赖 settingsKey”）；`HostPage`、`FailurePage` 在设置插件激活前挂载，用什么语言（本地记录，但“记录”何时写、写入失败怎么办）；设置快照超时 3 秒后晚到又怎样；多窗口里一个窗口切语言，另一个窗口靠什么得知（现有靠设置服务的跨实例同步，端口得订阅同一来源）。
- 为什么是问题：第 3 片之后组件读 `port.locale`，而第 6 片之前各插件仍把 `locale` 属性往下传——同一界面有两份语言来源，二者不同步时（引擎还停在本地记录，设置已是 en-US）同屏中英混杂，这个窗口期正好是大批量迁移的 10 多片。
- 如何核实：读 `src/web/mount.ts` 与 `browser-host.ts` 找不到任何对设置服务的引用；`rg "displayLocale(" packages/neuro-book/src --glob '!*.test.ts'`。
- 建议改法：第 2 片写明“引擎的 `locale` 由哪个对象驱动”：建议在 `nbook.settings` 浏览器入口激活时（或工作台根）用 `watchEffect(() => engine.setLanguage(displayLocale(settings)))` 单向驱动，并规定第 3 片起 `host.locale` 等一律是引擎 `locale` 的派生，不再各自从设置读。把“语言切换后三个根、已开的 Lab、其它窗口同步”写成第 2 片的验收。

### 5. 共享包几片与“语言类型收尾片”之间有锁步类型断言，中间状态 typecheck 必红；片内顺序没写
- 严重程度：重要（切片依赖、兼容窗口）
- 位置：plan.md:57-63、:65-67；`packages/neuro-book/src/plugins/markdown/web/host.ts:23`；`packages/nb-agent-ui/src/types.ts:14`（`AgentLocale = PromptLocale`）
- 现象：`host.ts:23` 写着 `[DisplayLocale, MarkdownLocale] extends [MarkdownLocale, DisplayLocale]`（注释“两边的界面语言是同一组值；改了一边这里报错”）。计划把 `MarkdownLocale`、`PromptLocale` 改字符串放在“共享包几片”（nb-markdown），把 `DisplayLocale` 改字符串放在“收尾几片”。nb-markdown 先改为 `string` 后，`[DisplayLocale, string] extends [string, DisplayLocale]` 为假，该文件 typecheck 失败；`AgentLocale` 经 `PromptLocale` 也跟着变，`nb-agent-ui` 的 `locale` 属性被传 `DisplayLocale` 时类型仍兼容，但反方向（宿主回调接收 `AgentLocale`）会失败。计划每片都要求 `typecheck` 通过，所以这一步要么与 `DisplayLocale` 同片改，要么先删断言。
- 为什么是问题：实现者按计划顺序做会撞上红色 typecheck 然后自行决定删断言——而这条断言正是提案“一种语言集合由宿主目录决定”之前的保护。另外 `nbook.settings/locale` 的 schema 改为字符串、`localeSetting` 的 `default` 与选项生成（`settings/configuration.md`）与 205 处 `DisplayLocale` 引用要一起动，不宜放到最后一片再“一次改”。
- 如何核实：读 `host.ts:15-24`；本地把 `MarkdownLocale` 改成 `string` 跑 `bun run --cwd packages/neuro-book typecheck`。
- 建议改法：把“语言类型改字符串”提前成独立一片（紧接第 3 片）：`DisplayLocale`、`MarkdownLocale`、`PromptLocale`、`AgentLocale` 同时改为 `string`，`sameLocale` 断言改成“两边都是 string”或删除；`nbook.settings/locale` 的校验在此片按宿主目录做，选项由目录生成。共享包后续各片不再碰语言类型。

### 6. 共享包片没有写清“宿主没有注入时”的默认端口，nb-ui 叶子组件有三个无根组件的消费方
- 严重程度：重要（遗漏的假设、兼容）
- 位置：plan.md:26、:57-63；提案第 6 节“宿主没有注入时”；`packages/nb-ui/package.json`（被 `dev-panel`、`neuro-book-legacy`、nb-story 查看器、nb-ui 自己的 playground 与 vitest 使用）
- 现象：提案只规定“包的根组件”（nb-agent-ui、nb-form、nb-markdown 的根）在没有注入时用自带目录提供端口，“嵌套的 nb-ui 控件因此也拿得到”。nb-ui 自己没有根组件，而 `rg '"@notnotype/nb-ui"' packages/*/package.json` 显示还有 `dev-panel`、`neuro-book-legacy`、`nb-story` 直接用它的叶子组件；这些场景里 nb-ui 的 `Dialog`、`AlertDialog`、`Notification`、`Input`、`Splitter` 等（`rg` 到的写死中文：`确认操作`、`确定`、`取消`、`关闭通知`、`清空输入`、`加载中`、`暂无数据`、`对话框` 等，大多是 `withDefaults` 的属性缺省值，另有 `Splitter.vue:612` 的 `调整 ${a} 与 ${b} 的${宽度|高度}` 这类带插值与分支的 aria-label、`Slider.vue:125` 的 `滑块 ${index}`）改为读端口后，**没有任何人注入时 `useText()` 返回什么**，计划第 1 片只写了“`TextPort` 注入键与 `useText()`，最小实现”，没有写缺省。
- 为什么是问题：旧应用、dev-panel 面板、nb-ui 的 vitest 与 playground 都是没有宿主的环境；若 `useText()` 在无注入时抛错或返回键名，这些包的现有测试和界面在“不应该改变”的包里整体回归（旧应用“依赖照装、不检查”，坏了没人发现）。带插值与分支的几处 aria-label 在 `_one/_other`、`{{name}}` 之外还需要参数命名，计划也没提这类“拼句”的处理。
- 如何核实：`rg -n "withDefaults|defineProps" packages/nb-ui/src/components/feedback/AlertDialog.vue`；看 `Splitter.vue:612-616`；`rg -l nb-ui packages/*/package.json`。
- 建议改法：第 1 片写明：`useText()` 无注入时回落到 nb-ui 自带目录 + 最小实现，语言取 `document.documentElement.lang` 或 zh-CN，使旧应用和单元测试行为不变；nb-ui 片的验收加“无任何注入时（`mount` 不带 provide）现有 nb-ui 单测原样通过”。属性缺省值改读端口时，在组件 `.md` 里写明“属性不传则读端口”并保留显式传值的优先级。

### 7. 第 6 片起的抽取脚本只覆盖 TS 字面量，未覆盖 `.vue` 与“表加调用”两种主流写法；改写目标形态没有定义
- 严重程度：重要（后续切片照字面实现会返工）
- 位置：plan.md:17、:53-55、:85
- 现象：计划选型是“用 TypeScript 编译器 API 找 `{"zh-CN": …, "en-US": …}` 字面量……改写调用处”。实测（`git ls-files src plugin-sdk` 排除 `.test.`）：含 `"en-US"` 的行共 960 行，其中 36 个 `.vue` 文件里 345 行（约 36%），例如 `HtmlPreview.vue:19-20`、`SnippetsEditor.vue:30-37` 是 `<script>` 里的表，另有 `:labels="{…}"` 一类模板表达式；TypeScript 编译器 API 不读 `.vue`，需要先用 `@vue/compiler-sfc` 切块并处理模板里的字面量，这条计划没有写。更关键的是，多数文字不是“内联在声明字段里”，而是 `const TEXT = {foo: {"zh-CN":…,"en-US":…}}` 表加 `text(TEXT.foo, {…})` / `localize(formatText(TEXT.foo, {…}), locale)` 调用，还有 `const text = (zh, en) => ({"zh-CN": zh, "en-US": en})` 这类构造器（`rg '"en-US": [a-zA-Z`]'` 得 19 行，含 ``{"zh-CN": `${id}（当前）`, "en-US": `${id} (current)`}``、`view-commands.ts:88-89` 对两种语言各 `.replace("{part}", …)`）。“改成约定键或文字引用”的目标形态（声明字段直接删掉、组件里 `t("key")`、纯 TS 构造器返回 `TextRef` 带参数、跨插件运行期文字）在计划里一种也没定义，第 5 片的“带类型取文字辅助函数”只有一句话。
- 为什么是问题：脚本做什么、人工做什么的边界取决于这份形态手册；没有它，Haiku/Sonnet 子代理对同一类写法会改出不同形态，主会话审 diff 时没有判据，且各插件片之间会不一致，之后统一要返工。插值语法也变了（`{name}` → `{{name}}`），脚本必须同时改占位符与调用处的 `formatText`，而 `formatText` 对两种语言各代入一次的语义，和 `t(key, params)` 的数值/复数参数校验（500 字截断、只收字符串与有限数字）并不等价，现有传 `reason`、`detail` 字符串的调用会触发参数诊断。
- 如何核实：`git ls-files src plugin-sdk | grep -vE '\.test\.' | grep '\.vue$' | xargs grep -c '"en-US"'`；读 `view-commands.ts:80-92`、`HtmlPreview.vue:15-30`。
- 建议改法：开第 6 片前先写一页“迁移手册”（5 到 6 种写法 ➜ 目标形态），第 5 片的辅助函数签名同时定下；脚本明确走 `@vue/compiler-sfc` + TS API；可以先拿 explorer 或 commands（体量小）做一个插件的端到端试片，再定后面片的分派。

### 8. 迁移后“断言中文文字的测试改成断言键或结构”会拿掉唯一的文字等价检查；Lab 截图不是自动比对
- 严重程度：重要（验证是否真能证明做对了）
- 位置：plan.md:54、:85；`packages/neuro-book/scripts/lab-shot.ts`、`e2e/lab-layout-baseline.ts`
- 现象：抽取脚本把字面量搬进 JSON 目录后，“搬对了”（值与原文完全一致、英文没落在中文位置、占位符没丢）目前的实际证据只有那 369 个断言中文文字的测试；计划却要把它们改成断言键或结构。第 5 片的“声明测试”只核对键存在，目录检查只核对语言间缺键/占位符一致，二者都不比较“新值 = 旧字面量”。计划里“每片跑 Lab 截图对照”：`lab:shot` 是出截图与溢出 JSON 的命令，没有基线图比对，对照对象不存在；`lab-scenes.e2e.ts` 的版面门禁只在默认 zh-CN 下量，英文更长造成的溢出也看不到。
- 为什么是问题：抽取是批量机械改动，出错形式是静默的（把 en-US 放进 zh-CN 键、少一个 `{{name}}`），而 `gate` 恰好只在键层面验。e2e 里 30/37 个文件断言中文是浏览器里看到的文字，本来就不用改成键（DOM 里没有键），把它们一起“改成键或结构”不可能也无必要。
