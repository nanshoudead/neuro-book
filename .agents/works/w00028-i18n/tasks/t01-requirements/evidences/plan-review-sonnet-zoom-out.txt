# w00028 t01 计划：拉远看审查报告

审查对象：`.agents/works/w00028-i18n/tasks/t01-requirements/plan.md`（107 行）。依据：ADR 0034、两个 Work README、Task README、`independent-design.txt`、`packages/neuro-book/src/shared/localized-text.ts`、`nb-runtime/src/plugin-manifest/schema.ts`、ADR 0030、0023。

总评：问题是真问题，方向（按命名空间分的 JSON 目录加 i18next）有 ADR 0034 背书，没有发现根因上的错。主要问题有三类。一是计划悄悄偏离了开发者已确认的“方向”。二是同一份格式要有两套实现，而第二套的使用者没有证据。三是几个会进公开接口的数据形状（跨插件文字、失败值、清单字段）没有把取舍讲透。

### 1. 计划改动了 Work README 里开发者已确认的两条方向，没有明说
- Work README“方向”写：“声明按约定取键，偏离约定时才写键”“清单的名称与说明在构建时从目录摘出”（`w00028-i18n/README.md` 方向一节第 4 条）。独立设计也是约定键（`independent-design.txt` 1.3）。
- 计划第 2 节改成“一律显式 `{key, params}`”，末尾风险栏只用一句“不做自动推导，避免隐式规则”带过。第 1 节改成“源语言字符串留在清单，其它语言写在目录的 `manifest.displayName`”，不再是构建时摘出。
- 影响：这两处都是改变作者体验和数据来源的决定。显式键让声明里每个标题多一层对象，独立设计自己列的最大风险正是“键与调用点分离让作者感觉比现状更麻烦”（`independent-design.txt` 结论 6b）。清单字符串加目录两处各存一份源语言名称，容易不一致，计划没说谁校验。
- 建议：提案“待定项”里把这两处列为“相对 2026-10-27 方向的偏离”，写清理由，交开发者再确认；至少补一条“清单源语言字符串与源语言目录 `manifest.*` 不一致时以谁为准”。

### 2. 同一份消息格式要有两套实现，第二套的使用者没有证据（YAGNI 候选）
- 计划第 5 节：宿主用 i18next，nb-ui 另写“几十行、只支持原生格式子集的最小实现”，宿主没提供 `t` 时共享包用它。
- 谁会用到这个回退？第 5 节自己说 nb-story 查看器“不注入，照旧单语中文”；NeuroBook 内的使用者都有宿主 `t`。剩下只有“外部宿主用已发布的 npm 包”这一种假想使用者。我在仓库里没找到外部宿主的记录：`nb-form`、`nb-agent-ui`、`nb-markdown` 版本都是 0.1.0，`nb-form/README.md` 只有 `locale="zh-CN"` 的示例用法。ADR 0034 也只写“预计会很小，不承诺行数”。
- 代价：两个实现要对齐插值转义、复数选择、缺键行为，需要一套一致性测试，并且 i18next 默认会转义插值（`escapeValue`），最小实现要和它同步行为，否则同一目录在两个宿主里显示不同。
- 更简单的做法（按“已有的约定”排序）：(a) 共享包只收 `t`，没给时回退到源语言字符串，只做 `{{name}}` 代入，不做复数，一二十行且不必声称“兼容 i18next”；(b) 干脆把 `t` 做成必填端口，Lab 和测试提供一个，不提供回退。两种都比“两套引擎等价”轻。
- 建议：提案要求 t02 回答“最小实现覆盖多少子集、谁在用”，没有真实使用者就降级为 (a)。

### 3. 跨插件传递的 `{key, params}` 的数据形状没讲清，是以后改不动的接口
- 第 2 节：“跨插件传递的运行期文字……用 `{key, params}`，由宿主按贡献者补命名空间，接收方不需要知道是谁的”。
- 问题：宿主在哪一步补命名空间，补完后的值是什么形状？状态栏条目、公开状态原因、快速选择项会跨进程、进快照、进测试。如果存的是不带命名空间的 `{key}`，接收方就无法翻译，除非每个接收点都带上贡献者 id；如果补成 `{ns, key, params}`，那就是第三种形状，第 6 节失败值又是 `{code, params}`，加上字面字符串，同一个“要显示的文字”共有四种形态。
- 插件 SDK 还没发布（ADR 0034 后果一节），现在是定形状成本最低的时候，之后就是锁死的公开接口。
- 建议：提案用一个类型图列出全部形态（字面、键、已限定的键、失败值）与它们之间的转换点；最好合并成一个“已限定文字”类型，失败值只是它的一个来源。

### 4. 层次归属没有对照 ADR 0030，清单字段和失败值会落到不确定的地方
- 计划把 `l10n: {source, locales}` 放进清单（`nb-runtime/src/plugin-manifest/schema.ts` 目前只有 `displayName?`、`description?`），把失败值 schema 和参数整理函数放进 nb-runtime。ADR 0030 决策 1、2 规定内核与应用无关、第三方插件通用管理在 `src/plugin-platform/`、由架构测试守住。
- 计划没有说：语言列表、源语言、zh-CN 这个默认值和“内置插件必须 zh-CN 加 en-US”属于内核还是应用平台档案？服务端发目录的 HTTP 接口属于哪层？如果源语言默认值 zh-CN 写进 nb-runtime，就违反“内核不出现应用专有常量”。
- 建议：提案加一小段“归属”表：清单 `l10n` 字段的通用部分（内核）、默认语言与内置要求（平台档案）、目录登记与 HTTP（`plugin-platform` 的 `shared/backend/web`）、失败值（nb-runtime 是否合适，因为它前后端共用且只依赖 TypeBox，看起来合适，但要写明）。

### 5. 计划把三件不同性质的事塞进一份提案，且“详情组件”与 i18n 无关
- 第 1 到 5 节是目录机制；第 6 节的失败值与码表属于错误模型；“详情”载体是 nb-ui 新组件加 `Notification.detail`、状态栏折叠形态。后者是纯 UI 决策，与语言无关（开发诊断是英文，详情里放的恰是不翻译的原文）。
- 并入的理由在 Work README 第 7 条：必须先于各错误域设计，否则文字迁两次。这个理由对“码、键、参数”成立，对“详情组件长什么样”不成立。把组件设计放进 i18n 提案，会让提案接受被 UI 评审拖住，也让 `design-review` 的流程（需要出稿给开发者看）混进来。
- 建议：提案里只写“详情载体需要什么能力”（可展开、可复制、带详情不自动消失）作为对 nb-ui 的需求，组件设计另起 Task 并走 UI 流程。

### 6. 编译期键检查在声明数据上并不成立，计划却写成已解决
- 第 7 节“编译期：键与参数名（`keyof typeof`）”，第 2 节声明里的类型却是 `{key: string; params?}`。`keyof typeof` 只能检查调用点（`t("...")`）和 `satisfies Record<Code, string>` 之类的位置；声明里 `key: string` 以后要出自清单 JSON（独立设计的前提：声明必须能不执行代码读出来），不可能有编译期检查。
- 也就是说，对声明文字（占改动的大头）真正起作用的是第 7 节的目录检查脚本，不是类型。计划没区分这两条线，会让读者以为键错写会在编译期被抓到。
- 建议：提案写明“声明里的键靠检查脚本（以及运行期缺键处理）保证，类型只管代码里的 `t` 调用”，并把脚本如何找到声明里的键（扫描 `defineXxx` 调用？读构建出的清单？）列为待定。

### 7. 方案依赖尚未验证的前提，却已把接法写进“关键设计”
- 第 4 节“`useText()` 含当前语言的 `shallowRef` 与 `t`”、第 3 节“切换语言是同步的”，依赖 t02 要验证的“渲染期 `t()` 能否随语言切换更新”（`t02/README.md` 目标第二条）。计划第 1 个切片是“t02 回来后修订”，说明已意识到。
- 但第 6 节的“码表穷举靠 `satisfies Record<Code, string>`”这类写法和第 3 节“一次取齐所有语言”的体积数字（34 KB）都没有证据路径。风险是提案写成定稿口吻，开发者接受后 t02 再推翻某一条。
- 建议：提案对依赖 t02 的条目显式标“待 t02 验证”，不要等回来再改措辞；34 KB 的出处（Task README 写“约 34 KB 以内”）要说明测的是内置文字还是估算。

### 8. 其它小点
- 一次取齐所有语言的触发条件“超过 5 种语言”是拍脑袋的阈值；更合适的是写成指标（压缩后总目录体积、首屏时间），不是语言个数。
- 第 6 节“字符串截到 200 字、至多 8 个参数、键只许字母数字”写进 nb-runtime schema，会成为线协议的一部分；w00031 第 7 条把它定为共用件是对的，但上限数值没有出处，提案里标成可调的默认值并说明改动要升线协议版本，比写成合同更稳。
- 清单 `l10n.locales` 列表与 `locales/` 目录里的文件是两个事实来源；若只是为了登记时校验，目录扫描就够，列表可以去掉。理由没写。

### 没有发现
- 要解决的问题：真问题。`localized-text.ts` 把“恰好两种语言”写进类型和 TypeBox 校验（`additionalProperties: false`），四个包各抄一套 `say/formatText`；ADR 0034 背景里的英文界面显示中文原因也是实际行为。
- 底层选择：ADR 0034 决策 3 是 2026-10-27 开发者刚定的；ADR 0023 的 vue-i18n 从未落地（`package.json` 里没有），不存在要为旧选择让步的情形。
- 回头路：插件 SDK 与新包都未发布，目录格式用 i18next 原生 JSON，翻译平台和以后换 ICU 都可逆；错误码已是 kebab-case（如 `unavailable`、`invalid-args`、`unknown-outcome`），`<命名空间>:errors.<code>` 没有字符冲突。
