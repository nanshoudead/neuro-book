### 1. `Text` 的三种字面形态没有判别字段：无参数的 `TextRef` 会被 nb-form 当成“按语言给出的文字”，界面上显示命名空间名

- **严重程度**：重要；**类别**：接口与合同（上一轮前端第 7 条第 1 点，未处理）
- **位置**：提案第 3 节（“只有一种类型：`Text = string | TextRef`”“`FormText` 保留为第三种字面形态”）；`packages/nb-form/src/text.ts:10-22`（`FormTextSchema = Union([String, Record(String, String, {minProperties: 1})])`、`resolveText`）；`packages/nb-agent-ui/src/types.ts:23`（`ViewText = string | LocalizedText | {key; params?}`）。
- **现象**：提案把 `TextRef` 定为 `{ns, key, params?}`，同时让 nb-form 的开放语言映射 `FormText` 与它并存。不带 `params` 的 `TextRef`（最常见的情形，例如 `ctx.text("x")`）的所有值都是字符串，满足 `Record<string,string>`。实测（`lab/formtext.ts`，直接 import 源文件）：
  - `isFormText({ns:"nb-form", key:"required"})` 为 `true`；
  - `resolveText({ns:"nb-form", key:"required"}, "zh-CN")` 返回 `"nb-form"`（`text[locale]` 与 `text["en-US"]` 都取不到，落到 `Object.values(text)[0]`，即命名空间字符串）；
  - 带 `params: {n: 1}` 的才不会命中（`isFormText` 为 `false`）。
  即同一个 `Text` 槽收到无参数 `TextRef` 时，是否被当作语言映射取决于它有没有 `params`，没有报错。nb-form 的 `isFormText` 还用来检查模型生成的 `x-form` 提示（`check.ts`），同样会放过 `TextRef` 形状。
- **为什么是问题**：提案第 3 节说“跨插件传递的运行期文字都传 `Text`”，设置窗口、表单这类把宿主文字送进 nb-form 槽的路径（设置项标题就是 `LocalizedText` 经 nb-form 画出来）会第一个踩到。上一轮报告第 7 条建议 `TextRef` 带判别字段，提案采用了“带命名空间”但没有加判别字段，也没写这条冲突。
- **如何核实**：`cd /tmp/w00028-review/t01-impl/lab && bun formtext.ts`；对读 `packages/nb-form/src/text.ts`。
- **建议改法**：在提案里选一种并写明：(a) `TextRef` 带判别字段（例如 `{$text: "ref", ns, key, params?}`），`FormText` 与 `LocalizedText` 判别都先排除它；(b) `FormText` 的开放语言映射在 nb-form 内部不接受 `ns`/`key` 两个键名（schema 里 `propertyNames` 限定为语言标签形状）。无论哪种，加一行“`Text`、`FormText`、`ViewText`、`LocalizedText` 并存期与终态”的类型对照表（见下一条）。

### 2. 迁移期类型并存没有设计，而提案的回滚承诺“按插件分片、每片可单独回退”恰好要求并存

- **严重程度**：重要；**类别**：迁移 / 回滚（上一轮前端第 7 条第 3 点，未处理）
- **位置**：提案“影响”一节（“迁移”“回滚：实施按插件分片，每片可以单独回退”）；`packages/neuro-book/src/shared/settings.ts:237,238,295,296`（登记时 `Value.Check(LocalizedTextSchema, …)`）；`plugins/commands/shared/contracts.ts:65-66`、`menus.ts:43`、`workbench/shared/{views,items,home}.ts`、`editor/shared/contracts.ts:94,127`、`settings/shared/sections.ts:52-69`、`state/shared/plugin.ts:46`、`settings/shared/contracts.ts:138`（`DisplayText`）等十处登记校验与类型写死 `LocalizedText`/`DisplayText`。
- **现象**：提案只写“约 1180 处内联文字用脚本按插件抽进目录”。但同一个贡献点（例如 `workbench.views`、`commands`）的登记校验是共享的：某个插件改成约定键（声明里不写 `title`）、另一个插件还在写 `{zh-CN, en-US}` 时，校验必须同时接受两种；运行期的 `DisplayText` 入参（`quickPick` 项、通知、状态栏、`status: Ref<LocalizedText|string|null>`）也一样。提案没有说：并存期有多长、校验放宽到什么形态、`LocalizedText` 何时删除、`nbook.commands/remote` 这种 schema 写死的合同怎么过渡（见第 3 条）。同一个 nb-agent-ui 的 `ViewText` 已有 `{key, params}`（无 `ns`），提案说它“就是命名空间为 `nb-agent-ui` 的 `TextRef`”，但 `TextRef.ns` 是必填，两者形状不同，转换点没写。
- **为什么是问题**：“每片可以单独回退”和“一次切完”矛盾；没有并存期，t03 要在一个提交里改十个校验、四个包的类型、约 190 个文件，回滚粒度就不是按插件。
- **如何核实**：`grep -rn "LocalizedTextSchema" packages/neuro-book/src --include='*.ts' | grep -v test`（10 个文件）；对读提案“影响”。
- **建议改法**：提案里加一张小表：每个现有类型（`LocalizedText`、`DisplayText`、SDK 的 `Text`、`ViewText`、`FormText`、`MarkdownText`）→ 并存期 → 终态；写明并存期的判别规则（接第 1 条）、`LocalizedText` 的删除条件（例如最后一个内置插件迁完，由 `governance:check` 报告剩余数为 0），以及哪些 schema 是线协议（第 3 条）要升版本。若不想设并存期，就把“按插件分片回退”改成“整体回退”。

### 3. “线协议：不变”与代码不符：`nbook.commands/remote` 的 `list` 输出里 `title` 是写死的 `LocalizedTextSchema`

- **严重程度**：重要；**类别**：与代码、Spec 不符的事实陈述
- **位置**：提案“影响”一节“线协议：不变。失败文案在浏览器端取，跨进程照旧只传码与各域合同里的参数”；`packages/neuro-book/src/plugins/commands/shared/contracts.ts:142-157,169-181`（`RemoteCommandSchema.title: LocalizedTextSchema`，合同 `nbook.commands/remote` `version: 1`、`additionalProperties: false`）；`commands/shared/plugin.ts:119-141`（`list` 把 `command.title` 原样放进返回值）；`docs/specs/workbench/commands.md:70-72`。
- **现象**：浏览器窗口把命令表经 `nbook.commands/remote` 交给服务端（给 Agent 列命令用），其中 `title` 是 `{zh-CN, en-US}` 两份。提案把命令标题改成“没写就按约定取键”，`command.title` 不再是 `LocalizedText`。要继续过这条线，只有三种办法：(a) 浏览器端在 `list` 里按某种语言解析成字符串；(b) 把 `TextRef` 送过去，但服务端没有目录（提案第 1、4 节：目录只在浏览器登记）解不开；(c) 继续送中英两份，等于浏览器端为每条命令各解析两种语言。三种都要改 `RemoteCommandSchema.title`，该合同 `additionalProperties: false`、带版本号，所以是线协议变更，要升 `version`（并写进 Spec 的“预期改动”：`workbench/commands.md` 现在只提到声明字段，没提这条合同）。
- **为什么是问题**：提案用“线协议不变”作为影响面小的论据，且把 `commands.md` 的改动描述成“声明字段”；实现时会撞上这条合同，带出 Agent 看到的命令标题该用哪种语言的问题（给模型的文字不跟界面语言，见 ADR 0034 决策 4，倾向 (c) 或固定源语言），这是一个需要在提案里定的取舍。
- **如何核实**：`grep -n "LocalizedTextSchema" packages/neuro-book/src/plugins/commands/shared/contracts.ts`；读 `plugin.ts:119-141`。
- **建议改法**：把“线协议：不变”改为“已知一处变更：`nbook.commands/remote.list.title`”，写明处理方式（建议：浏览器端送源语言解析后的字符串，因为接收方是 Agent，界面语言与它无关）和版本升级；再对 `rg "LocalizedTextSchema" packages/*/src` 命中的每个跨进程 schema 复核一遍（我只找到这一处出现在远程合同里，其余都是登记校验）。

### 4. “按约定取键”的约定表对不上现有声明：覆盖面、“本地名”、可选字段的缺省、选项的形状

- **严重程度**：重要；**类别**：方案与代码不符 / 遗漏
- **位置**：提案第 2 节；`docs/specs/workbench/menus.md:39,74`（`label` 可选，缺省用命令的标题）；`packages/neuro-book/src/plugins/{commands,workbench,editor,settings,state}/shared/*.ts`（见下表）；`nb-runtime/src/plugins/host.ts:829-839`（`idPrefix: "plugin"` 的保留发布者例外）；`packages/neuro-book/src/plugins/workbench/web/plugin.ts:97-100`（工作台登记命令）。
- **现象**：四处各自核实。
  1. **覆盖面**。约定表只列了命令、视图、设置项、菜单项、清单五类。现有声明里还有要显示的字段：设置分区与页面的 `title`、`description`、`groups[].title`、`keywords[]`（`settings/shared/sections.ts:52-69`，`keywords` 是 `LocalizedText[]`，没有可寻址的名字）；设置项的 `ui.unit`（`shared/settings.ts:62`）与选项的 `description`（`SettingChoiceDeclaration`）；活动栏条目、状态栏条目、标题栏条目的 `title`（`workbench/shared/items.ts:28,42`）；视图标题动作的 `title`（`views.ts:45`）；编辑器与编辑器页面的 `title`（`editor/shared/contracts.ts:94,127`）；首页的 `title`（`home.ts:22`）；公开状态的 `reason`（`state/shared/plugin.ts:46`）；标题栏菜单的四个固定组名（`workbench/shared/menus.ts:15-20`）。这些在提案里既没有约定键，也没有说“必须写 `{key}`”，Spec 预期改动里 `workbench/editor.md` 和设置的两份 Spec 只写“声明字段改为约定键、`{key}` 或字面字符串”。
  2. **“去掉插件前缀的本地名”不总存在**。内核允许保留发布者（`nbook`）的内置插件用“发布者加点”作前缀（`host.ts:829-839`），实际如此：插件 `nbook.workbench` 登记的命令 id 是 `nbook.view.set-part-hidden`、`nbook.view.set-panel-position` 等六条 `nbook.view.*`、`nbook.app.reload`、`nbook.help.documentation`、`nbook.quick-open.open-commands`、`nbook.settings.switch-theme`；插件 `nbook.editor` 登记 `nbook.edit.undo`、`nbook.edit.redo`；`nbook.projects` 登记 `nbook.help.welcome`。这些 id 不以 `nbook.workbench.` 开头，“去掉插件前缀”得不到本地名。要么按发布者去前缀（那么 `nbook.editor.save` 的键是 `commands.editor.save.title`，第三方 `acme.foo.x` 的键却是 `commands.foo.x.title`，规则不统一），要么内置命令必须写 `{key}`（那么约 25 条内置命令不能享受约定）。提案没有选。
  3. **可选字段的缺省**。`label`、`description`、`category`、`placeholder` 现在都是可选，菜单项 `label` 缺省取命令标题（`menus.md:74`）。“没写就按约定取键”之后，宿主分不清“作者没想写”和“漏了键”：缺键按第 4 节“落到键名时记诊断、测试里抛错”，那么没有说明的设置项也必须有一个空的 `description` 键？还是按键存在与否决定显示？菜单项没有 `label` 键时要不要退回命令标题？提案都没说，而这直接决定了目录里有多少“空值占位”。
  4. **选项的形状**。`settings.<设置名>.choices.<值>` 只给出一个字符串，现有选项是 `{value, title, description?}`；`value` 是 `string | number | boolean`（`SettingLiteral`），数字、布尔、含点的字符串（如 `gpt-4.1`）做键段都有歧义（`keySeparator` 是点，原型第 6 点已证实 `:` 会被改写，点会被拆成嵌套）。
- **为什么是问题**：开发者已确认“按约定取键”这个方向（Work README），提案把它列在核心方案里，但约定表只覆盖了一半声明，且对内置命令这一最大宗（约 190 个文件的迁移里占大头）无法套用。作者按提案写代码时会立刻遇到这四处。
- **如何核实**：`grep -rn "LocalizedTextSchema" packages/neuro-book/src --include='*.ts' | grep -v test` 对照第 2 节五类；`grep -rnE '"nbook\.(view|app|help|quick-open|edit)\.' packages/neuro-book/src/plugins --include='*.ts' | grep -v test` 看命令 id；对读 `host.ts:829-839`。
- **建议改法**：在提案里把约定写成“每个贡献点一行”的完整表（包括分区、页面、分组、`keywords`、各类条目与 `reason`），并补三条规则：内置贡献的本地名取法（建议：本地名 = 贡献 id 去掉插件 id 前缀，不满足时必须写 `{key}`，登记时报错而不是静默）；可选字段“键存在才显示”，必填字段缺键才是错误（目录检查按贡献点的必填集合核对）；选项键写成 `choices.<值>.title`/`.description`，值要先过 `[a-z0-9-]` 之类的字符校验，不合格的值必须写 `{key}`。

- **第 4 条更正（只追加）**：第 2 点里的数字按 `workbench/web/plugin.ts:96-103` 重数：工作台插件 `nbook.workbench` 登记的命令共 12 条，id 无一以 `nbook.workbench.` 开头：`nbook.view.*` 七条（面板位置、对齐、隐藏、收起、最大化，区域显隐，移动视图）、`nbook.app.reload`、`nbook.help.documentation`、`nbook.quick-open.open-commands`、`nbook.settings.switch-theme` 与 `switch-appearance`。“六条”改为“七条”；正文里“约 25 条”“约 190 个文件里占大头”没有数据支持，以本更正的 12 条为准（编辑器的 `nbook.edit.undo/redo`、项目插件的 `nbook.help.welcome` 另计）。

### 5. “加一种界面语言只加目录文件”在设置、类型和共享包三处都做不到，提案没有说明“语言集合”怎样成为单一来源

- **严重程度**：重要；**类别**：目标与方案不一致 / 遗漏
- **位置**：提案“目标”第 2 条、第 5 节“界面语言集合：宿主内置目录有的语言……`nbook.settings/locale` 的选项由它生成”；`packages/neuro-book/src/plugins/settings/shared/contracts.ts:54-69`（`localeSetting` 的 `schema` 是 `Union([Literal("zh-CN"), Literal("en-US")])`，`choices` 手写两项）；`packages/neuro-book/src/shared/localized-text.ts:19`（`DisplayLocale = keyof LocalizedText`）；`packages/nb-agent-ui/src/ports.ts:10`（`PromptLocale = "zh-CN" | "en-US"`）、`packages/nb-markdown/src/locale.ts:6`（`MarkdownLocale`）。
- **现象**：
  1. `localeSetting` 声明在 `plugins/settings/shared/contracts.ts`，由服务端、项目端、浏览器三个位置共用，服务端据其 `schema` 校验用户设置文件。宿主目录随前端构建进浏览器包（提案第 1 节），服务端取不到；“选项由宿主目录生成”没有说生成物在哪、服务端校验用什么。如果另写一份语言清单，就违反“只加目录文件”；如果清单从 `locales/` 目录构建期生成，需要一个服务端和浏览器都能 import 的生成物，提案未提。
  2. `DisplayLocale` 在 `neuro-book/src` 里有 113 个非测试文件引用，类型是 `keyof LocalizedText`，随 `LocalizedText` 删除而失去定义；`PromptLocale`、`MarkdownLocale`、`AgentLocale` 在共享包里是各自写死的两元联合。加第三种语言要改这些类型，不是“只加目录文件”。
  3. 设置项里的语言名选项（`简体中文`/`English`）现在有意写成各自的语言（`contracts.ts:63-67` 的注释），生成时不能走 `choices.<值>` 约定翻译，提案也没提要保留这个规则。
- **为什么是问题**：目标 2 是方案的主要卖点（“加语言”不改代码），提案接受后第一个加语言的人会撞到这三处。
- **如何核实**：对读 `plugins/settings/shared/contracts.ts:54-69`；`grep -rl "DisplayLocale" packages/neuro-book/src | grep -v test | wc -l` 得 113；`grep -n "Locale = " packages/nb-agent-ui/src/ports.ts packages/nb-markdown/src/locale.ts`。
- **建议改法**：提案里写明语言集合的单一来源（例如构建期从宿主 `locales/` 生成 `SUPPORTED_LOCALES` 常量，放在服务端与浏览器共用的模块），`DisplayLocale` 改为由它派生的类型或放宽为规范化的语言标签字符串；共享包的 `*Locale` 类型改为 `string`（运行期按注入或包内目录解析）；语言名的选项注明“用各自语言写，不走翻译”。若认为“加语言”本来就要改几处类型，就把目标 2 改成“加语言只需加目录和一处语言清单”，不要写“只加目录文件”。

### 6. 翻译端口的形状仍未定：`t` 的入参、取“全部语言写法”的办法、`Text` 类型的位置、插件组件怎样拿到绑定了命名空间的 `t`

- **严重程度**：重要；**类别**：接口与合同（上一轮前端第 4 条，只处理了一半）
- **位置**：提案第 3 节（“`ctx.text(key, params)` 构造，命名空间由插件身份绑定，不能伪造”）、第 4 节（“Vue 侧经 provide/inject 交出 `useText()`，内含当前语言与 `t`”）、第 6 节（“nb-ui 提供翻译端口，包括注入键、`useText()` 和一份最小实现”）；`packages/nb-runtime/src/plugins/contracts.ts:71-109`（`ActivationContext` 无 `text`）；`packages/neuro-book/src/sdk/sdk.test.ts:26`、`sdk/surface.test.ts:66-89`（SDK 导出名单与文件名单是逐项写死的断言）；`docs/specs/workbench/quick-open.md:48`；`packages/neuro-book/src/plugins/settings/web/settings-window.ts:382-392`。
- **现象**：上一轮已处理的部分：命名空间由 `TextRef` 自带（`{ns, key, params?}`）而不是靠 `ns:key` 字符串，缺键/数量参数/回退链在第 4 节写了。仍缺：
  1. **`t` 的入参**。第 4 节的 `t` 是收 `Text`（遇 `TextRef` 翻译、遇字符串原样返回），还是收 `(key, params)` 配绑定的命名空间？第 6 节的最小实现原型是 `t(key, params)`（`prototype-report.txt` 第 7 项），宿主引擎外面包的“翻译函数”是哪种，两者怎样互换，没写。
  2. **“全部语言的写法”**。命令面板要求候选在各语言下的写法都参与匹配（`quick-open.md:48`），设置搜索也比对两种语言（`settings-window.ts:382-392`，现在是 `Object.values(text)`）。`Text` 变成 `string | TextRef` 之后 `Object.values` 无从下手；提案说“一次取齐所有语言，设置搜索照旧比对多种语言”，但端口里没有对应方法（例如 `forms(text): string[]` 或 `t(text, {lng})`）。
  3. **`ctx.text` 的出处**。`ctx` 是内核 `ActivationContext`，它与应用无关（ADR 0030 决策 1），没有 `text`；提案没说由 SDK 的 `defineEntry` 包一层加上，还是内核加一个泛化的成员。服务端与项目端入口同样需要构造 `TextRef`（提案“线协议”一段说跨进程只传码，但状态/通知类文字可能由服务端插件产生），也没说它们拿不拿 `ctx.text`。
  4. **“不能伪造”不成立**。`TextRef` 是普通对象，任何插件都可以直接写 `{ns: "nbook.editor", key: "x"}`；只有声明里的 `{key}` 由宿主补命名空间。提案要么在接收边界（通知、状态栏、快速选择）校验 `ns` 等于调用方，要么把措辞改成“`ctx.text` 绑定自己的命名空间；跨命名空间引用不被阻止，只是不被鼓励”。（按“过度防御不改”的习惯，我倾向后者，只改措辞。）
  5. **类型与导出位置**。`Text`/`TextRef` 定义在哪个包？SDK 现有一个同名 `Text = string | LocalizedText`（`sdk/plugin.ts:30`）；nb-ui 的 `NotificationInput.message` 要接收它，所以应当在 nb-ui 或更底层；插件 Vue 组件里的 `useText()` 从 SDK 的哪个子路径导出（SDK 名单是写死的断言，新增要改 `sdk.test.ts`、`surface.test.ts`、`pack.test.ts`）；第三方插件的 Vue 组件拿到的 `t` 是否已绑定自己的命名空间（`useText()` 返回的是宿主级的 `t`，还是 `useText(ns)`）。
- **为什么是问题**：提案把端口放在 nb-ui、说明“共享包不依赖 i18n 库”，端口一旦发布就是公开接口（nb-ui 0.2.0）。这些问题答案不同，t03 的任务划分就不同。
- **如何核实**：读 `nb-runtime/src/plugins/contracts.ts:71-109`；`grep -n "Object.values(text)" packages/neuro-book/src/plugins/settings/web/settings-window.ts`；读 `quick-open.md:48`。
- **建议改法**：在提案第 3、6 节各补一段 TypeScript 签名草案（五到十行即可）：`Text`/`TextRef` 所在包、`t(text: Text): string`、`forms(text: Text): readonly string[]`、`useText()`、`ctx.text` 由哪层加；并把第 4 点的措辞改掉。

### 7. 共享包目录谁登记进宿主引擎没有写；`locale` 属性在有注入时被忽略，与四个包已发布的合同方向相反

### 10. 第 8 节“检查”的覆盖：显式写的 `{key}` 没人查、参数名拼错不会被发现、“`keyof typeof`”不是原型实际用的写法

- **严重程度**：建议；**类别**：自相矛盾 / 遗漏（上一轮前端第 8 条，处理了一半）
- **位置**：提案第 8 节；`prototype-report.txt` 第 4 项（A 方案：递归路径类型，折叠 `_one/_other`，几十行）。
- **现象**：上一轮的主要意见（参数名推导不出来）提案已承认并分成三层，是对的。仍有三处：
  1. **显式 `{key: "..."}` 无检查**。第 8 节的测试只枚举“声明推导出的约定键”；作者“偏离约定”写的 `{key: "..."}` 恰恰是最容易拼错的，它的类型是 `string`（第 3 节 `TextRef.key`），编译期不查，装载测试按“约定键”枚举也不会碰它。结果是偏离约定的路径比约定路径少一层保护。
  2. **参数名拼错**。目录检查只比各语言占位符集合一致，测试只覆盖被执行到的调用。`ctx.text("greeting", {nam: x})` 在生产里显示 `你好，{{name}}`（原型第 3 项：缺参数时原样留占位符），没有任何一层拦它。提案承认参数名推导不出来，但没有给出“谁查调用点的参数名”的答案。原型报告第 4 项给了两条路：目录改成 `as const` 的 TS 对象让类型抽占位符，或检查脚本扫描源码里字面键的调用；提案没选也没说放弃。
  3. **措辞**。“`resolveJsonModule` 加 `keyof typeof`”不足以得到点号路径键：`keyof typeof catalog` 只有顶层键，复数键还是 `files_one`/`files_other`；原型实际用的是 `keys.ts` 里递归路径类型并折叠复数后缀（约 40 行）。另外 `packages/neuro-book/tsconfig.json` 没有显式 `resolveJsonModule`，我用 tsc 5.9.3 在 `moduleResolution: "bundler"` 下试了 JSON 导入是可以的（`lab/tj/`），所以不需要改配置，但提案这句话会让实现者以为要改。
- **为什么是问题**：第 8 节是“写错键、漏翻译、占位符不一致在检查或测试里就能发现”这个目标的承载，三处各留一个洞，目标写得比实际保证强。
- **如何核实**：对读提案第 8 节与 `prototype-report.txt` 第 3、4 项；`cd /tmp/w00028-review/t01-impl/lab/tj && /home/notnotype/CodeRepository/neuro-book/node_modules/.bin/tsc -p tsconfig.json`（退出码 0）。
- **建议改法**：目标 4 的措辞限定为“键和跨语言的占位符”，参数名写成“由测试覆盖，未覆盖的路径不保证”；装载测试同时枚举显式 `{key}`；第 8 节“编译期”一条改为“用原型的 `keys.ts` 类型（递归路径、折叠复数后缀）”。如果开发者想要参数名也保证，把“目录改成 TS 对象”列为待定项。

### 12. `FormText` 的回退与回退链不一致：现有实现回退到 `en-US` 再取第一种，提案写“取不到用源语言”

- **严重程度**：建议；**类别**：行为变化未声明
- **位置**：提案第 3 节末（“`FormText` 保留为第三种字面形态，渲染时按当前语言取，取不到用源语言”）；`packages/nb-form/src/text.ts:14-20`（`FALLBACK_LOCALE = "en-US"`；`resolveText` 依次取 `text[locale]`、`text["en-US"]`、`Object.values(text)[0]`）。
- **现象**：`FormText` 是开放语言映射，它自己没有“源语言”这个概念（`nbdev` 面板与模型生成的描述都只给英文或单语字符串）。现行回退是 `locale` → `en-US` → 第一种。提案说“用源语言”，而宿主的源语言是 `zh-CN`；照字面改，一个只带 `en-US` 与 `ja` 的映射在 `zh-CN` 界面下的取舍会变（取 `zh-CN`？没有；再取 `en-US`？还是按回退链的第三环）。提案没说是保持现行规则还是并入回退链。
- **为什么是问题**：小，但这是已发布包（nb-form 0.1.0）的行为，且 `isFormText`/`resolveText` 是它公开的函数。
- **如何核实**：读 `nb-form/src/text.ts:14-20`。
- **建议改法**：第 3 节末改成“`FormText` 保持现行的回退（当前语言、`en-US`、第一种）”，或明确改成回退链并说明对已发布行为的影响。

- **第 7 条补充（只追加）**：第 6 节说宿主没有注入时 `locale` 属性“决定用哪份默认目录”，但 nb-ui 的组件没有 `locale` 属性（`grep -rn "locale" packages/nb-ui/src` 无命中）。没有宿主的使用者（nb-story 查看器、dev-panel、直接用 npm 包的人）给 nb-form 传 `locale="en-US"` 时，嵌在表单里的 nb-ui 控件（`NumberInput`、`Input`、`SearchSelect` 的读屏名称）读不到这个语言，会落到 nb-ui 自己的默认（中文）。现在 `ui/forms.md:158` 靠表单把这些名称按语言覆盖；提案要么保留这层覆盖，要么规定“包的根组件在收到 `locale` 属性且没有注入时，为子树提供一个用该语言的端口”。提案没写这一点，nb-form 的验收（`ui/forms.md:158`）会因此退化。

- **第 11 条补充（只追加）**：影响面还漏了作者材料：`packages/neuro-book/plugin-sdk/` 下有 9 个文件含 `"en-US"`、`localize(`或 `formatText`（`examples/plugins/{counter,focus,snippets}`、`examples/external/declarative/package.json`、`README.md`、`pack.test.ts`、`build-plugin.test.ts`）。AGENTS.md 规定示例是教学材料、讲解随场景测试一起改；其中 `external/declarative/package.json` 是纯 JSON 声明的第三方插件示例，没有代码，正好是“约定键 + `locales/`”这套写法最需要的第一个样板，应当写进提案的“迁移”一行。

### 13. 共享包随源码发布，`src` 里导入 `locales/*.json` 会让部分消费者的类型检查失败，提案只处理了 `files`

- **严重程度**：建议；**类别**：遗漏（上一轮前端第 12 条，处理了一半）
- **位置**：提案第 6 节“每个共享包自带 `locales/`，加进包的 `files`”；`docs/adr/0029-workspace-packages-publish-source-to-npm.md:39`（“TypeScript 消费者用自己的 tsconfig 检查这些源码，严格度不同时可能报错；`skipLibCheck` 管不到 `.ts`”）。
- **现象**：`files` 补上之后包里确实有目录文件，但包的 `.ts` 源码要 `import … from "../locales/zh-CN.json"`，消费者的 tsconfig 在 `moduleResolution` 为 `node16` 或 `node10` 且没开 `resolveJsonModule` 时报 TS2732。实测（tsc 5.9.3，`lab/tj/tsconfig.node16.json`、`tsconfig.node10.json`）：这两种配置报 `TS2732: Cannot find module './c.json'`，`bundler`（本仓库）与 `nodenext` 不报。nb-form、nb-agent-ui、nb-markdown 已发布 0.1.0，nb-ui 0.2.0，这是它们第一次在源码里带 JSON。
- **为什么是问题**：ADR 0029 已把这类“严格度不同”列为已接受的代价，但新增的一类应当在提案里被看到，而不是发布后才发现。
- **如何核实**：`cd /tmp/w00028-review/t01-impl/lab/tj && /home/notnotype/CodeRepository/neuro-book/node_modules/.bin/tsc -p tsconfig.node16.json`。
- **建议改法**：二选一并写进提案：(a) 共享包的目录在源码里是 `.ts`（`export default {…} as const`），`locales/*.json` 由构建/脚本从它导出供翻译平台用——这也顺带解决第 10 条的参数名推导（`as const` 字面量能用模板字面量类型抽占位符）；(b) 保持 JSON，把 `resolveJsonModule` 的要求写进各包 README 与 ADR 0029 的代价一节。
