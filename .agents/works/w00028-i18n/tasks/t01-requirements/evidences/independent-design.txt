# NeuroBook 语言与国际化：独立设计稿（2026-10-27）

## 结论先行

1. **界面文字**：用 `i18next`（框架无关，按“命名空间”隔离）作为唯一翻译引擎，目录是**每个插件/包自带的纯 JSON 文件**（`locales/<语言标签>.json`），不再在代码里写 `{"zh-CN": …, "en-US": …}` 成对字面量。声明（命令标题、设置项标题）只存**键**，显示时才翻译，保留“切语言即时换字”。共享包（nb-ui、nb-form、nb-markdown、nb-agent-ui）**不依赖任何 i18n 库**：导出默认目录 JSON，并通过一个 `t` 端口（`(key, params) => string`）接收宿主的翻译函数。
2. **错误**：三层分离。稳定的 `code`（+结构化 `params`）是唯一跨进程、跨语言的东西；用户文字由前端按 `code` 查目录生成；开发者排查用的文字（`Error.message`、诊断 `message`）**不本地化**，以 `code` 为检索键，发布到 npm 的包用英文。服务端不产生任何面向用户的本地化文本。
3. **给 LLM 的文字**：界面语言、书的语言、Agent 回复语言是三条互相独立的轴。领域提示词（写作人设、文风规则、剧情问答）属于**随作品语言走的版本化资产**，中文小说用中文，不走界面目录；协议类文字（工具说明、工具参数名、工具失败结果、系统提醒）用**英文 + 稳定错误码**；再加一句显式的语言指令。这一条的外部证据很弱，必须在项目自己的评测上做 A/B 再动手（见第 3 节）。
4. **推翻**：ADR-0023 里的 `vue-i18n`（从未安装）、全仓库的 `{zh-CN, en-US}` 双语字面量、各包私有的 `say/formatText/localize`、`DISPLAY_LOCALE` 写死、远程失败里夹中文 `detail` 的写法。
5. **迁移量**：约 108 个非测试文件、1178 处 `"en-US"`、174 处 `LocalizedText` 引用，其中 94 个文件在 `packages/neuro-book`。机械可转换，估 6 到 9 个工作日（含工具与检查），但不阻塞其它开发，可以按插件逐个切。
6. **最大风险**：(a) LLM 提示词语言的结论证据不足，若不做自家评测就整体改英文，可能伤到中文文风；(b) 把目录做成纯 JSON 后，“键与调用点分离”会让作者感觉比现在的就地双语更麻烦——这要靠类型化的键、`nb-i18n check` 与脚手架补偿，补偿没做好方案就输给现状。

## 1. 推荐方案：命名空间 JSON 目录 + i18next + 端口

### 1.1 为什么是 i18next，而不是 vue-i18n

- 本项目的核心形状是“**很多互不认识的所有者（插件、共享包）各自带目录，运行时增删**”。i18next 的 `addResourceBundle(lng, ns, …)` / `removeResourceBundle` 与命名空间正好对应这个形状；键默认带命名空间前缀 `nbook.editor:tabs.title`，天然避免撞名，热卸时一个 `removeResourceBundle` 就收干净。
- 它**不依赖 Vue**。nb-agent-ui 的核心、nb-form 的核心、nb-markdown 的语言层都是“纯 TS 核心 + Vue 层”，vue-i18n 只能服务 Vue 层，核心还得另想办法，等于两套。
- 翻译平台：i18next JSON 格式被 Crowdin、Weblate、Lokalise、Transifex 等普遍支持（这是我对生态的了解，未逐一核对 2026 年各平台页面，落地前要核一次）。
- vue-i18n 的现状（出处见下）：v11 已弃用 Legacy API 与 `v-t`，计划在 v12 删除；v9/v10 已进入维护模式，v12 仍是 alpha。也就是说选它要立刻按“Composition 模式”用，且要跟一轮破坏性升级。它和 Vue 绑定的程度也让“同一页面里宿主与插件共用一个实例”要靠 `inject`，而 `plugin-code-loading` 已规定共享 Vue，所以可行，但没有 i18next 的命名空间能力。
- 版本核对：本机依赖目录里 `i18next 26.5.11`、`intl-messageformat 12.1.4`、`@formatjs/intl 6.1.4`、`messageformat 4.1.0`。

出处：
- [vue-i18n v11 破坏性变更](https://vue-i18n.intlify.dev/guide/migration/breaking11)、[Legacy API 文档（标注弃用）](https://vue-i18n.intlify.dev/api/legacy)、[v12 alpha 变更记录](https://newreleases.io/project/npm/vue-i18n/release/12.0.0-alpha.4)

### 1.2 目录与键

```
packages/neuro-book/src/plugins/editor/
  locales/
    zh-CN.json     // 源语言（作者先写这一份）
    en-US.json
  web/...
```

- 文件内容是**嵌套或点分的扁平 JSON**，值用 i18next 原生插值 `{{name}}`；英文复数用 `_one/_other`（i18next 借 `Intl.PluralRules`），中文只需 `_other`。不引入 ICU 语法：本项目的复数、选择需求很少，ICU 带来的是译者培训成本。需要 ICU 时 i18next 有 `i18next-icu` 插件，是可逆的。
- 键的命名空间 = 插件 id（`nbook.editor`）或包名短名（`nb-form`）。第三方插件用自己的 id，**不能写别人的命名空间**（加载器只允许插件往自己的命名空间注册）。
- **源语言**定为 `zh-CN`（作者和主要用户都写中文）。内置插件要求 `zh-CN` 与 `en-US` 两份齐全；第三方插件只要求声明一份源语言，其余可缺，靠回退链兜底。
- **目录必须是 JSON 文件，不是 TS**：插件页要在不执行插件代码的情况下显示未激活插件的名字和说明，翻译平台也只吃数据文件。这是把“声明来自清单 JSON”的那半句约束落实。

### 1.3 声明里放键，不放文字

现在：`title: {"zh-CN": "预览标签页", "en-US": "Preview Tabs"}`。

改为约定式键，不手写：`defineSetting({plugin:"nbook.editor", name:"enablePreview", …})` 的标题自动取 `nbook.editor:settings.enablePreview.title` / `.description` / `.placeholder` / `.unit`；设置分区、命令标题同理（`commands.<id>.title`）。需要偏离约定时可以显式写 `titleKey`。
- 好处：声明变成纯数据，不带文字，TypeBox 里的 `LocalizedTextSchema` 整个删除；加语言不碰声明。
- 若声明里直接给字符串（第三方只写一种语言的最低门槛写法），视为“不翻译的字面文字”原样显示。这就是现在的 `DisplayText = string | LocalizedText` 里 `string` 那半。
- 清单的 `displayName/description` 同理：构建时 `plugin-sdk` 把 `locales/*.json` 里的 `manifest.displayName/description` 读成清单的 `i18n` 摘要，服务端不执行代码就能给插件页用。

### 1.4 端口：共享包不依赖 i18n 库

每个共享包导出：
```ts
export const messages: { "zh-CN": Catalog; "en-US": Catalog }   // 默认目录，可单独引用 ./locales/*.json
export type Translate = (key: string, params?: Record<string, string|number>) => string
```
组件通过 prop 或 `provide` 接收 `t: Translate`；宿主不传时用包自带的最小实现（替换 `{{x}}`，在 `messages[locale]` 里查），保证其它宿主零依赖可用。这样 nb-markdown/nb-form/nb-agent-ui 里三份 `say` 合并成一份“最小默认实现”，由 `nb-ui`（四个包都已依赖它）一处导出，或做一个只有几十行的 `@notnotype/nb-i18n-port` 类型包。

**坑**：nb-ui 里读屏名称（`closeLabel`、`aria-label`）目前由调用方传入，没有默认文案，保持这个做法；表单规格第 24 条写的“由表单按语言覆盖 nb-ui 控件里写死的读屏名称”说明 nb-ui 里仍有写死的文案，要查清（我只验证了 `closeLabel` 是 prop，其余“从代码推断”）。

### 1.5 回退、热更新与语言切换

- 回退链：用户语言（`zh-Hans-CN`）→ 同语种（`zh-CN`）→ 该插件的源语言 → `en-US` → 键本身。命中后两级时记一条诊断（每个键一次），开发/测试环境直接抛错。
- 当前语言是已有配置项 `nbook.settings/locale`，由 workbench 把它放进一个 `shallowRef`，`t()` 内部读它，所以所有显示点在渲染期调用 `t()` 就自动响应；命令面板这类“已打开的面板即时换字”无需额外机制。**禁止在模块顶层把 `t()` 的结果存成字符串**（这是现在就写在 `DisplayText` 注释里的同一条规则），由检查器与 lint 抓。
- 插件激活时注册命名空间，停止时 `removeResourceBundle`；这与现有“状态在激活时建立、停止时释放”的约定一致，只是多一类资源。
- 懒加载：目录跟随插件 web 入口以动态 `import("./locales/en-US.json")` 加载，当前语言先加载，回退语言后加载。
- 日期、数字、相对时间一律用 `Intl.*`，不进目录。
- 增加语言的步骤：加 `locales/xx.json` + 设置项的可选值加一项 + 翻译平台开新语言。不需要改任何声明或组件。

### 1.6 写错尽早发现

按“越早越好”排：
1. **编译期**：`t("nbook.editor:settings.enablePreview.title")` 的键类型由源语言 JSON 通过 `resolveJsonModule` + i18next 的 `CustomTypeOptions.resources` 生成，写错键 tsc 失败，补全可用。插值参数类型靠 i18next 自带的插值推断。
2. **构建/治理检查** `nb-i18n check`（挂进 `plugin-sdk` 的打包和 `governance:check`，约 200 行脚本，不是 i18n 引擎）：每个目录相对源语言的缺键、多键、占位符集合不一致、复数形式缺失；静态扫描未使用的键；设置/命令声明约定键是否齐全。内置插件缺 `en-US` 失败，第三方缺则警告。
3. **Lint**：对 `.vue` 模板与 TS 里的中文/英文字面量报错（`eslint-plugin-i18next` 的 no-literal-string，或自写一条只查含 CJK 的规则；注释、`class`、日志除外）。这个规则能防止“新写的界面又回到就地硬编码”。
4. **运行期**：开发与测试里缺键直接抛；生产里记诊断并显示回退。
5. **视觉**：伪语言 `en-XA`（加长并加重音符号，i18next 后处理器几行代码）进 Component Lab，抓溢出和漏翻译。

### 1.7 翻译平台

目录是纯 JSON，平台直连仓库同步即可。给译者的语境放在同目录的 `locales/context.json`（键 → 一句说明与截图名，可选），不进运行时包。机器预翻译只做初稿，术语表（“项目/书架/作品/剧情图谱”）进平台词库，避免“项目”被译成 project 又译成 book。

## 2. 错误处理方案

### 2.1 分层

| 层 | 内容 | 语言 | 给谁 | 载体 |
|---|---|---|---|---|
| 代码 | `code`（kebab，带领域前缀，如 `projects.identity-conflict`）+ `params`（结构化字段，如 `{path}`） | 无 | 程序、翻译、搜索 | `{ok:false, code, detail}` 里的 `detail` 约定改为**结构化对象**，不是句子 |
| 用户说明 | 前端按 `errors.<code>` 查目录并代入 `params` | 用户语言 | 用户 | 前端 `t()` |
| 开发者文字 | `Error.message`、诊断 `message` | 发布到 npm 的包与 nb-runtime 用英文；仓库内部应用代码可继续中文，但**必须以 `code` 开头** | 开发者 | 诊断 `event` 字段已有，就用它放 code |
| LLM 文字 | 见第 3 节 | 另议 | 模型 | 工具结果 |

- 一条规则：**服务端、harness、runtime 不产生用户界面文字**。需要显示的失败只给 `code + params`；没有对应目录项时，前端显示通用说明“发生了错误（`code`）”并带复制按钮，用户把 code 发给开发者即可搜到。这样“用户看得到的说得清楚”和“开发者好搜”是同一个 code 的两面，并且 code 不会随语言变。
- 说得清楚的标准写进目录规范：每条用户错误写“发生了什么 + 能做什么”（例如“目录在应用的状态目录里，请选其他目录”），不要只复述原因。现有 `projects/messages.ts` 的 `FAILURES` 表就是雏形，只缺“能做什么”。
- 诊断记录：`event` 用 code；保留 `message` 但允许中文。**不要**在日志里塞已翻译的用户文字（会让同一错误在不同语言下搜不到同一串）。`redaction.ts` 的脱敏与此正交。
- 远程调用 `detail` 现在有些是中文句子（`node.ts` 里“本实例没有连到服务端”“目标 … 与合同 … 的提供方位置 … 不符”）。这些是开发者向的诊断文字，应改成 `detail: {…}` 的结构化字段 + 诊断里的 `message`，前端永远不显示 `detail` 原文（`projects` 已经这么做，写成通则）。
- 未知 code（服务端比页面新）：显示通用说明 + code，这一点 `registerFailureReason` 已经在做。
- HarnessError 的 `code` 已齐全，保持；它的中文 `message` 改为开发者文字（可保留中文），但**不得再回流给模型**（见下）。

### 2.2 备选：服务端本地化（Accept-Language 后在服务端出文案）
否决：本项目是本地优先、前后端同一产品，且有跨进程（前端、服务端、插件宿主）与第三方插件；服务端出文案要让每个后端插件也带目录、请求上下文还要带语言，热卸载和错误冒泡的路径更长。code+params 让翻译只发生在“显示的那一刻、一个地方”。

## 3. 给 LLM 的文字

### 3.1 先拆开三条轴
- **界面语言**（用户设置）：只管界面，**不进提示词**。
- **作品语言**（项目/书的属性，如 `zh-CN`）：决定领域提示词用哪一套、小说正文输出什么语言。
- **回复语言**（Agent 对用户说话）：缺省跟用户最后一条消息；写在一句固定指令里。
目前代码没有“作品语言”这个概念；story-qa 的 `initial` 里应加 `lang` 字段（默认 `zh-CN`），Profile 按它选提示词模块。

### 3.2 四类文字各用什么

| 类别 | 例子 | 推荐 | 理由 |
|---|---|---|---|
| 领域提示词 | 写作人设、文风与去 AI 味规则（llmlint 本来就是中文规则库）、剧情问答的 System 段 | **随作品语言**。中文小说用中文原生撰写，不翻译；将来出英文小说时是**另写一套**，不是翻译同一份 | 这些文字是在“定义输出的文风”，直接示范目标语言的写法最稳；翻译会丢掉中文特有的修辞约束。它们是版本化 Profile 资产，不进界面目录 |
| 系统提醒（运行时在对话中插入的“请先…”“你已读了 N 章”） | harness、nb-story 的提醒 | **英文**，数字和名字用结构化占位 | 这是协议，不是文风；不依赖作品语言；与工具说明同语言，模型少一次语言切换 |
| 工具说明、参数名、枚举值 | `read`、`search` 的 description | **英文**，枚举/格式参数规定语言中立（如章节号、`"asc"`），自由文本参数明确写“用小说的语言” | 参考：[Lost in Execution（ACL 2026）](https://aclanthology.org/2026.acl-long.2039.pdf) 报告多语言工具调用的常见失败是把参数值生成成用户语言而 API 期望语言中立格式；[SEATauBench](https://arxiv.org/pdf/2606.28715) 显示工具说明混用语言仅有较小下降。工具名/参数名作为代码标识符本来就是英文 |
| 工具失败结果 | harness 的 `block:true, reason:"收尾工具要单独调用…"`、查不到章节 | **英文 + 稳定 code**：`{"error":"finish_tool_must_be_alone","hint":"Call the finishing tool by itself …"}` | 它进的是模型上下文，不是用户界面；用户若要看，由 nb-agent-ui 按 code 用界面目录渲染 |

### 3.3 证据状态（诚实标注）
- 能引用的同行评审证据只有上面两条：工具参数值语言漂移、多语言工具说明下降有限。“中文系统提示词 vs 英文系统提示词谁整体更好”我没有找到可信的对照研究；搜索到一份单作者 Zenodo 预印本声称英文提示词工具调用成功率极高，数字过于极端，我不采信；一篇宣称中文省 30%到50% token 的页面没有方法说明，也不采信。另一类证据（[Level-Navi](https://arxiv.org/pdf/2502.15690)）说英文为主的开源模型在中文指令下可能不遵循或不用中文回答，这支持“加显式回复语言指令”。
- 所以第 3.2 节的“协议英文、领域随作品”是**工程性推理 + 弱证据**，不是定论。**动手前先在已有的 story-qa 评测上做 A/B**（同一问题集，系统提醒/工具说明用中文 vs 英文，看答对率、输出语言正确率、token 数），再决定是否整体改。在评测出结果前，**不改现有中文提示词**；只对新增的协议类文字用英文，并把“领域提示词 / 协议文字”分文件存放，方便以后单独切换。
- 混合语言的已知风险：英文指令 + 中文原文可能让模型用英文回答。缓解：每个 Profile 末尾固定一条“All user-facing prose must be written in {{language}}（作品语言）”，用结构化占位代入，不用翻译。

### 3.4 备选：全部提示词走界面 i18n 目录（按界面语言翻译一份）
否决：把文风约束随界面语言翻译会让“中文小说作者把界面切成英文”时 Agent 改写英文提示词，输出文风变化；而作者的小说语言与界面语言本来就不绑定。另外领域提示词要版本化并随会话快照（`story-qa@4`），翻译平台改字会破坏快照一致性。

## 4. 备选方案与否决

| 方案 | 要点 | 否决理由 / 本项目的坑 |
|---|---|---|
| **B：保持就地双语对，扩成 `Record<Locale,string>`** | 零新依赖，改动最小；作者写起来最顺 | 加一种语言要改 1178 处；TypeBox 里 `additionalProperties:false` 全要放开，类型要么变宽要么每加一种语言重改；翻译平台不能吃代码里的字面量；各包 `say` 的重复无解；第三方插件被迫写两种语言。在“以后可能更多语言、接翻译平台”的目标下失败 |
| **C：vue-i18n 11** | ADR 已选；Vue 生态主流；SFC `<i18n>` 块 | 见 1.1：只服务 Vue 层，纯 TS 核心与共享包仍无解；命名空间与热卸载要自己拼；它的 Legacy 模式弃用、v12 在 alpha，选它要承担升级；若仍想用它也可行，把 `Translate` 端口接到 vue-i18n 的 `global.t` 即可——**端口设计使这是可逆选择** |
| **D：formatjs / intl-messageformat（ICU）自建薄层** | ICU 是业界通用语法，平台支持最广；MessageFormat 2 已在 CLDR 47 进入 Stable（[CLDR 47](https://cldr.unicode.org/index/downloads/cldr-47)），但采用仍早期（[locize 概述](https://www.locize.com/blog/messageformat-2-i18next)） | 它只是格式化库，目录加载、命名空间、回退链、热增删要自己写，等于手写一个 i18next；MF2 生态尚早，不建议现在押注。若将来要 ICU，i18next 有插件，迁移成本可控 |
| **E：编译期方案（如 Paraglide，每条消息编译成导出的函数，摇树）** | 类型与体积好 | **未做核实**，以下为推理：消息在应用构建期编译进包，运行时热装的第三方插件的目录无法进入这次编译，需要另走一条运行时通道，等于两套；因此不适合“插件热装”这一核心约束。 |
| **F：把翻译放在服务端出文案** | 见 2.2 | 已否决 |

## 5. 仓库现状里我认为应推翻的选择

1. **`{zh-CN, en-US}` 成对字面量作为公共合同**（`LocalizedTextSchema`、`DisplayText`、`formatText`、`formatText` 复制品）。理由：把语言数量写进类型；文字与声明耦合；无法对接翻译平台。
2. **ADR-0023 的 vue-i18n 条目**：从未落地，且与共享包 npm 发布、纯 TS 核心冲突。需要新 ADR 明确引擎与目录约定，并把旧条目标记为取代。
3. **“声明不经过翻译表”的注释**：把一个正当约束（读清单不执行代码）误推成“不要翻译表”。真正的约束是“目录是数据文件”。
4. **各包私有的语言类型**（`MarkdownLocale`、`PromptLocale`、`AgentLocale`、`DisplayLocale`，靠类型断言互相对齐）。改为一个 `string` 形的 BCP 47 标签，默认目录里有哪些由数据决定。
5. **远程失败 `detail` 与 `HarnessError.message` 里夹中文句子，并让 harness 的拦截理由直接成为模型上下文**。用户文字、开发者文字、模型文字三种读者共用一个字符串，是这次问题的根源。
6. **`DISPLAY_LOCALE="zh-CN"` 的写死与“字段接入仍待迁移”的半成品状态**：不如一次接上设置项。
7. 命令 `description` 稳定英文——**保留**，它恰好是我主张的“机器可搜”模式。
