## 五、发现

以下是固定基线的迁移前现状与 t03 设计输入，不是本次变更引入的回归；严重程度表示设计/迁移优先级，不要求 t02 实施。所有“如何核实”均为已读源码与本报告附件；未运行产品、测试或真实模型，未以静态推断声称运行复现。

### 5.1 t03 必须先定

#### F01：用户失败正文仍以底层句子为主，单改诊断语言会改变界面语言

- **严重程度：重要；类别：正确性。** 关联 `B-COMMAND-NOTICE`、`B-REMOTE-HANDSHAKE`、`B-SETTINGS-INVALID`、`B-STORY-HTTP`。
- **位置：** `packages/neuro-book/src/plugins/workbench/web/commands/failure-notice.ts:23-29`；`src/web/host/remote-session.ts:82-86,159-174`；`src/web/FailurePage.vue:30-41,69`；`src/plugins/settings/shared/layer-text.ts:101-135`；`packages/nb-story/src/web/host/client.ts:120-123`。应用相对路径均属 packages/neuro-book。
- **现象：** 命令只本地化标题，正文直接 reason；握手 message 改名 reason 后直接显示；设置解析器先把错误码变中文，再把该句当 reason；StoryCallError 保留 HTTP message 供页面直接显示。现在多数正文是中文，未知或第三方细节可混英文。
- **为什么是问题：** ADR 0034 决策 1/2 要求诊断英文、界面按拥有者命名空间+码本地化。把这些源 message 全改英文，会把英文作为用户主说明；只翻译界面外壳也不能补回参数。`denied/unavailable/invalid-input` 等跨域重名，不能拿裸 code 做全局消息键。
- **如何核实：** 第 2.1/2.2 节与 3.5 的握手样本已逐跳读至 FailurePage/Notification，`B-COMMAND-NOTICE` 已追到 nb-ui `Notification.vue:59-60`。这是静态链路证据，不是“界面已切换语言”的运行结论。
- **建议改法：** t03 分域确定拥有者、稳定码、可用参数、安全 detail 与未知码通用说明；同步迁移实际主说明消费者，不把 reason/message 的英文替换当失败投影完成。保留现有 NOTIFIED 白名单与 stale-target 不通知的产品语义。

#### F02：插件专有码在生命周期摘要处丢失，终点没有足够结构做本地化

- **严重程度：重要；类别：不变量。** 关联 `B-PLUGIN-CODE-SERVER`、`B-PLUGIN-CODE-BROWSER`、`B-PLUGIN-VALIDATION`。
- **位置：** `packages/neuro-book/src/plugin-platform/shared/plugin-code-error.ts:14-29`；`packages/nb-runtime/src/lifecycle/scope.ts:69-84`、`src/plugins/host.ts:1122-1123`；应用 `src/plugin-platform/shared/problems.ts:14-16,30-31`；`src/plugins/plugins/web/components/PluginsPage.vue:195-200,437`。
- **现象：** PluginCodeError 原本有 code/plugin/entry/url，detail 拼在 message；进入 FailureError 后只留 name/message。贡献验证仅留 invalid-declaration/detail，ManifestProblem 只有 path/message；底层每项原因没有稳定码。UI 对 entry-failed 只能拼 message，对拒绝只本地化上层原因。
- **为什么是问题：** 只在 PluginsPage 增目录仍无法区分 code-threw、code-shape、code-load-failed 或取出参数。反过来，从 message 解析码/插件/URL 会把当前诊断句子变成协议，违反按码分支。生命周期摘要有不携带资源值/凭据的明确安全目的，不能顺手序列化任意 Error 自定义字段来“补全”。
- **如何核实：** 3.5 的浏览器装载、贡献验证两条样本；`readManifest` 的 path/message 见 `packages/nb-runtime/src/plugin-manifest/read.ts:46-76`。已证实丢失点，不声称所有错误类都应进生命周期公共合同。
- **建议改法：** t03 在摘要之前确定域拥有者如何提供安全的失败投影，明确哪些码/参数允许跨边界；保持生命周期与插件合同的职责，不建任意异常字段透传器，不靠 message 还原结构。

#### F03：领域工具没有独立 code，中性拒绝靠中文前缀影响章数统计

- **严重程度：重要；类别：正确性。** 关联 `B-TOOLS-DOMAIN`、`B-TOOLS-REFUSED-PROJECTION`。
- **位置：** `packages/nb-story/src/qa/read-ledger.ts:90-96`、`qa/tools.ts:72-74,105-114,137-143`；`src/web/qa/tools.ts:20-44`。
- **现象：** query 的 code/candidates 展平成 content.text，answer 校验只回问题字符串，均无 details.code。chapter_limit 原有 code 在工具输出丢失，且 isError=false；readRefused 按 `result.text.startsWith("没有读：")` 判断，chaptersPhrase 据此排除没读的章节。
- **为什么是问题：** 修改工具说明文字或语言会改变工具卡摘要与已读章数，而不仅是措辞。只给 isError=true 的失败补 code 会漏掉 chapter_limit；旧日志回放也继续依赖中文前缀。这与 ADR 0034 决策 1/4 的稳定码分支、领域工具结构 code 要求不一致。
- **如何核实：** 已读 read-ledger 生产→tools 丢码→完整日志/临时事件→web readRefused 与 chaptersPhrase 的真实消费者，见 2.7、3.1。不是根据搜索到中文前缀推测。
- **建议改法：** t03 同时定义失败和中性拒绝的领域结果参数、details.code 及 UI 读取口径；明确旧日志无 code 时的读取策略。保持章数上限是正常拒绝、不是执行失败；不要通过把 isError 改 true 来规避分类缺口。

#### F04：临时事件、权威日志与 QA 降级是三种投影，不能只修 SSE

- **严重程度：重要；类别：正确性。** 关联 `B-AGENT-SSE`、`B-AGENT-LOG-REPLAY`、`B-QA-RECORD`。
- **位置：** `packages/nb-story/src/qa/web-events.ts:19-45`；`server/qa-service.ts:175-179,379-388,566-576`；`src/web/qa/source.ts:127,184-195,242-247`；`src/web/qa/record-messages.ts:17,28`；`packages/nb-agent-ui/src/harness.ts:215-236,261-285,352-369`。
- **现象：** QA SSE 工具结果截到 500 字且去掉 details；完整日志保留工具 details，前端适配器也能消费它。正常日志 run_end 按 kind 本地化；日志不可用时 record-messages 只保留 error.message，直接变界面正文，不用 record 的 code/kind。
- **为什么是问题：** 同一失败在流式、重连补发、日志缺失三种状态可能用不同文案和结构。只给 SSE 加 details 不会让旧日志与 QA 降级能按码显示；把临时截断误判成权威数据丢失，又会导致不必要的持久格式迁移。
- **如何核实：** 2.7 与 3.4 的精确行号更正；逐条读 source 的 snapshot/log/event 分派和日志失败分支，未把 nb-harness 通用 SSE serializer 当 QA 实际 HTTP 路径。
- **建议改法：** t03 分开约定临时事件允许丢什么、日志权威字段、record 降级需要哪些稳定字段及未知/旧值回退。投影要在三条读路上得到相同失败语义，但不强制相同载荷或取消截断。

#### F05：nbdev 共用校验的返回值就是中文，CLI 改英文会直接影响面板

- **严重程度：重要；类别：代码质量。** 关联 `B-NBDEV-CLI`、`B-NBDEV-HTTP`、`B-NBDEV-VALIDATION`、`B-NBDEV-SEARCH`、`B-NBDEV-TERMINAL`。
- **位置：** `packages/dev-panel/src/core/text-rules.ts:14-37`、`core/questions.ts:54-98`；`src/web/parts/AnswerForm.vue:78-86,129`；`cli/output.ts:25-32,99-124`；`server/writes.ts:291-298`；`server/serve.ts:291-307`。
- **现象：** validateAnswerValue/controlCharProblem 等返回 string/null，浏览器直接 import 并显示；服务侧再把同样的 reason join 到 NbdevError。CLI 和 HTTP 都序列化同一个 message，面板 ApiError 又取首错。终端 WS/search NDJSON/元数据内 warning 不走同一 HTTP 外壳。
- **为什么是问题：** ADR 的 nbdev CLI 英文、面板中文目标不能靠翻译一个 NbdevError 构造函数实现。把共用函数改返回英文会同时改变面板本地校验；只迁移 HTTP 也漏浏览器直调、WS 与流错误。
- **如何核实：** 读 AnswerForm 的 import/调用/最终插值与 writes catch→envelope→web ApiError，3.1 列出旁路。终轮计数把这批“直接作用户说明的异常”按用途归类，不拿异常语法掩盖多读者。
- **建议改法：** t03 先定共用校验的 code+参数合同、CLI 与面板各自的投影边界、warning/成功值内问题及多错处理；保留 nbdev 自有 errors[] 合同，不套产品所有域的统一错误对象。

#### F06：线协议、业务合同、控制 IPC 与磁盘格式不是同一个版本边界

- **严重程度：重要；类别：不变量。** 关联 `B-REMOTE-HANDSHAKE`、`B-REMOTE-BUSINESS`、`B-PROJECT-IPC`、`B-HTTP-HOST`、`B-HTTP-COVER`。
- **位置：** `packages/nb-runtime/src/remote/protocol.ts:14-21`、`node.ts:699-710,867-879`；`packages/neuro-book/src/server/projects/ipc.ts:18-29`；`src/plugins/plugins/shared/contracts.ts:21-34`；`src/plugins/http/backend/dispatch.ts:221-222`；`src/plugins/projects/web/plugin.ts:196-198`。
- **现象：** wire4 约束远程帧语义，每个 errors/detail 又有闭合业务 schema；项目 started failed 信封只有 detail，无独立版本。HTTP 另有宿主 error 外壳、封面顶层 code/detail、nbstory 顶层 code/message、nbdev errors[]，不能互读。封面 reader 对宿主外壳实际丢正文，只剩 status/statusText。
- **为什么是问题：** 在 detail 字符串槽改塞对象、给闭合帧添字段或只升业务 version，不能自动保证旧窗口/项目子进程懂新语义；提升 wire 也不能替代无版本 IPC/HTTP/存量记录的兼容判断。
- **如何核实：** 3.5 的 HTTP/握手样本及 3.4 合同版本更正；业务 detail 双侧校验已追到 node，不用错误码拼写推断兼容。
- **建议改法：** t03 逐域写清受影响 schema/帧/控制信封、版本与旧消费者拒绝/回退方式；保持四种 HTTP 合同的拥有者与用途，不为外形统一迁移无关域。raw route 的安全 not-found 折叠继续保留，不能为了显全码泄漏保护路径。

#### F07：旧错误文字、旧会话可读与旧会话可续跑是不同问题

- **严重程度：重要；类别：不变量。** 关联 `B-SESSION-JSONL`、`B-QA-RECORD`、`B-INGEST-STATE`、`B-NBDEV-NOTIFY`、`B-TASK-EVIDENCE`。
- **位置：** `packages/nb-session/src/entries.ts:133-184`、`jsonl-log.ts:12-27,73-84,99-107`；`packages/nb-harness/src/harness.ts:110-121`、`tools/effective.ts:115-141`；`packages/nb-story/src/core/qa-records.ts:169-207,266-276,361-397`；`ingest/job.ts:243-250`；`packages/dev-panel/src/core/notify.ts:214-235`。
- **现象：** session 无格式版本，旧条目外层可解析但无 session_snapshot 不能恢复；工具声明按 exact 比对，description 改动也会拒绝。QA 支持旧单轮与旧日志名，当前日志和 record 还有哈希配对。ingest usage.error 保存 message 而无 kind/status；通知/审计/进程记录各有自己的 schema，Task evidence 原字节显示。
- **为什么是问题：** 翻译磁盘旧 message 或工具描述，不仅改变 bug 报告可检索文本，还可能破坏日志哈希/会话恢复。现在没有通用“旧错误中文→新码”迁移器，不能假定英文诊断上线后历史也自动本地化。
- **如何核实：** 2.4/2.5 与 3.4；已读写入和读回两端，未执行 repair、重新保存、审计初始化或旧数据迁移。
- **建议改法：** t03 明确每种旧读的保留、未知码与无结构字段回退；日志可浏览与可继续分别验收。保持历史原字节，不批量改写 QA/session/Task 证据；Profile/工具声明语言变化按既有版本与质量合同另定，不借诊断迁移顺带改提示词。

### 5.2 迁移时注意

#### F08：有些包装分支没有 Error.cause，不能靠新英文 message 恢复原始诊断

- **严重程度：重要；类别：代码质量。** 关联 `B-PLUGIN-CODE-BROWSER`、`B-PROJECT-IPC`、`B-WORKFLOW-STATE`。
- **位置：** `packages/neuro-book/src/plugin-platform/web/plugin-code.ts:233-247`；`src/server/projects/ipc.ts:18-29`；`packages/nb-workflow/src/runner-execution.ts:156-175`。
- **现象：** 浏览器 hostModules 包装保留 cause，但工厂 code-threw/module-not-shared 只取 error.message；跨项目 started.detail 也是摘要，Workflow Run.error 只剩 string。后两者为跨边界/状态投影，不是把 Error 本体写盘。
- **为什么是问题：** t04 若仅换中文外层文本，工厂异常的类型/栈/因果仍丢失；反过来，跨进程不能传任意异常来代替稳定码+安全 detail。ADR 的进程内 cause 和远程 cause 枚举必须分别执行。
- **如何核实：** 已对照同文件 :234 与 :246-247 两个分支，及生命周期摘要和项目 IPC 转换；Workflow 错误归约源码直接可见。不声称外部 OMP 内部异常也丢 cause，其实现未追到。
- **建议改法：** 在拥有真实 Error 的进程内包装点保留标准 cause；t03 对跨边界决定安全结构投影，不传 stack/原始值给用户。t04 区分“原始外错保留”和“本项目诊断英文”，不翻译第三方原文。

#### F09：CLI 插件日志绕开诊断 store；迁移单一出口会漏路径

- **严重程度：重要；类别：安全与性能。** 关联 `B-CLI-PLUGIN-LOG`、`B-DIAG-JSONL`、`B-DIAG-FALLBACK`。
- **位置：** `packages/neuro-book/src/cli/plugin.ts:52-64`；`packages/nb-runtime/src/diagnostics/store.ts:252-261`、`redaction.ts:67-80`；应用 `src/plugins/diagnostics/backend/jsonl-exporter.ts:161-179,229-238`。
- **现象：** CLI 自己 JSON.stringify DiagnosticInput 写 cli.jsonl，Error 只 name/message，无 store 的脱敏/大小约束；主诊断 store 保留安全 error.cause，但不保留 Error.code；JSONL 丢 sequence，最小 stderr 再丢 data/error。
- **为什么是问题：** “诊断已经统一保留 code/脱敏/落盘”的迁移假设不成立。文本在旁路保留且可能含第三方回显；这是静态暴露路径，**未证明发生过真实凭据泄漏**。兜底最小记录的丢字段是当前明确行为，也不能靠它保证结构化失败回放。
- **如何核实：** 三个 writer 的字段逐项对比已写 2.1/2.3，不把都叫 JSONL 当成同一格式；未写新日志或模拟敏感数据。
- **建议改法：** t03/t04 把 CLI recorder 与 stderr 兜底纳入诊断边界，明确安全字段/限制和可检索码的位置；是否共用现有收敛实现由对应拥有者设计，不趁本次盘点重构日志。不要为保留 cause/码而扩大用户可见负载。

#### F10：状态拒绝、取消与结果未知不能在文案目录里合并成“失败，可重试”

- **严重程度：重要；类别：不变量。** 关联 `B-REMOTE-ROUTE`、`B-STORE-FAILURE`、`B-STORAGE-STATE`、`B-NBDEV-NOTIFY`、`B-WORKFLOW-STATE`、`B-OWNED-PROCESS`。
- **位置：** `packages/nb-runtime/src/remote/protocol.ts:63-83`；`packages/neuro-book/src/shared/store/persisted.ts:377-405`；`src/plugins/storage/backend/partition.ts:294-300`；`packages/dev-panel/src/core/notify.ts:20-28`；`packages/nb-workflow/src/runner-execution.ts:156-175`；`packages/owned-process/src/types.ts:4-18,48-58`。
- **现象：** 已发出的写请求中断是 unknown-outcome；store 留 pending 的 value/expect；corrupt/unsupported-version 是记录保护态，而不支持分区库格式当前报 io-error；通知 uncertain 可能已经送达，不能重发；workflow waiting/cancelled 与 failed 分开；自然非零进程退出是 completion，不自动变 OwnedProcessError。
- **为什么是问题：** 把这些槽按同名码或负向语气合并，会诱导重复副作用、错误 reset 或丢掉已经提交的数据。这是 t03 的语义保护要求，不是说当前这些结构已经有 bug。
- **如何核实：** 必查表与上述状态归约源码；抽取也存在 stopRequested 将 failed 映为 stopped（`packages/nb-story/src/ingest/runner.ts:138-154`），提交进度必须按实际书数据核对。
- **建议改法：** 每个域的投影合同和验收分别保留失败/取消/中性拒绝/未知结果/保护态；文案不得承诺未写入或安全重试。按当前不变量设计，不统一 retryable=true，也不因为中文文字相似合码。

#### F11：测试有措辞绑定，不能为迁移通过而把断言机械重钉为英文

- **严重程度：建议；类别：测试。** 关联 `B-TEST-ASSERTIONS`。
- **位置：** `packages/neuro-book/src/plugin-platform/backend/loader.test.ts:108,163,176,182`；`packages/nb-harness/tests/read-tool.test.ts:53-54,65-68,77-85`；`packages/nb-session/tests/session-log.test.ts:182,193-195`；`packages/dev-panel/src/core/questions.test.ts:60`。
- **现象：** 测试用 message 包含码/中文片段、toThrow 正则检验实现；其中 Error.message 包含码是插件摘要结构不足的症状。另一方面原生编辑文本有明确上游训练合同，不能与自写诊断措辞混为一类。
- **为什么是问题：** 把旧中文换新英文可让检查绿，但没有证明消费者的失败/取消/恢复行为正确；也会继续把内部措辞锁成合同。OMP 原生错误的稳定原文却属于有意保留的产品行为。
- **如何核实：** 本次只读测试及 `packages/nb-harness/docs/omp-capabilities.md:107-111,141`，没有跑测试，不能报告这些断言现在通过/失败。

#### F12：未接产品的基础库仍有独立失败语义，不虚构持久化与迁移消费者

- **严重程度：建议；类别：文档。** 关联 `B-WORKFLOW-STATE`、`B-WORKFLOW-CONTROL`、`B-HISTORY-ERROR`、`B-MEMORY-FAILURE`、`B-SNAPSHOT-FAILURE`。
- **位置：** `packages/nb-workflow/src/backend.ts:39-59`、`runner-run-store.ts:120-147`；`packages/nb-history/src/types.ts:153-181`；`packages/nb-memory/src/ingest/extract.ts:109-122`、`retrieval/llm-planner.ts:78-89`；`packages/file-snapshot-cache/src/snapshot-cache.ts:324,340,410-416`。
- **现象：** Workflow 具有 durable 端口合同但自带 backend 只有 memory，Run 错误字符串可经端口保存，不等于已有磁盘存量。History SQLite 保存操作/快照而非异常。Memory 降级只留计数/布尔，异常没先记日志；snapshot 的 lastBuildError 截断而 watcherError 不同。
- **为什么是问题：** 若按包名假设已经接到项目宿主或已经落盘，会设计不存在的旧错误迁移器，漏掉真正的无结构/原因丢失边界。没有原始错误留下的 memory 降级，也不能从一条 skippedChunks 恢复成具体失败码。
- **如何核实：** 在 neuro-book/nb-story/dev-panel 的 src 范围搜索五个包名没有生产 import；库 API/演示是真实可找到的消费者，具体见 2.6。这个负证据不否定外部用户、包外动态消费或未来集成。
- **建议改法：** t03 分“库公开合同”和“已接产品出口”，只对真实记录格式讨论旧读；缺失诊断原因是单独可观察性决定，不在语言迁移中顺带加重试/日志/新存储。
