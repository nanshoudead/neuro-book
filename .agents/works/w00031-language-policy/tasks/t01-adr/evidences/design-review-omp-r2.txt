### 1. 用户失败投影不进线协议，但浏览器端没有取得自定义失败文案的合同
- **严重程度**：重要；**类别**：正确性
- **位置**：`/tmp/review-lang-governance/design-v2.md:15-21,87-89`；`packages/nb-runtime/src/remote/contract.ts:157-171,319-322`；`packages/neuro-book/src/plugins/workbench/web/commands/failure-notice.ts:23-30`
- **现象**：第二版确认用户投影“只用在界面边界，不进线协议”，远程业务失败仍只有按方法声明的 `code/detail`，并把“插件自定义失败码怎么带文案”留到第 3 步设计。浏览器收到后端插件的自定义码时，现有远程结果没有双语目录、文案 provider 或宿主回退规则；`detail` 只能是业务详情，不能可靠承担主文案。
- **为什么是问题**：对内置命令可以在 web 端写静态码表，但第三方/后端插件的错误码是动态声明的，通用宿主既不知道码，也没有办法在不把文案放进 wire 的情况下显示双语失败说明。把 `LocalizedText` 塞进 `detail` 会破坏方法错误 schema；把英文 `detail` 当文案又违反决定 1。未知码、跨版本码、只提供服务端入口的插件都会落入“只有 code、没有用户说明”的失败路径。
- **如何核实**：用 `defineRemoteService` 声明一个 `errors: {"custom-failure": Type.Object({id: Type.String()})}` 的服务，经真实 `RemoteClient` 返回该码；调用方只能得到 `{ok:false, code, detail}`，现有 `failureNotice` 也只处理命令自己的 `reason`。再构造一个没有浏览器入口的后端插件，确认宿主没有可加载的文案表。
- **建议改法**：第 3 步必须先定 owner 和跨进程形状：例如由共享合同同时登记 `failureCode -> LocalizedText` 的纯 JSON catalog，浏览器/宿主按合同版本加载并对未知码回退固定文案；或规定自定义码只能由拥有浏览器入口的插件消费。catalog 的版本、缺失、冲突和第三方恶意超大文案都要进入 manifest/贡献校验与兼容合同，不能把它留作实现阶段的“怎么带文案”。
### 2. `MessageTemplate` 的 brand 在插件清单和跨进程登记后消失
- **严重程度**：重要；**类别**：不变量
- **位置**：`/tmp/review-lang-governance/design-v2.md:49-63,69-72`；`packages/nb-runtime/src/plugin-manifest/build.ts:44-58,179-196`；`packages/nb-runtime/src/plugin-manifest/read.ts:54-63,86-99`；`packages/neuro-book/src/plugin-platform-profile.ts:16-19,35-48`
- **现象**：设计用运行时 `templateBrand` 区分普通 `LocalizedText` 与 ICU 模板，并要求普通文字从不解析；但第三方插件的贡献声明会被 `buildManifest` 序列化进 `package.json`，清单读取只恢复 JSON 字符串，`MessageTemplate` 的 symbol brand 不会跨文件、进程或宿主模块表保存。草案的 `TemplateSchema` 只写“清单 JSON 用”，没有给出清单字段如何标记这是模板的形状。
- **为什么是问题**：宿主登记时无法知道一个 `{zh-CN,en-US}` 是普通文字还是模板。若按所有形似 `{name}` 的字符串编译，就违反普通文字不解析并会改变已有插件；若按普通文字直取，清单里的模板永远不格式化；若给 JSON 增加标记，又改变贡献声明/manifest schema 和旧插件读取合同。跨进程远程贡献和浏览器加载还会产生不同的 brand 实例，不能把 symbol 身份当持久化合同。
- **如何核实**：用第三方 `view`/`command` 声明生成 `package.json`，再经 `readManifest` 读回；读回对象只能包含 JSON 字符串，不能保留 `templateBrand`。对同一 `{zh-CN: "Hello {name}", en-US: "你好 {name}"}` 分别作为普通文字和模板登记，当前清单形状没有可观察差异。
- **建议改法**：给持久化声明定义显式、可版本化的模板形状，例如 `{kind: "template", messages: {"zh-CN", "en-US"}}`，并让普通文本保持原两字段形状；`buildManifest`/`readManifest`/SDK helper/贡献 schema/宿主共享模块一起校验和重建运行时对象。为旧清单定义“普通文本”兼容读取，不能靠运行时猜测或 brand 透传。
### 3. SDK 删除 `formatText`/`localize` 会在现有 `engines.neurobook` 兼容范围内造成运行时断裂
- **严重程度**：阻断；**类别**：正确性
- **位置**：`/tmp/review-lang-governance/design-v2.md:64-79`；`packages/neuro-book/src/sdk/index.ts:41-43`；`packages/neuro-book/src/sdk/entries.ts:5-7,14-16`；`packages/neuro-book/src/plugin-platform-profile.ts:22-24,35-48,61-68`；`packages/neuro-book/src/shared/product.ts:1-8`
- **现象**：设计把 SDK 的公开 `formatText`/`localize` 改成 `message`/`textOf`，只说“按 `engines.neurobook` 兼容变更处理”，没有定义产品版本、SDK 版本或宿主模块表的切换。当前产品版本是 `0.1.0`，第三方插件构建缺省写 `engines.neurobook: ^0.1.0`；运行时用同一 SDK 入口的宿主模块表给插件提供实现。
- **为什么是问题**：旧插件的浏览器入口或共享模块仍会调用宿主 SDK 的 `formatText`/`localize`。只删除导出而不提高引擎门槛时，manifest 仍会通过 `engineAccepts`，直到入口激活才因缺少导出失败；只提高产品版本又会把所有现有 `^0.1.0` 插件标成不兼容，必须明确升级/回退策略。SDK tarball 的版本来自 `PRODUCT_VERSION`，宿主共享模块的兼容承诺由 `SDK_ENTRIES` 固定，不能只改类型导出和 `typePaths`。
- **如何核实**：保留一个旧插件构建产物，令其入口调用 `@notnotype/nb-plugin-sdk` 的 `formatText`，在只导出新 API 的宿主模块表中激活；manifest `engines.neurobook: ^0.1.0` 仍通过，但入口加载/运行失败。现有 `packages/neuro-book/src/plugin-platform-profile.ts:22-24` 已明确每个共享模块都是 `engines.neurobook` 的兼容承诺。
- **建议改法**：选择并写死一种兼容策略：在同一引擎范围保留旧导出别名并继续测试，或提高 `PRODUCT_VERSION`/`engines.neurobook` 的不兼容范围并让安装器在激活前拒绝旧插件；若要双宿主 API，版本化 SDK 入口/宿主模块表。更新 `sdk.test.ts`、生成 SDK、插件安装兼容测试和 release smoke，不能把它归为普通源码改名。

## 中途复核更正（以下判断优先于前面的初稿）

- **第 1 条保留为“重要”，但收窄为第 3 步的设计前置条件**：静态代码证明当前远程结果不承载用户文案，不能证明“不让用户失败投影进入调用结果”本身不可行。调用方可以从双方共享的合同常量得到内联双语映射，未知码也可以显示固定双语兜底；不必建设全局消息目录，也不应为此限制插件必须有浏览器入口。第二版已把此事安排在第 3 步，需把“共享映射或通用兜底的 owner、未知码行为、两端版本错配”写成该步的验收，而不是当作已经完成的错误模型设计。前面的真实 RemoteClient 实验是建议核实方式，本轮尚未执行。
- **第 2 条撤回，不计入发现数量**：草案只给出类型 brand，没有声明 `templateBrand` 必须是运行时 symbol；`DisplayText` 已有 `{template, params}` 的可序列化外层判别。普通贡献的 title 目前只接受普通 `LocalizedText`，不能据此推断模板一定要以相同字段无标记穿过 manifest。JSON 不保存 symbol 是事实，但不足以证明本稿必然丢失模板身份；`TemplateSchema` 的字段接受范围和可移植校验属于尚待明确的实现合同，不能把臆定的运行时 brand 当作已存在机制。
- **第 3 条由“阻断”降为“重要”，标题中的“会在现有范围内断裂”是有条件结论**：设计第 79 行已经识别 SDK 兼容变更，没有决定继续使用 `0.1.0`。只有在删除导出且未同步不兼容版本时才发生该断裂。仓库作者文档 `packages/neuro-book/plugin-sdk/README.md:33,332` 明确 SDK 目前以 tarball 分发、不发布 npm；本轮读取 npm registry 的包与 latest 两个地址均返回 HTTP 404，不能据此声称从未分发过本地 tarball。保留的问题是第 1 步缺少选定的切换方案、对已安装产物的引擎拒绝验收，而不是已经证实的运行故障。建议沿用干净切换：明确不兼容产品版本、重建示例/SDK、在激活前按引擎范围拒绝旧产物；无须为未证实的消费者强制保留别名或引入双宿主入口。

以上更正不新增编号；最终统计排除第 2 条，并以第 3 条的修订级别为准。

### 4. 通道矩阵漏掉运行中事件：领域工具新增的 `details.code` 在网页投影中被丢弃
- **严重程度**：重要；**类别**：不变量
- **位置**：`/tmp/review-lang-governance/design-v2.md:13-14,87-89`；`packages/nb-story/src/qa/web-events.ts:12-17,38-42`；`packages/nb-story/src/server/qa-service.ts:161-179`；`packages/nb-agent-ui/src/harness.ts:215-235,352-369`
- **现象**：第 2 步列了工具结果与会话 JSONL，却没单列运行中的 Agent 事件/SSE 与后续日志补发。现有 `webEventOf` 的 `tool_execution_end` 只留下工具 id、名称、`isError` 和最多 500 字正文，整个 `details` 被删掉；会话日志中的同一结果则保留 `details`。因此第 13 行新增的结构化错误码只在稍后的权威日志到达后才对界面可用。
- **为什么是问题**：不能仅凭领域工具执行结果已有 `details.code` 就认定浏览器已经具备按码取文案的能力。当前 `createHarnessTranscript.applyEvent` 会把临时工具失败正文直接作为错误，`applyLogEntry` 才补回结构化详情；若只迁移最终日志消费者，运行中和日志读回会出现不同的失败主文案。日志是权威、事件可以裁剪的现有设计可以保留，但必须明确临时阶段展示固定失败文案/加载态，或透传最小安全码，而不是在两种输入上猜英文正文。
- **如何核实**：**已运行** `bun /tmp/review-lang-governance/lab-backend-r2/event-projection.ts`，调用仓库真实 `webEventOf` 和 `createHarnessTranscript`。同一个 `isError:true, details:{code:"not_found"}` 工具结果直接交适配器时保留 code，经网页事件投影后 `result.details` 为 `undefined`，`error` 只有原正文；断言全部通过、退出码 0。这是纯数据投影实验，未启动模型、HTTP 服务或浏览器。
- **建议改法**：在第 2 步矩阵中分别登记原始 harness 事件、网页裁剪事件/SSE、权威日志补发、QA 记录降级回放四条路径；第 3 步给临时与最终视图确定同一错误码投影语义。若保留事件裁剪，临时失败用固定产品说明，日志到达后补详情；若要即时显示领域原因，仅传有界、可校验的 `details.code`/安全字段，不把任意第三方 details 全量暴露。验收覆盖事件先到、日志先到和断线补发，不改写持久化的原始模型消息。

### 5. `nbdev` 错误英文化与面板中文不迁移共用同一批消息，不能只按 CLI 与网页文件分开
- **严重程度**：重要；**类别**：正确性
- **位置**：`/tmp/review-lang-governance/design-v2.md:28-30,85-89,97`；`packages/dev-panel/src/core/text-rules.ts:3-5,14-37`；`packages/dev-panel/src/server/writes.ts:291-295`；`packages/dev-panel/src/web/host/api.ts:46-48`；`packages/dev-panel/src/web/host/writes.ts:25-41,104-108`；`packages/dev-panel/src/web/parts/NewWorkForm.vue:5,24-26`
- **现象**：第二版已拆分 CLI 与网页，但尚未给两者共用的错误定义/校验函数安排投影。`NbdevError.message` 被 HTTP 接口原样放入 `errors[].message`，网页多数失败仍直接显示该 message；`controlCharProblem`、`titleProblem` 更是被后端断言与前端表单直接共用的中文字符串函数。对这些函数改英文会改变网页；完全不改又无法完成 `nbdev` 诊断英文化。
- **为什么是问题**：待确认项“网页单一中文，不纳入双语，也不改英文”只能是语言政策，不能被理解为网页消费者不需要迁移。共用的字符串现在既是诊断又是产品校验说明，外层 `invalid_text`、`usage` 等粗粒度 code 不足以还原所有中文细节；例如 `assertPlainText` 的结构化 details 只给 `reason:"control_char"`，没给实际 Unicode 码点。仅给一个泛化中文标题、继续把英文 message 当正文或字段错误，仍不满足中文面板合同。
- **如何核实**：**已运行** `bun /tmp/review-lang-governance/lab-backend-r2/panel-validation.ts`，调用真实共用模块：空标题得到 `不能为空`，NUL 得到 `含控制字符 U+0000`，同一输入的后端 `NbdevError` 是 `{code:"invalid_text",message:"goal含控制字符 U+0000",details:{field:"goal",reason:"control_char"}}`，断言通过、退出码 0。HTTP 原样转发和网页直接消费 message 的路径为静态核对，未启动面板。
- **建议改法**：不改变已确认的语言决定。第 2 步把 `nbdev` 共用校验结果、HTTP warnings/errors、预览字段问题、通知结果记录列成具体通道；第 3 步让共用校验返回稳定的问题码与必要参数（字段、码点、上限等），CLI 生成英文诊断、网页生成中文说明。先迁移中文消费者，再改生产者；网页只是不用双语，不是免做适配。对未知/旧数据保留中文主文案兜底和原文详情，不按 message 文本逆向分类。

### 6. 旧数据“能读”与会话“能恢复”不是同一合同，工具说明翻译会触发快照不兼容
- **严重程度**：重要；**类别**：不变量
- **位置**：`/tmp/review-lang-governance/design-v2.md:11-14,85-89`；`packages/nb-harness/src/tools/registry.ts:11-22`；`packages/nb-harness/src/tools/effective.ts:92-108,115-135`；`packages/nb-harness/src/harness.ts:106-118`；`packages/nb-story/src/qa/engine.ts:332-334`
- **现象**：计划只要求旧持久化数据兼容读取，没有分别定义工具声明迁移后的“只读查看”与“继续运行”。当前工具快照比对整个声明，不仅比 schema 与 provider version，也比 `description`。把基础设施工具说明由英文改中文，或给声明增加失败码元数据，即使工具名与参数完全不变，也会让旧会话得到 `session_incompatible`；nb-story 会转成 `qa_not_continuable`，还没有模型请求就拒绝续问。
- **为什么是问题**：这是已公开的保护合同，不应通过忽略描述、改写历史或宽松比较绕过；但意味着“旧 JSONL 解析成功、QA 记录读回成功”不能充当迁移兼容证据。若切片先发布了工具说明/声明改动，后续再补界面或旧数据策略，用户会先失去续问能力。第二版已承诺中文提示词，仍需把这种语言变化导致的会话断点列入切片验收，而不是混在诊断 message 的机械替换中。
- **如何核实**：**已运行** `bun /tmp/review-lang-governance/lab-backend-r2/session-restore.mjs`，经实际 `createHarness` 建快照、关闭、再恢复：相同工具说明恢复成功；只将 `Search the book` 改成 `搜索本书` 得到 `session_incompatible`，`modelCalls:0`，日志逐字未变，退出码 0。该 worktree 无 `node_modules`，实验的 Profile 经 `Bun.resolveSync` 与 harness 使用同一模块实例（输出路径是主工作区的 `packages/nb-profile/src/index.ts`）；harness、工具登记表、恢复比较与内存日志均来自审查 worktree。本轮未修改依赖或仓库；初次混入两份 Profile 身份标记的实验失败不作为产品证据。
- **建议改法**：第 3 步先按声明版本明确每类旧会话是“继续使用旧声明/旧版本实现”还是“只读查看、不能续问”；最小方案可以接受后者，但要在发布说明和界面中明确，不承诺无损恢复。不修改原始历史，不放宽全字段比较。第 4 步把 Profile/工具声明与调用方提示作为一个原子发布片，验收同时覆盖旧日志查看、旧会话恢复的既定结果、新会话、新旧声明错配；在第 1 步只改 UI 文字而不动工具声明时，无须提前改 harness 的日志格式。

### 7. 只登记新发布包不够：已发布消费者与 nb-story 网页产物没有版本和发布窗口安排
- **严重程度**：重要；**类别**：不变量
- **位置**：`/tmp/review-lang-governance/design-v2.md:35-42,79,85-89`；`docs/adr/0029-workspace-packages-publish-source-to-npm.md:25-28,40-41`；`docs/standards/repository-workflow.md:84-90`；`scripts/release/publish.ts:105-111`；`packages/nb-story/package.json:24-30,42-48,70-76`；`packages/nb-agent-ui/src/index.ts:13-15,31`；`packages/nb-form/src/index.ts:17-18`
