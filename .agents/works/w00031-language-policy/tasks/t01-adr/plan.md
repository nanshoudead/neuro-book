## 关键设计

### `docs/adr/0034-language-policy.md`（新）

frontmatter：`status: accepted`、`decided: 2026-10-27`。头部按 0028、0031 的写法列关联工作、相关文档与“部分取代：ADR 0023 决策 2 中的 vue-i18n；0023 的其余决定不变”。

**背景**：现状（中文消息与英文码混用、界面直接显示 `message`、各包四份内联双语副本、0023 写了 vue-i18n 却从没装过）与触发（开发者要为国际化定政策）。

**决策**（每条写理由与代价，细节只指向 Spec 与 Task）：

1. 三类文字：界面文字与给用户看的失败说明本地化；开发诊断英文、不本地化；第三方错误原样，原错放 `cause`。程序只按码分支。理由：日志落盘与跨语言检索要稳定、诊断量大翻译不划算（vim、git 也只翻给用户看的文字）。代价：现有中文诊断要迁移（t04）。
2. 错误：各错误域保留自己的合同（跨进程帧、`RemoteCallError`、`DiagnosticsError`、命令失败结果）；跨进程只传码、结构化参数与安全 detail；服务端、runtime、harness 不产生界面文字；界面按“拥有者命名空间 + 码”的消息键取文案，未知码显示通用说明并附码。理由：统一形状会破坏帧合同与 unknown-outcome 语义（第一轮后端审查第 1、2 条）；码在不同合同里会重名（第三轮第 1 条）。
3. 界面文字：每个插件、每个共享包自带按语言分的 JSON 消息目录，按插件 id 或包名分命名空间，随插件登记与注销；声明里放键，与语言无关的文字照旧写字符串；用 i18next 的原生格式，日期与数字用 `Intl`；共享包不依赖 i18n 库，接收宿主的 `t`。取代 0023 中的 vue-i18n。理由：插件生态的常规做法（VS Code、Chrome 扩展），能接翻译平台，加语言不改声明；vue-i18n 只服务 Vue 层；原生格式让共享包的最小实现只要几十行。代价：约 1100 条内联文字迁移，几份 Spec 的声明字段要改（w00028）。
4. 给模型的文字：界面语言、作品语言、回复语言分开；领域提示词用中文并随作品语言；基础设施提示词新写的用中文；契约已规定为英文的字段（命令 `description`）与现有英文说明保持原样，等 t05 的评测再定；OMP 原生 `read`、`edit` 的错误文本原样保留英文；领域工具的失败在 `details` 给 `code` 并按码写中文说明，第三方工具不强制。理由：输出是中文小说，上下文少混语言；但没有可信的对照研究，改现有说明要先评测；OMP 错误文本是模型训练依赖的协议。代价：评测前同一上下文里中英并存；改工具说明会让旧会话不能续跑（等 t05 一起定）。
5. 标识符（错误码、事件名、字段名、工具名、参数名、标签名）一律英文；注释、文档、Spec 与 Task 记录仍用中文（根 `AGENTS.md`）。

**备选方案**：内联双语字面量（只适合两种语言、接不上翻译平台；t49 采用时没有记录理由）；vue-i18n（只服务 Vue 层）；开发诊断也做 i18n（日志混语言、检索难，收益小）；统一的错误形状（理由见决策 2）；基础设施提示词改英文（证据不足，等 t05）。

**后果**：要随之改的真相源与归属的 Task；旧会话与已发布 npm 包的影响交给哪个 Task；本 ADR 不规定的细节（目录登记、回退链、类型检查、失败投影的形状）由哪份 Spec 定。
