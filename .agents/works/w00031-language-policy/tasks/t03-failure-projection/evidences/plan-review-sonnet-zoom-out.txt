### 1. 计划漏掉了 t03 README 与 ADR 点名要它定的两块：nbstory 命令行三层、诊断构造入口的机检

- 类别：范围缺口 / 完成判据不可信
- 位置：plan.md:30-46（问题表）、plan.md:56-58（切片清单）、plan.md:73（完成判据）；对照 t03 `README.md` “目标与范围”第 5、7 条、ADR 0034 “后果”表第 5 行（`story/cli-skill.md`、`story/qa.md`、`story/ingest.md` 由 t03 负责）
- 现象：t03 README 要求 “`nbstory` 分三层：提示词与工具说明、给人看的输出、`--json` 与 API 的 `message`（要版本化，或拆成 `message` 与 `detail`）” 和 “诊断构造入口带类型，机检检查入口而不是按中文判断”。plan 的 M9 行只写了 nb-story 网页，切片清单也只有“nb-story 网页（M9）”；nbstory 命令行（矩阵 `B-CLI-STORY`，channel-matrix.md:202，写明 “JSON 无统一错误版本”“并非所有 --json 失败都有 JSON”，`SKILL.md:20` 教模型读 `{error:{code,message}}`）没有去处。nbook 命令行 `--json`（`B-CLI-NBOOK`，channel-matrix.md:162，`{ok:false,code,message}` 无 schema 无版本）同样没去处。“机检入口”在整份计划里没有出现，B2 只管 CLI 插件日志。
- 为什么是问题：plan.md:73 的完成判据是 “M1 到 M17、B1 到 B4、9.5 节的 8 项都有去处”，按矩阵编号数全对得上，所以看上去完备；但 README 的目标清单比矩阵编号多出两项，判据没覆盖它们。把 `message` 改英文会直接改变 Skill 教给模型读的内容，这是给模型的文字，要和 ADR 决策 4 一起定，不能在 t04 实施时顺手改。“程序只按码分支”若没有机检，写完一轮之后新代码又会按文字分支（M8 的 `message.includes(path)` 就是这么来的）。

### 2. “字符串槽一律改英文诊断”与 ADR 决策 4 的“给模型的失败文字新写用中文”冲突，计划没有裁决
- 严重程度：重要
- 类别：合同矛盾 / 架构取舍没讲
- 位置：plan.md:27（字符串槽）、plan.md:37（M5、M11 行）；ADR 0034 决策 4 “基础设施提示词（system reminder、工具说明、工具失败结果）：新写的用中文”；channel-matrix.md:518-523（M11 “同一份文字两个读者”）
- 现象：领域工具失败时，`content.text` 同时是模型读的工具结果和界面显示的 `call.error`。plan 的 M5/M11 只说 “`details` 给 `{code, params}`，界面优先读 `details.code`，`message` 只作详情”，没说 `content.text` 本身用什么语言。按总则第 27 行 “`reason`、`message`、`detail` 改为英文诊断”，它会变英文；按 ADR 决策 4，它是工具失败结果，新写的应是中文。`chapter_limit` 的 “没读：” 前缀（`read-ledger.ts:90-96`）就是这个槽里的文字被当成数据用的实例。
- 为什么是问题：一旦各片各自定，同一类字段会出现两种语言，而且此时已经有 `readRefused` 一类按文字判断的代码。模型看到的失败说明从中文变英文，属于 ADR 决策 4 里“评测之前不动”的范围（t05 已搁置）。
- 如何核实：读 ADR 0034 决策 4 与 plan.md:27、37；`nb-story/src/qa/tools.ts:72-74,105-114,137-143`。
- 建议改法：提案里明确一条：模型可见的工具结果文字不属于“字符串槽改英文”，保持现状或新写用中文，界面从 `details.code` 取文案；“字符串槽改英文”只对界面不当主文案的 `reason/detail/message` 生效。

### 3. 待定项 2（nb-story 网页跟随浏览器语言）要给一个本来单语的应用造语言体系，是现在不需要的东西
- 严重程度：建议
- 类别：YAGNI
- 位置：plan.md:41（M9）、plan.md:88（待定项 2）；`nb-story/src/web/pages/QaPage.vue:523,535,579`、`shell/SettingsPage.vue:385,407`（`locale="zh-CN"` 写死）
- 现象：nb-story 网页目前整页是写死的中文（共享组件的 `locale` 都传字面量 `"zh-CN"`），没有语言来源。推荐项是 “跟随浏览器语言，用与应用相同的文字表写法”。
- 为什么是问题：只为失败文案造一套语言选择，页面其余部分仍是中文，英文浏览器上看到的是一半英文一半中文。README 与矩阵都写了 nb-story 后接插件（`novel-story-app.md`：先独立服务、后接插件）；接插件之后语言应由宿主给，现在做的浏览器语言探测届时要拆。
- 如何核实：`grep -n 'locale=' packages/nb-story/src/web -r`。
- 建议改法：推荐改为 “nb-story 网页保持单语 zh-CN，只做按码取表（不做语言选择）；接成插件时由宿主给语言”。M9 仍然成立（保留 `code` 与 `candidates`，页面按码查表）。待定项 1 同理但代价小：失败页 `FailurePage.vue:28-46` 已经是写死中文的固定标题与提示，真正变的只有 `reason` 进“详情”；按浏览器语言选一张两语小表可以，不选也可以，不阻塞。

### 4. 十几个域各自重造 `{code, params}`，没有共用的最小类型、上限和渲染兜底，“有上限、不含凭据”无人执行
- 严重程度：重要
- 类别：重复实现 / 提前锁死
- 位置：plan.md:23（投影值“不新增全局错误对象”）、plan.md:25（渲染）、plan.md:26（未知码）、plan.md:38（四份 `entryReason` 合一）、plan.md:42（M10 以 nb-form 为基线）
- 现象：ADR 决策 2 否决的是“把各域合同统一成一个形状”，计划把它推到了“连最小共用件都不要”。结果是命令、文件、设置、存储、项目、插件、Agent、QA、nbdev、nb-story、nb-form 各自定义 `params` 的形状、大小上限、脱敏规则和未知码兜底。现状已有这种重复的证据：`explorer/web/feedback-text.ts:36-39` 的 `reasonText` 把未知码拼成 `码：detail`，plan 要消灭的正是这类写法，而这类函数在各域都有（矩阵 M3 列了约八个域），M6 的 `entryReason` 重复了四份。
- 为什么是问题：这个计划自己在 plan.md:23 要求 params “结构化、有上限、不含凭据与大正文”，却没有任何一个地方执行它；没有共用的类型，t04 的十几片就会各写一份校验、各写一份“未知码显示通用说明加码”的渲染。业界同类做法也是有共用小件的：Google AIP-193 的 `ErrorInfo` 固定 `{reason, domain, metadata}` 三元组，`domain` 对应这里的拥有者，`reason` 对应码，`metadata` 对应 params，各服务不自造形状（https://google.aip.dev/193）。本计划的“拥有者加码加参数”与它同构，但缺它的“共用类型”这一半。
- 如何核实：数 matrix M3 列出的域（FilesResult、设置、插件、Storage、项目、nbdev、Story、Agent）和 `entryReason` 四份位置（matrix.md:487）。
- 建议改法：提案加一节 “共用小件”：只含 `FailureParams` 类型（值限 string/number/boolean，键数与长度上限）、一个 `describeFailure(table, owner, code, params)`（未知码兜底、详情折叠都在这里）、一个 `describeUnknown`（M7 已有）。放哪个包由提案定（`nb-runtime` 前后端共用，依赖只有 TypeBox，可放；共享 Vue 包不能依赖它，沿用端口）。各域合同仍保留自己的外壳，不违背 ADR 决策 2。与 w00028 README 里的 `{key, params}` 的关系也在此写明：投影值就是 `{key: "<owner>:errors.<code>", params}` 的一个特例。

### 5. 先于 w00028 固定键的写法，且让 t04 先做一遍 `LocalizedText` 表再由 w00028 搬一遍
- 严重程度：重要
- 类别：返工 / 难回头
- 位置：plan.md:11（依赖）、plan.md:24（消息键 `<拥有者>:errors.<code>`）、plan.md:25（`Record<码, 文字>`）；w00028 README “方向”最后一条；w00028 t01 状态“未开工”
- 现象：计划承认 w00028 的目录机制还没设计，却在 t03 里钉死键格式 `<拥有者>:errors.<code>`，并要求 t04 的每一片“沿用各拥有者现有的 LocalizedText 表”实现，等 w00028 t03 “一并搬进目录”。w00028 t01 还要定键规则、命名空间分隔、回退链、复数。
- 为什么是问题：t04 要改约 1000 个抛出点、几十张码表（t04 README 粗估）；如果这些表先以 `{zh-CN, en-US}` 内联落地，w00028 t03 又要把它们全部抽进 JSON 目录，等于同一批文字迁移两次，且 ADR 决策 3 自己写了“约 1100 条内联文字要迁移”。键格式如果和 w00028 t01 的结论不一致（例如 i18next 默认 `ns:key`，插件 id 本身带点；码里的连字符），已经改过的 t04 片要再改一遍。

### 6. “诊断改英文”的推进方式没讲：全量一次做，还是碰到就改，与“失败投影”绑在同一份提案里
- 严重程度：重要
- 类别：架构取舍没讲 / 范围
- 位置：plan.md:27（字符串槽）、plan.md:36（M3、M14 所有域 `detail` 英文）、plan.md:56-58（切片）；t04 README “粗估规模”（带中文的 `new XxxError` 约 1035 处、日志诊断约 211 处、`reason/message/detail` 约 791 处、断言中文的测试约 369 个文件）；ADR 0034 决策 1 “迁移之前中文诊断保持原样，新写的用英文”
- 现象：两件性质不同的事被放进同一个提案、同一组切片：一是“跨到界面的失败改成码加参数”（合同变化，必须设计）；二是“开发诊断翻成英文”（机械翻译，没有行为变化）。计划只给了前者的设计，对后者只在总则里一句话带过，没说是否要把 1000 多处全部翻掉、翻到什么时候、用什么判据确认完成。ADR 决策 1 的理由只涉及“日志里混两种语言、搜不到同一串文字”，且已经允许“新写的用英文”。
- 为什么是问题：t04 的体量和风险几乎全部来自第二件事（369 个测试文件、20.7 万行代码范围），而它对用户可观察行为几乎没有影响。把它与合同变更绑定到每个切片里，会让每一片都变成“改合同 + 翻译 + 改测试”的大包，审查和回滚都难。矩阵 M17 本身也警告了断言整批失败。
- 如何核实：t04 README 的规模数；plan.md 全文没有“按需”“顺手”“批量”之类对翻译策略的说明。
- 建议改法：提案里把两件事分开写：第一类（跨到界面的失败）按切片做，必须有 Spec 和消费者验收；第二类写成规则 “碰到哪个文件就把它的诊断改英文，新写的必须英文”，加一个机检（呼应第 1 条）统计新增的含汉字的诊断构造，不设全量完成日期；是否需要一次性全量翻译，作为单独的待定项交开发者，并附上规模数。

### 7. 对旧数据的处理自相矛盾：保留“旧的中文前缀判断”，却违背 README 的“不按旧文案猜码”
- 严重程度：建议
- 类别：自相矛盾 / 永久遗留代码
- 位置：plan.md:37（“旧的中文前缀判断只留给旧日志”）；t03 README “目标与范围”：“旧持久化数据怎么读；不按旧文案猜码”；`nb-story/src/qa/read-ledger.ts:90-96`（`startsWith("没读：")`）
- 现象：README 把“不按旧文案猜码”写成原则，plan 却为旧日志保留中文前缀判断，且没有写何时删除。
- 为什么是问题：旧日志是用户数据，`readRefused` 之类的判断会一直留着，并且要求以后任何人改动中文前缀措辞都不能动那几个字，这正是 ADR 要消除的耦合。保留它换来的只是旧日志里“已读章数”这一个展示数字。
- 如何核实：`grep -rn '没读：' packages/nb-story/src`。
- 建议改法：旧日志没有码时，按 kind 取通用文案并且“已读章数”标为“未知”或不显示，不再判断前缀；如果开发者认为旧日志的章数必须保留，则在提案里写成明确的、带删除条件的兼容分支，并说明判据（例如“只对没有 `details.code` 的条目”，且不再扩展）。

### 8. 线协议版本的升级理由写窄了，也没说清楚谁来升、升几次
- 严重程度：建议
- 类别：合同细节缺口 / 次序风险
- 位置：plan.md:43（M12）、plan.md:35（M2）、plan.md:58（“窗口与握手（M2，含线协议版本）”）；`nb-runtime/src/remote/protocol.ts:13-21`、`protocol.ts:304-307`
- 现象：plan 写 “闭合 schema 的线协议帧加字段要升 `WIRE_PROTOCOL_VERSION`”，同时 M2 说握手 `reject` 保留阶段码、只把 `message` 改英文。但 `protocol.ts:13-21` 注释明确写了：`reject` 帧的形状跨版本不变，帧形状不变而“含义变化”时也升版本（版本 4 就是这样升的），并且浏览器首次握手前没有别的同构建核对，只有这个常量能拦住旧页面。也就是说：(1) 只改 `message` 的语言不需要升；(2) 业务合同 `detail` 加 `params`（plan 让“各合同拥有者改”）本身也可能需要升，因为旧页面会按旧 schema 读新服务端的结果；plan 却只把它归在 M2 一片里。
- 为什么是问题：t04 分了十几片，若每片改一份业务合同的结果就各自升一次，每次合入都会让所有已打开的页面报“不兼容，请刷新”；若只在 M2 一片升，其它片先于它合入就没拦住旧页面。
- 如何核实：读 `protocol.ts:13-21` 的注释；对比 plan.md:43。
- 建议改法：提案写一条升版规则：“凡是改变远程结果的形状或码含义的，该片合入时升；同一发布窗口内多片合并只升一次”，并把升版动作放在切片清单的一个固定片里，其它片在 Spec 里写“依赖该片”。

### 9. 计划与 ADR 对“谁改 Spec”的分工不一致，且提案之外还留一道门

- 类别：流程一致性

## 回答五个问题的汇总
