### 1. 普通 button 不会产生高亮属性，右键菜单与手工级联菜单仍无高亮

- **严重程度：重要；类别：正确性。**
- **位置：** `plan.md:22,29,32`；`packages/nb-ui/src/components/controls/MenuNodes.vue:57-66,92-108`；`feedback/ContextMenuPanel.vue:99-125`；`controls/Menubar.vue:128-138`。
- **现象：** 计划只为 QuickPick 与候选菜单规定手动设置 `data-highlighted`，把其它菜单都当成 reka 项。实际上 ContextMenu 的根级、全部级联，以及 Menubar、DropdownMenu 的手工级联都没有传 `itemComponent`，落到普通 button 分支。该分支既不设置高亮属性，也不在悬停时聚焦。只替换类名并移除 `:hover`，这些菜单的鼠标和键盘高亮都不会出现。
- **为什么是问题：** 违反决定 1；计划声称“由此有了高亮”，但缺的是状态生产者，不是底色。`active` 当前只表示展开子菜单的父项，普通叶子项悬停时发出的值是 null，不能用它代替当前高亮。
- **如何核实：** 已逐行读取安装的 `node_modules/reka-ui/src/Menu/MenuItemImpl.vue:35-51,84-103`（pointermove 写 highlightedElement，focus/blur 驱动属性）、`Menubar/MenubarItem.vue:20-24`（转发 MenuItem）、`Select/SelectItem.vue:92-103,161-177`（悬停聚焦后才挂属性）。反查 MenuNodes 的原生分支没有这些机制。此项为代码已核实，未运行浏览器。
- **建议改法：** 给原生菜单路径明确的单一高亮状态与 pointer/focus 更新规则，跳过禁用项；与级联展开状态分开。验收要分根级与子级，不只测 reka 一级项。

### 2. 固定 28px 乘法无法兑现混合列表的“第 9 项半”，且没有区分表面高度与滚动视口高度

- **严重程度：重要；类别：正确性。**
- **位置：** `plan.md:14-16,24,33,37,81`；`packages/nb-ui/src/components/controls/MenuNodes.vue:72`；`feedback/QuickPick.vue:335-345`；`form/Select.vue:208-213`。
- **现象：** 公式得到 nbook 总高 `8.5×28+2×4=246px`，但滚动区域应为 238px；若照第 4 节把 246px 作为 viewport 的 max-height，再加外层 padding，会显示 8.786 行而不是 8.5 行。即使正确扣除外层 padding，分组标题、分隔线与两行项仍使固定乘法失效：现有分隔线占 `4+1+4=9px`，一条分隔线放在前 8 项中，就只露出第 9 个可选项的 5px，而非 14px；两条分隔线后，238px 的截断线甚至落在第 8 个可选项内。全部为 48px 的 QuickPick 两行项时，238px 只够 4 项加第 5 项的 46px。
- **为什么是问题：** 决定 4 已明确两行项另算，决定 5 又要求所有列表共用“最多 8 项半”的计算。方案没有定义混合高度的计数对象、装饰行处理、截断目标，也没有说明 size 收矮的是整个面板还是列表、header/loading 占高是否先扣除。照字面写会产生互不相容的实现与测试。
- **如何核实：** 已对照上述实际结构与高度、`PromptMenuPanel.vue:91-115` 的组标题/加载行，以及 `useDropdownFloating.ts:75-78` 目前把高度直接绑定 viewport 的调用链；数字为几何推导，尚未做浏览器测量。
- **建议改法：** 明确两层预算：整个浮层按可用空间夹紧，先扣 border/padding/header 等固定部分，再限制唯一滚动视口。按实际可选项的盒子求第 9 项中点（计入它前面的标题与分隔线），两行/换行项也复用该算法；空间更小则允许不截半，优先可见性。若只承诺 238px 像素上限，需明确这不能等价为已定的混合列表 8.5 项，并取得对应取舍。

### 3. autoUpdate 不会自动追踪“返回矩形的函数”，虚拟光标锚点会停在旧位置

- **严重程度：重要；类别：正确性 / 不变量。**
- **位置：** `plan.md:44-45,47,84`；`node_modules/@floating-ui/dom/dist/floating-ui.dom.mjs:27-29,621-689`。
- **现象：** 计划只给 `anchor` 一个矩形 getter，却把“锚点变化时重新定位”交给默认 autoUpdate。安装实现默认 `animationFrame=false`；它只从真实元素或虚拟元素的 `contextElement` 收集滚动祖先、ResizeObserver 与 IntersectionObserver。光标在同一编辑器内因打字/方向键移动时，不要求编辑器或菜单 resize，getter 返回值变化也不是 DOM 事件。getter 没有 `contextElement` 时，菜单若传送到 body，还收不到编辑器内部滚动祖先的事件。
- **为什么是问题：** 这是新组件承诺的核心定位能力，不是 floating-ui 选型的问题。当前 anchor 类型没有表达虚拟锚点所属元素，计划也没有规定宿主主动请求更新或启用矩形轮询的机制。第 84 行只测窗口缩放，抓不到同一元素内的光标移动。
- **如何核实：** 已读取实际依赖 autoUpdate：633 行只收集 referenceEl/floating 的祖先；638、656 行只观察 referenceEl；664-675 行只有显式 animationFrame 才重读虚拟矩形。677-688 行返回清理函数，必须由使用方调用。此项为依赖实现核实，未进行真实编辑器运行。
- **建议改法：** 把虚拟 anchor 定为 `{getBoundingClientRect, contextElement}`，并明确光标矩形变化的更新通道（宿主更新版本/显式 update，或仅在打开期间启用 animationFrame）。挂载后建立订阅，anchor/菜单元素变化先清理旧订阅，关闭和卸载均清理；异步 computePosition 结果也需失效保护。验收覆盖编辑器内滚动、光标移动、换锚点与卸载后不再更新。

### 5. shift 不能缩窄面板，96px 高度下限又可能压过真实可用空间

- **严重程度：重要；类别：正确性 / 边界。**
- **位置：** `plan.md:7,44-45,47,84`；`node_modules/@floating-ui/core/dist/floating-ui.core.mjs:817-879,964-1034`。
- **现象：** 计划只让 shift“左右夹进窗口”，size 只处理高度，没有面板宽度上限。390px 视口留两侧 12px 后最多容纳 366px；若 `matchAnchorWidth` 的锚点宽 390px，或长内容的固有宽度超过 366px，平移不可能同时满足左右边界。高度同样未定冲突优先级：选定方向仅剩 60px 时，`max(96, availableHeight)` 仍会越界至少 36px。Composer 又要求固定方向，不允许借翻转消除此冲突。
- **为什么是问题：** 直接违背“左右不出窗口”“空间不够时收矮”的验收；只调用 size 不会自动改样式，其默认 apply 是空函数。要求的 96px 应保留为正常情况下的下限，但必须定义容器/窗口连 96px 都容不下时怎么办，不能留下相互矛盾的承诺。
- **如何核实：** 已读取依赖：shift 只算 x/y 位移；size 只向 apply 提供 availableWidth/availableHeight（979 行默认空操作），尺寸由使用方施加。旧参照有默认宽度、最小宽度与视口收敛规则，而新接口与布局没有对应规则。上述为算法和数值核实，未做浏览器几何实验。
- **建议改法：** size 同时约束 border-box 最大宽度与高度，明确 matchAnchorWidth 遇到更窄边界时的优先级，长 label/hint 允许收缩截断。为不足 96px 的极端空间规定显式退让策略（例如允许跨轴移位并覆盖锚点，或把硬边界置于下限之前）；补固定方向、窄锚点、超宽锚点和小于 96px 可用高度的真实布局验收。

### 7. 用一个 header 插槽替换历史搜索框，漏掉焦点、组合输入与 ARIA 的迁移合同

- **现象：** 计划把“菜单不接焦点、按下鼠标 preventDefault”写成整体规则，但输入历史必须把焦点主动移到 header 内的搜索框。原有链条是 Ctrl+R → nextTick → focusSearch；搜索框自己声明 combobox、controls 与 active descendant，方向键/Enter/Escape 交给宿主。删掉面板后，header 插槽不会自动继承这些行为；若 preventDefault 放在外框而不是项列表，点击搜索框与移动插入点也会被阻止。若新菜单 Teleport，旧包裹 div 上 `focusout` 的 DOM contains 判断也不能直接照搬。

- **建议改法：** 明确 header 可以正常接收焦点，preventDefault 只限候选项/非交互区；搜索 input 的 ref、进入/退出焦点、keydown 与 ARIA 由 Composer 持有。定义 header 如何取得统一的 option DOM id 映射、如何判定整个浮层的失焦；保留标题、description→hint 与可本地化 loading/empty 说明。验收补输出 10、12，覆盖 Ctrl+R 直接打字、过滤、方向键、确认/Escape、点击搜索框及外点关闭。

### 8. 新增父级滚动后，已展开级联菜单的锚点与显式 height 没有更新协议

- **严重程度：重要；类别：不变量 / 正确性。**
- **位置：** `plan.md:32,35-38,69,81-82`；`packages/nb-ui/src/composables/useMenuCascade.ts:22-43`；`components/feedback/menu-cascade.ts:92-109`。
- **现象：** 计划只要求 ContextMenuPanel/Menubar 接上滚动件；现有级联面板却只在 open/switch 时量父项一次，写入固定 top/left/width/height。父级变成可滚动后，滚轮或拖滑块会移动展开它的那一行，已打开的子面板不会跟随，也没有“父项离开视口时收起”的规则。现有测量直接取 `.nb-menu-level-content` 的 rect 加 padding；如果为截断而另外包 viewport，它就仍可能拿到未截断的内容高度，并把这个高度显式写回外框。
- **为什么是问题：** 这是本次给 Menubar/ContextMenu 新增滚动带来的耦合，不是滚动条外观问题。它破坏“第一项与父项同一行”的既有级联合同。多级面板还必须各自拥有 viewport、滑块、遮罩与可用空间预算，不能把“六处接上”理解为每个菜单根只建一份滚动状态。
- **如何核实：** 已读取 useMenuCascade 的唯一测量时点、measureCascadePanel 的选取对象，以及 Menubar/ContextMenuPanel 的 v-for 多级结构；未见滚动后重定位入口。此项为代码推断的新集成风险，未运行滚动中的级联菜单。
- **建议改法：** 先定义父级滚动时子级是重定位还是关闭，并将该事件接入 cascade；测量与最终高度应使用受约束后的表面几何。用内部可滚动面板零件让每一级拥有独立 usePopupScroll 实例。验收覆盖两级以上长列表、父级滚轮与拖滑块、父项滚出可见区、同级替换短/长内容。

### 9. 分组后的 option id 下标没有定义，Composer 现有 ARIA 与键盘顺序依赖全局扁平下标

- **严重程度：重要；类别：接口 / 可访问性。**
- **位置：** `plan.md:44,51,86`；`packages/neuro-book/src/plugins/markdown/web/components/prompt/PromptEditor.vue:366-380,876-881`；`PromptMenuPanel.vue:38-43,91-99`。
- **现象：** 新组件接收 groups，却把每项 DOM id 定为 `${id}-${index}`，没有规定 index 是组内下标还是所有可选项的全局下标，也没规定标题/状态行是否计数、项 id 是否跨组唯一。两个组各有第 0 项时，按自然的内层 v-for 写法会产生两个相同 DOM id。Composer 当前按原始 menu.items 的扁平下标填写 aria-activedescendant，方向键也沿该顺序移动；旧面板只把相邻相同 group 合成标题，不会把不相邻同名组重新归并。
- **为什么是问题：** 新数据模型没有给迁移者一条能保证“焦点元素指向实际高亮 option”的确定规则。若把 `A组a、B组b、A组c` 按组名聚合成 `a,c,b`，键盘仍在原顺序，读屏关联与视觉顺序就分离。单组正常输入的验收抓不到它。
- **如何核实：** 已对照旧 rows 的全局 index、旧 header 的相邻判断与宿主 aria 的原始数组 findIndex；这是接口歧义与明确的错误实现路径，未把它描述成已运行的新组件故障。
- **建议改法：** 保留已定组件名，补充全局 item id 唯一约束与规范化顺序：各组按输入顺序展开，DOM 下标仅计可选项、跨组累计；Composer 只切分连续组段，不重排。更简单的替代是提供由稳定 item id 生成 DOM id 的公共纯函数，宿主与组件共用。覆盖多组、重复组标题、禁用项、过滤后下标改变及 activeId 不存在时清除引用。

### 11. 滚动合并没有覆盖动态内容、缩放拖动与 Select 的初始化时序，沿用旧逻辑会留下错误滑块

- **严重程度：重要；类别：不变量 / 结构。**
- **位置：** `plan.md:35-38,46,81-82`；`packages/nb-ui/src/composables/useFloatingScrollbar.ts:36-74,97-107`；`node_modules/reka-ui/src/Select/SelectContentImpl.vue:124-131`。
- **现象：** 新接口只写 `usePopupScroll(viewport,{maxRows?})`，没有列出内容变化与缩放时的几何更新合同。旧逻辑只 ResizeObserver.observe(viewport)，并不观察内容；固定高度列表已经溢出后，异步追加/过滤候选或同级子菜单内容替换，viewport 的 clientHeight 可以完全不变，而 scrollHeight 已变，滑块长度与触底遮罩就不会立即同步。拖动则直接把 clientY 位移除以布局单位 clientHeight，两者在 Lab zoom 不为 1 或 transform 缩放期间不是同一单位。
- **为什么是问题：** 新合并范围把异步 SuggestionMenu、搜索 QuickPick、多级复用面板都接进旧方案，动态内容不是异常用法。Select 还有独立的“定位完成后聚焦选中项”顺序：若共享逻辑挂载时重置/抢先 reveal，可能覆盖打开时的选中位置；若在新外层滚动而不是原 SelectViewport 滚动，又会与上游焦点滚动分成两个所有者。计划未选定所有权与同步时点，验收也没有这些输入。
- **如何核实：** 已读取旧 ResizeObserver 只观察 domEl、thumb 的 clientY/clientHeight 运算，以及安装的 SelectViewport（`position:relative; flex:1; overflow:hidden auto`）、SelectContentImpl 的 isPositioned→focusSelectedItem。**没有证据证明目前 popper 模式会持续改写视口高度**：SelectViewport 的扩高逻辑只在 item-aligned 上下文存在时运行；不能把该分支误报成本次 Select 必然冲突。缩放拖动与新异步组件尚未跑真实布局，列为计划缺失的边界，不声称已复现回归。
- **建议改法：** 共享件仅控制现有唯一 viewport，尤其保留 SelectViewport 的滚动所有权，不在初始化无条件重置 scrollTop。明确内容尺寸/列表数据变化后的同步、面板实例更换时重绑与拖动结束/卸载清理；轨道与指针使用一致坐标单位。验收覆盖 Select 打开到第 20 个选中项、方向键后滚动、已溢出列表追加/过滤且 activeId 不变、缩放画布内拖到两端，以及关闭重开。
