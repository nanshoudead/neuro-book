# w00029 nb-ui 作为 UI 库的实现审查报告

说明：条目按核实顺序追加，编号 L01 起；按影响排序的索引与整改顺序在文末。所有数字均为本次核实时 `grep` / 读文件所得（2026-10-20，master）。

### L01 [重要][耦合] `dist/nb-ui.css` 带着 ~450 条无层的 Tailwind 原子类，与调用方自己的原子 CSS 同名竞争，同一个 nb-ui 组件在不同宿主里渲染不同

- **位置**：`packages/nb-ui/src/tailwind.css:1-30`（三条“刻意取舍”）；`packages/nb-ui/dist/nb-ui.css:3`、`:1138`（`.text-sm`）、`:1913`（`:root` token）；`packages/neuro-book/src/web/boot.ts:7-12`（样式顺序注释）；`packages/neuro-book/uno.config.ts:7-31`（blocklist 补丁）；`packages/nb-story/src/web/app.css:1-6`、`packages/dev-panel/src/web/app.css:1-6`（同款迁就）。
- **现象**：
  1. 产物里有约 453 条 `.xxx { }` 原子类规则（`.flex`、`.hidden`、`.text-sm`、`.rounded`、`.shadow-lg` 等），全部不在 `@layer` 里（`grep -c "@layer"` 只有两处，都是 Tailwind 的 `properties`）。这是为了“让 UnoCSS 消费方也能吃”（`tailwind.css:10-15`）。
  2. 调用方因此反过来迁就 nb-ui：neuro-book 用 `uno.config.ts` 读 nb-ui 的 css、正则抽出所有 `translate/scale/rotate/skew` 类名做 `blocklist`（否则位移翻倍：Switch 滑块溢出轨道、chevron 转 360°）；nb-story、dev-panel 为了不被 nb-ui 的 `.flex` 压过，被迫放弃 `@import "tailwindcss"` 的 `@layer utilities`，手拆成 preflight 进 layer、utilities 不进 layer；`boot.ts` 的导入顺序注释里写了“UnoCSS 在 nb-ui 之后，否则 nb-ui 的 `i-lucide-*` 规则盖掉图标遮罩”。已知的 `i-lucide-* width:1em` 那一例就是这套机制的又一个后果（t04 后的坑 58），不是孤例。
  3. 语义不同的同名类：nb-ui 组件模板里直接写 `text-sm`（`IconButton.vue:45`、`Table.vue:69`、`EmptyState.vue:20`、`Notification.vue:53,70`、`Textarea.vue:50` 等 8 处）、`shadow-lg`（`Notification.vue:53`）。nb-ui.css 里 `.text-sm` 是 `font-size: var(--text-sm)`（= tokens 的 13px，因 `tokens.css` 的 `:root` 在同一文件里排在 Tailwind `@theme` 的 `:root` 之后，覆盖了 Tailwind 的 `--text-sm: 0.875rem`），而 neuro-book 的 UnoCSS（`presetWind3`）里 `.text-sm` 是 `0.875rem / 1.25rem`（14px），并且 `virtual:uno.css` 排在 nb-ui.css 之后，neuro-book 自己用了 58 处 `text-sm`，所以这个类一定会生成并盖掉 nb-ui 的。结果：IconButton / EmptyState / Table / Notification / Textarea 在 neuro-book 里是 14px，在 playground 与 nb-story（Tailwind）里是 13px，同一组件的字号随宿主原子 CSS 引擎而变。同理 `leading-tight`（token 1.3 对 Uno 1.25）、`font-mono`（token 栈对 Uno 栈）。
- **为什么是问题**：库的外观合同依赖于“宿主的原子 CSS 引擎碰巧不产出同名类、或碰巧排在前面”。每加一个宿主（第三个包），就要重新发现一遍“有哪些类同名、谁盖谁”，补丁散在宿主里（uno blocklist、app.css 注释），库自己无法保证渲染一致；nb-ui 的内部写法（用 Tailwind 原子类）被迫变成了公开 CSS 面。
- **如何核实**：`grep -c "^\.[a-z]" packages/nb-ui/dist/nb-ui.css`；`sed -n 1138,1145p dist/nb-ui.css`；在 neuro-book 开发页里看 `IconButton` 计算后的 `font-size`（从代码推断，未在浏览器验证，但 `boot.ts` 的导入顺序与 Uno 的 `text-sm` 定义是确定的）。
- **建议改法**：目标形状是“产物只含 nb-ui 自己的类”。(a) 组件模板里的结构性原子类改成 `.nb-ui-*` 语义类或 Vue `<style>`/`@apply` 编出的有前缀类（Tailwind v4 支持 `@import "tailwindcss/utilities.css" prefix(nb)`，把产物里所有原子类变成 `nb:flex` 这种有前缀的类，宿主零冲突，`uno.config.ts` 的 blocklist 与两个 app.css 的迁就全部删除）；(b) 把整个产物包进 `@layer nb-ui`，宿主任何无层规则或自己的层都能覆盖，不再需要“排在后面”的约定。(a) 比 (b) 更彻底；(b) 一条改动就解决 i-lucide width 与层序，但无层的宿主 CSS 会压过库样式，需要把 `.nb-ui-control-invalid` 这类依赖特异性的规则（`tailwind.css:10-15` 说的）一起检视。两者择一即可，不要两者并存。

### L02 [建议][可维护性] `src/styles.css` 里至少 8 组样式没有任何使用方（死 CSS），并带着旧应用的业务词；且无条件覆盖宿主页面的 `html`

- **位置**：`packages/nb-ui/src/styles.css:6-8`（`html { scrollbar-gutter: stable }`）；`:630-638`（`.animate-accordion-*` / `.animate-collapsible-*`，带 `nb-accordion-content`）；`:717-731`（`.nb-crystal-glow`）；`:733-747`（`.nb-pop-in`）；`:749-764`（`.scheme-fade-*`）；`:778-796`（`.nb-ui-switch-*`，注释里写“设置外壳的区段、Provider 导轨→详情、Agent Profile 的 Profile 切换”）；`:14-16`（`.nb-ui-scrollbar-center`）；`:68`（`.nb-ui-control-h-lg`）；`:407-413` 里的 `.nb-popover-enter-active` / `-leave-active` 选择器。
- **现象**：对 `packages/nb-ui/{src,themes}`、`packages/neuro-book/src`、`packages/nb-story/src`、`packages/dev-panel/src` 逐名 `grep`（排除 styles.css 自己与 `.md`），`scheme-fade`、`nb-crystal-glow`、`nb-pop-in`、`animate-accordion`、`animate-collapsible`、`nb-ui-switch-enter`、`nb-ui-scrollbar-center`、`nb-ui-control-h-lg`、`nb-popover-enter-active` 均 0 处使用；`nb-accordion-content` 在库里没有 Accordion 组件，只剩 Collapsible 的 `nb-collapsible-content`。`.nb-ui-switch-*` 的注释指向的是旧应用的界面（设置外壳、Provider 导轨、Agent Profile），这是库里残留的业务概念。`html { scrollbar-gutter: stable }` 对任何 `import styles.css` 的宿主页面生效，不是组件作用域内的规则。
- **为什么是问题**：死规则进了公开产物（影响 `dist/nb-ui.css` 体积与阅读），而且 `README.md` 与 `ui-development-spec.md` 把它们当作“全库微物理动效”登记，调用方会以为能用。全局 `html` 规则会让不需要稳定滚动条槽位的宿主（如全屏画布）无法关掉。
- **如何核实**：`for c in scheme-fade nb-crystal-glow nb-pop-in animate-accordion nb-ui-switch-enter nb-ui-scrollbar-center nb-ui-control-h-lg; do grep -rln -- "$c" packages/*/src packages/nb-ui/themes | grep -v styles.css; done` 全空。
- **建议改法**：删除上述死规则与对应关键帧（净删约 90 行）；`html { scrollbar-gutter }` 删掉，保留 `.nb-ui-scrollbar-stable` 让宿主自己挂到根上（dev-panel 已经这么用，`dev-panel/src/web/app.css`）。

### L03 [重要][复用] 级联菜单的键盘与“滚动收起子级”逻辑在三个入口各写一遍，`useMenuCascade` 自称“三个菜单入口共用”实际只被两个完整使用

- **位置**：`packages/nb-ui/src/composables/useMenuCascade.ts:69-113`（`levelKeydown`）与 `:60-66`（`focusNewLevel` 监听）；`packages/nb-ui/src/components/feedback/ContextMenuPanel.vue:24-33`（`collapseBelow`）、`:44-100`（整套 `onKeydown` + `focusNewLevel` + `itemsIn`）；`packages/nb-ui/src/components/controls/DropdownMenu.vue:91-95,121-131`；`packages/nb-ui/src/components/controls/Menubar.vue:104-117`。
- **现象**：
  1. `collapseBelow(depth)`（“第 depth 级滚动了：收起更深层，焦点在被收起的层里就回到展开它的那一项”）函数体在 DropdownMenu、Menubar、ContextMenuPanel 里各一份，共 3 份，只在“怎么找到展开它的那一项”那一行不同。
  2. “reka 一级菜单里，键盘在父项上展开子菜单则预约把焦点移进新一级”（`aria-haspopup === "menu" && ["ArrowRight","Enter"," "].includes(key)` → `cascade.expectKeyboardOpen()`）：DropdownMenu 与 Menubar 逐字相同（两份），`useMenuCascade.levelKeydown` 与 ContextMenuPanel 里又各有一份同条件判断，共 4 处。
  3. `useMenuCascade.levelKeydown`（ArrowDown/Up/Home/End 循环移动、ArrowLeft 收起并还焦点、ArrowRight 预约焦点）与 `ContextMenuPanel.onKeydown`（同样的 switch，同样的循环取模、同样的 `focusNewLevel` 监听）是同一套逻辑的两份拷贝；`useMenuCascade` 的文件头注释写“三个菜单入口共用”，但右键菜单只用了它的 `levels/schedule/truncate` 状态部分，键盘部分自己又写了一遍。原因是右键菜单的第 0 级不是 `MenuLevelPanel` 而是 `role="menu"` 根，`levelKeydown` 要求 `panels[depth]` 存在。
  4. 把 ref 解包成元素的写法 `element && typeof element === "object" && "$el" in element ? element.$el : element` 在 5 处各写一遍：`DropdownMenu.vue:99,106`、`ContextMenu.vue:83`、`usePopupScroll.ts:170`、`useMenuCascade.ts:118`。
- **为什么是问题**：菜单键盘合同（ARIA menu 模式）是最容易出细微差别的地方；两份拷贝已经在细节上分叉：`levelKeydown` 的 ArrowRight 分支同时认 Enter/空格，ContextMenuPanel 的只认 ArrowRight；ArrowLeft 找展开项用 `[aria-expanded='true']`，ContextMenuPanel 版带 `:scope >`。以后改一处（例如加 typeahead），另两处不会跟。
- **如何核实**：对比 `useMenuCascade.ts:69-113` 与 `ContextMenuPanel.vue:44-100`；`grep -n collapseBelow packages/nb-ui/src -r`（3 个文件）。
- **建议改法**：让 `useMenuCascade` 把“第 0 级容器”作为参数（`rootPanel: () => HTMLElement | null`，ContextMenu 传 `role="menu"` 根，DropdownMenu/Menubar 传 reka 内容），`levelKeydown` 与 `collapseBelow(depth)` 都收进 composable，三个入口只调用；`ContextMenuPanel` 的 `onKeydown` 整段删掉（约 60 行），`DropdownMenu`/`Menubar` 的 `collapseBelow`、`onContentKeydown` 删掉。`$el` 解包抽成 `utils` 里的一个 `elementOf(ref)`。

### L04 [重要][复用][API 形状] 弹出列表的“一行”只共用了 CSS，行的标记与数据形状在 6 个组件里各自拼；同一个概念有 6 套字段名

- **位置**：`MenuNodes.vue:100-108` 与 `:125-133`（同一模板在“reka 项”和“普通按钮”两个分支里逐字复制）；`Select.vue:158-176`；`SuggestionMenu.vue:200-212`；`QuickPick.vue`（列表行，3 处引用 `nb-ui-menu-item__*`）；数据类型：`controls/dropdown-menu.types.ts`、`feedback/context-menu.types.ts`、`controls/Menubar.vue:14-27`、`form/Select.vue:30-40`、`feedback/QuickPick.vue:29-39`、`feedback/suggestion-menu.ts:6-16`。
- **现象**：
  1. `nb-ui-menu-item__check/__icon/__label/__hint` 这组类被 MenuNodes（8 处）、Select（5 处）、SuggestionMenu（3 处）、QuickPick（3 处）各自手写标记；“有一项带图标则其余项留空图标列”的 `iconColumn` 计算在 4 个组件里各写一遍（`MenuNodes.vue:31`、`SuggestionMenu.vue:79`、`QuickPick.vue:88`、`Select.vue:111`），“有可勾选项则留勾选列”只在 MenuNodes 算。
  2. 同样是“一行菜单项”，6 个数据类型的字段名不统一：右侧次要文字叫 `shortcut`（DropdownMenu、ContextMenu、Menubar、QuickPick）或 `hint`（SuggestionMenu）；第二行说明叫 `description`（Select、QuickPick）；标识叫 `value`（Dropdown、Menubar、Select）或 `id`（QuickPick、Suggestion）或根本没有（ContextMenu 用 `action` 回调）；勾选类型叫 `type: "item"|"radio"|"checkbox"`（Dropdown）、`"item"|"checkbox"`（ContextMenu）、`"default"|"checkbox"|"radio"`（Menubar，同样是“普通项”却是 `default` 而不是 `item`）；危险项 `tone: "default"|"danger"` 只有菜单类三个有。`MenuNodes` 为了吃下三种菜单项用泛型约束写了一个由 9 个可选字段拼成的“伪接口”（`generic="T extends {label?; title?; disabled?; ...}"`），等于承认没有共同类型。
  3. 把样式类塞进数据：`iconClass`（出现在 22 个组件文件里：Button、IconButton、Input、Dropdown、ContextMenu、Menubar、Select、QuickPick、Suggestion、Tree、Tabs、Segmented、ToggleGroup、Badge、Banner、Notification、EmptyState、Breadcrumb、DropFeedbackOverlay 等）、`rightIconClass`（Dropdown）、`indicatorClass`（Select，文档要求传 `bg-emerald-500` 这类 Tailwind/Uno 类名）。这让图标的生成责任落在调用方构建上（README 自己写了“调用方传的 iconClass 仍由调用方构建生成”），并且类名字符串无法被库校验或换图标集。
- **为什么是问题**：想给“再加一种弹出列表”（例如 mention 列表、历史下拉）的人没有可复用零件：既不能拿现成的“行”组件，也没有共同的 item 类型，只能抄第七份。调用方在不同列表之间切换数据要写适配（neuro-book 里确实有适配代码，见 L09）。`indicatorClass: "bg-emerald-500"` 把调用方的原子 CSS 引擎写进了公开数据。
- **如何核实**：`grep -rn "nb-ui-menu-item__label" packages/nb-ui/src --include=*.vue`；对比六个类型定义。
- **建议改法**：先抽一个内部行组件 `MenuRow.vue`（props：`label / description / hint / checked / icon / tone / disabled / multiline`，内部持有“勾选列/图标列”的占位逻辑，由父级一次性给 `checkColumn`、`iconColumn`），MenuNodes 的两个分支、Select、SuggestionMenu、QuickPick 都渲染它。数据层统一一个基础形状 `MenuEntry = {id, label, description?, hint?, icon?, tone?, disabled?}`，各组件在此基础上加自己独有的（children、group、labelMatches）；`shortcut` 与 `hint` 择一（建议 `hint`，因为它承载路径、说明而不只是快捷键）。`iconClass` 保留是合理取舍（Iconify 类名是行业通行），但 `indicatorClass` 改成 `tone`（`success|warning|danger|neutral`）由库映射到 token 色，不让调用方传色类。

### L05 [重要][API 形状] “浮层是否打开”在 11 个组件里有 5 种写法，“为什么关闭”的原因有 3 套互不相同的词表

- **位置**：`feedback/Dialog.vue:43`（`modelValue: boolean` 必填 + `request-close`）；`AlertDialog.vue:22`、`Drawer.vue:19`、`Popover.vue:18`、`DropdownMenu.vue:38`、`layout/Collapsible.vue:11`（可选 `open?` + `update:open`）；`QuickPick.vue:42`（必填 `open` + `update:open` + `close(reason)` + `closed`）；`ContextMenu.vue:11`（`visible` + `close(reason)`，没有 `update:visible`）；`Menubar.vue:39`（`modelValue?: string` 是当前打开的菜单 id）；`SuggestionMenu.vue`（没有打开态，`anchor !== null` 即打开）；`Tooltip.vue:49`（内部自管）。
- **现象**：
  1. 打开态：`modelValue`（Dialog）、`open`（5 个 + QuickPick）、`visible`（ContextMenu）、`anchor`（SuggestionMenu）各一种。同为“可选受控”的组件，`open?: boolean` 默认 `undefined` 的写法统一，但 Dialog 不支持非受控，QuickPick 的 `open` 必填。
  2. 关闭原因词表：`DialogCloseReason = "overlay"|"cancel"|"close-button"|"esc"`；`ContextMenuCloseReason = "select"|"escape"|"tab"|"outside"`；`QuickPickCloseReason = "escape"|"outside"`。Escape 在两处叫 `escape`、一处叫 `esc`；“点外面”在 Dialog 叫 `overlay`，在另两处叫 `outside`。AlertDialog/Drawer/Popover 没有关闭原因，只有 `update:open`，宿主无法区分 Escape 与外部点击来决定焦点去向（ContextMenu 的类型注释自己就写了“宿主据此决定焦点去向”）。
  3. 关闭交接事件：只有 QuickPick 有 `closed`（真实关闭交接，`close-handoff.ts`）；Dialog、AlertDialog、Drawer 没有，宿主要自己等动画。
  4. 受控/非受控：`Switch`、`Slider`、`RadioGroup`、`ToggleGroup`、`CheckboxGroup`、`Tree`、`Menubar` 的 `modelValue` 默认 `undefined`（可非受控）；`Input`、`Textarea`、`NumberInput`、`Select` 默认 `""`，`Checkbox` 默认 `false`，`Progress` 默认 `0`，`Dialog` 必填：同样叫 `modelValue`，有的组件省略后是“未受控”，有的是“受控为空”，调用方无法从名字判断能否省略。
- **为什么是问题**：调用方要为每个浮层记各自的受控方式和关闭语义；通用的“焦点归还”逻辑（宿主根据关闭原因决定焦点去向）写不出统一代码。新增浮层时没有可照抄的标准。
- **如何核实**：`grep -nE "^\s+(open|visible|modelValue)\??:" -r packages/nb-ui/src/components --include=*.vue`；`grep -rn "CloseReason" packages/nb-ui/src`。
- **建议改法**：定一份“浮层合同”：打开态一律 `open?: boolean` + `update:open`（Dialog 的 `modelValue` 保留为别名可以，但 `open` 为准；ContextMenu 的 `visible` → `open`），一律可选受控（用 `@vueuse/core` 的 `useVModel`/`useControlledRef` 或 Vue 3.4 的 `defineModel`，库里 0 处用 `defineModel`，全是手写 `withDefaults + emit`）；统一一个 `OverlayCloseReason = "escape" | "outside" | "action" | "tab" | "button"`，Dialog 的 `overlay`→`outside`、`esc`→`escape`、`cancel/close-button`→`button`/`action`，所有浮层的 `update:open` 之前先 emit `close(reason)`；`closed` 交接事件上提到 Dialog/AlertDialog/Drawer 一并提供（用已有的 `useCloseHandoff`）。

### L06 [建议][复用][耦合] 滚动条有 3 套内部实现各写一套滑块颜色，库不提供“滚动条”token；3 个调用方各自手写同一段全局滚动条 CSS，并要撤销 nb-ui 的全局 `html` 规则

- **位置**：`components/layout/ScrollArea.vue:39,47`（滑块 `--text-main` 20%/35%）；`components/layout/OverlayScrollbar.vue:188,193,197`（32%/45%/55%）；`components/layout/PopupScrollbar.vue:21`（45%/70%/75%，宽 4px，位置靠 `usePopupScroll`）；调用方：`packages/neuro-book/src/web/styles.css:19-23`、`packages/nb-story/src/web/app.css:28-31`、`packages/dev-panel/src/web/app.css:24-36`；`packages/nb-ui/src/styles.css:6-8`（`html { scrollbar-gutter: stable }`）。
- **现象**：
  1. 同一个“细滑块”视觉三处各取一组不同的透明度和宽度（轨道 10px/滑块 6px；轨道 10px/ScrollArea 滑块 flex；4px），`src/tokens.css`、`themes/*/vars.css`、`src/theme/tokens.ts` 里没有任何 scrollbar 相关 token（`grep scrollbar` 全空），主题无法统一调整滚动条。
  2. 三个应用各自手写一遍 `* { scrollbar-width: thin; scrollbar-color: color-mix(... var(--text-muted) 55%, transparent) transparent }`，dev-panel 还写了 `html { scrollbar-gutter: auto }` 专门撤销 nb-ui 的全局规则，并在注释里说“nb-ui 的全局 `html { scrollbar-gutter: stable }` 在这里只会留下右缘一条空带”——这是库的全局副作用（见 L02）造成的调用方补丁。

  1. `requestClose` 先 `emit("request-close")`，然后用 `instance.vnode.props` 判断宿主**有没有挂** `onRequestClose` 监听：没挂就自己 `emit("update:modelValue", false)` 并 `emit("cancel")`，挂了就由宿主负责关。`confirm` 同理看 `onConfirm`。也就是说“给 `<Dialog>` 加一个 `@request-close` 日志监听”会让它从“自动关闭”变成“永远关不掉”；经一层包装组件转发（`v-bind="$attrs"` 或 `@request-close="$emit('request-close', $event)"`）也会改变行为。这是靠内部 vnode 判断的隐含合同，没有写在 props 里。（`Dialog.md:47` 有写，说明它是有意的设计，但组件签名里看不出来，类型层面 `request-close` 与 `update:modelValue` 都是普通事件。）
  2. 自动关闭路径会 `emit("cancel")`，所以点遮罩、按 Esc、点关闭按钮都会发 `cancel`，与“取消按钮”无法区分，`DialogCloseReason`（`overlay|cancel|close-button|esc`）里的 `cancel` 实际是按钮点击，而 `cancel` 事件是所有关闭路径。

  4. 默认值把“一个应用的设计结论”写进组件：`closable: false`（注释引 Apple UI Kit）、`overlayType: "opaque"`、`cancelLabel: "取消"`。
- **为什么是问题**：(1) 是会把调用方埋进去的隐含合同；(2)(3) 让 Dialog 成为全库最难改的文件，而浮动窗口（只有 neuro-book 一个入口使用）与对话框的重叠只是外框。

- **建议改法**：(1) 去掉 `hasListener`：要么 `closeOnRequest: "auto" | "emit"`（显式 prop，缺省 `auto`），要么永远只发 `request-close`，由 `v-model` 关闭由宿主决定；`cancel` 只在取消按钮路径发；(2) 把窗口模式拆成 `FloatingWindow`（复用同一个内部外框 `DialogSurface`），模态 `Dialog` 去掉窗口 prop；(3) `onTop()` 改为用 `useModalLayer` 里已有的叠放序号判断，不读 reka 的 `data-dismissable-layer`。

### L23 [建议][API 形状] 选项类控件的值类型写死为 `string`：`Select`、`RadioGroup`、`Tabs`、`CheckboxGroup` 都不是泛型，调用方自己做序号映射

- **位置**：`components/form/Select.vue:30-40,45`（`SelectOption.value: string`、`modelValue: string` 默认 `""`）；`form/RadioGroup.vue`、`controls/Tabs.vue:12,28`、`form/CheckboxGroup.vue`（`string` / `string[]`）；`controls/SegmentedControl.vue:15-30`（`SegmentedControlValue` 联合）；全库只有 `Table`（`Row`）和内部的 `MenuNodes` 用了 `generic=`；调用方：`packages/neuro-book/src/plugins/settings/web/components/SettingsControl.vue:35-41`。
