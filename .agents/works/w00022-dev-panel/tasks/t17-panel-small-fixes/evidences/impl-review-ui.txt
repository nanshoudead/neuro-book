### 1. Work 页 Task 表“谁在动”一列：标题被挤成一两个字，且列宽已在最窄
- 严重程度：重要
- 类别：设计缺陷（已知问题，交付报告未改）
- 位置：`src/web/parts/TaskTable.vue:80-82`（格子）、`:135`（`grid-template-columns` 末列 `minmax(7rem, 1.2fr)`）、`:129-131`（注释“最窄约 60rem”）；`src/web/parts/LeaseChip.vue:24-27`
- 现象：1440 宽时这一格只有约 7rem（115px），而 chip 本身要放图标、短键（`claude 6ef046c2`，约 75px）和内边距，标题那一段是 `min-w-0 max-w-64 truncate`，被挤到只剩一两个字（`shots/s2-work-1440x900-light.png`，表格右下角）。表内容越多越窄，宽度只会更差。
- 为什么是问题：计划要的“标题加短键”在这个位置只剩半截标题，还不如不显示；半截标题还会让人误以为是完整标题。交付报告说放宽到 10rem 会让表横向溢出，这个判断是对的，数字如下：行的 9 列，固定列 2+5.5+6+3+3.5+5.5=25.5rem，三个 `minmax` 的下限 16+12+7=35rem，8 个列间距 8×0.75=6rem，左右内边距 0.5rem，合计 67rem。1440 宽时表格容器是 1080px=67.5rem（截图里表从 x=325 到 1405），几乎正好是最小宽度，没有余量可分给最后一列。`.nbdev-task-grid { min-width: 60rem }` 与注释“最窄约 60rem”是错的（实际 67rem，行本身会超出 grid 容器 7rem；这是这次之前就有的，但这次的需求把它暴露出来了）。
- 如何核实：读 `grid-template-columns` 与 `shots/s2-work-1440x900-light.png`，按上面的和算一遍；在真实面板用 1440、1280 宽打开有租约的 Work 页量 `getBoundingClientRect().width`（未验证，从代码与截图推断）。

### 2. 会话在工作中时，“不能发”的原因只写在 placeholder：输入框里有草稿就看不到，对比度也低
- 严重程度：重要
- 类别：交互、正确性（相对改前是退化）
- 位置：`src/web/parts/SessionConsole.vue:53-60`（`promptBlocked` 的 `line: false`）、`:61`（`placeholder`）、`:90`（`:disabled="promptBlocked !== null"`）；`src/web/parts/SessionConsole.md` 输入框一条
- 现象：会话状态是 working 或其它非空闲时，原来的整行提示（`会话在工作中：空闲之后才能发文字（不排队）`）不再渲染，原因只进了禁用输入框的 placeholder。placeholder 只在输入框为空时可见。草稿在 `draft` 里一直留着（只有 `resetKey` 变才清，`:37-39`），所以开发者先在空闲时打了半句话、会话随后转成 working，输入框里就是一段灰掉的草稿、发送按钮禁用，界面上没有任何一处说明为什么；左侧只有“工作中”徽章，没有“不排队、要等空闲”这层意思。改前这一行是 `v-else-if="promptBlocked"` 常驻的。
- 另外：禁用的 textarea 带 `disabled:opacity-60`（`FormTextarea.vue`），placeholder 是 `--text-muted`。面板自己的 `app.css:93` 注释写着 `--text-muted` 在亮色页面底色上只有 2.88:1（2026-10-14 实测），再叠 60% 不透明度只会更低（估计约 2:1，未测）。`shots/s3-after-working-1440x650-light.png` 里这句话几乎看不见。
- 另外：`line: true`（等确认、整块不可用）时上面一行和 placeholder 写的是同一句（`placeholder` 不看 `line`），同一句话在屏幕上出现两次，读屏也读两次。
- 为什么是问题：计划的目的是“工作与空闲来回时高度不变”，代价是把状态原因藏进一个会消失的位置；这个状态很常见（会话几乎总在工作与空闲之间切换）。
- 如何核实：从代码推断。构造方式：空闲时在输入框里打字，再让会话转 working，看输入区；或在 `web-session-console` 一类的 jsdom 测试里挂 `SessionConsole` 断言“有草稿且工作中时能读到原因”。
- 建议改法：不要靠 placeholder 承载状态。保持“高度不变”的目标，在按键行（有空位）或发送按钮旁放一行不换行的小字原因（例如放在字数的位置：`工作中，空闲后才能发`），始终渲染、不占新行；或者给输入框外层加一个固定一行高的状态槽。placeholder 只写固定的 `发给这个会话的文字（Ctrl+Enter 发送）`；`line: true` 时也不要把同一句再塞进 placeholder。

### 3. 原因与说明的无障碍路径：`aria-description` 把 placeholder 挤出了描述位
- 严重程度：重要（未验证，从规范推断）
- 类别：无障碍
- 位置：`src/web/parts/SessionConsole.vue:90`（`aria-label` 加 `aria-description`，禁用时原因只在 placeholder）
- 现象：输入框的可读名是 `发给会话的文字`，描述是 `aria-description`（`替你在这个会话的输入框里打字并回车`）。HTML-AAM 里 placeholder 只在没有别的描述来源时才作为描述；这里 `aria-description` 占了位，禁用时的原因（工作中、审计不可用、等确认）对读屏用户就读不到。`aria-description` 本身还是 ARIA 1.3 草案属性，各浏览器与读屏的支持不一致。禁用的输入框不能聚焦，读屏用户只能在浏览模式下逐项读到它，更需要原因写在可读的文字节点里。
- 如何核实：Chrome 开辅助功能树看这个 textarea 的 Description；或用 NVDA、VoiceOver 浏览模式读一遍禁用态。我没有跑浏览器，这条标未验证。
- 建议改法：说明与原因都写成真实的文字节点（问题 2 里那行小字），用 `aria-describedby` 指向它；“替你在输入框里打字并回车”的说明也用一个 `sr-only` 的文字节点加 `aria-describedby`，不靠 `aria-description`。

### 4. 输入框行数按换行符数，不按可见行数：一长句会被折成看不见的几行，又不能拖高
- 严重程度：重要
- 类别：交互、设计缺陷
- 位置：`src/web/parts/SessionConsole.vue:63`（`rows = min(4, max(1, draft.split("\n").length))`）、`:90`（`style="resize: none"`）
- 现象：行数只看 `\n` 的个数。输入一整段没有换行的话（发给 Agent 的指令通常就是一两百字一行），textarea 仍是 1 行，文字在框内软换行后只露出最后一行，往上要滚动框内；因为 `resize: none`，用户也没法拖高。手机档（宽约 330px，一行约 20 个汉字）里写 40 个字就已经有两行看不见。改前是固定 2 行并可拖高。
- 另外：每按一次 Enter 终端就矮一截。1 行时 dock 高 92px（`s3-after-measure.json`），每多一行约 +20px（估计值，textarea 字号 14px），4 行时终端约 346-60≈286px，低于计划的验收目标 320px；交付的测量只量了空草稿。计划审查第 3 条担心的“终端反复调整尺寸”只是从“聚焦时”换成了“打字时”：观看模式的字号由 `fitWatchFont` 按框高算，打字加行会让终端字号跳一档，发送后清空又跳回去。
- 为什么是问题：用户写的内容在自己的输入框里看不见，是输入框的基本功能缺口；“行数由内容决定”的判据选错了量。
- 如何核实：从代码推断；真实面板里粘贴一段 150 字无换行的文字，看输入框高度；再按三次 Enter 量终端框。
- 建议改法：行数按可见行数算。Chrome 本机用 `field-sizing: content` 加 `min-height: 1 行`、`max-height: 4 行`（面板只给本机开发者用，浏览器版本可控），不用自己量；如果要兼容，监听 `input` 读 `scrollHeight` 再限制到 4 行。同时把验收补上“4 行草稿时终端仍不低于 320px”，做不到就把上限收到 3 行，或在草稿超过 1 行时才让 dock 增高并明说终端会变矮。去掉 `resize: none` 之前先想清楚：保留拖高把手只会在 `field-sizing` 下失效，两者二选一。

- 严重程度：重要
- 类别：规范一致性、设计

（对第 5 条的勘误：标题里的“三个零件”应为“四个零件”；行号应为 `WorkCard.vue:15`、`InboxList.vue:15`、`TaskTable.vue:29`、`ProcList.vue:13`。）

### 7. 常用宽度下，“带‘确认’的键先给你看屏幕再发”的说明永远不可见
- 严重程度：建议
- 类别：交互、可发现性

- 严重程度：建议

- 位置：`src/web/pages/RunsPage.vue:41-44`、`src/web/parts/ProcList.vue:42`、对比 `src/web/parts/LeaseChip.vue:24-27`
- 现象：“标题 + 短键”的规则在三处各自实现：chip 里是 `inline-flex` 加 Tooltip，`RunsPage` 的 `h3` 是 flex 加 `max-w-64 truncate`，`ProcList` 是 `inline-block max-w-64 truncate`。前一种有 Tooltip、可聚焦、写了标题来源；后两种标题超过 16rem 就被截断，没有 `title`、没有 Tooltip、不可聚焦，触屏与键盘读不到全文。计划审查第 9 条就是为这个问题要求 Tooltip 的。标题最长 120 字（`MAX_TITLE`），超过 16rem 很常见。`RunsPage` 还把 `ownerOf(session)` 在模板里算了 4 次。
- 为什么是问题：同一个会话在三个位置有三种截断与提示行为；规则以后要改（例如 `max-w-64`）要改三处。
- 如何核实：读上述三处。
- 建议改法：抽一个 `SessionLabel` 零件（标题可截断、短键不截断、带可选的 Tooltip），`LeaseChip` 里的标题与短键、`RunsPage`、`ProcList` 都用它；Tooltip 的文案由 `LeaseChip` 的 `tip` 那段逻辑搬进去。

### 12. `LeaseChip` 的无角色可聚焦 `span`：Tab 停靠点多、读屏会把标题读两遍
- 严重程度：建议
- 类别：无障碍
- 位置：`src/web/parts/LeaseChip.vue:20-21`（`:tabindex="tip === '' ? undefined : 0"`）
- 现象：只要有标题或 `hint`，每个 chip 都是一个 Tab 停靠点，没有 `role`。首页有 N 个 Work、Work 页的 Task 表每行一个，Tab 序列里多出不可操作的停靠点。Tooltip 的文字里又重复了完整标题，读屏读 chip 内容后再读一遍描述（标题两次）。触屏上点 chip 不会出提示（Reka 在 pointerdown 之后的 focus 不开提示，从代码与 Reka 文档推断，未在设备上验证），所以截断的标题在手机上仍然看不全，计划审查第 9 条要求的“触屏与键盘读得到”只做到了键盘。
- 建议改法：保留 tabindex 的前提是 Tooltip 里的信息读屏读不到别处；这里 chip 的可见文字已经含完整标题（DOM 里没被截断），所以 Tooltip 其实只服务视觉用户。可以让 `tip` 只在标题被截断或有来源信息时才有值，并给 chip 加 `role="group"` 配 `aria-label`（短键 + 标题来源）代替重复读。触屏上用点按展开的方案是另一件事，如果不做，应在 `LeaseChip.md` 写明“触屏上截断的标题看不到全文”。

（对第 10 条的勘误：第 3 小条的行号是 `PageShell.vue:40`。）

### 13. 用内联 `style="resize: none"` 盖 nb-ui 的 `resize-y`，与面板“用语义类代替内联 style”的约定不符
- 严重程度：建议
- 类别：代码质量
- 位置：`src/web/parts/SessionConsole.vue:90`；约定见 `src/web/app.css` 语义类一段的头注释（“代替散落的内联 style”）
- 现象：计划写的是 `resize-none`，实现用了内联 style，因为 `FormTextarea` 根上已经有 `resize-y` 类，两个原子类谁生效取决于生成 CSS 的顺序。内联 style 是确定的，但是这个面板别处不这么写，也没有注释说明为什么不用类。
- 建议改法：在 `app.css` 加一条语义类（如 `.nbdev-no-resize { resize: none; }`，选择器权重要不低于 `.resize-y`），或写 `[resize:none]!`；注释里写明“盖过 FormTextarea 的 resize-y”。如果按第 4 条改成 `field-sizing: content`，这一条自然消失。
