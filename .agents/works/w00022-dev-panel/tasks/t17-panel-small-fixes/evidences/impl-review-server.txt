### 1. 超预算的查找仍占着资源，新键下一轮再开 4 个，冷查找并发上限实际失效

- **严重程度**：重要；**类别**：不变量、安全与性能、合同一致。
- **位置**：`packages/dev-panel/src/server/session-titles.ts:267-275,320-357`；`src/server/state.ts:259-273,280-296`；`docs/panel.md:308`。
- **现象**：`BATCH_PARALLEL=4` 只限制一轮的 worker。2 秒 `Promise.race` 返回后，旧的 `lookupOnce` 仍在 `inflight` 中做 I/O；`titleTask` 却已经释放，新一轮遇到不同的键就再开 4 个。实际面板实例中观察到 **8 个不同文件的 pread64 同时在途**，不是全局最多 4 个。相同键单飞不能限制不同键的跨轮叠加。
- **为什么是问题**：计划和合同要求冷查找最多 4 个同时进行、后台标题任务不无限积压。慢盘时每次替换键集合都可以再增加一批，超预算没有释放并发配额，也没有跨轮共享配额；标题任务虽然不 await 到底，底层任务并不单飞。源码给出的上界是每轮 4 个，不是整个 resolver 4 个。
- **如何核实**：真实文件、真实 `startPanelServer`、HTTP `/api/runs` 与 `/ws`。先登记 4 个旧属主，再在它们读盘期间改登记为 4 个新属主，改 Work README 经真实 `fs.watch` → records → activity 触发刷新；没有调用私有调度、没有替换 `SessionTitles`。`strace` 仅对 8 个标题文件的真实 `pread64` 注入 `delay_enter=12s`，不改文件内容或 syscall 返回值。旧 4 个读请求从 Unix 时刻 `1792002337.520816–1792002337.520931` 在途到 `1792002349.521099–1792002349.521206`；新 4 个从 `1792002341.522853–1792002341.523045` 在途到 `1792002353.523027–1792002353.523198`：重叠约 **8 秒**。`overlap.trace` 第 44–47、66–69、80–83、95–98 行核实了 8 个不同 FD 与文件。新的活动仍在 **392.76 ms** 后经 HTTP 发布，WS 收到 activity changed。
  - 实际命令形状：`TMPDIR=/dev/shm/review-t17-srv-lab/tmp strace -f -qq -ttt -T -y -e trace=pread64,openat,close -e inject=pread64:delay_enter=12s -o /dev/shm/review-t17-srv-lab/overlap.trace -P <8 个普通标题文件，逐个 -P> bun /dev/shm/review-t17-srv-lab/runtime-probe.ts overlap`；完整命令与脚本在报告末附录。
  - 初版实验的异步 `/proc/self/fd` 观察器与读盘共用 FS 线程池，未及时取到 8-FD 快照，实验退出码 1；**并发结论来自真实 syscall trace**，不把这次观察器超时当产品错误。观察器改同步读 `/proc` 后的结果另在附录记录。
- **与 base 对照**：base 没有 `titlesOf`、预算后留存的后台批次或活动标题任务；这里是 t17 新增的跨轮生命周期/并发机制，非旧缓存问题。
- **建议改法**：在 resolver 中持有跨轮共享的 4 个冷查找配额，配额随实际 lookup settle 才释放；排队键按最新需求修剪，预算到点后不再给过期轮次启动新 lookup。不能只给每轮 `Promise.all` 开 4 个 worker，也不能为取消而把活动刷新重新 await 到慢 I/O。补真实慢读下键集合更换的 HTTP/WS 用例，核对并发上限与活动仍及时发布。

### 2. stop 返回后标题任务仍读盘并修改已停止实例的快照与 revision

- **严重程度**：重要；**类别**：不变量、资源释放。
- **位置**：`packages/dev-panel/src/server/state.ts:259-296,346-352`；`src/server/serve.ts:489-500`；`src/server/session-titles.ts:338-354`。
- **现象**：`PanelState.stop()` 只停 watcher、周期定时器与 herdr，不取消、不等待 `titleTask` 或实际 lookup，也不撤掉该轮预算定时器。`readTitles()` 在 await 后不检查 `stopped`，继续写 `knownTitles` 和 `activity.patch`。`scheduleTitles()` 自身也没有停止检查，已在途的 computeActivity 可以在 stop 后新起一轮；只有 finally 的“再来一轮”分支检查停止状态。
- **为什么是问题**：`await PanelServer.stop()` 不是标题后台工作的收口点。调用方收到停止完成后仍有普通文件 FD、预算计时器和读盘工作；慢 I/O 没有结束上界。止住后续刷新并不等于收掉当前资源。程序内反复启停实例、预热中收到退出信号时，旧实例仍占资源、发布内部变化。交付报告第 103 行所说“到点后仍等已开始的查找结束”不是 stop 的实际保证。
- **如何核实**：真实 `startPanelServer`、普通 Claude 标题文件、进程登记、真实 HTTP `/api/runs`。`strace` 只对目标文件的真实 `pread64` 延迟 **1500 ms**。预热后 HTTP 为 200、revision 1；在读取仍在途时 `await server.stop()` 用 **1.08 ms** 返回，目标 FD 仍打开。停止返回约 **1452 ms** 后，`state.stopped === true` 的实例再次发布 activity，revision 从 **1 增到 2**，快照加入“普通文件 1”的标题；随后 FD 才关闭。未调用私有 `readTitles`，未伪造结果或事件顺序。
  - 命令：`TMPDIR=/dev/shm/review-t17-srv-lab/tmp strace -f -qq -ttt -T -y -e trace=pread64,openat,close -P /dev/shm/review-t17-srv-lab/stop-home/.claude/projects/-repo/bbbbbbbb-0000-4000-8000-000000000001.jsonl -e inject=pread64:delay_enter=1500ms -o /dev/shm/review-t17-srv-lab/stop.trace bun /dev/shm/review-t17-srv-lab/runtime-probe.ts stop`，退出码 **0**。
- **与 base 对照**：base 的 Refresher/stop 对在途活动计算缺少全面停止防护，但没有独立标题后台任务。本条只归因新任务未加入生命周期，不把 base 的通用 Refresher 停止问题算本次回归。
- **建议改法**：为标题调度设置停止门；停止后不得启动、重新排队或 patch。让 resolver 拥有在途任务与计时器的停止/结束合同，`PanelServer.stop()` 显式等待该合同完成；无法取消的底层调用也需有有限收口方案，不能用忽略其 Promise 代替资源结束。补“正常运行中停止”和“预热中停止”两种真实时序，断言 stop 返回后无标题读取与状态变化。

### 3. 标题任务仍在主事件循环整份解析 Codex 索引，后台化没有隔离活动与 HTTP 的阻塞

- **严重程度**：重要；**类别**：正确性、安全与性能、预算合同。
- **位置**：`packages/dev-panel/src/server/session-titles.ts:280-293,338-354`；`src/server/state.ts:243-246,280-282`；`docs/panel.md:308`。
- **现象**：`readFile` 是异步的，但其后的整文件 `split("\n")`、逐行 `JSON.parse`、清洗标题与填 Map 都同步跑在面板主事件循环。`setTimeout` 的 2 秒 deadline 不能打断这段 CPU 工作；这段期间其它活动计算、HTTP/WS 回调都不能推进。
- **为什么是问题**：“computeActivity 没有 await 标题”只消除了等待 Promise 的依赖，没有消除执行线程耦合。合同没有给 Codex 索引规定尺寸上限，却允许每次索引变更重读整份；后台标题解析可以暂停所有页面和活动更新。预算也不是覆盖这段解析的有效截止，不能以一条 setTimeout 宣称整轮最多 2 秒。
- **如何核实**：不注入延迟、不替换函数。真实 Codex `session_index.jsonl` 含 **6,000,000** 条合法的改名索引记录，大小 **288,000,000 字节**；唯一属主只存在于进程登记 `startedBy`，无 herdr、无租约，不请求会话页或按需标题接口。保持真实 `/ws` 连接，更新文件，再修改 Work README 经真实 watcher 触发活动刷新；另起独立 Bun 进程每 10 ms 测 HTTP `/api/runs`，不把同进程计时当网络延迟。
  - 新实现：从触发刷新到新标题和客户端结束 **2970.62 ms**，独立客户端 **91** 次请求中单次最长 **2078.20 ms**；没有超预算诊断。命令：`TMPDIR=/dev/shm/review-t17-srv-lab/tmp bun /dev/shm/review-t17-srv-lab/large-index-probe.ts`，退出码 **0**。
  - `8276c0bb2` 基线：同样的索引、登记、watcher、HTTP/WS 和独立客户端，记录刷新完成 **345.40 ms**，独立客户端 **37** 次请求中最长 **4.79 ms**。命令：`TMPDIR=/dev/shm/review-t17-srv-lab/tmp bun /dev/shm/review-t17-srv-lab/large-index-base-probe.ts`，退出码 **0**。基线副本仅将已审的 5 个服务端模块的相对 import 改到对应源码位置；无改动的 core/herdr/其它服务端依赖沿用本 checkout。
  - 首次 3,000,000 条、144,000,000 字节实验只用同进程客户端，漏掉了事件循环暂停期，故没有把其 2.59 ms 作为“无阻塞”的证据；独立客户端才是本条的运行依据。
- **与 base 对照**：Codex 整份同步解析器本身是旧代码，不将它单独算回归。**新增回归是调用范围与时机**：base 的活动和运行页不读标题，只有 `/api/sessions` 需要时才读；本场景的登记属主不在活动会话里，base 不读取该索引。t17 将该无界解析接到周期/记录驱动的标题任务，使原本不读标题的活动、运行页也被同步 CPU 工作阻塞。
- **建议改法**：按有界块读/解析索引，块间让出事件循环并检查单调时钟的整轮截止；保留未完成进度以供下一轮，而非超时后重新整份扫描。或者把解析移到受管理的 worker，仍由统一并发配额与停止合同拥有。补真实大索引加独立 HTTP/WS 客户端的可用性测试，不能只断言标题最终出现。

## 基线已有问题，不计本次发现

- **缓存内存没有硬上限**（从代码确认，未做 RSS/heap 测量）：base 的 `createSessionTitles` 已持有 `cache`、`located`、`missed`、`reported`，均没有容量/代际淘汰；`missed` 的 60 秒是查询失效期限，不会删除 Map 条目。Codex 索引也缓存所有 id。t17 的 `knownTitles` 会按最新键集修剪，但没有给旧 resolver 缓存补内存上限。本条不是新增回归，不能声称全部缓存有界。
- **原有测试的固定等待/实现文案断言**：场景 1 的 `Bun.sleep(10/20)` 轮询、herdr 监视器的固定时长等待、FIFO 用例精确断言日志文案在 base 已存在。新增标题等待使用 waitUntil，不能把旧测试规范问题算 t17 新引入。
- **通用在途 Refresher 停止防护不足**：base stop 已不等待所有在途记录/活动计算。本次第 2 条仅统计新增标题任务没有 owner 收口的部分。
- **同步 Codex 全索引解析**：解析算法在 base 已有；第 3 条只统计后台接入让此前不查标题的活动/运行页也发生阻塞，不重复报告旧按需解析器。
