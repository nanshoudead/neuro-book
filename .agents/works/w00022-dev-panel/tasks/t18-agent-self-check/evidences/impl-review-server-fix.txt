## 偏离与理由
1. 增长用例没有对旧实现形成判别：要在黑盒里让旧实现追着读，写入速度得超过读者，可开始读前写入的又不能超过 4 MiB（否则本代结果
   掉出尾部窗口），两者在不控制时序的前提下互相矛盾；我按测试规范不用固定等待、不改产品代码加钩子。用例保留，说明“日志在增长时复用
   照样立刻报本代结果”的行为；固定 EOF 的判别证据是上面的 strace 测量。审查建议的“部分首行边界”同样因无法从外部控制尾部起点
   落在哪一行而没有加，旧有逻辑（起点前一字节不是行尾就丢掉首行）未改。
2. 复用（follow:false）的截止没有按代取消：复用方只等一行结果，截止是总时限，超时报一次就返回，不会把超时封到后面的代上；
   若也按代取消，复用方在后端重启后可能无限等。FollowSampleOptions.timeoutMs 的注释写明了两种模式的区别。
3. 取消以 signal.reason reject 而不是新增失败码：避免改 shared/projects.ts 的公开失败码合同（RPC、书架都在用）；只有传了 signal 的
   调用方会遇到，项目管理器与书架不传，行为不变。
4. createProjectDirectory 中“建 .nbook/ 加写身份文件”作为一步不再中途核对（理由见第 1 条）。
5. docs/specs/runtime/projects.md 未改：signal 是服务端内部 API 的可选参数，不改变黑盒合同。
