## 重写设计的新发现

### 1. 首次启动会先拒绝尚不存在的样例父目录，根本到不了 create

- **严重程度**：阻断；**类别**：正确性、边界。
- **位置**：t18 `plan.md:37-40,106,116`；`packages/neuro-book/src/server/projects/identity.ts:71-79,97-109,328-329`。
- **现象**：全新 worktree 没有 `<包目录>/.dev-sample/`。计划先调 `checkProjectDirectory`，失败就 `sample-failed` 且“不写任何东西”；该函数第一步 realpath，ENOENT 直接返回 `invalid-path`。后面的 `registry.create` 永远不会执行，因此主场景“新 worktree 一条命令放样例”必定失败。
- **为什么是问题**：这不是首轮的路径约束遗漏，而是重写后选错了现有函数与调用顺序。`checkProjectDirectory` 校验“已经存在的目录”；`ensureParentDirectory` 才承诺新建父目录、先排除状态根、再校验真实路径，`registry.create` 内部正是走它。
- **如何核实**：已逐行核对以上公开函数；没有运行尚未实现的 seedDevSample。主 Agent 验收须从 `.dev-sample/` 完全不存在开始，不先在夹具里 mkdir 它；同时覆盖 `NBOOK_STATE_ROOT=.` 与 `.dev-sample` 时不在状态目录内建样例。公开函数的真实文件 smoke 结果在报告末尾追加。
- **建议改法**：先读登记表，确认不是 registry-invalid；无 sample 时直接让 `registry.create({parent, title: "sample", ...})` 执行父目录规则，或显式用 `ensureParentDirectory`，不能先用要求存在的检查器拦住新建。把“不写”限定为被状态根/路径/身份规则拒绝的分支，区分“尚不存在，需要创建”与“不能登记”。

### 2. 后端复用 projectUrl 的指定路径违反现有前后端导入边界

- **严重程度**：重要；**类别**：不变量、代码质量。
- **位置**：t18 `plan.md:34,43`；`packages/neuro-book/src/plugins/projects/web/open-project.ts:10-16,29-32`；`packages/neuro-book/src/architecture.test.ts:67,88-93`；`packages/neuro-book/AGENTS.md:13-15`。
- **现象**：新 `src/server/dev/sample.ts` 若按计划从 `src/plugins/projects/web/open-project.ts` 引 `projectUrl`，架构检查会报告“后端引用了前端”。这是运行时导入，不会因为函数本身只有 encodeURIComponent 而被允许；模块还带入浏览器命令声明、消息与远程合同的依赖。
- **为什么是问题**：首轮要求地址由应用拥有，重写已做到；但现在后端选择了浏览器一侧的实现作为共享模块。当前架构测试明确把 `server/` 算为后端，把含 `web` 路径的目标拒绝，没有 `server/dev/` 例外。编译能解析不等于依赖合同允许。
- **如何核实**：已核对架构测试的实际判据和 projectUrl 的全部导入；未改源码、未运行假装已经存在 sample.ts 的架构测试。
- **建议改法**：把唯一的 `projectUrl` 干净迁到位置无关的 shared 模块（插件自己的 shared，或宿主共享路由模块），迁移浏览器调用者与后端调用者；不保留旧 web 重导出，也不放宽架构检查。应用继续在日志里报告完整 open-path，nbdev 不接管路由知识。

### 3. 样例 I/O 被移进 health 就绪门之前，但没有失败隔离的等待截止

- **严重程度**：重要；**类别**：失败语义、安全与性能。
- **位置**：t18 `plan.md:31,37-44,56,116-118`；`packages/neuro-book/src/server/start.ts:267-317`；`src/server/dev/backend-process.ts:79-88`；`docs/specs/runtime/server-host.md:49-50,78,93`。
- **现象**：现在正常 HTTP/RPC 准入依靠 startup 完成后 `admission.ready()` 才放行，监督进程等 health 200。若按计划在此之前 await 样例目录/身份/内容读写，慢盘或不返回的文件系统操作会把所有等待中的请求与 backend-ready 一起拖住；“失败时只打 sample-failed、服务照常运行”只处理 reject，没有处理永远不 settle。nbdev 的 180 秒 ready-timeout 只是打 NOT_READY，之后继续监管，不会让后端跳过样例，也不是这一步的截止。
- **为什么是问题**：首轮第 4 条的未登记前置子进程已消失；新增的是可选样例工作变成应用可用性的硬依赖。样例几 KB 限制数据大小，不限制 realpath/stat/read/write 的等待。若直接做成会 reject 的启动门禁，又会按宿主合同关闭整个实例并以 1 退出，与非致命样例失败相冲突。
- **如何核实**：已沿 startServer → admission.ready → health 探测 → backend-ready 的实际链路核对；尚无样例实现，未模拟私有时序或启动服务，慢盘卡住为代码推断。实施验收需用可控真实 I/O/子进程验证有限时间降级、服务仍可访问，并验证准备期间请求停止不会留下继续写样例的任务。
- **建议改法**：写明唯一插入点（运行时正常 startup 可用后、HTTP 准入 ready 之前）及样例准备的总截止和取消/收口所有权；已知样例失败与超时都转成一次 sample-failed 后继续正常准入，不吞掉真实运行时 startup 失败。不能只 Promise.race 超时后丢弃仍会写盘的任务；超时后的写入与后端重启须有明确收口规则。

### 4. 后端打印 open-path 不等于 nbdev 在 READY 前已经读到了它

- **严重程度**：重要；**类别**：跨进程时序、日志协议。
- **位置**：t18 `plan.md:31,37,43,50-55`；`packages/neuro-book/src/server/dev/backend-process.ts:50-55,79-88,91-103`；`src/server/dev/supervisor.ts:75-80`；`packages/dev-panel/src/dev/dev-ops.ts:165-179,275-282`。
- **现象**：open-path/sample-failed 由后端打印，先经 stdout/stderr 管道异步转发；backend-ready 由监督进程在另一条 health HTTP Promise 完成后直接打印。后端“打印后才让 health 200”只约束后端发出顺序，不约束监督进程已经消费那一行，特别是 sample-failed 若走 stderr 时还有两条独立管道。因此监督日志可先出现 backend-ready，再出现样例结果；nbdev 一次读到 EOF 后做 HTTP 探测，探测期间新增的样例行也不会再读就返回 ready。计划此时警告 sample_not_reported 且没有后续 SAMPLE 通道，能够把支持且已准备好的应用误判为未报告。
- **为什么是问题**：计划同时要求 READY 后“紧接”SAMPLE，又允许 READY 时没有报告就结束判定；现有机制没有提供样例结果到达的因果屏障。新起服务一次 READY 后结束 waitReady，复用已就绪服务现在甚至直接走 probe → emit READY 的快路径，必须另补日志消费，而不能只给 matcher 多两个正则。
- **如何核实**：已核对 forwardLines 与 probeReady 独立运行、supervisor 的事件打印位置及 waitReady 在 probe 后不再读日志的返回点；这是时序保证缺失的代码推断，未声称已观测到真实服务乱序。主 Agent 应在允许启动服务后取证：新起、迟到 READY、已就绪复用、后端重启都用真实进程验证样例结果与 READY 的关系，不能仅靠同一个夹具脚本连续同步打印三行。
- **建议改法**：让应用的监督层在确认收到本代后端的样例结果后，先把结果输出到同一日志流，再输出 backend-ready；或给 nbdev 定义有限的样例结果等待握手，明确最终 ready/not-reported 的时刻，不能发出 READY 后就立刻永久放弃结果。复用重放须选当前后端代的最新成功/失败，重启时清除前代结果，不能把旧 open-path 当成本代成功；历史日志扫描取固定 EOF 并有字节/时间边界，截断后无法恢复的结果明确警告，不无限追逐增长日志。路径校验应先排除绝对 URL、协议相对路径/反斜杠等，再用 URL.origin 核对同源。

### 5. 新起服务的样例警告若走现有 warnings 返回路径，要等服务停止才看得见

- **严重程度**：重要；**类别**：可观察性、接口与合同。
- **位置**：t18 `plan.md:54-55,89-92,118`；`packages/dev-panel/src/dev/dev-ops.ts:386-397`；`src/cli/dev-commands.ts:154-155`；`src/cli/main.ts:300`；`src/cli/output.ts:39-42`。
- **现象**：现有 Warning 先累积在 `devStart` 的结果里，CLI 只有 `await spec.run(...)` 返回后才 emit 警告。新起服务在 READY 后继续 await 子进程退出；把 sample_failed/sample_not_reported 加进这份 warnings，不会在准备失败时告诉调用者。开发服务运行 1 小时，警告就至少延后 1 小时；复用分支立即返回，反而会正常看到它。
- **为什么是问题**：样例失败被设计成退出码不变的非致命结果，警告因此是调用者得知“没有可用 SAMPLE 地址”的唯一明确通道。计划没有指定运行中警告如何输出，现有一次性返回通道不满足这种使用方式；只看到 READY、没有 SAMPLE 无法区分仍在等待与已经失败。
- **如何核实**：已核对 runCli 的 await 与 emit 位置，以及新起 supervise 只在进程结束后返回；未起开发服务。原有 emit 的公开输出边界可在临时脚本用真实 Writable 接收器观察，结果在末尾追加。
- **建议改法**：在识别样例失败或确定未报告时立即通过运行中的诊断回调输出警告，或明确新增事件类型；保持既有 stderr 人类警告与 JSON warning 形状，不污染 stdout 的 READY/SAMPLE 事件流。不要等 DevStartResult 返回，也不要同一警告在停止时再输出一遍；验收断言在服务仍存活时已收到警告。

### 6. t17：把整批标题 await 接进 activity，仍缺整轮耗时截止与降级规则

- **严重程度**：重要；**类别**：安全与性能、可用性。
- **位置**：t17 `plan.md:54-57,100,108`；`packages/dev-panel/src/server/state.ts:47-98,192-211,310`；`src/server/session-titles.ts:93-119,122-142,217-240`；`packages/dev-panel/docs/panel.md:304-310`。
- **现象**：新设计在算完活动之后 await 全部 titlesOf 才发布活动。限并发与同键单飞只限制数量，没有限制一轮耗时；已有 stat/open/read/readFile 没有截止，Codex index 变化时还会整文件读。一个标题读得慢，这一轮新租约、会话退出、进程结束都不能发布；后续 5 秒定时与 records/sessions 触发只合并排队，不能绕过在途的一轮。warm 也 await activity，所以标题首次冷读会影响 API 预热。
- **为什么是问题**：首轮的重复 GET 查盘成本已处理，这里是重写新增的“显示装饰阻塞整个活动状态”的耦合。5 秒是触发间隔，不是刷新完成上限。现有 Claude 最坏一次读 256 KiB + 1 MiB + 4 MiB = 5.25 MiB；100 个变化且末尾无标题的文件一轮最多读 525 MiB，慢盘等待还没有有限上界。正常文件系统失败原 resolver 会记录原因并回 null，不拖住；真正缺口是慢操作与批处理未完成时如何发布新 activity。
- **如何核实**：已核对 Refresher 的 compute 完成后才更新 part、单飞排队与 warm 的实际 await 链，及 resolver 的读取上限；525 MiB 是读取循环的代码上界，不是本轮实测吞吐。未伪造 titlesOf 或私有调度，未来实现需真实慢/大文件与活动变化的运行验证，不能只测标题改名最终收到 changed。
- **建议改法**：规定冷查找并发数、标题整轮总预算、超预算和局部读盘失败的降级；预算耗尽仍及时发布这轮真实 activity，标题沿用已知值或省略并诊断，后续有限任务补齐。标题任务不得无限积压，也不能让过期后台结果覆盖更新的键集合/快照。指纹只用最终 text/source 与稳定排序的完整键，不把时间戳、完成顺序或诊断状态放进去。

- **为什么是问题**：旧登记记录的是真实仍在运行的进程，不可因升级多一个字段被解析器跳过，否则会失去复用与停法的入口。CLI flag、登记值、应用收到的环境必须一致；相比首轮状态根错位，这里是新 NBDEV_SAMPLE 协议的优先级未定义。当前 differences 已是字符串数组，计划的“带 sample”应明确为增加字符串元素，不另改对象形状。
- **如何核实**：已核对旧格式、parseProcRecord 的宽容可选字段规则、spawn 原样传 env 与 backendEnv 的 process.env 继承；新字段尚未实现，未声称已经拒绝旧登记。环境继承使变量可达后端是已核实事实，不等于 supervisor DevConfig 对象能跨进程自动传入 ServerConfig。
- **建议改法**：在登记合同明确 `sample` 为 boolean、旧记录缺字段按 false 归一化且仍能复用/停止；新记录总是写有效值。明确 nbdev 是否由 --sample 独占控制变量（未传时清除/设 0），还是接受环境默认并把有效值写入登记；后端只在 development-main 的配置装配读取，生产入口不读。`details.differences` 保持 `string[]`，不一致时包含 `"sample"`，不改同键与所有权规则。补旧 v1 登记、环境中已有 NBDEV_SAMPLE=1、true/false 两向复用场景。
