### 1. 样例超时后仍会开始新的登记写入

- **严重程度**：重要；**类别**：正确性、不变量。
- **位置**：`.worktree/w00022-review-t18-impl/packages/neuro-book/src/server/dev/sample.ts:94-100,129-142,208-215`；实际写入链在 `src/server/projects/registry.ts:92-133,168-177`。
- **现象**：`signal` 只在调用 `registry.create/register` 之前检查，没有传进它们；进入登记后的读取、排队与多步写入不受取消约束。已经报告 `sample-failed 超时` 后，任务仍能新建状态目录、写临时登记表并改名落位；重建分支的 `mkdir` 与后续 `writeProjectIdentity` 之间也没有检查。
- **为什么是问题**：计划要求“每一步写入之前先查 signal”“超时后不再写”；`DevSampleOptions.signal` 允许已开始的一步完成，不允许尚未开始的登记表写入在取消后启动。把整个 `register/create` 当成一份不可取消写入没有兑现合同，也使停止截止返回时无法保证没有继续写盘的任务。
- **如何核实**：实际运行 `env TMPDIR=/dev/shm/review-t18-srv-lab/tmp bun --tsconfig-override /dev/shm/review-t18-srv-lab/tsconfig.json /dev/shm/review-t18-srv-lab/server-smoke.ts timeout-register`。实验使用真实 `startServer`、真实登记表与真实 FIFO，不替换方法：预建样例目录，把 `.nbook/project.json` 设成没有写端的 FIFO，让 `register` 卡在身份读取；300 ms 总截止后已收到 `[dev] sample-failed 超时（0.3 秒内没有放好样例）`，此时 `projects.json` 不存在；随后向 FIFO 写入合法身份 `{schema:1,id:"11111111-2222-4333-8444-555555555555"}`，登记表才被创建并含该 id。健康接口为 **200**，停止退出码 **0**、停止失败 **0**，结果行只有那条超时失败。Bun 结束时另有 `Internal error: directory mismatch ... tsconfig.json`，没有将其算作产品问题。
- **base 对照**：`8276c0bb2` 没有样例任务；登记与身份函数在本范围 diff 中没有变化。回归是新增样例取消合同没有进入既有多步写入链，不是把既有登记 API 不支持取消单独算作问题。
- **建议改法**：让样例使用的登记/建目录操作显式接受可选 signal，在队列真正执行时、各次异步等待之后和每次新写入前核对；保留已完成步骤的正常恢复语义。停止与总截止使用同一取消链。补“卡在登记内部，取消后释放真实 I/O”的行为用例；现有用例只在 `create` 返回后取消，FIFO 用例只卡在最前面的 `list`，两者均漏掉此边界。

### 2. 沿用已有样例时跳过目录校验，会在状态根内补文件并报告打不开的地址

- **严重程度**：重要；**类别**：正确性、不变量。
- **位置**：`.worktree/w00022-review-t18-impl/packages/neuro-book/src/server/dev/sample.ts:107-112,132-138`。
- **现象**：已有登记的样例目录存在且身份匹配时，`restore` 直接返回成功，没有调用 `checkProjectDirectory` 或父目录规则；随后直接补内容并打 `open-path`。状态根换成包目录或 `.dev-sample` 后，旧登记里的样例可以继续命中这个分支。
- **为什么是问题**：作品合同要求项目目录不在当前状态根内部，真正的项目打开在 `manager.ts:416-419` 仍执行此校验。样例分支因而一面在禁止的状态根内写作品文件，一面把无法打开的项目报成准备成功；首次新建的拒绝规则不能覆盖重启时沿用已有目录的分支。
- **如何核实**：实际运行 `env TMPDIR=/dev/shm/review-t18-srv-lab/tmp bun --tsconfig-override /dev/shm/review-t18-srv-lab/tsconfig.json /dev/shm/review-t18-srv-lab/server-smoke.ts existing-state-root`。先用真实登记表放好样例，保留其 id/path，把登记表迁到新的状态根 `<临时包>/.dev-sample/`，删掉实验样例的 `大纲.md`，再用真实 `startServer` 启动样例任务：输出 **`[dev] open-path /?project=sample`**，`大纲.md` 在状态根内部被补回；同一真实服务的 `server.projects.acquire("sample", "review-t18")` 返回 **`{status:"rejected",reason:"create-failed",detail:"不能登记应用的状态目录或它里面的目录"}`**。停止退出码 **0**、停止失败 **0**。Bun 的独立目录诊断同第 1 条。
- **base 对照**：base 的正常项目打开就已有状态根校验，且本次未改该链路；新样例的已有目录快路径独自绕过了它。
- **建议改法**：复用样例前对当前真实目录执行与打开项目相同的校验，校验通过后再检查身份和补内容；父目录规则保留给新建/重建。扩展现有状态根拒绝用例，覆盖“已有合法样例，换状态根后再次启动”，同时断言不补文件、不报成功。

### 3. 样例父目录是符号链接时，删目录重建会生成新 id 并留下身份冲突

- **严重程度**：重要；**类别**：正确性、恢复。
- **位置**：`.worktree/w00022-review-t18-impl/packages/neuro-book/src/server/dev/sample.ts:87-100`。
- **现象**：登记表保存真实路径，但 `expected` 只对 `packageRoot` 做 `realpath`，没有解析 `.dev-sample` 或 `sample` 的符号链接。`.dev-sample` 指向外部目录时，第一次正常创建与登记；删掉样例目录再重启时，旧登记的真实路径不等于这个字面 expected，被误判成“没有样例”，调用 `create` 生成新 id；登记随后按已有路径 id 不符拒绝，留下无法自动修复的身份冲突。
- **为什么是问题**：计划与作品合同明确采用真实路径认出项目，样例目录被删必须按原 id 重建。这里不是拒绝符号链接的设计：第一代允许并已经成功使用；第二代却因路径比较不一致破坏原身份，后续每次重启都失败。
- **如何核实**：实际运行 `env TMPDIR=/dev/shm/review-t18-srv-lab/tmp bun --tsconfig-override /dev/shm/review-t18-srv-lab/tsconfig.json /dev/shm/review-t18-srv-lab/server-smoke.ts symlink-rebuild`。所有路径在隔离实验根：`.dev-sample` 是指向 `external-samples` 的真实符号链接；首次真实 seed 得原 id **`5f78ed9d-2301-4da0-b8f3-8cea16599603`**；删除 `external-samples/sample` 后，由真实 `startServer` 再次放样例，收到 **`sample-failed 新建样例作品失败（register-failed）`**。登记表仍只有原 id，重建的身份文件却是 **`a912eeea-73ef-4b00-bf48-defa786bd270`**，两者冲突；停止退出码 **0**、停止失败 **0**。Bun 的独立目录诊断同第 1 条。
- **base 对照**：base 的 `checkProjectDirectory` / `registry.register` 已按真实路径登记，未被本次修改；错误是新增样例识别只规范化了路径的一部分。
- **建议改法**：样例存在时比较样例目录的完整真实路径；样例已删除时，解析仍存在的父目录（或最近的现存祖先）后拼出预期路径，再按旧登记恢复原 id。不要为了绕过冲突改写已有身份。给现有“目录被删按原 id 重建”用例增加符号链接父目录的同一行为场景。

### 4. 同一轮日志读取包含多代结果时，nbdev 永久漏报较早代的 SAMPLE

- **严重程度**：重要；**类别**：正确性、日志协议。
- **位置**：`.worktree/w00022-review-t18-impl/packages/dev-panel/src/dev/sample.ts:59-81`；测试缺口 `packages/dev-panel/tests/dev-live.test.ts:568-573`。
- **现象**：`readNew` 把读到 EOF 的所有行喂给 tracker，只在全部读完后查询一次 `current()`。如果这段中出现两行 `backend-ready` 及各自结果，第二代会把第一代 outcome 清掉，只有最后一代被 emit；被吞掉的那一代不会补报。
- **为什么是问题**：新起服务的合同要求 READY 后每次后端重启、报告结果就再打一行，不是每 200 ms 轮询只留最后一代。日志管道/调度会自然合并输出，一次 read 包含多代不需要非法日志。复用时重放只选最后一代是另一条合同，不能用同一个“最终快照”算法替代新起服务的逐代事件。
- **如何核实**：实际运行 `env TMPDIR=/dev/shm/review-t18-srv-lab/tmp NBOOK_HOST_SYSTEM_TEMP_ROOT=/dev/shm/review-t18-srv-lab/tmp bun /dev/shm/review-t18-srv-lab/cli-smoke.ts batch-generations`，真实 nbdev CLI 监管临时包的真实 Bun 开发脚本；收到 READY 后通过该应用的 HTTP 控制口一次写入第二代 `/two` 与第三代 `/three` 的四行合法日志，再放行第四代 `/four`。应用报告 **3** 个结果，nbdev 只输出 **2** 个 SAMPLE（`http://127.0.0.1:40791/three`、`http://127.0.0.1:40791/four`），`/two` 永久缺失；`dev stop` **0**、监管退出 **0**、应用存活 **false**、stderr 为空。没有直接调用私有读取器或改仓库实现。
- **base 对照**：`8276c0bb2` 没有 `src/dev/sample.ts` 和样例事件；本次新增读取/派发逻辑的问题。
- **建议改法**：首次历史重放只折叠到本代，转入跟随后在逐行消费时结算每一代的首个结果（或保留待发事件队列），不要等 EOF 后只读快照。扩展现有逐代事件用例，一次放行两代完整输出；当前测试每写一代都先等 nbdev 输出才继续，强制把本应受测的批量边界排除了。

### 5. 首代未报告就重启时，首代截止会错误地永久封掉新一代结果

- **严重程度**：重要；**类别**：正确性、状态转换。
- **位置**：`.worktree/w00022-review-t18-impl/packages/dev-panel/src/dev/sample.ts:73-86`。
- **现象**：deadline 没有绑定启动读取时的 generation。首代尚无结果、截止前又读到新 `backend-ready` 时，`settled` 仍为 null；原 deadline 到期却把此刻的新 generation 写进 settled，随后新一代合法结果被作为“已经超时的同代结果”永久忽略。
- **为什么是问题**：`FollowSampleOptions.timeoutMs` 明确只对开始时那一代计时，交付报告偏离 5 也明确后续各代只在报结果时输出、不另计时。现有实现把前一代的剩余时间借给新一代：新代最多只剩原时限减已耗时，甚至刚开始即被封掉；同一正在运行的服务，新起监管不报 SAMPLE，复用方却能从日志读到成功。
- **如何核实**：实际运行 `env TMPDIR=/dev/shm/review-t18-srv-lab/tmp NBOOK_HOST_SYSTEM_TEMP_ROOT=/dev/shm/review-t18-srv-lab/tmp bun /dev/shm/review-t18-srv-lab/cli-smoke.ts generation-timeout`。真实 CLI 用 `--sample --sample-timeout 1` 起临时开发应用，READY 后立即报告第二代 backend-ready、暂不报告结果；原 1 秒截止打出 **1** 行 SAMPLE_FAILED，之后应用写第二代 `/second-late`，原监管永久没有这行 SAMPLE。此时复用同一服务的 CLI 退出 **0**，输出 READY 加 **`SAMPLE .../second-late`**；再报告第三代 `/third`，原监管又正常打 SAMPLE，证明不是读取器停止。`dev stop` **0**、原监管退出 **0**、应用存活 **false**、stderr 为空。
- **base 对照**：样例等待器为本次新增；没有把 base 的旧就绪时限行为计入发现。
- **建议改法**：首次读完历史日志后记录被计时的 generation；后续换代时取消该代的截止判定，不能把超时结算写到别的 generation。若产品决定改为每代都有时限，应另定义每代起点并更新合同，不能沿用首代 deadline。把此顺序补到现有“超时与重启”行为测试，当前测试分别覆盖超时和重启，没有覆盖它们交叉。

### 6. 复用时没有固定 EOF，已有样例结果也会被持续增长的日志拖住

- **严重程度**：重要；**类别**：安全与性能、截止与收口。
- **位置**：`.worktree/w00022-review-t18-impl/packages/dev-panel/src/dev/sample.ts:47-48,59-77`。
- **现象**：stat 得到的 size 只用来算开始偏移，没有用作本轮结束边界；`readNew` 不断从新的 offset 读到动态 EOF 才返回，在这个内循环里不核对 deadline 或 shouldStop。已有本代结果也必须等增长日志被读到 EOF，才有机会 emit。
- **为什么是问题**：计划要求历史重放只读末尾的一段、不追着增长日志读，复用已有结果立即输出；两轮计划审查已明确需要固定 EOF 与字节/时间边界。4 MiB 在当前代码里只是起点，不是一次重放的上界。写者持续快于读者时，读取、超时判定、事件输出与收口都没有有限边界；这不是要求限制应用日志总大小。
- **如何核实**：实际运行 `env TMPDIR=/dev/shm/review-t18-srv-lab/tmp NBOOK_HOST_SYSTEM_TEMP_ROOT=/dev/shm/review-t18-srv-lab/tmp bun /dev/shm/review-t18-srv-lab/growth-smoke.ts`。真实 CLI 复用时，日志已有本代 `/current`，初始 **3,145,947 bytes**；收到复用 READY 后，让同一真实开发应用连续输出 64 块约 512 KiB 日志。用 `strace -f -qq -yy -e trace=pread64,read -o /dev/shm/review-t18-srv-lab/growth.trace` 跟踪复用 CLI，只统计目标 `.log` 描述符的已完成 read/pread64：共 **562** 次，实际读 **36,699,975 bytes**，不是合同的 **4,194,304 bytes**；结束时日志 **36,700,187 bytes**。SAMPLE 在这次增长重放之后才输出，复用退出 **0**、stderr 为空；`dev stop` **0**、监管退出 **0**、应用存活 **false**。有限日志实验已证实追逐增长；无限输出时的不收口为上述无边界内循环的代码推断，不声称本轮放了无限日志。
- **base 对照**：新 `followSample` 在 base 不存在；旧 `waitReady` 的相似循环未作为另一条回归计数，本发现针对新合同明确要求的样例复用边界。
- **建议改法**：历史重放固定首次 stat 的 EOF，每次 read 限制到该 EOF，最多读取尾部 4 MiB；立即结算这份快照已有的本代结果。需要等新结果时，再按有字节/时间预算的增量块跟随，并在块间检查截止、停止及派发结果。给复用测试加入读期间增长的真实日志与部分首行边界；当前尾部测试不足以检验动态 EOF。
