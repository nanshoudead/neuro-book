## 问题 1：产物编号误享 Work、Task 的短号精确匹配优先级

- **级别：重要；类别：正确性。**
- **位置：** `packages/dev-panel/src/core/search.ts:58-60`；影响截断的位置为 `packages/dev-panel/src/server/views.ts:366`。
- **具体场景：** 搜索 `T15`，存在 Task `t15-ui-polish`、标题为 `t15 计划` 的 Work，以及编号为 `t15-review`、标题为 null 的产物。实际顺序为 Task、产物、Work；按合同应为 Task、Work、产物。产物应属于“编号以搜索词开头”，却被算成“短号完全相同”。编号为 `w00022-report` 的产物有同样问题。
- **依据与原因：** 第 5 批实施进度明确“短号只认 Work 与 Task 的编号段”；代码注释也这样写。但第 59 行只检查编号的形状，没有检查 `match.kind`，对产物编号也提取了 `t15`、`w00022`。产物编号允许这种 kebab-case，并非非法输入。错误优先级也会改变 50 条的入选集合：实测 51 个 `t15-review-*` 产物与一个标题为 `t15 计划` 的 Work，返回 50 个产物，相关度本应更高的 Work 被截掉。
- **核实：实测。** 在集成 worktree 的 `packages/dev-panel` 执行仓库外实验 `relevance.ts`，使用真实 `assertArtifactId`、`listArtifactIds` 验证并索引临时产物目录，再调用 `matchRecords`、`recordMatches`。分数输出为 `[["w00022-dev-panel",1],["t15-ui-polish",0],["t15-review",0]]`；缓存视图输出为 `["t15-ui-polish","t15-review","w00022-dev-panel"]`；51 个产物的场景输出为 `{"returned":50,"workRetained":false}`。没有启动 HTTP 服务；结论是实际缓存视图的排序与截断行为，不冒充浏览器或 HTTP 实测。
- **建议改法：** 仅在 `match.kind === "work" || match.kind === "task"` 时提取短号；产物、会话只能按完整编号比较。补充 `t15-review`、`w00022-report` 不得越过标题前缀命中的排序用例，并覆盖超过 50 条时正确保留标题前缀命中。
- **测试缺口：** 新增两条单测均通过，但没有 `t15-*`、`w00022-*` 形状的产物用例，也没有服务端 `recordMatches` 的 50 条边界用例。`t15-review` 的错误顺序与截断已实测；`w00022-report` 同样被提升为精确匹配是从第 59 行正则推断，其编号合法性与可索引性已实测。
