  • 底座：以 master 的 nb-harness（nb-story 在用的那套）为底座，参考内核分支 feat/w00002-harness-kernel，分支做得多的地方逐块移过来。

一、20 条需求逐条对照

1. Composer：模型、推理档、附件、模式、状态栏 t17

现在有什么

  • nb-agent-ui 已有模型选择、思考档、模式、排队、附件、上下文用量，在 Lab 里能跑；对话视图 Spec 列了 composer 的字段与动作（planned）。
  • harness 的 turn(input: string) 只收文字，图片附件怎样进模型没有设计。
  • 模式（normal、discuss、plan）只在命令系统里出现，有哪些、各是什么意思没定。
  • 旧应用还有：图片预算（最多 8 张、单张 16 MB）、草稿持久化（10 条、30 天过期）、状态栏（上下文占用并可点开看构成、缓存命中率、累计费用）。

要讨论

  • 模式要不要保留 discuss、plan，和审批怎样配合（t06）；附件存哪（t08）；模型选择依赖模型服务（t09）。

2. Composer 的输入框 t17

现在有什么

  • nb-markdown 的 PromptEditor 已实现（implemented），附件写成 ![image #N](local://…)、[file #N · 文件名](local://…)。
  • 旧应用有三种触发符：/ 命令、$ 插入 Skill、@ 引用（章节、卷、设定集等，依赖旧的剧情模型）。

要讨论

  • $ 与 @ 在新应用里引用什么；@ 的种类应由插件贡献（文件、章节、剧情图谱里的人物……）。

3. Agent 是内置插件，要留贡献点 t10

现在有什么

  • 平台提案已定：agent.tools、agent.skills 两个贡献点，激活事件 onAgentTool:<名>，导出“以某 Profile 发起任务”。都没实现，新应用里没有 nbook.agent。
  • 内核分支给插件留的落脚点：工具来源、工具调用拦截、审批应答、Profile 节点与数据源与字段、压缩方法、资源方案。

要讨论（建议的清单）

  • 工具、工具组；Skill；Profile；文档（第 12 条）；资源方案（第 11 条）；斜杠命令；@ 引用的种类；对话视图的工具渲染器（nb-agent-ui 已有注册表）；上下文槽；钩子（第 7 条）；压缩方法。
  • 哪些是声明式贡献（清单里写），哪些要激活后命令式登记。

4. nb-harness 和应用各管什么 t02

现在有什么

  • master 的原则：harness 不认识插件、不读配置文件、不解析模型角色，会话日志由宿主给。
  • 内核分支把配置快照、凭据存储、角色解析都放进了 harness，这是两条线分歧最大的地方。
  • harness 的第二类使用方已经存在：nb-story（独立应用）；以后还有评测脚本。
建议：按“离开 NeuroBook 还能不能用”来分。进 harness：会话、Profile、工具协议、审批判定、提问通道、压缩、运行控制。留在插件：贡献点、设置合成、密钥存放、资源地址到真实目录的映射、nb-history 记账、命令桥、HTTP 与推送。

5. 工具池：命名空间 id、模型看到的名字、工厂函数 t04

现在有什么

  • 已有，叫“登记表”：id 带命名空间（builtin.read、story.search），给模型看的名字是单独的字段；工具由工厂函数创建（createReadTool(options)）。登记的是“声明（可冻结）+ 调用句柄（可撤回）”。
  • 差别：master 的模型名要显式写，不是“没写就取 id 最后一段”；内核分支是把 id 里的 /、. 换成 __、_。

要讨论

  • 默认取最后一段时 builtin.file.read 与 story.read 会撞名，nb-story 已经撞过一次（它的 read 与 nb-agent-ui 内置工具同名）。撞名时报错，还是自动加前缀？

6. Profile：提示词、工具、钩子 t05

现在有什么

  • master：TSX 写的 defineProfile({manifest, initialSchema, tools, context})，<If tool> 按工具是否生效渲染；没有钩子。
  • 内核分支：另加 tools、model、compaction、approval 一等属性，节点、数据源、字段都可注册，有上下文槽 <Slot>，文件改动后重载。
  • 旧应用还有：Profile 自带设置表单（人设、文风预设）、每轮结构化输入、结构化结果、skills.include、用户从模板新建、项目级覆盖；profile home 在项目里。

要讨论

  • 存放几层（内置、用户级、项目级）；用户能不能自己写 Profile（加载即执行代码）；旧应用的这些字段哪些要。

7. 插件给所有 Profile 加工具、工具发现、全局钩子 t04、t05

现在有什么

  • 现行 Spec 明确不做：给所有 Profile 的公共工具、用配置追加工具、工具发现（10-15 定为后续）。
  • 约束：工具定义在提示词缓存前缀的最前面，会话中途加减工具会让整段缓存失效。所以现在会话开始时算出工具集、写进快照、会话内不变。
  • w00017 移交的调研讨论过两条路：Profile 直接引用插件工具；插件在声明里请求装进某些 Profile，由用户按“工具 × Profile”批准。

工具发现的现状（调研第 4 节）

  • 接口原生：Anthropic Messages 与 OpenAI Responses 都支持“工具搜索 + defer_loading”；Gemini 没有找到；DeepSeek 等 Chat Completions 兼容端点没有找到。
  • OMP 18.2.5（仓库锁定）：
    • 工具有 loadMode: essential | discoverable，但怎样呈现要上层自己做；
    • deferLoading 只对 Anthropic 生效；
    • Anthropic 另有“会话内增减工具”：新工具追加到末尾、不改前缀、不破坏缓存，但要 beta 头，缺省关；
    • OpenAI Responses 的延迟工具不会发出。
  • omp 命令行自己的做法：去掉了 BM25 工具搜索，改成 xd:// 设备：工具从 tools 数组撤下，模型用已有的 read、write 列出、取 schema、执行。代码注释说多数模型不懂这套，常用工具（web_search 等）只能留在顶层。
建议：
  • 工具发现做在客户端：一个“查工具、加载工具”的机制，所有服务商都能用；Anthropic、OpenAI 的原生延迟加载当作优化。
  • 和“插件给所有 Profile 加工具”合起来做：
    • 插件把工具登记进公共池，标成可发现；
    • Profile 声明要不要开发现、开哪些工具组，不用改 TSX；
    • 被加载的工具只往会话里追加，不改已有前缀，并记进会话日志，以便恢复。
要定的是加载后的工具怎么调用：放进 tools 数组（非 Anthropic 时会破坏缓存），还是像 xd:// 那样经一个分发工具调用（缓存不受影响，但模型更容易调错）。

全局钩子

  • 没有设计。平台提案只写了“按顺序询问多个插件的钩子由拥有者定义贡献点，并规定收集顺序、合并方式与失败处理”。钩子点（每次模型请求前、工具调用前后、一轮结束）放在 t05 与 Profile 一起讨论。

8. 多 Agent t14

现在有什么

  • 旧应用：create_agent 可以带父会话，invoke_agent 前台阻塞或后台作为 job 运行、结果作为后续消息回流，另有 detach_agent 与关系列表。人和 Agent 走同一个 invokeAgent，只差调用方类型，这一点和你的印象一致。
  • 内核分支提案的设想：子代理是记了父会话的普通会话；父会话批准派生就算授权；子代理以无界面方式运行，遇到要询问的调用直接失败；用收尾工具交回结果（master 已经有收尾工具）。
  • omp：一个 task 工具，可批量、后台，结果经 agent:// 读；DeepSeek Harness：子代理是接缝，并存多种提供方。

要讨论

  • 子代理遇到审批：直接失败，还是冒泡到父会话的界面上问用户；后台子代理的结果怎样回流；Workflow 的位置（见清单外第 7 项）。

9. 审批、ask、人在回路 t06

现在有什么

  • master 没有：harness 只有空闲、运行中、关闭三种状态。
  • 内核分支已做：OMP 的读、写、执行三档等级加四种模式，审批模型（让另一个模型先判），ToolContext.ask 写进日志与待处理、进程重启后还能回答。
  • 平台提案定的形态：服务端把待处理事项持久化并推送事件，用户经普通调用回答。命令系统的 confirm 级命令也等这条通道。

要讨论（拿例子过）

  • discuss 模式下 Agent 要改一章：审批卡片显示 diff，批准、拒绝、改了再批。
  • Agent 用 ask 问“这章用第一人称还是第三人称”，附选项，也能自由输入。
  • 插件被禁用时，正在等审批的调用怎样结算（调研留的待定项）。
  • 子代理的审批（同第 8 条）。

10. 基础工具 t12

现在有什么

  • master 只有 read、edit（五种编辑模式，默认 hashline）；grep、glob、bash 在资源 Spec 里是 planned。
  • omp 常驻的核心集：read、write、edit、bash、grep、glob、find、task、todo、ask；旧应用另有 web_search、web_fetch、request_user_input、switch_mode、report_result。

要讨论

  • bash 不经资源地址：会绕过 nb-history 记账（只能被记成外部修改）和只读模式。旧应用就有这个洞：bash、execute_sql 没标成“会写”，discuss 模式下照样能写。

11. agent home：session、profile、agent 三层 t08

现在有什么

  • 资源 Spec 已有 方案://路径：project://、user:// 已实现；local://（会话工作目录）、tmp://、docs://、插件注册新方案的接口是 planned。内核分支已实现 project、local、tmp、docs、artifact 五种。
  • 没有 session、profile、agent 三种 home。
  • 冲突：local:// 在资源 Spec 里是会话工作目录，在提示词编辑器 Spec 里是附件短地址。
  • 旧应用：profile home 在项目里（agents/<profile>/ 下的 context.md、memory.md）；附件按内容哈希存，可以共享。omp：local:// 是会话的暂存区，memory:// 按项目，agent:// 是子代理的输出。

要讨论

  • 三层之外还有一个维度：放项目里还是跨项目（profile home 在项目里，还是用户级）。
  • fork 会话时附件复制还是共享（按内容哈希存就能共享）。
  • 命名：agent:// 在 omp 里是“子代理的输出”，换个名字可以免得和它撞义。
  • 长期记忆（清单外第 9 项）落在哪一层。

12. 文档：docs:// 与插件贡献文档 t08

现在有什么

  • omp 的文档 URI 实际叫 omp://，提示词写着没被问到就别读；我们的 docs:// 定为“产品参考文档，只读”（planned）。插件贡献文档没有设计。
  • SDK 的 npm 包已经带了 docs/ 与 specs/。
建议：docs:// 放产品使用文档、SDK 作者文档、插件贡献的文档（按插件 id 分目录），Agent 写插件时直接用得上。仓库自己的 Spec、ADR 是开发文档，用户用不到，不放进去。

  • 旧应用：安装层与项目层，同名整体覆盖，可运行的 Skill 带 package.json，内置 17 个。nb-story 已有 nbstory skill install。

要讨论

  • bun 脚本的依赖什么时候装、装在哪；uv 可以用脚本内联依赖（uv run --script），不需要预装。

16. nb-history 接入 t13

现在有什么

  • 包的能力都在（时间线、误删找回、收件箱、会话游标），新应用没接。
  • 旧应用：Agent 写文件前后记账，人写的记 user，外部程序改的由文件监听补记 external；收件箱可以接受、还原、全部接受；每轮开始时告诉 Agent 上次之后谁改了哪些文件（三档）。

要讨论

  • 归属：文件底座提案写 nbook.history，平台提案放进 nbook.project。
  • bash 的写入只能被记成 external（第 10 条）。

17. rewind、tree、fork、swipe t03

现在有什么

  • nb-agent-ui 的视图层已有分支切换、树面板、编辑重试的动作。
  • master 的会话日志是线性的：条目只有序号、没有父条目，分支的数据从哪来没有定义。内核分支的格式按树（id、parentId），v1 只用一条链。
  • 旧应用与 omp 都是“条目带父条目的树 + 当前叶子”，回退只移动叶子、不删历史。

要讨论

  • swipe（同一条回复重新生成、左右切换）在树模型里就是同一父节点下的兄弟分支，和 retry 同一个机制。
  • omp 的 rewind 有两个意思：/rewind 就是 /branch，回退的是会话；rewind 工具按 git 检查点回滚文件。我们回滚文件应走 nb-history，不走 git。
  • 树与“前缀稳定、只追加”不冲突：每条路径仍只追加；恢复会话按当前叶子走。

18. Agent 操控 NeuroBook t16

现在有什么

  • 命令系统已实现：never、confirm、auto 三种暴露级别；跨实例的 list 与 execute，来源记为 agent:<调用方>；只读模式下拒绝写类命令；每次执行留审计。
  • 缺两样：确认通道（现在 confirm 级命令一律返回 confirmation-required），以及 Agent 这一侧调用命令的工具。
  • 旧应用还能让 Agent 打开工作台面板、切换主题。命令提案有三个待决项：插件的命名空间、Ctrl+P 搜哪些东西、两种模式动作集的关系。

现在有什么

二、清单之外值得讨论的

1. 上下文压缩 t11

  • 长篇写作的会话一定会超出上下文。旧应用有自动（预留 25600 token、保留最近 24000 token）与手动 /compact；内核分支做了 soft 压缩；master 明确不做。

2. 运行中插话、排队 t07

  • 旧应用有 steer 与 followup，内核分支有，master 没有。nb-agent-ui 已有排队界面，现在宿主把它关掉了。

3. 模型服务插件 t09

  • 新应用没有模型相关的插件；模型角色合同是 accepted，但没有 Spec，引用的还是旧应用路径。
  • 密钥的存法不一致：设置的 secret 没实现，10-20 定 API Key 当明文配置项；nb-story 只存环境变量名（ADR 0032）。

4. 多窗口、多实例同时写一个会话 t03

  • harness Spec 写“同一时刻只由一个进程里的一个会话写”，但 v2 是多实例拓扑（ADR 0024），两个窗口可能打开同一个会话。旧应用为此有一份会话租约 Spec（planned）。

5. 运行不绑页面 t10

  • nb-story 的做法可以照搬：服务端跑，SSE 推送（更新最多 100 毫秒一次，积压超过 2 MiB 断开），断线后补齐；页面关了 Agent 照样跑完。

6. 会话的周边 t17

  • 标题与摘要自动生成（旧应用每 16 次调用一次）、归档与恢复、会话列表、上下文检查器、分项用量（nb-story t24 留下的）、费用“未知”与“免费”的区分。

7. Workflow 与 Agent 的关系 t14

  • nb-workflow 包在（只被旧应用依赖），对话视图里也有 run_workflow 节点与 workflow.submit 动作，但两者怎样配合没有任何合同。

8. 只读模式里哪些工具算“写” t06

  • 和第 10 条的 bash 是同一个问题，要在工具声明里定死（OMP 的等级没声明时按执行档处理）。

9. 长期记忆 t08

  • nb-memory 还是 spike；和 agent home 一起考虑落在哪一层。

10. 真实模型测试的预算与授权 t18

  • nb-story 的经验：渠道不稳、推理档对结果影响大、OMP 自带重试关不掉。评测方法与预算要在 Work 开头定下来。

三、讨论顺序
