NeuroBook Agent harness 内核：图解与演示

给 NeuroBook 开发者与插件作者。依据提案 docs/proposals/agent-harness-event-model.md（draft，2026-10-29）。接口名字与签名还是草稿，以提案与之后的 Spec 为准；页面里的演示用浏览器里的一个小引擎真的跑归约与反应，不调模型。

1. 一句话：一个循环

日志是唯一的真相。会话里发生的每件事（用户的话、模型的回复、工具结果、插件记下的事实）都是一条只追加的事件。

状态由日志归约出来，不另外存：回退、fork、重启之后，再归约一遍就对了。

请求是状态的视图：一个纯函数把状态算成发给模型的请求，所以不调模型也能预览。

调用模型、执行工具是副作用，经拦截链执行，结果写回日志，循环继续。

熟悉 Elm 或 Redux 的话：事件就是 Msg 或 action，reduce 就是 update 或 reducer，视图算出的不是界面，而是请求。

2. 扩展只做四件事

Profile 与插件都是“扩展”，用同一套接口；Profile 排在最后、地位最高。四样都是可选的，用到哪个写哪个。页面里这四种颜色固定代表它们。

归约

reduce(state, entry) → state
什么时候跑
每条事件写进日志之后，全部扩展都跑
能做什么
维护自己那一片状态：计数、记下没送达的改动
不能做什么
I/O；看别人的状态；改日志

反应

react(entry, ctx) → 新事件[]
什么时候跑
这条事件被全部扩展归约之后
能做什么
I/O（检索、读文件、调小模型），返回要追加的事件：种子、提醒、通知、“接着写”
不能做什么
改已经写下的事件；阻止模型消息与工具结果写入

视图

contribute(mine, input) → {slots, tail, attach}
什么时候跑
只在要发请求、或预览的时候
能做什么
交片段：往 Profile 留的槽里填稳定内容；在请求末尾放只对这一次有效的内容。布局归 Profile 的 prompt
不能做什么
I/O；写日志

拦截

model(request, next, ctx) → response
什么时候跑
接受输入、调用模型、执行工具、压缩这四个副作用发生时
能做什么
改请求与结果、拦下、重试、换模型；日志会记下谁改了什么
不能做什么
改服务商格式的原始请求体；盖过用户配置的拒绝与只读模式

4. 一条事件怎么处理

用户说“续写第 3 章”，这条事件写进日志后：

  1. 归约 全部扩展各更新自己那片。同步、纯函数、很快；谁先谁后结果都一样，因为每个 reduce 只看得到自己那片。
  2. 反应 全部扩展拿到同一份归约后的状态，并发执行，可以做 I/O。
  3. 反应全部完成后，追加的事件按扩展顺序写入（插件按依赖顺序，Profile 最后）。每条新事件再走一遍 1、2。
  4. 视图 不跟着事件跑，只在没有新事件、要请求模型时算一次。
横轴是时间（示意）。
同一轮看不到彼此追加的事件。 上图里 nb-memory 的检索结果与 nbook.history 的通知是同一轮的反应，谁也看不到谁这一轮追加的东西；要看到，得等那条事件自己被归约、反应的时候。这样结果不取决于谁先跑完。

5. 沙盒：写手续写第 3 章

四个扩展挂在这个会话上：nbook.history 记下用户改过的文件，下次发言时告诉模型；nb-memory 用户发言后检索记忆；reminder 每 3 次用户发言提醒一次文风；Profile：写手 写种子、记字数、不到 3000 字就让模型接着写、只许改正文目录。

先按“下一步”看一遍剧本（模型的回复是写好的）。剧本放完后进入自由模式：点日志里任意一条就是回退到那里，状态会重新归约；也可以自己发消息、在编辑器里改文件，看扩展怎样反应、请求怎样变。

6. 状态：共享与私有

内置的片 全部扩展只读

  • 历史：沿当前路径的消息，处理过压缩
  • 工具集
  • 会话设置：模型、推理档、审批模式、Agent 模式（会话级，不跟路径走）
  • 运行状态与待处理事项

只有内核能改，由对应的控制事件推动。

扩展的片 默认私有

只有它自己的 reduce 能改，只有它自己读得到原样。

想给别人看，导出一个只读的选择器：

exports: {pendingChanges: (s) => s.pending}

别的扩展这样读：

ctx.state.read("nbook.history", "pendingChanges")

选择器的返回类型就是公开接口，内部结构随便改。

不是状态的东西

  • 内存缓存：数据库连接、索引句柄，放在 setup 的闭包里；丢了要能从状态重建
  • 配置：Profile 设置、插件设置，经 ctx 读，用户在设置里改
  • 作用域 session 的片（scope: "session"）：和标题一样在树外，回退不影响，例如“记忆已索引到哪一章”
为什么状态由日志归约，而不另存一份？ 状态要跟着对话路径走：回退到第 3 次发言，提醒计数也要回到 3。存在内存里，回退和重启都不对；另存状态文件，要给树上每个节点存一份才回得去（那就是又一份日志），而且日志写成了、状态没写成时两边会对不上。只有日志一个真相源，换一片叶子重新归约就对。代价是 reduce 要守纯函数的纪律，扩展事件要带版本（改了事件含义就升版本，否则旧会话重新归约出来的状态会变）。

7. 视图与缓存

“视图”指整个“状态 → 请求”这一步，由两样东西一起完成：Profile 的 prompt 定布局，扩展的 contribute 交片段。布局只有一个拥有者，否则谁先谁后会影响结果；要改整个请求，用模型拦截。

谁产出去处放什么
Profile prompt（可选）TSX系统提示词、历史的位置与渲染、固定消息能读全部状态、按模型能力写条件、<History render filter> 控制每条怎么渲染。不写就用缺省布局：系统提示词加全部槽，再接历史
扩展 contributeslotsProfile 留的同名 <Slot>稳定的内容：书的设定、记忆的长期摘要。Profile 没留这个槽就丢弃并写诊断
tail接在历史末尾的消息每次都变的内容，只对这一次有效
attach附在请求最末尾那条消息里（用户消息或工具结果）同上，但不想多出一条消息。只附在最末尾：附在更早的消息上，内容一变，它之后的整段历史都失去缓存
扩展 render消息历史里它自己的事件例如检索结果存结构化数据，渲染成 <memory> 块；Profile 可以覆盖

为什么会变的内容不能放进系统提示词

服务商的提示词缓存按前缀命中：两次请求从头开始相同的部分越长，越便宜越快。下面是同一会话里连续两次请求。

8. 拦截链

四个副作用（输入、模型调用、工具执行、压缩）各有一条拦截链，一层套一层：外层是插件，里面是 Profile，最里层是真正干活的。每层拿到 next：改了再调、调两次（重试）、不调（拦下）都可以。

每层做了什么
点“运行”。
审批永远在工具链的最里层：扩展的放行只能免掉审批模式本来要弹的询问，盖不过用户配置的拒绝、工具声明的拒绝与只读模式。预览时模型链也会跑，只是最里层不发请求、把请求截下来，所以预览看到的就是最终请求。

9. 生命周期

扩展插件激活→声明登记→每个会话 setup→dispose→插件停用
会话创建（一次）→打开（每次加载，含重启后）⇄空闲 / 运行中 / 等用户→关闭
运行受理→输入→循环：请求 → 回复 → 工具 × N→准备结束→结束（循环中随时可能压缩；中止或出错时收口）
一条事件写进日志→全部归约→全部反应→追加的事件各走一遍

没有单独的钩子点：“会话已创建”“运行开始”“最终回复”“压缩完成”“运行结束”都是日志里的事件，扩展在 react 里按 entry.type 处理。setup 在每次打开会话时调用（包括服务端重启后），所以扩展的内存缓存要在这里建、在 dispose 里放。

ctx 给什么、不给什么

给

  • 读：内置的片、自己的片、别人导出的选择器、工具、当前模型、上下文用量、read(uri)
  • 主动：complete（不进会话的模型调用）、invokeTool（走审批）、ask、send（插话或排队）、emit、compact、abort、setTitle、诊断
  • 会话身份、preview 标志、中止信号

不给

  • 改工具绑定（归用户）
  • 改会话设置（归用户；按请求换模型用模型拦截）
  • 服务商格式的原始请求体
  • 定时器与界面（插件自己的入口与贡献点能做）

10. 写一个扩展

文件改动通知：归约加反应

export default defineAgentExtension({
    id: "nbook.history.file-notice",
    setup: () => ({
        state: {
            initial: {pending: [] as string[]},
            // 只看得到自己这一片与这条事件；不认识的事件原样返回
            reduce(s, e) {
                if (e.type === "nbook.history/file-changed") return {pending: [...s.pending, e.data.path]};
                if (e.type === "nbook.history/notice-delivered") return {pending: []};
                return s;
            },
            exports: {pendingChanges: (s) => s.pending},
        },
        // 用户发言之后：有没送达的改动就追加一条通知，再记“已送达”
        async react(e, ctx) {
            const {pending} = ctx.state.mine();
            if (e.type !== "user" || pending.length === 0) return;
            return [
                {kind: "message", role: "user", content: await describeChanges(pending, ctx)},
                {kind: "extension", type: "nbook.history/notice-delivered", v: 1},
            ];
        },
    }),
});

回退到用户发言之前，“已送达”那条不在路径上，pending 自动恢复，下次发言时模型会重新收到通知。这里没有一行处理回退的代码。

只想存一个值：pathState

const outline = pathState<{chapter: number}>({initial: {chapter: 1}});

defineAgentExtension({
    id: "demo.outline",
    setup: () => ({
        state: outline.slice,                                  // 内核生成的 reduce：取路径上最后一次 set
        async react(e, ctx) {
            if (e.type === "tool_result" && e.tool === "outline.move") await outline.set(ctx, {chapter: e.data.to});
        },
        contribute: (mine) => ({slots: {outline: `当前写到第 ${mine.chapter} 章`}}),
    }),
});

export default defineProfile({
    id: "writer",
    tools: {required: ["read", "edit"], optional: ["grep"]},
    globalExtensions: {exclude: []},
    prompt: ({state, model}) => (
        <>
            <System>
                你是本书的写手，只改正文目录。
                {model.capabilities.vision && "用户可能贴图，按图写场景。"}
                <Slot name="memory" />
            </System>
            <History render={{"nb-memory/result": (e) => `<memory>${e.data.text}</memory>`}} />
        </>
    ),
    // 自带的扩展：每项和插件的扩展同一个形状，排在全局扩展之后
    extensions: [
        {
            id: "writer/words",
            setup: () => ({
                state: words.slice,                                // 字数在反应里读、写成事件（略）
                // 只对这一次请求有效、不进日志、总在请求末尾
                contribute: (mine) => ({attach: [{type: "text", text: `本章当前字数：${mine.words}`}]}),
            }),
        },
        {
            id: "writer/edit-scope",
            setup: () => ({
                intercept: {
                    async tool(call, next) {
                        if (call.name === "edit" && !call.args.path.startsWith("project://正文/"))
                            return {isError: true, content: "写手只改正文目录"};    // 不调 next：拦下
                        return next(call);
                    },
                },
            }),
        },
    ],
});

旧机制去了哪里

旧机制新设计变化
七种提醒写在 AppendingSet 里，每个 Profile 各列一遍（WorkspaceFocusReminder 出现在 9 个内置 Profile 里）归拥有那份数据的插件，作为全局扩展：工作区焦点归宿主、文件变更归 nbook.history、模式归 nbook.agent、任务归 todo 工具所在的插件、已关联 Agent 归多 Agent、提到的 Skill 归 SkillProfile 里这部分是零行；不要的按标签排除；插件不改 Profile 就能给它加上下文
TaskReminder 靠 stateKey: "agent.tasks" 字符串读 customState，工具往同一个键写任务的状态片由 todo 工具的结果归约而来，提醒和工具在同一个插件里没有跨模块的字符串约定
ModelContext（库结构摘要）不落盘，每次请求插在本轮追加消息之前；下一轮它挪到新一轮之前，上一轮那段的缓存就失效（从 prompt-order.ts 推断）nbook.sql 扩展从状态填系统提示词里的 <Slot name="sql-schema">，库结构变了才变每轮不再丢一段缓存
context() 每次渲染读一次人设文件人设是 sessionState，在会话打开、设置变化、文件被改时读一次，写成事件prompt 是纯函数，预览不读盘，回放用记下的值
HistorySet 只在历史为空时写入seed() 在会话创建与压缩完成时写压缩后种子自动重写
“写作任务必须交给 writer”只写在提示词里自带的工具拦截：改 project://正文/ 时返回错误结果从“请模型遵守”变成能挡住
模式提醒的措辞经 ModeReminder 专用的 ModeSlot 定制通用的 <History render> 覆盖任何扩展事件的渲染一种机制覆盖所有扩展
文件变更感知的档位是主创自己的设置项是 nbook.history 扩展的设置，用户在 Profile 设置里按 Profile 配每个 Profile 不必各写一遍
固定顺序 History → ModelContext → AppendingSet → CurrentUserInput布局由 prompt 定；提醒是日志里真实的事件，按写入顺序出现顺序看日志就知道
runtimeDefaults.summarizer 每 16 次调用跑一次nb-memory 扩展归约“运行结束”计数，到 16 次启动 summarizer（后台运行等 t22）记忆归记忆插件
强在哪里
  • 规则能挡住（工具拦截）
  • 插件能给不认识的 Profile 加上下文
  • 回退与预览自动正确，压缩后种子重写
  • 缓存不再每轮丢一段
  • 写法上要学的只有 sessionState、seed、<Slot>、<History render> 四样
代价
  • 主创收到的完整上下文分散在多个插件里，要靠预览看全（每条标了来源）
  • 人设改了，系统提示词跟着变，缓存失效一次（用户改的，可以接受）
  • 扩展的设置要能在 Profile 设置里按 Profile 显示
  • 验证中改了一处写法：Profile 自带的扩展写成 extensions 列表（待定项 10）

12. 常见错误

写法后果改成
在 reduce 里读文件、查数据库、取当前时间重放与回退得到不同的状态在 react 里做 I/O，把结果作为事件写进日志
在 prompt、contribute 里调 ctx.complete 或读文件预览会发请求；每次请求结果不同同上；视图只读状态
把字数、时间放进 slots系统提示词每次都变，缓存从头失效tail 或 attach
读别的扩展的内部状态对方改了结构，你悄悄坏掉用对方导出的选择器
改了扩展事件的含义却没升版本旧会话重新归约出来的状态和当时不一样升 v，reduce 对旧版本按旧含义处理
在反应里无条件追加“接着做”死循环按状态判断；内核也有上限（连续 3 次）
在 setup 闭包里的变量当真相重启、回退后丢失或不对真相放状态片，闭包只放能重建的缓存

13. 状态与待定

提案是 draft（第二稿）。开发者已同意的方向与细节见提案的“决策记录”；还待定的：

  1. 名字叫“扩展”还是“钩子”（推荐扩展）。
  2. Profile 在拦截链的最里层（推荐）还是最外层。
  3. 归约的快照存在压缩点（推荐）还是每 N 条。
  4. 反应链深度最多 3 层、“接着做”连续最多 3 次。
  5. 请求录制缺省关（推荐）。
  6. reminder() 缺省写进历史（推荐）。
  7. 工具拦截里附加的说明写进日志（推荐）。
  8. 反应直接调 ctx 做 I/O、内核给每个动作记一条日志（推荐），还是像 Elm 那样只返回动作的描述。
  9. 不经事件就会变的数据（当前时间、字数）：扩展的在反应里读、写成事件（沙盒里写手的字数就是这样）；时间这类通用的由内核在算视图前取一次、记进请求记录。
