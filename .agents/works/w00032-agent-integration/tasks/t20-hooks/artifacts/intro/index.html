NeuroBook Agent harness 内核：图解与演示

给 NeuroBook 开发者与插件作者。依据提案 docs/proposals/agent-harness-event-model.md（第三稿，2026-10-29）与 spike（.agents/works/w00032-agent-integration/tasks/t20-hooks/spike/，53 个场景检查通过，两位审查者审了两轮）。接口以 spike 的 api.ts 为准，定稿后以 Spec 为准；页面里的演示用浏览器里的一个小引擎真的跑归约与反应，不调模型。

1. 一句话：一个循环

日志是唯一的真相。会话里发生的每件事（用户的话、模型的回复、工具结果、插件记下的事实）都是一条只追加的事件。

状态由日志归约出来，不另外存：回退、fork、重启之后，再归约一遍就对了。

请求是状态的视图：一个纯函数把状态算成发给模型的请求，所以不调模型也能预览。

调用模型、执行工具是副作用，经拦截链执行，结果写回日志，循环继续。

熟悉 Elm 或 Redux 的话：事件就是 Msg 或 action，reduce 就是 update 或 reducer，视图算出的不是界面，而是请求。

2. 扩展只做四件事

Profile 与插件都是“扩展”，用同一套接口；Profile 排在最后、地位最高。四样都是可选的，用到哪个写哪个。页面里这四种颜色固定代表它们。

归约

reduce: {片名: (值, e, ev, 兄弟片) => 新值 | undefined}
什么时候跑
每条事件写进日志之后，全部扩展都跑
能做什么
维护自己的片：计数、记下没送达的改动；返回 undefined 表示不变；简单的值直接用 ctx.set
不能做什么
I/O；看别的扩展；看另一个作用域的片

反应

react(e, ctx) => 事件[] | {events, continue}
什么时候跑
这条事件被全部扩展归约之后，同一份状态上并发
能做什么
I/O（检索、读文件），返回要追加的事件：种子、提醒、通知；要模型接着做写 continue: true
不能做什么
改已经写下的事件；写别的扩展或内核的事件类型

视图

contribute: {槽名: {volatile?, value}}，sample: {名字: async}
什么时候跑
只在要发请求、或预览的时候
能做什么
往槽里交内容（稳定的、会变的）；每次请求前现取外部数据（sample）。布局归 Profile 的 prompt
不能做什么
在 contribute 里 I/O；写日志

拦截

model(request, next, ctx) => response
什么时候跑
接受输入、调用模型、执行工具、压缩这四个副作用发生时
能做什么
改请求与结果、拦下、重试、换模型；日志记下谁改了什么
不能做什么
改服务商格式的原始请求体；盖过用户配置的拒绝与只读模式

4. 一条事件怎么处理

用户说“续写第 3 章”，这条事件写进日志后：

  1. 归约 全部扩展各更新自己那片。同步、纯函数、很快；谁先谁后结果都一样，因为每个 reduce 只看得到自己那片。
  2. 反应 全部扩展拿到同一份归约后的状态，并发执行，可以做 I/O。
  3. 反应全部完成后，追加的事件按扩展顺序写入（插件按依赖顺序，Profile 最后）。每条新事件再走一遍 1、2。
  4. 视图 不跟着事件跑，只在没有新事件、要请求模型时算一次。
横轴是时间（示意）。
同一轮看不到彼此追加的事件。 上图里 nb-memory 的检索结果与 nbook.history 的通知是同一轮的反应，谁也看不到谁这一轮追加的东西；要看到，得等那条事件自己被归约、反应的时候。这样结果不取决于谁先跑完。

上限与出错

  • 根事件是第 0 层，反应写的是第 1 层，最多写到第 3 层；再往下不写，留一条 reaction_limit
  • 反应有时限（缺省 30 秒）；出错或超时，这次的输出丢弃，写带扩展 id 的诊断，运行继续
  • 一个扩展对一条事件的输出是一个整体：有一条不合规矩，这次的全部不写

“接着做”要显式写

对最终回复的反应返回 {events, continue: true} 才会再请求一次，连续最多 3 次。只写了事件、没写 continue 的（例如回复后补一张角色卡），下一次用户发言时才被看到，不会让模型多跑一次。

5. 沙盒：写手续写第 3 章

四个扩展挂在这个会话上：nbook.history 记下用户改过的文件，下次发言时告诉模型；nb-memory 用户发言后检索记忆；reminder 每 3 次用户发言提醒一次文风；Profile：写手 写种子、记字数、不到 3000 字就让模型接着写、只许改正文目录。

先按“下一步”看一遍剧本（模型的回复是写好的）。剧本放完后进入自由模式：点日志里任意一条就是回退到那里，状态会重新归约；也可以自己发消息、在编辑器里改文件，看扩展怎样反应、请求怎样变。

状态片 由路径归约出来；刚变的闪一下
本次请求 视图算出的

图例：对话 缺省投影成消息；控制 运行、请求与工具的开始等事实；扩展 扩展自己归约。每条日志下面写着事件类型（扩展事件带扩展 id 前缀）、来源与由哪条事件引出。请求里绿色左边线是与同一路径上一次请求相同的前缀（缓存命中），橙色是新增的，虚线框是会变的槽（只这一次有效、不进日志）。真实系统里回退会写一条树外的 leaf_changed，沙盒省略了。

6. 状态：片、作用域、共享

一个扩展可以有几片状态，每片一个作用域：

path(初值) 跟着对话路径走

回退、fork 之后自动回到那一刻的值。例如提醒的计数、没送达的改动、写手记下的字数、“工作区焦点送达到哪了”。

收 path 事件：用户消息、回复、工具结果、运行开始与结束、会话创建……

session(初值) 在树外

不随回退变。例如人设、库结构、工作区焦点本身。

只收 session 事件：settings_changed、leaf_changed、profile_changed 与扩展声明成 session 的事件。要从 path 事件得到一个不随回退变的值，在反应里 ctx.set 写进 session 的片（否则回退后再走一遍会重复计数）。

不是状态的东西

  • 内存缓存：连接、索引句柄；丢了要能重建
  • 配置：经 ctx.settings 读
  • 内核的状态：工具集、运行状态经 ctx.tools、ctx.run；历史经 core.history 的选择器

默认私有，经选择器共享

别的扩展只能读 exports 导出的选择器：ctx.read("nbook.history", "pendingChanges")。插件经声明合并登记它导出了什么，读的一方得到类型，名字拼错是编译错误。同一个 Profile 自带的扩展之间可以读原样（ctx.own(id)、Profile 模板里的 state.own(id)，也有类型）。

只读、确定

  • 状态与选择器的结果都是只读的；开发模式下冻结，原地修改直接失败
  • 归约出错不挡日志：叶子照样前进，那一片保持原值并写诊断；重放时同样出错、同样保持
  • 每条事件写入时记下它之后的 path 与 session 状态这一对；反应读的就是这一对
为什么状态由日志归约，而不另存一份？ 状态要跟着对话路径走：回退到第 3 次发言，提醒计数也要回到 3。存在内存里，回退和重启都不对；另存状态文件，要给树上每个节点存一份才回得去（那就是又一份日志），而且日志写成了、状态没写成时两边会对不上。只有日志一个真相源，换一片叶子重新归约就对；换 Profile 或插件清单时也照日志从头重新归约，新加的扩展立刻知道过去发生了什么。

7. 视图：模板、槽与缓存

“视图”指整个“状态 → 请求”这一步：core.history 把日志投影成消息并按时间切成三段，扩展往有名字的槽里交内容，Profile 的 prompt 是模板，决定这些摆在哪。请求的内容是块，每块记着来源（事件 id、slot:名字@扩展、fixed），所以模型分得清哪句是用户说的，缓存比对也能定位到块。

节点取什么本轮第一次请求ReAct 中途的请求
<History />本轮开始之前的全部对话事件（处理过压缩）以前各轮不变
<Input />本轮的用户输入；没有新输入的“继续”运行为空有值仍是同一条
<Transcript />本轮里除输入之外的对话事件：持久的提醒、回复、工具结果、插话只有持久的提醒越来越长
<Slot name>扩展交的内容，每次请求现算当前值当前值；上一次的值不留下

缺省布局（Profile 不写 prompt 时）

<System>{system}<Slot name="*" stable /></System>
<History /><Input /><Transcript />
<Slot name="*" volatile />
  • 只写了 <History /> 时，<Input />、<Transcript /> 依次接在后面
  • 单轮模板可以不放 <History />，把 <Input /> 放进一条固定消息；输入带的 payload（例如选区）从 read("core.history", "input") 读
  • 容器（System、User）里每个子节点一段；行内（P、Tag）的文字与表达式直接相连

槽、现取的数据与渲染

  • contribute: {"word-count": {volatile: true, value}}：声明与内容写在一起；* 必须写 stable 或 volatile
  • 两个扩展交同名的槽各成一块；有意共用都写 shared: true，否则写“槽撞名”诊断
  • sample：每次请求前现取（剩余额度、选区），值按内容寻址存一次，记进 model_started；预览过去的请求用记下的值
  • render 写在 Profile 与扩展上，对历史、本轮输入、本轮记录一律生效；写在 <History> 节点上是模板错误（事件从本轮挪进历史时会变样）

缓存：放在哪里，代价是多少

服务商的提示词缓存按前缀命中。内核拿每次请求与同一条路径上最近的那次请求比（模型、参数、工具集也算前缀），算出要重算的 token，超过阈值写诊断并写出两侧的来源。下面是同一会话里连续两次请求：

写法同一轮里下一轮
会变的槽放在最末尾（缺省布局）只丢最末尾的槽只丢最末尾的槽
会变的内容由反应写成事件（持久的提醒）全部命中全部命中
会变的槽放在 <Input /> 前面从槽开始往后全部失效上一轮整段失效一次
会变的槽放在系统提示词里全部失效全部失效

spike 三轮对话：缺省布局重算 0 token；槽放在输入前约 4,300 token 并给出诊断。确实要这样放的（单轮任务，或明知代价）写 <Slot name="outline" cacheCost="accepted" />，诊断降为 info。

8. 副作用与拦截

四个副作用（输入、模型调用、工具执行、压缩）各有一条拦截链，一层套一层：外层是插件（按依赖排序、同层按 id），里面是 Profile，最里层是真正干活的。每层拿到 next：改了再调、调两次（重试）、不调（拦下）都可以。

每层做了什么
点“运行”。

各入口读到的是哪一刻的状态

reduce这条事件之前的自己那片
react这条事件写入之后
sample、contribute、prompt、模型拦截这次请求所在的叶子（预览时是被预览的叶子）
工具拦截发出这批调用的回复所在的叶子：同一批调用看到的世界相同

出错时

reduce那一片保持原值，叶子照样前进
react、sample、contribute这次的结果丢弃或缺席
render用缺省渲染
输入拦截、模型拦截跳过这一层；模型拦截在 next 之后出错用里层的回复（模型已经回复、花了钱，不丢）
工具拦截缺省拒绝这次调用
Profile 的 prompt这次请求算不出来，运行以 error 收口

每条都写带扩展 id 的诊断。

审批永远在工具链的最里层：扩展的放行只能免掉审批模式本来要弹的询问，盖不过用户配置的拒绝、工具声明的拒绝与只读模式。预览时模型链也会跑，只是最里层不发请求、把请求截下来，所以预览看到的就是最终请求。模型链的最里层是 nbook.models 的适配器：把 ModelRequest 转成 OMP 的 Context，调 streamSimple，消费事件流（增量推界面，done 得到完整回复，error 与中止交回失败）。

9. 内核的保证

缺省行为尽量做成和插件同一个形状的内置扩展；内核只留下必须固定的部分。下面是它对扩展作者做的保证，每一条在 spike 里都有对应的场景检查。

保证怎么做到
事实先落盘：崩溃后知道发生到哪了发模型请求前写 model_started，执行工具前写 tool_started；重新打开时 recover() 把开始了但没结果的工具调用结算为“结果未知”，没回复的请求写 model_failed，运行以 interrupted 收口，之后的请求合乎协议
单写者：日志顺序不取决于谁先到所有写入口（发送、外部事实、设置、回退、换 Profile、压缩、恢复）排进同一条队列，前一个连同它的反应做完后一个才开始；运行中到达的进运行的收件箱，在下一个边界（下一次模型请求之前）按到达顺序写入
中止可收口ctx.signal 贯穿反应、sample、拦截、模型与工具；不合作、卡住不返回的由内核接管（内核等的每个 Promise 都与中止赛跑）；没完成的工具调用写“已中止，结果未知”，运行以 aborted 收口，迟到的结果不写日志
并行工具一个回复里的工具调用是一批：shared 的并行、exclusive 的单独跑；结果按调用顺序写入，整批写完后派发反应，每条结果的反应都看整批写完之后的状态
重启后一样加载前校验日志（id 唯一、seq 递增、父节点在前、形状合法、幂等键不重复），不过就拒绝打开；当前叶子照 leaf_changed 恢复；预览过去的请求用那次请求记下的 now、samples、session 状态与设置
名字撞不了、来源可信扩展事件自动带扩展 id 前缀，内核事件只能由内核写；未知来源写不了事件；扩展 id 有格式、不能重复；同一来源同一个幂等键只写一次，命中时反应也不再跑
状态确定状态只能是普通数据（Map、Set、Date 被拒绝），只读；归约出错那一片保持原值、叶子照样前进；换 Profile 时照日志从头重新归约，profile_changed 记下内容哈希
请求合乎协议最终请求过内核校验：工具调用与结果成对、角色顺序、工具名合乎服务商规则；历史投影被替换过也一样
防循环、防卡死反应链最多 3 层、“接着做”连续最多 3 次、反应与 sample 有时限
审批不可绕过审批与只读模式在工具链最里层

内置扩展

core.history历史投影；Profile 用 render、filter 定制，确实需要时整个替换（只有 Profile 能，插件不能）
core.compaction压缩的触发、方法顺序、恢复流程；不能替换，方法经 agent.compactionMethods 贡献
core.title标题；用户设置里关掉

压缩

经压缩拦截链，最里层是压缩方法。结果是一条压缩事件 {method, summary, firstKept, …}：core.history 把 firstKept 之前的换成摘要、之后的原样保留；种子由 Profile 对压缩事件的反应重写。旧的条目都还在日志里，界面照样能看。

10. 生命周期

扩展插件激活→声明登记→每个会话装配（id 格式与重复、依赖排序、replaces 权限）→换 Profile 或插件停用时摘下
会话创建（session_created 带 initial）→打开（校验、归约、recover）⇄空闲 / 运行中 / 等用户→关闭
运行受理→输入→循环：边界 → 请求 → 回复 → 工具批次→结束（出错、中止都收口）
一条事件写进日志→全部归约→全部反应→追加的事件各走一遍（最多 3 层）

没有单独的钩子点：“会话已创建”“会话已打开”（不进日志）“运行开始”“最终回复”“压缩完成”“运行结束”都是事件，扩展在 react 里按类型处理。换 Profile 或插件清单（运行收口之后）：内核换上新的扩展，照日志从头重新归约，写 profile_changed（新的清单、顺序与内容哈希）；旧扩展写的事件留在日志里，没有扩展认它们就不起作用，改了含义的靠版本区分。

ctx 给

  • 自己的：mine（各片）、ev（自己的事件构造与守卫）、set、message
  • 读：read（别人导出的选择器）、own（同一 Profile 的兄弟扩展）、settings、tools、run、file(uri)
  • preview 标志、signal
  • 主动接口 complete、invokeTool、ask、compact：实现时定（待定项 8）

不给

  • 改工具绑定（归用户）
  • 改会话设置（归用户；按请求换模型用模型拦截）
  • 服务商格式的原始请求体
  • 读别的扩展的原样
  • 定时器与界面（插件自己的入口与贡献点能做）

11. 写一个扩展

文件改动通知：片、事件、归约、反应、导出

export const fileNotice = defineExtension({
    id: "nbook.history",
    tags: ["history"],
    state: {pending: path<string[]>([])},
    events: {
        fileChanged: ext<{path: string}>(),   // 类型是 "nbook.history/fileChanged"
        notice: conv(),
        delivered: ext(),
    },
    reduce: {
        // 返回 undefined 表示不变，不必写“不认识的事件原样返回”
        pending: (p, e, ev) => (ev.fileChanged.is(e) ? [...p, e.data.path] : ev.delivered.is(e) ? [] : undefined),
    },
    exports: {pendingChanges: (m) => m.pending},
    react(e, ctx) {
        if (!is(e, K.user) || ctx.mine.pending.length === 0) return;
        return [ctx.ev.notice({text: `用户改过这些文件：${ctx.mine.pending.join("、")}`}), ctx.ev.delivered({})];
    },
});

// 别的插件读它导出的选择器：登记一次，读的一方得到类型，名字拼错是编译错误
declare module "nb-harness" {
    interface ExtensionExports {"nbook.history": ExportsOf<typeof fileNotice>}
}

旧机制新设计变化
七种提醒写在 AppendingSet，每个 Profile 各列一遍（WorkspaceFocusReminder 在 9 个内置 Profile 里）各归拥有那份数据的插件，作为全局扩展Profile 里零行；插件不改 Profile 就能加上下文
TaskReminder 靠 "agent.tasks" 字符串读 customState任务清单由 todo 工具的结果归约，提醒和工具在同一个插件里没有跨模块的字符串约定
ModelContext 每次插在本轮之前，下一轮挪位置，上一轮那段缓存失效（从 prompt-order.ts 推断）nbook.sql 交稳定的槽，库结构变了才变每轮不再丢一段缓存
context() 每次渲染读人设人设是 session 的片，打开、设置变化、文件被改时读一次prompt 是纯函数
HistorySet 只在历史为空时写seed() 在会话创建与压缩后写；能读调用方给的 initial压缩后种子自动重写
“写作必须交给 writer”只写在提示词里自带的工具拦截挡住能挡住
ModeReminder 专用的 ModeSlotProfile 级 render 覆盖任何扩展事件，键用扩展导出的事件类型一种机制
固定顺序 History → ModelContext → AppendingSet → CurrentUserInput模板定位置；提醒是日志里真实的事件顺序看日志就知道
强在哪里
  • 规则能挡住（工具拦截）
  • 插件能给不认识的 Profile 加上下文
  • 回退、重启、预览自动正确，压缩后种子重写
  • 缓存不再每轮丢一段
  • 主创的上下文部分约 120 行 → 约 60 行；Opus 照新 API 重写的四个例子合计 200 行 → 130 行
代价
  • 完整上下文分散在多个插件里，要靠预览看全（每块标了来源）
  • 人设改了，系统提示词跟着变，缓存失效一次
  • 扩展的设置要能在 Profile 设置里按 Profile 显示
  • 公开 API 的名字比第一版多（约 56 → 77），换来类型、诊断与组合

13. 常见错误

多数写错的地方现在会被编译器或内核诊断抓到，剩下的靠纪律：

写法后果谁抓
在 reduce、contribute、prompt 里读文件、取当前时间重放与回退得到不同的结果纪律：I/O 放 react 或 sample，时间用 view.now
session 的片去归约用户消息永远是初值（session 的片只收 session 事件）纪律：在反应里 ctx.set
把字数、时间放进系统提示词的槽每次请求整段缓存失效诊断 volatile-in-system、cache-miss
片名、事件字段、选择器名、自带扩展 id 拼错—编译错误（typetest.ts 八种）
Profile render 的事件类型拼错覆盖静默失效装配诊断 render-unknown-type
在 <History> 上写 render事件从本轮挪进历史时变样模板错误
想让模型接着写，却只返回了事件不会再请求纪律：返回 {events, continue: true}
两个插件用了同一个槽名内容混在一起诊断 slot-collision（有意共用写 shared）
单轮模板没写 globalExtensions: "none"别的插件的提醒进了请求info 诊断
改了扩展事件的含义却没升版本旧会话重新归约出来的状态不同纪律：升 v

15. 状态与待定

提案第三稿（draft）。没有在 spike 里验证、实施时第一个切片要验证的：真实 OMP streamSimple 的适配器、压缩的触发与方法顺序及之后的公共流程、真实的日志存储与进程重启、扩展的 dispose。

按审查改动、改变了已定写法、需要你确认的：

  1. 扩展从单片状态改为多片（path、session），pathState、sessionState 改为片的构造函数与 ctx.set。
  2. 扩展事件改由 events 声明，类型自动带扩展 id 前缀。
  3. render 从 <History> 节点上移到 Profile 与扩展上。
  4. “接着做”要显式写 continue。
  5. 相邻的 user 消息不再在内核里拼接，内容改为块。
  6. 预览的“视图输入”记进日志（model_started）。
