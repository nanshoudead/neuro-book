## 第二版新发现

### 1. 空闲入口与收尾仍可并发写日志
- **严重程度**：阻断；**类别**：不变量 / 正确性
- **位置**：`spike/kernel.ts:537-565,819-827`。
- **现象**：`external()`、`changeSettings()` 在 `running` 为 false 时直接 `append` 并启动各自的 `dispatch()`；`send()` 的 finally 先把 `running` 置 false，再异步 `drain()`。没有统一写锁。临时实验同时调用两个 idle `external()`，第二条反应先写，第一条反应随后挂到第二条事件上：输出为 `second(parent=e3,cause=e3)`、`first(parent=e4,cause=e2)`。
- **为什么是问题**：同一会话不再有唯一提交顺序；反应完成时的当前叶子可能已经被另一入口推进，因果链、父节点和回放顺序取决于 Promise 时序。finally drain 与新 external 也能交错，违反 t03/t07 的单写者合同。
- **如何核实**：运行 `/tmp/review-w00032-t20-design/r2/lab-omp/new-findings.ts`，查看 `idle-race`；静态对照 `external()` 的直接 `append` 与 `dispatch()` 的异步反应。
- **建议改法**：所有入口，包括 idle、finally drain、open、rewind、reconfigure，都进入同一个提交队列；队列拥有 append、apply、dispatch、边界和收尾，禁止任何公开入口直接 append。
### 2. 幂等键命中后仍重复派发旧事件
- **严重程度**：阻断；**类别**：正确性 / 幂等
- **位置**：`spike/kernel.ts:289-315,536-540`。
- **现象**：`append()` 命中 `source|key` 时返回已有 Entry；`external()` 不区分“新写入”和“已命中”，仍把该 Entry 交给 `dispatch()`。同一个 `key` 两次 external 的日志只有一条事实，但反应事件写了两次；实验输出 `duplicate-dispatch 2`。
- **为什么是问题**：幂等合同要求重复通知既不重复事实，也不重复副作用。当前文件监听重连会重复检索、提醒或写文件；如果反应输出没有 key，还会让日志出现重复对话，重放和实时结果分叉。
- **如何核实**：运行临时脚本的 `duplicate-dispatch` 场景；第一轮场景 39 只断言事实条数，没有断言重复 external 后的反应条数。
- **建议改法**：append 返回 `{entry, inserted}`；幂等命中时不 dispatch、不更新因果链。load 也要拒绝同一作用域内重复 `(source,key)`，或定义可验证的迁移规则。
### 3. 中止无法接管挂起的 sample 与扩展调用
- **严重程度**：阻断；**类别**：正确性 / 中止
- **位置**：`spike/kernel.ts:570-587,461-478,658-670`；`api.ts:194-195`。
- **现象**：`view()` 直接 await `sample`，`runReact()` 只用 timeout，`modelChain()` 不包整个拦截链的 abort race。`abort()` 只 abort 当前 controller。临时实验让 sample 永不完成：`abort()` 后 60 ms 仍为 `timeout`，`running=true`，日志停在 `session_created/run_started/user`。
- **为什么是问题**：t07 要求宽限后运行回到空闲并写中止收口；现在一个失控插件就能永久占住会话，后续输入、回退和恢复都无法执行。仅把 signal 放进 ctx 不等于内核会接管不合作的 Promise。
- **如何核实**：运行 `/tmp/review-w00032-t20-design/r2/lab-omp/new-findings.ts` 的 `abort-sample`；检查 sample 与 react 的 await 路径没有 race/代次屏障。
- **建议改法**：每个 sample/react/interceptor 建立带代次的调用控制器；宽限到期由单写者强制收口，迟到结果只能诊断、不能写日志，并明确不可中断 I/O 的副作用结算。
### 4. 未知 source 可以伪造内核事件
- **严重程度**：重要；**类别**：安全 / 正确性
- **位置**：`spike/kernel.ts:280-287,536-540`。
- **现象**：`check()` 只有在 `source` 能在已装配扩展中找到时才检查扩展前缀；未知 source 走 `!ext` 分支，只要 `type` 属于 `KERNEL_TYPES` 就放行。公开 `external("ghost", {type: K.user, ...})` 被接受，路径出现伪造的 user，实验输出 `unknown-source-kernel ["forged"]`。
- **为什么是问题**：提案明确扩展写不出内核事件。宿主或插件 id 配置错误时会静默绕过这条边界，伪造输入、设置或运行控制事件，污染历史投影和反应计数。
- **如何核实**：运行临时脚本的 `unknown-source-kernel`；逐行对照 `check()` 对未知 source 的分支。
- **建议改法**：内核事件只允许内部不可伪造的写入口；`external()` 必须先查已登记扩展并拒绝未知 id，扩展事件同时校验声明的 cls/scope/version，不能只按字符串前缀。
### 5. 工具批次的反应快照不是批次完成后的同一状态
- **严重程度**：重要；**类别**：不变量 / API
- **位置**：`spike/kernel.ts:835-847,318-334,485-492`。
- **现象**：`toolBatch()` 先逐条 `kernel(tool_result)`，再一次 `dispatch(settle())`；但每条 Entry 在 append 时就把 Pair 存进 WeakMap。批次反应因此分别读到自己的结果之前状态。实验两个工具结果的反应读到 `transcript:2`、`transcript:3`，而不是同一份完整批次状态。
- **为什么是问题**：代码注释和提案都把工具结果定义为“整批完成后派发”。扩展若在结果反应中更新计数、检索或判断是否继续，会因调用顺序看到不同世界；批次重放与并发执行的状态语义不明确。
- **如何核实**：运行临时脚本的 `batch-reaction`；现有场景 25 只检查工具拦截的发送前快照，没有检查 tool_result 反应快照。
- **建议改法**：明确合同：若批次反应应看完整批次，先原子写入全部结果并为整批生成一个 post-batch Pair；若保留逐条 Pair，就不要称为批次级反应，并在 API 中显式暴露顺序语义。
### 6. reconfigure 的 hash 不能识别 Profile 内容变化
- **严重程度**：重要；**类别**：正确性 / 恢复
- **位置**：`spike/kernel.ts:374-387`。
- **现象**：`profile_changed.hash` 只对 `[profile.id, extensions.map(id)]` 做 hash。两个同 id、同扩展清单但 system 文本分别为 A/B 的 Profile 重配置后，实验输出同一个 hash `4e594d0795145c2c`。
- **为什么是问题**：日志无法证明重放时使用了哪一版 Profile；提示词、工具声明、依赖顺序或 reducer 代码变化可以改变归约/请求，却被记录成同一配置。进程重启或换实例不能按 hash 校验合同。
- **如何核实**：运行临时脚本的 `reconfigure-hash`；静态读 hash 输入没有 `system/tools/extensions` 内容。
- **建议改法**：记录规范化的 Profile/扩展清单版本与内容 hash，包含工具声明、模板/渲染与依赖顺序；代码实现版本变化要有迁移或拒绝加载的规则，不能把 id 当内容版本。
### 7. freezeNew 对 Map/Set 只冻结外壳
- **严重程度**：重要；**类别**：不变量
- **位置**：`spike/kernel.ts:115-124`；`api.ts:124-131`。
- **现象**：`freezeNew()` 通过 `Object.keys()` 递归普通对象；`Object.freeze(new Map())` 不冻结 Map 的内部槽。`path(new Map())` 合法，扩展在冻结状态上执行 `ctx.mine.m.set("x", 1)` 不报错，状态在无事件情况下变成 1，实验输出 `map-freeze [] 1`。
- **为什么是问题**：提案承诺状态和选择器只读、原地修改应失败。任意 Map/Set/Date/自定义可变容器都会绕过冻结，破坏日志归约和回退确定性。
- **如何核实**：运行 `/tmp/review-w00032-t20-design/r2/lab-omp/freeze.ts`；类型层 `SliceSpec<T>` 对 T 没有限制。
- **建议改法**：限制状态为可验证的 immutable 数据形状并在注册/加载时 schema 校验，或对 Map/Set 转不可变表示、选择器输出做深不可变封装；不要把浅 `Readonly` 与运行时只读混作同一合同。
### 8. 模型拦截失败没有扩展诊断或 model_failed
- **严重程度**：重要；**类别**：失败语义 / 可观测性
- **位置**：`spike/kernel.ts:658-670,781-818`。
- **现象**：模型拦截器抛错直接穿过 `modelChain()`；`send()` 只追加 `run_ended(error)`，不写扩展诊断，也没有 `model_started/model_failed`，实验输出 `model-interceptor-error [] ["user","run_ended"]`。
- **为什么是问题**：提案把拦截器纳入失败与超时合同，开发者无法知道是哪个扩展拒绝/崩溃；更换模型、重试或审批失败也无法从日志区分“未发 provider 请求”与“provider 请求失败”。
- **如何核实**：运行临时脚本的 `model-interceptor-error`；对照工具拦截专门的 catch（`kernel.ts:875-884`）。
- **建议改法**：每层拦截统一捕获、带扩展 id/request id 写结构化诊断，并按钩子类型应用 deny/ignore/abort 策略；模型链未到 terminal 时写可重放的失败原因。
### 9. load 不检查幂等键唯一性，回放后 key 索引可漂移
- **严重程度**：重要；**类别**：日志完整性 / 幂等
- **位置**：`spike/kernel.ts:344-360`。
- **现象**：`load()` 只检查 id、seq、父节点，遇到两个相同 `source|key` 的已持久条目时直接逐条写入 `keys`，后者覆盖前者；日志本身保留两条事实，下一次 append 的幂等命中对象取决于最后一条。
- **为什么是问题**：幂等键是跨重启去重依据，索引与日志不一致会让重启前后的重复通知行为不同，并掩盖存储损坏或迁移重复。
- **如何核实**：静态读 `load()` 没有 `(source,key)` 集合校验；构造两条合法 seq、不同 id 但同 source/key 的 Entry 即可观察覆盖。
- **建议改法**：加载时校验 `(source,key)` 唯一性并报结构化损坏/迁移错误；若允许同键多版本，定义 scope、替换规则和可验证索引重建。

## 交开发者之前必须解决的

当前稿**不能按“第三稿已可定方向、实现细节以后再说”直接通过**。事件溯源、Profile 作为最终组装者、扩展四种能力这条大方向可以保留，但以下合同必须先补清并在 spike 或真实运行时验证：

1. **单写者与提交边界**：修复第 1 条新发现，并覆盖第一轮第 16 条。所有 idle/运行中/finally/open/rewind/reconfigure 写入必须经过同一队列，明确外部事实、插话、设置与收尾的顺序。
2. **幂等与事件权威**：修复第 2、4、9 条新发现，并补第一轮第 22、27 条。幂等命中不能再次派发；未知 source 不能写内核事件；load 必须校验 key、版本、类型、scope、data 与树结构。
3. **中止、失败和收口**：修复第 3、8 条新发现，并补第一轮第 1、15、17 条。sample、react、每层 interceptor、模型流、工具批次都要有超时/取消/宽限/迟到结果屏障；所有失败都要有可重放的失败事实和 `run_ended`。
