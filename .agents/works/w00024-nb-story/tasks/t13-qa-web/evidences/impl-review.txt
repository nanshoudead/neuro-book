# w00024 t13 网页实现审查报告（web 部分，审查固定在 ad8c8494c）

### 1. `ended` 帧到、重读（qa.get）回来之前，运行这一轮的消息被分错：提问 id 变掉、整轮并进上一轮
- **严重程度**：重要；**类别**：正确性 / 不变量
- **位置**：`packages/nb-story/src/web/qa/source.ts:106`（`attachedRun` 对已结束且已保存的运行返回 null）、`:182-185`（`ended` 帧只更新 `state.run` 然后 `changed()`）、`:192-194`（`end` 里才 `load(false)`）；`turns.ts:88-128`
- **现象**：`ended` 帧（`saved: {ok: true}`）到达后，`messagesOf` 里 `attachedRun` 立刻为 null，`running` 变 null，但转录里这一轮的消息还在、记录还是旧的（少一轮）。`composeMessages` 只按记录的各轮切，这一轮的消息被全部分到最后一个记录轮，提问 id 从 `q:<对话>:2` 变成日志的 `h4`，乐观提问的“补一条”逻辑也不再生效，没核实的出处（来自 `run.result.reply.unverifiedRefs`）也不再挂。随后 rAF 的 flush 会把这个错误形状画出来（`ended` 与流关闭几乎同时到，`load(false)` 的 qa.get 往返几乎必定晚于下一帧画面），等 qa.get 回来才又变成 `q:c:2`。
- **为什么是问题**：`turns.ts` 头注释明说“提问 id 固定为 `q:<对话 id>:<轮号>`……乐观的、补的与真的前后是同一个 id，视图按 id 复用这一轮的组件，展开状态不丢”。每次看着一轮答完，这条不变量就在结束的一瞬间被破坏：这一轮的提问与回复组件被重新挂载（用户展开的思考、工具调用折叠状态丢失，答案卡片重新量宽），并有一两帧版式跳动。`source.test.ts` 的“看着它结束就重读”只断言最终结果，没有断言中间状态。
- **如何核实**：真实调用链的实验，写在 `/tmp/claude-1000/review-t13-impl/exp/exp.test.ts`（用 `source.test.ts` 的 harness，不绕过 `createQaSource`）：运行中收 snapshot、log（提问 h4、回复 h5），再发 `ended`（saved ok）、让 qa.get 一直不回。输出：
  `before [["q:c:1","user"],["h3","assistant"],["q:c:2","user"],["h5","assistant"]]`
  `after-ended [["q:c:1","user"],["h3","assistant"],["h4","user"],["h5","assistant"]]`
  命令：`bun test /tmp/claude-1000/review-t13-impl/exp/exp.test.ts`。
- **建议改法**：让“已结束已保存”的运行在重读完成前仍按接在后面处理。例如源里加一个 `reloading` 标记（`ended` 帧与快照里已结束已保存时置位，`load` 成功后清除），`attachedRun` 在它为真时不因 `saved.ok` 返回 null；或者 `ended` 帧到达时先不写 `state.run`，等重读的结果一起换。并在 `source.test.ts` 补一条中间状态的断言（提问 id 前后同为 `q:c:2`）。

### 2. 退避次数在每次 qa.get 成功就清零：推送连不上（或一连上就被断开）时永远 1 秒一轮，退避不生效
- **严重程度**：重要；**类别**：正确性 / 安全与性能
- **位置**：`packages/nb-story/src/web/qa/source.ts:222`（`attempts = 0`）；`:144-151`（`retryLater`）、`:189-198`（`end`）
- **现象**：`attempts` 在 `load` 里 qa.get 一成功就清零，而不是在订阅真的收到快照之后。只要 qa.get 好使、`/api/qa/events` 失败（5xx、401、反向代理缓冲后断开、服务端因积压断开后再次积压），每一轮都是 qa.get 成功 -> 清零 -> 订阅失败 -> `retryLater` 取 `retryDelay(0)` = 1 秒。
- **为什么是问题**：注释与 Spec 都写的是 1、2、4…最多 15 秒退避；这条路径实际固定 1 秒，运行中的页面对服务每秒打一次 qa.get（读记录与整份日志）加一条新的流，直到运行结束；多个标签页叠加。积压断开恰恰是服务端过载的信号，再以最短间隔重连会加重它。`source.test.ts` 的退避用例只让 qa.get 失败，覆盖不到这条。
- **如何核实**：`/tmp/claude-1000/review-t13-impl/exp/exp.test.ts` 的“订阅总是立刻断开”用例（用 `source.test.ts` 的 harness）：连续三次订阅 `end("dropped")`，实测 `delays [1000,1000,1000] gets 4 subs 4`。
- **建议改法**：只在订阅收到 `snapshot` 帧时才清零（`watch` 的 snapshot 分支里 `attempts = 0`），qa.get 成功本身不清零；补一条订阅反复断开时延迟递增的测试。

### 3. `qa.start` 往返期间切换对话：新对话被抢走视线、新对话的草稿被别的对话的草稿污染、原对话的草稿没清
- **严重程度**：重要；**类别**：正确性 / 不变量（触发需在 qa.start 返回前切换，窗口小，但后果是数据串位）
- **位置**：`packages/nb-story/src/web/pages/QaPage.vue:211-239`（`submit`）
- **现象**：`submit` 开头取 `const id = selectedId.value`，`await qa.start` 返回后再读 `composer.value`（此刻是当前选中对话的草稿，不是发出时那个）、`selectedId.value`、`book.qaConversation`，没有核对“还在发出时的那个对话”。
  - 新对话（`id === null`）：用户在等待期间点了别的对话 B。返回后 `acceptSubmission(composer.value, text)` 因 B 的草稿与 `text` 不同而原样返回 B 的 composer；随即 `composers.set(started.conversation, {...B 的 composer, modes: []})`，新对话的输入框里出现 B 的草稿与输入历史；`composers.delete(NEW)` 又删掉了发出时那份；最后 `book.qaConversation.value = started.conversation` 把用户从 B 拉到新对话。
  - 续问（`id !== null`，A）：切到 B 后 `setComposer(accepted)` 写进的是 `selectedId.value`（B）的槽，值是 B 自己的 composer；A 的草稿从未被清，也没记进输入历史，回到 A 时刚发出的问题还留在输入框里，再点发送在这一轮结束后会重复发送。`source?.refresh()` 刷新的也是 B 的数据源。
  - `starting` 是页面级的单个标志，在等待期间也锁住 B 的发送与改变 `run` 状态（B 显示“运行中”）。
- **为什么是问题**：草稿“按对话各存一份”是页面写下的不变量（`composerOf`、`setComposer`），这里读写都用了“此刻的选中项”而不是“发出时的对话”。
- **如何核实**：从代码推断（未跑 e2e）。复现方式：在 `qa.start` 上加人为延迟，发送后立即点另一个对话。
- **建议改法**：`submit` 在 `await` 前固定 `const target = id` 与发出时的 composer；返回后写 `composers`（按 `target` 或新 id）而不用 `composer.value` / `setComposer`；只有 `selectedId.value === target` 时才 `refresh()` 与（新对话时）切换 `book.qaConversation`，否则只刷列表；`starting` 改为按对话记。

### 4. 续问受理后到重读回来之前，页面短暂“空闲”：可再发送、停止钮闪现、问题要等 qa.get 回来才出现
- **严重程度**：建议；**类别**：正确性
- **位置**：`QaPage.vue:229-232、236-238`（`setComposer(accepted); source?.refresh();` 随后 `finally { starting.value = false }`）；`:143`（`running` 取自数据源状态）；`:195-196`
- **现象**：`source.refresh()` 是异步的（`load(false)` 不等待），`finally` 立刻把 `starting` 置 false；数据源状态仍是上一轮结束后的 `run: null / ended`。于是 `canSend` 为真、`run.status` 为 idle，直到 qa.get 往返回来才变成运行中。草稿已清空，所以这一小段时间里用户看到的是“发出去了，什么都没发生”，且可以再提交一次（会撞 `qa_busy`，错误条出现在输入框上方）。
- **为什么是问题**：`starting` 本来就是用来盖住 qa.start 到 `run` 生效之间的空档，被提前放掉。
- **如何核实**：从代码推断；e2e 里可在 `qa.get` 上加延迟观察。
- **建议改法**：让数据源暴露 `refresh()` 的 Promise（或 `loading` 标志），`submit` 等它完成再放掉 `starting`；或续问时直接把受理返回的 `runId/turn` 先写成乐观的 running 状态。

### 6. 流式时每个半截人名都发一次 `entity.card` 请求；失败结果永久缓存

### 1. 停服和删除无法取消阻塞中的准备阶段
- **严重程度**：重要；**类别**：不变量；
- **位置**：`packages/nb-story/src/server/qa-service.ts:185-191,206-228`；`packages/nb-story/src/qa/engine.ts:156-200,260-294`。
- **现象**：`settle()` 只对 `runs` 里的运行调用 `controller.abort()`，对 `preparing` 里的准备没有取消；它随后无上限地等待 `preparing` 的 Promise。`start()` 把 `controller.signal` 只传给了最终的 harness `turn()`，而 `prepareQuestion` 的 `readQaConfigFile`、`openBook`、`book.info`、全读 `source.read` 和恢复日志都没有消费这个 signal。准备阶段任何一个底层 I/O 卡住，`qa.close()`、`qa.remove()` 和 `book.remove` 的 `qa.exclusive` 都一直等不到收口。
- **为什么是问题**：停服回调在 `serve.ts:102-116` 要先等 `qa.close()`，所以服务可能既不撤销登记也不停止监听；删除会一直占用删除门。该路径违反“准备中也要取消并等待后再删/停”的不变量，不是普通模型请求超时。

- **建议改法**：把准备项存成包含 `controller` 与 Promise 的记录，关门时先 abort 全部准备项；引擎在每个准备边界检查取消，并把底层书库/查询调用扩展为接收 AbortSignal 或用可取消的任务包装。没有可取消的底层调用时不能宣称停服可收口；至少应为这类准备失败定义有界的取消/失败路径，并补真实 `qa.remove` 与停服期间准备卡住的收口测试。
### 2. `onProcessTermination` 会抢在同进程的 `onProcessInterrupt` 收口完成前退出
- **严重程度**：重要；**类别**：不变量；
- **位置**：`packages/nb-harness/src/interrupt.ts:25-35`；调用方 `packages/nb-story/src/server/serve.ts:120-126`，相邻协议 `packages/nb-story/src/cli/ask.ts:43-57`。
- **现象**：`postmortem` 会把同一轮登记的清理回调同时启动并等待它们；新 API 的回调却在自身完成后直接 `process.exit(await callback(signal))`。因此同一进程同时登记 `onProcessInterrupt` 与 `onProcessTermination` 时，终止回调一完成就硬退出，其他回调仍可能未完成。该 API 没有把 `onProcessInterrupt` 的 Promise 纳入 `onProcessTermination` 的等待集合。
- **为什么是问题**：如果宿主进程同时有 ask 的“取消并写记录”和 serve 的“停服务并撤销登记”两种收口，SIGINT 会使其中一个收口被截断；记录、登记、锁和监听可能处于半完成状态。文档注释声称“同一轮里别的登记与它同时开始”，但没有说明它会在别的登记完成前退出，公开 API 的组合语义是不安全的。
- **如何核实**：报告目录的 `termination-race-probe.ts` 注册一个 `onProcessInterrupt`（200ms 后写 `interrupt-done`）和一个 `onProcessTermination`（20ms 后返回 0），再用 `process.emit("SIGINT")` 触发真实 postmortem 收口。运行命令：`bun /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00024-nb-story/tasks/t13-qa-web/reports/omp-impl/termination-race-probe.ts`；退出码为 0，`/tmp/nb-story-termination-race.log` 只有 `termination-SIGINT-start`、`interrupt-start`、`termination-done`，没有 `interrupt-done`。

### 3. 已中止的 SSE 请求不会退订，流和心跳可以永久存活

- **现象**：新 API 把宿主回调登记进 postmortem，但没有改变它的清理期限。postmortem 在约 10 秒后自行退出 `128 + signal`，即使宿主回调尚未完成。serve 先等待 `ingest.close()` 和 `qa.close()`，而抽取任务自身的停止兜底期限是 15 秒：需要进入 15 秒兜底的合法停止路径一定到不了撤销登记、停监听与返回宿主退出码那几步。

- **如何核实**：已运行 `bun --no-env-file /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00024-nb-story/tasks/t13-qa-web/reports/omp-impl/termination-deadline-probe.ts`。真实子进程通过公开 `onProcessTermination` 登记 11 秒收口并应返回 1，父进程在 ready 后实际发送 SIGTERM；实测 `exit:143`、`ms:10057`，证据文件只有 `start:SIGTERM`、没有 `done`。此为公开 API 的真实信号运行，不是伪造内部清理时序；15 秒与 10 秒的服务组合从源码核实，未声称已经让产品抽取线程卡到 15 秒。
- **建议改法**：让上游终止协调器允许宿主接管期限和最终退出码，或调整服务的整体停止期限使所有已承诺兜底先完成；不要在一个受 10 秒上限约束的 callback 里宣称无条件等完宿主。补大于 10 秒的真实子进程合同测试，并让 serve 的抽取/问答收口期限与进程退出协议一致。

### 12. 合法的 `__proto__` 环境变量名被 keys 结果静默丢掉
- **严重程度**：建议；**类别**：正确性；
- **位置**：审查 worktree `packages/nb-story/src/server/qa-service.ts:368-373`；`packages/nb-story/src/contract/config-schema.ts:19`。
- **现象**：schema 允许 `apiKeyEnv:"__proto__"`，但 `keysOf()` 用普通 `{}` 和 `keys[name] = boolean` 组装结果。`__proto__` 命中继承的 setter，布尔赋值不会创建 own property，所以接口返回 `keys:{}` 而不是 `{"__proto__":false}`。
- **为什么是问题**：config.get/set 承诺对每个配置变量名给出是否设置；该合法名字的状态缺失，页面只能误认成“保存后才知道”。不构成任意原型污染，因为写入值只有 boolean；影响限定为特殊名字被漏掉。
- **如何核实**：`config-http-probe.ts` 的真实 HTTP 输出 `proto.status:200`、`state:"valid"`、`config.model.apiKeyEnv:"__proto__"`，同时 `keys:{}`。同一运行还验证未知字段名含假密钥时 `state:"invalid"` 的 problem 不回显该字段，`leaked:false`。
- **建议改法**：用 `Object.fromEntries()` 或 `Object.create(null)` 构造字符串键字典，保留合法名字，不必收紧环境变量合同。补特殊名字和三个位置同名去重的结果测试。

### 13. 服务测试未覆盖计划承诺的准备期门和未保存终态

## 未发现问题的方面

- **接纳门的正常交错**：在当前单线程无 reentrant observer 的实际 HTTP 调用下，`preparing` 登记早于 `start` 第一次挂起；准备结束后的关门复查与 `abandon()` 在删除/停服等待的 preparation Promise 释放之前完成；计数门在重叠删除期间不会被较早完成的一方提前打开。仔细检查后没有发现正常准备完成时漏接纳或漏等待的问题；底层 I/O 永不完成的替身实验不作为产品发现。
- **运行/保存收口**：运行保持 running 直至引擎保存返回；`settle` 等待 done 后才移除，HTTP 正常删对话/删书与 SIGINT/SIGTERM 的已运行路径通过。书的跨进程代际隔离缺陷另见第 9 条。
- **事件顺序**：pending message_update 在其它事件、日志与 ended 前 flush，timer 被清理；失败订阅者从各自集合移除，不中断其它订阅者。SSE 的真实慢连接上限与 12 秒安静模型测试通过。预中止 Request 的直接 handler 实验没有真实 HTTP 可达证据，不计发现。
- **脱敏与配置输入**：真实 provider 的 401 回显密钥在输出、日志与事件扫描中不泄漏；网页白名单删掉 assistantMessageEvent、agent_end.messages 和 provider 原始附属字段。配置三处 apiKeyEnv 的已知密钥形状拒绝及未知字段拒绝通过；invalid 配置正文不回传。无法可靠区分任意随机密钥与变量名是已记录取舍，不重报。
- **schema 与记录兼容**：没有发现本轮 QA_METHODS 正常返回被输出 schema 拒成 500 的问题。QaTurnSchema 的 logFrom 可选；旧一问一条记录照常读取，新旧 logFrom 混合轮可续问。运行结果的 logFrom 与日志序号连续性一致。
