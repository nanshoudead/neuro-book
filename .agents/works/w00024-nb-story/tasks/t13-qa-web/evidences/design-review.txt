### 1. 调用方对话 ID 必须满足记录层格式
- **严重程度**：重要；**类别**：正确性
- **位置**：计划“引擎”第 35–36 行、“合同与路由”第 79 行；`packages/nb-story/src/core/qa-records.ts:138-143,178-180`
- **现象**：计划允许调用方为新对话提供任意 `conversationId`，但 `QaRecords.save()` 只接受 `/^\d{17}-[0-9a-z]{6}$/`。新对话开始时该值直接替代生成 ID 并用于 `createMemorySessionLog`；结束保存时不符合格式会抛错，最终 `recordSaved: false`，网页却仍持有该 ID，无法列出或续问。还未规定 ID 在同一本书内唯一；复用一个已有 ID 时 `expectTurns: 0` 保存只会冲突，调用方看不到唯一性规则。
- **为什么是问题**：调用方生成 ID 的契约与持久层公开约束不相容，后续实现按计划传入 UUID 或普通随机 ID 都会静默变成不可持久对话。仅把 ID 换成记录格式也不能解决跨页面重复 ID 的行为与碰撞报告。
- **如何核实**：代码核对：`RECORD_ID` 与 `save()` 的入口校验；`startNew()` 当前使用 `newQaRecordId()`。再按计划传入 UUID 与已存在 ID 跑 `QaRecords.save()`，前者抛 ID 不合法、后者返回冲突。
- **建议改法**：优先由引擎继续生成符合 `QaRecords` 的 ID，并在 `qa.start` 响应中于模型启动前返回；若必须由调用方指定，则将 ID 格式与唯一性明确纳入合同并校验冲突为稳定的客户端错误，且保证该形状符合 `QaRecords` 与文件名约束。
### 2. 未保存的一轮刷新后没有可读结果
- **严重程度**：重要；**类别**：正确性
- **位置**：计划“服务端运行”第 65 行、“合同与路由”第 77–84 行；`packages/nb-story/src/qa/engine.ts:263-270`、`packages/nb-story/src/core/qa-records.ts:271-289`
- **现象**：保存失败时引擎返回本轮 `QaTurnResult` 和 `recordSaved: false`，但 `QaFrame.turn_end` 只计划推该结果；运行中内存条目未说明在运行结束后保留。新对话保存失败时 `qa.get` 必然没有记录，续问保存失败时 `qa.get` 仍只读上一轮记录及旧日志。刷新、订阅断开后，完整答案与本轮会话日志均无法取回。
- **为什么是问题**：Spec 明确结果不因保存失败而变；网页在收到一次性 `turn_end` 后刷新即丢失用户可见的回答，且新对话没有列表入口可重新打开。`recordSaved: false` 不是恢复通道。
- **如何核实**：构造 `QaRecords.save()` 返回 `conflict` 或写失败的运行，观察 `qa.get` 只返回旧记录/未找到；计划中的 `QaFrame` 没有 `conversation` 或会话日志字段，且活动运行结束后未定义保留期限。
- **建议改法**：明确运行结束但未保存时的读取合同：例如服务在本进程内保留不可变的终态结果与日志，并让 `qa.get/list` 可返回“未保存”状态直到服务重启；或在 `turn_end` 内提供完整可显示且可恢复的转录并让页面缓存。不得把虚构的 `conversation.log: null` 当作可持久记录。
### 3. 订阅补发与实时通知必须有原子交接
- **严重程度**：重要；**类别**：正确性
- **位置**：计划“服务端运行”第 53、65 行、“切片 1”第 117 行；`packages/nb-session/src/memory-log.ts:34-44,69-88`、`packages/nb-harness/src/harness.ts:141-160,244-280`
- **现象**：计划要求订阅“先补发已有日志，再推后面的条目”，但没有规定捕获补发截止 `seq`、队列化通知或订阅注册时序。若先 `read()`、之后注册 listener，append 可发生在两步之间而永远漏掉；若先注册 listener、再 `read()`，append 通知与补发会重复，且跨异步写队列的通知可能在后续 seq 前到达。`createHarnessTranscript.applyLogEntry()` 是单条接口并按 `seq <= lastSeq` 直接忽略，不会缓存乱序空洞，先收到 seq 12 会使随后 seq 11 被丢弃。
- **为什么是问题**：订阅重连后的 transcript 可能永久缺用户消息、工具结果或 `run_end`；事件只补运行态文本，README 明确日志才是错误与用量权威，缺日志不能靠事件修复。
- **如何核实**：按共享对象时序：补发读完 seq 10，append seq 11，注册 listener；或 listener 收到 seq 12 后补发 seq 11。检查 transcript 的 `lastSeq` 单调去重实现，第二种会丢 seq 11。
- **建议改法**：在持有运行记录的串行队列/锁中原子确定 replay watermark 并登记订阅，再将 `(watermark, entries > watermark)` 依序送入每个订阅者；给每订阅者串行发送队列，处理断开与慢消费者；单进程内的 append 通知应在 `append()` 返回已编号条目后发布。替代方案是提供 cursor-based 追读并由客户端检测 seq 缺口后补读，不能只依赖“按到达顺序”的未定义假设。
### 4. 服务停止可能漏掉尚未登记的启动请求
- **严重程度**：重要；**类别**：不变量
- **位置**：计划“服务端运行”第 48、68 行；`packages/nb-story/src/server/ingest-service.ts:53-59,86-114,160-177`、`packages/nb-story/src/server/serve.ts:97-114`
- **现象**：`ingest-service` 不仅关闭后拒绝新任务，还登记已接纳但仍在异步启动中的请求；`close()` 等它们完成登记，再停止新拿到的任务并等待收尾。QaService 计划只描述“取消全部运行中的轮次、等它们保存完”，没有说明已通过 `start` 门、尚未进入运行表的配置读取、打开书、创建 harness 期间如何与 `close()` 竞争。
- **为什么是问题**：若 `close()` 先快照运行表并返回，刚好完成配置/书解析的 start 仍可能启动模型请求；`serve` 随后撤销登记并强制停 HTTP，停止服务的合同无法保证该轮被取消并保存为中断。只测已进入模型请求的任务测不到该窗口。
- **如何核实**：按 `ingest-service.ts` 的真实异步窗口复现：让 QA start 在读配置或 `openBook` 时暂停，随后调用 `QaService.close()`，再放行 start；观察模型是否仍启动、close 是否在该轮保存前返回。
- **建议改法**：沿用抽取服务的 `closing` 门与 `starting` 跟踪；在首个 `await` 前原子接纳并登记 start promise/取消控制器，close 关门后等待所有已接纳的准备阶段，再取消已生成的轮次并等待 `askQuestion` 保存与流完成后才返回。

### 5. qa.get 与订阅之间结束的轮次会永久漏掉
- **严重程度**：重要；**类别**：正确性
- **位置**：计划第 53、65、78、98 行；`packages/nb-story/src/core/qa-records.ts:297-304`、`packages/nb-agent-ui/src/harness.ts:291-303`
- **现象**：页面先取 `qa.get` 再连 SSE。续问第二轮时，GET 读到只含第一轮的记录；连接 SSE 前第二轮完成并退出运行表。按订阅合同，没有运行中的轮次只推 `idle`，既不补第二轮日志，也不补 `turn_end`。客户端显示第一轮并进入空闲，第二轮的答案、失败和没核实出处都不出现。保存失败时更没有可重取的磁盘记录，属于第 2 条同根因的更强版本。
- **为什么是问题**：`seq` 去重只消除重复，不会请求没有收到的条目；EventSource 自动重连也仍得到 `idle`。这一空隙存在于两个真实 HTTP 请求之间，不取决于同步 subscribe 的内部写法；页面刷新“接着看”与多个标签页接入都受影响。
- **如何核实**：按现有记录成对发布机制，令 `qa.get` 在第二轮保存前读到第一轮；在 SSE 请求前释放脚本端点使第二轮结束。期望当前页无需再次刷新就见第二轮；照计划只收到 `idle` 无法达成。当前尚无 QaService 实现，未声称已跑不存在的服务测试。
- **建议改法**：订阅握手必须包含与记录版本/日志游标一致的终态或完整快照；最小方案是收到 `idle` 或重连握手后重新取 `qa.get`，并在读到新版本时重建转录。未保存结果需有有界的终态重放期限或明确的一次性结果丢失提示；补“GET 旧快照→轮次完成→订阅 idle”与“断线期间完成”的合同测试。

### 6. 允许命令行并行续问，却把 seq 当成整个对话的唯一游标
- **严重程度**：重要；**类别**：正确性
- **位置**：计划第 44、65–66、78、98 行；`packages/nb-session/src/memory-log.ts:55-77`、`packages/nb-agent-ui/src/harness.ts:114-130,279-303`
- **现象**：同一份第一轮日志末尾为 seq 4 时，网页与 CLI 各自恢复内存日志，两个第二轮都会写 seq 5、6、7，但内容不同。CLI 先保存、网页后保存得到 `conflict` 是允许的。此时页面若 `qa.get` 先取到 CLI 的日志，再补发网页运行中的条目，网页第二问/答全被当作重复 seq 丢掉；反向先看网页分支，再把磁盘权威日志增量喂入，则 CLI 的第二问/答全被丢掉。
- **为什么是问题**：输出 25 的保存冲突只防覆盖，不提供分支共享序列。`createHarnessTranscript` 去重的前提是同一条 append-only 日志，而不是“同一对话 id 下的任意版本”。最终结果、没核实出处的附注和下一轮历史会分别来自不同分支；仅在 `turn_end` 写“没保存”并不能恢复一致性。
- **如何核实**：已运行 `bun --no-env-file /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00024-nb-story/tasks/t13-qa-web/reports/omp-design/sequence-probe.ts`，cwd 为主工作区 `packages/nb-story`。真实 `createHarness` 分别从同一份日志恢复，两个后缀均为 seq 5–7；真实适配器的“GET 后补发”仅显示 CLI 第二答，“直播后重读磁盘”仅显示网页第二答。另一个 `runtime-probe.ts` 经真实 `askQuestion` 同时续问，先完成者 `recordSaved: true`、后完成者 `recordSaved: false/conflict`。未伪造模型调度或条目顺序。

### 7. 第 N 轮不等于日志里第 N 个用户提问
- **严重程度**：重要；**类别**：正确性
- **位置**：计划第 98、135 行；Task README 决定后的接入说明第 64 行；`packages/nb-harness/src/harness.ts:311-324`、`packages/nb-story/src/qa/engine.ts:249-270`
- **现象**：缺密钥与已取消信号会在 harness 写用户消息之前结束，但引擎照常保存失败/中断的一轮。计划按“第 N 个用户提问”把记录的第 N 轮对应到日志，假定“失败、中断的轮次也有日志，不能漏”，实际只有 `run_end`，没有该轮用户消息。第一轮缺密钥、第二轮正常后，日志第一个用户提问已是第二轮；第二轮的 `unverifiedRefs` 找不到第二个用户提问，后续附注继续错位。
- **为什么是问题**：决定 8 要求文字回复的没核实出处在对应回复后显示；这里会漏显示或挂到别轮。仅按用户消息计数还无法在历史中还原失败轮的问题；这不是 UI 渲染取舍，而是服务端交出的轮次/日志缺少关联键。
- **如何核实**：已运行同目录 `runtime-probe.ts`，真实 `askQuestion`、harness 和磁盘记录：记录有 2 轮（`failed, answered`），问题分别为“缺密钥的第一问”“第二问”；日志为 `session_snapshot, run_end, agent_message, agent_message, usage`，仅 1 条用户消息（seq 3，第二问），第二轮 `unverifiedRefs` 为 `["4.999"]`。没有模型网络请求，缺密钥路径在任何请求前结束。
- **建议改法**：由引擎记录并返回每轮的日志起止 seq/用户消息 seq（允许没有用户消息），通过明确范围关联结果和最终助手消息；不要改 harness 既有密钥校验时序来迎合计数。对缺密钥、传入已中止 signal、createHarness 恢复失败分别定义网页表现，至少补“失败第一轮→成功第二轮带未核实出处”的真实运行合同测试。

### 8. 内容摘要不是原子比较并写入，复用当前配置写入还会撞临时文件
- **严重程度**：重要；**类别**：不变量
- **位置**：计划第 82–83、110、117、134 行；`packages/nb-story/src/qa/config.ts:102-126`、`packages/nb-story/src/cli/config.ts:109-115,188`
- **现象**：计划只在网页 `config.set` 增加 expect 摘要，现有 CLI 没有参与比较/锁定；“读摘要相同→CLI 改名发布→网页改名发布”仍会覆盖 CLI 更新。两个网页请求也可以同时读到相同摘要。此外现有 `saveQaConfig` 的临时名固定为 `${path}.${process.pid}.tmp`，同服务两个请求会写同一个文件，一个请求可能发布另一个请求的内容、另一个得到 `qa_config_write_failed`。
- **为什么是问题**：原子 rename 只保证不读到半份配置，不保证 `expect` 的条件与发布原子关联。配置是多个书、标签页共享的一份文件；当前方法从一命令一进程改为常驻多请求调用后，临时文件唯一性的前提也不成立。服务端成功返回摘要可能不对应实际发布的配置。
- **如何核实**：已运行 `sequence-probe.ts`，真实文件系统与 `saveQaConfig()` 并发 10 组、每组 A/B 两份配置；9 次写入拒绝，10 组均至少一次成功返回的值与最终磁盘相反。典型：A 成功返回、B 报写失败，磁盘却是 B。此实验直接跑共享写入入口，不声称尚不存在的 HTTP config.set 已复现；跨进程 expect 的窗口从现有 CLI 无锁的控制流确定。
- **建议改法**：为所有程序写入路径共用一个按配置路径的跨进程写入门禁，在锁内完成“重读→比较 expect/变更字段→校验→唯一临时文件→rename”；CLI init/set/unset 与网页必须一起接入。临时文件每次带随机后缀。手编文件若不参与锁则明确只做尽力冲突检测，不能承诺严格 CAS；补双标签页同 expect、CLI 在网页比较之后提交、失败不改变文件与返回摘要一致性测试。

### 13. 先停后删没有覆盖删除期间新接纳的轮次
- **严重程度**：重要；**类别**：不变量

- **现象**：QaService 只有按对话的运行表和服务级 closing 门，没有“正在删除这本书/这个对话”的接纳状态。删除先 abort 已有运行并等待保存；等待期间另一个标签页可以给同一本书的新对话发 start，或在旧运行完成、运行表释放后再次续问待删的对话。新轮次不在停止快照里，随后书/对话删除完成，它仍继续调用模型，最后才保存冲突。
- **为什么是问题**：照搬 ingest.stopLocal 不足以提供这里的排斥性：抽取任务还持有与删除相同的书 id 锁，QA 的 ask 不持那把锁，且同一本书可有多个运行。保存层能防止复活旧记录，却不能兑现网页“删除时先停”的运行寿命，也不能避免用户删除后仍消耗模型请求。此条不否定计划已明确的停服 starting 处理，针对的是单书/单对话删除这一段没有关门。

### 14. 纯内存运行无法在异常重启后补记中断轮次
- **严重程度**：重要；**类别**：文档
- **位置**：计划第 12、65、109、151 行；`docs/specs/story/qa.md:171-180`；`packages/nb-story/src/qa/engine.ts:189,249-270`
- **现象**：计划风险写“一轮期间服务重启丢掉这一轮，按中断记录”，但运行状态、问题和本轮日志都仅存于内存，书库直到结束才写文件。SIGKILL、崩溃或掉电后，新的服务不知道存在过该轮；首轮整个对话消失，续问仍停在上一轮，不可能创建中断记录。正常 SIGTERM 等保存与异常重启被混为一种保证。
- **为什么是问题**：后续实现无法同时遵守“不在运行中写书库”和“异常重启留下中断轮次”。既有 Spec 已明确强行结束什么都不留下，计划的 Spec 改动却未区分这个兼容边界；测试只覆盖正常停服也证明不了重启恢复。
- **如何核实**：从现有引擎唯一的保存位置、QaService 内存表及 qa Spec 的强行结束规则可直接确定；没有额外状态可供重启恢复。未起 serve 或强杀生产数据进程。
- **建议改法**：保留现有不落盘取舍时，明确只有正常停服会取消并保存为中断；异常退出丢失本轮，重启后显示上一份记录且旧登录态失效，不能承诺中断记录。若确实要异常恢复，则必须另定运行清单落点和恢复合同，属于需批准的数据寿命变更；不要在实施时悄悄加入。验收分正常 SIGTERM 与强行退出两个场景。

### 15. 日志通知异常会被当作写日志失败，破坏记录与转录的一致性
- **严重程度**：重要；**类别**：不变量
- **位置**：计划第 37–43、48、53–54、86 行；`packages/nb-harness/src/harness.ts:141-160,244-248,294-305`
- **现象**：计划把 `onLogEntries` 放进 SessionLog.append 的包装中，append 返回编号条目后通知；没有定义通知回调的异常隔离。若 SSE listener 对已取消/关闭的流 enqueue 抛错，包装 append 在内存日志已经写入后 reject；harness 将其判为真实日志写失败，置会话 broken。`onAgentEvent` 同样在 harness 写 `message_end` 之前执行，某个 listener 抛错会阻断后面的写日志分支，并使其他订阅者漏通知。
- **为什么是问题**：页面断开本应只退订、不影响后台问答。观察者异常不应改变模型结果或持久化语义；仅保证连接断开时调用 off，仍需处理已排队通知与取消的竞争。多标签页时，一个慢/已关的消费者也不能影响其他消费者。
- **如何核实**：已运行 `bun --no-env-file /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00024-nb-story/tasks/t13-qa-web/reports/omp-design/log-observer-probe.ts`（cwd 主工作区 `packages/nb-story`）。使用真实 createHarness、真实内存日志、正常脚本模型回答；仅在包装 append 已成功写入助手消息之后让通知抛错。观察到运行由正常回答变为 `stopReason:error/local`；结果 entries 只有 seq 2，而底层日志已含 seq 1–4（含助手消息与 usage），且 run_end 无法追加。这是所依赖机制的真实运行证据，不把假设的 SSE 断开时序冒充已实现 HTTP 缺陷。
- **建议改法**：将通知作为与日志写入结果隔离的旁路；逐订阅者捕获传输失败并退订/清理心跳，不使 append reject，也不阻断其他 listener 或 harness 的持久化路径。通知队列必须保序，回调仅接收只读条目。合同测试覆盖已连接的两个标签页中一个先关闭、另一个仍完整收到结果，以及 listener 抛错但结果与保存不变。

## 第 12 条的证据修正

## 未发现问题的方面

- **单分支 seq 衔接与 append 顺序**：`createMemorySessionLog({entries})` 要求从 1 连续并从末尾接着编号，实例内 queue 串行；续问不重新广播旧条目合理。第 6 条仅针对明确允许的并行分支，不否定单分支机制。
- **正常关闭与成对保存的已有基础**：引擎先 await harness.close，再读日志并经 QaRecords 发布新的一对；harness 关闭等待写队列、释放工具后退订。append 通知只要不改写/提前持久化且隔离错误，不需要另改成对保存机制。已有 expectTurns、冲突丢弃新日志、删除后的防复活检查仍应复用。
- **服务内 busy 与 CLI 冲突的区分**：计划明确 qa_busy 只管本服务的同对话运行，CLI 并行继续走输出 25；不要求新增跨进程运行锁。问题是两分支的转录身份，不是允许 CLI 并行本身。服务内 busy 登记需在首个异步边界前，运行占用保持到保存结束，照 ingest 的 starting/closing 模式可实现。
- **登录与 SSE 心跳基础**：同源 EventSource 可复用 HttpOnly、SameSite=Strict 的服务 cookie；现有 auth 无闲置过期且进程退出即失效。SSE 路由应放在现有 `/api/` 登录校验之后；serializeSseComment 是合法注释行，注释不进入 JSON。未发现必须换 WebSocket 或新建认证机制的理由。
- **事件/日志与适配器职责**：applyEvent 收裸 AgentEvent，applyLogEntry 收单条 SessionEntry，日志才提供费用与运行错误；事件丢失后等待下一条日志是已定的合理退路。当前 QA 工具只返回文字和普通参数，未发现需要传递函数/循环引用等事件；已测 401 的全部事件可序列化，但脱敏不合格另见第 9 条。不能据此宣称任意外部工具的 unknown details 均可序列化。
- **probe 的问答连通性复用**：probeModel 与 QA 同用 configuredModel/thinkingOption，finally 关闭 harness，不返回模型正文，可复用。它只测试问答模型，结果不带 model/thinking；服务输出需补此次配置身份，避免与刚修改的设置混淆。它不等于 CLI 的抽取两档/recall 测试；本计划没有明确承诺逐组测试，未将额外能力列为缺陷。若界面文案声称测试整份配置，应增加目标与逐项结果合同。
- **已确认决定与评测口径**：决定 1–16 不重议；章数正常拒绝不改变实际读段、按轮新章上限、出处校验与“图当目录”判分口径。当前固定 provider 不发送 isError，不能凭状态位变化声称模型必然反复重试；没有擅自要求重跑已搁置的真实评测。未审网页外观、设置布局或换控件，只有接口耦合进入发现。

### 1. 新对话的第一轮在落盘前根本不存在：列表、刷新、页头元数据都没有来源

- **严重程度**：重要；**类别**：正确性

- **如何核实**：读 `engine.ts` 末尾 `askQuestion` 的保存段，确认运行期间没有任何写盘；读计划两个方法的描述。
- **建议改法**：在计划里写明：`qa.list` 把服务内存里“还没有记录的运行中对话”并进去（带首问、P、做法、开始时间、运行中），`qa.get` 对这类对话返回“没有记录、只有运行中的元数据”的形状（或让 `QaService` 在 `start` 时就登记这些元数据，`subscribe` 的第一帧给出）。页面按“记录缺失但在运行”的形状渲染，并在 e2e 里分别覆盖“新对话第一轮刷新”和“续问轮刷新”。

### 2. 一轮结束、服务重启、启动失败时页面怎么收口，计划没写；“重启后按中断记录”做不到

- **严重程度**：重要；**类别**：正确性
- **位置**：计划“网页/qa/conversation.ts”；“服务端运行”的 `QaFrame`；“不做与风险”第 2 条
- **现象**：
  1. `conversation.ts` 只写了“`qa.get` 的条目先喂适配器，再连 SSE，`log` 帧喂 `applyLogEntry`、`event` 帧喂 `applyEvent`”。`turn_end`、`idle` 帧到了以后页面做什么没有写：要不要重新 `qa.get`、要不要重建转录对象、列表那一行什么时候刷新。
  2. 适配器只进不退（`harness.ts` 的 `applyLogEntry` 在 `seq <= lastSeq` 时直接忽略，没有重置接口）。服务进程重启时这一轮的日志只在内存里，根本没写盘；重连后 SSE 给 `idle`，但页面转录里还留着半截回合，“运行中”的工具永远不收口（`applyRunEnd` 没有机会被调用）。“不做与风险”写的“服务重启丢掉这一轮，按中断记录”做不到：进程已经死了，没有人来写记录。
  3. 引擎在 `startNew`/`startContinued` 里会在运行前抛错（`full_read_unavailable`、`qa_not_continuable`、书被删、位置不合法，见 `engine.ts` 的 `askQuestion` 开头），这时没有日志也没有 `QaTurnResult`。`QaFrame` 里的 `turn_end` 带 `result: QaTurnResult`，没有“没能开始”的帧，`qa.start` 又“立即返回 `{conversation, turn}`”，页面没有通道知道这一轮没跑起来。“全读超过上限”是用户很容易碰到的失败。

### 3. 用户的提问在日志里出现得很晚，有的失败轮根本没有用户消息：空白对话、错挂的错误、上一轮被当成运行中、附注挂错轮

- **严重程度**：重要；**类别**：正确性
- **位置**：计划“网页/conversation.ts”最后一句（“第 N 轮对应日志里第 N 个用户提问开始的那一轮……失败、中断的轮次也有日志，不能漏”）；README 的“接入 nb-agent-ui 的说明”同一条
- **现象**：`packages/nb-harness/src/harness.ts` 的 `execute()` 里，缺密钥（`model.apiKey()` 抛 `MissingModelKeyError`）、会话已坏、`current.cancelled`（刚点了停止）这几条路径在写用户消息之前就 `finishRun`，日志里这一轮只有一条 `run_end`，没有 `agent_message` 的用户消息。用户消息本身也要等 `createHarness`、（全读时）读原文之后才写。结果：
  1. 对应第 N 轮的“第 N 个用户提问”不存在，后面轮的提问会被数成第 N 轮，`unverifiedRefs` 附注挂到错的轮上。计划说失败、中断的轮次“不能漏”，但漏的恰恰是这种没有用户消息的轮。

- **建议改法**：不要靠“数用户提问”对轮次。(a) 让引擎在每轮开始写一条 `meta` 条目（`key: "qa.turn"`, `value: n`；适配器已经忽略 `meta`），日志自己带轮号；或退一步按记录里 `turns[i].startedAt` 与条目的 `at` 划分。(b) 页面在 `turn_start` 到日志用户消息到达之间，往 `ctx.messages` 末尾放一条 `delivery: "pending"` 的乐观用户消息，用户消息日志到达后去掉它；没有用户消息就收到 `run_end` 时也保留这条，让错误挂在它后面。(c) 把“失败轮没有用户消息”“停止发生在用户消息之前”加进 `conversation.test.ts` 与 e2e。

### 4. 全读做法的第一条用户消息是 P 以前的全部原文，会整段显示成用户气泡

### 6. 把 `SearchBox` 的结果面板换成 nb-ui `Popover`，会在输入过程中抢走输入框焦点

- **严重程度**：重要；**类别**：正确性（从代码推断，未在浏览器里复现）

- **建议改法**：这一处先别换，或者先给 nb-ui `Popover` 加“打开时不抢焦点”的开关与“不用 trigger 的锚点”（`PopoverAnchor`）再换；在计划里把它从“逐处替换”挪到“依赖 nb-ui 补能力”。切片 4 的验收写明搜索输入不丢字。

### 11. `message_update` 事件每条带两份完整的半截消息，直接转发会二次方增长，计划没有节流

- **严重程度**：重要；**类别**：安全与性能
- **位置**：计划“关键设计/引擎”`onAgentEvent`（“原样转发”）、“服务端运行”（`event` 帧）、“网页/conversation.ts”
- **现象**：OMP 的 `message_update` 事件是 `{message, assistantMessageEvent}`，`assistantMessageEvent` 的各个 delta 变体都带 `partial: AssistantMessage`（`node_modules/@oh-my-pi/pi-ai/src/types.ts:1391` 起）。一条几千 token 的思考流会发几千个事件，每个事件含两份到当前为止的全部文字，字节数与长度的平方成正比。页面这边，README 的示例是每个事件之后 `ctx.messages = transcript.messages()`，`applyEvent` 每次对半截消息 `assistantFrom` 重建，Vue 对该轮重新整理。运行一到六分钟、思考模型的话，一轮会流过几十 MB。
- **为什么是问题**：本机回环上字节不算大问题，主线程才是：每个事件一次 JSON 解析加一次整轮重算，思考流稍长就掉帧，“过程逐步展开”这个核心体验最先坏。
- **如何核实**：读 `types.ts` 里 `AssistantMessageEvent`；用脚本端点发一条长文字回复，量 SSE 字节数。
- **建议改法**：(a) 服务端对 `message_update` 合并后再推（同一条消息只保留最新一次，间隔不小于约 100 毫秒；`message_update` 本来是整条快照，丢中间帧不影响结果）；(b) 页面用 `requestAnimationFrame` 合并：同一帧里的事件都喂适配器，只在帧末取一次 `messages()`；(c) 只转发适配器用到的事件类型（`message_start`、`message_update`、`tool_execution_*`、`agent_start`、`agent_end`），丢掉 `assistantMessageEvent`。把节拍与合并写进 `conversation.ts` 的说明，并在 `now` 的节拍（运行中每秒）里一并说明。

### 16. “章.段”改写应与引擎共用一条规则，并处理 `DrawerSource` 只认“—”、卡片文字里的出处没人改写

- **严重程度**：建议；**类别**：正确性
- **位置**：计划“StoryMarkdown.vue”；“AnswerCard.vue”
- **现象**：
  1. 引擎判断“正文里哪些是出处”用 `read-ledger.ts` 的 `REF_IN_TEXT`（先 `normalize("NFKC")`，接受“—”“–”“-”，前后不挨数字与小数点，三段数字不算）。没核实的出处列表就是按它算的，所以“3.5 倍”会被列为没核实出处。计划另写一份“把‘章.段’改成链接”，没有说是否共用。若页面的改写规则比引擎窄（不做 NFKC、只认“—”），附注里列出的“３９．１”“39.1-40.3”在正文里就不是链接；若比引擎宽，误伤更多。
  2. 现有 `DrawerSource.vue` 只认 `^(\d+)\.(\d+)(?:—(\d+)\.(\d+))?$`，用连字符或 en dash 的范围会得到 `range = null`，抽屉空白。
  3. 链接目标含“—”（`paragraph://38.12—40.3`）：渲染器可能把 `href` 百分号编码，`MarkdownDisplay` 的 `onClick` 发出 `anchor.getAttribute("href")`，宿主的 `reference.open` 处理要先 `decodeTarget`（`nb-markdown/src/targets.ts`）再解析；计划没写（未验证，需要在真实渲染器里看一眼）。
  4. 答案卡片里的 `conclusion`、`how`、`explanation`、`coverage`、`points[].text` 里也有写成“章.段”的出处（t14 草稿的真实数据里 `explanation` 含 `(35.35—35.45)`），草稿用 `{{ }}` 直接插值，不可点；viewer 输出 19 写的是“任何‘章.段’都可以点”。
  5. 代码块与行内代码、已有链接里不改，这条计划写了；误伤的下一类是列表序号、日期、版本号（`2026.10`、`v1.2`），与引擎同规则就只剩引擎也认为是出处的这些。
- **为什么是问题**：同一份文字被两套规则认，附注和链接对不上。
- **如何核实**：读 `read-ledger.ts:20-30`，`DrawerSource.vue` 的 `range`，`nb-markdown/src/targets.ts`。
- **建议改法**：把 `REF_IN_TEXT` 抽到一个不依赖 node 的纯模块，引擎与页面共用，并加一个“归一成标准写法”的函数（NFKC 加统一用“—”），改写与抽屉打开前都过它；卡片里的文字都走同一个改写（`StoryMarkdown` 或同一函数）；单测覆盖：代码、已有链接、“3.5 倍”、全角、连字符范围、句末“39.1。”、三段数字。

### 17. “依据出处常显一行、放不下写‘等 N 处’”的做法没有写成可实现的规则，容易产生布局位移

- **严重程度**：建议；**类别**：代码质量
- **位置**：已定的取舍 2；计划“AnswerCard.vue”；`packages/nb-ui/docs/ui-development-spec.md` 第 55、439 行（零布局位移，同行两段文字一段先收）
- **现象**：纯 CSS 的单行截断只能出省略号，不能把“等 N 处”这个与可见个数相关的文字算出来；要显示“等 N 处”就得知道放得下几个出处，必须测量。测量在以下时机会让一行的内容变化：卡片挂上、窗口或主区宽度变化（用户点出处开抽屉会让主区宽度突然少 400px，第 12 条）、字体加载、切换亮暗。同一行里还有“依据”标签与右端的“详细”按钮，按 nb-ui 规范要明确哪段先收（出处区应 `flex: 1 1 0`，标签与按钮不收）。
- **为什么是问题**：测量重算时可见出处个数变化，“等 N 处”的宽度也变，整行轨道伸缩；点“详细”展开再收起时也可能变。
- **如何核实**：读 ui-development-spec 第 55、439 行；对照草稿 `DraftAnswerCard.vue` 的 `.answer-foot`（`flex-wrap`，没有截断）。
- **建议改法**：写成固定规则：一行分三格——标签（不收）、出处区（`flex:1 1 0; min-width:0; overflow:hidden`，按 `ResizeObserver` 量出放得下的个数，其余用一个固定宽度的“等 N 处”药丸代替，药丸宽度按位数预留）、“详细”按钮（不收）；出处个数只由宽度决定，不随点击变化。测量逻辑写成纯函数（输入各出处宽度、可用宽度，输出个数）加单测；e2e 在两个宽度各断言一次出处个数与整行高度不变。

### 18. 附注与消息对象的复用：按 id 缓存会拿到过期对象；对话的 `now` 节拍计划只写了列表

- **严重程度**：建议；**类别**：正确性
- **位置**：计划“网页/conversation.ts”（“换成新消息对象并按依据缓存”）与“QaPage”（“每分钟更新 `now`”）
- **现象**：
  1. README 建议“按消息 id 加出处列表”缓存带附注的对象。但 `harness.ts` 在助手消息之后马上到的 `usage` 条目、以及工具结果，都会把 `logged[i]` 换成新对象（`applyUsage`、`applyAgentMessage` 的 `toolResult` 分支）。按 id 缓存会让带附注的对象停在换新之前，缺少用量或工具结果，被视图当成“没变”。

- **如何核实**：读 `harness.ts` 的 `applyUsage`、`applyAgentMessage`；README 的“宿主接入”示例。
- **建议改法**：附注缓存键用底层消息对象本身（`WeakMap<MessageView, MessageView>`）加出处列表；对话 `ctx` 的 `now` 节拍写进 `conversation.ts` 的职责，仅运行中每秒、空闲停止；单测断言“节拍之后 `messages` 里的对象引用不变”。

### 22. 订阅一直开着：每个看着的对话占一个连接，服务端关流还会让 EventSource 自动重连

- **严重程度**：建议；**类别**：安全与性能
- **位置**：计划“技术选型/流式通道”“合同与路由”（`GET /api/qa/events`，每 20 秒一条注释帧）
- **现象**：计划没有说什么时候连、什么时候关。`subscribe` 在没有运行轮次时“立即推 idle”，如果服务端随后关流，浏览器的 `EventSource` 会按默认间隔（约 3 秒）无限重连；如果不关，则每个打开的问答页标签一直占一个连接。`Bun.serve` 本机明文走 HTTP/1.1，浏览器对同一来源最多并发 6 个连接，开到 6 个标签后，同一来源的 `fetch`（查询、保存阅读位置）会排队。计划把多标签页只留给合同测试。
- **为什么是问题**：卡死的症状是整个查看器没响应而不是问答页出错。
- **如何核实**：浏览器规范；读计划。
- **建议改法**：页面只在“已知有运行中的轮次”时订阅（`qa.start` 刚返回，或 `qa.get`/`qa.list` 的“运行中”为真），收到 `turn_end` 或 `idle` 就 `close()`；服务端在 `idle` 与 `turn_end` 之后结束响应并给 `retry:` 很大的值，或页面主动关。这条规则同时解决第 2 条里“收口”的问题。

### 23. 运行中的“停止”被输入框草稿挡住，按计划写的页面就没有别的停止入口

- **严重程度**：建议；**类别**：正确性
- **位置**：计划“AgentConversationView……运行中能停”
- **现象**：`AgentConversationComposer.vue` 里 `showStop = running && currentText.trim() === "" && canStop`。运行中一旦输入框里有字，主按钮变成发送（且 `canSteer`/`canQueue` 都是 false 时是禁用的），停止按钮消失（Spec 输出 268 的行为）。一轮要跑一到六分钟，用户很可能一边等一边写下一个问题。

### 25. 接入依赖与样式的几处没列：`package.json`、`app.css` 的两条导入、大包按需加载

### 26. `StoryMarkdown.vue` 是包装层，不在 nb-markdown 的端口类型检查之内；改写的范围和流式半截文字都没定

- **严重程度**：建议；**类别**：正确性
- **位置**：计划“网页/StoryMarkdown.vue”；`packages/nb-markdown/src/prompt/agent-ports.typecheck.ts` 头部注释；nb-markdown README“接到 nb-agent-ui”
- **现象**：
  1. 类型检查文件明说它对的是 `.vue` 源组件，“包装那一层只转发属性与插槽，不在这里核对”。`MarkdownDisplay` 满足 `MarkdownDisplayPortProps`，但 `StoryMarkdown` 满足不满足没人查：`onActivate` 要被原样转发（`MarkdownDisplay` 发的是 `activate` 事件）、`streaming`、`resolveAsset` 要透传、根元素要接收 `style`（对话视图靠它写 `color` 与 `--markdown-font-size`）。包装层多出一个根元素，思考、提醒的淡色小字就失效。
  2. 改写范围：计划写“代码与已有链接里不改”。围栏代码块（流式过程中未闭合的围栏要算到文末）、缩进代码、行内代码、已有链接与图片、自动链接与裸网址（`http://x/1.2`）、HTML，都要排除。`nb-markdown` 纯入口已导出 `findInlineLinks`、`writeInlineLink`，可复用，围栏代码需要自己加。
  3. 流式：文末半截的“38.1”会先被改写成指向 38.1 的链接，下一批字到了变成 38.12，目标与小块宽度都在变；`MarkdownDisplay` 流式时每帧整篇重读。
- **为什么是问题**：1 是静默的样式失效；2、3 是在真实模型输出上才会出的错。
- **如何核实**：读类型检查文件头部注释、`MarkdownDisplay.vue`（只有一个根，发 `activate`）、`nb-agent-ui` 的 `AgentMarkdown.vue`；对 `nb-markdown/src/index.ts` 看导出。
- **建议改法**：给 `StoryMarkdown` 加一条同样的类型断言（`Accepts<PropsOf<typeof StoryMarkdown>, MarkdownDisplayPortProps>`），保持单根并用 `v-bind="$attrs"` 之外的属性不拆；改写做成纯函数，围栏、行内、链接、HTML 的排除各一条单测；流式（`streaming` 为真）时对文末不完整的出处（后面没有终结符）暂不改写。

### 27. `EventSource` 看不到状态码：登录失效与服务停止无法区分，`ctx.connection` 计划也没用

- **严重程度**：建议；**类别**：遗漏
- **位置**：计划“技术选型/流式通道”“网页/conversation.ts”；viewer.md 失败表 F1
- **现象**：F1 要求登录失效时“显示登录已失效，不显示任何书的内容”，`createHttpClient` 靠 `fetch` 的 401 触发。`EventSource` 的 `onerror` 不带状态码，401 与服务停止都表现为断开并自动重连，页面会停在“连接中”而不是“登录已失效”。nb-agent-ui 的 `ctx.connection`（`connected`/`connecting`/`disconnected`，`actionRequired`）本来就是给这个用的，计划没有映射。
- **为什么是问题**：登录失效是 viewer 已有的合同，新增的一条通道不能绕过它。
- **如何核实**：读 `host/client.ts` 的 `createHttpClient`；读 `types.ts` 的 `ConnectionView`。
- **建议改法**：`onerror` 时把 `ctx.connection` 设为 `connecting`/`disconnected`，并发一次廉价的 RPC（如 `qa.list`）探测：返回 401 就走 `onUnauthorized`；与第 10 条的 `StoryClient.subscribe` 放在一起实现，这样 401 处理只写一份。
