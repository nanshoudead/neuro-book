# 抽取的编译随书变长：先修称呼匹配，再看只要进度的查询

## 目标与范围

长书（几百章）每章的编译不随书长线性变慢；ingest.status 可以只取进度。依据 t06 S6 的实测：98 章的书一次编译十几到二十几秒，每章编译三四次，兜底丢弃时每轮再编译一次。

合同：编译的输出不变（[`story/ingest.md`](../../../../../docs/specs/story/ingest.md) 的行为合同未变）；`ingest.status` 加只要进度的参数时改 ingest.md 的“网页”一节。

## 当前状态

2026-10-20 经 nbdev 新建，尚未开工。同日在会话里先量了一次（样例书，t34 最终草稿，本机）：

| 章数 | 段落 | 称呼 | 编译用时 | 其中称呼匹配 |
| ---: | ---: | ---: | ---: | ---: |
| 25 | 2,423 | 122 | 0.45 秒 | |
| 50 | 5,128 | 207 | 2.2 秒 | |
| 98 | 9,923 | 360 | 12.4 秒 | 94% |

- 章数翻一倍、用时约 6 倍，大致是章数的三次方。原因在 `compile.ts` 的 `matchMentions`：每一段 × 每个不同的称呼字串 × 每次再把全部称呼过滤一遍找归属，三者都随书长增长。按这个增长推 300 章，一次编译约 6 分钟。
- 原型（只改 `matchMentions`）：每个字串的归属预先算好（同一字串最早登记的那个，此刻已登记就是它）、草稿指定的提及按段落预先分组、段落里没有这个字串就跳过。98 章 12.4 秒降到 0.61 秒，25 章、50 章、98 章三份结果与原来逐字段相同（含整理稿）。改后大致线性，按 0.6 秒每百章推 300 章约 2 到 3 秒。
- 剩下增长较快的是 `checkNameLeaks`（每条记录 × 每个称呼，章数的平方），98 章约 0.3 秒；书很长时可以改成一次扫出全部称呼（多模式匹配）。增量编译暂时不需要。

## 下一步

把原型落成正式改动：`matchMentions` 按上面的做法改，测试用 100 章最终草稿对比改前改后整份数据相同，并加一条用时上限；再定 `ingest.status` 只要进度的参数。
