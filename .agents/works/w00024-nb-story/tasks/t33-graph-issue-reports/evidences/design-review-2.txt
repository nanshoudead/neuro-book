## 新问题 1
**严重程度**：重要；**类别**：代码机制、实验设计；**位置**：plan.md「检测」第 72 行；packages/nb-story/src/ingest/context.ts:120-128

**现象**：第二版把 C 定义为读取“截至第 30 章的全部记录（不裁剪）”，但复用的 `renderContext(graph, 30)` 实际仍只输出最近 12 条情节和最近 400 条说法；它也不输出 `summaries`、`arcs`。无 `focus` 只是不按本章文本筛选，不等于全量序列化。

**为什么是问题**：若 C 直接用 `renderContext`，它看不到计划声称的全部记录，事后扫描召回会受隐藏的 12/400 上限影响；若脚本另写全量序列化，又不再是计划技术选型中的上下文，输入长度、字段和模型可见信息都变了。C 的“事后扫描”结果因此没有稳定的输入合同。

**如何核实**：读 `context.ts:120-128`：`episodes` 使用 `.slice(-12)`，无 focus 时 `statements` 使用 `.slice(-400)`；读 `context.ts:120-134` 可见输出中没有 summaries/arcs。

**建议改法**：二选一并写死：C 使用现有 `renderContext`，就把它命名为“无本章相关性裁剪但仍有产品上限的扫描”，按实际可见记录评分；或为 C 定义独立、固定字段的全量图序列化，列出所有实体、说法、情节、整理产物及位置，并把它作为与 A/B 不同的输入合同。

## 新问题 2
**严重程度**：重要；**类别**：成本、代码机制；**位置**：plan.md「检测」第 72 行、「技术选型」第 25 行、「验证」第 116 行；/tmp/review-t33-design/exp/c-size-v2.ts

**现象**：按第二版的 C 输入，当前样本的系统提示词约 14,187 字、截至第 30 章上下文约 25,234 字、第 1 到 30 章原文约 64,011 字，系统加用户任务前已约 103,432 字；默认抽取输出上限是 32,000 token。计划只说 dry run 打印长度，没有要求按实际 tokenizer 和模型 `contextWindow` 验证输入加输出是否能装下。

**为什么是问题**：C 可能触发 context overflow 或在输入很长时把输出截断，导致两遍都失败、修订结果不完整、费用却已经发生；即使 gpt-6-luna 能容纳这次输入，C 的成本和可用输出空间也与 A/B 不在同一量级。当前调用接口只给 `max_tokens`，并不替实验自动检查上下文总预算。

**如何核实**：运行 `bun /tmp/review-t33-design/exp/c-size-v2.ts`，输出 `systemChars:14187`、`contextChars:25234`、`sourceChars:64011`、`totalBeforeTaskChars:103432`；读 `packages/nb-story/src/qa/config.ts:278-317` 可见默认输出上限 32,000，读 `packages/nb-story/src/ingest/model.ts:335-343` 可见请求发送 `max_tokens` 但没有上下文窗口检查。

**建议改法**：dry run 必须用模型实际 tokenizer 和配置的 `contextWindow`，把输入、推理预算、输出上限一起验算；超限时在模型调用前明确失败并计入 C 的固定失败分母，或拆成合同明确的多次扫描。报告分别给 C 的上下文长度、截断/overflow 比例和实际成本，不把“请求发出但无有效修订”当成正常零召回。

## 新问题 3
**严重程度**：重要；**类别**：测量口径、实验设计；**位置**：plan.md「检测」第 72 行、「报告」第 94 行

**现象**：C 改为直接输出修订，形状是“同下面的修复”，而 A/B 输出 `graphIssues`。报告仍要求“每组金标召回、准确率”，但没有定义如何从 C 的 `addStatement`、`editStatement`、`reject` 或“不可表达”映射回一条被发现的问题、问题类型、证据和 false positive。

**为什么是问题**：C 可以修对一条问题却没有产生可计数的检测报告，也可以输出一条字段错误的修订而被同时算成“发现了”和“修复错了”。没有一对一的 detection record，C 的召回/准确率与 A/B 不同义，只有修订质量可比；第 4 个问题的数字不能从原始 C 回复唯一重算。

**如何核实**：对照 plan 第 60 到 65 行的 `graphIssues` 合同与第 72 行 C 的修订形状，再对照第 94 行把 C 纳入“每组金标召回、准确率”的要求；C 没有单独的输出字段、操作到问题的映射或评分规则。

**建议改法**：让 C 同时输出明确的 `findings`（问题 id/类型/记录/evidence/claim）和 `revisions`，或把 C 只纳入修订质量而从检测召回/准确率表移除。若从操作反推发现，预先规定每个操作如何关联金标、拒绝和不可表达如何计分，并让 `report.ts` 能从原始 C 文件重算。

## 新问题 4
**严重程度**：重要；**类别**：代码机制、可复现性；**位置**：plan.md「技术选型」第 25 行、「记录与续跑」第 78 行；packages/nb-story/src/ingest/model.ts:42-48,74-81,325-403

**现象**：计划要求对每次 HTTP 尝试记录 `finishReason` 和 `effortUsed`，并计划依赖 `onAttemptStart`、`onAttempt`。实际 `Attempt` 只有 attempt、用量和 error；`finishReason` 只在最终 `ModelReply` 上，`effortUsed` 也只在成功逻辑调用的最终回复上。`onAttempt` 不接收这两个字段。

**为什么是问题**：按当前公开回调，无法完整记录网络重试、推理档回退、流中断等每个 HTTP attempt 的结束原因和实际推理档。报告会出现“每次 attempt 已记录”但关键字段实际未知，重试与成本分析不能完全复盘；若为取得这些字段改产品代码，又违反本 Task 只做实验、不改产品的边界。

**如何核实**：读 `model.ts:42-48` 的 `Attempt`、`74-81` 的 `ModelReply`；读 `model.ts:325-326` 可见 `onAttempt` 回调只收到 usage/error，读 `367-403` 可见 finish reason 在 attempt 内部但没有随 Attempt 暴露。

**建议改法**：把记录合同改为：每个 HTTP attempt 记录可观察的 usage/error，finish reason 和 effort 只按逻辑请求/最终 round 记录，未知写明；或在不改产品的前提下用实验专用的本地 OpenAI 兼容端点捕获请求和流事件，并明确这不是 `callModel` 回调提供的字段。不要把不可取得的字段列为每次 attempt 的必备证据。

## 新问题 5
**严重程度**：重要；**类别**：成本、实验设计；**位置**：plan.md「可比口径」第 76 行、「费用」第 79 行、「修复」第 81 到 90 行

**现象**：计划把检测逻辑请求固定为 80，但只写“加修复”；没有规定 A/B 独立修复 agent 的调用批次、每遍次数、失败重试上限或修复请求的预算分母。C 自己修订，A/B 还进入 `repair.ts`，两类修订调用的成本路径不同。

**为什么是问题**：预算停止条件无法执行到完整实验：检测跑完后，修复阶段可能再产生未预先限定数量的调用，超过 ¥20 才发现已经超支；报告也不能从 `runs/` 唯一重算总费用。把 A 的费用写成“只算比 A0 多出来的部分”还混合了实际发生费用与反事实增量，可能产生负的或不可复现的成本比较。

**如何核实**：读 plan 第 76、79、81 到 94 行；只有检测三组和 C 的 80 次有明确数量，`repair.ts` 没有调用次数/批次合同，也没有修复费用如何纳入 `¥20` 停止条件的说明。

**建议改法**：在修复前冻结每组、每遍、每批的请求数和失败重试规则，所有修复 attempt 与检测 attempt 使用同一 manifest 和预算计数；报告同时给实际发生费用与 A 相对 A0 的估算增量，后者不能替代总费用。若修复调用数必须按问题数动态增长，先定义硬上限和每条问题的成本分母。
