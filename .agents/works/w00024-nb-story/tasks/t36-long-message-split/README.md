# 抽取请求的长消息分段：单条消息超过网关上限前拆成几条

## 目标与范围

网关限制单条消息约 70 到 80 KB（t33 实测）；抽取的用户消息超过阈值时在段落边界拆成几条用户消息，阈值以下的请求逐字不变；413 给出明确的错误说明

合同：[`story.ingest`](../../../../docs/specs/story/ingest.md) 输出 4 加一句长消息分段。来源：[t33](../t33-graph-issue-reports/README.md) 的网关实测。计划见 [plan.md](plan.md)。代码在 `.worktree/w00024-t36-long-message-split`，分支 `feat/w00024-t36-long-message-split`。

## 当前状态

2026-10-28 经 nbdev 新建（autonomous-delivery）。实测魔女学院图上写草稿的用户消息第 100 章约 67 KB、第 164 章约 77 KB，已越过网关单条上限；四条各 60 KB 的请求没有被 413 拒。计划已写；任务小，计划审查按 reviewing 的降级交 Claude Sonnet。

## 真实网关验证：方案不成立（2026-10-28）

用 t36 分支的 `callModel` 对真实网关发 212 KB 的用户消息：先 413，拆成每条 50 KB 仍 413，再拆成每条 25 KB 仍 413，最后以 `provider` 失败。接着直接探测网关（[gateway-probes.md](evidences/gateway-probes.md)）：上限不是单条消息的字节数，而是整个请求的大小，计量口径不明（汉字单条 80 KB 被拒、ASCII 单条 110 KB 能过），同一个请求不同时间结果不同。t33 得出“只限单条、总量不限”只凭两个数据点，不成立；t36 的计划与两轮审查都以它为前提，没有在动手前复测。

所以**不合入 t36**：拆成几条消息对这个网关没有用，反而让请求多发几次。分支 `feat/w00024-t36-long-message-split` 保留（`splitMessage` 与测试可作参考）。

问题本身仍在：魔女学院图上写草稿的请求（系统约 29 KB 加用户消息）第 100 章约 96 KB、第 164 章约 106 KB，长书后面的章在这个网关上会被拒；核对补漏、全量整理的请求更大。能做的只有让请求变小（例如被 413 拒时按固定顺序少列已有记录，会影响抽取质量，要用真实模型回归验证）或换网关。这改变了本 Task 的方向，停下交开发者判断。
