## 已核实的发现

### 1. 开关漏掉真正读取配置的命令行与服务端入口

- **严重程度**：重要；**类别**：接口与合同。
- **位置**：`plan.md:35-38,47,58`；`packages/nb-story/src/cli/ingest.ts:232-245`；`packages/nb-story/src/server/ingest-service.ts:109-118`。
- **现象**：计划新增 `personaCheckEnabled(config)`，但接线清单只有 `job.ts`、`runner.ts`、`start.ts`、`worker.ts`，缺少把配置读出来并传入 `startIngest` 的两个产品入口。
- **为什么是问题**：`StartInput` 不接收 `QaConfig`，`start.ts` 只判断原文与已保存进度，不读配置。照字面实施，`ChapterRun.personaCheck` 不给时关闭：两个入口不传就会使默认开不生效；若改为 runner 内默认开，配置中的 `enabled: false` 又无法传入。直接构造 runner 参数的测试不能证明配置文件已经生效。
- **如何核实**：顺序读取上述两个入口、`runner.ts:49-67,156-160`、`worker.ts:17-30,47-59`、`start.ts:56-108`；`ingest.recall` 在两个入口分别调用 `recallModel(config)` 并显式传参，计划没有对应的一跳。代码核实，未执行新功能（尚无实现）。
- **建议改法**：把 `cli/ingest.ts`、`server/ingest-service.ts` 列入接线切片，两处从本次加载的配置解析开关并传进 runner、worker、job；默认值只在配置解析处确定。各补一条经实际入口加载配置的开/关场景，不只测直接构造 `StartInput`。

### 2. 用章末称呼生成文字，却把成立位置回填到模型任意早段，能直接剧透

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`plan.md:23-24,45-46`；`packages/nb-story/src/ingest/compile.ts:249-271,867-880`；`packages/nb-story/src/core/projection.ts:87-100`。
- **现象**：请求包含本章全文与章末全部候选，程序生成的文字使用双方“当前称呼”，但只要求证据中有本章段落，没有要求该段晚于双方对象及所用称呼的成立位置。编译把说法的 `at` 定为证据最晚段，不会自动推迟到文字里名字首次出现的位置。
- **为什么是问题**：章内后面才揭晓的名字会提前出现在可见说法文字里；即使其对象引用被投影去掉，文字也不会被遮蔽。`name-leak` 只是警告，计划的“编译出错才去掉”不会拦住。违反 `story.queries` 输出 1 与 `story.ingest` 输出 8；候选而非确定连接不能消除文字剧透。
- **如何核实**：在实现 worktree 执行 `bun /tmp/review-t35-design/exp/contracts.ts`：4 段小书，账号在 1.2、人物在 1.3、名字“银空”在 1.4；按计划生成文字并引用 1.2。真实 `compile` 返回 **0 个错误、1 个 name-leak 警告**；经真实 `book.import` 与 `entity.statements` 在阅读位置 **1.2** 查询，返回“银色账号可能就是银空。”。未调用模型；复现是计划允许的模型回复经真实编译和公开查询的结果。
- **建议改法**：定义新说法的可见位置下界，至少不早于双方对象、所用称呼、全部依据的成立位置；不能靠扩大出处伪造原文证据。可明确把核对产物固定在章末可见，并让编译保留这个位置，或选取满足下界的真实本章证据，否则跳过。增加章内较早阅读位置的公开查询验收，而不只查请求中没有下一章位置。

### 3. 已知错连样本“志愿者学姐”不会被现有泛称过滤排除

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:5,13,21-22,45`；`packages/nb-story/src/core/generic-names.ts:10-30`；t34 `README.md:60,67-68`。
- **现象**：计划把 t34 的泛称错连风险交给 `isGenericName` / `allGeneric`，但词表只有“志愿者”和“学姐”，没有“志愿者学姐”，也不组合识别。导致两遍实验都错连的第二位学姐仍被当作有专名的马甲。
- **为什么是问题**：真实样本 `e4-2` 的称呼恰好是 `["志愿者学姐", "学姐"]`；`allGeneric` 返回 false。默认开启后它仍会被反复问并写候选错连。只写候选限制了破坏程度，却没有实现 t34 明确建议的“跳过称呼全是泛称”的主要风险控制。
- **如何核实**：只读查询 t33 `graph-164.json` 的 `e4-1`、`e4-2`；执行 `bun /tmp/review-t35-design/exp/contracts.ts`，真实函数返回 `isGenericName("学姐") = true`、`isGenericName("志愿者学姐") = false`、上述两称呼的 `allGeneric = false`。t34 `score.md:50-51`：两位学姐分别 **88 次中错 15 次、88 次中错 5 次**。
- **建议改法**：在现有泛称真相源补足该已知复合泛称，并用两位学姐的真实称呼做过滤验收；不要在新模块另建一份泛称表或用包含“学姐”过滤所有称呼，以免把“墨学姐”等专名一起删掉。

第 3 条数字更正：`score.md:50-51` 的“次数”已合并两遍，正确分母分别是 **44 次中错 15 次、44 次中错 5 次**，不是 88 次；该更正只改数字，不改变发现。

### 4. 候选永不退出选择集，已有候选也无去重，会持续追加同一条猜测并占满 5 个名额

- **严重程度**：重要；**类别**：正确性 / 安全与性能。
- **位置**：`plan.md:21-24,30,45,79`；t34 `score.md:63-105`；`packages/nb-story/src/ingest/compile.ts:147-158,244-275`。
- **现象**：排除条件只有“已有确定连接”，新增连接却一律是候选；已有候选、本章主抽取刚写了候选、核对刚写过的同一对象对都不会退出。每次触发继续问，答同一对象就用新编号再写一条。排序永远按本章最早出现及编号，未定义已问过与未问过之间的轮换。
- **为什么是问题**：这不是只写候选的必然代价，而是缺少重复处理合同。6 个未确定马甲持续同序出场时，前 5 个在每章重复问，第 6 个连续 **100 章也可 0 次**；若前 5 个每次答同一对象，则 100 章可新增 **500 条重复候选**、至少 **500 次逻辑请求**。候选本来就不会自动转确定，t34 的费用与产品离线策略却按“首次 same / not-persona 后不再问”统计，不能为此重复策略背书。
- **如何核实**：按选择与写入条件演算，候选写入前后排除谓词不变；`bun /tmp/review-t35-design/exp/contracts.ts` 将同一对象对、同一出处用两个新编号送入真实编译，得到 **0 个错误、2 条说法**，证明最终编译不会替计划去重。`job.ts:144,153-155,178-183` 会保存并在接着抽时重新编译这些草稿，不会清掉它们。
- **建议改法**：不改变“只写候选”的取舍；明确同一对象对的候选幂等规则、本章已有候选时如何处理、什么新证据才重问。若仍允许重问，应避免再写相同候选，并给未问过/延后的对象公平机会；状态按提交保存，整章作废不算已处理。补跨章、接着抽与 6 个对象封顶的行为验收。

### 5. 沿用探针问法，却新增“必须有本章证据”的写入门槛，已有实验不能证明同样召回

- **严重程度**：重要；**类别**：接口与合同 / 验收。
- **位置**：`plan.md:5,23-24,60-68`；t34 `scripts/probe.ts:31-38,67-95`；`story.ingest` 输出 5。
- **现象**：探针允许模型用历史段落回答，系统提示词没有要求提供本章有效证据；计划复用该提示词，却只接受至少一处本章出处，并丢掉历史出处。实验评分只看回答对象与确定度，没有这个写入门槛。
- **为什么是问题**：真实回答并非都会引用当前章。旧章已揭示、当前章只是触发时，答对仍可能永远写不下去；不能把 t34 的“找回”当作新步骤“已写入”的证据，也不能为通过门槛凭空指定当前段落。只留当前出处还可能删掉实际推断依据。输出 5 的本章出处限制必须保留，因此要先解决问法与持久化合同的错位。
- **如何核实**：在实现 worktree 执行 `bun /tmp/review-t35-design/exp/evidence-audit.ts`，只读 t34 已有的 **308** 份记录，不发模型请求：**134** 次 same 中 **28** 次无本章证据；揭示后答对的 **106** 次中 **19** 次无本章证据。`witch-e6-5` 第 1 遍唯一首次答对在第 **12** 章，但只引 **6.64、6.65**，按计划不能写，整个已观测日程无合格答对；`sample-e10-1` 第 2 遍从第 **12** 章延迟到第 **16** 章。另 `score.md:26` 已写明一个用例需第 **5** 次才答对，计划首段“15 个两遍都在第 1 到 3 次”也不符合表格。
- **建议改法**：请求明确区分历史依据与本章可落盘的触发依据，程序校验真实段落范围；无法满足本章合同就明确记为不能写，不拿已有探针成功抵验收。对现有回答先按产品写入门槛离线重评分，再用包含“只能引用历史证据”的确定性场景验收；真实模型回归以最终落盘和公开查询为判据。

### 6. 网页要“开着时多一格”，但状态没有本次任务开关，且漏掉步骤文案真相源

- **严重程度**：重要；**类别**：接口与合同。
- **位置**：`plan.md:39-40,59`；`packages/nb-story/src/web/shell/IngestPage.vue:93-103,201-204`；`packages/nb-story/src/web/host/ingest.ts:8-12`；`packages/nb-story/src/ingest/status.ts:42-58,160-170`。
- **现象**：计划承诺开着就显示“核对马甲”，但 `ingest.status` 只增加 `step` 枚举，没有返回启用值；页面从状态里拿不到这次任务开没开。现有 recall 并非按配置显示，它只在当前步骤恰好为 recall 时临时列出。共用步骤标签实际在 `web/host/ingest.ts`，计划也没列这个文件。
- **为什么是问题**：配置默认开不等于当前任务开；命令行可以用另一份 `--config` 发起，配置还可能在任务中途修改，页面读服务当前配置也不能还原启动时的值。`enabled: false`、开启但本章无候选、已进入整理三种情况，不能仅凭当前 `step` 区分。新增合同枚举还会让 `STEP_LABELS: Record<Step, string>` 缺键，网页类型检查失败，或被绕过后显示空标签。
- **如何核实**：代码核实上述字段与页面计算；`IngestPage.vue` 的 `steps` 仅在 `recall` / `consolidation` 当下加项，`status.features` 只有跟书保存的 ledger / secrets，不含运行配置。未运行网页与 e2e（本次规则禁止）。
- **建议改法**：明确选择一种可实现的显示合同：要全程显示，就把本次启动的 `personaCheck` 作为任务快照写入状态并经合同返回，旧记录缺字段有明确默认；若沿用 recall 的“正在此步时才显示”，则修改计划措辞并在整理态保留需要的完成信息。将 `web/host/ingest.ts` 标签和对应网页状态用例列入切片。

### 7. 回放对新步骤无条件回 unknown，会把错误触发与额外请求变成绿色

- **严重程度**：重要；**类别**：测试。
- **位置**：`plan.md:35,41,46-47,58-59`；`packages/nb-story/testing/ingest-replay.ts:4-6,63-85`；`docs/specs/story/ingest.md:225`。
- **现象**：原回放遇到没有录音的请求会记 `unknown` 并回 418；计划对所有 `persona` 请求合成成功的 `unknown` 回答。这样任何章、任何数量、同一马甲重复请求也会被接受，测试不知道是预期新请求还是错触发。直接 `ChapterRun` 测试缺省关闭，与经配置默认开启的 runner / CLI / server / e2e 是两条路径。
- **为什么是问题**：`played.unknown === []` 不再证明产品只发了预期请求；新步骤选错对象、超额或重复调用而不写数据，都可被兜底隐藏。全套旧回放只覆盖“不改变数据”的回答，不会覆盖候选写入后对整理、下一章请求、停止重做和接着抽的影响。计划只补一条单章 same、两条 runner 进度费用，缺少这些产品路径。
- **如何核实**：代码核实 `ingest-replay.ts` 的严格拒绝合同；`runner.test.ts:36-60`、`cli/ingest.test.ts:41-52`、`server/ingest.test.ts:59-74`、`e2e/ingest.e2e.ts:29-36` 均共用回放，CLI / server / e2e 的配置原来没有此字段。recall 的先例是在测试中显式 override（`runner.test.ts:127-145`），而不是给所有 recall 请求默认成功。未运行新功能测试（尚无实现），未跑 e2e。
- **建议改法**：保留无录音即失败；旧场景显式关闭，或明确提供只允许预期章、对象、次数的 persona 回放。新增经 runner 的 same 落盘后停止/接着抽/追加场景，以及在 persona 请求中取消、渠道失败、两次坏回复场景；CLI、HTTP 各验默认开与显式关。回放键或 override 需能区分同章最多 5 个马甲，而不只 `章:步骤`。
