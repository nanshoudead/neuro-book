## 发现 1：只选 Responses、未写推理档时，请求没有思考摘要

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/qa/harness-model.ts:21`、`:25`、`:33`；测试覆盖缺口在 `packages/nb-story/src/cli/ask.test.ts:109`。
- **现象**：配置 `{api: "responses"}`、不配置可选的 `thinking`，实际 `config test` 向 `/v1/responses` 发出的正文没有 `reasoning`，也没有 `include: ["reasoning.encrypted_content"]`。加 `thinking: "xhigh"` 后才出现 `reasoning: {effort: "xhigh", summary: "auto"}`。现有测试只测后一种组合，假端点又无条件返回脚本里的摘要，掩盖了缺少请求参数。
- **为什么是问题**：qa.md 输出 36 要求选 Responses 就请求摘要，推理档仅在配置写了时发送。合法配置中 `thinking` 可缺省；用户只切换“接口”后，真实服务不会因为接口名改变就自动打开摘要，功能仍然看不到思考。`configuredModel` 把“支持推理”与“用户指定了推理档”绑定为同一个布尔值；OMP 在 `model.reasoning === false` 时不组装 reasoning 参数。
- **如何核实**：执行 `env NBOOK_AGENT_TEMP_ROOT=/tmp/claude-1000/review-t15-impl/omp-scratch bun /tmp/claude-1000/review-t15-impl/omp-scratch/runtime-probes.ts`，经真实 CLI 的 `config test` 跑两种配置；结果保存在 `omp-scratch/runtime-1792777872827/results.json` 的 `summary-omitted` 与 `summary-xhigh`。两次退出码均为 0，但前者实际请求没有 `reasoning`，后者有完整的 `effort`、`summary`。OMP 18.2.5 的 `src/providers/openai-shared.ts:3819`、`:3844` 与 `src/stream.ts:1942` 可解释该差异。
- **建议改法**：把接口的“请求摘要”与可选的 effort 分开传递；Responses 即使没配 effort 也发 `reasoning: {summary: "auto"}`，仍不替用户补 effort。若现有 harness 不能表达，扩展它的模型请求选项或提供受控的 provider 参数接缝。用本机端点按请求决定是否返回摘要，补“不写 thinking、只切 api”的 ask 与 probe 行为用例。

## 发现 2：model.api 的非法值走配置错误，退出码与同类枚举字段不一致

- **严重程度**：建议；**类别**：正确性、测试。
- **位置**：`packages/nb-story/src/qa/config-edit.ts:40`、`:86`；错误被固定进测试的位置为 `packages/nb-story/src/cli/config.test.ts:122`。
- **现象**：`config set model.api grpc --json` 与空字符串都退出 1，报 `qa_unconfigured`；正文把 `/model/api must be equal to constant` 重复两遍，再补 `must match a schema in anyOf`，没有告诉用户可写 `chat` 或 `responses`。文件确实保持原字节不变，错误没有回显原值。
- **为什么是问题**：qa.md 输出 22 与验收 10 规定值的写法不对是用法错误、退出 2；现有同类枚举 `model.thinking max` 也是 2。新增 `api` 却被登记成 `text`，任意字符串都会越过字段解码，直到整份校验才失败。输出 20 的整份校验保护仍然生效，因此没有配置损坏或泄漏；问题是 CLI 合同与可操作的错误信息。新测试明确断言 1，未保护既有规则。
- **如何核实**：执行上述 `runtime-probes.ts`；`omp-scratch/runtime-1792777872827/results.json` 的 `api-invalid-grpc` 与 `api-invalid-empty` 均记录 `code: 1`、`unchanged: true` 和完整错误正文。指定测试的其他非法写法用例要求退出 2。
- **建议改法**：同 `thinking` 一样，在字段解码层识别接口枚举、抛 `ConfigEditError` 并列出可用值；错误不带用户输入。整份 schema 校验保留，用来拦截手编配置与整份写入。若确实打算把该值定义为配置错误，必须在 Spec 的退出码与验收里明确例外，而非仅改测试。

## 发现 3：Responses 假端点把截断与自定义用量悄悄改成成功的固定回复

- **严重程度**：建议；**类别**：测试。
- **位置**：`packages/nb-story/testing/openai-endpoint.ts:55`、`:97`、`:98`；调用分派为 `:131`。
- **现象**：`EndpointReply` 的 `text` 接受 `finishReason` 和 `usage`；Chat 分支消费它们，新增 Responses 分支却完全忽略。传 `finishReason: "length"`、自定义 251 输入/99 输出 token，实际仍发 `response.completed`、`status: "completed"`，用量固定 100/10，未发 `response.incomplete`。真实协议的输出上限应是 `response.incomplete` 加 `incomplete_details.reason: "max_output_tokens"`。
- **为什么是问题**：已有问答合同区分已答但截断与普通停止，也统计用量；同一测试脚本仅改 `model.api` 就不再测试原场景，却没有报错提示。`EndpointReply` 的类型和调用方不能发现该退化，会把截断路径或计量回归测成普通成功。终态 `response.output` 还恒为空，与之前发过的 output items 不一致；思考 item 没有真实服务在无状态重放中返回的 `encrypted_content`，所以现有成功用例不证明密文回放。
- **如何核实**：执行 `env NBOOK_AGENT_TEMP_ROOT=/tmp/claude-1000/review-t15-impl/omp-scratch bun /tmp/claude-1000/review-t15-impl/omp-scratch/protocol-probes.ts`。`omp-scratch/protocol-1792778665826/results.json` 的 `outcomes.fakeTruncation.body` 是从该假端点真实 HTTP 读取的流，显示 completed 和 100/10。相同脚本经 CLI、harness、OMP 收取完整 Responses 截断事件时，`outcomes.truncated` 给 `reply.truncated: true`、用量 100 未缓存输入 +40 缓存读、35 输出，证明正式路径能区分，但原测试端点不能表达。
- **建议改法**：按 Responses 语义映射 `finishReason` 与 usage，终态带已生成的完整 output；不支持的脚本选项明确拒绝。给 reasoning 产生可辨认的假密文字段并断言续问原样回传；流式摘要分至少 2 个 delta。事件对象使用 Responses wire 的判别联合或一个与它核对的固定夹具，避免只靠 `Record<string, unknown>` 手拼。

## 未发现问题的方面

1. **Responses 实际解析与主要事件字段**：测试端点确实没有 `sequence_number`、`response.in_progress`、`response.content_part.done`，created/completed 信封也省略 `object`、`created_at`、`model` 等字段；但 OMP 18.2.5 的 HTTP Responses 解析器不靠这些字段定位内容，没有证据表明省略本身会造成实际请求失败。测试里的 `output_index`、`item_id` 对应一致，usage 的 `input_tokens`、`output_tokens`、`input_tokens_details.cached_tokens`、`output_tokens_details.reasoning_tokens` 字段名正确。完整事件实验加入这些字段、2 个交错的 function call、每个参数 2 个 delta，经过 CLI 正常执行，两个工具结果分别对应正确的 call_id。未把单纯的字段省略列为产品故障。
