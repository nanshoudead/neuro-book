### 1. 书删除后继续作答，与运行中按书路径追加的会话日志不相容

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`docs/specs/story/qa.md:148-155`；`.agents/works/w00024-nb-story/tasks/t05-qa/plan.md:54-55,90-94`。
- **现象**：合同承诺删除书后这一问仍答完；计划只在最后保存记录失败时返回 `recordSaved: false`。但运行期间 harness 每条消息都写 `<书 id>/qa/`，`Library.removeBook` 先将整个书目录 rename，再递归删除；nb-session 每次 append 都按原路径重新 `appendFile`，不持有固定文件句柄。删除后的下一次日志写入失败，会先让 harness 以 `error/local` 停下，根本到不了“答案照常、只是记录没保存”。同 id 重新导入后，如果新的 `qa/` 还没创建仍失败；若已被另一问创建，则旧日志的后半截会写入新一代目录，缺失快照和前半历史。
- **为什么是问题**：固定内存索引只固定查询，不固定日志的落点与寿命；harness 把日志成功写入作为继续模型请求和 `finished` 的必要条件。计划把日志故障误当成最后记录写入的可忽略故障，破坏 qa 的删除语义和 harness 输出 7、16。
- **如何核实**：已逐行核对 `packages/nb-story/src/core/library.ts:11-18,214-226`、`packages/nb-session/src/jsonl-log.ts:48,73-84`、`packages/nb-harness/src/harness.ts:123-142,190-197,231-240,288-299`。后续使用真实 `createHarness` 与 `createJsonlSessionLog` 的无模型探针核对实际结果；实验结果追加在报告后文。
- **建议改法**：为在途日志选择不随书目录 rename/rm 消失的寿命边界，例如运行时放在书库级独立会话区，结束时在代际检查下归档到 `qa/`；删除书时在途问可完成但不重新创造书目录。若坚持书目录内逐条追加，则必须先改日志存储与删除协议，不能仅补 `write(record)` 的 catch。补“删除后不重新导入”“删除后重新导入且新代无 qa/”“新代有另一个 ask”三个真实运行时场景。

补充实测（发现 1）：执行 `bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t05-design/probes/runtime.ts`。使用真实 `Library.removeBook/importBook`、`createHarness`、`createJsonlSessionLog`，只替换模型输出，在模型请求进行中删除书：不重新导入、重新导入但无 `qa/` 两种情况均为 `stopReason: "error", errorKind: "local", finish: null`；重新导入且创建新代 `qa/` 时为 `finished`，但新目录里的旧问日志 seq 只有 `[3,4,5]`，缺 seq 1 的快照与 seq 2 的用户问题。不是绕过运行时直接调用内部函数的推演。

### 2. `admit → await 查询 → record` 在默认并行工具调度下会读出第 21 章

- **严重程度**：重要；**类别**：不变量。
- **位置**：`.agents/works/w00024-nb-story/tasks/t05-qa/plan.md:71-75`。
- **现象**：读账本先检查章数，等查询返回后才登记。计划未声明 `read` 为 `exclusive`，也没有预占名额；nb-harness 插件工具默认 `concurrency: "shared"`。已读 19 章时，同一模型消息并批读第 20、21 章，两次检查都看到 19，都通过，最终已读 21 章。
- **为什么是问题**：这是同一问内共享可变账本，不是“查询工具都只读”就能安全并行；违背开发者决定 17 与 qa 输出 5。没有步数上限不是放宽章数上限的授权。
- **如何核实**：上面的 `runtime.ts` 经真实 harness 调度与真实书库查询复现计划顺序，不手工并发调用工具：`admissions` 中两个新章的 `before` 都为 19、`allowed` 都为 true，最后 `chaptersRead: 21`。默认值见 `packages/nb-harness/src/tools/registry.ts:123-135`，声明透传见 `tools/bridge.ts:41-48`。此探针验证的是计划的竞态，问答产品尚未实现。
- **建议改法**：最简单的是仅把 `read` 登记为 `exclusive`，其余查询保持并行；或者让账本原子预占新章、失败时释放。新增同一助手消息批量读两章的确定性验收，验证总数最多 20 且被拒调用不返回原文。

### 3. 把固定的 20 章上限变成了可任意调大的配置

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/qa.md:62-65,90`；`.agents/works/w00024-nb-story/tasks/t05-qa/plan.md:70-75`。
- **现象**：开发者决定 17 是“一问最多读 20 个不同的章”，Spec 却公开 `qa.maxChapters`、仅写默认 20，执行规则也完全使用这个值，没有 `1..20` 的有效范围；配置为 21 或 100 就按合同允许超过 20 章。
- **为什么是问题**：把已定硬上限悄悄改成默认值；同时没定义 0、负数、非整数的配置失败语义，0 会让所有正常非“无法确定”答案都没有可引用原文。
- **如何核实**：对照 `.agents/works/w00024-nb-story/tasks/t05-qa/README.md:41` 与上述 Spec/计划；输出 5 的判据是 `maxChapters`，不是 `min(maxChapters, 20)`。这是目标合同本身的差异，不依赖尚未实现的代码。
- **建议改法**：取消这个可调项，或者仅允许整数 `1..20`、默认 20；非法配置在模型请求前按配置错误拒绝。保留全读不受这条上限约束的已定决定。

### 4. 只校验 refs 数组，正文里的出处可以绕过“读过且不晚于 P”

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/qa.md:95-116`；`.agents/works/w00024-nb-story/tasks/t05-qa/plan.md:76`。
- **现象**：`conclusion`、`knowledge[].how`、`points[].text`、`explanation`、`coverage` 都是自由文本；输出 8 明确把“每个出处”限定为三个 refs 数组。读过 1.1、P=38.57 后提交 `evidence: ["1.1"]`，同时在 `explanation` 写“依据 38.60／39.1／未读过的 21.1”，五条校验仍全部通过，格式化后的答案会把这些编号原样呈现为出处。
- **为什么是问题**：开发者决定 18 约束的是作答引用的出处，不只是独立数组；当前校验允许未读引用与越过 P 的引用作为已答答案保存。此处不要求机器判断自然语言结论真伪，只需让可识别的出处统一进入同一套位置与阅读账本校验。
- **如何核实**：逐项代入输出 8：形状、conclusion 非空、数组里的 1.1 合法且已读、无 knowledge 行、evidence 非空，全部成立；没有一项会看 explanation 中的引用。计划 76 照这五条实施也会接受。现阶段为合同反例，尚无问答实现可运行。
- **建议改法**：明确自由文本不允许内嵌出处、引用只通过结构化 refs 并由 formatter 插入；或者统一抽取自由文本里的合法引用记法并按同一账本校验。补“合法 evidence 搭配正文未读／越界引用”的验收，不能仅测试 evidence 数组。

### 5. “密钥不落地”依赖了 harness 并不存在的 provider 错误脱敏

- **严重程度**：重要；**类别**：安全与性能。
- **位置**：`docs/specs/story/qa.md:131,163`；`.agents/works/w00024-nb-story/tasks/t05-qa/plan.md:90-94,148-150`。
- **现象**：计划只验证成功请求时假密钥没被输出，没有处理 provider 错误正文回显密钥的情况。现有 harness 原样保留 provider 的 `errorMessage`，既进 `TurnResult.error.message`，也进 `agent_message` 和 `run_end` 日志；引擎再把错误存进问答记录与 CLI JSON。HTTP 401 正文只要含发送的密钥，就会落盘。
- **为什么是问题**：提案 `docs/proposals/novel-story-app.md:254` 和 qa 输出 17 明确连错误正文都不能含密钥。密钥只传给 HTTP 客户端，不等于响应与错误通道会自动脱敏；这是依赖机制的真实缺口，不是要求隐藏错误归类。
- **如何核实**：执行 `bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t05-design/probes/provider.ts`。真实本机 OpenAI 兼容端点从 Authorization 取假密钥、回 401 错误正文；真实 OMP provider + harness + JSONL 得到 `stopReason: "error", kind: "auth", keyInResult: true, keyInSession: true`。不调用真实模型，不直接伪造 harness 的内部错误。
- **建议改法**：在模型错误进入 harness 日志前对本次使用的密钥做精确脱敏，并确保返回错误与记录复用同一份已脱敏值；可以在 harness 提供统一的敏感值边界，不能只在 CLI 最后打印时遮盖。补 401／provider 5xx 回显假密钥的端到端验收，同时保留原错误 kind/status。

### 6. 新增 qa 写入口没有接入“不认识的书库版本只读”门禁

- **严重程度**：重要；**类别**：不变量。

### 7. “参数与 CLI 同名”与“直接去掉 method.input 的 book/at”是两套不相容的工具接口

- **严重程度**：重要；**类别**：代码质量。
- **位置**：`docs/specs/story/qa.md:77-88`；`.agents/works/w00024-nb-story/tasks/t05-qa/plan.md:73-75`。
- **现象**：计划要求参数 schema 直接取方法 input，同时又要求位置参数与命令同名。CLI 的 `read <章.段[-段]>` 经 `decodeRange` 展开为 `from/to` 两个 Position 对象；`para <章.段>` 展开为 `chapter/paragraph`；`find <名字或称呼>`、`between <对象> <另一个>` 实际对应 `query`、`entity/other`；`--min-together` 对 `minTogether`，`kinds` 在 CLI 是逗号字符串、方法是数组。两边不能仅 Omit 就获得同一参数名与形状。CLI 的分页提示还输出 `--cursor`，而工具需要 JSON 的 `cursor`。多数方法 input 一律带 perspective，CLI 只有一部分命令暴露它，不适用视角的方法又会忽略。
- **为什么是问题**：编码者必须在“CLI 风格参数再解码”和“原生方法参数”之间自行选一边，另一份承诺就不成立。工具说明仅取 `summary`（read 只有“读原文”），没有解释 Position、范围缺省、视角、游标续页的具体调用方式；把 CLI 用法直接写进 Profile 会诱导模型提交 schema 拒绝的参数。命令表可复用，但它目前并不是工具参数协议。
- **如何核实**：真实 TypeBox Compile 探针 `runtime.ts` 输出：CLI `decodeRange("38.50-81")` 得到 `{from:{chapter:38,paragraph:50},to:{chapter:38,paragraph:81}}`；派生 schema 拒绝 `{"章.段[-段]":"38.50-81"}` 与 `{from:"38.50-81"}`，只接受 Position 对象。字段依据为 `packages/nb-story/src/cli/commands.ts:40-51,95-96,119-120,133-143,151-168`、`src/contract/contract.ts:38-47,445-464`，分页提示见 `src/cli/format.ts:23-25`。
- **建议改法**：选原生方法参数作工具合同最简单：明确工具只复用命令名、摘要与结果 formatter，参数采用方法 schema，不声称位置参数同名；给 Position/from/to、perspective、cursor/limit 补具体说明与 JSON 示例。若要 CLI 风格，则在命令表增加可生成 schema 的结构化元数据并走现有 decoder，不能混用。验收至少覆盖 read 跨章、para、between、筛选数组、角色视角与第二页实际取回新条目。

### 8. 19.6% 是 33/168 四舍五入后的基线，按字面验收却只允许错 32 份

### 10. 核心组合不变量没有对应的组合验收，单段与顺序测试抓不到账本错误

- **严重程度**：重要；**类别**：测试。
- **位置**：`docs/specs/story/qa.md:180-186`；`.agents/works/w00024-nb-story/tasks/t05-qa/plan.md:138-149`。
- **现象**：现有场景分别测本章裁剪、第三个新章被拒、单段未读出处；没有测跨章范围、范围内漏读一段、同章分多次阅读的并集、跨章请求整体超过额度时不允许部分读取，也没有把“提醒”与 length/error/aborted 或混批收尾组合起来。删除验收还是“答完后删除”，计划的运行中测试只写了“删除再重新导入”，漏掉不重新导入及新代另有 ask 的情况。
