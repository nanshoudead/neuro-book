### 3. 工具结果序列化失败后，下一轮 turn 永久等待；取消与 close 都无法结束

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`.worktree/w00024-t05-impl-review/packages/nb-harness/src/harness.ts:197-201,259-267,360-378,388-396`。
- **现象**：普通查询工具返回循环引用的 `details` 时，第一轮按 `error/local` 返回，但该工具结果已进 OMP 的内部消息、没有进 harness 的 `history`。同一会话第二次 `turn()` 把这条旧结果列为 expected；它不会再收到 `message_end`，新一轮又清空了 `hostError`，于是永远等 `historyChanged`。随后 abort 与 `close()` 也不唤醒等待，二者都挂住。
- **为什么是问题**：等待把“当前尚未投递的结果”和“上一轮已明确无法持久化的结果”混为一类；只检查当前 run.hostError 不够。破坏 harness 输出 10 的运行期失败可返回、关闭必须完成的寿命合同。这条无限等待由本次新增循环引入，base 没有这段等待。现有循环引用测试只覆盖收尾工具的第一轮，不覆盖普通工具出错后再次运行。
- **如何核实**：`bun /home/notnotype/.claude/jobs/568d0811/tmp/review-t05-impl/probes/harness-wait.ts`，真实 `createHarness`、工具执行、OMP 调度与 memory session log；第一轮 `error/local`，第二轮 300 ms 后 `settled:false`，发 abort 并调 close 后再 300 ms 仍 `settled:false, closed:false`，请求数不再增长。超时仅用于观测死等，没有伪造 message_end 的顺序。代码同时证明该历史结果没有后续唤醒来源。
- **建议改法**：持久化失败必须成为会话级不可恢复状态，后续 turn 立即返回明确 local 错误，或在失败当轮就把 OMP 调度历史恢复到可持久化的完整历史；不要永久等上一轮的旧结果。等待只跟踪本轮已登记的在途提交，并接入取消/关闭唤醒。补“普通工具序列化失败 → 再次 turn → abort/close”的真实运行时用例。

### 4. writableBook 返回裸路径后换代，旧问仍写进新书并谎报保存成功

### 9. transformContext 对每个历史结果重新扫描全部 history，整轮工具会话变成立方级扫描

- **严重程度**：建议；**类别**：安全与性能。
- **位置**：`.worktree/w00024-t05-impl-review/packages/nb-harness/src/harness.ts:198-201`。
- **现象**：`expected.some(id => !written().has(id))` 每检查一个 id 都重新 filter/map 整个 history、创建一个 Set，不是每次检查建一次。即使没有任何消息迟到，这段也会执行完整重复扫描。
- **为什么是问题**：本产品明确不设工具步数上限。设已有 n 条工具结果、history 至少 2n+1 条消息，一次请求就建 n 个 Set 并扫描 n(2n+1) 个消息项。连续 1000 轮、每轮 1 个工具，仅检查“都已写入”的成功路径就至少构造 500500 个 Set，累计扫描 668167500 个消息项；无需这种开销就能判断提交是否追上。此重复扫描是本次新加，base 没有。
- **如何核实**：按上述行的调用位置逐项计数；`context.ts` 探针已在真实运行时走到该路径。本条是静态复杂度核实，不冒充已做大规模性能基准，未声称具体耗时或内存峰值。
- **建议改法**：最小改法是在每次循环条件检查前只构建一次 written Set；更简单的生命周期模型是在成功提交时维护已提交结果 id/提交序号，等待本轮尚未提交的那一批，不逐次回扫所有历史。与发现 3 的会话失败状态一并收口，避免新增另一套旁路状态。
