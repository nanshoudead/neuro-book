# t10 实施计划：长书抽取的单章费用

## Context

抽取每章发 3 到 4 次请求（时间点与段落块、其余记录、核对补漏，必要时修复），每次都带上“已有记录”（[`story/ingest.md`](../../../../../docs/specs/story/ingest.md) 输出 4）。“已有记录”里有五节按全书累计、没有上限，单章费用随章数线性增长，整本随章数的平方增长。实测见 [README](README.md) 的“当前状态”：样例书第 98 章时已有记录 55,775 字，是本章原文的 24 倍；“已有的说法”每章带约 356 条、约 1.7 万字，99 章里只被引用 16 次；对象、疑问、秘密、时间点的引用都集中在最近几章与本章出现的对象上。

开发者 2026-10-20 的决定：

1. 对象、疑问、时间点、秘密先用简单规则筛。
2. 说法改成挑与本章相关的几十条，由一个可配置的 LLM 挑（这次用 gpt-6-luna）。挑选的方式做成可替换的：以后可以换成 Jev 这类 decision 模型，两者的输入输出相同、执行过程不同（例如 decision 模型逐条或二分判断，LLM 一次看一批）。decision 模型的召回评测（Jev 与其他模型）另立后续 Task。
3. 不加判分模型；不改图结构。
4. 数值、秘密做成按书可关闭（数值默认开），另立 t11，不在本 Task。
5. 缓存实验已做（jiji gpt-6-luna）：一条消息时前缀就能命中，拆消息没有好处，消息结构不改。

## 关键设计

### 一、`src/ingest/context.ts`：规则筛选

`renderContext(dataset, afterChapter, focus?)`。`focus` 是这次要抽的章的原文与挑好的说法；不传时（整理）照旧全量。行的写法不变，只改每节列哪些行：

- **相关对象**：此时已登记的称呼（至少两个字）出现在本章原文里的对象，加上最近 3 章有称呼出现（`dataset.mentions`）的对象。快速匹配用 t09 的 `occurrenceFinder`，从 `compile.ts` 移到 `ingest/` 下的共用模块并导出。
- **对象名册**：相关对象照现在的格式详列；其余对象收进一行“其他对象”，只写编号与当前称呼。
- **秘密与知情**：秘密的 `about` 含相关对象，或有相关对象的知情记录，才列。
- **当前状态**：`owner` 是相关对象的才列。
- **未解的疑问**：最近 20 章里提出或有进展的才列。
- **时间点**：按先后取最后 20 个。
- **最近的情节**：不变。
- **已有的说法**：列 `focus` 里挑好的说法（见下一节）。
- 被筛过的节标题下加一句说明列了哪些、没列的怎么办，措辞随回归定。

实测与召回（样例书、t34 最终草稿的实际引用为准）：对象 93.5%、疑问 97%、秘密 97.2%、时间点 99%；规则漏掉的对象仍在“其他对象”里有编号与称呼。

### 二、`src/ingest/recall.ts`（新）：挑相关的说法

接口按“候选加本章原文，返回选中的编号”定义，LLM 是第一种实现：

```ts
interface RecallInput { chapter: number; text: string; candidates: {id: string; text: string}[]; limit: number }
interface Recaller { select(input: RecallInput, run: StepRun): Promise<string[]> }
```

- **候选**：先用规则缩小，再交给 LLM。全量说法每章约增 700 字（第 98 章约 7 万字、300 章约 21 万字），直接全塞时单这一步的输入就比省下的多，而且超出上下文。规则：说法的 `about`、`by`、`holder` 含相关对象，或挂在本次列出的秘密、疑问上，从新到旧取，到字数上限（暂定 2.5 万字）为止。
- **LLM 实现**：一次请求，系统提示写清“挑出写本章记录时可能要印证、反驳、修正或作为推断依据的说法，至多 `limit` 条（暂定 40）”，回复 `{"ids": [...]}`；不在候选里的编号丢掉；推理档 `minimal`。失败按现有的重试、重发规则处理，仍失败时这一章退回“最近 40 条”，在问题列表里记一笔（不让整章失败）。
- **配置**：`ingest.recall`，可写 `model`（与 `ingest.model` 同形）；不写时用 `ingest.model`。以后加 decision 模型时多一种 `kind`。
- **可回放**：每章选中的编号随章保存在抽取数据里，用量记在这一章、步骤名 `recall`；进度页步骤多一项“挑相关说法”。

### 三、`src/ingest/chapter.ts`

每章先 `recall`，再 `prefixFor({context: renderContext(prior, chapter - 1, focus), targets})`；整理照旧全量。

费用估算（第 98 章、按字数）：主请求里说法一节从约 1.7 万字降到约 1,600 字，按每章 3.5 次请求约省 5.4 万字；挑选一次约 2.5 万字。另外三节（疑问、时间点、对象）约省 1.5 万字 × 3.5 次。合计已有记录相关的输入约降一半；300 章时差得更多。主请求命中缓存时省得少一些（说法一节本来就只有第一次付全价）。

## Spec 与文档改动

- `ingest.md`：非目标“不控制费用”改写；输出 4 写明各节列哪些、说法由挑选步骤决定；每章步骤加“挑相关说法”；配置加 `ingest.recall`；实现合同里“发给模型的文字与定型时录下的请求逐字相同”改为与本 Task 回归通过时录下的相同。
- `qa.md`（配置一节若有引用）、`cli-skill.md` 的 `config` 字段同步。
- `context.ts` 模块头：验证依据改为本 Task 的回归。

## 切片

1. **S1 规则筛选**：`context.ts`、`occurrenceFinder` 移位、单元测试、字数表；说法一节先保持“最近 400 条”，单独看规则筛选的效果。
2. **S2 挑选说法**：`recall.ts`、配置、`chapter.ts`、进度步骤、回放测试与 Spec。
3. **S3 回归与长书评估**（真实模型）：不过门槛回到 S1、S2 调整，最多三轮，仍不过交开发者。
4. **S4 收尾**：后端审查（omp）、合入、Task 记录。

## 验收映射

- ingest.md 输出 4（改后）：`context.test.ts` 小书用例（本章出现的对象详列，其余进简表；超过 20 章没进展的疑问不列；整理用全量；说法只列挑中的）。
- 挑选步骤：`recall` 的回放用例（选中编号随章保存；回复里不在候选里的编号丢掉；挑选失败退回最近 40 条并记问题）。
- 质量：前 20 章三次回归合计不低于 360/477（t06 验收 11 的尺子）。

## 验证

1. `test:affected`、typecheck。
2. 已有记录字数：样例书第 25、50、98 章改前改后。
3. 长书评估：前 60 章用 t34 最终草稿直接提交，真实模型抽第 61 到 70 章两遍（现在的已有记录与改后的）。比较：与已有对象重名的新对象数、引用前文说法的次数（`rel`、`premises`、秘密挂的说法）、引用错误与编译错误、丢弃的记录数、每章输入 token 与费用。
4. 未验证的边界：300 章以上的真实运行，只按推算给出。

## 不做与风险

- 不做：decision 模型（另立 Task）；数值与秘密的开关（t11）；改图结构；改情节与说法以外的上限；时间点与段落块那一步的单独精简（见 README，等缓存与本 Task 的结果再看）。
- 风险：规则漏掉的对象可能被重复新建（靠整理合并、靠长书评估量）；超过 20 章的疑问被解答时会新建疑问；挑选漏掉该印证的旧说法；挑选那一步也要钱，主请求缓存命中好时净省得少。
- 真实模型费用（需开发者批准）：20 章回归三次约 6 元；长书评估两遍各 10 章约 3 元；每多一轮调整再加约 9 元。
