### 1. 默认请求基线漏掉显式全开与 repair，两个请求文字变异仍全部通过

- **严重程度**：重要；**类别**：测试。
- **位置**：`packages/nb-story/src/ingest/chapter.test.ts:39-40,77-78,100,133,139-143,189-196,225`；`packages/nb-story/tests/fixtures/ingest/requests-t10.json:2-39`
- **现象**：新增基线只被“不传 features”的前 10 章与 recall 第 10 章回放调用。fixture 的 34 个请求键中没有 repair；新增三个关闭组合也没有显式 `{ledger:true,secrets:true}`。隔离副本里仅在显式全开时向真实请求前缀增加一行，`chapter.test.ts` 仍是 21 pass / 0 fail；仅在 repair 用户消息尾增加一行，同样 21 pass / 0 fail。
- **为什么是问题**：Spec ingest 输出 18 与计划验收明确保护“两项都开时每个请求逐字相同”，计划还要求缺省与显式全开分别对照，且基线包括修复请求。现在 HTTP 回放只按请求头选回复，正文变化不影响回复；repair 测试只看结果与步骤，不比较正文。以后这两条实际路径改变提示词，现有基线不会报警。这是已证实的测试缺口，不是声称当前默认提示词已经改变。
- **如何核实**：原始六文件定向测试为 77 pass / 0 fail。运行 scratch 下三个隔离副本各自的 `bun --no-env-file --no-install test src/ingest/chapter.test.ts`：`mutations/explicit` 与 `mutations/repair` 各 21 pass / 0 fail / 168 expect；对照 `mutations/context` 只改变普通章已有记录、保持全量 context 不变，新基线在第 133、225 行失败（19 pass / 2 fail）。完整输出在 `scratch/mutation-explicit.log`、`mutation-repair.log`、`mutation-context.log`。均经真实 extractChapter → OpenAI SDK → 本机 HTTP，不改仓库源码。
- **建议改法**：同一套基线回放参数化覆盖不传 features 与显式全开；另注入确定的结构错误，使 review 后进入 repair，将实际 repair 请求纳入不可替换的基线，并验证这两种变异都会失败。保留现有已能抓住 narrowed context 差异的直接断言。

### 2. 关闭秘密时把一般知情复核指令也删掉，没有按计划保留 statement 知情的更新要求

- **严重程度**：重要；**类别**：正确性（提示词合同）。
- **位置**：`packages/nb-story/src/ingest/prompts.ts:171-177`，特别是第 173 行的 `[features.secrets, ...]`。
- **现象**：原条目包含两件事：“秘密清单里的每个秘密……”以及一般的“知情表里标了推断的判断，本章有没有新的依据（支持或反驳）；有就补一条知情记录”。实现用同一个 secrets 条件把整条删掉，没有为关闭分支保留后一件事。真实第 4 章 SDK/HTTP 请求的【任务】里不再有知情判断随新依据更新的要求。
- **为什么是问题**：开发者决定 2、Spec ingest 输出 18 明确保留指向说法的知情；计划第 45 行要求把此项改为只讲知情，而不是删除。关闭 secrets 不代表不需要在后章修正先前对说法的推断。当前改动裁掉了另一项仍启用行为的抽取指令。这里证明的是发出的任务缺失，不声称已通过真实模型测出丢失率。
- **如何核实**：`cd /tmp/review-w00024-t11-impl/scratch/experiments && bun --no-env-file --no-install check-pipeline.ts`，经原实现 `extractChapter → OpenAI SDK → 本机 HTTP`；`scratch/pipeline-results.json` 的 `secretsOff.hasReevaluateInstruction=false`，任务全文在同项 `task`。该章确实保留了 4 条显式 statement 知情（`k4-4,k4-5,k4-6,k4-9`）与 1 条本人 identity 派生知情，说明一般知情仍是开启功能，不应连同秘密自查一起关掉。代码对照可直接看到仅有的该条指令被 secrets 条件包住。
- **建议改法**：默认全开分支逐字不动；secrets=false 时使用计划要求的一般知情复核条目，只去掉关于秘密清单的前半句。验收关闭分支实际请求仍要求在新依据支持或反驳旧推断时补知情，而不是只验“不要写 secrets”与数据数组为空。

### 3. 关闭组合测试没有覆盖补丁重入，删除每次 applyPatch 后的 strip 仍全部通过

- **严重程度**：重要；**类别**：测试。
- **位置**：`packages/nb-story/src/ingest/chapter.test.ts:137-178`；受保护的实现是 `packages/nb-story/src/ingest/chapter.ts:194-200`。
- **现象**：三个关闭组合都只抽录下的第 4 章；该章 review 的 replace 不写 ledger、secrets、statement.secret 或指向秘密的 knowledge，也不会进入 repair。把第 199 行 `draft = strip(fixPositions(applyPatch(...)))` 改为不调用 strip 的版本，整份 `chapter.test.ts` 仍为 21 pass / 0 fail / 168 expect。
- **为什么是问题**：初稿剥离不能保证补丁不会再加入禁用记录。计划与 Spec 的编译前去掉必须覆盖每次补丁，而这是新增代码中独立的第二个调用点。当前回放只证明初稿路径，未保护补丁重入与 repair 后兜底的提交不变量；不是当前实现少了调用，而是调用被删掉时所列验收仍会通过。
- **如何核实**：在 `scratch/mutations/patch-strip` 的隔离副本运行 `bun --no-env-file --no-install test src/ingest/chapter.test.ts`，输出在 `scratch/mutation-patch-strip.log`。另经原实现的 `check-pipeline.ts` 与本机 HTTP，分别在初稿、review、repair 三次回复写同一组禁用记录并让 repair 留一条坏说法：真实执行两轮补丁和兜底，最终 ledger=0、secrets=0、statement.secret=0，保留 1 条显式 statement 知情与 1 条本人派生知情；说明累计去掉每类各 3 条，dropped=1（只算坏说法）。当前实现正确，但仓库测试没有这条能杀死变异的场景。
- **建议改法**：在现有“按书关闭”行为测试里，给 review/repair 的真实 HTTP 回放注入重新写入禁用记录的回复，明确使结构问题延续到兜底；按具体记录核对禁用类缺失、启用类和 statement 知情保留、去掉的计数与 dropped 分开。删除第 199 行 strip 的变异必须令该测试失败。

### 4. “指向说法的知情保留”只断言至少一条，漏掉部分显式知情仍通过

- **严重程度**：建议；**类别**：测试。
- **位置**：`packages/nb-story/src/ingest/chapter.test.ts:157-170`，特别是第 163 行。
- **现象**：第 4 章有 4 条显式 statement 知情，测试只要求 `knowledge.some(item => item.about.startsWith("s"))` 为 true。隔离副本仅在关秘密时额外删除 `k4-4`（仍保留其余 3 条），整份 `chapter.test.ts` 仍 21 pass / 0 fail / 168 expect。额外变异把关闭分支的 about 写法重新改成“写秘密编号”，测试也全部通过。
- **为什么是问题**：决定 2 保护的是已有的显式 statement 知情照常保留，不是最后还有任意一条就算成立；而计划要求对 about=s 的请求写法有实际验收。这两种会让关闭功能误伤保留功能的错误，当前断言都无法识别。原实现运行中确实保留了这 4 条，故这是覆盖缺口，不是数据已经丢失的指控。
- **如何核实**：在 `scratch/mutations/explicit-knowledge` 与 `scratch/mutations/knowledge-instruction` 各运行 `bun --no-env-file --no-install test src/ingest/chapter.test.ts`。完整日志为 `scratch/mutation-explicit-knowledge.log`、`scratch/mutation-knowledge-instruction.log`；原实现保存的具体 4 条见 `scratch/pipeline-results.json → secretsOff.explicitKnowledge`。所有变异都只改 scratch 副本。
- **建议改法**：按已录下的行为断言这 4 个 id、about 与 derived=false 都保留，另独立断言本人 identity 的派生 statement 知情；不要把 expected 从 stripDisabled 的结果生成。请求任务段核对关闭分支仍明确要求 about 指向 statement，而非只匹配“这本书不记秘密”。
