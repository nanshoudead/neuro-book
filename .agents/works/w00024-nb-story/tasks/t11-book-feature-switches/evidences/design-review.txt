# t11 设计审查报告

### 1. `features` 没有落到书库元数据，`books.list` 无法按合同返回
- 严重程度：阻断
- 类别：不变量
- 位置：计划 `plan.md:17-19,42-45`；`packages/nb-story/src/core/library.ts:51-70,227-271,310-344`；`packages/nb-story/src/contract/contract.ts:57-65,367-377`
- 现象：计划同时要求 `book.features` 写入 V9 数据、`books.list` 与 `book.info` 返回 `features`，但现有 `BookMeta` 没有该字段。`books.list` 只读 `book.json` 元数据，`book.info` 也直接从 `ctx.index.meta` 返回元数据；`book.import` 只把原始 graph 文件写入书目录，`commitExtraction` 只从 Dataset 更新章数、段数和抽取进度。计划没有说明把 features 写入 `BookMeta`，也没有说明导入时如何让列表查询拿到 graph 内的字段。
- 为什么是问题：照字面只把字段放进 `Dataset.book`，`books.list` 仍无法知道每本书的开关；只把它放进 `BookMeta`，抽取提交与 `book.import` 又没有来源；只在查询时临时打开 graph 读取，会改变 `listBooks` 的轻量元数据路径且没有导入/旧书兼容的原子更新合同。结果至少有一条公开接口缺字段，或不同入口对同一本书显示不一致。
- 如何核实：读取 `Library.listBooks()` 的返回值和 `bookInfo()` 的取值路径；读取 `importBook()` 与 `commitExtraction()` 的 `BookMeta` 构造，确认当前没有 `features`。再按计划验收 `books.list`、`book.info`，现有合同 schema 也会因缺字段失败。
- 建议改法：先决定唯一存储源。稳妥做法是给 `BookMeta` 增加可选 `features`，新建抽取提交与 `book.import` 都从 Dataset 归一化后写入，旧 `book.json` 读时补 `{ledger:true,secrets:true}`；`Dataset.book.features` 同样按旧数据默认全开。若坚持只存 graph，则必须明确并实现列表/书信息的原子读取与缓存策略，并补并发提交、导入失败和旧书路径的合同测试。

### 2. 单独关闭一项时，`draftTask` 的固定尾句会禁止另一项
- 严重程度：阻断
- 类别：正确性
- 位置：计划 `plan.md:27-32`；`packages/nb-story/src/ingest/prompts.ts:149-172`
- 现象：计划要求关闭任一项时在 `draftTask` 末尾追加固定文字“这本书不记数值（ledger）和秘密（secrets）：不要写这两部分，说法也不写 secret 字段”。但设计支持四种状态：两项都开、只关 ledger、只关 secrets、两项都关；只关一项时该句仍说两类都不要写，并且无条件禁止 `statement.secret`。
- 为什么是问题：只关 ledger 的书仍应抽取秘密与 `secret` 字段，否则秘密查询和“指向秘密的知情”会被静默丢失；只关 secrets 的书仍应抽取 ledger，否则数值功能被错误关闭。这不是模型偶发偏差，而是发给模型的任务合同直接与开关语义相反。若把句子只在“两项都关”时追加，又没有覆盖单项关闭时对应的禁止语句，仍不能满足单项路径。
- 如何核实：逐项代入 `ledger=false,secrets=true` 与 `ledger=true,secrets=false`，对照计划 `draftTask` 的输出字段和自查条目；当前函数的字符串是单份固定文本，默认不传参数时也没有任何 feature 分派。
- 建议改法：按两个布尔值生成明确的禁用片段，只声明实际关闭的类别；`secret` 字段只在 `secrets=false` 时禁止。保留默认 `{ledger:true,secrets:true}` 的旧函数输出作为逐字断言，并分别断言两种单项状态仍保留另一类的字段、检查和自查规则。

### 3. 关闭秘密后仍会触发 `secret-missing`，导致每章反复核对或无法提交
- 严重程度：阻断
- 类别：正确性
- 位置：计划 `plan.md:33-40`；`packages/nb-story/src/ingest/compile.ts:554-569`；`packages/nb-story/src/ingest/chapter.ts:90-96,191-220`
- 现象：现有编译器对每条确定的 identity 说法检查：没有 `secret` 且没有覆盖两端对象的秘密时产生 `secret-missing`；`chapterIssues()` 把这一 warning 特别提升为本章核对问题。计划要求 secrets 关闭时移除所有 `secrets` 与说法的 `secret` 字段，却没有定义关闭状态下禁用这条检查。
- 为什么是问题：只关 secrets 的正常草稿会留下 identity 说法但不允许建秘密。照现有流程，这些合法记录仍被列入 checklist，review/repa​​ir 还会被要求“补 identity 说法、秘密和知情”；即使模型不补，最终 `remaining` 仍会记录该问题，且修复过程可能把不该写的秘密重新加回来。把记录在编译后再过滤也太晚，因为错误已经影响核对和提交判定。
- 如何核实：构造一个只含确定 identity statement、不含 `secrets` 的单章 draft，运行 `compile()` 与 `chapterIssues()`；现有实现会得到 code=`secret-missing`，而不是空问题。再按计划把 `secret` 字段删除，条件不变。
- 建议改法：把 features 作为 compile 的显式输入，并在 `secrets=false` 时跳过 `secret-missing` 规则及所有依赖秘密存在的自动知情/身份提示；同时在关闭状态下对 `statement.secret`、秘密记录和秘密知情做统一过滤后再编译。为“只关 secrets 仍可提交 identity 说法”和“只关 ledger 不改变 secret 校验”各补一条回放测试。

### 4. “编译前去掉”没有定义跨章引用闭合，过滤后会制造新的引用错误
- 严重程度：重要
- 类别：正确性
- 位置：计划 `plan.md:35-40`；`packages/nb-story/src/ingest/compile.ts:119-139,287-307,349-360,390-401,447-457`；`packages/nb-story/src/ingest/draft-tools.ts:200-226,305-359`
- 现象：计划只列出删除 `secrets`、`statement.secret`、`knowledge.about` 和 `ledger`，没有规定先建立全书的被禁用 id 集，再递归处理引用。现有编译器允许知情记录用 `about` 指向前章说法或后章才建立的秘密，`ConsolidationSchema` 的 `summary.items[].deps` 也会检查 `knowledge` 与 `ledger`；修复路径里的 `applyPatch` 可以再次从 `replace` 添加这些记录，`remove` 只按 id 删除，不会清理引用。
- 为什么是问题：跨章场景中，前章知情可能指向后章建立的秘密；只按当前章或按编号前缀过滤会漏掉它。过滤秘密后，残留的知情会触发 `ref` 错误，`pruneReference` 对 knowledge 的必填 `about` 只能整条丢弃；整理摘要若保留被删 ledger id 会触发 `summary` 错误。修复回复里重新放回被关闭的 section 也会绕过一次性清理。这样合法的“指向说法的知情”与不合法的“指向秘密的知情”无法靠当前计划的字段清单区分，提交结果依赖修复轮次和丢弃顺序。
- 如何核实：构造两章草稿：第 1 章 knowledge 指向第 2 章才创建的 secret，第 2 章再关闭 secrets；另构造 consolidation 的 `deps` 含 ledger id，运行 `compile()`。现有 `has()` 和摘要检查分别产生 `ref`/`summary` 问题；读取 `applyPatch()` 可确认 repair 的 `replace` 会重新加入被关闭 section。
- 建议改法：在抽取管线入口把 features 传入，先扫描所有已提交草稿与候选修复的全书 secret/ledger id，生成禁用 id 集；每次草稿刚生成、每次 patch 后、整理 sanitize 后都按这个集合过滤，并递归清理 `statement.secret`、knowledge 的 `about`、摘要 deps、问题更新中指向被删记录的字段以及 `remove` 造成的引用。过滤条件必须是查表，不是 `x`/`l` 编号前缀；保留指向仍存在 statement 的 knowledge，并为前章知情指向后章秘密补测试。

### 5. 导入的关闭书没有查询层门禁，非空 ledger/secrets 会重新暴露
- 严重程度：重要
- 类别：不变量
- 位置：计划 `plan.md:17-19,42-45`；`packages/nb-story/src/core/dataset.ts:208-226`；`packages/nb-story/src/core/book-index.ts:158-215`；`packages/nb-story/src/core/projection.ts:77-128`；`packages/nb-story/src/core/queries/books.ts:31-55`、`graph.ts:136-178`
- 现象：计划明确允许 V9 导入数据文件带 `book.features`，但又把“关掉的书本来就没有这类记录，查询自然返回空”当作实现依据。现有 `DatasetSchema` 只校验 `ledger`/`secrets` 数组，`buildBookIndex()` 无 features 过滤，`BookView`、`book.stats`、`chapter.digest` 与 `graph.book` 都直接消费这些数组。
- 为什么是问题：导入文件是外部输入，不能假设它已经遵守“关闭后绝不含记录”的内部不变量。一个 `features: {ledger:false,secrets:false}` 但数组非空的合法 V9 文件会让 `ledger.tracks`、`secrets.matrix`、统计、章节摘要和全书图继续返回秘密/数值；网页隐藏导航也挡不住 CLI、HTTP 或问答的直接查询。这同时违反“关掉后不列、不提供查询”和导入数据与抽取得来的书用法相同。
- 如何核实：写一个最小 V9 数据文件，`book.features` 两项为 false，同时放一条 ledger、一条 secret，调用 `Library.import` 后依次调用 `secrets.matrix`、`ledger.tracks`、`book.stats`、`chapter.digest`、`graph.book`；按现有索引/投影路径这些记录都会进入结果，除非实现另加门禁。
- 建议改法：在导入边界明确合同：要么拒绝 features 关闭但数组非空，要么在导入/索引时规范化丢弃整类记录并闭合引用。更安全的是在 `BookIndex`/`BookView` 的统一出口按 features 过滤，并让 `book.stats`、`chapter.digest`、图和 QA 共享这个投影；旧数据 features 缺省全开。为“关闭但输入数组非空”补核心 API 与 HTTP 同结果测试。

### 6. QA 的静态 Profile 会继续声明关闭的工具，计划列出的文件不足以实现“命令表按书生成”
- 严重程度：重要
- 类别：接口与合同
- 位置：计划 `plan.md:54-56,71-73`；`packages/nb-story/src/qa/story-qa.profile.tsx:7-24`；`packages/nb-story/src/qa/engine.ts:121-132`；`packages/nb-story/src/qa/tools.ts:54-58,84-142`
- 现象：现有 `story-qa.profile.tsx` 在模块加载时用固定 `QUERY_TOOL_IDS` 把 20 个查询工具全部放进 Profile；`askQuestion()` 创建 Harness 时传入这个静态 profile。`storyQaPlugin()` 虽然每问可拿到 book state，但当前总是注册全部工具。计划只列 `qa/tools.ts`、`qa/engine.ts`，没有处理 Profile 的工具引用、注册时序或 optional 工具机制。
- 为什么是问题：只在 `tools.ts` 里从 `QUERY_COMMANDS` 过滤并不够：关闭书的 `ledger`/`track`/`knows` 要么仍被模型看到，要么 Profile 引用未注册工具而 Harness 在建会话时报 `tool_unavailable`；把 execute 改成返回“未知命令”也违反“命令表里没有”，且模型仍会调用。系统提示词第 31 行也固定写“人物、身份、谁知道什么、情节、数值、悬念”，不随工具集合变化。
- 如何核实：读取 `defineProfile()` 的静态 `tools` 与 Harness 的 `createHarness({profile, registry})` 调用；用一个关闭 features 的 `BookSession` 只注册非关闭工具，现有 Profile 仍要求全部 `story.knows`、`story.ledger`、`story.track`，工具解析阶段即不满足。用当前注册全部工具则模型仍收到这三个声明。
- 建议改法：把 Profile 工具集合改成可按初始 features 派生的定义，或把所有查询引用标为 optional 并让注册插件按书只注册可用工具；同时按 features 生成 QA 系统说明。静态 Profile 与动态工具的实际 API 要先用 nb-harness 的 effective-tools 合同验证，再补“关闭书模型看不到工具、直接调用也得到未知命令”的工具测试。

### 7. 隐藏页的地址回退不在计划列出的外壳文件里，直接地址会渲染空组件
- 严重程度：重要
- 类别：正确性
- 位置：计划 `plan.md:47-52,71-73`；`packages/nb-story/src/web/host/book.ts:23-25,113-115,150-195`；`packages/nb-story/src/web/shell/BookFrame.vue:31-63,264-287`
- 现象：页面枚举 `PAGES`、地址合法性 `isPage()` 和从 `route.params.page` 初始化当前页都在 `web/host/book.ts`；外壳只是按固定 `NAV` 和 `PAGES[book.page.value]` 渲染。当前 `/book/id/ledger` 会被接受为合法页，外壳也会加载 LedgerPage。计划只列 `BookFrame.vue` 等页面文件，没有列 `host/book.ts` 或地址同步逻辑，却要求地址直达关闭页时回总览并提示。
- 为什么是问题：只从导航数组移除页不能处理旧链接、手输地址、保存状态中的旧页或全书图/总览跳转产生的目标。直接地址在计划实现前仍打开关闭页；若只改 `NAV` 而不改 host，`book.page` 仍是 `ledger`，页面可能显示空壳/空查询结果，不会按合同回总览。地址回写还可能把旧页再次写回 URL 或 `reading.set`，造成刷新后重复进入。
- 如何核实：调用 `openBookSession()` 时把当前 route 设为 `/book/<id>/ledger`，观察第 165 行的 `isPage()` 会接受它；`BookFrame` 第 266/287 行直接索引对应页面。现有代码没有任何 features 判断或 fallback 分支。
- 建议改法：在 host 会话初始化、外部路由变更和保存状态恢复三个入口统一校验 `page` 是否被 features 允许；不允许时原子地设为 overview、清理对应 target/tab，并设置一次性 notice，再同步地址。导航、手机“更多”、全书图节点跳转和保存状态都只从同一份允许页集合生成。计划和 e2e 必须覆盖直接打开、后退/手改地址、旧 reading state 三条路径。

### 8. 统计页和逐章图不在查看器切片中，关闭后仍显示“秘密/数值”空壳
- 严重程度：重要
- 类别：遗漏
- 位置：计划 `plan.md:47-52,71-73`；`packages/nb-story/src/web/pages/StatsPage.vue:19-22,37-65`；`packages/nb-story/src/web/parts/ChapterBars.vue:8-17`；`packages/nb-story/src/contract/contract.ts:73-82`
- 现象：计划列出的查看器文件没有 `StatsPage.vue`、`ChapterBars.vue`，也没有说明 `book.stats` 的 `visible`、`chapters`、`extraction.written/generated` 如何按开关改标签与图例。现有统计页固定把 `secrets`、`ledger` 放进 LABEL，逐章图固定绘制 `ledger` 系列；API 的统计结果也固定返回两项计数。
- 为什么是问题：即使核心查询返回 0，关闭两项的“说明与统计”仍会列出“秘密 0”“数值流水 0”“数值”颜色条，用户看到的是被隐藏功能的空壳，且与计划“关掉的项不显示”不一致。若仅删除查询数组而不改 stats schema/组件，图例、堆叠列和全书抽取统计还会出现无意义行；若改 schema 而不改 `StatsPage`，渲染又依赖缺失字段。
- 如何核实：用现有样例数据调用 `book.stats`，`StatsPage` 对 `Object.entries(stats.visible)` 和固定 LABEL 直接渲染；`ChapterBars` 的 `SERIES` 固定含 ledger。代码路径没有 features 分支。
- 建议改法：明确 stats 的过滤层和输出合同：关闭时从 visible、逐章 rows、抽取 written/generated 中移除相应键，或保留机器字段但页面必须用 features 过滤；`StatsPage`、`ChapterBars` 和相关文档一并更新。验收应断言两项关闭时统计页没有秘密/数值行、图例和颜色系列，而不是只断言总览没有块。

### 9. 评测计划没有把 53 条尺子变成可复现的 29 条子集，`regress-20.sh` 也不接收开关
- 严重程度：重要
- 类别：测试
- 位置：计划 `plan.md:90-99`；`.agents/works/w00024-nb-story/tasks/t06-ingest/scripts/regress-20.sh:5-29`；`.../scripts/ruler/check.ts:9-19,36-42`；`.../scripts/ruler/score.ts:1-19`
- 现象：现有回归脚本用法只有 `regress-20.sh <运行名>`，第一次 ingest 没有 `--no-ledger`/`--no-secrets`，后续 `--book` 也没有 feature 参数。尺子检查器支持的只有按显式 id 的 `--only`，计分器按传入结果目录中的所有结果计算；计划只说“去掉秘密、数值两类”而没有固定 id 清单、脚本参数或输出元数据。
- 为什么是问题：清单共 53 条，其中数值相关 15 条（账本数值 7、道具 3、任务进度 5），秘密/知情相关 9 条（知情 7、秘密存在 2），剩余 29 条。若仍跑完整清单，关闭后的记录必然被判“缺”或因空数组触发错误；若手工用 `--only`，三次运行可能选出不同集合，`score.ts` 也不会验证集合一致，满分和 t10 全量基线不可比。脚本不传开关则连待评估的书都不是关闭配置。
- 如何核实：运行 `jq -r '.items | group_by(.category)[] | [.[0].category,length] | @tsv' .../checklist-ch1-20.json` 得到上述 11 类数量；读取 `regress-20.sh` 的参数解析和第一次命令，确认没有开关；读取 `check.ts`、`score.ts`，确认没有按类别过滤或集合一致性校验。
- 建议改法：给回归脚本增加显式 `--no-ledger`、`--no-secrets` 或 `--features` 参数，仅在第一次新建命令传入，并把生效 features 写进输出元数据；为尺子生成固定的 `t11` checklist/`--only` 清单（明确 29 个 id），`score.ts` 校验所有结果目录的 id 集相同、报告 29 条和满分 261/次。报告同时保留与 t10 相同的剩余类别、同一判定方式和 token/费用字段，避免把不同分母的总分误称为可比。
