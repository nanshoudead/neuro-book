### 1. 角色视角中按独立身份打开人物卡，实际返回另一身份的人物卡

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/core/api.ts:93-96`、`packages/nb-story/src/core/queries/entities.ts:38-40`。

- **建议改法**：对象参数在当前查询分组中解析；原始对象 id 必须先保留再映射到该分组，名字匹配也在该分组中去重。视角人物自身的解析与普通查询对象的解析分开，不复用只返回读者代表 id 的接口。

### 2. 秘密矩阵把历史上的“知道”永久保留，忽略最新知情状态

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/core/queries/secrets.ts:38-43`。
- **现象**：没有确定身份连接的秘密，读者在 `1.2` 为 `knows`、`2.2` 改为 `unaware`，第 3 章的矩阵仍返回 `state="knows"`、`revealedAt="1.2"`。
- **为什么是问题**：输出 9 要求判断“读者最新的知情状态为知道或读到”，否则取最新状态。实现虽然先计算 `own`，却又把全部历史 `knows/read` 加入候选；只要曾经知道，最新状态永远不生效。`chapter.digest` 的揭晓列表也消费此结果。
- **如何核实**：同一个 `lab/queries.ts` 后半段通过公开导入接口导入合法 V9 小书，秘密不含身份说法，只有上述两条知情记录。输出 `latestSecret` 为 `{"columns":[{"id":"reader","label":"读者"}],"rows":[{"id":"x-test","title":"秘密","revealedAt":"1.2","cells":[{"column":"reader","state":"knows","ref":"1.2"}]}]}`。
- **建议改法**：先按最新知情记录决定读者知情分支是否成立，再与可见确定身份连接一起确定出处；不能用任意一条历史 `knows/read` 代替“最新状态”。补充从知道变成非知道状态的行为测试。

### 6. 文件系统阶段的 serve 启动失败绕过退出码 3

- **严重程度**：建议；**类别**：合同。
- **位置**：`packages/nb-story/src/server/serve.ts:38-40`、`packages/nb-story/src/cli/main.ts:141-143`、`packages/nb-story/src/cli.ts:8`。
- **现象**：`--library` 的父路径是普通文件时，`mkdir` 抛错直接冒出顶层；真实命令退出码为 1，输出 Bun 堆栈，而不是 serve 启动失败的退出码 3。
- **为什么是问题**：cli 输出 7 规定 serve 启动失败为 3，不只限于监听端口失败。拿锁前的目录创建与 `acquireServeLock` 都在启动错误收口之外，自动化无法凭退出码区分查询失败和服务启动失败。
- **如何核实**：`lab/boundaries.ts` 在临时根创建普通文件 `not-a-directory`，运行真实 CLI `serve --library <该文件>/library`；输出 `serveFsError {"code":1,"stdout":"","stderr":...}`，错误堆栈指向 `await mkdir(library, {recursive: true})`。
- **建议改法**：以一个拥有全部启动资源的外层错误分支覆盖目录、锁、监听、登记的建立；所有启动失败统一诊断并返回 3，已取得的资源按实际状态释放。

### 9. 畸形的 RPC 方法编码逃出错误边界，返回无实例号的 HTML 500

- **严重程度**：重要；**类别**：合同。
- **位置**：`packages/nb-story/src/server/http.ts:84-86,92-95`。
- **现象**：已登录后向 `/api/rpc/%` 发 `POST {}`，服务返回 500、`content-type: text/html;charset=utf-8`，没有 `x-nbstory-instance`，不是约定的 JSON 错误。此后 SIGTERM 虽删掉登记，但该进程退出码为 1。
- **为什么是问题**：`decodeURIComponent` 在 RPC 的 try/catch 之外抛出 `URIError`，外层 route 也没有错误边界，最后的实例号响应头根本没有执行。无效的外部路径编码不能变成运行时默认错误页；机器客户端既拿不到失败码，也不能按实例头识别该响应。
- **如何核实**：运行 `lab/server-runtime.ts`，通过真实 CLI 启动服务、登录，再请求上述路径。输出 `badMethodEncoding {"status":500,"contentType":"text/html;charset=utf-8","instance":null,...}`；日志含 `POST - /api/rpc/% failed`，最后 `serveExit 1`。该服务 PID 为 `3558954`，脚本已发送 SIGTERM 并等待其退出。
- **建议改法**：将路径解码纳入输入边界，畸形编码返回 400 与 `invalid_params`；在整个 HTTP 路由的最外层统一错误响应与实例号响应头，避免框架默认 HTML 错误页漏出。

### 11. serve 接受 --json，却输出无法解析的普通文字

- **严重程度**：建议；**类别**：合同。

- **建议改法**：将输出模式传给 serve，启动成功向标准输出写一份包含登录地址的结构化结果，诊断放标准错误；按现有合同覆盖启动失败的 JSON 行为。

### 14. 默认时间线按原始 order 排序，已知日子会从第 21 天倒退到第 20 天

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/core/queries/timeline.ts:27-41`；覆盖缺口见 `packages/nb-story/src/core/queries/timeline.test.ts:20-27`。
- **现象**：样例书的默认故事时间线先给 `t64-2`（`day=21`、`part="evening"`），紧接着给 `t64-3`（`day=20`、`part="night"`）；后者的相对时间还明确写为前者“之前 1 天”。第 64 章与第 100 章的位置都能看到这个次序。
- **为什么是问题**：queries 输出 12 要求按第几天、时段、同一天内的先后排序。实现只信任数据中的 `order`（这两点分别是 115、116），没有让已知日子参与排序；真实样例的结果与其自己的日子、相对时间矛盾。现有测试名称写“按故事时间排”，实际只检查存在补叙、补叙字段与章号相同，以及另一个 `order=source` 分支的章号有序，完全未断言默认排序。
- **如何核实**：运行 `bun /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00024-nb-story/tasks/t03-impl/reports/code-review-s1-s5/lab/timeline-order.ts`，经公开 API 得到 `backwardsKnownDays` 中恰有上述一组逆序；`timelineAt64` 仍是先 21 后 20。对原始样例的 `lab/sample-invariants.ts` 检查同时显示这两个 `order` 值。包内 128 条测试全部通过，不能检出这个问题。
- **建议改法**：已知日子的故事顺序首先按日子和时段决定，数据中的 `order` 仅用于同一天内仍需区分的先后；未知日子保留独立组。补叙判定使用同一套故事时间比较，避免排序与标记各用一套含义。用真实样例这两点断言结果顺序与相对时间一致。

### 15. 停止时撤销登记失败会让服务继续监听，之后的中断也不能完成清理

- **严重程度**：重要；**类别**：资源。
- **位置**：`packages/nb-story/src/server/serve.ts:81-92`、`packages/nb-story/src/server/registry.ts:58-60`。
- **现象**：服务启动后，将临时书库目录权限改为 `0500` 再发 SIGTERM，撤销 `.serve.json` 报权限错误。等待 2 秒后进程仍未退出，登记仍在，HTTP 仍返回 401。恢复权限后再发 SIGINT 也无法完成停止，实验最后用 SIGKILL 才结束。
- **为什么是问题**：`stop` 在第一步就把 `stopping` 置为 true，但 `await lock.withdraw()` 没有异常收口；失败后 `server.stop(true)`、`lock.release()` 和 `resolve(0)` 均不会执行，后续信号又被 `stopping` 拦住。一个登记文件的删除失败不应让服务无法关闭并永久持锁。权限变化、只读文件系统与 I/O 失败都是文件系统边界可发生的失败。
- **如何核实**：运行 `bun /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00024-nb-story/tasks/t03-impl/reports/code-review-s1-s5/lab/shutdown-failure.ts`，真实 CLI 服务 PID 为 `3657946`；输出 `shutdown.result="still-running"`、`registration=true`、`stillListening 401`，错误日志指向 `withdraw` 的 `rm`，最终 `finalExit 137`。脚本在 finally 恢复临时目录权限并等待该 PID 退出，未留下服务。
- **建议改法**：保留撤销登记先于停止监听的正常顺序，但停止流程使用 finally 保证关闭监听与释放锁，登记失败保留诊断并返回适当的失败退出码；重复中断不应把失败的停止流程锁死。用真实服务测试文件系统失败后的监听、锁与退出状态。

### 16. 服务测试的通用收尾全部强杀，无法发现正常停止失败

- **严重程度**：重要；**类别**：测试。
- **位置**：`packages/nb-story/src/server/server.test.ts:22-24`、`packages/nb-story/testing/processes.ts:34-50`；同类失败收口缺口在 `packages/nb-story/src/core/library.test.ts:19-21,118-138`。
- **现象**：服务测试的 afterEach 对所有实例执行 `stop("SIGKILL")`，也不检查返回码。只有两个用例中途显式检查 SIGTERM 的正常退出；其余服务用例的清理都直接跳过撤销登记、关闭监听和放锁的正常流程。`startServe` 的就绪等待若超时，会在返回进程句柄前抛错，调用方的 running 数组拿不到这个进程；换代测试的子进程与 pinned 句柄也没有失败路径的 finally，afterEach 只删临时目录。
- **为什么是问题**：仓库测试规则明确要求失败时也收口、在 afterEach 停止并核对正常关闭。强杀是“模拟崩溃恢复”用例需要的动作，但把它当作通用清理，会让第 15 条这样的停止流程缺陷在正常测试中被掩盖；就绪超时或中途断言失败时还会遗留进程或打开的文件。
- **如何核实**：逐行核对上述 afterEach、`serve()` 在 `startServe` 返回后才 push 的顺序，以及 library 的循环和清理。包内 128 条测试实跑全过。另用真实服务运行 `lab/shutdown-failure.ts`，已证明撤销登记失败后 SIGTERM 不能停服，最后必须强杀；测试通用收尾恰好不会验证这个正常关闭合同。超时和断言失败下的遗留风险是从现有所有权路径推断，未声称本轮制造了测试超时。
- **建议改法**：通用收尾发送 SIGTERM、等待并核对退出与登记撤销，SIGKILL 只用于明确的崩溃场景或有诊断的最后兜底。进程在 spawn 成功时就登记 owner；就绪等待失败、测试断言失败也经 finally 停止并 await。pinned 文件句柄与 watcher 同样在 finally 释放，再清理临时目录。
