# w00024/t06-ingest S1 到 S3 只读实现审查
### 1. 首章发布期间删除会成功返回，却留下无法继续抽取的书

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/nb-story/src/core/library.ts:347`、`:354`；`packages/nb-story/src/ingest/job.ts:115`、`:118`。
- **现象**：`removeBook` 先读 `meta` 与 `ingest`，然后才等待本进程任务停止、取得锁。首章正在写 `.importing-*` 时，`meta` 为 null；任务已经通过提交前的停止检查，仍会完成首章发布。删除拿到锁后继续使用旧的 `meta === null`，只删 `.ingest/<id>`，返回成功，但正式书目录仍在。实际运行 10 次，10 次都是 `removed.ok=true, books=1, source=false`。
- **为什么是问题**：违反 ingest 输出 16、验收 8：删除成功后书还存在，抽取记录已丢失；同 id 再发起会得到 `book_exists`，无法按 `new` 开始。旧书不是事后重建，而是被请求删除的任务自己发布的。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/storage.ts remove-first`。真实 `startIngest`、Bun Worker、HTTP 协议端点、`ingestRemoveGuard`、书库与文件系统；`fs.watch` 观察首章 `.importing-*` 目录出现后调用真实 `removeBook`，不替换实现、不伪造 Worker 事件。输出根目录 `/tmp/review-w00024-t06-impl/scratch/remove-first-1792477519729`。base 没有抽取任务与首章前状态，此路径为本次新增。
- **建议改法**：停止本进程任务并取得 id 锁之后，重新读取书与抽取记录，再决定删除哪些目录；不要跨等待保留存在性判断。补首章发布中删除与提交前停止的真实运行时用例。

### 2. 进度读取会在正常章提交时打开已经回收的抽取文件

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/ingest/job.ts:68`、`:75`；`packages/nb-story/src/ingest/status.ts:79`；`packages/nb-story/src/core/library.ts:290`、`:292`。
- **现象**：`readCommitted` 先读 `book.json`，再按路径读取 `extraction-N.json`，没有固定文件句柄或重试。两步之间提交可发布 N+1 并删除 N，导致正常 `ingestStatus` 抛 `ENOENT`。150 次连续真实提交、并发读取进度 620 次，出现 1 次 `open .../race/extraction-91.json` 的 `ENOENT`。
- **为什么是问题**：抽取期间的进度查询不能稳定返回；S5 的轮询会把合法提交显示为失败。`pinBook` 已专门处理同一种“读 meta 后旧文件被回收”的窗口，但进度走了另一套读取协议。不能只依赖主线程或 id 锁：`ingestStatus` 不持有写锁，其他进程也可查询。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/storage.ts status-race`。持真实 flock 的写者依次调用真实 `commitExtraction`，并发调用真实 `ingestStatus`，无 mock 或人为替换文件操作。输出 `reads=620, failures=1`；实验书库 `/tmp/review-w00024-t06-impl/scratch/status-race-1792477519766`。base 没有 `readCommitted` 与版本回收，本次新增。
- **建议改法**：为提交清单提供与图相同的固定快照读取协议：读 meta、打开文件、重验 generation/revision；因回收导致打开失败时重试，已固定的句柄读完即关。status 必须使用该协议；补与真实章提交并发的测试。

### 3. 未知格式的书库仍会写抽取记录并发送模型请求

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/ingest/runner.ts:62`、`:71`；`packages/nb-story/src/ingest/store.ts:106`；`packages/nb-story/src/core/library.ts:261`。
- **现象**：`startIngest` 在验证书库格式之前创建 `.locks`、占用 `.ingest/<id>` 并启动 Worker；只有整章抽完、调用 `commitExtraction` 才执行 `assertWritable`。实际给 `library.json` 写 `format:99` 后，发起返回 `action:new`，端点已收到 3 次 HTTP，原文已保存在书库；任务最后才以 `unsupported_format` 失败。
- **为什么是问题**：ingest“副作用与数据”要求不认识的格式只读不写、发起直接得到 `unsupported_format`。现路径既改变未知版本书库，又让用户为注定不能提交的一章付费。append 同样能先替换保存的原文；resume/done 的判定也不经写门禁。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/storage.ts unknown-format`。真实 start/Worker/SDK/本机 HTTP，假密钥；输出 `action:new, requests:3, sourceExists:true, outcome.code:unsupported_format`。实验书库 `/tmp/review-w00024-t06-impl/scratch/unknown-format-1792477519756`。base 的导入与删除在入口先 `assertWritable`，本次新增抽取入口没有沿用。
- **建议改法**：提供核心库拥有的写入准入检查，start 在任何书库写入与模型请求之前调用；取得 id 锁后再按需要复核。已有单书格式也应在提交前检查，而不能只检查根 `library.json`。补未知格式下新建、追加与续抽都不写业务数据、不发 HTTP 的用例。

### 4. 真正的 TCP 断流被归成本机错误，不执行任何渠道重试

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/ingest/model.ts:121`、`:139`、`:143`；`packages/nb-story/src/ingest/chapter.test.ts:168`。
- **现象**：SDK 只把建立连接阶段的失败包装成 `APIConnectionError`；读取已开始的 SSE 时，Bun 的断线错误直接从响应体迭代器抛出，被 `classify` 的末尾归为 `local`。真实 TCP 端点先发送 200、一个 SSE delta，再断开未结束的 chunked 响应；结果 `kind:local, received:1, waits:[]`。
- **为什么是问题**：ingest 输出 9 明确连接或流中断按 30/60/120/180/300 秒重试，最多 6 次；当前最常见的传输断流反而一次就终止。现有“流没有结束原因就断了”测试用的是正常 EOF（`cut` 返回完整 HTTP Response），不能覆盖响应体读取抛错的实际断线。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/model-cases.ts socket-reset`，真实 `node:net` 服务器、Bun fetch、OpenAI SDK 与 `callModel`；未注入 fetch 或错误对象。端点实际只收到 1 次 HTTP，错误原文 `The socket connection was closed unexpectedly. For more information, pass \`verbose: true\` in the second argument to fetch()`。来源的模型客户端使用另一条传输路径；本次新 SDK 适配引入。
- **建议改法**：在网络/流边界按错误类型和稳定错误码识别真实传输错误，不按错误文案；将响应体断线归为 `network`。保留正常 EOF 测试，另经真实断开的 TCP 响应核对 6 次上限和退避参数。

### 5. SDK 的 timeout 只管收到响应头，流一旦开始就没有超时

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/ingest/model.ts:97`、`:164`、`:207`；依赖 `openai/src/client.ts:809-814`。
- **现象**：`timeout:600_000` 被当成请求超时，但 SDK 在 fetch 返回 Response（收到响应头）后立即 `clearTimeout`；后面的 `for await` 没有计时器。服务发出一小段非空内容后不再发送，也不结束连接时，任务永远停在这一步，不重试。用真实 SDK 将同一 timeout 选项缩短为 50 ms，端点发 1 个 SSE chunk 后挂住，305 ms 时仍 `ended:false, chunks:1`；随后主动 abort 才结束。
- **为什么是问题**：输出 9 的超时恢复在流读取阶段不存在；跑飞检测也挡不住停止输出或慢到不产生 2000 个空白的连接。把 timeout 从 50 ms 改为产品里的 600000 ms 不改变其生命周期。实际产品请求没有独立的总时限或流空闲时限。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/model-cases.ts sdk-timeout`；真实本机 HTTP 与未改 SDK。额外读取 `/home/notnotype/CodeRepository/neuro-book/node_modules/openai/src/client.ts:781-815`，确认计时器确实只包住 fetch；未等待产品的 10 分钟阈值，产品永久等待结论来自同一 SDK 控制流。实验的 300 ms 是观察超时是否生效的截止时间，不是仓库测试的固定等待。
- **建议改法**：抽取传输层持有覆盖整个 SSE 消费过程的超时控制器，完成、失败、停止都清计时器；计时器触发须归 `network` 并进入同一重试预算。用真实 SSE 挂起端点验证，不只测响应头迟到。

### 6. SDK 在解析坏 SSE 时直接打印原始数据，绕过密钥遮盖

- **严重程度**：重要；**类别**：安全与性能。
- **位置**：`packages/nb-story/src/ingest/model.ts:160`、`:207`；依赖 `openai/src/core/streaming.ts:61-66`。
- **现象**：OpenAI SDK 的 SSE JSON 解析失败时，用 logger 直接输出原始 `sse.data` 和 `sse.raw`；本层的 `classify` 脱敏发生得更晚，只遮盖最后的 Error.message。端点在不合法 JSON 中回显假密钥 `FAKE_REVIEW_SECRET_012345` 后，标准错误出现 2 次完整假密钥：`Could not parse message into JSON: {bad FAKE_REVIEW_SECRET_012345` 与 `From chunk: [ "data: {bad FAKE_REVIEW_SECRET_012345" ]`。
- **为什么是问题**：违反 ingest 的“密钥不出现在输出与错误里”以及边界输入不打印原文的约定。401 回显密钥测试通过不能证明 SDK 自己的日志安全；渠道返回异常流或开启 SDK 日志时仍可把真实密钥写入 CLI/serve 日志。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/model-cases.ts sse-secret`，真实 SDK、HTTP、`callModel`，未开启 debug，也没替换 console；只用了可辨认的假密钥，没有读取真实密钥。最后抛出的 `ModelError` 本身不含密钥，但此前的原始日志已经泄露。本次新增 SDK 路径。
- **建议改法**：为 SDK 提供受控的脱敏 logger，所有级别的所有参数都按本次密钥清洗，或禁掉 SDK 原始日志、由传输层仅输出脱敏诊断。补坏 SSE 回显假密钥的真实子进程 stdout/stderr 检查。

### 7. 收到 finish 与 usage 后中止流，会把被中止请求记成完整成功

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/ingest/model.ts:229`、`:243-257`。
- **现象**：SDK 的 SSE 迭代器遇到 AbortError 会正常返回，不一定进入本层 catch。如果服务已发 `finish_reason:stop` 与 usage，但还没结束 HTTP 响应，此时用户停止，循环正常退出；`attemptOnce` 没有在循环后检查 signal，仍 `record(null)` 并返回成功。实测中止后返回 `ok:true, json:{ok:true}`，记账为 `error:null, complete:true, input:10`。
- **为什么是问题**：ingest 输出 13 明确中止请求的合计要标不完整；现有 stop 场景只中止尚未收到 finish 的请求，掩盖这条合法时序。外层任务的提交前 stop 检查可以阻止提交，但不能修正已经写入 usage.jsonl 的完整性标记。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/model-cases.ts abort-after-finish`。真实本机 SSE 发出 finish 与 usage 后保持连接；fetch 透传响应体，只观察该批字节已到达，在下一轮事件中 abort；真实 SDK 与模型调用未修改。依赖 `openai/src/core/streaming.ts:91-98` 确认 AbortError 被吞为正常迭代结束。来源未使用此 SDK，非原管线既有问题。
- **建议改法**：所有离开流迭代的路径统一检查外部停止信号；被停止时先 `usage.complete=false`、记录中止，再抛 `ModelAborted`，不要只依赖 catch。覆盖 finish 前和 finish 后、usage 前后的停止顺序。

### 8. 核对和修复的请求完全相同时，回放端点把修复当成重试

- **严重程度**：重要；**类别**：测试。
- **位置**：`packages/nb-story/testing/ingest-replay.ts:68-81`；`packages/nb-story/src/ingest/chapter.ts:143-175`。
- **现象**：端点靠同章上一次核对正文是否相同来区别渠道重试和 repair；真实管线里，清单只有结构问题、review 返回 `{}` 时，repair 的 system/user/effort 与 review 完全相同。实际 extractChapter 执行了 review、repair 两步，端点却记成 `review-1, review-1`，`unknown=[]`；准备好的 repair 回复从未使用，最后兜底丢掉 1 条说法。
- **为什么是问题**：计划审查的“请求识别补充”已经指出这个歧义，但实施仍采用该算法。它既会用错回复，又能在 unknown 为空的条件下报告成功；重启同一章还共享旧的 lastCheck 状态。现有十章录制没有 repair 请求，逐字对照通过也锁不住修复路径。
- **如何核实**：`bun --no-env-file /tmp/review-w00024-t06-impl/scratch/chapter-cases.ts replay`。真实 extractChapter、compile、SDK、HTTP 与 replay；第 1 章有一条缺 by 的 speech，说法触发结构清单，录制的 review=`{}`、repair=`{"remove":["s1-1"]}`。输出 `checkRequests:2, firstTwoSame:true, played:[review-1,review-1], unknown:[], dropped:1`。这不是伪造同文请求，而是实际单章流水线自然生成。
- **建议改法**：不要从正文相等推断逻辑调用身份。为传输适配器传入章、步骤、轮次与内容重试身份，用测试端点约定的请求元数据辨认，渠道重发保留同一身份；不改变生产提示词文字。补“review 不改草稿、紧接同文 repair”与“同章停止后重做”的回放验收。

### 9. 导入在竞争失败前已经对查询可见，改名后的互查不是原子占用

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/nb-story/src/core/library.ts:318`、`:327-329`；`packages/nb-story/src/ingest/store.ts:113`、`:120-126`。
- **现象**：导入先把目录改成正式书目录，之后才检查抽取是否占用同 id、决定是否撤回。真实导入与抽取争 id 的 15 次实验里，15 次均是抽取成功、导入报 `book_exists`，但撤回之前 `readMeta('shared')` 已成功返回失败导入的书名“已导入的数据”；导入失败后 `listBooks()` 又为空。
- **为什么是问题**：queries 的时序合同要求导入完成前对任何调用方不可见，导入失败不能发布书；ingest 输出 1 要求首章前书库里没有书。改名加互查虽然这次让至少一边退回，却先发布了注定失败的导入；此时被杀还会来不及撤回。[INFERENCE] 查询或问答能把这份最终未成功导入的数据固定下来，单靠之后撤回目录不能撤回已返回的结果。
- **如何核实**：恢复前已执行 `bun --no-env-file /tmp/review-w00024-t06-impl/scratch/id-race.ts`。真实 `Library.importBook`、`startIngest`、Worker、flock、文件系统与本机端点；看到 `.importing-*` 出现才开始同 id 抽取，看到正式目录出现便调用真实 `readMeta`。15 次输出均有 `imported.ok:false, started.ok:true, probe.visible:true, probe.title:已导入的数据, books:[], ingest:true`；实验根 `/tmp/review-w00024-t06-impl/scratch/id-race-1792478752463`。base 的导入在 rename 后不会再因另一条占用路径失败，这个发布后撤回窗口为本次新增。
- **建议改法**：导入、抽取占用和删除使用同一个可原子争夺的 id 凭据；核心保持 Node API 不等于只能在发布之后补检查，可由宿主注入共享协调门禁或设计共同的原子占用记录。正式书目录只能在所有可能的 id 冲突判定完成后发布，补竞争中查询与强杀的组合验收。

### 10. 进程被强杀时在途请求从账本消失，合计反而标成完整零用量

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/nb-story/src/ingest/model.ts:189`；`packages/nb-story/src/ingest/job.ts:147-157`；`packages/nb-story/src/ingest/status.ts:55-70`。
- **现象**：用量只在一次 HTTP 尝试结束回调时落盘。端点已经收到请求并开始 SSE、子进程此时被 `SIGKILL` 后，没有任何用量条目记录这次已发出的请求；进度正确识别 `stopped/exited`，却给 `thisRun` 与 `allRuns` 都报 `input:0, output:0, complete:true`。
- **为什么是问题**：ingest 输出 13 要求拿不到用量的中止、断流等尝试让对应合计标为不完整，不能当作精确的 0；强杀恢复也是明确支持的路径。旧的完整合计会掩盖这次已经可能计费的请求；续抽成功后仍没有证据把合计改回“不完整”。这与第 7 条的正常停止时序不同：本条是持久化协议根本没记在途请求。
- **如何核实**：恢复前已执行 `bun --no-env-file /tmp/review-w00024-t06-impl/scratch/progress.ts crash-usage`。真实 `testing/ingest-child.ts`、Worker、SDK 与 HTTP 端点，端点确认收到请求并发出 SSE 后才杀进程；没有手工构造状态或用量。结果 `stopReason:{kind:exited}, committed:0, thisRun.complete:true, allRuns.complete:true`，根 `/tmp/review-w00024-t06-impl/scratch/progress-crash-usage-1792478820400`。本次新抽取账本路径，非搬迁源既有查询回归。
- **建议改法**：按稳定请求身份记录“已开始但未结算”的尝试，结束时补用量；恢复时未结算尝试必须污染本次、历次与对应章的完整性。正常停止或失败也要等待用量写入收口，再发布任务结束、放锁。

### 11. 整理能把已提交历史变成错误图，当前门禁仍把这一章提交为成功

- **严重程度**：阻断；**类别**：正确性。
- **位置**：`packages/nb-story/src/ingest/chapter.ts:208`；`packages/nb-story/src/ingest/job.ts:104-118`。
- **现象**：整理的错误检查只收 `issue.chapter === 当前章`，而合并对象可能让旧章账本产生错误；job 最后两次 compile 又都直接丢掉 issues。真实抽取 5 章：第 1 章对象余额设为 10，第 2 章另一个同名对象增加 2、原文余额为 2，各自编译无错误；第 5 章整理合并两对象后，第 2 章的累加值变成 12，与记录的 2 冲突。任务仍返回 `done`、提交到 5，保存了该整理，章问题清单为空。
- **为什么是问题**：直接违反 ingest 输出 5“提交时整份数据没有错误”和输出 7“不合格整理跳过”。错误已经写进权威图，不是短暂的读取状态；下一章的本章过滤同样看不到这个旧章错误。这里报告的是本次承诺新增的全图门禁仍未落实，不把原编译器合并会重算账本这一既有语义当作迁移回归。

### 12. 续抽更换币种后把不同币种直接相加，并标成第一种币种

### 13. 进度的用时只累计 HTTP 时长，章平均又漏掉此前作废的整章尝试

### 15. 书 id 在拿锁之后才校验，拒绝非法输入前已能越界创建文件

- **严重程度**：重要；**类别**：安全与性能。
- **位置**：`packages/nb-story/src/ingest/runner.ts:59-66`；`packages/nb-story/src/ingest/store.ts:87-90`；`packages/nb-story/src/ingest/start.ts:35`。
- **现象**：`startIngest` 先把原始 id 拼进锁路径并 `openSync(...,"a")`，之后才走 `planFromText` 的 BOOK_ID 校验。输入 `../../escaped` 最后虽返回 `invalid_params`，但已经在指定书库的上一级创建 `escaped.lock`。从保存原文发起的路径也没有在锁前验证 id。
- **为什么是问题**：非法外部输入必须在文件系统副作用前拒绝；锁文件又按设计永不删除，拒绝请求会留下书库之外的永久文件。[INFERENCE] 按宿主写权限还可占用书库之外的同名 `.lock`，不能把“后面会报 invalid_params”当成路径边界防护。这里没有声称能覆盖任意文件内容，实测是越界创建空文件。
- **如何核实**：仓库根实际执行：`bun --no-env-file -e 'import {mkdir,stat} from "node:fs/promises";import {join} from "node:path";import {Library} from "./packages/nb-story/src/core/library.ts";import {startIngest} from "./packages/nb-story/src/ingest/runner.ts";const parent="/tmp/review-w00024-t06-impl/scratch/id-input-"+Date.now();const root=join(parent,"library");await mkdir(root,{recursive:true});const result=await startIngest({library:new Library(root),id:"../../escaped",title:"测试",text:"第一章\n正文。",endpoint:{baseUrl:"http://127.0.0.1:1/v1",model:"m",apiKeyEnv:"REVIEW_NON_EXISTING_KEY",maxTokens:100},price:null,runner:"serve"}).then(()=>({ok:true}),e=>({ok:false,code:e.code}));console.log(JSON.stringify({parent,result,outsideFile:(await stat(join(parent,"escaped.lock"))).isFile()}));'`。输出 `result.code:invalid_params, outsideFile:true`；文件只在指定 scratch 内。base 的 `importBook` 是先校验 id 才产生对应目录，新抽取入口顺序不同。
- **建议改法**：书 id 在任何锁、路径或状态访问之前统一验证，new/resume/append/status/remove 都消费已验证的 id；至少先修 startIngest 的入口顺序。补非法 id 被拒绝且书库及其父目录没有新增文件的黑盒场景。

### 16. 任务测试每次留下 9 个临时书库，失败路径也没有等子进程退出

- **严重程度**：建议；**类别**：测试。
- **位置**：`packages/nb-story/src/ingest/runner.test.ts:29-30`、`:43-49`、`:241`。

- **为什么是问题**：违反仓库“测试自身清理临时根、子进程失败时也收口”的约定。重复运行会持续积累原文与图文件；失败时发出 kill 不等于已经退出，不能把后续端点停止或全局 24 小时扫旧当作该用例的资源收口。

- **建议改法**：资源 owner 在 afterEach 中按“停止并等待全部 Runner/子进程、停止端点、最后删除 root”收口；某一项失败仍继续清理其余资源，最后汇总抛错。强杀子进程也必须 await exited。
