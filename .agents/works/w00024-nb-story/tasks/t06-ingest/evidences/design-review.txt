# w00024/t06-ingest 设计审查

### 1. 一问只固定“一代”，没有固定抽取进度，多次工具查询可以混用两份图

- **严重程度**：阻断；**类别**：合同。
- **位置**：`docs/specs/story/queries.md:157-160`；`docs/specs/story/qa.md:78,131,156`；`docs/specs/story/ingest.md:132`。
- **现象**：新合同只保证“一次查询”固定一代与抽取进度；问答仍只要求所有工具查同一代、一问固定开始时的一代。抽完新章不换代，因此一次问答先查人物第一页，再抽完一章，再续页或查人物卡，既可以依字面读新图并使游标失效，也可以继续读旧图，两种行为都符合现有文字。
- **为什么是问题**：一问是多次查询组成的事务，不是一次查询。较早位置的称呼、计数会随编译变化，混用图会改变 Agent 的证据与候选解析；仅记录 generation 和 P 也无法说明答案基于哪份图。保存问答记录不受抽取影响与固定问答快照是两件事。
- **如何核实**：已读 `packages/nb-story/src/core/api.ts:41-57` 与 `packages/nb-story/src/qa/engine.ts:104-117,178-191`：现实现通过 `openBook` 保留整份内存索引，一问实际共享这个索引；这是实现额外提供的保证，新 Spec 没把它扩展为“代号 + 抽取进度”的问答合同。这里只核实设计缺口，未运行抽取功能。
- **建议改法**：同步改 qa 输出 2、15 与时序合同：一问开始固定一代及抽取进度，全部工具、分页、原文校验与作答均用该快照；之后抽完新章不使这一问内的游标失效；新发起的独立查询仍按当前进度校验。问答记录保存开始时的进度，补“一问跨一次章提交仍用旧图，下一问用新图”的验收。

### 2. 第 1 章尚未提交的任务不属于“书”，发起判定会把已保存的任务当成新建

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/ingest.md:82-88,94,113,139-140`。
- **现象**：输出 1 只“按书 id 找书库里的书”，没有书就 `new`；输出 6 又规定第 1 章抽完前书不在书库里，仅有抽取记录。第一次请求失败或在第 1 章 Ctrl-C 后，再跑同一条命令，照输出 1 必须判 `new`，不是要求的接着抽。`--book` 也未规定怎样解析这个尚不存在的书。
- **为什么是问题**：首章前是合法且常见的停止状态，已经保存原文与花费。此时原文一致性检查、历史用量保留、跨 `book.import` 的 id 占用都没有合同：既可覆盖已有原文，也可让导入数据文件抢占同 id，之后旧任务再提交第 1 章。现有 `Library.resolveBookId/readMeta/removeBook` 都只认正式书目录，不会自然覆盖这个状态。
- **如何核实**：逐项对照上述 5 处文字；实现依据为 `packages/nb-story/src/core/library.ts:129-142,181-245`，`book.import` 以正式目录 rename 竞争 id，`book.remove` 先要求可读书元信息。未把未实现的 ingest 当成已运行代码。
- **建议改法**：把“书或尚未产出首章的抽取记录”作为同一 id 的占用主体；明确首章前停止后为 `resume`、原文仍需比对、用量仍累计，`--book`/status/remove 可按 id 访问它。明确它与 `book.import` 共享 id 排他合同，并补首章前停止、改文本、导入竞争与删除的组合场景。

### 3. 删除必须先停任务，但网页被禁止停止命令行任务，缺少跨进程删除的结果合同

- **严重程度**：阻断；**类别**：合同。
- **位置**：`docs/specs/story/ingest.md:88,99,113,133-135,171`。
- **现象**：CLI 进程 A 抽书，serve 进程 B 收到网页 `book.remove`。输出 12 要求 B 先让 A 停下再删除；时序末条却说网页只能停止 serve 里的任务，命令行任务用 Ctrl-C 停。没有说明删除是否属于停止权限的例外，也没有定义远端运行者无法响应、删除中又发起任务时应返回什么。
- **为什么是问题**：只持有“同书一个抽取任务”的锁并不足以保护删除。先检查任务、发停止、再删目录之间，另一进程可以接着抽；旧运行者也可在删除成功后完成第 N 章提交，甚至写到同 id 的新一代。现有书库删除只是 rename 整个目录后删除，没有任务停止或等待机制。不能用给 PID 发进程级信号代替任务停止：serve 可能同时抽几本书，杀进程会停止无关任务。
- **如何核实**：静态构造 A=CLI、B=serve 的合法调用顺序即可得到权限冲突；读 `packages/nb-story/src/core/library.ts:233-245`、`packages/nb-story/src/server/serve.ts:92-112`，现机制没有跨进程按书停止/确认通道。场景 7 只覆盖网页发起的任务，未覆盖这个合法状态。
- **建议改法**：明确删除是否允许跨 owner 请求停止，并给无法停止时的失败码/恢复方式；删除接纳后须阻止该 id 的新任务与旧任务提交，等运行者确认不再写入后才成功返回，旧任务不得写入重建的新一代。补 CLI 抽取时网页删除、CLI remove 删除 serve 任务、删除与章提交/续抽竞争，以及 serve 同时抽两本书只停目标书的验收。

### 4. 只保存“每章最终草稿”不足以恢复整理结果，重启会丢失主线或重新付费生成

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`docs/specs/story/ingest.md:92,139-140,165-166`。
- **现象**：持久化清单有原文、每章最终草稿、问题与用量、任务状态，没有整理稿。实际 v2 的整理稿是独立于章草稿的输入，包含 `merges`、`summaries`、`arcs`；仅凭章草稿重新编译无法恢复它。输出 4 还只把整理写成“对象摘要与主线”，漏掉会改变对象 id 与全部引用的去重合并。
- **为什么是问题**：抽完 6 章后追加到 8 章，必须保留已经产生的第 5、6 章整理结果。若恢复时丢掉它们，旧位置的主线/摘要消失，对象去重改变；若照实验入口从第 1 章补跑整理，会在同一代、同一抽取进度下换一份模型生成的数据，违反 queries 的纯函数与游标合同，并重复计费。历史章草稿还可能继续引用整理后保留的对象 id。
- **如何核实**：已读实验 `t29-v9-ingest/v2/run-v2.ts:125-129,142-158,163-167,248-253`：`draft.json` 与 `consolidation-NNN.json` 分开保存，恢复时显式读取后者，compile 接受四个输入（其中第四个是整理稿）。`t27-v9-schema-gold/compile.ts:320-365` 执行合并与全图重定向。无需真实模型即可核实输入缺失。
- **建议改法**：不增加原始请求/回复存储；明确保存程序检查后的最终整理稿（或与之等价、可确定性恢复的最终结果），包含批准保留的去重合并语义。已经提交的整理批次在续抽/追加时保留且不重生成；说明旧文件末章的整理仍保留，新末章另加一批。验收重启后追加前后旧批次、对象 id 与用量不变。

### 5. 场景 9 只抽一次却要求 360 分，单次满分只有 159，验收永远不通过

- **严重程度**：阻断；**类别**：验收。
- **位置**：`docs/specs/story/ingest.md:173,180`。
- **现象**：场景写“抽样例书前 20 章”一次，用 53 条尺子打分且总分不低于 360；引用的 384 是三次抽取合计分，不是一次的分数。
- **为什么是问题**：尺子每条“对/部分/缺/错”分别是 3/2/1/0 分。一次上限 `53 × 3 = 159`，三次才是 `477`；360 比单次满分多 201。照字面执行，无论抽取多好都失败。此外 Spec 没链接可执行尺子与固定样例原文：仅链接提案描述，脚本和 checklist 目前只存在未提交的 w00005 worktree 中，干净 checkout 无法按它验收。
- **如何核实**：已读 `t33-v9-extraction-v2/scripts/groups.ts:4-21` 的原始评分定义和累加式；`docs/proposals/novel-memory-v9.md:389-400` 表格标题也明确三次、满分 477。`check.ts:5,36-37` 依赖实验模型客户端和固定 dataset 文件形状；本次未运行任何模型判分。
- **建议改法**：明确三次独立抽取并合计至少 360/477；若确实只打算抽一次，另明确一次的归一化门槛，不能拿 384 直接比较。将 53 条 checklist、样例原文版本/段号、评分规则及入口纳入可版本化验收资产，固定判分模型与失败/重判规则；迁移入口可放计划，不把本机未提交产物当长期证据。

### 6. “较早位置可能变化”放过了称呼归属回填，新章可把未来代号泄露到前文

- **严重程度**：阻断；**类别**：正确性。
- **位置**：`docs/specs/story/queries.md:113,157`；`docs/specs/story/ingest.md:92,140`。
- **现象**：新合同允许新学到称呼后重算前文出现次数，但搬来的 compile 不只是改计数，还把称呼的可见位置从新章倒推到前文同名字串。前文的普通词与后文代号相同，就会提前暴露“这个词是该人物的称呼”。输出 1 的不剧透合同并未允许这个例外。
- **为什么是问题**：字串在前文出现，不等于读者当时知道它属于这个对象。按模型正确写下的 `name.at` 过滤原本可以防剧透；compile 提前改了这个位置后，核心查询无法再恢复揭示时点。允许计数变化不能隐式允许称呼、身份归属变化。
- **如何核实**：已运行 `bun /tmp/review-w00024-t06-design/scratch/contracts.ts`，调用真实实验 compile，再经现有 `Library.importBook` 与 `StoryApi.call('entity.card')` 查询，未调用模型。第 1 章是“林晚独自赶路。”“北斗星在天边闪烁。”；第 2 章才有“林晚的秘密代号是北斗星。”，新称呼草稿正确标 `2.2`。两份编译结果均为 0 个 error，但 compile 把新称呼改为 `1.3`；P=第 1 章的人物卡从仅“林晚”变成“林晚、北斗星”。依据为 `t27-v9-schema-gold/compile.ts:378-389`、`packages/nb-story/src/core/projection.ts:67-70`。
- **建议改法**：区分“字串首次出现”与“该称呼对该对象成立”的时点；后者不得仅凭整书字串匹配倒推。明确较早结果允许变化的范围仍受输出 1 约束，保留模型给出的归属揭示位置，或提供等价的可见性依据；增加上述同名字串/新代号的真实编译加查询验收。

### 7. “原子替换数据文件”没有覆盖元信息与续抽记录的共同提交，不能继承现有 pinBook 保证

- **严重程度**：重要；**类别**：不变量。
- **位置**：`docs/specs/story/ingest.md:94,99,131,139-140`；`docs/specs/story/queries.md:158,167`。
- **现象**：Spec 指定每章原子替换书里的数据文件，同时要求章数、extractedThrough、最终草稿、任务进度增长，却没规定这些持久化事实在进程被杀后的共同提交边界。现有元信息与图分为 `book.json` 和 `graph.json`，pinBook 的 inode 检查原本依赖“目录从不原地改写”；只对数据文件做 atomic rename 不会把这两个文件变成一个快照。
- **为什么是问题**：数据先改时可读到旧章数+新图，元信息先改则读到新章数+旧图；任一窗口被杀会把暂态永久留下。最终草稿先落盘、查询图未落盘时，接着抽还可能越过未发布章；反过来则可能重抽已发布章。同代更新还使当前仅按 generation 缓存的索引永久命中旧图。查询“不能看到一半”的总要求是对的，但指定的文件级做法没有说明章提交失败后哪些事实算已完成，实施不能直接复用当前保证。
- **如何核实**：已运行 `/tmp/review-w00024-t06-design/scratch/contracts.ts` 的真实文件系统实验：以现有书库导入 1 章，按 Spec 所述 rename 新 graph，真实 `pinBook` 返回 `metaChapters:1, graphChapters:2`；再更新 meta，`books.list` 返回 2 章，但同进程 `book.info` 仍返回缓存的 1 章。代码依据：`library.ts:12-19,145-178`、`book-index.ts:224-239`。这是对指定更新做法的反例，不声称 planned ingest 已有实现。
- **建议改法**：把黑盒合同写完整：章数据、查询所用元信息、恢复所需最终结果、extractedThrough 必须属于同一提交点；任意写入阶段被杀后，查询与续抽共同恢复到提交前或提交后，绝不能分歧。跨进程新查询必须刷新到当前进度，已有快照继续可读。删去“每章全量编译/替换哪个文件”的实现约束，具体快照布局和发布机制放 plan；验收覆盖提交窗口强杀与预热缓存后的更新。

### 8. 可选抽取模型必须整节完整，现有逐字段 set 无法从无到有创建它

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/qa.md:134-139`；`docs/specs/story/ingest.md:67-75`。
- **现象**：qa 输出 23 仅新增 `ingest.model.*` 点路径；输出 20 仍要求每次写之前整份配置合法。`ingest.model` 一旦存在，就必须同时有 baseUrl、id、apiKeyEnv。缺省没有该节时，第一次 set 无论写哪个字段，都会缺另外两个必填字段而被拒绝；`config init` 又没有抽取模型选项。反向删除只写“整节可以去掉”，也没给可接受的 unset 字段名。
- **为什么是问题**：承诺由 `nbstory config` 维护的可选配置，实际上只能手工编辑 JSON，照字段规则无法走通创建流程。不能靠允许中间写入无效配置补救，否则破坏输出 20 的原子校验规则。
- **如何核实**：已读 `packages/nb-story/src/qa/config-edit.ts:24-35,89-105`，现有 model.price 已因同样的整组约束要求整组 JSON 写入；`qa/config.ts:16-39,84-104` 每次整份校验再写。新 Spec 没有批量写三字段或整节写入的公开入口。
- **建议改法**：明确一个原子创建/替换整节的入口，例如 `config set ingest.model '<完整 JSON>'`，同时明确 `config unset ingest.model`，其余点路径只编辑已存在且完整的节；也可给 init 增加等价一次填全的流程。补“默认只有 model → 新建 ingest.model → 改字段 → 整节删除并回退”的验收。类型示例用不含 thinking 的形状，避免 `QaConfig['model']` 与正文禁止 thinking 相互矛盾。

### 9. 切章规则只有前缀没有词边界，“第三回合开始了”会被当成新章

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/ingest.md:59-63,170`。
- **现象**：按当前字面规则，9 字的“第三回合开始了”不超过 40 字、不以列出的句末标点结尾、以“第三回”开头，三个条件全满足；“序言里提到的那个人”也符合“序言开头”。场景 6 只用“长句”验证第三回合，如果长于 40 字或有句末标点，自然不会暴露这个误切。数字之间能否有空格、全角数字是否属于“阿拉伯数字”也没有可判定定义。
- **为什么是问题**：误切会改变后面所有章号和出处。用户抽完才发现再去修，逐章比对会判 `ingest_text_changed`，只能重建；不是无害的预览显示差异。40 字上限和句末排除已经确定，不需要重议，缺的是它们覆盖不到的词法边界。
- **如何核实**：对照输出前置条件逐项代入上述短句即可，未把自写正则当成产品实现。另比较 `第1章`、`第 1 章`、`第１章`、连续两个同名标题、仅有标题无正文：目前后两者依输出 62 应分别成为独立章和一段章，而空格与全角数字可被两个实现做出不同结果。卷标题被丢弃时，输出字段 droppedChars 定义只数首章前文字，和第 61 行要求统计中途卷标题也不一致。
- **建议改法**：在已定识别规则上明确标题标记后的边界及特例，给接受/拒绝的短字符串表；固定空白、全角数字与“字数”的计算口径。补 40/41 字、短“第三回合”、句末引号、空章、重复标题的切章结果；droppedChars 改成全部被丢弃字符数，或分别报告首章前文字与卷标题，避免同字段两种含义。
- **数字与引用校正**：上文“第三回合开始了”是 7 字，不是 9 字；“输出 62”应为 `ingest.md:62` 的切章规则行。两处校正不改变误切与空章/重名章的判断。

### 10. “沿用导入检查即可每章无错误”不成立，现管线漏掉 chapter=null 的全图错误

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/ingest.md:92-93,159,169,173`。
- **现象**：输出 5 把导入用的检查描述为“没有结构错误，引用都存在，出处在本章”；现有导入只做 TypeBox 形状校验，并不校验引用与时间关系。v2 的修复入口又仅处理 `issue.chapter === 当前章`，而编译器会产生 `chapter:null` 的全图错误，所以不能照搬后宣称“每章都能用、没有结构错误”。
- **为什么是问题**：这不是设想中的异常输入：现有 100 章回放产物就有 1 个全图时间环错误，逐章修复没看到它。形状完全合法并不代表引用/故事时间一致。只写“修不好丢弃记录”也没规定没有章归属的错误怎样归因，无法保证丢掉哪条才能恢复已提交历史的有效性。
- **如何核实**：已运行 `bun /tmp/review-w00024-t06-design/scratch/compile-recorded.ts`：回放最终草稿和整理稿，20、50、100 章均有 1 个 error；录制 `run-med-100/issues.json` 的 error 是 `chapter:null, code:'time'`（时间点先后自相矛盾）。读 `run-v2.ts:216-220,248-252` 可见按章过滤；`packages/nb-story/src/core/dataset.ts:258-265` 只校验形状。未调用模型。
- **建议改法**：独立定义提交前必须满足的全图语义不变量，不把“导入校验”当成现成的全部能力；明确跨章引用、全图时间环等错误要能归因到本章新增内容并处理，无法安全修复时本章失败、旧快照保留。回放验收同时断言全图 error 为 0，不能只数当前章 error。

### 11. 每章全量重编译是写进 Spec 的实现约束，照搬到 serve 会连续阻塞事件循环 11 秒

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/ingest.md:99,131,140`；`docs/specs/story/viewer.md:63`。
- **现象**：第 140 行强制“由全部抽完的章重新编译”，但实际 compile 是一个同步调用。网页任务又在 serve 进程里运行；同一线程上照搬时，编译期间查询、进度、停止请求都不能处理。Spec 没规定编译/发布阶段的响应与取消边界，验收只停在模型请求期间。
- **为什么是问题**：本次实测 20/50/100 章一次 compile 分别为 317/1900/11038 ms，100 章已经超过查看器首屏 1 秒的合同 10 倍以上；模型再慢也不能抵消网页会在章提交阶段卡住的事实。这不是要求本次解决长书模型费用，而是同进程抽取不能阻塞正在读书和停止任务。全量编译还是内部算法：改成增量编译且外部结果不变时不应迫使修改 Spec。
- **如何核实**：命令 `bun /tmp/review-w00024-t06-design/scratch/compile-recorded.ts`，只读 run-med-100 的最终草稿、原文与整理稿，真实调用编译器，无网络、无 serve；测量是当前机器单次耗时，不作为跨机器性能上限。`compile.ts:51-446` 无 await，`run-v2.ts:127-129` 直接同步调用。未实测 100 章以上，不外推具体耗时。
- **建议改法**：Spec 只要求新进度与从已提交最终结果确定性编译得到的数据等价，删除固定全量算法；补抽取的编译/发布期间 serve 查询、进度与 stop 仍有界响应的合同及组合验收。是否用 worker、如何增量化放 plan，保留“任务属于 serve 生命周期”的已定决定。

### 12. config test --ingest 沿用问答探测语义时不带固定推理档，会把不能抽取的配置报为通过

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/qa.md:137,139`；`docs/specs/story/ingest.md:67-75,95`。
- **现象**：qa 输出 21 规定 test 只在配置写了 thinking 时发推理档，输出 23 只增加“--ingest 检查抽取模型”。但抽取节不允许 thinking，真正抽取必须发 minimal 与 medium。按输出 21 实现的 --ingest 只能测不带档位的一次请求：端点支持普通请求、拒绝 minimal 时探测仍通过，开始抽取马上 400。
- **为什么是问题**：允许任意 OpenAI 兼容模型与只验证 luna 质量是已定取舍，但协议可用性不是抽取质量。固定档位不能悄悄降低或不发。现有模型配置只有 reasoning 布尔值，没有“支持 minimal”的能力保证；继承问答 model 时尤其无法从配置判断。Spec 也未规定 --ingest 在不存在独立抽取节时如何显示实际回退模型与两档探测结果。
- **如何核实**：已读 `packages/nb-story/src/qa/config.ts:111-128`、`packages/nb-story/src/cli/config.ts:159-175` 及 `packages/nb-harness/src/model.ts:32-46`，现探测沿问答配置的 thinking；实验 `luna.ts:79-81` 直接发送 reasoning_effort。此处是输入协议与探测合同冲突，未调用非 luna 服务，未宣称哪个真实服务已拒绝。
- **建议改法**：为 --ingest 明确覆盖 qa 输出 21：解析同抽取一样的模型回退规则，用抽取真正要求的 minimal/medium 请求路径探测，分别报告通过/失败；不支持固定档位时以 model_failed/provider 给出明确说明，不静默降档。补本机端点“普通请求接受、minimal 返回 400”的确定性验收；固定档位决定不变。

### 13. “出处都在这一章内”删除了 V9 明确允许的后建秘密回补旧章知情

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/ingest.md:92-93,141`。
- **现象**：Spec 一律要求一章的出处都在本章，且模型请求只含当前章原文。V9 现行规则明确有例外：后面才建的秘密，可以给前面章节已经知情的人补记，引用当时的原文。编译器也专门对 knowledge 关闭 sameChapter 检查。
- **为什么是问题**：照 Spec 加统一“本章出处”检查会把管线原本合法的记录丢弃，属于悄悄改变已接受的 V9 语义。反过来只照搬编译器接受旧章出处，又不满足本 Spec 的每章检查与请求材料限定。早期知情是否能回补会改变秘密矩阵和按位置问答，不是内部实现差别。
- **如何核实**：已读实验 `t27-v9-schema-gold/rules.md:172-180`、`compile.ts:92-105,264-270`（knowledge 调用 `spansOf(..., false)`）；普通记录仍要求本章出处。这是明确的参照合同差异，不是依名字猜功能。未增加或执行真实模型请求。
- **建议改法**：明确保留该例外及它的依据材料如何获得、何时可见，或把取消该例外作为显式产品差异提交决定，不能声称无差别照搬。若保留，需保证新秘密不可见时旧位置的引用也不可见，并增加“新章建秘密、补旧章知情”的确定性编译与查询场景。

### 14. HTTP 成功但回复无法构成一章时，没有定义失败、重试与丢弃的边界

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/ingest.md:92-95,148-153,159,169`。
- **现象**：只定义渠道错误重试和“坏记录丢弃、不让章失败”。没有覆盖合法 HTTP 200 下的坏 JSON、输出截断、缺少当前 chapter、缺失全部 beats、整理稿整体不合格。它们并非一条可定位的坏记录，不能一律通过丢弃记录保证合法章。引用的 v2 实际对这些情况采取不同结果：解析/截断直接抛错，缺章抛错，坏整理稿则跳过。
- **为什么是问题**：照字面实现可以把缺失记录的章当作成功，也可以报未列出的内部错误，或不断修复；退出码、status、旧进度、是否下次从本章重做都不确定。场景 5 只放 1 条坏记录，证明不了整个外部回复不合格的行为。此外 Spec 写“只输出空白”才重试，实验真实故障是先输出一段坏 JSON 再连续空白；若只在结束后判断整份回复为空白，会丢失管线已有的跑飞掐断能力。
- **如何核实**：已读 `run-v2.ts:85-99,132-139,142-155`、`draft-tools.ts:60-67,97-108`；草稿结构 `schema.ts:204-208` 要求至少一个 beat，编译 `compile.ts:169-181` 要求连续覆盖全章。实验 `luna.ts:67-72,98-110` 对连续 2000 个尾随空白提前中止，而不要求整个回复都是空白。这些均是生产可遇到的模型输出，不需要发真实请求即可确认合同未覆盖。
- **建议改法**：区分可修复/可丢弃的单条记录与无法形成合法章的整体回复；后者定义明确失败码/kind、退出 4、保持旧进度并可重做本章，不将无图章默认为成功。明确整理稿失败是否阻断这一章及其计数。保留已定 5 次渠道重试，不擅自扩大到内容错误；将尾随空白跑飞作为已定“空白跑飞”的准确边界，补坏 JSON、截断、无 beats、坏整理稿和部分内容后持续空白的回放场景。

### 15. 停止和重试必然产生未知用量，进度却没有“下界/不完整”的表达

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/ingest.md:95,99,103-108,139`。
- **现象**：进度要求本次、历次合计与每章费用/token 数，却没有未知或不完整的标记，也没说明失败重试和被丢弃的半章已花的用量是否累计。流中断、用户中止、空白跑飞都可能已计费，但拿不到结尾 usage；“未配置价格费用为空”不是这种未知。
- **为什么是问题**：按实验客户端默认值实现会把缺失 usage 记成 0，于是失败多、停得多的任务显示的费用反而偏低；一章作废也不能意味着付出的模型用量作废。harness 与现有问答已经明确这类数值只是下界，新增抽取进度退回无标记精确数值会误导用户。这不要求估总价或新增费用控制。
- **如何核实**：`docs/specs/agent/harness.md:129` 明确取消/察觉 provider 重试时 complete=false；`docs/specs/story/qa.md:121` 也要求标不完整。实验 `luna.ts:67-72,109-110` 说明中断时没有 usage；`run-v2.ts:79-84,103` 用缺失字段的 0 计算费用，不能作为产品报告的精确账单。
- **建议改法**：复用现有 usage.complete/下界语义，失败尝试、半章与重做的已知用量均累计到本次及历次；任何未知尝试污染相应汇总的完整性，未知不算 0。明确平均值分母及“章成本”是否包含该章历次失败尝试，记录每次已知单价对应币种，避免改配置后重算历史费用。用回放中途断流后成功、停止再续抽验证汇总与不完整标记。

- 同一代不变、查询和分页绑定抽取进度，是可以实现的合同；不是非得把每章改成新一代。问题在快照、缓存、问答和恢复要一起迁移，而非这项产品决定本身不可行。
- “同书同时至多一个任务、两个同时发起恰有一个开始”已有可判定的黑盒要求。现有 serve 的互斥靠 `flock`（`server/registry.ts:1-7,43-67`），进程退出即释放，不需要把 PID 存活检查算法写进 Spec。实现须以持有者实例/锁的实际所有权判旧，不能只靠可复用的 PID；旧状态回收不得覆盖随后新 owner 的 running 状态。
- 回放端点可用：录制 response 包含 content、finishReason、usage，测试端点可包装成 OpenAI 兼容响应。请求文本不是稳定公共合同，不应逐字匹配旧 request；按章/步骤的语义匹配回放，并在遇到未知请求时立即失败，不能仅按第 N 次请求顺序发回复。真实网络端点仍可门控“某次模型请求正在进行”，用于 Ctrl-C、跨进程排他等组合场景。
- 场景 3 的原子性可以用真实文件系统、真实查询入口测试，但要在实现计划里提供可控的发布边界，保证查询实际跨过一次提交，并分别观察提交前、已开始的旧查询、提交后的新查询。只启动一堆并发 Promise 然后接受它们全为旧值，不足以证明“写入期间”。Spec 不必指定测试钩子；第 7 条已要求补对应可观察判据。
- 场景 5 注入时钟可行，符合仓库测试规范；时钟推进应替换等待，不替换真实 HTTP、文件系统或运行状态。退避合计 `30+60+120+180+300=690` 秒，无需让测试真实等 11 分 30 秒。CLI 退出码仍需经真实进程/真实命令路径观察；不是改写全局假计时器。
