# t22 实现审查

## 1. 重要｜正确性｜`packages/nb-harness/src/finish-watch.ts:29-36`

**现象**：结束原因探针只读取 `choices[0].finish_reason`，但把任意非空字符串（包括字面量 `"null"`）当成有效结束原因；同时忽略 `choices: []` 块上的顶层 `finish_reason`。因此两类 OpenAI 兼容网关形状会错判：`choices: [{finish_reason: null}]` 后跟带 `usage`、`choices: []`、顶层 `finish_reason: "stop"` 的正常末块仍被记为 `missing`，而 `finish_reason: "null"` 的无结束原因块会被当作已正常结束。

**为什么是问题**：前一种会把正常完成改报 `length`，问答记录写成 `truncated: true`，`config test` 报 `not_finished`；后一种让半截回复继续按正常 `stop`，正好绕过 #258 要补的截断保护。实现的注释与 Spec 都要求“非空的结束原因”代表完整结束，但字面量 `"null"` 不是合法的完成原因。

**如何核实**：在审查 worktree 执行：

```sh
bun -e 'import {createFinishWatch} from "./packages/nb-harness/src/finish-watch.ts"; const w=createFinishWatch(); w.observe({data:JSON.stringify({choices:[{finish_reason:null}]})}); w.observe({data:JSON.stringify({choices:[],usage:{completion_tokens:3},finish_reason:"stop"})}); w.observe({data:"[DONE]"}); console.log(JSON.stringify({missing:w.missing}))'
```

输出 `{"missing":true}`。把第二个块改为 `choices:[{finish_reason:"null"}]`，输出 `{"missing":false}`。两种结果均由真实探针直接得到，未调用模型。

**建议改法**：按协议形状同时检查所有可出现结束原因的位置（至少 `choices` 中的 choice 与约定的 usage-only 末块）；只接受已知的有效原因，明确把 `null`、空串与字面量 `"null"` 视为缺失。补上“usage-only 末块带结束原因”和“字面量 null”两条 provider 行为测试。

## 2. 重要｜正确性｜`packages/nb-story/src/ingest/model.ts:144-149, 279-285, 386-389`

**现象**：`supportedEfforts()` 只要求错误正文同时出现 `Supported values` 与 `Unsupported value`/`not supported`/`reasoning_effort`，没有确认被拒绝的参数就是 `reasoning_effort`。因此其它参数的 400 也会触发降档。例如正文 `Unsupported value: 'temperature'. Supported values are: 'none', 'low', 'medium'.` 会被解析成推理档列表，`minimal` 被改成 `low` 并重发。

**为什么是问题**：会把无关的参数错误静默改写成另一条请求，改变错误归类与请求内容；如果实际错误是 temperature、工具参数或其它字段，重发仍会失败或成功但语义已经改变。合同只允许“网关不接受固定推理档”时降档，不能按错误文案里碰巧出现的单词分支。

**如何核实**：在审查 worktree 执行 `/tmp/review-t22-impl/regex.ts`（本机 HTTP 端点，第一请求返回上面的 temperature 400，第二请求才成功），输出：

```text
{"count":2,"efforts":["minimal","low"],"text":"{\"ok\":true}"}
```

**建议改法**：按结构化错误字段或至少按错误正文明确指向 `reasoning_effort` 的语法解析；无法确认参数就是推理档时保持原 400，不重发。新增一个无关参数 400 的行为测试，要求只收到 1 次请求且错误保持 `provider`。

## 3. 重要｜正确性 / 不变量｜`packages/nb-story/src/ingest/model.ts:270-286`

**现象**：降档分支没有“一次性”标记。第一次 400 后改为另一个档位并 `continue`，第二次请求若仍返回一个把当前档位排除在外的合法列表，又会再次改档；网关可以让这条逻辑请求在几个档位之间无限循环。`maxAttempts` 只限制渠道重试，不限制这条降档链。

**为什么是问题**：Spec 要求“改发一次”，而实现可能不返回、不进入失败路径，也不受 `config test --ingest` 的 `maxAttempts: 1` 保护。真实的严格网关若对同一模型返回不稳定或逐档拒绝，会让 `ingest` 永远占住任务与锁，停止之前没有最终错误。

**如何核实**：在审查 worktree 执行 `/tmp/review-t22-impl/loop.ts`。本机端点对 `minimal` 返回合法列表 `low`，对 `low` 返回合法列表 `minimal`，调用带 `maxAttempts: 1`，50 毫秒后由 `AbortSignal` 收口；输出：

```text
{"requests":213,"aborted":true,"name":"ModelAborted"}
```

请求数远大于规定的第一次请求加一次降档重发，证明循环不受 `maxAttempts` 限制。

**建议改法**：为一次逻辑调用单独记录 `effortFallbackUsed` 或剩余一次降档机会；成功或失败都最多做一次 400 降档。若第二次仍是 provider 400，按原错误收口并保留网关正文，不再次解析为下一档。缓存应只记成功可用的映射，不能让缓存绕过这条调用级上限。

## 4. 重要｜正确性｜`packages/nb-story/src/cli/program.ts:158-164`

**现象**：动作级帮助用 `tokens.slice(1).find(isConfigAction)` 扫描所有 token，而不是读取 `config` 后实际的第一个位置参数。选项值会被当成动作：`config --config init --help`（配置文件路径就是 `init`）输出 `config init` 的帮助；同样 `config --model init --help` 会把模型名 `init` 当成动作。

**为什么是问题**：`--help` 只应描述用户实际选中的动作；这里会在没有动作时误报专属选项，且把合法的选项值误当成位置参数，破坏动作帮助与配置路径/模型名的组合。该路径在 commander 和 `configCommand` 之前直接返回，后续参数个数校验也无法纠正。

**如何核实**：在审查 worktree 执行：

```sh
NODE_PATH=/home/notnotype/CodeRepository/neuro-book/node_modules bun -e 'const {parseCommandLine}=await import("/tmp/t22-review-wt/packages/nb-story/src/cli/program.ts"); const out=[]; const result=parseCommandLine(["config","--config","init","--help"],{stdout:s=>out.push(s),stderr:()=>{}}); console.log(JSON.stringify({result,usage:out[0]?.split("\\n")[0]}));'
```

输出 `{"result":{"exit":0},"usage":"用法：nbstory config init [选项]"}`，但输入没有 `init` 动作。

**建议改法**：先用同一套位置参数规则解析 `config` 后的第一个非选项 token，跳过已知选项及其值；仅当该 token 本身是 `init/show/set/unset/test` 时走动作帮助，否则保留总览或交给正常用法错误处理。补上 `--config init`、`--model init` 等值等于动作名的行为测试。

## 5. 重要｜正确性｜`packages/nb-story/src/cli/config.ts:242-260`

**现象**：未知服务商的判断只在 `missing.length > 0` 时进入专门报错。已有 `custom` 配置时，`legacy` 的地址和密钥变量会把 `missing` 补空，于是 `config init --model my-relay/some-model --force` 被当成“沿用已有自定义地址”而成功写入 `custom/my-relay/some-model`，没有按合同报“内置目录里没有服务商”。

**为什么是问题**：#256/Spec 的条件是：`--model x/y` 的服务商不在内置目录，且本次没有 `--base-url`、`--api-key-env`，就是用法错误；不能因为磁盘上恰好有旧自定义地址就把另一个服务商名静默改成 `custom` 下的模型名。这会把用户原本想引用的服务商路由到旧网关，模型引用和请求目标都变了。

**如何核实**：在审查 worktree 执行下面的本机配置实验：已有 `custom` 地址后，不给地址和密钥变量运行 `config init --model my-relay/some-model --force`，结果为退出码 `0`，文件新增 `custom/my-relay/some-model`，输出没有未知服务商错误：

```text
{"code":0,"file":{"providers":{"custom":{"models":[{"id":"old"},{"id":"my-relay/some-model"}]}},"models":["custom/old","custom/my-relay/some-model"],"model":{"use":"custom/my-relay/some-model"}}}
```

**建议改法**：未知服务商条件独立于 `legacy` 补全逻辑：只要 `--model` 含服务商前缀、该前缀不在目录，且本次没有同时给 `--base-url` 与 `--api-key-env`，直接报用法错误；若要沿用已有自定义地址，文档明确只接受不带服务商前缀的模型名。补上“已有 custom 后仍拒绝未知 `x/y`”测试。

## 6. 建议｜测试｜`packages/nb-harness/tests/provider.test.ts:197-210`

**现象**：新增 provider 测试只覆盖单次无工具请求的两种 Chat Completions 结束块。没有真实 provider 测试覆盖“第一次工具调用后继续请求、最后一次请求决定最终文字”的场景，也没有 Responses、Anthropic 或 Google 流形状的回归用例。

**为什么是问题**：本次接入的状态字段就是“每次请求新建观察、`run.lastFinish` 记最后一次”；单轮测试不能阻止把观察器误留在第一次请求，或把工具调用的 `toolUse` 错改成 `length`。Spec 又明确无 `choices` 的 API 不受影响；当前测试不能对这条判据做变异检查，删掉 `run.lastFinish = watch`、在请求间复用观察器等回归可能仍通过。

**如何核实**：阅读 `provider.test.ts` 可见新增用例只有 `harness.turn` 一次，`complete` 两次均为无工具；搜索 `packages/nb-harness/tests`，除目录模型字段断言外没有实际 `openai-responses`、`anthropic-messages` 或 `google-generative-ai` 的 provider 流测试。当前审查环境依赖未安装，无法把整包测试跑到该断言处；缺口由测试文件静态核对确认。

**建议改法**：用真实本机 SSE 端点增加一条带工具的两轮 Chat Completions 场景，第一轮 `tool_calls`、第二轮分别覆盖正常结束与缺结束原因；再至少用真实 Responses 流确认 `response.completed` 不被标成缺失。测试结果断言最终 `stopReason` 与文字，不断言观察器内部状态。

## 7. 建议｜正确性 / 兼容｜`packages/nb-story/src/cli/program.ts:152-156`

**现象**：版本处理只检查 `argv[0]`。因此合同示例的 `nbstory --version --json` 可用，但同一组根选项换成常见的 `nbstory --json --version` 或 `nbstory --json -V` 会被当成命令名，退出码 2。

**为什么是问题**：命令行其余根选项通过 commander 支持写在命令名前后；`--json` 是版本输出的修饰选项，交换顺序不应改变结果。当前预解析绕过了 commander 的选项归一化，造成版本接口的顺序不一致。

**如何核实**：在审查 worktree 运行 `parseCommandLine(["--json", "--version"], io)` 或 `parseCommandLine(["--json", "-V"], io)`，两者均得到退出码 `2` 与“没有命令 --version/-V”；`["--version", "--json"]` 和 `["-V", "--json"]` 才得到退出码 `0`。

**建议改法**：在版本判断前先从根级 token 中提取 `--version`/`-V` 与 `--json`，只对根级选项做顺序无关的识别，并对多余命令/选项仍走用法错误。补上两种顺序的 JSON 输出测试。

## 未发现问题的方面

- `finish-watch` 只把包含 `choices` 的块纳入 Chat Completions 判断；按已安装 pi-ai 的 Anthropic、Responses 与 Google provider 实现，正常事件没有该字段，直接观察时 `missing` 为 `false`。
- `harness.ts` 当前代码确实在每次 `streamFn` 调用时新建观察器并把它写入 `run.lastFinish`；`toolUse` 分支仍不改为 `length`，没有确认到这两条实现本身的回归。
- `nearestEffort` 的 `minimal -> low`、`xhigh -> max/high`、`max -> xhigh`、距离相同取更高档，以及排除 `none`，与已安装 pi-ai 的 OMP 规则逐项对照未发现差异；本报告列出的是错误识别、重复降档与缓存收口问题。
- 自定义模型缺省 `maxTokens` 为 32768、磁盘 schema 仍接受大于 64000 的旧值，且 OpenAI 系请求的 64000 夹限由 pi-ai 发请求边界处理；代码与计划一致。
- `packageVersion()` 的相对路径指向 `packages/nb-story/package.json`，发布 `files` 列表也包含 `src`，npm 包的 package.json 按发布规则保留；未发现该路径本身的问题。
- `config set ingest.model` 三段式保留已有字段、`ingest.recall.model` 的读取路径和 `config test --ingest` 的实际档位输出，静态对照未发现另一个已确认的正确性缺陷。
