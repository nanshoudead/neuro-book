### 1. 身份秘密不是完整的身份等价表，照此合并既通不过指定验收，也会拆散主要人物

- **严重程度**：阻断；**类别**：正确性。
- **位置**：`docs/specs/story/queries.md:92-98,167-168`；`docs/specs/story/viewer.md:121,125`。
- **现象**：输出 3 的“当且仅当身份秘密已经揭晓”与真实数据不相容：
  1. `x6-1`、`s6-25` 已在 **6.96** 把 `e1-1`（苏天晴）与 `e6-2`（视频中的狐狐）明确连成同一人。第 7 章按正文就应合并，不能满足验收 2“第 7 章两个点、第 8 章起一个点”。而“心月狐”这个称呼在 `e1-1.names` 的可见位置是 **8.48**，不能把“第 7 章已有心月狐这个点”作为判据。
  2. 南嘉鱼相关的四个对象是 `e8-2`（猫女兽人）、`e10-1`（无称呼的反派身份）、`e30-1`（深蓝倩影）、`e33-1`（地狱猫）。`x10-1.about` 连前两个；`x30-1.about` 连 `e30-1/e10-1`，但最初依据 `s30-13` 在 **30.61** 只是 `certainty=candidate`；后来确定的 `s37-1` 在 **37.8** 连的是另一对 **`e33-1/e8-2`**。secret 的 `about` 不等于每条身份说法的端点；“秘密揭晓”也不是一个现成的布尔字段。
  3. `e30-1/e33-1` 的直接联系 `s33-17` 是角色台词 `kind=claim`，没有 secret；`e5-1`（苏天晴考虑的新代号）没有名字，也没有把它并回本人的身份秘密。数据里的三次 `mergedFrom` 只涉及 `e1-3/e3-1/e6-1`，不是这些主要人物的马甲补全表。
- **为什么是问题**：按 secret.about 合并会提前确认候选身份、仍漏掉地狱猫；按已确认 statement.about 合并又不满足“当且仅当有身份秘密”。即便后者修好，深蓝倩影和无名身份如何处置仍无合同。实现者要么写特例，要么悄悄改变合并规则与验收。
- **如何核实**：运行上面的脚本，查看“身份相关对象”“身份秘密”“相关身份说法”“实体去重残留”。苏天晴对 `x30-1` 在第 38 章的最新记录确为 `k38-3=unaware`，南嘉鱼对风信子秘密在该位置确实没有记录；这两个状态事实成立，但不足以补出整个身份等价关系。
- **建议改法**：明确身份判断使用的结构化证据、确定性、否定/反驳、secret 与 statement 端点的关系；区分“同一马甲换代号”“马甲与本人”“抽取时建重去重”。列出第一版数据可支持与无法支持的合并，无法从数据确定的保留分点且不冒充同一人。验收改为由实际记录位置驱动：苏天晴/视频狐狐在 6.96 合并，心月狐称呼另在 8.48 出现；不要用第 7/8 章的错误前提锁定实现。

### 2. “所有计数只按可见记录算”与抽取来源统计冲突，现有数据无法还原后者的历史值

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/queries.md:55,90,139`；`docs/specs/story/viewer.md:61`。
- **现象**：`book.stats` 和说明页承诺“草稿写了多少条、程序生成了多少条”，同时输出 1 要求所有计数按 P 可见部分算。样本的来源计数只有全书 `stats.written/generated`，没有每项贡献的位置或逐章统计。它不是现存记录数：草稿对象 **179**、编译后对象 **176**；草稿称呼 **362**、现存称呼 **360**；草稿情节连接计数 **33**、现存 `episodes.links` **479**；`generated.nameFirstSeen=48` 也没有逐项校正历史。
- **为什么是问题**：直接返回 stats 会在第 1 章暴露后 99 章的规模；过滤现存数组再计数不能叫“草稿写了多少条、程序生成了多少条”。只凭这份导入文件无法同时满足两个承诺。`mergedFrom` 的三个去重结果也没有合并位置，不能作为按 P 还原草稿历史的依据。
- **如何核实**：运行数据脚本，查看“基本信息”“书库统计无法靠现有位置还原的计数”“实体去重残留”；检查 `stats` 只有累计整数。
- **建议改法**：把“当前可见的产品记录数”与“全书抽取过程统计”分开定义。前者按 P 计数；后者若保留，明确是不受 P 约束的生产元数据例外，并在说明页标示统计范围。若不接受这一例外，就取消无法定位的来源统计，不用现存数组伪造草稿/生成量。

### 3. 秘密矩阵的“最新知情记录”不能同时表达读者已读到的确认，关系图还缺中间知情状态

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/queries.md:59,81,94-98,103-104`；`docs/specs/story/viewer.md:55,78`。
- **现象**：矩阵含读者，但输出 8 只规定取最新 knowledge。数据里读者对 `x30-1` 的最后一条 knowledge 是 **30.61 的 `k30-2=suspects`**；**37.8 的 `s37-1`** 已由旁白确定地狱猫就是南嘉鱼，没有后续 reader knowledge 更新。因此第 38 章按输出 8 仍显示读者“怀疑”，按身份揭晓规则却已当作确定事实。角色侧也不只有 `unaware/no-record/knows/read`：第 100 章南小风对 `x93-1` 最新为 `k93-1=suspects`，林沐瑶对 `x66-1` 的最新相关记录为 `k:s68-7:e53-1=heard`。这些人在输出 5.1 下不合并，却既不满足 5.3 的 unaware，也不是 no-record，`sameIdentity` 无值可表达。
- **为什么是问题**：同一画面会把同一秘密一边当作已揭晓、一边当作仍怀疑；角色图还会丢掉“听说/怀疑但没确认”的差异，或把它错误降格为“不知道”“没有记录”。这是状态合成规则缺失，不是抽取条数不足。
- **如何核实**：数据脚本输出“e1-1在38章对x30-1的知情”“e8-2在38章对x30-1的知情”与相关身份说法；进一步筛 `knowledge` 的 `who=reader, about=x30-1`，唯一结果为 `k30-2`；筛 `who=e4-1, about=x93-1` 得 `suspects`。样本六种 knowledge 状态数量为 believes **495**、heard **467**、knows **61**、read **84**、suspects **64**、unaware **185**，不是只存在两种分点状态。
- **建议改法**：定义读者行如何合成可见的旁白确认、候选推断、显式 reader knowledge 与后续反驳，不能只取 knowledge 最新一条；定义角色对同一秘密及关联说法的合并优先级。为有记录但尚未确认的状态给出独立、完整的图返回值与显示规则，保留开发者已定的 unaware/no-record 区分。

### 4. 主线整理稿跨批重建且没有稳定身份，“给 P 前所有主线”会重复归纳同一段情节

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/queries.md:63,108,112`；`docs/specs/story/viewer.md:52,59,84`。
- **现象**：样本有 **116** 条 arcs，按 through 每 5 章产生一批；不是为固定主线 id 追加版本。第 38 章能看到 **33** 条历史主线，其中情节 `p1-1` 被 `a5-1/a10-1/a15-1/a25-1/a30-1/a35-1` **6 次**收入。arc 只有 `id/title/summary/episodes/status/through/at`，没有“替代哪条”或跨批稳定键。正文只说给 P 之前已归纳出的主线，没有决定历史批次是累计并存、只取最新批次，还是要去重。
- **为什么是问题**：三种做法会给出不同的主线列表、全书图节点与聚合出场数；同一段情节会在全书图里重复挂六遍。只取最新批次也不能自动理解为正确：不同批次主线数量、覆盖范围不同，Spec 没承诺最新一批是此前的完整替代。人物摘要已写“各方面最新的一次”，主线却缺同等明确的快照规则。
- **如何核实**：运行脚本，查看“38章主线重复收录”“38章可用归纳截止”。第 38 章最新归纳截止是 **35**，不是 38；through=35 有 **5** 条主线，不能从 id 对应回此前各批。
- **建议改法**：规定查询可依赖的整理批次/主线版本合同。若只展示最近一批，明确这批是否完整快照，以及遗漏的历史情节如何归类；若要累计，先给出有数据依据的主线身份与替代关系。验收同时核对主线列表、主线图节点与聚合计数，不只验证 at 没超过 P。

### 5. 已批准的“本章余文可读”例外没有贯穿防剧透合同，段落块概要又被要求无条件返回

- **严重程度**：重要；**类别**：正确性。
- **位置**：`docs/specs/story/queries.md:28,90,109-110,166`；`docs/specs/story/viewer.md:14,48,60`；`docs/specs/story/cli-skill.md:58,71`。
- **现象**：queries 输出 13、t02 决定 4 明确允许 P 所在章 P 之后的原文，但 viewer 输出 6 与目标、CLI 输出 3 又绝对禁止“阅读位置之后的任何内容”。同时 `source.read` 要求每段带概要，viewer 原文页要求插入概要，没有写出概要必须等整个块可见。真实数据的 `b38-3` 从 **38.48** 开始、到 **38.81** 才可见；P=38.57 时若在块开头展示它的 gist，就提前显示 38.81 才完成的观看回放与舍友猜测。`b38-4` 要到 **38.121** 才可见。
- **为什么是问题**：保留本章余文符合开发者决定，却违反另外两份 Spec 的字面全禁；为了全禁截断原文又违反已定例外。把概要当成原文附属物全部返回，还会突破“原文可读、记录不可见”的边界。当前 smoke 只检查 38.60 的原文与记录数，没有检查同一响应里的概要或搜索结果。
- **如何核实**：运行脚本，查看“38章以后才可见的本章概要”；对照 t02 决定 4 与上述输出条目。无需启动服务即可判定这组要求不能按字面同时成立。
- **建议改法**：在提供方统一定义例外并让 viewer、CLI 链接：只有 `source.read` 的本章原文允许越过段级 P；段落概要、名字注解、记录数、段落记录和搜索仍按各自可见位置处理。P 落在块中间时省略整个块概要，不按块起点截断或自行重写概要；补充这一真实数据场景。不要撤销已经批准的本章余文例外。

### 6. 删除后允许复用书 id，但查询与 cursor 没有绑定书的代际

- **严重程度**：重要；**类别**：不变量。
- **位置**：`docs/specs/story/queries.md:125-134,149`；`docs/specs/story/cli-skill.md:77`。
- **现象**：删除后进行中的查询“照常完成”，旧 cursor 在书删除后再用应得 `book_not_found`；导入又允许显式指定 id，只在 id 已占用时拒绝。合同没有定义删除后用同一 id 导入另一份数据时，旧查询、旧 cursor 与新书的关系，也没有 cursor 的重启寿命或失效错误。
- **为什么是问题**：合法顺序“取 A 的第一页 → 删除 A → 同 id 导入 B → 用旧 cursor 取下一页”中，按书 id 检查会把 B 的记录接进 A 的分页；旧查询如果延迟读路径，也可能在承诺“照常完成”的同时读到 B。只写“同一书、同一组参数”不能区分两个同 id 的实际导入。多进程命令行与服务共享书库，使该顺序不只是单个调用栈里的假设。
- **如何核实**：按上述四步推演 `book_exists`、已删除状态与 cursor 条款；再推演旧查询完成晚于同 id 新导入。正文没有能唯一判定这两条结果的版本标识或寿命边界。属于合同缺口，未运行服务实验。
- **建议改法**：定义一次成功导入的不可复用身份/代际；在途查询固定到开始时的那一代，删除后新查询不可进入旧代；cursor 明确绑定这一代、参数集合及重启后的有效性，给出可恢复的无效 cursor 错误。补同 id 并发导入恰有一个成功、另一个 `book_exists`，以及崩溃发生在发布完成之前/之后的可观察结果；不要规定必须用哪种锁或落盘算法。

### 7. 服务登记的失效判据不足以支持崩溃恢复，而且写入边界互相矛盾

- **严重程度**：重要；**类别**：不变量。
- **位置**：`docs/specs/story/queries.md:139-140`；`docs/specs/story/cli-skill.md:60,76-83`。
- **现象**：CLI 只规定“异常退出留下的登记，检查发现进程已不在时无效”，没有规定 PID 被复用、地址被另一进程占用、登记存在但服务尚未就绪时如何判断。也没定义端口监听成功、服务登记可被其他命令看到、启动成功输出之间的先后。queries 又说只有三个方法写书库、不认识版本时只读不写，CLI 的 `serve` 却必须在同一书库写入/撤销服务登记。
- **为什么是问题**：仅发现“有这个进程”不能证明登记对应的那次服务还在；正常重启可被死登记永久挡住，CLI 也可能输出指向无关服务的地址。另一边，`serve` 在未知版本书库上到底能不能启动并登记，两份合同给出相反要求；若登记失败而端口仍监听，独占和退出码也失去依据。
- **如何核实**：对照两份“副作用与数据”以及 CLI 输出 5；推演原服务异常退出后 PID/端口被别的进程复用、登记写入失败、第二个服务恰在第一个启动未完成时进入的结果。现有验收 4 只覆盖两个稳定运行/正常停止的服务，不覆盖这些分支。未运行进程实验。
- **建议改法**：定义“有效服务登记”必须绑定同一书库、同一次存活服务身份与已就绪地址，而不是裸 PID 存在；启动失败应释放自己取得的占用与登记，撤销不能删掉后来一代登记。明确服务登记是否独立于书库业务格式、未知版本时能否写它，并统一写入边界。规范可观察状态与错误，不必写锁或文件实现。

### 8. 首次登录在字面合同下无路可走，口令换会话与会话寿命都没有公开定义

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/queries.md:135,155,160-161`；`docs/specs/story/viewer.md:32,108`；`docs/specs/story/cli-skill.md:60`。
- **现象**：提供方规定“每个请求都要带登录后的会话，没有会话得到 unauthorized，静态网页资源同样要求登录”，但服务启动只给一个带口令链接，没有任何允许未登录访问、把口令换成会话的入口/响应合同。只规定重启全部失效，没有说明口令能否重复使用、同一次服务内会话是否超时、关闭浏览器是否失效，以及会话如何随 HTTP 请求携带。
- **为什么是问题**：按“每个请求”执行，首次打开带口令链接也拿不到页面或会话；自行补匿名换票入口则是在实现时新增公开协议。客户端不能预测何时该恢复登录，viewer“关闭浏览器后换浏览器打开”的验收也无法据此固定登录前置条件。
- **如何核实**：从无会话的新 Chromium 配置开始，逐条尝试仅凭 Spec 列出的路径完成“打开登录链接 → 获得会话 → 获取受保护静态页面 → RPC”；合同只定义最后一步 `/api/rpc/<方法>`，没有前三步的公开转换。此为文档推演，未启动服务。
- **建议改法**：在 queries 写明登录链接的公开形状或稳定生成合同、唯一的未认证换票例外、成功/错误响应、会话载体及服务内有效期；明确口令重用与新浏览器行为，以及停止/重启后在途请求和已发会话如何结束。RPC 的错误码到 HTTP 状态码也在同一提供方给出固定映射，不能用“相应的状态码”交给各实现猜。

### 9. 阅读状态只有“最后到达者赢”，没有保存完成与关闭恢复的时序合同

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/queries.md:117,133`；`docs/specs/story/viewer.md:43,95-96,102,123`。
- **现象**：`reading.set` 未规定位置和界面 JSON 是整份原子替换还是局部合并、成功响应是否意味着已经持久化；“后到达”为进程内调用进入、HTTP 接收还是实际提交也不明确。viewer 合并“短时间内”变化，但没有最迟保存时点、失败反馈、离开/关闭前的保存边界。验收 2 却要求变更后关浏览器、换浏览器就回到同一画面。
- **为什么是问题**：位置 38.57 与其配套的苏天晴视角/南嘉鱼抽屉如果分开落盘，会恢复出从未展示过的组合；先发的旧保存请求晚到达时，可在当前画面已变化后覆盖新状态。浏览器在合并窗口内关闭时根本还没有发送请求，“关闭后恢复”与允许无限延后的合并同时存在。只丢弃旧查询的响应并不解决旧保存。
- **如何核实**：按“连续两次界面变化 → 两次保存相反次序完成”“变更后在尚未发保存前关闭”“位置写成功而界面状态写失败”三种顺序推演；现有合同不能给出恢复值和成功/失败响应的唯一答案。未运行浏览器。
- **建议改法**：保留已写出的最后写入覆盖策略，但定义服务端的线性化点、整份原子替换及成功后持久化保证；调用方明确串行/合并发送且旧结果不回灌。给出可观察的保存完成/失败状态或其他可等待的保存边界，验收在该边界之后关闭浏览器；规定未保存关闭时允许丢失什么，而不是用固定 sleep 猜“短时间”。

### 10. 方法表还不是可共用的接口合同，CLI 的“一一对应”也已在表内被打破

- **严重程度**：重要；**类别**：一致性。
- **位置**：`docs/specs/story/queries.md:51-84,103-113,160`；`docs/specs/story/viewer.md:52-62,78`；`docs/specs/story/cli-skill.md:14,29-52,56,57`；t02 决定 5.3。
- **现象**：
  1. 没有逐方法输入/结果 schema 或可引用的现存 schema。唯一节选只定义位置与关系图点线；甚至共同规则“参数一律带 book，只有一本书时可省略”也套到了空书库的 `books.list` 和首次 `book.import`，这两个调用不能先选择一本已存在的书。
  2. 页面依赖的返回值没有落到合同：`book.info` 的目录/来源、ledger 的任务状态与道具流水区分、原文名字的定位信息、关系图上方的“本视角用了多少条说法/不知道哪些身份”。`RelationEdge` 的 `knows` 在类型里必有，但注释又限定仅读者视角，角色视角到底返回 0、null 还是省略未定。概览、状态筛选、排序及搜索的具体参数也没有可调用形状。
  3. CLI `info` 对应 **两个方法**、`records` **三个**、`ledger/episodes` 各 **两个**；`source.records`、`reading.get/set`、`graph.book/storyline` 没有命令。对象允许用名字或任一称呼，却没有规定同名、同称呼对应多个对象时的错误/选择规则；样本里两个人都叫“苏天晴”，名字冲突是真实存在的。
- **为什么是问题**：HTTP、直接调用、CLI、以后工具若各自补字段、命令分派与名字解析，逐字段一致性测试只能在实现后把其中一份当答案，不能验证开发者批准的公共合同。尤其 `--json.data` 对一个映射多个方法的命令没有唯一“对应方法结果”；这直接违反 t02 决定 5.3，而不只是文档写得略。
- **如何核实**：逐行把 viewer 所需数据映射到 queries 的方法/结果；再把 queries 的方法反向映射到 CLI 命令。上面的缺项与多对一直接来自三张表。数据脚本的对象名册可核实苏天晴/原主的同名情况。
- **建议改法**：在提供方列出可独立调用的精确参数与结果，或链接唯一受规范约束的 schema；区分书库级与书级方法。补齐页面消费字段与视角可选字段语义。按已定“一条命令一个方法、参数同名”拆清命令/子命令并补齐缺失入口；若确实只想暴露子集或允许组合命令，必须显式修订该决定，不能仍称一一对应。定义重名解析的稳定错误码与恢复方式。

### 11. 页面地址是公开协议，却没有地址格式，也没有它与书库恢复状态的优先级

- **严重程度**：重要；**类别**：合同。
- **位置**：`docs/specs/story/viewer.md:33,43,68,95,115,123`；`docs/specs/story/cli-skill.md:59,103`。
- **现象**：viewer 规定 URL 能还原书/页/对象/P/视角，同时规定打开书“先取回”书库里的上次页面、对象、位置与视角。没有说明 URL 与保存值冲突时谁赢；也没有路径、参数名、位置/视角编码、可定位人物卡页签的合同，或提供公共的 URL 生成入口。
- **为什么是问题**：书库存的是第 100 章读者视角时，CLI 输出的“苏天晴人物卡、第 38 章”链接按恢复规则可以回到第 100 章；按链接规则又必须是第 38 章。两边独立实现不能保证落到同一画面，最坏会把明确请求的防剧透位置覆盖掉。使用方也不可能只凭“地址包含这些东西”生成彼此兼容的地址。
- **如何核实**：把保存状态设为与 CLI 验收 3 不同的位置/视角，再分别应用 viewer 输出 4、输出 20 与状态条款；两套优先级都能从现有正文读出来。未运行浏览器。
- **建议改法**：在 viewer 作为提供方固定公开地址形状或唯一可引用的生成/解析合同，区分普通“打开一本书”与明确深链接；明确 URL 指定字段优先，只有缺省字段才可从保存状态补齐，并说明无效对象/视角随 P 回退时如何归一化。CLI 只引用该合同，不自行拼另一种 URL。

### 12. 已定的记录可靠度标记与部分默认收起行为没有进入查看器合同

- **严重程度**：重要；**类别**：一致性。
- **位置**：`docs/specs/story/viewer.md:54-60`；`docs/specs/story/queries.md:58,103`；依据为 t01 决定 2、5 与 V9 提案第 5.2 节。
- **现象**：t01 决定 5 要沿用“明说、推断、角色的说法”标签，决定 2 明确推断记录照常显示，并默认收起记录编号、原文段落块概括、琐碎悬念。新 Spec 只保留“自动抽取，以原文为准”的全局页脚；记录页和原文页没有这些逐条标签/默认收起合同，原文输出 15 直接要求插入段落概要。次要人物、长称呼表的默认收起则已写入，遗漏不是一次统一撤销。
- **为什么是问题**：V9 明确把旁白 fact、角色 belief/claim 与 basis=inferred 分开；如果页面只给一句正文与出处，用户无法辨认“角色声称”与“原文明说的事实”。全局免责声明不能替代这些逐条差异。按当前 Spec 实现并通过验收，仍会丢掉开发者明确要求沿用的机制。
- **如何核实**：对照 t01 决定 2、5 与 viewer 所有输出条目；数据里 `s30-13` 是 inferred/candidate、`s33-17` 是 speech/claim、`s37-1` 是 narrator/fact，三个维度实际存在，不能用单个“有出处”替代。
- **建议改法**：把已定的逐条标记、推断记录不隐藏，以及相关内容的初始折叠状态写进 viewer；在 queries 的记录结果里保留这些结构化字段。为“琐碎悬念”给出可判定的分组依据或明确人工/数据标记来源，不让实现者凭任意隐藏规则处理。

### 13. Skill 验收引用了不存在的“38 章以内 16 题”，22.9% 的分母和判分环境也变了

- **严重程度**：重要；**类别**：验收。
- **位置**：`docs/specs/story/cli-skill.md:20,105-107`；`docs/proposals/novel-story-app.md:263-264`。
