### 1. 尾部指纹没有绑定 generation，相同前缀的重新导入会串到新一代尾部

- **严重程度**：重要；**类别**：不变量 / 正确性。
- **位置**：`packages/nb-story/src/core/unextracted.ts:62-66`；`packages/nb-story/src/core/api.ts:239-249`（路径均相对 `/tmp/t29-30-review-wt`）。
- **现象**：旧 `openBook` 固定了 24 章的图；另一个真实 Bun 进程删除同 id、重新导入前 20 章并发布带 25 章的新 source 后，旧会话的 `unextracted()` 返回第 25 章“换代后的新尾部”，尽管新旧 generation 不同。
- **为什么是问题**：只比较已提交章的段数，既不比较 generation，也不比较原文哈希。重抽同一部书、重新导入相同前缀后改后续章，前缀一致是正常情况，不是计划所称“概率可忽略”的随机碰撞。旧图因此拼入新源，违反 `qa.md:245` 与 `queries.md:160` 的固定一代合同；两份不同正文只要分段相同也会通过。t30 设计审查第 1 条没有被真正解决。
- **如何核实**：`bun /tmp/review-t29-30-impl/reach-smoke.ts` 的 `pinned-other-generation` 输出：旧代 `23b77149-5b35-4177-8196-0b96805522f0`、新代 `62f89e6b-4bf7-405d-b396-7cbb2aaa262d`、旧图 24 章、返回新代尾部 1 章。实验使用真实 `Library.removeBook/importBook`、`IngestStore.replaceSource` 和公开 `StoryApi.openBook`，不替换文件系统方法或伪造工具状态。
- **建议改法**：把源的稳定身份与书 generation 显式绑定；固定图时一并固定并核对源快照，至少使用已提交 SourceChapter 的真实 sha256 校验，不能以段数表当身份。删除换代后旧会话只能保留旧快照或无尾部，不能再按 id 接新源。补跨进程“同书相同前缀重抽、尾部改稿”的回归。

### 2. source 缓存仅凭 mtime 与 size，原子换文件后仍可返回旧正文

- **严重程度**：重要；**类别**：正确性 / 缓存失效。
- **位置**：`packages/nb-story/src/core/unextracted.ts:35-55`。
- **现象**：已经解析过 source 后，以另一个 inode 原子替换相同路径，保留相同 `mtimeMs` 和字节数；新建 `openBook` 仍读到旧尾部。磁盘为“换代后的另尾部”，返回“换代后的新尾部”。
- **为什么是问题**：缓存键既不含 inode/ctime，也不含源身份或 generation。替换可跨进程发生，删除与重新导入也没有清理全局 Map；新一轮问答会用过时正文校验出处。generation 检查本身也不够：同一代正常追加或外部恢复源文件同样需要文件身份判别。
- **如何核实**：同一实验的 `same-mtime-size-cache` 输出 `sameMtime:true,sameSize:true,differentInode:true`，磁盘与返回值不同。通过真实 `rename` 和 `utimes` 建立用户指定的同 mtime/size 边界；没有伪造 stat。正常抽取的 `replaceSource` 是写临时文件再 rename，不会半写 JSON；但当前 `stat(path) → readFile(path)` 仍不是同一个文件快照，替换发生在两步之间可把新内容缓存到旧元数据下。
- **建议改法**：打开源文件后对同一个 handle 做 fstat 与读取，用 generation/源身份及 dev、ino、ctime 等可靠版本信息作为缓存键，读取前后检查版本；不要把一次 stat 的元数据与另一次路径打开的内容配对。补相同 mtime/size 的真实原子替换用例。

### 4. “只画最强的线”先排名后应用连线层，隐藏的强线挤掉唯一可见线

### 5. base64 长度估算漏减填充，符合 32 MiB 上限的文件被拒绝

- **严重程度**：建议；**类别**：正确性 / 输入边界。
- **位置**：`packages/nb-story/src/server/ingest-service.ts:152-155`。
- **现象**：实际为 `33554431` 字节（32 MiB−1）或 `33554432` 字节（恰好 32 MiB）的合法 V9 JSON 都报 `ingest_bad_text`“文件超过 32 MiB”；`33554430` 字节可导入。
- **为什么是问题**：`content.length / 4 * 3` 算的是补齐后长度，未减末尾 `=` / `==` 对应的 1 / 2 字节。浏览器先按实际 File.size 允许选择，再在服务端被错误拒绝，违背 viewer 输出 54“不超过 32 MiB”的边界。旁边已有 `decodeContent:48` 使用了正确公式，新分支复制时丢了一部分。
- **如何核实**：`bun /tmp/review-t29-30-impl/import-smoke.ts`，经真实 `createIngestService.call('book.importGraph')` 导入同一合法样例 JSON 加尾随空格到这 3 个大小；输出依次 success、ingest_bad_text、ingest_bad_text。未替换 base64、schema 或导入实现。
- **建议改法**：复用统一的 base64 字节数检查，扣除 padding；在既有导入行为测试补 `MAX−1`、`MAX` 与 `MAX+1`，避免把字符串长度当实际文件字节数。

### 6. 自定义模型目录把配置币种强制改成 USD，混币种防护因此失效

### 8. 应力布局 400 点边界没有可接受的排版结果保障

- **严重程度**：重要；**类别**：正确性 / 性能。
- **位置**：packages/nb-story/src/web/graph/sigma-kit.ts:301-371、sigma-kit.test.ts:22-38。
- **现象**：真实 graphology 数值实验中，400 点链图的应力布局耗时约 7.46 秒，且跑满三轮 noverlap 后仍警告有重叠；401 点退回力导向仍约 3.66 秒并警告重叠。测试只测 7 点，不测 Spec 明确的 400 点边界、400 点布局时间或不重叠可观察结果。
- **为什么是问题**：关系图切换到应力后会阻塞主线程，400 点是公开上限而非理论数字；“点、名字互不重叠”是同一 Spec 条款，当前实现对上限图没有达到它，400/401 还出现明显非线性体验。separateNodes 本身是 O(n²) 检查和 noverlap，多轮把 SMACOF 的 O(400²×300) 叠加。
- **如何核实**：bun /tmp/review-t29-30-impl/layout-smoke.ts，真实 graphology + sigma-kit：count=400 ms=7460.6、nonFinite=0、coincident=0、min distance=1.467，并打印“排版到上限仍有点重叠”；count=401 ms=3662.2，同样警告。count=0/1 不崩，重合起点输出有限坐标，边界功能本身可运行。
- **建议改法**：把 400 作为实测性能与布局验收边界；减少全对迭代、采用 Barnes-Hut 或 worker，或降低上限并按实际可接受阈值分档。若 noverlap 不能达成标签不重叠，应明确降级而不是宣称不保证收敛却把该模式作为合同能力。

### 12. 不填书名导入非 V9 文件时，绕过 unsupported_format 合同
