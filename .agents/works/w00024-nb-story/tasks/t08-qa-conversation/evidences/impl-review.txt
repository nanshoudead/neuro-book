## 发现 F1：不可读的会话日志逃出 F8，`ask --json` 没有 JSON 且退出码错误

- **严重程度**：重要；**类别**：正确性 / 接口合同。
- **位置**：`/home/notnotype/CodeRepository/neuro-book/.worktree/w00024-nb-story/packages/nb-story/src/core/qa-records.ts:275`、`packages/nb-story/src/qa/engine.ts:150`。
- **现象**：把一条真实对话引用的日志权限设成 `000` 后续问，`sessionLog()` 只处理 `ENOENT`，其余读取异常原样抛出。真实 `ask --continue <id> --json` 退出码为 **1**，stdout 为 **空串**，stderr 是 `[Uncaught Exception] Error: EACCES` 与堆栈。
- **为什么是问题**：计划的“恢复不了”、Spec 输出 26 与 F8 明确包含日志“读不成”：应在请求前给 `qa_not_continuable`、退出码 **4**、保持记录不变。当前既绕过失败码合同，又破坏 JSON 消费端的单个 JSON 输出合同。权限不足、I/O 错误、日志路径变成目录都能走这个分支；不是模型失败。
- **如何核实**：运行 `bun /tmp/review-w00024-t08-impl/scratch/log-permission.ts`，退出 0。脚本经真实 `createStoryApi`、`askQuestion`/脚本模型建立对话，仅对 scratch 内的日志执行 chmod，再同时调用引擎和真实 CLI。输出：`engine {"name":"Error","code":"EACCES"...}`；`cli {"exit":1,"stdout":"","stderr":"...Uncaught Exception..."}`；`recordUnchanged true`。脚本使用的模型地址为本机关闭端口，没有真实模型调用。
- **建议改法**：在日志读取边界把无法读取的文件系统异常转换成带诊断原因的 `SessionLogRead {ok:false}`，由现有 `startContinued` 统一抛 `qa_not_continuable`。补一条真实不可读文件的 CLI 断言：退出 4、stdout 可解析且 code 正确、记录和日志字节不变。

## 发现 F2：立即删除上一份日志会让跨发布边界读取的正常续问误报“不能续问”

- **严重程度**：重要；**类别**：不变量 / 并发。
- **位置**：`/home/notnotype/CodeRepository/neuro-book/.worktree/w00024-nb-story/packages/nb-story/src/qa/engine.ts:148`、`packages/nb-story/src/core/qa-records.ts:232`、`packages/nb-story/src/core/qa-records.ts:275`。
- **现象**：续问甲在 `records.get()` 已读到第 1 轮记录、尚未打开其日志时暂停；续问乙正常完成第 2 轮保存并删除第 1 轮日志；甲接着读旧记录指向的文件，得到 `qa_not_continuable`，请求数 **0**，提示“会话日志不在了。请开新对话”。磁盘上的最新对话和最新日志都是完整可续问的。
- **为什么是问题**：单次 rename 发布记录只能保证指向的新日志已存在，不能保证读者手上旧版本的日志还存在。输出 15 的“读者看到的记录与它指向的日志总是成对的”没有实现；输出 25 约定重叠追问照常输出本轮结果、保存时再报 conflict。这个失败发生在读取阶段，完全不涉及已接受的“轮数核对与写入之间极短窗口”，即使双方保存完全串行也会触发。用户被错误地要求丢弃一个健康对话。
- **如何核实**：运行 `bun /tmp/review-w00024-t08-impl/scratch/read-publish-race.ts`，退出 0。脚本使用真实书库、真实 `QaRecords` 与真实 harness/脚本模型，仅在甲的公开 `get()` 返回边界设置 Promise 栅栏；乙从真实 `askQuestion` 完成整个发布流程后才释放甲。输出 `continuedError {"name":"QaError","code":"qa_not_continuable",...,"modelRequests":0}`，随后从磁盘读到问题 `["第一问","先保存的追问"]`，最新日志摘要校验 `ok:true`。没有伪造日志缺失或改写产品实现。
- **建议改法**：把记录和对应日志作为一次可重试的读取操作：旧日志缺失时重新读当前记录，只有记录仍指向同一日志才判 F8；若已发布新版本则按新的一对重试，更新起始轮数和账本。保留当前无锁保存方案和发布后删旧日志；补跨 `get → sessionLog` 发布边界的真实运行时用例。

## 发现 F5：`qa rm` 扫掉尚在发布的新日志后，save 仍返回已保存并发布缺日志的记录

- **严重程度**：重要；**类别**：不变量 / 并发。
- **位置**：`/home/notnotype/CodeRepository/neuro-book/.worktree/w00024-nb-story/packages/nb-story/src/core/qa-records.ts:203`、`:214`、`:299`。
- **现象**：第二轮先写好新日志并通过 expectTurns 核对，在记录 rename 前暂停；此时执行真实 `QaRecords.remove()`，它先删记录，再按前缀把旧日志和第二轮尚未发布的日志都删掉。恢复 save 后，记录 rename 成功，generation 复查通过，返回 **saved:true**；目录里只剩 **1 个记录 JSON、0 个日志**。再次读取这条记录的 sessionLog 为 `{ok:false, problem:"会话日志不在了"}`。
- **为什么是问题**：这是删除把发布者正在使用的日志误当成孤儿清理，破坏输出 15 的配对不变量；结果声称保存成功，实际对话永久不能恢复。这与允许并发追问在轮数核对后覆盖一轮不同：已接受的是可能丢一轮，没有允许发布引用不存在文件的记录。把保存前再核对轮数当成唯一保护，无法协调 remove 的跨文件清理。
- **如何核实**：运行 `bun /tmp/review-w00024-t08-impl/scratch/remove-save-race.ts`，退出 0。脚本创建真实一轮对话，子进程调用真实 `QaRecords.save`；`pause-record-publish.ts` 仅经 Bun loader 在原 `await rename(temps[1], recordPath)` 前插入 SIGUSR2 栅栏，不改保存、删除逻辑或日志内容。父进程等明确的 `REVIEW_READY_PUBLISH` 后执行真实 remove，再发信号继续。输出 save 的 `saved:true`、files 仅 `<id>.json`，随后输出 `log.ok:false`。这个顺序对应产品真实 await 窗口；早先 strace 路径过滤没命中的尝试不计证据。
- **建议改法**：让“删除对话”拥有明确的提交边界，并阻止在途发布重新写回已删除容器。例如对话的一对文件进入独立目录，remove 先整体改名移走，再清理；续问只向开始时已经存在的容器发布，不能重建它。这样保持不加锁，也避免删除按共享 qa 路径扫到在途日志。不要只加一次 exists/轮数检查，那仍有相同的检查到 rename 窗口。补断言：删除与发布交错后要么完整一对可恢复、要么记录不存在，不能 saved:true 加缺日志。
