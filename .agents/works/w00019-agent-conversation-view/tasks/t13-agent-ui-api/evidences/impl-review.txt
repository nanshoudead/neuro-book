## F1 结果节点后面还有最终回复，或一次交了两个结果节点时，结果区里的节点仍被计入过程操作次数
- 严重程度：重要；类别：正确性、合同
- 位置：`packages/nb-agent-ui/src/conversation-turns.ts:241-246`（`outcomeCallId` 只取最后一个答案；`collectTools(body).filter(id !== outcomeCallId)`）
- 现象：`outcomeCallId` 只在“最后一个答案是节点”时非 null。节点之后跟最终回复时它为 null，结果区里的节点（q2）照样算进 `metrics.steps`；同一条消息交两个成功的结果节点时，`outcomeStart` 把两个都划进结果区，只排除后一个。
- 为什么是问题：Spec（`agent-conversation-view.md` 第 201 行）写“结果节点不计入整轮摘要的操作次数”；结果区里显示的节点是结果，却被算成“过程 · N 次操作”。
- 如何核实：`exp/outcome.test.ts`（bun test）：消息序列 user、read、answer(成功)、最终回复文字 -> `steps 2 outcomeCallId null outcomeStart 1 blocks [chain,node,content]`（应为 1）；一条消息里两个成功 answer -> `steps 2 outcomeCallId q2 blocks [chain,node,node]`（应为 1）。现有测试 `src/conversation-turns.test.ts:355` 的“结果节点之后还有最终回复”用例只断言 `outcomeMessage` 与 `outcomeCallId`，没有断言 `metrics.steps`，所以没发现。
- 建议改法：排除集合改为“结果区（`outcomeStart` 之后）里所有 `isAnswer` 的节点的 call id”，与 `outcomeCallId`（给复制用的那个）分开；补断言 `steps`。

## F2 被排除出过程的结果节点连带从 `changedFiles` 与 `filesRead/filesChanged` 里消失
- 严重程度：建议（目前内置与 Lab 的结果节点都没有 `effects`，是潜在问题）；类别：正确性、合同
- 位置：`conversation-turns.ts:246`（同一个 `tools` 同时喂给 `computeMetrics` 与 `collectChangedFiles`）
- 现象：结果节点带 `effects`（例如写报告并作为结果的领域工具）时，它改的文件不进轮末的“改动文件”列表，`metrics.filesChanged` 也变 0。
- 为什么是问题：计划与 Spec 只要求“操作次数”不含结果调用，没有说文件改动也不算；轮末汇总靠 `changedFiles` 让用户看到这一轮改了什么，结果节点改了文件反而看不到，`file.openDiff` 也无入口。
- 如何核实：`exp/outcome.test.ts` 最后一例：`write_report` 渲染器 `presentation: "node"`、`outcome: true`、`effects.changed=[r.md]`，成功 -> `changedFiles []`、`filesChanged 0`、`outcomeCallId w1`。
- 建议改法：只让 `steps`（以及 `failed`，成功的结果节点不会失败，可不管）排除结果调用；`filesRead/filesChanged/changedFiles` 仍用全部调用。

## F3 步骤行各自持有展开状态：工具组成形、出错项露出位置变化时，用户已点开的步骤被重置
- 严重程度：重要；类别：不变量、与 Spec 的一致性
- 位置：`src/vue/stream/AgentToolStepRow.vue:30`、`AgentTextStepRow.vue:24`（`const open = ref(false)`）；`AgentChainBlock.vue:81-110`（同一步骤可由三处不同位置的实例渲染）
- 现象：展开状态由行组件实例自己持有，实例会因思维链的重新分组而卸载重建，状态随之丢失。已用真实视图复现：运行中，思考行（夹在两次探查之间、此时还是组外的独立行）被用户点开；下一次 `read` 到达后思考行并入工具组，组内是新实例，展开状态丢失。`processDisclosure: "live"`（nb-story 用的模式）下组本身是展开的，用户刚点开的思考在眼前收回去。另外出错的工具项在组收起时露出的实例与组内实例是两个，展开其一后再展开/收起组，状态互不相通。
- 为什么是问题：Spec“展开与折叠”写“用户点过的以用户为准”；旧实现展开状态按步骤 id 存在 `useOpenSet` 里，与重新分组无关。作者自述的偏离（步骤行自持状态）正是破坏点：计划 `use-open-set.ts` 的目的就是“按 id 记录”。`AgentChainBlock` 已经有按 id 的 `openSet`，步骤行改成受控（`expanded` + `update:expanded`）即可。
- 如何核实：`exp/state.dom.test.ts` 的 “live regroup” 例：live 模式，点开“思考”行后文字可见（`LIVE before true`）；追加 `read` 后 `has 第二行 false`，按钮列表里思考行仍在但已折叠。非 live 的同样操作：重新分组后组默认折叠，展开组后思考行也是折叠的。
- 建议改法：步骤行改为受控组件，由 `AgentChainBlock`（与 `AgentToolStepRow` 的使用者）用 `openSet.isOpen(step.id)` 传入；判断“偏离是否成立”：不成立，因为它削弱了 `useOpenSet` 想保证的“按 id、跨重建保持”，且没有省代码（每个步骤行都多一个 ref）。

## F7 `acceptSubmission` 用草稿原文，发送来自宿主组件（非输入框）时清掉用户正在写的草稿并把它记成“已发送”
