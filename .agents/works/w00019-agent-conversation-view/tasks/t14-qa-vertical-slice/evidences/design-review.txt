### F1 重要 / 正确性：条目排在压缩分隔线之后时，最终回复被收进过程，整轮收起后看不见回复

- 位置：计划 Context 第 1 条（“所以条目作为一条系统消息排在回复之后，分轮规则不用改”）与关键设计 5（“条目插在第 N 轮最后一条消息之后”）；代码 `src/conversation-turns.ts` 的 `splitTrailing`（396 行起）与 `findOutcomeStart`（168 行起）。
- 现象：`splitTrailing` 只把“末尾连续的 divider”移到 trailing；末尾夹着一个 notice 时 divider 留在 `blocks` 里，`findOutcomeStart` 倒扫碰到 divider 就停，随后向前跳过非结果块，最后 `outcomeStart === blocks.length`。
- 如何核实（真实运行时，`exp/f1.test.ts`）：消息序列 `用户, 助手(读文件), 助手(最终回复), system(compaction), system(custom 条目)` 得到 `blocks = chain, reply, divider, notice`，`outcomeStart=4`（等于块数），`foldable=true`。也就是回复在过程区，整轮收起后什么结果都不露，`outcomeMessage` 也为 null，角色行的复制等消息操作消失。对照：条目在分隔线之前时 `chain, reply, notice`，`outcomeStart=1`，正常。
- 为什么是问题：Lab 的 `answer` 场景就是“结果之后跟一条压缩分隔线”，nb-story 的会话日志在回复之后压缩是可能的；宿主按计划“排在这一轮最后一条消息之后”就会踩到。计划把“分轮规则不用改”当成已核实的事实，这条对一种合法排列不成立。这个缺口在系统提醒上本来就有（同一机制），条目只是让它更容易被触发。
- 建议改法：二选一并补单测。(a) `splitTrailing` 在末尾连续的 divider 与 notice 混合段里只摘出 divider，notice 留在结果区；(b) `findOutcomeStart` 倒扫时同样越过 divider（它已经被 `splitTrailing` 管着，之后的分隔线在 trailing）。验收 28 的分轮单测要列全位置：回复之后、结果节点之后、分隔线之后、回复之前、两轮之间、运行中末尾（见 F10）。

### F2 重要 / 合同：条目的时间戳是“约定”，写错会悄悄把用时拉长

- 位置：计划关键设计 4“宿主写条目的约定”第 1 条与“不做与风险”的“条目时间戳”；代码 `computeMetrics`（`end = group.at(-1)!.timestamp`）。
- 现象：用时按组里最后一条消息的时间算，条目是最后一条。实验 `entry late ts`：条目时间戳比回复晚 600 秒，`durationMs` 从 3000 变成 602000，没有任何诊断。
- 为什么是问题：条目是宿主批注，不是对话中发生的事；它的时间戳落在哪里不该影响一个显示给读者的数字。计划选择“写进 README、不在视图里特判，免得系统消息的时间从此不算数”，但需要靠自觉的约定正是 w00019 一路在避免的东西（t13 F5、F6 都是宿主写法失误）。另外“同一对象”约定的失败后果是性能，不是正确性，这一条没问题；时间戳这一条是正确性。
- 建议改法：`computeMetrics` 取“最后一条不是 `source: "custom"` 系统消息的消息”的时间（`custom` 在 Spec 里本来就是宿主或插件的消息，没有“对话发生时刻”的合同）。提醒、压缩仍然算。这样 README 只剩“引用稳定”一条约定。若坚持不特判，至少让 `buildTurn` 在开发期发现条目时间晚于它前一条助手消息时打一条诊断。

### F3 建议 / 别扭之处：把条目放在 `ctx.messages` 里，位置、时间和“是否可见”都由排列顺序隐式决定；有更不易写错的形状，也顺带回答待确认第 2 项

- 位置：计划关键设计 4、5。
- 现象（`exp/f1.test.ts`）：同一条条目，因所在位置不同，行为不同：回复之后进结果区（整轮收起仍露出）；回复之前（`chain, notice, reply`，`outcomeStart=2`）落在过程区，整轮收起就藏起来；放在没有回复的已结束轮次末尾（中断的轮次）`outcomeStart=2`，同样藏起来；放在第一条用户消息之前会自成一个“没有用户消息”的轮次（`head` 实验，`notice` 单块、`foldable=true`）。Spec 把信息条目定义为常显层，这些情形与它不符，只是现有 `notice` 行为的继承。运行中把条目插在助手消息中间，还会切开思维链（`flush()`）。
- 另一个落差：评审板图 01 里黄色的“没核实的出处”画在回复气泡里面；计划的条目组件是“不占角色行、不加气泡”的独立块，渲染在气泡下方，外观与开发者看过的图不一致（计划验证一节安排了重截图 r2，可以在那里让开发者看，但这是已定图示的改变）。
- 更不易写错的形状：给 `AssistantMessageView` 加一个可选的 `footers`（或 `annotations`）数组，元素是 `{customType, details, text}`，由宿主在它要跟随的那条助手消息上带出来；视图在这条消息的内容之后画它。它没有位置、时间戳、分轮、分隔线的任何交互：条目永远跟着它的回复一起显示与收起；原始视图里它就在那条消息的 JSON 里，不会出现一条“不在会话日志里的幽灵消息”（待确认第 2 项的担心消失）；能画在气泡里面，与图 01 一致。代价与现有做法相同：宿主要为带条目的那条消息做一个新对象并缓存，才能保持适配器给的引用稳定。条目只挂在助手消息上，其他种类要挂时再加。
- 若仍用消息形状：至少让分轮规则把 `custom` 条目当作它前一个块的附属（算入同一块的结果区），不依赖位置。

### F4 重要 / 对照需求：第一个使用方的文案与已定图示不一致（会话与对话）

- 位置：计划关键设计 6（文字表 `sessions.*`、`header.untitled`）与“不做与风险”最后一条。
- 现象：w00024 t13 决定 6、评审板图 09 到 16 与开发者看过的稿里，一律写“对话”：“还没有对话”“正在加载对话”“新对话”“对话列表没取到”“对话”下拉。计划里包内文字全部写“会话”（`sessions.empty` 等，新建按钮名“新建会话”，缺省标题“会话”），只有 `title` 能由宿主改，计划自己承认“nb-story 要整页改称对话时再加属性”。
- 为什么是问题：第一个（也是现在唯一的）使用方上线时空状态、加载中、出错、新建按钮的读屏名都是“会话”，与同页顶部下拉的“对话”不一致；而“要整页改称”在决定 6 里已经成立，不是将来的事。晚加属性意味着改完全部文字键，返工点是预见得到的。
- 建议改法：现在就加一个轻量覆盖：`labels?: Partial<Record<"title" | "create" | "loading" | "empty" | "error" | "retry" | "untitled", string>>`（宿主给整句，英文也由宿主给）；或者只加一个 `noun` 属性，文字表里用占位符。二选一，前者更直白。

### F5 建议 / 接口：条目渲染器按 `customType` 整个替换了 `EntryRendererEntry`，与 Spec 与 t11 已写的范围不同

- 位置：计划关键设计 4“注册表”；Spec 的“注册表”一行（149 行“匹配的消息类型与系统条目来源”）；t11 README “接上没有消费者的扩展点”。
- 现象：现有 `EntryRendererEntry = {messageKind, systemSource?, component}`，Spec 与 t11 都按它写，t11 要在“信息条目”上接。计划把它改成只有 `customType`，等于 t14 单方面收窄了 t11 的范围（计划写了“需要时再加”，但这条加回去就是再次改形状）。

### F6 建议 / 上游选择：`markdownPreviewLine` 在核心里自己实现一份“半个 Markdown 方言”，而计划自己的理由说方言属于宿主

- 位置：计划技术选型第一条与关键设计 2；`docs/specs/workspace/markdown-dialect.md` 输出 6、7、24 与方言一览表。
- 现象：计划的依据是“Markdown 的解析与方言属于宿主，通用库不认识”，然后在核心手写了一份去标记规则。NeuroBook 的方言与它的规则有出入：输出 6 规定 `*`、`_`、`**`、`__`、`~~`、`==` 的开闭按 CJK 友好规则判定（紧挨汉字或全角标点也能开能闭，例如 `他说：**“走吧。”**然后离开。` 里引号也是粗体）；输出 24 有 `==高亮==`；还有 `<mark>`、`<span style>`、`<comment>`、`<sup>` 等行内标签。计划列的规则里没有 `==`、没有这些标签，“成对且紧贴文字”里“文字”是否包含全角标点也没说。结果：宿主展开显示是粗体的写法，预览里可能留着 `**`；宿主不认的写法，预览里被去掉。
- 具体的几处要在实现前写进规则或测试（计划 30 的用例清单没有）：
  - 行首 `#` 与 `-`、`*`、`+`、`>` 必须后跟空白才算块标记（`#伏笔`、`*注：…`、`-5℃` 不是）；
  - `_` 的“词边界”不能用 JS 的 `\b`：`\b` 把汉字当非词字符，`读取_章节_摘要` 会被剥成“读取章节摘要”，而方言按 CJK 规则怎么判要对照实现，不要凭猜；
  - 第 1 步先在 `****` 处断开、第 4 步才切出行内代码，所以 `` `a****b` `` 会在代码里被拆开；顺序要反过来或第 1 步也避开代码；
  - 以代码围栏、`---`、表格行、HTML 标签开头的第一行；
  - 流式半截：`**Gathering…**` 逐字到达时会短暂出现 `…arcs*` 或 `…arcs***` 的残留星号（规则 5 只管 `**` 开头的）。
- 实验：没有单独跑（实现不存在）。上面各条按计划文字推演，标“从代码推断”。
- 建议改法：让宿主决定怎么做预览。在 `ports.ts` 与 `AgentViewRenderers` 加一个可选函数 `markdownPreview?: (text: string) => string`，包内缺省用计划里那份简单规则（只保证 `**`、`#` 这类常见写法），neuro-book 注入时用 `nbook.markdown` 的解析取第一行的纯文字，方言写法自动一致；单元测试用宿主的渲染结果当对照。这与现有“Markdown 显示与编辑器由宿主注入”是同一种分工。若坚持只在核心做，至少把规则收窄到“明显的几种”，并按上面列的反例补测试。
- 顺带：计划把 `firstLine` 说成“只剩原始视图在用”，实际 `AgentQueuedMessages.vue` 也在用（用户排队消息的纯文字，正确地不该去标记）；模块头的说明要改对。

### F7 建议 / 边界：被退回的结果调用移进思维链，几个边界计划没写

位置：关键设计 3；代码 `buildBlocks`、`makeChain`、`AgentChainBlock`、`harness.ts`。实验 `exp/f2.test.ts`（真实 `buildTurns`，按计划描述的行为推演改后形状，标“从代码推断”）。

- **中断不是退回**：适配器在运行被中断时把仍在运行的调用改成 `status: "error"` 且不带 `error`（`harness.ts` 260 行）。结果工具在这时也会走 `rejectedOutcome`，进思维链；Lab 的 `summary` 写成 “退回：” 加 `call.error` 第一行，这时是空的，读者看到“退回：”后面什么也没有，还把中断说成退回。建议计划规定 `summary` 在 `call.error` 为空时的写法（例如不加“退回：”），并在 Lab 样例里体现。
- **整轮的结果都被退回**：`A all rejected` 实验：改前 `chain, node, node`，`outcomeStart=3`；改后只剩一条思维链，状态仍是 `done`，没有结果块、整轮收起，只有摘要里一个“失败”提示。这与改前一致，但计划“整轮的结果区与摘要”没有交代这种情形，也没有验收。nb-story 的“停止且没有文字”走 `no_answer` 失败，不算这种；而“每次交卷都被退回、运行到上限”要看 harness 怎么结束，未验证。
- **思维链换 id、展开状态丢**：思维链 id 取第一项的 id。`E first rejected` 实验：被退回的调用是整轮第一个块时，它后面那条思维链并进它，id 从 `chain:a3:thinking` 变成 `chain:c1`；在 `processDisclosure: "collapsed"` 下，用户点开过的后一条思维链状态丢失（`live` 下默认展开，不受影响）。节点卡片的展开状态在 `AgentTurnBlock` 的 `useOpenSet`，变成行后在 `AgentChainBlock` 的 `useOpenSet`，两个实例，用户点开过的卡片变成行时收起。都是小跳动，与计划“风险”最后一条同类，但没写。
- **探查组被切断**：被退回的调用是 `interact` 类，计划写了“按 interact 类别结束当前工具组”。于是 `读, 退回, 读` 不再成组，nb-story 想要的“读了第 33–37 章”在有退回的轮次里被拆成两个单次读。可以让被退回的行不结束探查组（作为组内的一项收进去），代价是组内多一种项。
- **流式中被判错**：`toolCallPhase` 把 `streaming`、`running` 归为 running，`error`、`invalid` 归为 error，所以流式半截的参数校验失败（`invalid`）那一刻块从 `node` 变成行，宿主节点组件被卸载；组件内部状态（例如还没点开的详情）丢失。适配器目前只产生 `error`，`invalid` 没有来源，这是潜在路径。

### F8 建议 / 合同：`groupPhrase(calls)` 的几处保证与写法提示

位置：关键设计 1；`makeToolGroup`、`groupExploreTools`、`guardTool`。

- 已核实成立：探查组不会跨思维链（组在 `groupExploreTools` 里按每条链分别算），所以“同一组跨思维链”不会出现；`guardTool` 对每个回调只在 `reported` 集合里记一次，换成收调用后抛错仍只报一次，仍退回 `toolGroup.generic`。
- 没写的：
  - 组里有出错的调用（例如读原文超出“一问最多读 20 章”被拒的那些）与运行中的调用时，`calls` 都给了，宿主不过滤就会把被拒的读也算进“读了第 33–37 章”，也会在流式半截参数时出现“第 33–33 章”再跳成“33–37”。注释只写“含运行中与出错的”，应明确写“要按 `call.status` 自己过滤；想只说成功读到的，要过滤出 `success`”，并在 Lab 的样例里做一遍。
  - 摘要行（`describeChain`）按“不同路径”数文件，组短语按调用写，两处会对不上（计划已在“不做”里承认内置 `read` 的这个问题，nb-story 的短语上线后问题在它自己的页面里更明显）；至少让 README 写明两处口径不同。
  - 阈值：组只在 `tools.length >= 2` 时成形，同一渲染器只有 1 次调用的短语也会被调用，写法提示要说“至少一次，不一定是多次”（计划写了“至少一次”，没有说为什么出现 1 次）。

（F7 第一条的更正：适配器把“运行结束时仍没有结果的调用”改成 `error` 且不带 `error` 文字，不限于用户中断，`harness.ts` 的 `applyRunEnd`；影响面比我写的更宽。）

### F9 建议 / 一致性与细节：`AgentSessionList`

位置：关键设计 6。

- **时间写法**：
  - “前一天”必须按日历日比较（年月日），不能用 `now - 24h`；夏令时那天按 24 小时算会错一天。计划只写了“与 now 同一天、前一天”，实现与测试都没要求跨夏令时的用例；
  - `Intl.DateTimeFormat` 写“月-日”在 `en-US` 下得到 `10/18`，计划的“月-日”与英文输出不同，测试按哪个写要定；
  - 昨天可以用 `Intl.RelativeTimeFormat(locale, {numeric: "auto"}).format(-1, "day")`，不必加 `sessions.yesterday` 两份文字；
  - `now` 是宿主给的单个数；宿主不更新它，跨过午夜后“今天”的行永远不变成“昨天”。组件没有 `env:timer`（对，且应该没有），但 README 要写明宿主要定期更新 `now`；`updatedAt > now`（多机时钟差）也要有一句话说怎么显示。
- **读屏与键盘**：`<ul>` 配 `list-style: none` 时 Safari 与 VoiceOver 会丢掉列表语义，要写 `role="list"`；每行一个 `<button>` 意味着 N 个 Tab 停靠点（几十个对话时不方便），评审板草稿原来用的是 `listbox/option`；选择 `aria-current` 加按钮没有错（导航式列表常见），但要在 `.md` 里写明“不是 listbox，不做方向键漫游”，免得 t11 的弹窗再改一次。运行中、已中断、出错三个状态除颜色外要有文字（计划有）；时间建议用 `<time datetime>`。
- **谁关下拉**：点行发 `session.select`、点新建发 `session.create`，宿主处理这两个 action 时自己关下拉；点已选中的行也发（计划正确，否则宿主关不了），但 README 要明确写“收到 action 后关下拉是宿主的事，列表自己不持有开关”；出错重试发 `sessions.refresh` 时下拉不该关，这点宿主要区分，也要写。
- **能力标签**：计划写 `[]`；组件若不持有任何 `ref`（计划写“不持有状态”）可以成立，但键盘焦点管理、悬停之类只要用到 `ref` 就是 `state:local`，按 `docs/standards/code/components.md` 要如实声明，实现时核对。
- **与 t11 弹窗的复用**：`AgentSessionListItem` 没有 `archived`、`profile`、`pinned` 等 t11 弹窗需要的字段，也没有“行上的更多菜单”的位置；计划写了“以后加”，都是可选字段、不会逼出破坏性返工，这一点成立。但 `status: "interrupted" | "error"` 是 nb-story 问答记录的状态，NeuroBook 的真实会话（`SessionView`）没有这两个值，t11 接主应用会话列表时需要决定它们的来源；建议字段注释写明“宿主按自己的状态映射”。
- 一致性：不 inject、只收 `locale` 属性——这个选择成立：它挂在 `AgentConversationView` 之外，`provideAgentView` 提供的 `inject` 到不了它；`PlainMarkdown` 等宿主注入的零件已经是同一种做法。没有问题。

### F10 建议 / 验收映射：28 的“整轮收起”与分轮边界没有对应的可执行场景

- 位置：计划关键设计 7 的 `reply-unverified`；验收映射 28、29；“风险”里引用稳定一条。
- 现象与理由：
  - `reply-unverified` 场景写的是“一轮文字回复，回复之后跟一条条目消息”，没有过程。没有过程的轮次 `foldable` 为假（`outcomeStart=0`），“整轮收起后条目仍在回复下面”根本测不到。场景要带至少一次工具调用，才有整轮摘要可收起，e2e 才能点开再收起去验证。
  - 验收 28 的单元测试只写了“回复之后的自定义消息在结果区”，F1 与 F3 列的位置（分隔线之后、回复之前、两轮之间、运行中末尾、已结束但没有回复的轮次末尾）一个都没有。我跑出来的行为：回复之前、无回复的轮次末尾条目会收进过程；分隔线之后会把回复一起收进过程。
  - 29：缺“整轮的结果调用都被退回”“被退回的调用在流式中从 `streaming` 变成 `error`（`node` 变行）”“运行结束时没有结果的调用”三种用例。
  - 引用稳定只在“风险”里写“实施时核对一次”，没有验收；它影响打节拍时的重算，建议加一条用例：带条目的轮次在 `ctx` 整体替换后沿用同一个分组数组（`reuseTurnGroups`），条目对象每次新建时不沿用，用例断言的是 `buildTurn` 被调用的次数，需要一个计数点，计划没设计。
  - 26 与 27 的 DOM 测试断言时间文字，必须用本地时区构造（计划已写）；e2e 在 Lab 里的场景输入是固定的毫秒数，在不同时区的机器上渲染出不同的 `HH:mm`，截图基线与文字断言会按机器而变，场景里应传一个“与本地时区无关”的构造方式，或 e2e 不断言时间文字。
- Lab 登记本身可行：`defineSubjectFixture` 与 `index.dom.test.ts` 的四条检查（每个可挂载组件至少一个场景、组件名唯一、场景指向索引里的组件、输入能 JSON 往返）都满足；`lab-sources.ts` 的 `import.meta.glob("./**/*.vue")` 能收到根目录下的 `AgentSessionList.vue`。

### F11 建议 / 失败路径：条目组件抛错时整块换成错误卡片，过重，也没有利用 `text` 兜底

- 位置：计划关键设计 4 视图一节与验收 28。
- 现象：`RenderGuard` 的失败画面是一张 `CollapsibleCard`（状态为错误，标题“此内容无法显示”），为工具节点与详情设计；条目原本是淡色一行。而 `SystemMessageView.text` 的注释写了“没有登记渲染器时显示的正文，写成单独读也看得懂的一句”，恰好是兜底内容。`RenderGuard` 的 `failed` 一旦置位不会复位（`onErrorCaptured`），即使之后数据变好也不重试，这是已有行为，条目上也会照样出现。
- 建议改法：条目组件抛错时退回默认的淡色一行（用 `text`），并打开发诊断；验收 28 相应改成“抛错时退回默认一行”。或者给 `RenderGuard` 一个 `fallback` 插槽。
