# 可维护性与耦合审查：nb-agent-ui（w00019 t10）

范围：`packages/nb-agent-ui` 核心 `src/`、渲染层 `src/vue/`，以及 Lab 夹具 `packages/neuro-book/src/plugins/lab/web/fixtures/nb-agent-ui/`。只读；没有改仓库文件。

## 先给规模

`src/` 共 9744 行（含测试与文档）。最大的非测试文件：`conversation-turns.ts` 582、`AgentTurnBlock.vue` 543（脚本 117 / 模板 201 / 样式 225）、`AgentConversationComposer.vue` 539（脚本 256 / 模板 122 / 样式 161）、`AgentConversationTurn.vue` 496（脚本 174 / 模板 127 / 样式 195）、`AgentConversationView.vue` 496（脚本 201 / 模板 105 / 样式 190）、`types.ts` 423、`harness.ts` 387、`messages.ts` 322（有一版正在改，不看）。

逐个判断：
- `conversation-turns.ts`（582）：类型 30 到 145 行、分组与 key 146 到 245、块与思维链 247 到 470、状态与用量 471 到 575。职责是“消息到轮次”一件事，内部分段清楚，每段有注释，不必拆。真正的问题是它的行为要靠 `vue/builtin-tools.ts` 才能测，见第 1 条。
- `AgentTurnBlock.vue`：一个文件里有 7 种块和一整条思维链展开树，模板里同类行重复多份，见第 3 条。
- `AgentConversationTurn.vue`：脚本里混了用量格式化，见第 6 条。
- `AgentConversationComposer.vue`：脚本 256 行，职责是“草稿、发送门禁、附件、编辑器句柄”，t11 还要往里放就地编辑与提问向导，见第 12 条。
- `AgentConversationView.vue`：顶栏、历史分页、预览请求状态机、滚动，4 件事，各自不长；预览请求的 40 行状态机（`openPreview` 等）是最该独立的一块，但 t11 的弹窗与面板会和它并列，现在不动，留给第 4 条一并处理。

### 1. 内置工具登记放在渲染层，核心的分轮行为因此离不开 Vue，42 条纯逻辑测试被迫放进 Vitest
- 严重程度：重要
- 类别：核心与渲染层的分界、测试可维护性
- 位置：`src/vue/builtin-tools.ts:1-133`；`src/vue/conversation-turns.dom.test.ts:1-8`（29 条）；`src/vue/registry.dom.test.ts:3`（6 条中 3 条）；`src/index.ts:3-10`；`AGENTS.md` “边界”一节
- 现象：`buildTurns` 的行为（探查工具合并成工具组、改动文件统计、读写文件数）完全由登记项的 `category`、`groupPhrase`、`effects` 决定，而这些登记项在 `vue/builtin-tools.ts`。这个文件里真正需要 Vue 的只有 `detail`、`node` 两个字段（`AgentCommandDetail`、`AgentFileContentDetail`、`AgentFileDiffDetail`、`AgentTaskListNode` 四个 import），其余 100 多行是纯数据与纯函数。结果：测分轮必须 `import {builtinToolsContribution} from "./builtin-tools"`，Bun 加载不了 `.vue`，29 条分轮测试和 3 条注册表测试只能写成 `vue/*.dom.test.ts` 交给 Vitest。文件名带 `.dom` 却一个 DOM 都不碰，是被依赖拖过去的。
- 为什么是问题：包的卖点是“核心纯 TS，服务端、nb-story、以后的终端都能用分轮与适配器”（`src/index.ts` 模块头、`AGENTS.md`）。但没有内置登记，`buildTurns` 对 `read`、`edit` 一类工具只会得到通用渲染器，分轮结果与界面上看到的不同；而内置登记在渲染层，非 Vue 宿主要么拿不到，要么得引入整个 `./vue`。这条承诺现在只有 `entry.test.ts` 用空登记表验证，验证的是最弱的情形。对维护者：改分轮规则时要在两个测试运行器之间切换，核心测试与渲染测试的界线对不上目录。
- 建议改法：拆成两层，不新增概念。核心新增 `src/builtin-tools.ts`，导出不带组件的内置工具登记（`id`、`toolNames`、`category`、`icon`、`label`、`summary`、`groupPhrase`、`effects`、`presentation`），入口导出 `builtinToolsContribution`。渲染层 `vue/builtin-tools.ts` 缩成一张映射：
  ```ts
  const DETAIL = {read: AgentFileContentDetail, write: AgentFileDiffDetail, edit: AgentFileDiffDetail,
                  apply_patch: AgentFileDiffDetail, bash: AgentCommandDetail, execute_sql: AgentCommandDetail};
  const NODE = {task: AgentTaskListNode};
  export const builtinToolsContribution = withComponents(coreBuiltinTools, {detail: DETAIL, node: NODE});
  ```
  然后 `conversation-turns.dom.test.ts` 改名挪到 `src/conversation-turns.test.ts` 用 Bun 跑，`registry.dom.test.ts` 同理。`.dom.test.ts` 里只剩真要挂载的用例。这样 `vue/` 目录下的测试都真的需要 DOM，边界一眼可见。

### 2. 同一种工具的知识散在四个文件里，`fileDiffLines` 还按工具名绕过了注册表
- 严重程度：重要
- 类别：重复、耦合
- 位置：`src/vue/builtin-tools.ts:21-60,86-100`（summary 与 effects）；`src/tool-detail-lines.ts:30-56`（`call.name === "write"`、`"apply_patch"` 分支）；`src/tool-args.ts:61-101`（补丁与 hashline 解析）；`src/vue/tools/AgentFileDiffDetail.vue:13-16`（标题再算一遍）
- 现象：工具名（`write`、`edit`、`apply_patch`）与参数格式（nb-harness 的 `input` 补丁或 hashline、旧的 `{path, edits}`、Codex 的 `patch`）被四处各自判断。`AgentFileDiffDetail` 是三个工具共用的详情组件，它自己的 `label` 计算（`apply_patch` 取补丁里的路径，其余取 `path` 或 `editInputChanges`）与 `builtin-tools.ts` 里 `edit`、`apply_patch` 两项的 `summary` 一字不差；`tool-detail-lines.fileDiffLines` 再按 `call.name` 分派一次，同一件事第三次判断。`{path, edits}` 的旧写法在 `editEffects` 与 `fileDiffLines` 各处理一份。
- 为什么是问题：注册表的初衷是“新增一种工具只需登记一项”（`registry.ts` 模块头、`AgentConversationView.md` 开头）。现在新增一种改文件的工具（nb-story 或以后的 Agent 插件一定会有）要同时改四处，漏一处表现为摘要对、diff 空白、标题缺失这类不报错的错位。`tool-args.ts` 也名不副实：前 40 行是通用的参数读取，后 60 行是特定工具格式的解析，放在“小工具”文件里没人会想到去那里找。
- 建议改法：让登记项自己交出展示数据，组件不再认工具名。`ToolRendererEntry` 已经有 `effects(call)`（对文件的影响），再加一个可选 `diff?: (call) => CodeLine[]`，内置的 write、edit、apply_patch 各给自己的实现；`AgentFileDiffDetail` 改为 `entry.diff(call)`，标题用 `entry.summary(call)`，`tool-detail-lines.ts` 里的工具名分支随之搬进对应登记项。补丁与 hashline 解析从 `tool-args.ts` 挪到新的核心 `builtin-tools.ts` 旁边（与第 1 条同一次改动），`tool-args.ts` 只留 `argString`、`argArray`、`argNumber`、`countLines`。

### 3. `AgentTurnBlock.vue` 一个文件装了 7 种块，思维链模板里同类行重复多份
- 严重程度：重要
- 类别：模块大小与职责、重复
- 位置：`src/vue/stream/AgentTurnBlock.vue:117-319`（模板）
- 现象：模板是一条 `v-if` 链：`chain`（约 120 行）、`content`、`node`、`notice`、`divider`、`steer`、`error`。其中最大的 `chain` 分支里：

  - 思考行写了 2 份（工具组内、顶层），外加系统提示词行第 3 份（结构相同，只是 label 与展开条件不同）；

  - `<AgentMarkdown … :services="props.services" @action="emit('action', $event)" @preview-image="emit('preview-image', $event)">` 在同一文件里出现 8 次；
  - `openItems[x]` / `setOpen(x, …)` 配对出现 20 多次。
  样式 225 行里，只属于思维链的约 90 行与只属于其他块的约 130 行混在同一个 scoped 块里。
- 为什么是问题：t11 要在这里补提问留痕、模式切换、Workflow 等“专用渲染器”（`AgentConversationView.md` 已知偏差），都会往这条 `v-if` 链里加分支。现在改一处“工具行长什么样”要改 3 处，漏一处时只有展开某种组合才看得到。`AgentRawView.vue` 里又有第 4、5 份类似的行（`:112-155`）。

  2. 在 `stream/` 里加一个内部小组件 `AgentStepRow`（包住 `CollapsibleRow`，内置 `running-label`，接收一个步骤对象：`{kind: "tool" | "thinking" | "prompt", …}`），三种行各一份模板变一份；
  3. `openItems` 提成 `useOpenSet()` 小函数（返回 `isOpen(id)`、`set(id, open)`），`AgentRawView` 也用；
  4. Markdown 的转发见第 4 条。
  按 `src/vue/README.md` 的规则，`AgentChainBlock`、`AgentStepRow` 属于 `stream/`，依赖方向不变。

### 4. 同一对事件在 View、Turn、TurnBlock 三层里逐层手工转发，还把整袋 `services` 传给只需要一个函数的 Markdown
- 严重程度：重要
- 类别：耦合、概念数
- 位置：`AgentConversationView.vue:252-269`；`AgentConversationTurn.vue`（`emit('preview-image', $event)` 4 处、`emit('action', $event)` 4 处）；`AgentTurnBlock.vue`（各 8 处）；`AgentRawView.vue`、`AgentConversationComposer.vue`；`parts/AgentMarkdown.vue:6-15`
- 现象：从 `AgentConversationView` 到 `AgentConversationTurn` 到 `AgentTurnBlock` 到 `AgentMarkdown`/`AgentUserContent`，每层都要写 `@action="emit('action', $event)" @preview-image="emit('preview-image', $event)"`。`grep -F "emit('preview-image', \$event)"` 在渲染层命中 13 处，`emit('action', \$event)` 16 处。`preview-image` 这条事件只有顶层 `AgentConversationView` 一个消费者（`openPreview`），中间层纯转发。`AgentMarkdown` 的属性是整个 `services: AgentConversationServices`，实际只读了 `services.resolveMarkdownAsset`。`ctx`、`services`、`registry` 这“三件套”在 5 个组件（View、Turn、TurnBlock、RawView、Composer）的签名里全套出现，`AgentToolDetail` 带 ctx 与 registry，`AgentTaskListNode` 带 ctx，`AgentMarkdown` 带 services；`ToolDetailProps` 里的 ctx 只有任务清单要用，3 个详情组件的文档写着“ctx 必填；本组件不使用”。
- 为什么是问题：t11 要加的状态栏、待处理区、提问向导、面板都会再造新的层，每多一层这对转发就多一份；漏转发时表现为“点了没反应”，不报错。`preview-image` 的类型在各文档里还写得不一样（第 9 条）。`AgentMarkdown` 的签名让读者以为它会用 `services` 的别的东西，单独挂载时被迫构造整个 `services`。
- 建议改法（选概念更少的一条）：把“预览图片”收进 `action` 体系的内部成员，`AgentConversationView` 在 `@action` 里拦截它，不再转给宿主：`AgentViewAction` 增加内部类型 `{type: "image.preview"; request: PreviewImageRequest}`（或在渲染层定义一个只在视图内流通的扩展），于是 `preview-image` 事件、`PreviewImageRequest` 在各组件 emits 里的声明、各文档里的那一行全部消失，剩下 `action` 一条通道。再让 `AgentMarkdown` 只收 `resolveAsset?: MarkdownAssetResolver`，不收 `services`。若不想让内部动作混进公开类型，退一步用 `provide/inject` 注入一个 `previewImage(request)` 函数（与 `provideAgentView` 同层），也能去掉一整条转发。

### 7. `AgentChainSummary` 的展开事件叫 `toggle`，与同包其余折叠零件的 `update:expanded` 不一致
- 严重程度：建议
- 类别：API 一致性、概念数
- 位置：`src/vue/stream/AgentChainSummary.vue:15-17`；`AgentChainSummary.md` “数据”；`AgentTurnBlock.vue:122`（`@toggle="setOpen(…, $event)"`）；Lab 夹具 `index.ts` 里 `events: ["toggle"], writeBack: {toggle: {layer: "props", key: "expanded"}}`
- 现象：已定的折叠约定是 `expanded` 加 `update:expanded`（nb-ui 的 `Collapsible`、`CollapsibleRow`、`CollapsibleCard`，本轮刚统一过）。`AgentChainSummary` 仍是 `expanded` 属性加 `toggle(expanded)` 事件，同一个 `TurnBlock` 里的两种折叠零件要用两种写法绑定（`@toggle` 与 `@update:expanded`）。`.md` 的开头还特意写了“受控展开状态”，说明它本就是 v-model 形状。
- 为什么是问题：读者要多记一条例外；t11 加顶栏下拉、待处理区的折叠项时容易照着最近的零件抄成 `toggle`，Lab 的 `writeBack` 也要为它单独写一份映射。
- 建议改法：事件改名 `update:expanded`，同时改 `.md`、`AgentTurnBlock`、`AgentConversationTurn` 里的两处绑定与 Lab 夹具的 `events`/`writeBack`（`writeBack` 可省，同一个约定 Lab 已有通用处理时直接删）。

### 8. `state:inject` 出现在 20 个组件上，而它们要的只是“当前语言”；缺提供方时静默退回中文
- 严重程度：建议
- 类别：耦合、可用性
- 位置：`src/vue/host.ts:30-86`；23 个组件的同名 `.md` 标签；`src/vue/AgentConversationView.md` “隐藏通道理由”
- 现象：逐个核对标签与实现，23 个组件里 20 个带 `state:inject`（唯独三个 `fallback/` 组件是空标签或 `state:local`）。其中 `AgentMarkdown`、`AgentUserContent`、`AgentConversationComposer` 三个还取渲染组件，其余 17 个只为取一个 `t()`。取不到提供方时 `FALLBACK_HOST` 默认给 `zh-CN`、不给任何提示。Lab 为了单独挂零件，要 `host.ts` 里 `provideLabMarkdown`、`provideLabAgentHost`、`withAgentHost`、`agentSubject` 四个辅助函数，Lab 的每个零件场景都经这一层。
- 为什么是问题：耦合度按隐藏通道数量计，这些是同一个 key 的 20 个读取点，实际风险集中在一件事：零件被挂在没有 `provideAgentView` 的地方时，英文界面悄悄变成中文（宿主单独挂 `AgentTurnBlock`，或 nb-story 只挂输入框，都会遇到）。`.md` 只写了“语言与渲染组件经 `provideAgentView` 交给子组件（`state:inject`）”，没有写“漏了会怎样”。
- 建议改法：先不改架构（用环境注入承载界面语言是通行做法，`nb-form` 的 scope 也是这样）；做两处小改：开发模式下 `useAgentText` 在没有提供方时 `console.warn` 一次（写明组件名与“请先 `provideAgentView`”），生产不影响；各 各 `.md` 的 `state:inject` 一行统一补一句“未提供时按中文显示”。如果以后想进一步降耦合，对 `AgentDeliveryNotice`、`AgentChainSummary`、`AgentMessageActions` 这类只有两三个固定文案的叶子，可以改成属性传入文案。

### 9. `OriginalImagePreviewDialog` 是通用零件却放在本包，标签与实现对不上，文档还留着旧应用的描述
- 严重程度：建议
