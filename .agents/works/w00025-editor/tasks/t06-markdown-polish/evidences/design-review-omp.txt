### 1. 分块所依赖的 `raw` 无损拼接不变量不成立，重复定义会让后续来源偏移整体错位

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`plan.md` 第 2 节，行 39–41；方言 Spec 输出 1、2。
- **现象**：计划断言顶层词法单元的 `raw` 依次拼接等于规范化输入。实测 `[a]: /first

[a]: /second

正文[a]` 只得到第一个 `def` 和最后的 `paragraph`，第二个定义整段没有词法单元。按 `raw.length` 累加得到的“正文”起点实际落在被吞掉的第二个定义里。
- **为什么是问题**：重复引用定义是合法 Markdown（先定义者生效），不是可以拒绝的坏输入。原始切片之间补“间隔”也救不了：词法单元不提供实际起点，计划的游标已经错位。另一个缺口是 `marked` 还把单独 `` 变成 `
`，计划偏移表只覆盖 CRLF。这会直接破坏“不编辑不改字节”及后续块的来源。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/source-probe.ts`。输出“重复引用定义”的 `rawEqual:false`；两个 token 的 raw 分别为 `[a]: /first

` 和 `正文[a]`；“单回车”同样为 `rawEqual:false`。依赖源码 `node_modules/marked/lib/marked.esm.js` 的 `blockTokens` 在 `tokens.links[tag]` 已存在时不 push 第二个 `def`。
- **建议改法**：先确定能够记录消费区间的词法适配层，保留所有被词法器消费但不产出 token 的源区间；偏移表覆盖词法器全部换行归一化。用重复、大小写/空白等价标签、定义与正文相同文字及 CRLF 混用的输入验证真实起点，不只检查普通样例的 raw 拼接。

### 2. 无节点的源块在 `Origins` 中没有位置，引用定义无法随文档写回

- **严重程度**：阻断；**类别**：正确性。
- **位置**：`plan.md` 第 3 节行 45、49，第 4 节行 53–56；方言 Spec 输出 1、2。
- **现象**：计划明确让 `def` 不产出节点，却只保存“顶层节点对象 → 来源”，写回也只遍历当前顶层节点。独立的 `[a]: /first` 因而没有任何 owner；位于开头、中间、结尾的定义都不能通过所定义的数据结构找回。只有定义、没有正文的文件还要求编辑器填充空段落，计划没有说明它与零节点原文的关系。
- **为什么是问题**：即使修好第 1 条的偏移，这个模型仍不能表达全部原文。定义行不是可以丢掉的空白间隔；丢掉后所有引用式链接失去目标，直接违反输出 2 对定义行独立保留的承诺。删除或移动相邻正文也不能被解释成删除定义。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/editor-probe.ts`；真实 `MarkdownManager.parse('[a]: /first\n')` 返回 `{type:'doc',content:[]}`。对照计划 `ReadResult` 只有 prefix/doc/origins，没有独立源块序列或零节点块的附着规则。
- **建议改法**：把完整有序源单元（含零节点定义、空白、尾部）作为一等数据；节点来源只是该序列的索引。定义明确的插入/删除/移动关联规则，补“仅定义文件”“删除定义两侧正文”“移动引用而保留定义”等测试。

### 3. 逐块 `eq` 不能证明拼接后的文档正确，删除隔断段会静默合并列表

- **严重程度**：阻断；**类别**：正确性。
- **位置**：`plan.md` 第 4 节行 54–59；方言 Spec 输出 3。
- **现象**：真实编辑器打开 `- 甲\n\n桥\n\n- 乙`，用公开 `deleteRange` 删除“桥”段后，文档里保留两个独立的 bulletList，两个节点对象均未变。计划因此复用两块原文、在它们之间写一个空行，得到 `- 甲\n\n- 乙`；重新打开却是一份含两个项的列表，`eq:false`。两个块单独校验都能通过，甚至按计划根本不校验这两块。
- **为什么是问题**：块的含义不仅取决于块内文字；相邻列表的连续性、引用定义的生效范围及普通文字与定义的结合都有文档上下文。第 4 节“现在只有一种上下文依赖：分截批注”不成立。读回防线遗漏整个拼接文档，允许静默改变结构，而不是按输出 3 拒绝。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/editor-probe.ts` 的“删除隔断段”：`reused:[true,true]`、当前文档 2 个 bulletList、读回 1 个、`eq:false`。`source-probe.ts` 也证明两个孤立 list 块经一个空行拼接后成为一个 list。实验使用真实 Tiptap Editor、公开编辑命令和真实解析器；拼接文字按计划规则推导，尚无新 codec 实现。
- **建议改法**：把块边界与共享定义纳入上下文判定；拼接完成后至少做整篇语义校验。必须定义相邻独立列表的可表示写法（或显式返回 unrepresentable），不能把空行当作普遍安全的分隔符。增加删除隔断、增块、移动块、重复引用定义优先级变化的真实编辑测试。

### 4. 解析后再统一解实体会二次解码，把作者的字面实体改成另一个字符

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md` 第 3 节行 48；依赖 `MarkdownManager.ts:706–717,900–903`。
- **现象**：当前依赖已经在文字 token 上调用 `decodeHtmlEntities`。实测 `甲&amp;amp;乙` 读成文字 `甲&amp;乙`，这是正确的一层解码；再执行计划的“解析后在正文文字节点里解码 HTML 实体”会把它变成 `甲&乙`。转义产生的字面 `&nbsp;` 也不能与源实体混为一谈。
- **为什么是问题**：这是打开文件时就改变正文语义，不是写法规范化。节点仍然合 schema，后续写出/读回对错误的树自洽，四条往返性质也不能自动纠正。旧实验看到的 `&nbsp;` 问题不能推出“对所有文字再解一次”安全。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/parse-probe.ts` 的“实体已解码一层”；依赖源码上述位置。另有 `Paragraph.parseMarkdown` 把单独的 `&nbsp;` 或 U+00A0 当作空段落（`extension-paragraph/src/paragraph.ts:77–94`），与 Spec 输出 4 要保留 U+00A0 文字还有冲突，迁移原段落扩展时也要处理。
- **建议改法**：只在原始 token → 文字的边界解码一次，保留 escape token 的字面语义；明确 NBSP 与空段落的区分。增加字面 `&amp;`、`&nbsp;`、实体表达的 NBSP、单独 NBSP 段落以及代码里的实体的独立期望树断言。

### 5. “在块后附全篇定义行”会把引用定义注入未闭合代码块的正文

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md` 第 3 节行 45，S1 的指定做法；方言 Spec 输出 21、读入不会失败。
- **现象**：整篇 `[a]: /url\n\n```\n代码` 的代码内容只有“代码”；把该 code 块单独取出并附上全篇定义，解析 ` ```\n代码\n\n[a]: /url` 后，代码内容变成“代码\n\n[a]: /url”。两棵树都合 schema。
- **为什么是问题**：CommonMark 允许文件末尾的未闭围栏；代码块必须按输出 21 保留文字而不是注入全篇链接数据。这里不是来源偏移问题，修好第 1 条仍会发生。附定义也不是一个可靠的 S1 临时接口，后续切片会基于错误的 read 合同开发。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/parse-probe.ts`，对照“整篇未闭围栏”与“按计划逐块附定义”，两者 `schemaCheck` 都是“通过”。使用真实 `MarkdownManager.parse`，没有访问私有方法。
- **建议改法**：整篇 lex 一次，沿用该 lexer 的 links 与既有 token 解析；或明确实现公开的 links 注入适配，不向正文拼接任何定义文字。把未闭围栏、可吞到 EOF 的 HTML/原样片段、定义引用嵌套在列表/方言中的情况纳入 S1。

### 6. 把写法属性也纳入原始 `eq`，与新建节点及降级写法冲突

- **严重程度**：重要；**类别**：合同。
- **位置**：`plan.md` 第 4 节行 59，第 6 节行 92–107，第 9 节行 139；方言 Spec 输出 2、3、10。
- **现象**：新建节点的 `markdown` 属性为空，解析规范写法后却从 raw 得到非空属性。按计划直译的粗体最小模型，新建 `bold(markdown:null)` 写出 `**甲**`，再读是 `bold(markdown:'**')`，语义完全一样但 `eq:false`。退到 HTML 时，原 Markdown 写法属性与 HTML 写法同样不一致；有限的 3 种候选会全部失败，而不是解决真实语义问题。
- **为什么是问题**：这会让正常新建格式被报 unrepresentable，并使随机往返“无写法属性的新文档，读回必须 eq”按字面无法成立。Spec 输出 3 允许在必要时更换写法，输出 2 要尽量保持写法；不能用同一原始属性相等判定同时实现这两件事。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/schema-probe.ts` 的“新建写法属性eq”输出 `eq:false`。该部分是按计划添加一个写法属性的 throwaway 模型，使用真实 Schema 与 MarkdownManager；不是尚未实现 codec 的回归结论。`prosemirror-model/src/node.ts:118–133` 明确将全部属性纳入 eq。
- **建议改法**：先定义语义相等与写法保留两套独立判据，或定义规范写法属性的唯一归一化（含 null 的含义）。降级成功必须比较语义；写法偏离只能发生在明确允许的降级场景。专测新建、沿用块内写法、HTML 降级、标记顺序及连续空文字归一化，不能删除真实文字/格式来让 eq 通过。

### 7. 无 DOM 编解码器依赖的 HTML 解析仍然需要 DOM，测试与浏览器会读出不同的树

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md` 第 1 节行 34，第 4 节行 59，第 6 节行 114、116；`MarkdownManager.ts:939–959`。
- **现象**：保留的解析器遇到已知 HTML 时通过 `generateJSON` 和扩展的 parseHTML 解析；没有 window.DOMParser 则把 HTML 当字面文字。实际 `parse('<strong>甲</strong>')` 在纯 Bun 中是含标签的普通文字，在 happy-dom 的相同扩展组中是粗体“甲”。计划自己的 HTML 降级恰好依赖这条路径。
- **为什么是问题**：第 1 节“不依赖 DOM、bun test 直接测”的架构边界目前不成立。单纯移走 Markdown 扩展、不用 getMarkdown，不会改变 MarkdownManager 的 HTML 路径。服务端/未来字数统计与浏览器可能理解不同，降级和语料测试也不能证明真实行为一致。
- **如何核实**：分别运行 `bun packages/neuro-book/zz-review-lab/omp/parse-probe.ts` 的“HTML粗体无DOM”，以及 `bun packages/neuro-book/zz-review-lab/omp/editor-probe.ts` 中 `<strong>甲</strong>` 的“读入”。依赖代码明确判断 DOMParser。当前 HtmlFallback 也明确把 strong/em/del/br 等交回该 DOM 路径。
- **建议改法**：明确为全部允许的 HTML 形式提供无 DOM 的 tokenizer/parseMarkdown 规则，覆盖残片与 HTML mark 嵌套；或收回无 DOM 承诺并选定一致的解析环境。不能让 Bun 的 fallback 与浏览器的真实解析器分叉后只测前者。

### 8. 表格仍允许 Enter 产生多个段落，写成 `<br>` 后严格校验必然拒绝正常保存

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md` 第 5 节行 66，第 4 节行 59，S2/S4；方言 Spec 输出 20；`conversion.md` 发现 5。
- **现象**：真实 TableKit 中在 `ab` 中间执行 Enter 对应的 splitBlock，单元格变成两个 paragraph。计划把它写成 `a<br>b`，读回却是一个 paragraph 里的 hardBreak。两棵树都合 schema，但不 eq；三种转义/HTML 强调降级都不能改变这个结构差异。
- **为什么是问题**：这把 conversion.md 已发现的“正常回车写出 U+001F”换成“正常回车导致 unrepresentable”，没有实现 Spec 的单元格换行合同。计划没有改 tableCell 的 block+ 内容约束，也没有给 Enter 定义单元格专用命令。合并单元格等 TableKit 可表达、GFM 不可表达的状态也没有规定入口限制。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/render-probe.ts` 的“表格单元格回车”；使用真实 Editor、实际表格扩展、公开 splitBlock 命令，输出 current 的 cell 含 2 个段落、reread 含 1 个段落，`eq:false`。
- **建议改法**：在编辑器接入前把表格限制为方言可表达的模型：单元格 Enter 产生 hardBreak，或在事务内执行有明确定义的规范化。明确 colspan/rowspan、列宽等不可写属性的处理。验收用真实回车和保存重开，而不是只构造一份本来就只有 hardBreak 的表格节点。

### 9. 原样片段只有规范化后的 raw，没有嵌套来源，编辑父块会改掉片段里的 CRLF

- **严重程度**：重要；**类别**：不变量。
- **位置**：`plan.md` 第 2–3 节行 39–49，第 6 节行 116；方言 Spec 输出 9。
- **现象**：原文 `甲<unknown>内一\r\n内二</unknown>乙` 中的行内原样片段，经现有词法器读入后属性已经是 `<unknown>内一\n内二</unknown>`。计划只为顶层节点记录原文切片，迁入 rawInline 后仍只有 `{raw}`。在甲或乙处加字使父段落重新写出，LF 占多数的文件会把这个片段内部 CRLF 改成 LF。嵌在列表、引用、块批注里的 rawBlock 也有同一层级问题。
- **为什么是问题**：输出 9 承诺原样内容的字节不变，不限于父块完全未编辑时。顶层整体复用只能遮住问题；读回 eq 比较的是早已规范化的属性，也发现不了原样数据被改。性质 3 只断言“其它块”不变，没有保护被编辑块内部的原样区间。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/render-probe.ts` 的“行内原样片段换行”，输入的 raw CRLF 与解析属性 LF 的差异已观察到。新 writer 尚未实现，父块写回的后果是按计划的数据模型与主导换行规则推断。
- **建议改法**：原样节点必须直接持有原始源字节/字符串切片，或具有可映射到原文的嵌套消费区间；不能从规范化 token.raw 重建。测试混合换行的原样片段，分别编辑它之前/之后的文字及外层容器，断言片段内部逐字节不变。

### 10. 最小转义遗漏 GFM 裸自动链接，完全转义兜底会接受明显不最小的结果

- **严重程度**：重要；**类别**：合同。
- **位置**：`plan.md` 第 5 节行 68，第 4 节行 59；方言 Spec 输出 4。
- **现象**：转义清单没有裸网址/邮箱的起始判定（也没列新 raw 数学语法的 `$`）。已有普通文字 `www.example.com`，最小路径不转义任何字符，却会读成 link；下一步“每个 Markdown 标点都转义”写成 `www\.example\.com`，语义校验能通过，但第二个点的转义完全多余。只转义第一个点 `www\.example.com` 已足够。
- **为什么是问题**：读回 eq 只能判断语义，不可能证明“最小”。把完全转义候选直接接受，违反输出 4，并会在包含大量 `[注]`、`a_b_c`、标点的同一段里重新制造 conversion.md 的过度转义问题。新 raw 语法也必须进入同一逃逸判据。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/render-probe.ts` 的“自动链接分词”：无转义是 link；只转义首个点与转义全部点都得到同样的普通文字。该实验验证解析行为，未实现新的转义器。
- **建议改法**：补齐裸 URL/邮箱、数学/HTML/方言等所有会把文字转成节点的语法上下文；让完全转义只作诊断候选，成功后逐项缩减到必要转义，或者明确修改合同为非最小的安全转义。增加输出字符串的独立断言，不能只断言读回树相等。

### 11. 重叠批注要求同名标签嵌套，但现有 tokenizer 与缓存都不支持，改 `excludes` 不够

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md` 第 6 节行 113，第 5 节行 67；方言 Spec 输出 11、场景 7；`markdown-workbench.ts:46–48`、`Comment.ts:358,488–489`。
- **现象**：行内和块批注的 tokenizer 都在第一个 `</comment>` 处终止，没有同名嵌套计数。把 Comment 改为 `excludes:''` 后，`c1` 内再嵌一个 `c2`，实际只得到 c1；c2 的开标签变 rawInline，c1 的尾部正文跑出范围。两个块批注嵌套也被截断。现有 collectComments 还只 `find` 第一枚 comment mark，重叠文字上的第二枚不会进入缓存。
- **为什么是问题**：写出器“保证标签正确嵌套”不等于读入器能解析这些嵌套；schema 允许重叠也不等于缓存能收集。特别是块批注内的行内批注，与外层使用同一个标签名，场景 7 直接依赖这条链路。原样兜底只能保标签，不能履行读回仍是两条批注的合同。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/contract-probe.ts`：按计划扩展 `excludes:''`，通过真实 MarkdownManager 与挂载的 Editor schema 读取两组嵌套样例，comments 都只有外层 1 条。源码 `findCommentMark` 明确只返回第一枚。
- **建议改法**：将同名标签的平衡扫描、块/行内混合嵌套、每个节点上多枚 comment mark 的收集列为 S3 的明确工作，而不是只迁移缓存。补交叉覆盖的两条/三条批注、块内行内、嵌套块、硬换行与行内原样节点上的批注范围测试。

### 12. 同 id 不同 body 的分截不能按 id 判定“第一截”，后续无 body 截的归属也未定义

- **严重程度**：重要；**类别**：合同。
- **位置**：方言 Spec 输出 11 的“残缺的分截”；`plan.md` 第 4 节行 58、第 6 节行 113。
- **现象**：合法输入依次为 `c1/body=A`、`c1/body=B`、`c1/无body`。Spec 同时要求“同 id 合成一条”与“不同 body 各自成条”，却没有说明第三截属于 A、B、两者或空意见。计划写出前只按 id 算一个“第一截”，无法同时保存 A 和 B 两条批注及各自 body。删除 A 的首截、移动 B 的首截时问题继续扩大。
- **为什么是问题**：这不是实现可以自行选择的属性归一化；不同选择改变正文归属和用户意见。每文件 id 又是持久身份，不能在没定规则时悄悄合并、丢 body 或改所有 id。逐块读回需要的批注上下文也不能只是一张 id→首块表。
- **如何核实**：按上述 3 截逐条代入输出 11 与计划第 4 节；它们要求同一 id 同时具有 2 个独立意见，却仅定义 1 个首截。该发现是合同推演，没有把现有实现当作目标实现。
- **建议改法**：先定义冲突输入的分组与延续规则、内部唯一身份及写回如何保持原 id；写出上下文按“逻辑批注身份”而非裸 id 管理。用上述 3 截及删除/重排变体给出唯一预期结果，补入 Spec 后再实现。

### 13. `reload` 的事务会触发自动链接，按位置把新原文绑定到当前节点的前提不成立

- **严重程度**：重要；**类别**：不变量。
- **位置**：`plan.md` 第 7 节行 122；`MarkdownControl.vue:112–137`；`extension-link/src/helpers/autolink.ts:52–72,89–97,167–173`。
- **现象**：原文 `前 www\.example.com\n\n尾` 中网址是普通文字。同步新原文 `前改 www\.example.com\n\n尾改`，按现有 findDiffStart/End + replace + addToHistory:false 重载后，Link 的 appendTransaction 会给第一段网址加上 link mark；当前文档与新读入文档 `eq:false`。`loading` 只挡控件的 onUpdate，不挡插件；addToHistory:false 也不阻止自动链接。
- **为什么是问题**：计划“留下来的旧节点与新读入节点结构相同”不是事务后的保证。把解析来源按位置强行赋给被插件改过的节点，之后会复用不包含该 mark 的原文，绕开读回检查；显示、下一次保存、另一个组的来源表会不一致。新增会改变结构的插件还可能改变顶层节点数量。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/contract-probe.ts`，Editor 实际挂载到 happy-dom、启用真实扩展插件、使用当前 reload 的同一组公开事务，输出“重载后相等”的 `eq:false`，actual 比 expected 多一枚 link mark。不是伪造 appendTransaction 顺序。
- **建议改法**：导入/外部同步事务明确关闭输入辅助变换（至少 preventAutolink），再在整个 applyTransaction 完成后检查 doc 与解析结果一致；不一致时不能授予原文复用资格。来源重建必须基于最终节点及可证明对应的消费组，并测两个组、外部只改写法、同步后本地撤销重做与插件追加事务。

### 14. `refuse` 只传原因，未裁决模型却只存 Markdown 字符串，关闭与终态恢复没有可用合同

- **严重程度**：重要；**类别**：合同。
- **位置**：`plan.md` 第 7–8 节行 121、125–129、文档改动表行 148；editor 输出 4、13、21、22；`documents/store.ts:139,700–727,775–780`、`area.ts:581–584`。
- **现象**：现有未裁决输入是文档 store 的 `Map<token,string>`，保存阻止、离开询问、rescue 都以它为准；新 refuse 只有 `{code,block}`，根本没有候选正文。计划只列 area.ts/contracts.ts，未定义 store 如何持有这种输入。关闭选择“保存”还会无条件调用 keep-view，再保存；这与新类型“只能采用当前正文”冲突。终态页救援接口只返回字符串，拿不到未提交的 PM 文档。
- **为什么是问题**：如果只在 area 里记标志，store.save/rescue 不会看到它；如果沿用字符串候选放空串/旧正文，keep-view 会错误覆盖或丢掉真正输入。即使成功挡住保存，服务端重启时尚未编码的文字与格式仍只活在控件里，违反 editor 输出 22。计划“之后 accepted commit 清掉”还需要清理原有冲突候选，而不是只清一个 UI 标志。
- **如何核实**：逐项核对上述真实公开接口、store 的 candidates/resolve/saveNow/rescue 以及 closeOne；当前所有通路都要求候选是字符串，新 refuse 并无可用实现。这里没有新实现可运行，结论为接口与状态机审查。
- **建议改法**：给未裁决输入定义明确的判别联合，至少区分修订冲突与不可编码输入；由 document store 统一持有阻止保存的状态和可恢复内容/取回入口。定义关闭“保存”、采用当前正文、修正后提交、视图销毁、其它组更新及终态抢救的状态转换；增加这些入口的行为测试，不只测提示条。

### 15. 字数的新合同跨前后端共用，计划只补单测，未给出可复用的方言解析边界

- **严重程度**：重要；**类别**：合同。
- **位置**：方言 Spec“副作用与数据”行 158；`plan.md` 第 1、6 节与验收映射行 175；`src/shared/word-count.ts:15–24`。
- **现象**：当前 countWords 直接数源文字，`<comment body="意见">正文</comment>`、ruby、bilingual 三例实测都是 7，按新合同应是 2；未知 HTML 原样片段实测 6，新合同应是 0。它同时被浏览器状态栏与项目进程 `plugins/projects/project/stats-tracker.ts:215,338` 使用。新编解码器和全部 syntax 模块却放在 editor/web，含 NodeView/DOM 依赖；计划对计数只写“单测补样例”，没有共享层的改动或语法使用边界。
- **为什么是问题**：只改编辑器的 PM 文本统计不能覆盖源码模式与书架统计；让 shared/项目进程反向导入 editor/web 又破坏现有运行位置边界。若另写一套正则剥标签，原样内容、分截批注、代码中的字面标签会再次与方言解析分叉。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/scale-probe.ts` 的 4 条字数输出；源码调用位置经搜索核实（LSP references 不可用，工具返回 No language server found）。这是新合同与现有共享算法的差距，不冒称为 t06 已实现回归。
- **建议改法**：在计划中明确共享的无 DOM 语法/正文提取层和 owner，使浏览器与项目进程使用同一解释；视图扩展与 NodeView 留在 web。增加真实共享函数的独立数值断言，含代码里的方言标签、未知 HTML 内文字、脚注定义、链接地址及 body/注音/译文。

### 16. 四条往返性质不能验证“读对了”，验收映射仍漏掉可观察行为

- **严重程度**：重要；**类别**：测试。
- **位置**：`plan.md` 第 9 节行 133–141、验收映射行 167–175、未验证边界行 182。
- **现象**：四条性质全以被测 reader 自己产出的树作为基准。把所有脚注读成普通链接、把未知 HTML 全部当正文、把提示块读成普通引用、或把某种格式读成原样块，都可以保持字节、自洽往返并通过 schema 检查；“每条输出至少一份 .md”并不增加语义 oracle。随机生成器还没有表格、任务项、提示块或 raw 节点。只在现有块里插字不会触发删除/移动隔断块、批注首截迁移、空段落转换和外部同步。
- **为什么是问题**：conversion.md 的发现 1/6/7 涉及首次读取的语义，不能只看幂等；发现 5 需要真实表格回车。现有 markdown-dialect.test.ts 中针对节点类型、body、块内容的明确断言如果只“搬成语料”，会失去覆盖。映射还把输出 12 的“加格式不能进入注音”、23 的折叠交互等界面行为映到纯语料；场景 6 既列成 e2e，又在行 182 声明分截只在格式层与语料验证，且本 Task 不提供新建批注 UI，入口没有定义。
- **如何核实**：逐项对照四条性质的断言对象与上述输出；本次实际观察到“定义被吞”“实体二次解码风险”“表格 2 段变 1 段”“自动链接改变重载树”，其中多项均合 schema。实验脚本分别为 source/parse/render/contract-probe.ts。
- **建议改法**：保留每类语法的独立期望文字、节点、标记、属性和最小输出断言；再加往返性质，不以其替代。生成器覆盖整个允许 schema，并增加真实 Editor 的插入/删除/移动/撤销/同步操作序列。给每个 UI 判据指定 DOM/Lab/产品 e2e 的真实入口；将明确延期的行为从本次完成判据中准确划出，保留 planned 标记，而不是宣称纯语料已覆盖。

### 17. 沿用宽容规范化的逐开标签向后搜索，十万字符异常输入已造成 1.3 秒同步阻塞

- **严重程度**：重要；**类别**：性能。
- **位置**：`plan.md` 第 2 节行 39、性能验证行 181；`markdown-workbench.ts:125–158,189–201`。
- **现象**：输入 8000 行 `正文<comment>` 加最后一行闭标签，共 96013 个字符，当前规范化同步耗时 1298.59 ms。1000/2000/4000 行分别为 25.45/80.96/305.80 ms。每个开标签都重新向后找闭标签，同时对 lines 做 splice，数量翻倍接近四倍耗时。计划明确整体沿用该判据，且新 reader 可能在保存校验中再次调用它。
- **为什么是问题**：输出 9 要接纳残缺/无法表达的文件；异常文件不能用“正常章节平均更快”覆盖。同步主线程冻结不是变块写出减少序列化就能解决。另一个可量化放大是 S1 每块附全篇定义：2500 个正文块、50000 字符的定义区，仅附加部分就需解析 125000000 字符，未计正文。
- **如何核实**：`bun packages/neuro-book/zz-review-lab/omp/scale-probe.ts`；上述数字是本次单轮实测，不是正式 p95 基准。新 codec 尚未存在，未测它的端到端耗时。源码的双重扫描证明复杂度来源。
- **建议改法**：宽容扫描改为一次线性配对/记录插入点，最后统一构造结果；复用整篇链接表而非复制定义文本。性能验收同时包含十万字符的一般章节、多块/多定义、未闭合与密集标签输入，分别记录 read、write、reload 的主线程耗时和明确上限。

### 18. S3 删除旧模块早于 S4 迁移直接调用方，该片无法单独通过 typecheck

- **严重程度**：建议；**类别**：代码质量。

- **为什么是问题**：按字面逐片提交会留下不能构建的切片，也会使 S3 的“转换核心审查”审到一个尚未连通的状态；这不是开发者需要裁决的产品取舍。

### 19. 新路径语义已确定，但旧文件的 project-relative 链接兼容边界没有写出来
