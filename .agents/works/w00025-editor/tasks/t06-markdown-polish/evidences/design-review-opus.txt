### 1. 编解码器是模块级单例、自带 schema，但 Tiptap 编辑器每个实例自己建 schema，读出的文档放不进编辑器

- **严重程度**：阻断；**类别**：正确性 / 合同
- **位置**：plan.md 第 1 节“编解码器按扩展组建一次、全应用共用（模块级单例）”、`interface MarkdownCodec { readonly schema }`；第 7 节 `load`“用结果的 `doc` 建 `EditorState`”。
- **现象**：`@tiptap/core` 的 `Editor` 不接受外部 schema，`ExtensionManager` 构造时 `this.schema = getSchemaByResolvedExtensions(this.extensions, editor)`（`node_modules/@tiptap/core/src/ExtensionManager.ts:52`），每个编辑器实例（每个编辑组一个）各有一份 schema。编解码器单例的 `doc` 属于另一份 schema：节点类型对象不同，ProseMirror 的内容检查按类型对象比较。
- **为什么是问题**：照字面实现，`EditorState.create({doc: codec.read(...).doc})` 得到的 state 的 schema 是编解码器的，而 Tiptap 的命令、输入规则、键位（`wrapIn(this.type)`、`setNode`、`splitListItem` 等）用的是 `editor.schema` 的类型，混进同一棵树就报 `Invalid content`；`MarkdownControl.enter` 里 `view.state.schema !== editor.schema` 也会永远为真，每次切回都按正文重建、撤销历史丢失（违反 editor 输出 10）。若改成 `toJSON`/`nodeFromJSON` 过一道桥，节点对象换新，第 3、4 节“来源表按节点对象”的前提又不成立。另外 `Comment.configure(onSelect/onCommentsChange)`、`HtmlEmbed.configure(i18n、数据接口)` 是按编辑器注入的回调，单例的扩展组装不进它们。
- **如何核实**：`bun zz-review-lab/opus/empty.ts`：同一份 `createMarkdownDialectExtensions()` 建两次 `getSchema`，输出 `same schema instance: false same paragraph type: false`；把 schema A 的段落放进 schema B 的 `doc` 再 `check()`，报 `Invalid content for node doc: <paragraph>`。
- **建议改法**：编解码器按 schema 建，不做模块级单例：`createCodec(schema)`，用 `WeakMap<Schema, MarkdownCodec>` 缓存；编辑器用 `editor.schema` 取自己的编解码器，测试用 `getSchema(syntaxExtensions)`。独立的 `Marked` 实例与分词规则可以按扩展组共用（它们不碰 schema），只有“token → 节点”这一步按 schema。计划第 1 节与接口里的 `readonly schema` 照此改写，并写明“读出的文档必须属于编辑器的 schema”这一条不变量。

### 2. 新建的空段落（按回车留空行）单独写出是空串、单独读回是零个节点，读回校验必然失败

- **严重程度**：阻断；**类别**：正确性
- **位置**：plan.md 第 3 节“`space` 单元……成为空段落”、第 4 节“重新写出的块……读回……`eq` 才接受……都不等就返回 `unrepresentable`”；方言 Spec 输出 5“按 Enter 新起一段”、输出 3。
- **现象**：计划只说读入时多出来的空行变成空段落、有来源；没说**新建**的空段落怎么写。空段落不在来源表里，按第 4 节要“重新写出这一块，然后读回校验”。但空段落没有独立的 Markdown 写法：`@tiptap/extension-paragraph` 对第一个空段落写 `""`、连续的第二个起写 `&nbsp;`；`MarkdownManager.parse("")` 得到零个节点。单独读回永远不等于“一个空段落”，三级降级（转义、完全转义、HTML 形式）都改变不了空串，结果是 `unrepresentable`。
- **为什么是问题**：在段末按回车、停手 150ms（`MarkdownControl.vue` 的 `COMMIT_DELAY_MS`，`commitNow` 每次停手都会跑写出）就会触发。按第 8 节，这会把绑定标成未裁决输入：组顶部出提示、切换文档被挡（editor 输出 9）、移动标签被挡（输出 49）、资源管理器的移动改名被挡（输出 24）。这是写作里最常见的操作，等于编辑器不可用。反过来若为了读得回来写成 `&nbsp;`，文件里会出现大量 `&nbsp;` 行，与 Spec 输出 4“最小转义”、输出 5“段与段之间写一个空行”的意图相反。
- **如何核实**：`bun zz-review-lab/opus/empty.ts`：`"" => []`，`render empty para: ""`；`"a\n\n\n\nb"` 与 `"a\n\n\n\n\nb"` 都读成一个空段落（多对一）。
- **建议改法**：Spec 与计划都要定“空段落”的写法与校验单位。可行的一种：空段落不算块，算间隔的一部分——连续 k 个空段落写成 k+1 个空行（与 `createImplicitEmptyParagraphsFromSpace` 的计数一致），读回校验按“块加它前后的间隔”而不是孤立的块来做；空文档（零个块、编辑器补的一个空段落）单独规定为写出空串（见第 3 条）。把“回车后停手”“连续两次回车”“删掉空段落”放进性质 3 与组件测试。

### 3. 引用定义不产出节点，只能落在“间隔”里；按间隔规则，在文末接着写一段就会删掉文末全部引用定义

- **严重程度**：阻断；**类别**：正确性 / 不变量
- **位置**：plan.md 第 2 节“引用定义（`def` 单元）也是块”、第 3 节“`def` 单元不产出节点”与“来源记每个顶层节点对象”、第 4 节“间隔”规则；方言 Spec 输出 2“定义行属于它自己的块，不被改写”、验收 1（含引用式链接）。
- **现象**：来源表以顶层节点对象为键，`def` 块没有节点，它的原文只能并进相邻节点的 `gapBefore` 或结尾间隔。第 4 节的间隔规则是：相邻节点 `index` 不连续时写一个空行；最后一个节点不再是原来的最后一个时，结尾“按原文末尾有无换行决定”。于是：
  - 引用定义通常写在文末。作者在最后一段后面接着写一段（最常见的写作动作），最后一个节点变成新节点，原来的结尾间隔（含全部定义）被换成一个换行，**定义全部消失**；
  - 删除或移动定义前后的任一段落，`index` 不再连续，夹在中间的定义被一个空行替换；
  - 引用这些定义的 `[文字][1]` 所在块没被编辑、按原文写回，不经过读回校验，重新打开后都变成字面的 `[文字][1]`。整个过程没有任何失败或提示。
  富文本里看不到定义（它不是节点），作者也无从察觉。同一问题适用于将来任何“零节点”的块。
- **为什么是问题**：违反输出 1–2（没编辑的块字节不变）与输出 3（语义不变），而且是静默的数据丢失；方言 Spec 的验收 1 本身就含引用式链接。
- **如何核实**：`bun zz-review-lab/opus/lex.ts`：`defOnly` 一例 `def` 是独立的顶层单元；计划第 3 节明说它不产出节点。按第 4 节的间隔规则手推“文末追加一段”即得。
- **建议改法**：让 `def` 产出节点：读成不可编辑的原样块（`rawBlock`，可以显示为“链接定义”小卡片），这样它有来源、能被看到、删除也是用户的显式动作；或者在写出时把零节点块单独登记为“锚在原文偏移上的块”，间隔规则重写时保留它们。另外引用定义的删除会改变别的块的意思，见第 5 条。

### 4. `marked` 遇到重复的引用定义会丢掉它的原文，“顶层单元 raw 拼起来等于输入”并不总成立；`\r` 单独出现也被换成 `\n`

- **严重程度**：重要；**类别**：不变量
- **位置**：plan.md 第 2 节“已核实：顶层单元的 `raw` 依次拼接等于输入（LF 文字）”“规范化……CRLF 换成 LF”。
- **现象**：`marked` 17.0.6 的 `blockTokens` 对 `def`：前一个单元是段落时并进段落；否则只有 `this.tokens.links[tag]` 还没有这个标签时才 `push`，**同名的第二条定义既不进单元列表也不进别的单元的 `raw`**（`node_modules/marked/lib/marked.esm.js` 第 43–46 行）。另外 `lex` 用 `carriageReturn: /\r\n|\r/g` 规范化，单独的 `\r` 也会变成 `\n`，计划的偏移表只记 CRLF。
- **为什么是问题**：分块按 `raw` 推进偏移；重复定义一出现，后面所有块的偏移都错位，按块写回会把错位的原文切片写到别的块上。计划把这条当作已核实的前提，S1 的不变量测试会在语料里没有这类样例时照样通过。
- **如何核实**：`bun zz-review-lab/opus/lex.ts`：`dupDef` 输出 `eqNorm= false`，单元里只有第一条 `[1]: https://a.com`，`[1]: https://b.com\n\n` 消失；`loneCR` 输出 `"甲\r\r乙\r"` 被切成 `甲`、`\n\n`、`乙\n`。
- **建议改法**：分块不要信任 `raw` 拼接，改为在规范化后的文字上按偏移逐个核对：每个单元的 `raw` 必须恰好出现在当前偏移，否则把跳过的那段原文作为原样块（或并进前一块）并记诊断。偏移表把 `\r` 单独出现也算进去（或者明确在 Spec 的“编码”里说单独的 `\r` 读成什么）。语料里加重复定义、定义在引用块与列表项里、单独 `\r` 三例。

### 5. 读回校验只校验被重写的那一块，块与块之间会互相改变意思的情况抓不到

- **严重程度**：阻断；**类别**：正确性
- **位置**：plan.md 第 4 节“间隔……`index` 连续时，写原来的间隔”“读回校验……用同一套读的流程读回”；方言 Spec 输出 3“重新写出的每一块，按本方言再读一遍”。
- **现象**：`marked` 里一个块的结尾换行有时属于块（标题 `"# 标题\n"`、段落后紧跟列表时 `"para\n"`），有时属于后面的 `space` 单元（`"甲"` + `"\n\n"`），原来的间隔可能是空串。重写一块后照旧写原间隔、孤立地读回这一块，以下情况读回都“相等”，整篇重读却变了：
  1. 标题紧跟正文（中间无空行），把标题改成正文段：写成 `标题\n` + `""` + `正文第一段\n`，整篇重读是**一段**（输出 5 下中间是换行），后面那段被吞进来；
  2. 正文段之间有空行、各段用两个 ASCII 空格缩进，把一段改成列表项：`- 甲\n` + `\n` + `  乙\n`，`乙` 成了列表项的第二段；
  3. 标题后紧跟缩进代码，标题改成正文：代码成了段落的懒续行。
  这些都不是假想：标题与正文之间不空行、用半角空格缩进都是常见写法；改块类型是第 6 片之后的排版菜单与现在 Tiptap 自带快捷键（`Mod-Alt-0` 等）能做到的。
- **为什么是问题**：输出 3 的保证是“写回读得回来”，按块孤立校验时这条保证有洞，而且洞里的结果是改坏没编辑的相邻块，正是输出 2 要防的事。另外“块的原文含不含结尾换行”计划没定义，写出器照字面实现时还可能把两块粘成一行。
- **如何核实**：`bun zz-review-lab/opus/merge.ts`：`after` 一行是 `[["paragraph","标题\n正文第一段\n"]]`，`after2` 是 `[["list","- 甲\n\n  乙\n"]]`，`after3` 是 `[["paragraph","H\n    code\n"]]`。
- **建议改法**：（1）定义块与间隔的切法：块的原文不含结尾换行，换行全部归间隔（或反过来），写出器只产出不含结尾换行的块文字；（2）读回校验的单位改成“重写的块连同前后各一个块与间隔”的窗口，校验窗口重读后的块边界与节点都对得上；或者重写块与原样块相邻且原间隔里没有空行时，强制写一个空行（只动间隔）；（3）性质 3 只“在块里插一个字”测不到改块类型，补“改块类型”“包进列表、引用”两种编辑。

### 6. “写法属性参与 `eq`”与“新建节点没有写法属性”“新内容跟随块里已有的写法”互相矛盾，照字面实现新建的格式全部写不回

- **严重程度**：阻断；**类别**：合同 / 正确性
- **位置**：plan.md 第 4 节“节点与原节点 `eq`（含写法属性，见第 6 节）”、第 6 节“解析时从词法单元的 `raw` 取……新建的节点没有这个属性，用规范写法”、第 9 节随机往返“新建（无写法属性）后写出、读回，必须 `eq`”；方言 Spec 输出 2“块里新加的内容……跟随同一块已有的写法”。
- **现象**：ProseMirror 的 `Node.eq`/`Mark.eq` 比较全部属性。新建的节点或标记 `markdown` 属性为空；写出后读回，解析器“从 `raw` 取”写法，读回来的属性是 `"-"`、`"**"`、`"newline"` 之类，不等于空。再叠加输出 2 的“跟随”：在用 `__` 的段落里新加粗体会写成 `__x__`，读回属性是 `"__"`，与编辑器里的空属性也不等。降级的三步（转义、完全转义、HTML 形式）都不改变写法属性的差异，最后一律 `unrepresentable`。按 Shift+Enter 新加的硬换行、新建列表、新加粗体都会命中。第 9 节的随机往返在这个定义下按构造就不可能通过。
- **为什么是问题**：读回校验的判据没有定义清楚，后续切片照字面实现会让普通编辑全部保存失败；改成“比较时忽略写法属性”又会让输出 2 的“写法保持”失去校验。
- **如何核实**：读计划原文即可确认三处定义同时成立时矛盾；ProseMirror `Mark.eq` 为 `this == other || (this.type == other.type && compareDeep(this.attrs, other.attrs))`（`prosemirror-model`）。
- **建议改法**：把“期望的节点”与“编辑器里的节点”分开：写出器在写每块时同时产出“按实际写法补齐写法属性后的节点”（新建节点补规范写法或跟随到的写法），读回结果与它 `eq`；或者约定规范写法在解析时记为空、比较时把“空”与规范写法视为相等，并删掉输出 2 的“跟随”或把跟随的结果也按同一办法补齐。不管哪种，在计划第 4、6 节写清楚比较函数，并给它单测。

### 7. `refuse` 借用“未裁决输入”通道，但这个通道处处假定有一份候选正文；照现有代码，关闭时选“保存”会静默丢掉写不回之后的全部输入

- **严重程度**：阻断；**类别**：合同 / 正确性
- **位置**：plan.md 第 8 节“把这个绑定记成有未裁决输入（与 editor 输出 13 同一通道）……只给‘采用当前正文’”；第 7 节 `commitNow` 失败时“这次不提交”。
- **现象**：现有的未裁决输入是 `entry.candidates: Map<token, text>`（`web/documents/store.ts:139、712–735`），所有出口都以那份 `text` 为准：
  - `area.ts:582`：关闭询问里选“保存”时先 `documents.resolve(document, token, "keep-view")`（把候选正文设为正文），再 `save`，然后关标签；
  - `store.ts:775–781` 的 `rescue()`：终态页列出候选正文（editor 输出 22）；
  - editor 输出 13 的“保留本视图的内容”、输出 23 的“先保存再复制”同样走 `keep-view`。
  `unrepresentable` 没有可用的正文。照计划“同一通道”实现，要么候选正文为空、要么是上一次被接受的正文：关闭时选“保存”会把旧正文存盘、关掉标签、编辑器状态随之释放，写不回的那块**以及之后在这份文档里的所有输入**（之后每次 `commitNow` 都整篇失败）一起丢掉，没有任何失败提示；服务端重启时终态页也抢救不到这些输入。
  另外 `MarkdownControl.vue:196` 只在 `view.held && binding.unresolved()` 时跳过重载；计划没说 `refuse` 后设 `held`，此时另一组提交一次，`reload` 就会用文档正文覆盖本视图的编辑。
- **为什么是问题**：Spec 输出 3 与失败表承诺“文档保持未保存……用户修改那一块后再保存，或放弃修改”，实际路径里有静默丢数据的出口。一个写不回的块会让整份文档此后的输入都停在视图里，影响面是整份文档而不是那一块。
- **如何核实**：读 `area.ts` 第 545–592 行 `closeOne`、`store.ts` 第 700–781 行；按计划的“同一通道”代入 `unrepresentable` 即得。
- **建议改法**：不复用候选正文的通道，给文档加一种独立的标记（例如 `blocked: {token, code, block}`），它：挡保存、计入询问与“需要保存”；关闭询问只有“不保存 / 取消”（不能“保存”），或“保存”时明确失败并留在原处；抢救时用写出器的“尽力而为”结果（失败的块写原文或节点的纯文字）并标明；`refuse` 同时设 `held`。在 editor.md 输出 4、13、21–23 与控件合同里把这种状态单列，而不是写成“也是未裁决输入”。也可以考虑写不回时只把那一块写成原样（保留读入时的原文）而让其余块照常提交，影响面缩到一块。

### 8. 写出在每次停手 150ms 就跑，不在保存时；Spec 说“保存时检查、保存失败”，两者对不上，保存命令也拿不到这个失败

- **严重程度**：重要；**类别**：合同
- **位置**：方言 Spec“状态与转换”“保存时先对全部被编辑过的块做输出 3 的检查，任一块失败则整次保存不写入”、失败表；plan.md 第 7 节 `commitNow`、第 8 节“保存遇到它按输出 13 不发出写入”；`MarkdownControl.vue` 的 `COMMIT_DELAY_MS = 150`、`onBlur → commitNow`、`leave → commitNow`。
- **现象**：控件的写出发生在输入回执（每次停手、失焦、切走）而不是保存；`refuse` 时这次输入不进文档，文档的 `dirty` 只反映上一次被接受的正文。若写不回之前的修改都已保存，文档不 dirty，`nbook.editor.save` 的 `when` 是 `dirty`，Ctrl+S 什么都不做，Spec 说的“这次保存失败，说明是哪一块”不会在保存路径上出现；用户看到的是打字时冒出来的组顶部提示。另外，按第 2 条，打开一份新建的空文件、点进去再点出来（`onBlur` 也会 `commitNow`）就可能触发。
- **为什么是问题**：Spec 是黑盒合同，测试照 Spec 写“保存时失败”会和实现对不上；“文档保持未保存”在不 dirty 时也不成立。
- **如何核实**：对照 `MarkdownControl.vue` 第 60–79、262–280 行与 Spec 原文。
- **建议改法**：二选一写进 Spec：（a）写不回在输入时就报告（Spec 改为“输入不进入正文、组顶部说明是哪一块，保存、切换、关闭按第 7 条的状态处理”）；（b）真正在保存时检查：输入回执时写不回的块先按原文写（文档仍 dirty），保存前由控件再做一次完整写出、失败则保存失败。并把“打开不编辑、失焦”这条路径列进验收（Spec 输出 1 的“切走或关闭”）。

### 9. 空文件（或只有 frontmatter）读入后，编辑器补的那个空段落没有来源，不编辑写回也会走“重新写出”

- **严重程度**：重要；**类别**：正确性 / 不变量
- **位置**：plan.md 第 3 节（来源只来自词法单元）、第 4 节；方言 Spec 输出 1；验收性质 1。
- **现象**：`MarkdownManager.parse("")` 得到零个节点（`empty.ts` 输出 `"" => []`），而文档的内容表达式是 `block+`，编辑器必须补一个空段落。这个段落不来自任何词法单元，来源表里没有它。新建章节、新建文件都是空文件；打开后点进正文再点出（`onBlur` 调 `commitNow`），或者切走（`leave` 调 `commitNow`），写出就会把它当作新块重新写出，再撞上第 2 条（空段落写不回）。计划的性质 1 只在语料上跑，语料里没有空文件这一例就测不到。
- **为什么是问题**：违反输出 1“打开后不编辑……不改变任何字节”，并且在最常见的“新建一章”上触发写不回的提示。
- **如何核实**：`bun zz-review-lab/opus/empty.ts` 第一行；`markdown-empty-document.dom.test.ts` 现有测试也写明“空白经 markdown parse 后确实是空 doc”。
- **建议改法**：读入时零个块的正文，补的空段落记一个来源（原文为整个正文，通常是空串或只有空行），写出时“文档只有一个空段落且它有来源”直接写原文；“文档只剩一个空段落（用户删光了）”定为写出空正文。语料加空文件、只有 frontmatter、只有空行三例。

### 10. 分截批注的读回校验也依赖别的块：非第一截单独读回时 `body` 为空，与编辑器里的批注不等

- **严重程度**：阻断；**类别**：正确性
- **位置**：plan.md 第 4 节“上下文依赖……现在只有一种：分截批注的 `body` 写在第一截”、“读回校验……用同一套读的流程读回”；第 6 节 `syntax/comment/`“读入时同一 `id` 的各截合成一条”。
- **现象**：读入时各截合成一条，编辑器里每一截上的批注标记都带着同一个 `body`（意见）。用户只改第二截所在的段落，这一段重写为 `<comment id="c1">two改</comment>`，按块单独读回，没有第一截，得到 `body: ""` 的标记，与编辑器里 `body: "意见"` 的标记 `eq` 不成立，降级无效，`unrepresentable`。计划只把“写出时 `body` 放哪一截”列为上下文依赖，没有把读回时的合并列进去。
- **为什么是问题**：Spec 验收 6 的“在 `two` 中间回车拆段并保存”正好命中，分截批注在任何非第一截的段落里都不能编辑。
- **如何核实**：按计划第 4 节读回流程代入；现有 `Comment` 的解析在没有 `body` 属性时给 `body: commentToken.body ?? ""`（`dialect/Comment.ts:149`）。
- **建议改法**：读回校验接收一份全篇上下文（批注 `id` → `body` 表、引用定义表），与读入时同一套合并规则；把“上下文依赖”抽成一个显式的接口（读与写都用），而不是写出器里的特例。

### 11. 同一 `id` 带不同 `body` 的几截，Spec 说“各自成条、都保留”，但计划按 `id` 找第一截，第二个 `body` 会被写丢；没有 `body` 的截归哪条也没定义

- **严重程度**：重要；**类别**：合同 / 正确性
- **位置**：方言 Spec 输出 11“残缺的分截”第三句；plan.md 第 4 节“写出前先算出每个批注 `id` 的第一截在哪一块”、第 6 节“冲突的各自成条”。
- **现象**：Spec 规定同一 `id`、不同 `body` 的几截读成几条批注、写回都保留；这时有几个“第一截”。计划按 `id` 计算第一截，只会有一个，其余那条批注的 `body` 在它所在块被重写时不再写出，读回成空意见（或并进别的批注）。另外 `<comment id="c1" body="A">`、`<comment id="c1">`、`<comment id="c1" body="B">`、`<comment id="c1">` 这样交替时，没有 `body` 的截属于 A 还是 B，Spec 没说，读与写各自猜就会不一致。
- **为什么是问题**：Spec 与计划在同一条规则上给出不同的键（`id` 与 `(id, body)`），后续切片照字面实现会丢意见文字。
- **如何核实**：对照 Spec 输出 11 与计划第 4 节原文。
- **建议改法**：Spec 写明没有 `body` 的截归属于“文件顺序上它之前最近的带 `body` 的同 `id` 截”（之前没有时归第一个带 `body` 的），计划按 `(id, 归属到的 body 截)` 计算第一截；语料加交替的例子。或者更简单：读到同 `id` 不同 `body` 时整组读成原样片段，不支持编辑。

### 12. 现有的行内与块批注分词规则是非贪婪匹配，嵌套的批注会配错标签；Spec 输出 11 与验收 7 需要的“正确嵌套”读不回来

- **严重程度**：重要；**类别**：正确性
- **位置**：方言 Spec 输出 11“两条批注重叠时，在重叠的边界处拆成截，保证标签正确嵌套”、验收 7；plan.md 第 6 节 `syntax/comment/` 只说“从现有 `dialect/*.ts` 搬入”；`markdown-workbench.ts:46、48` 的 `COMMENT_INLINE_PATTERN = /^<(comment|inline-comment)(?:\s+([^>]*))?>([\s\S]*?)<\/\1>/`。
- **现象**：`甲<comment body="A">乙<comment body="B">丙</comment>丁</comment>戊` 读成：`乙` 带 A、`<comment body="B">` 原样片段、`丙` 带 A、`丁` 无批注、`</comment>` 原样片段。块批注里套块批注同样配错（外层块在第一个独占一行的 `</comment>` 处结束，剩下的成了 HTML 兜底块）。
- **为什么是问题**：写出器按第 5 节正确嵌套地写出后，读回一定与编辑器里不同，验收 7 会以 `unrepresentable` 失败；计划没有把“分词规则改成按标签配对计数”列为工作项，S3 估计不足。
- **如何核实**：`bun zz-review-lab/opus/nest.ts`，两例输出如上。
- **建议改法**：S3 明确重写批注分词：按开闭标签计数找配对的闭标签（行内只数行内的 `<comment`，块只数独占一行的），语料加嵌套与“行内套在块里”“块套块”各一例。也可以在 Spec 里规定行内批注不嵌套，重叠时一律拆成并列的截（不嵌套的写法分词简单得多）。

### 13. 第 2 节说 `space` 是间隔，第 3 节又说 `space` 转成的空段落有来源、原文是那段空行；两种说法拼在一起，改相邻段落会多出空段落

- **严重程度**：重要；**类别**：不变量
- **位置**：plan.md 第 2 节“每个非 `space` 单元是一块……块之间的原文切片是间隔”；第 3 节“`space` 单元……空段落也有来源，原文是对应的那段空行”；第 4 节“间隔”规则。
- **现象**：`a` 与 `b` 之间四个空行，`marked` 切成 `a`、`space("\n\n\n\n\n")`、`b\n`，读成“段、空段、段”。按第 3 节，空段落的原文是那段 `\n\n\n\n\n`；按第 4 节，`a` 被编辑后成了新节点，它与后面的空段落之间“写一个空行”，于是写出 `a改\n\n` + `\n\n\n\n\n` + `b\n`，重新读入是“段、空段、空段、段”，**每编辑一次空行前的段落就多一个空段落**。`space` 到空段落的计数还是多对一的（三个与四个空行都读成一个空段落），原文与节点之间没有一一对应。
- **为什么是问题**：违反性质 3（“再读入的文档只有那一处不同”）；这类空行在小说正文里很常见（场景切换）。
- **如何核实**：`bun zz-review-lab/opus/space.ts`：`orig P_P`，`after editing a P__P`。
- **建议改法**：与第 2 条一起定：空行（含它转成的空段落）一律属于间隔，空段落节点只是间隔在编辑器里的表示；间隔规则按“两侧节点是否都未变、间隔里的空段落是否都还在”决定写原文还是按空段落数重新生成。把这个模型写成一段明确的规则与单测，再写写出器。

### 14. “上下文依赖”不止分截批注：引用定义被删、两个列表变相邻都会改变没编辑的块的意思，而这些块不经读回校验

- **严重程度**：重要；**类别**：正确性
- **位置**：plan.md 第 4 节“上下文依赖……现在只有一种”；方言 Spec 输出 2、3。（第 3 条里“见第 5 条”应为本条。）
- **现象**：
  1. 引用定义：按第 3 条的建议让定义成为可删除的原样块之后，删掉 `[1]: …`，引用它的 `[文字][1]` 所在块没变、写原文、不校验，重新打开成了字面文字；同样，新打的 `[注]` 是否需要转义取决于全篇有没有 `[注]: …` 定义（简写引用链接）。
  2. 列表相邻：两个 `-` 列表中间夹一段正文，删掉这段后两个列表节点相邻，两者都没变、写原文，间隔按规则写一个空行：`- 甲\n\n- 乙`，重新读入是**一个**松散列表（`lists.ts` 输出 `[["list",2]]`）；有序列表同理。新建的列表（规范写法 `-`）紧挨着已有的 `-` 列表也一样。
  3. 第 5 条的“改块类型后吞掉相邻块”。
- **为什么是问题**：输出 3 的保证只覆盖“重新写出的块”，而这里变的是没写出的块的意思，校验看不到。
- **如何核实**：`bun zz-review-lab/opus/lists.ts`；引用定义一项按 CommonMark 规则即得。
- **建议改法**：保存（或写出）后对整篇做一次廉价的结构核对：重读整篇只到顶层词法单元，核对单元数与边界与预期一致，不一致时在相邻处补空行或改写法；或者在间隔规则里加“相邻两个同符号列表之间至少写一个非列表的分隔（如 `<!-- -->`）”这一类局部修正。引用定义的删除可以定为“删除时提示还有 N 处引用”，或删除后把引用它的块标为“变了”重新写出（它们会写成转义的字面文字或内联链接）。

### 15. 段内单换行读成文字里的 `\n`，Shift+Enter 却产生 `hardBreak` 节点；两者写出都是一个换行，读回对不上

- **严重程度**：重要；**类别**：正确性 / 合同
- **位置**：方言 Spec 输出 5“按 Shift+Enter 写出单个换行”“行尾两个空格……读进来与单换行一样显示，写回时保持各自原来的写法”；plan.md 第 6 节写法属性表“硬换行：单换行、两空格、反斜杠、`<br>`”。
- **现象**：现在的解析里，`甲\n乙` 是一个文字节点 `"甲\n乙"`（软换行留在文字里），`甲  \n乙` 与 `甲\\\n乙` 是 `hardBreak` 节点，`甲<br>乙` 在没有 DOM 时是字面文字。编辑器里按 Shift+Enter 插入的是 `hardBreak`，`MarkdownHardBreak` 写成 `"\n"`，读回却是文字里的 `\n`，`eq` 不成立。计划的写法属性表把“单换行”列为硬换行的一种写法，暗示要在解析时把文字里的 `\n` 转成带属性的 `hardBreak`，但第 3、6 节都没写这一步。
- **为什么是问题**：Spec 指定的换行操作（Shift+Enter）每用一次都会读回失败；若实现者不做转换，`unrepresentable` 会成为日常现象。另外两种表示并存时，字数统计、大纲文字、搜索都要各自处理两种换行。
- **如何核实**：`bun zz-review-lab/opus/br.ts`：四种写法的解析结果与 `render hardBreak: "甲\n乙"`。
- **建议改法**：在第 3 节明确：段落（以及标题以外的行内容器）里的软换行在解析时一律转成 `hardBreak{markdown: "newline"}`，文字节点里不留 `\n`；`<br>` 在不依赖 DOM 的前提下解析成 `hardBreak{markdown: "br"}`。给“四种写法各自往返、Shift+Enter 新建的读回”加单测。

### 16. 编解码器依赖 DOM：`@tiptap/markdown` 对 `<strong>`、`<b>`、`<u>`、`<br>` 等行内 HTML 在有没有 `window.DOMParser` 时走不同分支，`bun test` 测到的不是浏览器里的行为

- **严重程度**：重要；**类别**：测试 / 不变量
- **位置**：plan.md 第 1 节不变量“编解码器不依赖 DOM 与 Vue，在 `bun test` 里直接测”、第 4 节降级“强调与删除线改写成 HTML 形式（`<strong>`、`<em>`、`<del>`）”、第 6 节 `syntax/raw/`“HTML 兜底（现有 `HtmlFallback.ts` 的三件）”；方言 Spec 输出 3、输出 9 第三项。
- **现象**：`MarkdownManager.parseHTMLToken`（`MarkdownManager.ts:952–955`）在没有 `window.DOMParser` 时把认得的 HTML 当字面文字，有 DOM 时用 `generateJSON` 解析成标记。现有 `HtmlFallback.ts` 的 `DOM_HANDLED_INLINE_TAGS`（`a b strong i em u s del strike code br img sup sub mark`）正是有意交给 DOM 路径的。所以：
  - 在 `bun` 里 `他说：<strong>“走吧。”</strong>然后` 读成字面文字，在浏览器里读成粗体；计划第 4 节的第三级降级在 `bun test` 里永远读不回，在浏览器里才可能成功，单测与真实运行时结论相反；
  - 浏览器里 `<b>粗</b>`、`<u>下</u>` 读成粗体、下划线标记；所在块被编辑后写成 `**粗**`、`++下++`（见第 17 条），与 Spec 输出 2“行内 HTML 的大小写与属性顺序”保持、输出 9“本方言之外的 HTML 标签……为原样片段”都不符。
- **为什么是问题**：计划的全部性质测试与随机往返都在 `bun test` 里跑，覆盖不到浏览器分支；Spec 对标准 HTML 行内标签的处理与现有代码相反，计划没有指出要改哪一边。
- **如何核实**：`bun zz-review-lab/opus/html.ts`：`window defined: undefined`，`<strong>`、`<em>`、`<del>` 三例都是一整段字面文字；对照 `MarkdownManager.ts:939–985` 与 `HtmlFallback.ts:33–36`。
- **建议改法**：编解码器自己处理全部行内 HTML，不经 `parseHTMLToken`：`<strong>/<b>/<em>/<i>/<del>/<s>/<br>` 等要么在 Spec 里列为能读的写法（带写法属性 `html`，写回保持），要么一律原样片段；第 4 节的第三级降级只在前一种选择下成立。在 S1 加一条测试，断言在有与没有 `DOMParser` 两种环境下读同一份语料得到同一棵树。

### 17. StarterKit 里的下划线扩展在读 `++文字++`：`他会C++和C++。` 读成下划线，Spec 与计划都没提这种语法

- **严重程度**：重要；**类别**：正确性 / 合同
- **位置**：`markdown-dialect-extensions.ts` 的 `StarterKit.configure`（没有关掉 `underline`）；`@tiptap/extension-underline` 的 `markdownTokenizer`（`++`）与 `Mod-u` 快捷键；方言 Spec 输入一览、输出 4、9、10；plan.md 第 6 节 `syntax/core/` 清单（没有下划线）、第 5 节最小转义的字符表（没有 `+`）。
- **现象**：`他会C++和C++。` 读成 `他会C` + 下划线的 `和C` + `。`；`a++b++c` 同理。编辑器里 Ctrl+U 还能新建下划线。Spec 没有这种语法，计划的写出器、转义表、模块清单都没有它。
- **为什么是问题**：现在就在改坏含 `C++` 的文字（被编辑时写成 `++和C++` 或丢标记）；Spec“边界与兼容”说“新语法只占用现在读成普通文字或原样保留的写法”，而 `++` 现在实际是语法，Spec 没把这个现状写出来。实现者照计划迁移 `syntax/core/` 时多半漏掉它。
- **如何核实**：`bun zz-review-lab/opus/under.ts`。
- **建议改法**：开发者定一处：（a）关掉 `underline`（推荐：`++` 不是常见 Markdown，小说里“C++”比下划线常见），Spec 写明 `++` 是普通文字；或（b）Spec 定义下划线的写法（`<u>`）并列入规范写法、转义与模块清单。语料加 `C++` 一例。

### 18. 中文放宽只覆盖 `*`、`_`：`~~“删除”~~然后` 仍读不成删除线；Spec 对 `==` 放宽、对 `~~` 不放宽，降级用的 `<del>` 又不在 Spec 里

- **严重程度**：重要；**类别**：合同 / 正确性
- **位置**：方言 Spec 输出 6（只列 `*`、`_`、`**`、`__`）、输出 7、输出 24（“开闭判定与 `~~` 相同，并按输出 6 对中文放宽”）、输出 3（降级只写 `<strong>`、`<em>`）；plan.md 第 4 节第三级降级含 `<del>`、第 6 节 `syntax/cjk/`“强调先评估 `marked-cjk-friendly`”。
- **现象**：`marked-cjk-friendly`（0.1.2，`peerDependencies: marked >=15`）的 README 只处理强调；删除线的放宽规则在上游是另一个包（`remark-cjk-friendly-gfm-strikethrough`），没有 `marked` 版本。实测 `他说：~~“走吧。”~~然后` 读成整段字面文字。Spec 输出 24 说 `==` 的判定“与 `~~` 相同，并按输出 6 放宽”，等于 `==` 放宽、`~~` 不放宽，两个兄弟语法规则不同；给引号里的对白加删除线时只能靠 `<del>` 降级，而 `<del>` 作为能读的写法在 Spec 里没有，读它又依赖 DOM（第 16 条）。

- **如何核实**：`bun zz-review-lab/opus/html.ts` 最后一例；`npm view marked-cjk-friendly readme`。
- **建议改法**：Spec 输出 7 与 24 统一：`~~` 与 `==` 都按 CJK 友好规则（上游删除线规范）判定，或都不放宽并在输出 3 写明降级为 `<del>`/`<mark>`；计划在 `syntax/cjk/` 里把 `del` 与 `==` 的侧翼判定列为自己实现的工作项，并与 `escape.ts` 共用同一个判定函数（第 5 节要求“按与解析相同的侧翼判定”，共用代码才能保证）。

### 23. 四条性质只有“在块里插一个字”一种编辑，本报告第 2、3、5、9、13、14、19 条这类缺陷都不会被测到

- **严重程度**：重要；**类别**：测试
- **位置**：plan.md 第 9 节性质 1–4 与随机往返；“验收映射”第 1–3 行；brief 重点 6。
- **现象**：性质 3 只做“在每一块的文字里插一个字”；随机往返只做“新建文档→写出→读回”，生成器不含表格、空段落、硬换行、任务列表、提示块。拆段（回车）、并段、删块、移动块、改块类型、包进列表或引用、表格里回车、在文末追加段落——这些最常见的编辑一个都不在性质里。按 `conversion.md` 逐条对照：发现 5（单元格里分段）读入永远得不到多段单元格，只能靠编辑产生，性质测不到；发现 2、6 能测到；其余依赖语料是否恰好包含。
- **为什么是问题**：计划把“全部块与间隔拼回原文”的不变量与这四条性质当作 S1–S3 的主要护栏，而读回校验只覆盖重写的块（第 5、14 条），没有“编辑后整篇重读”的性质，跨块的问题全部漏掉。
- **如何核实**：对照第 9 节原文与本报告各条的触发操作。
- **建议改法**：加性质 5：对语料里的文档随机施加一串真实的 ProseMirror 编辑（`splitBlock`、`joinBackward`、删除节点、`setBlockType`、`wrapInList`、在文末插段、表格里 `splitBlock`），然后 `write`；要么得到 `unrepresentable`，要么整篇重读后 `eq` 编辑后的文档（忽略写法属性按第 6 条的比较函数），并且“没被编辑触及的顶层节点”的原文字节都还在输出里。用 `fast-check` 生成编辑序列，失败时会自动缩小到最短的复现。

### 24. 旧应用的链接约定是“不带 `/` 的作品根相对路径”，新 Spec 把同样的写法解释为相对当前文件；旧文件的链接意思会变，Spec 没写兼容

### 25. Spec 条目之间的小矛盾与缺口

- **严重程度**：建议；**类别**：合同 / 文档
- **位置**：方言 Spec 输出 2、10、11、14、17、19，“状态与转换”。
- **现象与建议**（逐项）：
  1. 输出 17 说宽容写法“所在的块被编辑后按标准写法写回”，但按计划的偏移表，“正文”与块之间原来没有空行，间隔是空串；块被重写后接着写原间隔，又成了 `正文<comment>`，不是标准写法。要么 Spec 改为“保持原样”，要么写明这时间隔补一个空行。
  2. 输出 11“写回时保持批注原来的形态”与同条“重叠时拆成截”冲突；在行内批注中间按回车拆段时，它也只能变成分截。写明例外：结构使原形态写不出时改为分截并分配 `id`。
  3. 输出 14 的 `<align value="left">` “读成普通内容”：一块读成多个节点、标签不在文档里，编辑其中任一段就会把标签去掉，与输出 2 不符，也不是 Spec 说的“取消对齐时”。

  5. 输出 19 只说 `- [ ]`；`1. [ ] 甲` 实测读成有序列表里的字面文字 `[ ] 甲`（`task.ts` 的 `ordered` 一例），Spec 应写明有序任务项不支持、按文字读写。
  6. “状态与转换”说“外部修改后重新读入时……重新开始计”，计划第 7 节的 `reload` 对另一组的输入也重新计；Spec 应把“同一文档另一个视图的输入”也写进去，否则测试照 Spec 会以为本视图编辑过的块在另一组提交后仍按“被编辑过”处理。
  7. 输出 4 的例子 `[注]` 只在全篇没有 `[注]: …` 定义时才“原样写出”（简写引用链接），`[[维基链接]]` 同理；写明条件。

### 26. 写回在每次停手都对“全部被编辑过的块”重新写出与读回，没有缓存；被编辑过的块只增不减，整篇替换后每 150ms 停手要重读整篇

- **严重程度**：建议；**类别**：性能
- **位置**：plan.md 第 4 节、第 7 节 `commitNow`、“验证”里的性能一条（“写回只重新写出变了的块，应不慢于现在”）；方言 Spec“状态与转换”（被编辑过的块一直按被编辑过处理）。
- **现象**：`commitNow` 每次停手 150ms 就跑写出；来源表只在 `load`/`reload` 时建，被编辑过的块在本视图里一直要重写并读回。实测（`perf2.ts`，2000 段、约 15 万字符，热身后）：逐块解析 2000 段约 110ms，整篇写出约 31–51ms，整篇解析约 410ms。全选替换、粘贴整章、大范围撤销之后，每次停手的写出成本是“整篇逐块解析 + 写出 + `eq`”，约 150ms 以上，比现在整篇 `getMarkdown` 加按行合并慢；编辑过几百段后，每次停手也有十几到几十毫秒。
- **为什么是问题**：计划的“应不慢于现在”没有依据；主线程上每次停手都卡一下，打字体验会变差。
- **如何核实**：`bun zz-review-lab/opus/perf2.ts`（逐块数字只含解析与建节点，不含写出与比较）。
- **建议改法**：写出结果按节点对象缓存（`WeakMap<Node, {text, context}>`，上下文没变就直接用），同一个节点只写一次、读回一次；被接受的提交之后可以把“这次写出的文本”当作新的来源（相当于对自己的提交做一次 `reload` 的来源重建），被编辑过的集合就不会无限增长。性能验收写成具体数字（例如十万字章节停手后写出不超过 16ms）。

### 27. “解析后在文字节点里解码实体”会二次解码：`&amp;nbsp;` 与 `\&nbsp;`（字面文字）到那一步已经和 `&nbsp;` 分不开

- **严重程度**：重要；**类别**：正确性
- **位置**：plan.md 第 3 节“实体解码：解析后在正文的文字节点（代码以外）里解码 HTML 实体，`&nbsp;` 成为 U+00A0（输出 4）”；方言 Spec 输出 4。
- **现象**：`@tiptap/markdown` 在建文字节点时已经做过一次 `decodeHtmlEntities`（只认 `&lt; &gt; &quot; &amp;`，`@tiptap/core/src/utilities/htmlEntities.ts:7`），转义单元 `\&` 也直接成了 `&`。实测三种写法读出来都是文字 `甲&nbsp;乙`：`甲&nbsp;乙`（实体，应为 U+00A0）、`甲&amp;nbsp;乙`（作者要的字面 `&nbsp;`）、`甲\&nbsp;乙`（同上）；`甲&amp;lt;b&amp;gt;乙` 读出 `甲&lt;b&gt;乙`。在文字节点上再解码一遍，后两种被改成不间断空格、`<b>`。块没被编辑时写原文看不出来，但显示已经错了；块一被编辑，写出器把 U+00A0 写成 `&nbsp;`，读回校验对照的是同样错的文档，照样通过，原文被静默改写。数字实体 `&#x200B;`（Spec 规定零宽字符就写成它）现在则完全不解码。
- **为什么是问题**：Spec 输出 4 要求“只在不转义就会被读成语法时才转义”，前提是读的一侧能分清字面与实体；后处理的方案做不到。
- **如何核实**：`bun zz-review-lab/opus/ent.ts`。
- **建议改法**：实体在词法单元层处理：文字单元按 `raw` 用完整的 HTML5 实体表一次解码（含数字实体），`escape` 单元原样取字符，不再经过 `@tiptap/markdown` 的 `decodeHtmlEntities`（在我们自己的段落、标题等 `parseMarkdown` 里接管行内文字的建立，或在独立 `Marked` 实例的 `walkTokens` 里把解码后的文字写进单元并标记已解码）。语料加 `&amp;nbsp;`、`\&nbsp;`、`&#x200B;`、`&#20013;` 四例。

### 28. `refuse` 只给块号；“第 N 块”对用户没有意义，`reload` 按位置重建来源也缺一道核对

- **严重程度**：建议；**类别**：合同 / 代码质量
- **位置**：plan.md 第 1 节 `{ok: false; code: "unrepresentable"; block: number}`、第 8 节“第 N 块的格式写不回 Markdown”、第 7 节 `reload`。
- **现象**：
  1. 块号是顶层节点的序号，空段落、原样块都算；在十万字的章节里“第 137 块”用户找不到，Spec 失败表要求“说明是哪一块”。
  2. `reload` 的 `findDiffStart/End` 加 `tr.replace` 一般能让文档与新读入结果 `eq`，但 `replace` 的 `Fitter` 在开放深度不一致时可能补节点或改结构；计划“按位置”直接把新原文配给当前节点，前提没有核对，一旦不等，会把别的块的原文配给这个节点，下次写出把错的原文写回。
- **为什么是问题**：前者让失败无法处理（只能放弃修改）；后者是低概率但后果是静默改写。
- **如何核实**：读计划第 7、8 节。
- **建议改法**：失败结果带文档位置 `{from, to}`，提示条给“定位”按钮，把选区移到那一块并滚动过去；`reload` 后断言 `doc.eq(next)`，不等时退回“整篇替换（`addToHistory: false`）并全部按新来源”，按位置配来源时逐个确认 `child(i).eq(next.child(i))`，不等的节点不配来源（按被编辑过处理）。

### 29. 文档与依赖的小缺口：editor 验收 5 的“只有那一行变化”、`marked-cjk-friendly` 不在已批准的依赖里

- **严重程度**：建议；**类别**：文档 / 合同
- **位置**：`docs/specs/workbench/editor.md` 验收 5“编辑一个段落后保存，只有那一行变化”；plan.md“Spec 与文档改动”表（只改输出 13、19 与控件合同）；README 决定 13（“加开发依赖 `fast-check`，锁定 `@tiptap/*` 与 `marked` 的版本”）；plan.md 第 6 节 `syntax/cjk/`“先评估 `marked-cjk-friendly`”。
- **现象**：
  1. 按块写回后，编辑多行段落（段内单换行）或列表里的一项，变化的是整块，不是“那一行”；editor 验收 5 与输出 19 的现行句（“编辑过的行按编辑器的写法写出”）都要随实现改，计划的改动表只列了输出 19 的 planned 句。
  2. `marked-cjk-friendly` 若合格会成为运行时依赖，决定 13 只批准了开发依赖 `fast-check`；它也应纳入“锁定版本、升级先跑语料”的范围。
- **建议改法**：计划的改动表补 editor 验收 5；`marked-cjk-friendly` 的引入在 S2 评估后交开发者确认，并写进锁版本的清单。

## 未发现问题的方面

- **节点对象不变的前提**：在当前扩展组里，ProseMirror 的 `ReplaceStep` 只重建包含改动的那个顶层节点，其余顶层子节点保持同一对象；拖动移动块时被移动的节点也保持对象（随后按间隔规则补空行）；撤销把整块删除还原时放回的是原对象（会写回原文，正确）。`appendTransaction` 插件只有 Tiptap 核心的“全选删光”、链接的自动链接（只碰改动范围）与表格的 `fixTables`（只查改动范围），没有发现会换掉未编辑顶层节点的插件或事务；方言代码里没有就地改 `attrs` 的写法。前提是第 1 条（schema 与编辑器一致）先解决。
- **两个组共用一份文档**：每组的视图状态各自持有读入结果，另一组的输入被接受后本组 `reload` 重建来源，这个模型本身没有发现问题（`reload` 的核对见第 28 条，`refuse` 后的 `held` 见第 7 条）。
- **引用式链接的分块解析**：混合任务列表里嵌套内容的引用式链接，在带链接扩展的扩展组下能解析到定义（`reflist.ts`）。
- **frontmatter 拆分**：`splitFrontmatter` 对 BOM、CRLF、没有闭合分隔线的处理与 Spec“输入与前置条件”一致。
- **`marked-cjk-friendly` 与 `marked` 17 的版本兼容**：`peerDependencies: marked >=15.0.0`，可以装。
- **开发者决定的覆盖**：决定 7、10、11、12、13 在 Spec 与计划里都有对应条目；没有发现悄悄改变已定项的地方（第 21、22、24 条是已定项的落地缺口，不是改变）。
