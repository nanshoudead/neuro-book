# 富文本模式的难点：Markdown 与 ProseMirror 的转换

开发者 2026-10-15 要求：看富文本模式的难点，特别是 Markdown 与 ProseMirror 转换这一块；研究怎样提高转换逻辑的可维护性，以及转换的准确性与一致性。

依据：t03 的线（worktree `.worktree/w00025-t03-tabs-and-split`）的代码，加上三组实验。实验用的是真实的扩展组（`createMarkdownEditorExtensions`）、真实的 `@tiptap/markdown` 3.27.3 与 `marked` 17.0.6，最后一组在 happy-dom 里跑真实的 `Editor`。实验输出在 `evidences/`：

- `conversion-roundtrip.txt`：42 段样例读入再写出、再读再写；12 段打出来的文字写出再读回；
- `conversion-edit-save.txt`：在一行上打一个字后，经真实的三方合并保存，再读入写出；
- `conversion-real-editor.txt`：在真实编辑器里打开任务列表与带竖线的表格，打字、回车。

实验脚本不入库，放在本地 `.local/agent/works/w00025-editor/tasks/t06-markdown-polish/probes/`。

## 现在的链路

1. **拆 frontmatter**（`source-merge.ts` 的 `splitFrontmatter`）：frontmatter 不进编辑器，原样留着。
2. **读入时规范化**（`markdown-workbench.ts` 的 `normalizeMarkdownDialectBlocks`）：把“开标签黏在正文后”的方言写法整理成标准块形态。
3. **解析**：`@tiptap/markdown` 用 `marked` 切成词法单元，每个单元交给声明了它的扩展转成节点（方言扩展各自带 `markdownTokenizer`）；没人认领的 HTML 由 `HtmlFallback.ts` 兜底成源码块。
4. **编辑**：ProseMirror 的节点树。
5. **写出**：`@tiptap/markdown` 按节点逐个调用扩展的 `renderMarkdown`，转义正文里的特殊字符。
6. **保存**（`source-merge.ts` 的 `mergeSource`）：打开时的写出结果（base）、磁盘原文（ours）、编辑后的写出结果（theirs）按行三方合并：只有编辑改了的行用写出结果，其余行保持原文的字节。

每一步都会丢信息，后一步再设法补回来。第 6 步的合并让“没编辑的行不变”成立，但被编辑的那一行，以及与它在同一个结构里的行，仍然暴露在第 3 到第 5 步的问题之下。

## 实验发现

### 会改坏内容的

| # | 现象 | 例子 | 后果 | 出在哪一层 |
|---|---|---|---|---|
| 1 | 中文引号、括号贴着 `**` 时不算粗体 | `他说：**“走吧。”**然后离开。` 读进来是普通文字；在富文本里给“走吧。”（连引号）加粗，写出 `**“走吧。”**然后`，重新打开粗体就没了；这一行被编辑后，`**` 被写成 `\*\*`，从此成了字面的星号 | 中文小说的对话几乎都在引号里，给对话加粗会在重开后丢失，并且原文被永久改写 | 解析：CommonMark 的强调规则（左右“侧翼”判定）只把空白当分隔，`“` 与 `然` 之间的 `**` 不算闭合；写出不检查读回是否一致 |
| 2 | 改列表的一项，列表被拆成几个 | `* 甲\n* 乙\n* 丙` 改“乙”后保存为 `* 甲\n- 乙改\n* 丙`，重新读入是三个列表（项之间多出空行） | 列表结构被改变；有序列表 `1)` 同理变成 `2.` | 写出把 `*` 统一成 `-`，按行合并只换了被改的那一行，同一个列表里出现两种符号；CommonMark 规定换符号就是新列表 |
| 3 | 任务列表打开后编辑器坏掉 | `- [ ] 未完成` 读进来不合编辑器的结构约束（`listItem` 里直接是文字），在里面回车报错 `Called contentMatchAt on a node with invalid content`；写出时复选框丢了 | 打开含任务列表的文件，在列表里回车会出错；保存后 `[ ]`、`[x]` 消失 | 解析：`marked` 认识任务列表，但没有扩展认领，转出的节点不合 schema，解析后也没有校验 |
| 4 | 表格单元格里的竖线把格子拆开 | `\| b \\| c \| 2 \|` 读进来格子里是 `b \| c`，写出没转义竖线，再读就成了两格，最后一格 `2` 被挤掉 | 表格数据丢失 | 写出：`@tiptap/extension-table` 不转义 `\|` |
| 5 | 表格单元格里分段后，文件里写进控制字符 | 在单元格里回车再保存，文件里出现 U+001F（单元分隔符） | 文件里混入不可见的控制字符 | 写出：`@tiptap/extension-table` 用 U+001F 拼接单元格里的多个段落 |
| 6 | 脚注与引用式链接所在的行被编辑后变形 | `正文[^1]。` 加一个字后保存为 `正文改[^1](脚注内容。)。`；`看[这里][1]。` 变成行内链接 `看改[这里](https://example.com)。` | 脚注变成一个奇怪的链接；引用式链接的写法被改 | 解析：脚注 `marked` 不支持，被读成链接；引用定义被内联，写出时不再生成定义行 |
| 7 | 实体 `&nbsp;` 变成字面文字 | `甲&nbsp;乙` 被编辑后保存为 `甲改&amp;nbsp;乙` | 不换行空格变成了六个字符 | 解析没有解码 `&nbsp;`，写出再把 `&` 转义 |
| 8 | 行首的 `# `、`1. `、`- ` 写出时不转义 | 文字 `1. 不是列表`（例如粘贴进来的）写出后原样是 `1. 不是列表`，重新打开成了有序列表 | 普通文字重开后变成标题或列表 | 写出：只转义行内的特殊字符，不转义行首的块语法 |

### 不改坏内容、但让原文变难看的

被编辑的那一行（以及同一结构里重写的行）会出现这些改写。文件给作者、Agent 和别的编辑器看，这些改写都是噪音：

- **过度转义**：`第1~2章` 写成 `第1\~2章`，`a_b_c` 写成 `a\_b\_c`，`[注]` 写成 `\[注\]`，`5*3` 写成 `5\*3`；`<`、`>`、`&` 写成 `&lt;`、`&gt;`、`&amp;`。按 CommonMark，这些位置大多不需要转义。
- **写法统一**：列表符号、`_斜_` 改成 `*斜*`、Setext 标题改成 `#`、`~~~` 围栏改成反引号、缩进代码改成围栏、`***`/`___` 分割线改成 `---`、标准 ruby 改成属性式、松散列表变紧凑、懒续行补上 `>`、裸网址写成 `[网址](网址)`。没编辑的行由三方合并保住，被编辑的行会变。
- **硬换行**：行尾两个空格、行尾反斜杠的硬换行写成单个换行；重新读入时语义变了（硬换行变成段内软换行），因为编辑区是 `pre-wrap`，看起来一样。

### 没问题的

中文段内单换行、多个空行、全角空格缩进、行尾空格、HTML 注释、数学 `$…$`、图片、删除线、嵌套的粗体与链接，以及全部项目方言（批注、注音、双语、对齐、颜色与高亮、`<html>` 块、未知标签）都能原样往返。旧应用 101 任务修过的方言问题，在新应用里没有复现。

## 难点归纳

1. **两种模型表达力不对等**。Markdown 有很多写法表达同一个意思（三种列表符号、两种强调、两种标题、引用式与行内链接）；节点树只记“意思”，不记“写法”。写回时只能选一种写法，所以会改写原文。反过来，节点树也表达不了某些 Markdown（任务列表、脚注、引用定义），这时要么丢掉，要么读成别的东西。
2. **CommonMark 的规则对中文不友好**。强调的边界判定是为以空格分词的语言设计的，`**` 贴着中文标点时规则不成立（发现 1）。这不是实现错误，而是规范本身的问题；Obsidian、GitHub 也有同样的问题（参照，未核对）。社区有“CJK 友好”的强调规则（remark 与 markdown-it 有对应插件，参照，未核对），`marked` 没有现成的。
3. **写出时不验证**。写出的文字读回来是否还是同一棵树，没有任何检查。发现 1、4、8 都是“写得出、读不回”。
4. **解析结果不校验**。不合 schema 的节点直接进了编辑器（发现 3），到用户回车时才报错。
5. **合并的粒度是行，结构的粒度是块**。按行合并保住了没编辑的行，但一个列表、一个表格是一个整体：只换其中一行，整体就可能变成别的结构（发现 2）。
6. **依赖的库还年轻，行为在变**。`@tiptap/markdown` 是 Tiptap 3 新加的官方包。`package.json` 写的是 `^3.23.1`，实际装的是 3.27.3，写出时的转义规则就在这期间加进来的（`escapeMarkdownSyntax`）。升级一个小版本就可能改变写出的结果，现在没有测试能发现这类变化。
7. **规则分散在多处**。方言的语法在 `markdown-workbench.ts` 的正则、各扩展的 `markdownTokenizer`、`HtmlFallback.ts` 的排除名单、`normalizeMarkdownDialectBlocks` 的判据里各写一部分，注释里多处提醒“改这里要同步改那里”；新应用也没有方言 Spec。

## 改进方案

按“准确性、一致性、可维护性”分三组，每组按收益排序。

### 准确性：写出的东西读回来必须一样

1. **以块为单位保留原文，取代按行合并**。ProseMirror 的节点是不可变的：没被编辑的块，编辑后还是同一个对象。打开时记下每个顶层块对应的原文片段，保存时逐块处理：还是同一个对象的块写原文片段（连同块之间原来的空行），变了的块才重新写出。
   - 发现 2 随之消失：改了列表的一项，整个列表重新写出，符号一致。
   - 比现在按行的三方合并（Myers 差异加区域判断）简单，也更准。
   - 前提已核实：`marked` 顶层词法单元的原文拼起来就是整篇原文，只有 CRLF 例外（`marked` 先把 `\r\n` 换成 `\n`），要自己换算偏移。
   - 要处理：一个词法单元可能转出零个或多个节点（例如连续空行转成空段落），需要一张“单元到节点”的对照；引用定义这类全篇共享的东西要单独处理。
2. **重新写出的块保留原来的写法**。解析时把写法记在节点属性上：列表符号与有序列表的分隔符、强调用 `*` 还是 `_`、标题是 `#` 还是 Setext、围栏的符号、分割线的写法、硬换行的写法；写出时按属性来，新建的节点用默认写法。这样重新写出的块也尽量保持原样，被编辑的那一块不会整片变样。
3. **写出后立即读回校验**。每个重新写出的块，读回来与节点比较（只比较变了的块，开销小）；不一致时换一种写法再试：
   - 粗体贴着中文标点读不回（发现 1）：改写成 `<strong>…</strong>`，或者采用第 4 条的解析规则；
   - 行首会被读成块语法的文字（发现 8）：加转义；
   - 都不行就保留这个块的原文并提示，绝不悄悄写出读不回的内容。

   这一条是兜底：以后再有没想到的写法问题，也不会悄悄改坏文件。
4. **中文友好的强调规则**（要开发者定，见文末）。在解析器里放宽强调边界的判定：`**` 贴着中文标点也算粗体。好处是作者的写法在 NeuroBook 里符合直觉；代价是同一份文件在 Obsidian、GitHub 里可能还显示星号。不放宽时，就按第 3 条写成 `<strong>`。
5. **读不懂的写法一律原样保留**。现在只有 HTML 有兜底；扩展到所有没被认领或认领后不合 schema 的语法（任务列表、脚注、引用定义、实体……）：读成一个显示源码的块或行内小块，原文原样写回。解析后对整篇做一次 schema 校验，不合格的块退回成源码块，不让不合格的文档进编辑器（发现 3）。
6. **最小转义**。正文里的特殊字符只在“不转义就会被读成语法”时才转义，并由第 3 条的读回校验兜底。`~`、`_`、`[`、`<`、`&` 在大多数位置都不需要转义（发现“过度转义”）。
7. **修正或替换有问题的写出**：表格的竖线转义与单元格里的多段（发现 4、5）；实体的解码（发现 7）；任务列表用 Tiptap 的任务列表扩展正式支持，或者按第 5 条保留原文（发现 3）；脚注按第 5 条保留原文（发现 6）。

### 一致性：同一份文件，各处的理解一样

1. **方言 Spec**：把“NeuroBook 怎样读 Markdown”写成合同，包括项目方言，也包括这些通用规则：段内单换行算换行（编辑区是 `pre-wrap`，CommonMark 算空格）、强调规则是否放宽、支持哪些 GFM 扩展（表格、删除线、任务列表）、不支持的语法怎样保留。字数统计、Agent 读写、导出都按这一份来。
2. **一份解析配置，各处共用**。编辑器、字数统计、往返测试，以及以后的导出与 Agent 工具，都从同一个入口取扩展组与解析选项（现在 `createMarkdownDialectExtensions` 已经是测试与编辑器共用的单一来源，把编辑器另加的表格、图片、硬换行也并进来，测试才覆盖到发现 3、4、5）。
3. **和别的工具的差异写清楚**：哪些写法在 NeuroBook 和 Obsidian、GitHub 里显示不同（例如放宽后的强调、项目方言），写进方言 Spec，作者与 Agent 都能查到。

### 可维护性：改的时候知道有没有改坏

1. **一份往返语料加四条性质测试**。语料是一组 `.md` 样例：小说正文、方言、各种 Markdown 写法、本文的全部发现，以后每修一个转换问题就加一个样例。对每个样例检查四条性质：
   - 不编辑就保存，字节不变；
   - 写出再读回，节点树不变（幂等）；
   - 在任意一块里打一个字再保存，其它块的字节不变，整篇的结构除了这一处都不变；
   - 解析出的文档合 schema。
2. **随机生成的往返测试**：随机生成小文档（段落、列表、强调、链接、特殊字符、中文标点），写出再读回，必须得到同一棵树。比手写样例更容易找出转义类问题（例如发现 1、8 这类）。
3. **锁定依赖版本**：`@tiptap/*` 与 `marked` 锁到确切版本，升级时先跑上面两组测试，再看写出结果有没有变。
4. **每种方言一个模块，规则只写一处**：一个方言的语法（正则）、节点定义、解析、写出、在规范化与兜底名单里的登记、它的语料样例，放在同一个模块里，由模块统一登记到各处名单，不再靠注释提醒“同步改”。

### 不建议的方向

- **换掉解析器，改用 remark（mdast）**：remark 每个节点都带源码位置，GFM 扩展齐全，也有中文友好的强调插件（参照，未核对），Milkdown 就是 ProseMirror 加 remark。但方言要改写成 micromark 扩展，这套接口比 `marked` 的分词器难写得多，现有的方言实现与 101 任务的经验都要重做。上面的改进在 `marked` 上都做得到（第 1 条需要的块位置已核实可得），先不换。如果以后发现 `marked` 的限制挡住了某条改进，再评估。
- **换成 CodeMirror 6 的文本模型**：开发者已定这一期只做富文本（[analysis.md](analysis.md)）。

## 建议的顺序

1. **先修会改坏内容的**：发现 3（任务列表让编辑器出错）、4 与 5（表格丢数据、写进控制字符）、7（实体）、8（行首块语法）。改动小，影响大。
2. **往返语料与性质测试**，加上锁定依赖版本。之后的改动都在它的保护下做。
3. **以块为单位保留原文**、**重新写出时保留写法**、**写出后读回校验**：这是准确性的主体，替换现有的按行合并。
4. **读不懂的写法原样保留**、**最小转义**。
5. **方言 Spec**，与第 1 步并行写：上面每一条行为都要落进它。

中文强调规则（发现 1）等开发者定了，放在第 3 步一起做。

## 要开发者定的问题

1. **中文贴着标点的粗体怎么处理？**
   - 放宽解析规则（推荐）：作者在 NeuroBook 里怎么写都对；同一份文件在 Obsidian、GitHub 里可能显示星号。
   - 不放宽，写出时改用 `<strong>`：各处显示一致，但原文里出现 HTML 标签，作者在源码里手写 `**“走吧。”**` 仍然不生效。
2. **任务列表、脚注要正式支持，还是只保证原样保留？** 我建议任务列表正式支持（Tiptap 有现成扩展，作者可以用来列待办），脚注先只保留原文。
3. **段内单换行**：现在显示为换行（`pre-wrap`），与 CommonMark 的“算空格”不同，但符合中文写作习惯。我建议写进方言 Spec 作为 NeuroBook 的规则，并说明在别的工具里会连成一行。
