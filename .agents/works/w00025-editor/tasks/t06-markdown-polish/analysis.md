# Markdown 编辑器功能分析

开发者 2026-10-15 列出七项要分析的功能。本文逐项写现状、参照产品的做法、可选的做法与取舍、建议，以及要开发者定的问题。旧应用的逐项清单见 [legacy-markdown.md](legacy-markdown.md)。

“现状”取自 t03 的线（worktree `.worktree/w00025-t03-tabs-and-split`，提交 `d0b131745`）。参照产品的做法凭公开资料与使用经验，没有逐一核对源码，下文标为“参照”。

## 先回答三个问题

1. **新应用用的编辑器**：和旧应用一样，富文本是 Tiptap 3（ProseMirror），Markdown 的读写用 `@tiptap/markdown` 加 `marked`；源码是 Monaco。两种编辑器都是 t02 起的“编辑器”贡献，可以在一个标签上“用其它编辑器重新打开”。
2. **支持的方言**（`web/markdown/dialect/`，和旧应用逐文件一致；`docs/specs/workbench/editor.md` 输出 19 只列了名字）：
   - 批注 `<comment body="…">…</comment>`：行内；开闭标签各占一行时作用于整段；
   - 注音 `<ruby text="…">…</ruby>`（兼容标准的 `<rt>` 写法）；
   - 双语对照 `<bilingual text="…">…</bilingual>`（段落级）；
   - 对齐 `<align value="center">…</align>`；
   - 文字标记：颜色 `<span style="color:…">`、高亮 `<mark style="background-color:…">`、上标 `<sup>`、下标 `<sub>`；
   - 可渲染 HTML `<html>…</html>`（默认是源码卡片，点了才在沙箱里渲染）；
   - 未知 HTML 原样保留，显示为源码块或源码小块，不渲染；
   - 硬换行（Shift+Enter 写成单个换行）；
   - 工作区与领域链接按普通 Markdown 链接保留。
   - 另外还有标准 Markdown 与 GFM 表格、图片。
   - 缺口：旧应用有一份完整的方言规范（`packages/neuro-book-legacy/assets/reference/content/markdown-dialect.md`，含批注、注音、宽容形态的规范化、Agent 要守的规则），新应用的 `docs/specs/` 里没有对应的 Spec。方言是作品文件的格式，Agent 也按它读写，应当有一份 Spec。
3. **空白文件没有占位、找不到能输入的地方**：是缺陷。`MarkdownControl` 支持 `placeholder` 属性，Tiptap 的占位扩展和样式也都接好了，但宿主（`EditorGroup.vue`）挂控件时没有传这个属性，所以占位是空字符串。空文件的版心里什么都不画，看不出哪里能输入。能输入的区域是 720px 宽、至少 60vh 高的版心，在里面点能放进光标；点版心左右与上下的留白（上 64px、下 120px、两侧到编辑组边缘）不会。修法：传占位文字；点编辑区里版心以外的空白时，把光标放到离点击处最近的位置（下方的空白放到末尾）。这一条不必等分析定稿，可以先修。

## 1. 实时预览（Obsidian、Typora 那种）

**参照**：
- **Obsidian**：“实时预览”（Live Preview）建在 CodeMirror 6 上。底下始终是 Markdown 源码，渲染靠装饰：光标不在的地方，把 `**`、`#`、链接地址这些标记藏起来，按渲染后的样子显示；光标所在的那一处（行或语法片段）露出源码。另有“源码模式”和只读的“阅读视图”。
- **Typora**：自己的引擎，按块切换。光标进入的那一块（段落、标题、表格、公式）露出 Markdown 标记，其余块按渲染后的样子显示。官方叫“实时预览”或“所见即所得”，也有单独的“源代码模式”。
- **Vditor**（开源 Markdown 编辑器）：把模式分成三种，正好对应你说的三种：所见即所得（WYSIWYG）、即时渲染（IR，Typora 式）、分屏预览（SV）。

**和现在的架构的关系**：实时预览的模型是**源码文本**，不是富文本树。这带来三点好处：
- 未编辑的字节天然不变，不需要 `source-merge.ts` 那样的三方合并；
- 光标、选区、流式写入都直接用源码偏移表示，和源码编辑器、Agent 看到的位置一致；
- 方言标签在光标离开时显示为控件（注音的小字、批注的波浪线），光标进入时露出源码，不会因为没有“新建”入口就改不了。

**能做实时预览的引擎**：
- **CodeMirror 6**（推荐）：装饰可以把一段源码替换成控件（replace decoration），Obsidian 就是这样做的；体积小，按需加载。缺点是多了第三套编辑器引擎，方言要再写一遍（语法解析用 Lezer 的 Markdown 扩展，显示用装饰与控件）。
- **Monaco**：装饰只能改样式，或在一段文字的前后插入文字，不能把一段源码换成控件（从 Monaco 的 API 推断）。做出来只能是“高亮得更好的源码模式”，做不到 Obsidian 那种效果。
- **Tiptap**：要在富文本树上模拟“光标处露出标记”（在光标所在的 mark 前后画出假的 `**`）。标记不是真的文字，删一个 `*` 这类操作做不出来；Typora 式的按块切换要把整块换成源码节点再换回来，复杂而且容易丢东西。不推荐。

**建议**：实时预览用 CodeMirror 6 做成一个新的编辑器贡献（和 t02 的图片查看器、HTML 预览同一个机制），名字叫“实时预览”（沿用 Obsidian 的叫法）。

## 2. 传统富文本的排版菜单

**现状**：富文本的快捷键可用（Tiptap 自带的 Ctrl+B、Ctrl+I 等，从代码推断），但没有任何可点的入口。

**可选的形式**：
- **选区浮动菜单**（Notion、旧应用）：选中文字才出现，不占版面，适合专心写作；
- **固定工具栏**（Word、Google Docs）：一直在版心上方，可发现性最好，但占一行，也会分散注意力；
- 两者都有，工具栏可以在设置里关掉。

**关键设计**：排版菜单、右键菜单、斜杠命令和快捷键调用的应该是同一组**编辑命令**（加粗、标题、列表、插入链接、注音……），由当前的编辑器（富文本、实时预览、源码）各自实现。这样三种模式共用菜单，插件也能往里加命令。这组命令和第 3、4 项共用。

**建议**：富文本做选区浮动菜单，另加一个可以在设置里打开的固定工具栏；实时预览也用同一个浮动菜单（Obsidian 没有，但新手需要）。

## 3. 右键文本菜单

**现状**：右键是浏览器自己的菜单；Spec 把正文右键菜单列在“不承诺”。

**做法**：新增菜单位置“编辑器正文”（`workbench/menus.md` 的位置表），用 nb-ui 的 `ContextMenu`。分组：剪切、复制、粘贴（包括粘贴为纯文本）；撤销、重做；格式（同第 2 项的命令）；插入（链接、图片、表格、注音、批注……）；插件贡献的项。三种模式共用这个位置，各模式只显示自己能执行的项。源码编辑器那一份在 t05。

**一个要注意的约束**：浏览器不允许网页的脚本随便读剪贴板，“粘贴”菜单项要走异步剪贴板接口，第一次使用会弹出浏览器的授权提示；拿不到授权时提示用 Ctrl+V。VS Code 的网页版也是这样。

## 4. 对外的接口（包括流式输入输出）

**现状**：控件句柄只有聚焦、结算、跳到行、大纲、跳到标题（`shared/contracts.ts` 的 `EditorControlHandle`）；其它插件改正文只能整篇替换（`TextEditorBinding.commit`），也不知道选区在哪。

**要的接口**（按需要的先后）：
- **读**：活动文档的选区与光标（按源码偏移）、选中的文字；
- **改**：按源码范围替换，作为一步可撤销的编辑；
- **流式写入**（Inline AI）：在一个范围上开始一次流式写入，逐段追加；写入期间显示为预览（另一种底色，不进撤销），用户接受后作为一步编辑提交，拒绝则撤回；写入期间用户在别处改正文，范围随之平移；
- **装饰**：给一段范围加标记（AI 引用高亮、Agent 的批注提示），随编辑平移。

**关键约束**：这些接口都应当用**源码偏移**表示位置，三种模式各自换算，这样插件不用知道当前是哪种模式。实时预览和源码模式里，换算是恒等的；富文本里要在源码偏移和富文本树的位置之间换算。`source-merge.ts` 已经有“哪一段源码对应编辑过的内容”的对应关系，但要做到任意位置的精确换算还要额外的工作，这是富文本模式做这组接口的主要成本。

**建议**：这一项先定接口形状，写进 Spec 的控件合同；流式写入等 Inline AI 时再实现（你说优先级低）。

## 5. 几种模式

| 模式 | 用户看到的 | 引擎 | 现状 |
|---|---|---|---|
| 源码 | Markdown 源码，语法高亮 | Monaco | 有（“用源码编辑器重新打开”） |
| 实时预览 | 渲染后的样子，光标处露出标记 | CodeMirror 6（建议） | 没有 |
| 富文本 | 只有渲染后的样子，不碰 Markdown | Tiptap | 有 |

**名字**：Obsidian 和 Typora 都叫“实时预览”，Vditor 叫“即时渲染”。建议叫“实时预览”。

**要你定**：
- **三种都做，还是只做两种？**
  - 三种都做：照顾两类作者。富文本给不想碰 Markdown 的人，实时预览给熟悉 Markdown、想看见源码的人。代价是方言和编辑命令要在三套引擎上各实现一遍，第 4 项的接口也要做三份换算。
  - 只做实时预览加源码：Obsidian 的做法，只有一种文本模型，接口最简单；但不碰 Markdown 的作者会看到标记，Tiptap 上已经做好的方言要在 CodeMirror 上重写。
  - 只做富文本加源码（现状）：最省事，但做不出实时预览。
  - 我的建议是三种都做：富文本作为默认（作者是小说作者，多数不熟悉 Markdown），实时预览作为可选；第 2 项的编辑命令层先做，三种模式共用它。不过这是这一轮最大的取舍，影响后面所有任务的工作量，由你定。
- **模式怎么切**：现在是“用其它编辑器重新打开”，藏在菜单里。建议在编辑区标题加一个模式切换按钮（富文本、实时预览、源码），切换记在标签上；默认模式放进设置。

## 6. 各种方言

### 内嵌 HTML

**现状**：`<html>` 块在 `<iframe sandbox="allow-scripts" srcdoc>` 里渲染，源不透明，拿不到应用的数据；但页面里的相对引用（图片、样式、脚本）读不到作品里的文件，也不能控制联网。

**能否复用 HTML 预览**：能，而且建议复用。HTML 预览（`docs/specs/workbench/html-preview.md`）是同一种沙箱，多了两样：预览令牌加 `<base href>`，让相对引用读到作品里的文件；以及“允许联网”的开关。`<html>` 块改用同一套机制：相对引用按 Markdown 文件所在的目录解析，联网开关与安全说明也一致。改动在 `dialect/HtmlEmbed.ts` 生成 `srcdoc` 的那一步，令牌由文件服务签发，和 HTML 预览共用。

### 图片、音频、视频

- **图片**：标准写法 `![说明](路径)`，已能显示，但相对路径（例如 `../images/a.png`）在富文本里显示不出来（从代码推断：没有把路径换成作品里的文件）。要做：按 Markdown 文件所在目录解析相对路径，经文件服务读出来；读法可以复用 HTML 预览的令牌地址，或者图片查看器那种按字节读。还要有插入图片的入口：选文件、粘贴、拖进来。粘贴或拖进来的图片存到哪个目录（例如和文件同级的 `assets/`），要你定，Obsidian 和 Typora 都把这个做成设置。
- **音频、视频**：标准 Markdown 没有写法。有两种做法：
  - 用 HTML 标签 `<audio src>`、`<video src>`：其它编辑器也认得，GitHub 也能显示；
  - 用图片的写法、按扩展名识别（`![](a.mp3)` 显示成播放器）：写起来短，但别的工具会把它当成一张坏掉的图片。
  - 建议用 HTML 标签，作为方言的一部分（现在会被当成未知 HTML、显示成源码），渲染时同样按相对路径解析。

### 注音、双语、对齐、文字标记

数据格式已有，缺的是入口（第 2、3 项的菜单与命令）。注音有一个已知的限制：注音里的文字被别的格式拆开时，小字会重复显示，旧应用的规范要求注音里只放纯文字。入口做出来时，加粗等格式要避开注音的范围，或者把注音当成不可拆的整体。

### 批注

这一条要讨论存法。三种存法：

| 存法 | 样子 | 好处 | 代价 |
|---|---|---|---|
| 写在正文里（现状） | `<comment body="意见">正文</comment>` | 跟着文件走，复制、移动、用 Git 都不丢；Agent 读正文就能看到；外部编辑器改了正文，批注还在原处 | 正文里多了标签，别的编辑器里看着乱，还要在字数、导出、Agent 写作时剔除；不好放回复、作者、时间、是否已解决 |
| 存在旁边的文件里 | `a.md` 旁边的 `a.comments.json`，按引用的原文与上下文定位 | 正文干净；回复、作者、时间、已解决都好放 | 外部改了正文后要重新定位（按原文与上下文模糊匹配，找不到的变成“孤立批注”）；移动、改名文件时要一起带走 |
| CriticMarkup 这类既有约定 | `{==正文==}{>>意见<<}` | 有现成的约定，少数编辑器认得 | 同样写在正文里；表达力和第一种差不多，NeuroBook 已经用了 XML 风格的方言，再引入一套写法不一致 |

**问题**：
- 批注是给谁看的：只是作者自己的笔记，还是要和 Agent 来回讨论（有回复、有已解决）？
- Agent 写作时要不要读到批注？

前者倾向写在正文里，后者倾向存在旁边的文件。你还没定之前，我不建议先做批注的界面。

## 7. frontmatter、`@` 引用这类小块与卡片

- **frontmatter**：现在不进富文本，改它要用源码编辑器。参照 Obsidian 的“属性”面板：正文上方一块，按字段显示（文字、数字、日期、列表、勾选），也能切到 YAML 源码；没有 frontmatter 时显示“添加属性”。字段的类型可以先按值推断，以后由作品的设定（角色、地点等）给出类型。三种模式共用这一块（源码模式里 frontmatter 就是源码，不需要它）。
- **`@` 引用小块**：输入 `@` 弹出候选（章节、人物、地点、文件），插入后显示成带图标的小块，点了跳过去。写进文件的格式要定：普通 Markdown 链接 `[林雪](project://characters/林雪.md)`（现在的做法，别的编辑器也认），还是 Obsidian 式的 `[[林雪]]`（短，但别的工具不认，还要解决同名）。候选和跳转依赖作品的索引（按名字查文件、人物），新应用还没有。
- **卡片**（把另一个文件的内容嵌进来显示，Obsidian 的 `![[笔记]]`）：依赖同一个索引，也要定格式。

**建议**：frontmatter 面板不依赖别的系统，可以早做；`@` 引用和卡片先定格式、写进方言 Spec，等作品索引有了再做界面。

## 依赖关系与建议的顺序

1. **先修**：空白文件的占位与点击（问题 3）。
2. **方言 Spec**：把方言规范补进新应用的 `docs/specs/`；后面的每一项都会改它。
3. **编辑命令层**：第 2、3 项的基础，三种模式共用；先只在富文本上实现。
4. **右键菜单与选区浮动菜单**（第 2、3 项），加上插入链接、图片、表格，以及相对路径的图片（第 6 项）。
5. **frontmatter 面板**（第 7 项）、`<html>` 块改用 HTML 预览的令牌（第 6 项）、音频与视频。
6. **实时预览**（第 1、5 项）：CodeMirror 6 的新编辑器，复用第 3 步的命令层。
7. **对外接口**（第 4 项）：先定形状，流式写入随 Inline AI 再做。
8. **批注**：等存法定了。`@` 引用与卡片等作品索引有了再做。

## 要开发者定的问题

1. 三种模式都做吗？默认用哪一种？（第 5 项）
2. 实时预览用 CodeMirror 6 吗？这会引入第三套编辑器引擎。（第 1 项）
3. 排版菜单用浮动菜单、固定工具栏，还是两者都有？（第 2 项）
4. 批注是作者的笔记，还是要和 Agent 讨论？存在正文里还是旁边的文件里？（第 6 项）
5. 粘贴、拖进来的图片存到哪里？（第 6 项）
6. 音频和视频用 HTML 标签吗？（第 6 项）
7. `@` 引用写成普通链接还是 `[[ ]]`？（第 7 项）
8. 上面的顺序有没有要调整的？t06 做到哪一步，后面怎么拆 Task？
