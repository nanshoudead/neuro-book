# Agent 输出展示的三种做法：性能测量（2026-10-16）

测量代码在本地 `.local/agent/works/w00025-editor/tasks/t07-markdown-plugins/spike-display/`（不入库），基于 master `ee9cee973` 的编解码器与语法模块。

## 方法

- 本机 Chrome（Playwright `channel: "chrome"`，无头），视口 1200×900，Vite 开发服务；每种做法每次新开页面。
- 语料：按固定种子生成的 Agent 回复，每条约 1280 字：标题、段落（粗体、斜体、行内代码、链接）、嵌套列表、有序列表，隔条加 12 行代码块、5 行表格、提示块、批注。
- 三种做法：
  - `html`：`marked` 转 HTML 后 `innerHTML`（旧应用 `AgentMarkdown` 的做法，不认方言）；
  - `static`：编解码器 `codec.read` 读成文档，再用 schema 的 `DOMSerializer` 逐个顶层块序列化；流式更新时重新读入，只替换第一个不同的块之后的部分；
  - `editor`：每条消息一个只读 Tiptap 编辑器（`editable: false`，全部语法扩展）；流式更新用 `codec.reload`。
- `cv=1`：每条消息加 `content-visibility: auto; contain-intrinsic-size: auto 600px`。
- 指标：`mount` 全部消息挂上并完成布局；`layout` 列表宽度在 520 与 760 之间来回改 40 次，每次改完强制布局的耗时（拖动外层容器时每帧要做的事）；`update` 最后一条消息每次追加 40 字、共 60 次，每次更新加布局的耗时；`heap` 结束后强制回收再读 JS 堆。单位毫秒、MB。

## 结论

- 拖动改宽度的卡顿来自整页布局，与用哪种渲染关系不大：不加 `content-visibility` 时三种做法每次改宽度都要重排全部消息（100 条 12–16 毫秒，300 条 34–45 毫秒）；加上之后只排看得见的，都在 3 毫秒左右。这条要求落在对话列表上，与展示器选哪种做法无关。
- 只读 Tiptap 的首次显示约是静态序列化的 3 倍（100 条 0.6 秒，300 条 1.8 秒），JS 堆约 3 到 6 倍（22.7 MB、48.4 MB 对 7.6 MB、7.5 MB），并随消息数线性增长。
- 流式追加三种都在 4 毫秒左右（最后一条消息约 1300 到 3700 字）。
- 未测：选区变化时每个只读编辑器的监听开销、节点视图（提示块、批注、引用小块）的挂载开销、低端机器。
