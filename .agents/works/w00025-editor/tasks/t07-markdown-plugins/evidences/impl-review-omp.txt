### 1. 撞名检查遗漏原样语法与组合扩展，外来方言能让整份语言创建失败

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/markdown/web/language-registry.ts:24-31`、`web/syntax-catalog.ts:39-44`、`web/language.ts:68-84`（后两处同属 `src/plugins/markdown/`）。
- **现象**：`taken` 只包含七种内置方言与 `coreSyntax`，不包含 `createMarkdownLanguage` 随后自动追加的 `raw`；`namesOf` 又只查看顶层扩展名，不展开 `StarterKit`、`TableKit` 的子扩展。真实插件宿主交付一个带 `writeInline.rawInline` 的方言后，目录仍将其列为 active、没有诊断，`languageFor` 抛出 `Error: rawInline 的写法登记了两次（raw）`；交付名为 `bold` 的扩展也被接受，建 schema 时出现 `[tiptap warn]: Duplicate extension names found: ['bold']`。
- **为什么是问题**：违反 `workspace.markdown-syntaxes` 输出 3、4 的失败隔离：与核心撞名应只让外来方言不生效，不能使新建的 Markdown 视图创建失败。原样保留属于核心语法，恰好是不可被方言替换的兜底。当前测试只覆盖标签撞名，没有覆盖原样 writer 或核心组合扩展。
- **如何核实**：`bun zz-review-lab/omp/catalog-probe.ts`，真实 `createApplication`、产品贡献点与 receiver 交付；输出 `raw-writer` 的 active 为 `["test.kbd.kbd"]`、inactive 为 `[]`，随后抛上述异常；`nested-bold` 同样 active 且无诊断，并输出重复扩展警告。S1 前不存在外来方言组成路径，这是本次新增缺口。
- **建议改法**：在一处收集完整的保留语法集合（包括 raw），用 Tiptap 的实际扩展展开机制取最终节点与标记名，再统一完成冲突筛选后组成语言；不要让目录与语言层各判一半。补核心子扩展、raw 节点及 writer 撞名的真实交付用例，要求外来方言被隔离、核心读写仍可用。

### 2. 新链接词法与 marked 不一致，并把反斜杠后的换行读进了行内小块

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/markdown/shared/link-syntax.ts:43-51,61-83,100-116`；`src/plugins/markdown/web/components/prompt/prompt-text.ts:449-454`（同包）。
- **现象**：三个已运行的反例：① ``[`a]b`](x)`` 被 `marked` 读成链接，新词法不认；② `[x](a\ b)` 在 `marked` 中是普通文字，新词法却生成目标为 `a\ b` 的引用；③ 尖括号目标中出现“反斜杠 + 实际换行”时，扫描器跳过换行并生成一个跨两行的引用小块，`findCompletedWriting` 也将它报告为已完成。
- **为什么是问题**：合同明确要求引用按 Markdown 行内链接识别，Composer 又明确不允许跨行。`closeBracket` 不跳过代码片段；三个扫描器都无条件把 `\` 后的字符跳过，但 CommonMark 的反斜杠转义只适用于 ASCII 标点，不能把空白与换行变成合法目标。新 `tokenizeInline` 还删掉了旧版对 `token.raw.includes("\n")` 的兜底过滤，因此第三例实际显示时会把两个段落合成一枚不可拆的小块。这里不是要求 Composer 解释普通 Markdown 排版。
- **如何核实**：`bun zz-review-lab/omp/links-probe.ts` 同时输出实际 `Marked.lexer`、`findInlineLinks`、`parsePromptText` 与 `findCompletedWriting` 的结果，上述三例均能直接核对；原文写回仍相同，问题是识别与文档结构错误。旧 `prompt-text.ts` 已用 `git show 865c9f593:packages/neuro-book/app/components/common/form/prompt-editor/prompt-text.ts` 核对，旧版明确过滤跨行 token；本次新增了这套手写词法。
- **建议改法**：把行内链接的识别复用实际 Markdown tokenizer 的链接规则，仅提取链接，不让 Composer 解释其它排版；若保留独立扫描器，先限制为同一行，按 ASCII 标点处理转义，并正确跳过标签文字中的代码片段。补三例对照与真实编辑组件的手打完成用例。

### 3. 移植时重写选区引用，丢掉旧版短写法并改变了已有行号与路径的含义

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/markdown/web/components/prompt/prompt-text.ts:86-87,441-446,492-499`。
- **现象**：旧版能识别的 `manuscript/ch1.md#L3-L9` 在新版完全不是选区小块；`[[manuscript/ch1.md#l3-l9]]` 原先指向 `manuscript/ch1.md` 的第 3–9 行，现在把 `#l3-l9` 当成文件名的一部分、没有行号；`[[./manuscript/ch1.md#L3]]` 也不再去掉 `./`。另一个边界是 `#L0`：旧版不产生范围，新版发出第 0–0 行。
- **为什么是问题**：开发者只批准改写 Markdown 引用目标的识别，选区不属于旧领域地址迁移。计划第 7 节要求其它文字写法不变，`ui.prompt-editor` 也要求旧文字照常读入。被删掉的是旧 `readSelectionRefChipAt` 的现有能力，计划、新 Spec 与移植测试都没有登记这项收缩。原文虽仍能写回，但点击后交给宿主的文件地址和范围已经不同，短写法更失去点击入口。
- **如何核实**：`bun zz-review-lab/omp/legacy-probe.ts` 从 `865c9f593` 读取并运行未改写的 `inline-editor-selection.ts`，将其结果与当前 `parsePromptText` 对照：第一例旧版返回范围 `{startLine:3,endLine:9}`、新版 token 数为 0；其余三例输出上述地址或范围差异。旧 Composer 确实经 `tokenizePlainReferenceText → collectSelectionMatches → readSelectionRefChipAt` 使用这些能力，已核对历史源码调用链。
- **建议改法**：保留旧选区识别器的短写法、大小写与规范化规则，只移除旧应用业务类型依赖；不要为链接改造另写一个不完整的选区子集。将上述旧写法加入文字往返与 `token-activate` 的范围断言。

### 4. 未闭合方括号让新链接扫描退化为平方级，32 KB 草稿每敲一个字阻塞约 1.47 秒

- **严重程度**：重要；**类别**：安全与性能。
- **位置**：`packages/neuro-book/src/plugins/markdown/shared/link-syntax.ts:43-51,123-135`；`src/plugins/markdown/web/components/prompt/prompt-editor-extensions.ts:361-379`（同包）。
- **现象**：`findInlineLinks` 遇到每个 `[` 都从该位置扫描到行尾找闭括号，失败后只前进一个字符。用不含 `[[` 的 `'[a'.repeat(n)` 排除选区正则干扰，单独扫描 8000、16000、32000、64000 个 ASCII 字符分别耗时约 62、200、1058、4510 毫秒。在实际挂载的 `PromptEditor` 内派发一次正常的单步 `insertText`，8000、16000、32000 字符的单字符输入分别耗时 **92.25、383.32、1468.67 毫秒**。
- **为什么是问题**：手打完成插件对每次单字符输入都扫描整行，不只是初次导入；因此一个约 32 KB 的正常草稿可以让每次输入阻塞主线程超过一秒。中、大粘贴的分档不能保护重新打开的草稿，也不能保护纯文字粘贴。旧引用扫描在找不到任何 `](` 时直接结束，没有这条逐个开括号重扫到末尾的新路径。
- **如何核实**：`bun zz-review-lab/omp/legacy-probe.ts` 给出独立扫描数字；`bunx vitest run --config zz-review-lab/omp/vitest.config.ts zz-review-lab/omp/display.dom.test.ts zz-review-lab/omp/schema.dom.test.ts --reporter verbose` 给出真实 Tiptap transaction、实际 completion 插件下的输入耗时。实验没有替换计时器或伪造插件回调。
- **建议改法**：把括号配对改成单次扫描／栈配对，或让失败位置共享“不存在闭合”的结果，避免对每个开括号重扫余下全文；完成判断优先局限在这次输入可能结束的候选范围。补不成对括号的数量级用例，不能只测合法短链接。

### 5. 展示器的 schema 缓存建在每个组件实例里，两条同语言消息仍各构造一份

- **严重程度**：建议；**类别**：安全与性能。
- **位置**：`packages/neuro-book/src/plugins/markdown/web/components/MarkdownDisplay.vue:24-32`。
- **现象**：`schemas` 在 `<script setup>` 内创建，Vue 每挂一条消息就执行一次 setup，因此这张 WeakMap 从未跨消息共享。通过真实插件宿主交付一个可计数的方言扩展，再挂两条使用同一 `SyntaxCatalog`、同一语言的消息，schema 构造累计数为 **[1,2]**，不是共用一次。
- **为什么是问题**：代码注释承诺“同一时刻挂上的消息共用”，实际缓存仅活在一个固定语言的实例内，该实例本来只调用一次 `schemaOf`。100 条消息就会有 100 次 schema 构建，以及 100 份按 schema 缓存的编解码器；这部分没有承担任何隔离职责，是展示器首次显示路径上可直接省掉的工作。未在本次浏览器中测量这部分的毫秒数，不把组件实验的数量当作浏览器性能结果。
- **如何核实**：上述 Vitest 实验命令中 `schema.dom.test.ts` 输出 `schema-builds [1,2]`；方言经真实 `createApplication` 与产品 receiver 交付，没有直接改写 active ref。`DisplayRenderer` 自己的 schema 输入没有实例相关属性。
- **建议改法**：把 WeakMap 与 `schemaOf` 移到渲染器／语言模块的模块级作用域，或者由语言对象持有 schema；删除组件内这张没有命中机会的缓存，不新增服务或实例状态。
