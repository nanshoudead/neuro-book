# t16 nb-markdown 抽包计划：设计审查报告

审查对象：`.agents/works/w00025-editor/tasks/t16-nb-markdown-package/plan.md`（主工作区）；现有实现在 worktree `packages/neuro-book/src/plugins/markdown/`。

## 1. 【重要 / 正确性】`MarkdownHost` 的类型与缺省值放进轻量入口 `./host`，会同时打破后端类型检查与首屏

- **位置**：计划“宿主接口：`src/host.ts`”（46–64 行）、入口表 `./host` 一行（依赖只写 vue）、“`nbook.markdown` 改成包装”（92–97 行）。
- **现象**：
  1. `ChipIcon` 的 `render: (document: Document) => Element` 写在 `host.ts` 里。nbook 的 `web/plugin.ts` 要静态导入 `markdownHostKey`/`provideMarkdownHost`，而这份文件在后端 `tsc`（`tsconfig.json`，`lib: ["ESNext"]`、`types: ["bun"]`，不含 DOM）的检查范围内：`src/*.test.ts` 里的 `builtin-manifest.test.ts` 导入 `nbook/web/plugins`，一路到 `markdown/web/plugin.ts`。我在 worktree 里用同样的选项编译一个只写 `(d: Document, e: HTMLElement) => Element` 的文件，结果是 TS2304 `Cannot find name 'Document'/'HTMLElement'/'Element'`（实验文件在 `/tmp/claude-1000/review-t16-design/exp/dom.ts`）。
  2. 同一原因波及动态导入：现在 `web/plugin.ts` 动态导入的是 `.vue`，后端 tsc 靠 `src/types/vue-sfc.d.ts` 的通配声明把它们当成普通组件，不展开内容。改成 `import("@notnotype/nb-markdown/chip")`、`./prompt` 后，tsc 会解析到包里真实的 `index.ts`；计划的 `./chip` 入口导出 `chipView`、`renderChipIcon`（用 `Document`），`./prompt` 导出 `promptReferenceText` 等文字函数和 TipTap 扩展，都会被后端 tsc 展开并报 DOM 类型缺失。
  3. `MarkdownHost.language(): MarkdownLanguage` 是同步函数，缺省值写“内置方言加核心语法”，nbook 提供的是 `language: () => languageFor(catalog)`。要让 `web/plugin.ts`（插件入口，首屏）构造这个对象，就得静态引用 `defaultMarkdownLanguage()`（包的 `./language`）与 `language-registry.ts` 的 `languageFor`。`language-registry.ts` 的头注释和 `plugin.ts` 的模块头都明确写着“不能进插件入口的引用链”，因为它带着全部语法模块、marked 与 ProseMirror。`check-dist.ts` 的 `FIRST_SCREEN_FORBIDDEN`（`"Invalid content for node"`、`"marked(): input parameter"`）会在首屏命中。
- **为什么是问题**：计划写的做法照字面实现，第 3 片的 `bun run typecheck` 就红，第 6 片的 `check-dist` 才暴露首屏问题（计划只在第 6 片跑 build）。对应 `workspace.markdown-syntaxes` 输出 2。
- **如何核实**：上面的 tsc 实验；`rg "FIRST_SCREEN_FORBIDDEN" packages/neuro-book/scripts/check-dist.ts`；读 `web/plugin.ts` 与 `language-registry.ts` 的头注释。
- **建议改法**：
  - `host.ts` 只放类型、`InjectionKey` 和 `provideMarkdownHost`，类型里不出现 `Document`（`render` 改成 `(parent: {ownerDocument: unknown}) => unknown` 太绕，更直接的是把 `ChipIcon` 的 render 变体放进 `./chip` 的类型文件，`MarkdownHost.fileIcon` 的返回类型用不含 DOM 的描述，例如 `{iconName: string; ...}` 由包里的 `./chip` 去渲染）。
  - 缺省宿主放在组件侧：各组件用 `inject(markdownHostKey, null) ?? defaultHost()`，`defaultHost` 住在重模块里（`./language` 一侧）。
  - nbook 的 `language: () => languageFor(catalog)` 不能在入口里构造。让 `withHost` 的 `load()` 同时拿到组件与“宿主实现”两个动态导入（`Promise.all([import(组件), import("./host-impl")])`），宿主对象在懒加载的 chunk 里建；`withHost` 本身只 provide 一个异步构造好的对象或一个返回它的工厂。
  - 另一个选择是让组件自己调 `languageFor`，宿主只给 `catalog`（现状），`MarkdownHost.language` 去掉；这样 nb-story 的缺省宿主也不需要同步语言。要保留 `language()`，就必须接受上一条。
  - 每片都跑 `bun run build:web && bun run check:dist`（neuro-book 的 `build` 脚本里已有），不要留到第 6 片。

## 2. 【重要 / 正确性】四个组件目前没有经过 `withHost`，计划没有写要包，会悄悄退回缺省宿主

- **位置**：计划 92–97 行“`web/plugin.ts`… `withHost` 提供 `MarkdownHost`”。
- **现象**：`web/plugin.ts` 现在只有 `MarkdownControl` 与 `MarkdownDisplay` 走 `withHost`；`InlineChip`、`MarkdownImage`、`PromptEditor`、`PromptTextView` 是裸的 `defineAsyncComponent`（plugin.ts 第 81–84 行）。今天这没问题，因为它们不 inject 任何东西。计划让它们读 `targets`（`PromptEditor` 里的小块、`linkAttrs`、`promptReferenceText`）与 `fileIcon`（小块图标），而 `provide` 只发生在 `withHost` 里。照计划只写“提供”，PromptEditor 与 PromptTextView（nb-agent-ui 经 `markdownKey` 取到的就是它们）在应用里拿到的是包的缺省宿主：`project://x.md`、`/设定/林雪.md` 变成 `other`，没有文件图标、色调也变，`encodeFile` 退化为原样（文件名含 `#`、`?`、`%` 时引用读回不再指向同一个文件）。没有任何报错。
- **同类的 Lab 面**：`plugins/lab/web/fixtures/nb-agent-ui/host.ts`、`MarkdownDisplayFixture.vue`、`PromptEditorFixture.vue`、`InlineChipFixture.vue`、`editor-scene/EditorAreaFixture.vue` 直接挂组件，只 provide 方言目录/资产服务。计划写“Lab 场景改引包”，没写它们要 provide nbook 的宿主。不 provide 的话 Lab 与 e2e（`lab-markdown.e2e.ts`、`lab-agent-ui.e2e.ts`）会在“能跑但图标变了”的状态下通过，视觉回归只有截图能看见。
- **为什么是问题**：违反“用户可见行为不变”，而且静默。`ui.prompt-editor` 与 `workspace.markdown-dialect` 输出 27 都要求三种界面同一分类。
- **如何核实**：`sed -n 40,90p packages/neuro-book/src/plugins/markdown/web/plugin.ts`；`rg "syntaxCatalogKey" packages/neuro-book/src/plugins/lab`。
- **建议改法**：计划写明六个服务组件全部过 `withHost`（`InlineChip`、`MarkdownImage` 也过：它们读 `fileIcon`）；Lab 提供一个 `labMarkdownHost()`（用 nbook 的适配），所有直接挂包组件的 fixture 经它 provide。再加一条 nbook 侧测试：经 `startMarkdownBrowserHost` 取 `markdownKey` 的六个组件，各挂一次，断言 `/设定/林雪.md` 是文件图标（见第 5 条）。包的缺省宿主可以考虑在开发模式下对“没有 provide”记一条 `console.warn`，让漏 provide 不再静默。

## 3. 【重要 / 正确性】小块的三条“普通 DOM”路径拿不到 provide/inject，计划没有写宿主怎么传进去

- **位置**：计划 46–64 行（宿主经 provide/inject 交给组件）、入口表 `./chip`、`./editor`。
- **现象**：画小块的地方有四处，只有一处是 Vue 组件：
  - `InlineChip.vue`：可以 inject。
  - `display/renderer.ts` 的 `decorateLinks`：普通函数，调 `classifyTarget`、`chipView`、`renderChipIcon`，入参是 `StaticViewHost`（`{document, locale, resolveAsset, activate, report}`），没有 targets、fileIcon。
  - `editor/reference-links.ts`：ProseMirror 插件，同样调 `classifyTarget`、`chipView`、`renderChipIcon`，入参是 `MarkdownViewHost`（`{base, locale, assets}`）。
  - `display/static-views.ts` 的图片：`render(h(MarkdownImage…), dom)` 挂到普通 DOM，没有 `appContext`，里面 inject 一律拿到缺省。现在 `MarkdownImage` 不 inject，所以安全；这是约束，计划没写“MarkdownImage 永远不能依赖宿主”。
  计划只说“宿主经 provide/inject 交给组件”，所以实现者要自己发现：`chipView(input)` 要多收 `targets` 与 `fileIcon`，`StaticViewHost`、`MarkdownViewHost` 都要加字段，`MarkdownControl` 要 inject 后塞进 `viewHost`，`createMarkdownEditorExtensions` 的签名要变。这几处的任何一处漏掉，行为是静默退回缺省分类。
- **同一处的类型冲突**：`chip.ts` 现在已经导出 `ChipIcon = {file: CatppuccinIcon} | {className}`；计划在 `host.ts` 里又定义了另一个 `ChipIcon = {className} | {render}`。同名不同形，`./chip` 与 `./host` 同时导出会撞。并且 `InlineChip.vue` 用 Vue 组件 `FileIcon.vue`（带 `svg[data-file-icon]`、`data-icon`，`InlineChip.dom.test.ts` 靠它断言）画文件图标；宿主给的是 `render(document) => Element`，Vue 模板里要用一个把 Element 挂进 span 的小包装（`onMounted` 里 `append`，名字变了要重挂），计划没有写。`busy` 时转圈与 `renderChipIcon(document, icon, busy)` 的分支也要保留。
- **如何核实**：`rg "chipView|renderChipIcon|classifyTarget" packages/neuro-book/src/plugins/markdown/web`；读 `static-views.ts` 末尾的 `render(h(MarkdownImage…))`。
- **建议改法**：计划加一小节“宿主怎么到达四处小块”：`chipView` 收 `{targets, fileIcon}`（或一个已解析的 `ChipEnv`），`StaticViewHost`/`MarkdownViewHost` 加 `chipEnv`；把 `host.ts` 的图标类型改名（如 `HostIcon`），文件图标的 Vue 路径写明；在 `MarkdownImage.md` 写一句“不 inject 宿主”，并在包内加一条测试断言它在无 `appContext` 时可用。

## 6. 【重要 / 不变量】Component Lab 的组件索引按 `plugins/*/web/components/**` 扫描，搬走后 11 个组件会从 Lab 消失；计划没有 `lab-sources`

## 7. 【重要 / 接口】`./language` 的公开面不足以让留在 nbook 的 `language-registry.ts` 与 `syntax-catalog.ts` 成立

- **位置**：计划 29–44 行入口表、88–90 行“内置方言的顺序”。
- **现象**：逐个核对留下的文件引用了什么：
  - `language-registry.ts`：`createMarkdownLanguage`、`MarkdownLanguage`、`builtinOrder`（含每个内置方言的 `order`）、`coreSyntax`、`createRawSyntax`、`MarkdownSyntax`，加 `@tiptap/core` 的 `flattenExtensions`。计划的 `./language` 只写“`createMarkdownLanguage`、`MarkdownSyntax` 等类型、内置语法模块与 `builtinSyntaxes()`、`defaultMarkdownLanguage()`、`codecFor`、`schemaFor`”，没有 `coreSyntax`、`createRawSyntax`。`createRawSyntax` 是组装的实现细节（`createMarkdownLanguage` 内部自己追加，`language-registry` 用它只是为了算“保留名字”），把它公开等于冻结一个内部形状。
  - `compose` 把内置方言与外来方言按 `order` 数字混排（外来的 order 夹在内置的 10..70 之间）。`builtinSyntaxes()` 如果只返回有序列表、没有 `order`，nbook 就要靠 `syntax-ids.ts` 反向配 id 再配 `BUILTIN_DIALECTS[id].order`；包里的顺序与声明里的数字两份要同步，计划的“核对测试”只比对顺序，不比对数字插入位置的语义。
  - `syntax-catalog.ts`：`MarkdownSyntax` 的 `blockOpens`、`inlineTags`、`extensions`、`writeBlock/Inline/Mark` 字段都被 `namesOf` 读；这些字段成了包的公开合同，外来方言作者（`web/contracts.ts` 再导出的 `MarkdownSyntax`）按它写。计划没有说这是公开面，也没有说变更规则。
  - `schemaFor` 现在在 `display/renderer.ts`（同文件含 `DOMSerializer`、`decorateLinks`）；计划把它列在 `./language`。要拆出去，或者让 `./language` 里的 `schemaFor` 单独成文件，否则 `./language` 会带进展示器的 DOM 代码。
  - `web/contracts.ts`（供贡献方言的插件做类型引用）要改成从包再导出 `MarkdownSyntax`；示例插件或第三方若写了 `nbook/plugins/markdown/web/syntax/…` 深导入就会断，需要 `rg` 确认（我查过 `examples/` 与 `e2e/`，没有）。
- **建议改法**：计划写出 `./language` 的完整导出清单，并把 `order` 带进 `builtinSyntaxes()` 的返回（`{name, order, syntax}`），删掉 `syntax-ids.ts` 的“配 id”一步，只留 `BUILTIN_DIALECTS` 与它在测试里逐项比对；`createRawSyntax` 不公开，把“保留名字”的集合改由包提供（例如 `reservedSyntaxNames()`）。

## 8. 【建议 / 代码质量】包的依赖清单写得比实际少，Bun 提升（hoist）会掩盖缺漏

- **位置**：计划“技术选型”（11–13 行）。
- **现象**：计划只列 `marked`、`marked-cjk-friendly`、`entities`、TipTap 与 `@tiptap/pm`。我按 import 统计，要搬的代码还用：`@tiptap/starter-kit`、`extension-image/link/table/paragraph/code/list/placeholder`、`@tiptap/vue-3`（`PromptEditor`、`PromptTokenView`、`PromptPasteBlockView`）、`@tiptap/pm` 的 `history`/`gapcursor`/`transform`/`view`/`state`、`@notnotype/nb-ui/components`（`IconButton`、`SuggestionMenu`）；测试用 `fast-check`、`@vue/test-utils`、`happy-dom`、`@notnotype/neuro-book-test-support/wait`。neuro-book 的 `package.json` 里 `@tiptap/extension-list` 在 `dependencies`、其余 TipTap 在 `devDependencies`，`entities`、`marked-cjk-friendly` 在 `dependencies`。根 `node_modules` 现在全部提升（`marked` 17.0.6、`@tiptap/pm` 3.27.3、`entities` 8.0.0 都只有一份，我查过），所以漏声明时本机一切正常，类型检查也通过；只有在别的包单独安装或将来换安装方式时才暴露。
- **建议改法**：计划列出完整依赖并说明 dependencies 与 devDependencies 的分法（nb-agent-ui 的做法：运行时由宿主打包的放 devDependencies，`vue` 放 peer）；`boundary.test.ts` 加一条“源码里 import 的第三方包都在 package.json 里声明”的检查（`neuro-book-test-support/import-boundary` 已有扫描器，可复用）。nbook 保留自己对 TipTap 的声明（`MarkdownControl.vue` 仍直接用 `@tiptap/core`），两处版本写成同一个固定值即可，装出两份的风险我没有发现。

## 9. 【建议 / 接口】缺省目标分类是第二份 `SCHEME`/`EXTERNAL` 逻辑；`encodeFile` 的调用合同不清

- **位置**：计划 66–82 行。
- **现象**：
  - 缺省规则“`http`、`https`、`mailto` 是 external，别的都是 other”要重新写一遍方案识别（`SCHEME` 正则、小写化、去查询与片段取 `name`）。nbook 的 `classifyTarget` 里同样一份。两份规则对大小写（`HTTPS://x`）、`mailto:`、`name` 的取法各自演化，两个宿主下同一个链接会分成不同类。
  - `encodeFile(target)` 的注释写“文件目标写进链接时的地址”，但调用点 `promptReferenceText(label, target)` 对任何目标都调用（外部链接也会传进来）；nbook 的 `encodeFileTarget` 自己判方案、对外部地址原样返回。接口没说“调用方不先判类”，实现者（另一个宿主）可能只处理文件目标而对其它输入崩。
  - `Target.name` 对 `other` 也有值（nbook 里 `设定/林雪.md`、`base` 为 null 时是 `other` 且 name 是 `林雪.md`），计划没规定 `name` 在非文件类别里的含义。
- **建议改法**：缺省规则放在 `.`，nbook 的 `classifyTarget` 先委托它判 external/other，再叠加 work/user/local；`encodeFile` 的注释写明“对任何目标调用，不属于文件的原样返回”；`name` 的含义写进 `Target`。

## 11. 【建议 / 别扭之处】给 `InlineChip` 这类展示零件加隐藏通道，与组件规范“外部能力由父组件通过 props 传入”相悖

- **位置**：计划 46–64 行；对照 `docs/standards/code/components.md`（“组件产生外部影响时发出事件…需要外部能力时由父组件通过 props 传入可替换的入口”，`state:inject` 单列计入耦合）。
- **现象**：`InlineChip` 现在只有 props，唯一的外部依赖是 `FileIcon`；改后它多了一条 inject 通道，读 `targets`、`fileIcon`。`MarkdownImage`（已知不应用宿主）没问题。`MarkdownDisplay` 今天就 inject 目录与 report，属已有的通道。
- **取舍**：这是“有理由的取舍”还是能用普遍做法？调用 `InlineChip` 的有 `PromptTokenView`（TipTap 节点视图，inject 可用，见下）和 Lab；让这些调用方按需传入已算好的 `kind`/图标（`InlineChip` 的 props 里增加可选的 `view?: ChipView`，缺省走内部 `chipView`），可以让它保持“纯展示”。不改也能工作，但每增加一个 inject 点，Lab 的 `验证入口`、标签、假宿主就多一份维护。
- **关于节点视图能否 inject**：我读了 `@tiptap/vue-3` 的 `EditorContent`，它在挂载时把自己的 `instance.provides` 放进 `editor.appContext` 并调 `editor.createNodeViews()`，`VueRenderer` 把 `appContext` 赋给 vNode，所以 `PromptEditor` 里经 `VueNodeViewRenderer` 渲染的 `PromptTokenView`、`PromptPasteBlockView` 在 `EditorContent` 挂上之后能 inject 到祖先 provide（首次构造 Editor 时那一轮的节点视图没有 appContext，但紧接着会被 `createNodeViews()` 重建）。这一条我没有在真实浏览器里验证，建议第 4 片给 `PromptEditor` 加一条测试：外层 provide 一个自定义 `targets`，断言初始文档里的引用小块用的是它。
