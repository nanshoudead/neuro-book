### 1. 关闭询问期间新增可编辑副本后，“保存”回答被跳过，源标签直接关闭但文件不保存

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/editor/web/area.ts:560–571,579–582`；调用入口 `web/commands.ts:95,104–105,196,204–205`。
- **现象**（从代码推断）：A 是 dirty 文档最后一个可编辑标签，关闭 A 后出现询问；等待回答时经公开打开/拆分命令建立 A 的另一个可编辑标签，再回答“保存”。`nowShared !== shared` 触发 `continue`；下一轮 `shared=true` 且源视图没有自己的未裁决输入，直接在第 561 行 `break`，根本不到 `documents.save`。结果是源标签关闭、另一标签仍 dirty、磁盘仍是旧内容。相同变化下“不保存”也被直接跳过，而不是计划要求的重新询问。
- **为什么是问题**：用户明确选择“保存”，关闭动作却成功结束且没有保存；第三版计划第 29 行要求状态变了重新问，不是重新计算后静默取消回答的语义。此处不是前两轮“丢弃范围没有重验”的重复：新加的重验分支正是丢掉保存意图的原因。base 的关闭路径在非取消、非丢弃回答后会执行 `documents.save`，没有本次新增的 `continue`。
- **如何核实**：主 Agent 在真实命令服务与 Files 场地中打开 A、修改正文，执行 `nbook.editor.close {tabId: A}`；等询问可见后，通过命令服务执行 `nbook.editor.split-right {tabId: A}`（或 `open` 到另一个组），再点“保存”。核对关闭结果、存活标签的 dirty 与磁盘正文；应真正保存或再次询问，不能无写入地报告关闭成功。本轮未运行；若只在 `area.test.ts` 里直接调用控制器摆时序，只能算公开控制器合同证据，仍需确认真实命令入口在询问期间接受该操作。
- **建议改法**：把“是否需要询问”与“已收到的保存/丢弃决定”分开。状态变化需要重新确认时，携带这一事实进入下一次显式询问，不能回到可直接关闭的分支；或者在文档身份仍有效时保留并执行保存意图。不要靠禁用所有命令绕过关闭事务的重验合同。

### 2. “关闭已保存”把尚未取得引用的恢复标签当作干净，忽略同地址已加载文档的 dirty

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/editor/web/area.ts:628–633,819–821`；惰性取得引用在 `:182–189,347–350`；恢复标签的既有判据见 `area.test.ts:658–676`。
- **现象**（从代码推断）：恢复一个两组会话：左组活动 A，右组有 A、B 且活动 B。恢复后右组的非活动 A 没有 `references`，但左组已加载同一份 A。左组修改 A 后，在右组执行“关闭已保存”，`saved(右组 A)` 因没有该标签自己的引用直接返回 true，右组的 dirty A 被纳入并关闭。右组原本应只关闭干净的 B、留下 A。
- **为什么是问题**：正文按地址唯一，dirty 属于文档，不属于某个标签有没有触发过惰性加载；Spec 输出 51 要求筛掉需要保存的文档，输出 5 又保证恢复标签先出现、正文按需读取，这两条必须同时成立。现有测试只覆盖每个候选都已经有引用的情况。base 没有“关闭已保存”，这是新增路径的缺口，不把惰性加载本身记为回归。
- **如何核实**：主 Agent 用真实组模型生成上述合法快照，经真实 `createEditorArea` 恢复；等左右活动文档就绪，在左组编辑 A，再从右组 B 的标签菜单执行“关闭已保存”。断言右组 A 保留、B 关闭、结果 `closed=1`，并核对共享 A 的正文仍 dirty。另补 A 尚未交出的控件缓冲：判据应先结算共享文档，而不是只查标签引用。本轮未运行，不能以直接 `commit` 的控制器用例代替缓冲输入的控件验证。
- **建议改法**：以 `references.get(tab.id)?.document ?? documents.get(tab.address)` 查当前已存在的共享文档，存在时先结算再检查；两个地方都没有文档时才按“尚未读取、无已知修改”处理。无须为筛选强制加载所有恢复标签。

### 3. 横向滚动中的可见行尾被当作完整分区末尾，拖放会越过尚未显示的标签

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/editor/web/tab-drag.ts:108–130`；共享原语 `packages/nb-ui/src/components/layout/grid-drop.ts:277–295,323–328`；真实滚动容器 `EditorTabBar.vue:242–252`。
- **现象**（从代码推断）：关闭多行，普通标签完整顺序为 A、B、C、D、E，横向视口只露出 A、B、C。在 C 的可见尾缘放下 A，共享 `resolveListInsertion` 裁掉视口外的 D、E，返回 `beforeId=null`，意思只是“最后一个可见成员之后”。`stripDrop` 只尝试找下一条行，没有下一行就仍把 null 交给模型，实际得到 B、C、D、E、A，而不是 B、C、A、D、E。多行模式下超宽固定行也有同一缺口。
- **为什么是问题**：插入反馈贴的是 C 的可见尾缘，提交却去完整分区最后，显示与动作不一致；第三版计划第 81 行明确要求把行尾转换到完整顺序里的后继。两轮设计审查提出过这个合同，本次实现只处理“下一行存在”的情况，横向裁剪后的后继仍未落实。base 没有标签拖动入口。
- **如何核实**：主 Agent 在真实浏览器打开至少 5 个足够宽的普通标签，关闭多行，让 D、E 在视口右侧不可见；把 A 拖到 C 可见尾部，核对插入线和最终完整标签顺序。另用超宽固定行重复。必须使用真实布局与滚动，不用伪造 `getBoundingClientRect`；本轮未运行。
- **建议改法**：保留完整分区顺序，依据最后一个实际参与几何判定的成员取得其完整后继，把 null 转成这个后继；后继确实不存在时才表示分区末尾。用同一后继同时决定动作与跨行指示线，不能只查下一条 `Line`。

### 4. 正文中央落点的原位判断漏掉固定分区，只有固定标签的组无法通过拖入正文取消固定

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/editor/web/tab-drag.ts:148–155`；应执行的模型转换在 `web/groups/groups.ts:363–370`。
- **现象**（从代码推断）：组里只有一个固定的 A，把 A 拖到本组正文中央；或组里全是固定标签，把最后一个固定标签拖到正文中央。`last === dragged.tabId` 被判为原位，返回 `action=null` 和“保留”反馈；标签仍固定。这个落点的合同却是“移到普通分区末尾”，因此应取消固定，即使数值位置碰巧不变。
- **为什么是问题**：原位必须同时满足组、分区与位置相同。`stripDrop` 已按目标分区筛完整顺序，模型也会比较 `isPinned`；只有 `contentDrop` 把“最后一个标签”误当成“普通区最后一个标签”，上层拦截掉本来正确的模型转换。Spec 输出 50、55 与计划第 81 行的正文中央语义不成立；base 没有该路径。
- **如何核实**：主 Agent 在真实浏览器仅打开 A、固定它，再从名字拖到正文中央，断言同一个标签 id 仍存在且不再固定；再测 P1、P2 全固定时拖 P2，以及普通区末尾普通标签的真正原位。本轮未运行；现有拖动 e2e 没有正文中央与固定标签组合。
- **建议改法**：原位判断同时核对被拖标签不固定；更简单的是让正文与标签条共享一个按完整分区顺序判断原位的小函数，避免两个地方各自维护不同的不变量。

### 5. 固定分区为空时，标签条没有任何能产生“固定”动作的落点

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/editor/web/tab-drag.ts:65–79,110–129`；实际行生成 `web/components/EditorTabBar.vue:49–53`。
- **现象**（从代码推断）：目标组没有固定标签时，多行只生成 `normal` 行；`linesOf` 不生成空固定行，`partitionOf` 对该行所有非固定成员与 null 一律返回 normal。因此无论指针位于第一行上沿还是其它位置，标签条都不可能产生 `partition="pinned"`。用户只能先通过菜单固定至少一个标签，才有可拖入的固定区；空组同样没有该入口。
- **为什么是问题**：第三版计划第 81 行已经明确“空的固定区：拖到第一行之上的区域时进固定区”，这是已确认的落点合同，不是要求重议固定行设计。当前不是命中区域太小，而是解析器里根本没有这一分支。base 没有固定与标签拖动。
- **如何核实**：主 Agent 用真实浏览器准备一个没有固定标签的目标组，把另一组普通标签拖到目标第一行上沿的约定区域，检查反馈与落地的 `pinned`；另测空组和已有固定标签作为对照。当前静态判据已经证明 `partitionOf` 在“所有成员不固定”的输入下只能返回 normal，运行验证应确认真实命中区域，不用伪造行矩形。本轮未运行。
- **建议改法**：在落点解析中显式表示空固定分区，按计划的第一行上沿区域产生 `{partition: "pinned", before: null}`，并让反馈显示这次转换。该分区不必增加一个永久显示的空行；不要把“能不能固定”继续依赖于已有标签的 `pinned` 属性。
