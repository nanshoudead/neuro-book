# V9 小说记忆图：模型只写草稿，程序生成其余

开发者在看过前 5 章金标、查看器、抽取管线和第十二节的四轮试验后接受本提案的长期取舍：以 V7 为基础的读者视角记忆图，模型只写章草稿、程序生成其余记录。接受不等于已接入产品：抽取仍不稳定（第十二节第 9 小节），下一步先做稳抽取，Spec 和 Work 待抽取稳定后再立。2026-10-13 开发者决定评测停在 t34、转向立 Spec；立 Spec 前要定的事见第十二节 12.11 小节。

- 查看器：t28（w00005 分支 `feat/w00005-v6-ingest-viewer` 上的 `.agents/works/w00005-novel-understanding-spike/tasks/t28-v9-viewer/README.md`），金标页面是 `tasks/t28-v9-viewer/viewer-v9.html`

## 一、问题

五轮评测（见 评测体系提案（w00005 分支上的提案 `docs/proposals/novel-memory-evaluation.md`） 和 w00005 的 t19 到 t25）得出三条结论：

1. **记忆图有帮助，但不明显。** 100 章规模下，带 V8 图的一组比只搜原文少错约 5 个百分点，和通读全文接近。
2. **图组错在判断，不在找材料。** 第四轮图组每轮平均答错 21.3 题，其中 20.3 题已经找到了关键材料。错误集中在三类：把读者知道的事当成角色也知道（约四成）、认错人或认错身份、把推断说成原文明说。
3. **V8 的图装不下回答这些题需要的东西。** 具体是：
   - 没有全书统一的对象入口。“地狱猫”在 20 个章节各有一条记录，只有 6 条连到了前面。
   - 110 条知情记录里没有一条“不知道”。
   - 680 条说法用了 420 个关系名，343 个只用过一次，程序没法按类别查。
   - 跨章引用有歧义，模型写出的 857 个跨章引用里有 101 个指向不明。
   - 没有余额、道具、任务进度这类状态的记录，也没有悬念的记录。

更早的 V7 表达力足够，但它的金标是高水平模型逐条写出来的：前两章 4,234 字有 615 条记录，其中约六成是可以由程序生成的机械内容（直接依据、评估、提及、谓词定义）。旧管线让便宜模型把这些全部写一遍，成本和返工都很高。

## 二、目标与非目标

**目标：**

1. 图里直接有答案的题型要覆盖现有题库的 12 类，以及新补的 8 类“只搜部分原文答不全”的题（别名穷举、全书穷举、名字何时可见、故事时间与倒叙、认识被后文推翻、反查出处、逐条依据、多个角色的不同认识）。
2. 模型只写需要读懂原文才能写的内容，其余由程序生成和检查。
3. 任何查询都带“读到哪里”，后文才有的名字、身份和知情不会出现在前面。
4. 每条记录都能回到原文出处。
5. 抽取成本朝每百万字 1 到 2 美元的目标靠近，实际数字以试跑为准。

**非目标：**

- 不做逐条的论证和评估记录，不做谓词定义表，不做对象类型约束。
- 版本和变更管理留给存储层，草稿里不出现。
- 本轮不接产品、不迁移旧数据、不替换 nb-memory。
- 本轮只验证到前 5 章，长书下的上下文挑选和整理步骤还没有证据。

## 三、设计概览

V9 分两层：

| 层 | 是什么 | 谁来做 |
| --- | --- | --- |
| 章草稿 | 每章一份，记下读懂这一章才能写的内容 | 模型（抽取时）或标注者（做金标时），按同一份规则 |
| 记忆图 | 把各章草稿合在一起，补上定位、推导和核对 | 程序 |

草稿里有 12 类内容，另有每隔若干章写一次的整理稿：

| 内容 | 一句话解释 | 书里的例子 |
| --- | --- | --- |
| 段落块 | 把全章连续切成小块，每块一两句概括 | “回忆五分钟前：连上三个夜班后在面摊倒下”（第 1 章第 15 段） |
| 时间点 | 故事里的一个时刻，尽量标出主线第几天 | 第 1 天；“前世倒下”在第 1 天之前，相隔五分钟 |
| 对象 | 人物、身份（马甲）、组织、地点、物品、概念、任务 | 苏天晴；墨丘利秘典；魔法少女“风信子”这个身份 |
| 称呼 | 对象在书里的每个叫法和首次出现位置 | 黑色古书（1.7），墨丘利秘典（1.29，自报），小破书（1.49，苏天晴的叫法） |
| 提及 | 只标程序认不出的称呼归属 | 第 3 章的“苏天晴小姐”指的是原主人 |
| 说法 | 一条陈述加它的出处 | “古书自称墨丘利秘典，从星空彼岸来寻找适格者”，出处：台词，古书对苏天晴说 |
| 秘密 | 有人知道、有人不知道的关键事实 | 风信子就是南小风 |
| 知情 | 谁对哪条说法或哪个秘密知道、相信、怀疑、不知道 | 苏天晴在第 5 章从秘典情报页读到风信子的真名 |
| 情节 | 一段有头有尾的事，含在场者、步骤、结果、与前情的关系 | “签完才得知要当反派魔法少女，苏天晴后悔” |
| 状态变动 | 会变的量的每一次变化 | 神典石：启动资金 200，买强化药花 50，任务奖励 100 |
| 疑问 | 书里提出、暂时没回答的问题，以及后来的进展 | 造物主是谁（1.66 提出，未解） |
| 整理稿 | 对象摘要、故事线、合并建重的对象 | 苏天晴的概览、性格、经历各几句，每句列出依据 |

## 四、和 V7、V8 的关系

V9 以 V7 为基础。下面是 V7 的 16 类记录在 V9 里的去向：

| V7 的记录 | V9 的处理 | 说明 |
| --- | --- | --- |
| 实体 | 保留为“对象” | 名字表保留，每个称呼加一句话说明 |
| 局部指称 | 并入“对象” | 身份不明的人、马甲各建一个对象，不再每章每个对象建一条 |
| 归属 | 变成“身份同一”类的说法 | 带确定程度、依据和可见位置，可以先候选后确认 |
| 提及 | 由程序生成 | 模型只标程序认不出的 |
| 披露、事实 | 合并为“说法” | 出处（谁、以什么方式）和断言类型分开记 |
| 谓词定义 | 换成 12 个固定大类加自由小标签 | 程序只依赖大类 |
| 论证 | 变成说法上的“理由和依据”，以及说法之间的印证、反驳、修正 | 直接依据不再单独成条 |
| 评估 | 由程序按阅读位置计算 | 明说、推断、只是可能、被后文印证或反驳 |
| 段落块 | 保留 | 加上时间点和回忆标记 |
| 情节 | 保留 | 加步骤和“以什么身份在场”；要求连接前情 |
| 时间 | 保留为“时间点” | 增加“主线第几天” |
| 知情 | 保留 | 可以指向秘密；听说、读到、相信大多由程序推出 |
| 实体摘要 | 移到整理稿 | 不必每章重写 |
| 综述 | 整理稿里的“故事线” | |
| 待观察、变更管理 | 去掉 | 属于存储层 |
| 没有 | 新增秘密、状态变动、疑问 | 对着评测里错得最多的题型 |

和 V8 相比，V9 多了全书统一的对象名册、称呼的可见位置、秘密与“不知道”、状态变动、疑问、时间点、情节步骤，并且编号全书唯一，不会再出现指向不明的引用。V8 的“说法带来源”这一点保留了下来。

## 五、各部分的设计

### 1. 对象、称呼和身份

**名册。** 每个对象全书只有一个编号，后面的章节直接引用它。编号里带章号（`e4-2` 是第 4 章新建的第 2 个对象），所以不会重复，也不会指错。

**称呼带位置。** 每个称呼记下首次出现的段落。查询“读到第 1 章第 20 段”时，古书显示为“黑色古书”；读到第 29 段之后才显示“墨丘利秘典”。对象的整理标签只能用首次出现时已知的信息。

**马甲是单独的对象。** 书里有人只认识一个身份、不知道背后是谁时，这个身份单独建对象，再用一条“身份同一”的说法连到本人。例如“风信子”和“南小风”是两个对象，第 4 章旁白写明“魔法少女风信子，真名南小风”，这条说法把两者连起来，同时它也是一个秘密。这样角色的看法始终挂在他认识的那个身份上：苏天晴在第 4 章对“风信子”的评价不会被算到“南小风”头上，因为那时她还不知道这个名字。

**读者视角和角色视角。** 查询时程序按“谁在看”合并身份：
- 读者视角：合并此时旁白已经确认的身份。
- 某个角色的视角：只合并这个角色此时知道的身份。

**身份不明的人。** 出场时看不出是不是已有的某个对象，就新建一个对象，另写一条标为“只是可能”的身份说法；以后原文点明了，再写一条确定的说法并标明它印证了前一条。前面的记录不用改。

**同名不同人。** 主角和这副身体的原主人都叫苏天晴，是两个对象。程序默认把称呼算给最早登记它的对象，个别地方指另一个对象时，草稿里单独标出。

### 2. 说法

一条说法包含：一句完整的话、大类、涉及的对象、出处。

**出处**记四样：原文位置、渠道（旁白、台词、心理、文字、作者声明）、谁说的或谁想的、谁听到或读到。

**断言类型由程序按渠道填，不由模型自由填：**

| 渠道 | 断言类型 |
| --- | --- |
| 旁白 | 世界事实 |
| 心理 | 这个角色的信念 |
| 台词、文字 | 这个角色或这份文字的说法 |

所以“古书自称从星空彼岸而来”只会是古书的说法，不会变成事实。要把角色的话记成事实，必须另外写明理由。

**12 个大类**：身份同一、亲属、人际关系、所属、持有、所在、特征、设定与规则、目标与任务、态度、事件、其他。每条说法还可以有一个自由填写的小标签，程序不依赖它。

**明说和推断。** 原文没有直接写、由几处内容合起来得出的，标为推断，并写出理由和依据的说法。

**后文和前文的关系。** 后面的说法可以标明它印证、反驳或修正了前面哪一条。例如英雄协会的公告说风信子“中了怪人的陷阱”，而前一章旁白写的是苏天晴设的局，后一条标为与前一条相反。查询时，前一条说法上会显示“与后文相反”或“被后文印证”，并且只在读到后文之后才显示。

**记什么、不记什么。** 关系、身份、来历、能力、规则、目标、态度、角色对一件事的说法或想法要记；一次性的动作、表情、环境描写不单独记，写进情节的步骤。这条规则用来控制“桌子有四条腿”这类细枝末节。

### 3. 秘密和知情

**秘密**是少数关键的、有人知道有人不知道的事，主要是身份秘密。每个秘密在后面每一章都会出现在给模型的“已有记录”里，让模型专门检查：这一章有没有人得知、起疑，或者表现出仍不知道。

**“不知道”分三种情况处理：**

| 情况 | 怎么记 |
| --- | --- |
| 原文明说（“她全然没有注意到”） | 记“不知道” |
| 原文没明说，但表现看得出（把两个身份当成两个人、当面问“你是谁”） | 记“不知道”，标为推断，写明是什么表现 |
| 原文完全没有涉及 | 不记。查询时显示“没有记录”，不说“不知道” |

**程序推出的知情。** 角色的心理活动意味着他自己相信；写了听者的台词和写了读者的文字意味着对方听到或读到。这两类不用模型写。

**知情表。** 查询某个秘密时，程序给出一张表：读者一行，每个有记录的角色一行，写明状态、从哪里起、怎么知道的。

### 4. 状态变动

记“某个量变了”：谁的、哪个量、增减多少或设为多少、原因、出处。只记真正发生的变化，不记悬赏和标价。

- 数量（神典石、粉丝数）由程序逐笔累加。原文在变动的同时写出了变动后的数值时，程序用它核对累加结果，对不上就报错。
- 持有的东西记得到、失去、用掉。
- 任务进度、强化阶段这类记“设为某个值”。

### 5. 疑问

记书里提出、暂时没回答的问题，以及后来每次再提起、部分解答、解答的位置。解答要指向给出答案的说法，并说明答案是旁白确认的、只是角色说出来的、是角色自己心里的想法，还是推断。查询“读到第 N 章还有哪些悬念”时，程序按位置筛选。

### 6. 时间点、段落块和情节

- **时间点**尽量标“主线第几天”和一天里的时段。主线开始之前的事（前世、半年前）没有天数，只记它在哪个时间点之前、相隔多久。程序据此排出故事里的先后。钟点和日期如果比这段戏本身交代得晚（先写她回到家，过了十几段才说离开时是八点），可以标明是哪一段交代的，在那之前查询不显示。
- **段落块**连续覆盖全章，每块指向一个时间点；回忆和倒叙单独成块并标出来。所以“这一段是不是回忆”“这件事发生在第几天”都能直接查。
- **情节**记在场者（可以写明以哪个身份在场）、步骤、结果，并且必须连到前面相关的情节：在它之后、接续、回述、由它导致、动机来自、因它才可能。“某人在哪些章出场”查的是情节的在场者；“在哪些章被提到”查的是程序找到的称呼。

### 7. 整理稿

每隔若干章做一次，包含三样：合并建重的对象；给主要对象按方面写摘要（概览、外貌、性格与说话方式、人际关系、经历、能力与道具、处境与目标），每句话列出依据；把相关情节归成故事线。

## 六、程序生成和检查的部分

**生成：**

| 内容 | 怎么得到 |
| --- | --- |
| 称呼在原文里的每次出现 | 用名册里的称呼逐段匹配，长称呼优先 |
| 断言类型和持有人 | 按出处的渠道 |
| 说法的故事时间 | 取出处所在段落块的时间点 |
| 听说、读到、相信类的知情 | 从说法的出处推出 |
| 数量的累计值和核对结果 | 逐笔累加 |
| 时间点的故事先后 | 按天数、时段、钟点和先后关系排序 |
| 每条记录从哪里起可见 | 取出处的最后一段 |
| 对象的显示名 | 取阅读位置之前最新的主要称呼；两个对象显示名相同时自动带上说明文字 |
| 身份合并、知情表、疑问状态、当前状态 | 查询时按阅读位置计算 |

**检查：**

- 引用的记录是否存在，编号是否重复。
- 原文位置是否有效，是否在本章。
- 段落块是否连续覆盖全章。
- 称呼是否真的出现在所标的段落里。
- 记录的文字里有没有用到后文才出现的称呼。
- 台词、心理、文字是否写了是谁的；把角色的话记成事实时是否写了理由；推断是否写了理由。
- 账本累加结果和原文给出的数值是否一致。
- 时间点的先后关系是否自相矛盾。
- 只提醒、不算错的两项：章中间只含分隔线的段落块；手写的知情和程序本来就会生成的重复。

## 七、抽取管线

逐章串行，每章四步：

1. **写时间点和段落块。** 模型读已有的时间点和本章原文，输出本章的时间点和段落块。这一步用最低的思考档。
2. **写其余记录。** 模型读“已有记录”和本章原文，输出对象、称呼、说法、秘密、情节、知情、状态变动、疑问。“已有记录”由程序从截至上一章的记忆图生成，包含名册、秘密和知情表、未解的疑问、当前状态、时间点、最近的情节、已有的说法。
3. **程序编译和检查。** 有问题时把问题清单发给模型，只让它改出问题的那几条，最多两轮。
4. **兜底。** 两轮之后仍有问题的记录直接丢弃并记账，保证每一章都能编译。

每隔若干章加一步整理：模型读记忆图，输出整理稿。

和旧管线的区别：模型不写机械内容；不逐条复核；修复只改出问题的记录，不重写整章；历史引用用全书唯一的编号。

两步调用共用同一段系统提示词（规则加一个与样书无关的虚构示例），让接口的前缀缓存可以在所有章节之间复用。

## 八、对评测题型的对应

| 题型 | 图里对应的内容 |
| --- | --- |
| A 定位概括 | 段落块、情节、故事线 |
| B 认人 | 对象、称呼及位置、身份同一的说法、读者和角色两种视角 |
| C 来源可信度 | 说法的出处和断言类型、印证和反驳 |
| D 关系 | 亲属、人际关系类的说法，对象摘要 |
| E 情节因果 | 情节的步骤和相互连接 |
| F 枚举计数 | 名册、称呼出现处、情节在场者、状态变动 |
| G 设定汇总 | 设定与规则类的说法、概念对象、对象摘要 |

## 十二、试做结果（2026-10-03）

设计、结构定义、金标、查看器和抽取管线都已做出，范围是前 5 章（12,834 字）。这一节记录做出来之后看到了什么；过程和证据见 t27（w00005 分支 `feat/w00005-v6-ingest-viewer` 上的 `.agents/works/w00005-novel-understanding-spike/tasks/t27-v9-schema-gold/README.md`）、t28（w00005 分支 `feat/w00005-v6-ingest-viewer` 上的 `.agents/works/w00005-novel-understanding-spike/tasks/t28-v9-viewer/README.md`）、t29（w00005 分支 `feat/w00005-v6-ingest-viewer` 上的 `.agents/works/w00005-novel-understanding-spike/tasks/t29-v9-ingest/README.md`） 各自的过程记录。

### 1. 金标：结构放得下，要写的量是 V7 的四分之一

- 前 5 章的金标共 433 条草稿记录，程序另外生成 756 项（称呼在原文里的出现处 469、断言类型 118、说法的发生时间 105、派生的知情 48 等）。折合每千字约 34 条需要人或模型来写；V7 金标是每千字约 145 条。
- 12 类内容都用上了：40 个对象和 64 个称呼，118 条说法，3 个秘密（其中“狐娘魔法少女就是苏天晴”有两个角色记了“不知道”），15 笔状态变动（例如神典石：启动资金 200，花 50，得 100，程序累计出 250），21 个疑问和 11 次进展，12 个时间点（3 个在主线开始之前）。
- 金标经过一轮独立审查：逐条核对 432 条，改了 58 处。问题集中在三类：规则更新后没跟上的写法、保留语气丢失或挂错对象、马甲出场时标签用了后文才有的信息。数值没有错。审查结论是改完后可以作为参考答案。
- 审查对规则和格式提了 10 条意见，采纳 7 条并已落实：钟点和日期可以标明“从哪一段起才交代”；疑问解答的可靠度增加“角色自己的想法”；类别和个体的写法约定；程序会生成的知情不要手写；马甲和秘密的标签只用当时已知的信息；分隔线单独成块时程序报警；显示名相同时自动带上说明。

### 2. 查看器：按阅读位置过滤在页面上可以直接验证

三个离线页面：金标、管线最好的一次试跑、管线最便宜配置的一次试跑。把“读到”往前拨，后文才出现的称呼、身份、知情、状态变动、钟点都会消失。三个页面都通过了无界面浏览器的自动检查（9 个页签都能打开，没有报错，不联网）。开发者的人工审查还没有做。

### 3. 抽取管线：跑得通，质量和成本都还没有达标

| 规则那段提示词每次都命中缓存时的估算 | 15.4 | 15.4 | 22.1 | 14.1 到 22.1 |
| 金标的对象，管线找到 | 65% | 65% | 83% | 55% 到 83% |

说法和疑问是否对得上、两边的秘密是不是同一件事，由模型判断，没有人抽查；同一份内容判两次，结果会差几个百分点。

可以说的结论：

- **跑得通。** 7 次试跑每章都编译通过。最便宜的配置每章两次调用。模型多写出来的说法里被判为有错的，每次只有 0 到 1 条。
- **成本还没有进目标区间。** 目标是每百万字 7 到 14 元（1 到 2 美元）。最便宜的配置测得 22 到 24 元，是目标上限的 1.6 到 1.7 倍：输入约 15 元，输出约 9 元。输入里大部分是每次调用都要重发的那段规则，渠道的缓存时有时无；稳定命中的话总费用约 15 元，仍略高于上限。再往下要靠压缩输出：现在每千字输出约 2,300 token，大约是原文的两倍。高思考档加修复贵在修复：每修一次都把整段提示词重发一遍，7 次试跑的 15 次修复调用里只有 1 次命中过缓存。
- **不修复的配置原先靠“丢记录”过关，这一点已经改掉。** 模型常把“旁白转述某人的看法”（苏天晴觉得、认为、猜测、打算）写成旁白加持有人，却没写这是谁的看法，检查不通过；不修复时程序只能把整条丢掉，试跑 006 因此丢了 16 条说法，占模型写出的六分之一。这种情况意思很明确，现在由整理程序自动补成“这个人的看法”。用同一批回复重放：试跑 006 留下的说法从 80 条变成 96 条，金标说法完全没有覆盖的从 30% 降到 23%；另外两次不修复的试跑（003、005）变化较小。
- **骨架可靠，细节和判断不稳。** 回忆和倒叙的标记、主要对象比较可靠。称呼只登记到五六成；说法有两到三成完全没有覆盖；秘密知情、状态、疑问这三类 V9 新增的内容最不稳定。断言类型约八成一致，不一致的多数是管线更保守（把旁白事实记成角色的看法），少数是把角色的说法或想法记成了世界事实，后一种是要防的方向（逐项统计见 t29 的过程记录）。
- **单次试跑的噪声很大。** 思考档相同、规则只差几句的两次试跑之间（005 对 006，004 对 007）的差别，和高低思考档之间的差别差不多大。例如“第几天”：试跑 006 的多数时间点只写了先后、没写第几天，只有 19% 一致；005 是 93%。每种配置只跑了三四次，目前不能说高思考档一定更好。

### 4. 试做暴露的设计缺口

下面这些都还没有改，列出来供审查时一并考虑。

1. **“第几天”不该让模型直接写总数。** 试跑 003、004 和 006 都把第 5 章的“翌日早晨”记成了第 1 天。更稳的做法和账本一样：模型只写“比上一个时间点晚几天”，程序累加，并在模型同时写了总数时核对。（2026-10-10 已改。结果：模型多数只写“翌日”“当天傍晚”这类文字不写天数，程序补了从文字读天数；但模型判断相隔几天时照样会错，第 4 章那个夜晚被判成晚一天，后面全错一天。见第 8 小节。）
2. **秘密和知情需要更强的约束。** 有的试跑没有给变身后的主角单独建身份，于是“谁不知道她是谁”无处可记；有的试跑想给已有的秘密补内容，格式里没有“补充”的写法，结果建了一个同名的重复秘密。可选做法：程序发现有人以新身份出场却没有对应的秘密时报警；或每章加一步只看秘密清单的复查，代价是多一次调用。（2026-10-10 已加报警并交给修复；改后管线前 5 章的秘密知情表 12 格对 7 格，是历次最好。）
3. **任务进度经常整类漏掉。** 金标里 10 个量有 5 个是任务进度，管线多数没记。规则需要把“任务也是状态”写得更明确，或由程序在任务对象建立时提醒。（2026-10-10 已把任务写进自查清单；改后管线 5 个任务量对 4 个。）
4. **几处表达不了的情况。** 说法的发生时间是推断出来的时没法标明；情节里“以什么身份在场”只能整段生效；后面章节才交代前面某天的日期时，没法补到已有的时间点上；只在书页或公告里被提到、还不知道是谁的具体人物怎么建，规则没有写。
5. **长书没有验证。** 5 章时“已有记录”全部放得进提示词；章数多了要挑选，挑选的效果和成本都没有证据。（2026-10-10 跑到 20 章：“已有记录”约 2.5 万字，还没有触发挑选，每章草稿调用输入 3 万到 5 万 token；100 章时的挑选仍未验证。）
6. **还没有用 V9 的图答过题。** 上面的对照量的是“像不像金标”，不是“答题有没有变好”。管线也只用 gpt-6-luna 试过，没有用真正的便宜模型跑。（2026-10-06 已用金标图和两份自动抽取的图在前 5 章的 13 题上试答，见第 7 小节；还没有用真正的便宜模型跑管线。）

  - **看 51 到 100 章的难题**：8 道题五组 15 份里错了 8 份以上，全读也错。逐题看是题目难、标准答案有问题还是作答规则的问题；不调用模型。
  - 评测要分出几个百分点的差别，得加题或者二审多复核几次取多数；暂不建议，先看 A2 能不能拉开差距。
- 第三轮（2026-10-13，开发者同意把挑章做准、逐题看难题）：
  - **挑章 v2**：挑章 Agent 先在图里查清对象的全部称呼，再按称呼搜出相关记录（说法、秘密、知情、情节、账本等）；程序把这些记录的出处章补进来，总数仍不超过 20 章。标准答案出处所在章的挑中率，51 到 100 章从 69% 提到 76%，全部挑中的作答从 25% 提到 43%；21 到 50 章本来就高（79% 到 80%）。
  - **挑得更全，答错没有减少。** 用一审比（同一个判分器、每份作答单独判）：21 到 50 章 v1 答错 11.1%、v2 21.0%；51 到 100 章 v1 25.3%、v2 23.0%。五组一起二审，v2 全部答错 29.2%，全读 22.6%。标准答案出处章全部挑中的作答，v1、v2 都答错约 19%，和全读差不多：挑全以后剩下的错出在作答。
  - **v2 变差的原因找到了**：秘密记录（例如“心月狐就是苏天晴”）的出处是旁白向读者点破身份的那一章。程序按秘密记录补进这类章的 22 份作答答错 41%，v1 答同样的题只错 10% 到 15%；其余作答 v1、v2 几乎一样。作答者读了揭示章，就把读者知道的写成角色知道的，这正是难题里最多的一类错。对照试验：这 22 份沿用原来挑的章，只去掉秘密记录补的章，重答后答错从 9 份降到 5 份，没有一份变差；v2 一审答错回到 19.6%，和 v1 的 18.5% 持平。剩下 5 份在最难的知情题上，只给第 66 到 71 章也照样把读者知道的写成角色知道的。
  - **全读仍然最好。** 一审答错：全读 13.1%，V9 图直接作答 16.7%，只搜原文 19.0%，挑章 v1 18.5%、v2 去掉秘密章后 19.6%，V8 图 20.2%；二审也是全读最低。本书 100 章以内，没有一种用图的做法胜过一次性全读。图当目录、读整章的好处是篇幅再长也只读 20 章以内，不是更准。
  - **难题**：五组 15 份里错 8 份以上的 8 道题，多数是真正的阅读难点（分清谁知道什么、隔章才揭晓、几十章外的数字推算），全读也错，应该留着。两处要开发者定：强烈暗示、原文没明说的推断写成明说算不算答错（E25、B24，五组共 11 份因此判错）；C23 要不要拆成三问。
  - 第三轮约 30 元，t34 三轮合计约 126 元。
- 建议下一步（待开发者定）：
  - **挑章到此为止。** 挑全以后剩下的错出在作答，再改挑章最多回到 v1 的水平。若保留“图当目录、读整章”，按记录补章时不补秘密记录的出处章。
  - **D：专门治“读者知道的当成角色知道的”**（推荐）。这是各组共同的最大错因，全读也犯，而且不管用不用图，产品作答都会遇到。做法：作答规则里写明“某角色知道某事”必须指出这个角色在场、被告知或自己推断的段落，旁白向读者的揭示不算；只在知情、身份类的题上，用全读和图当目录两组各答三次，单独一审，看这类题的答错是否下降。约 10 元、两小时。
  - **E：停在这里，转向立 Spec。** 结论写成：一次放得进的篇幅用全读；放不下时用图当目录、读整章，答案只凭原文。图的准确性和抽取费用已经有数，评测再加轮次也分不出三个百分点以内的差别。

### 12.11 能不能用起来（2026-10-13）

开发者 2026-10-13 定下转向立 Spec（E），同时按 D 改作答规则（D 的结果见 t34 第四轮），并问两件事：这个图对人梳理剧情有没有帮助；能不能做成初步的产品。

**结论：可以做一个范围收窄的第一版。主要价值是给人看，其次是长篇里给 Agent 当目录。立 Spec 之前有四件事要开发者定，另有两个工程问题要在第一版里解决或限定范围。**

给人看：

- 图里记的正是人读长篇时最难记住的东西：每个对象的全部称呼和首次出现（苏天晴有 45 个称呼）；11 个秘密在每个阅读位置上谁知道、谁不知道；神典石等数值的逐笔流水和余额；257 个悬念从提出到解答；按故事先后排的时间线；每章的情节和在场者。每条记录都带原文出处，点开就能核对；把“读到第几章”往前拨，后文的内容不会提前出现。
- 前 100 章的自动抽取结果已做成离线页面 `.agents/works/w00005-novel-understanding-spike/tasks/t34-v9-100ch/evidences/viewer-v9-100ch.html`（双击打开，约 2.9 MB，不联网）。自动浏览器检查逐个打开了 9 个页签、对象详情和原文段落，页面报错 0、联网请求 0。
- **这一点还没有验证过**：评测只测了问答，查看器开发者还没有人工看过。要靠开发者翻一遍页面来判断。
- 页面上能看到的质量问题：对象分类粗（南嘉鱼本人被归成“化身”，舍友、导购员和主角并列在人物名册里）；称呼有张冠李戴（南嘉鱼的称呼里混进了“天晴”）；身份合并有错（第 93 章“完美使魔是心月狐的替身”被当成同一人，苏天晴的同一身份里于是出现了完美使魔）；知情记录偶有把嘴上的否认当真。给人看时要标明“自动抽取，以原文为准”。

给 Agent：100 章以内全读最准，重复提问命中缓存时也最便宜；图的作用是篇幅放不进一次请求时当目录（读整章、不补秘密记录的出处章）。几百章的场景还没有测过。

D 的结果（t34 第四轮，约 9 元）：作答规则 v5 写明哪些写法只说明读者知道、角色知道要指得出哪种段落。在 16 道知情、身份题上，图当目录的二审答错从 41.7% 降到 25.0%，和全读（v4 33.3%、v5 29.2%）持平；全读的变化在波动之内。副作用是偏保守：角色靠猜测或情境推断知道的（H24），v5 下更常写成“原文没有表明他知道”。产品问答两种做法都用 v5；规则里再补一句“角色自己的猜测、按当时情境能推出的，写成推断他知道并给出段落”，等产品问答用 t34 的题回归时一起测。v5 对另外 40 题的影响没有测。

工程问题：

1. **费用随篇幅增长。** 每章抽取都要带上全部“已有记录”，第 100 章时有 5.7 万字，单章费用从 0.17 元涨到 0.29 元。照此粗算，300 章约 110 元，1000 章约 900 元（按 deepseek-flash 低谷价），离每百万字 7 到 14 元的目标很远。要支持长书，抽取时只带与本章相关的已有记录，这是第一版必须做的改动。
2. **速度。** 逐章串行，每章约 4.5 分钟，100 章约 7.5 小时，只能后台跑、断点续跑。
3. **模型。** 所有抽取都是用 gpt-6-luna 跑的，费用只是按 deepseek-flash 的价格折算；换成产品实际使用的模型要重测质量。
4. **改稿。** 管线只会往后追加。改了前面的章，要从那一章重抽到最后，费用和时间都随章数增长。

立 Spec 之前要开发者定的事：

1. **第一版给谁用**：拆书（导入别人的书，只读）、写自己的书（会改稿），还是两者都要。只做拆书就不用处理改稿。
2. **第一版做哪几样**：建议做查看器（给人看）和“图当目录”的问答工具（给 Agent，用于长篇）；人工修正记录先不做，只标明自动抽取。
3. **和现有 `packages/nb-memory` 的关系**：那是另一套记忆框架（Task 113 的产物），没有接入主应用。V9 是取代它，还是另起一个包。
4. **先把 w00005 落到主线**：master 上只有 t01 到 t03；t04 到 t10 已提交在分支 `feat/w00005-v6-ingest-viewer` 上（已推送，没有合入）；t11 到 t34、本提案、抽取管线和查看器都还没有提交。分支落后 master 700 多个提交，Task 目录连同实验产物约 3.2 GB。Spec 和产品 Work 要引用的东西得先进 master。建议只提交提案、各 Task 的 README、脚本和关键的小证据，大实验产物不提交。master 的 `docs/specs/` 现在没有记忆相关的分区，Spec 放在哪里也要一起定。
